Node.js Best Practices Guide

A comprehensive guide compiled from industry best practices for developing Node.js applications. This guide covers all aspects of Node.js development from project structure to production deployment.

Table of Contents​

  1. Project Structure
  2. Error Handling
  3. Code Style Practices
  4. Testing and Quality
  5. Production Best Practices
  6. Security
  7. Performance
  8. Docker Best Practices

1. Project Structure​

1.1 Structure Your Solution by Components​

One Paragraph Explainer

For medium-sized apps and above, non-modular monoliths are really bad - having one big software with 'spaghetti' of dependencies is just hard to reason about. The ultimate solution is to develop smaller software: divide the whole stack into self-contained components that don't share files with others, each is a standalone logical app (e.g., has its own API, service, data access, test, etc.) so that onboarding into it and changing the code is much easier than dealing with the whole system.

✅ Good: Structure your solution by self-contained components

my-system
├─ apps (components)
│  ├─ orders
│  │ ├─ package.json
│  │ ├─ api
│  │ ├─ domain
│  │ ├─ data-access
│  ├─ users
│  ├─ payments
├─ libraries (generic cross-component functionality)
│  ├─ logger
│  ├─ authenticator

❌ Bad: Group your files by technical role

my-system
├─ controllers
│  ├─ user-controller.js
│  ├─ order-controller.js
│  ├─ payment-controller.js
├─ services
│  ├─ user-service.js
│  ├─ order-service.js
│  ├─ payment-service.js
├─ models
│  ├─ user-model.js
│  ├─ order-model.js
│  ├─ payment-model.js

1.2 Layer Your Components​

Keep your components simple by creating distinct layers - web layer, service/domain layer, and data access layer. Each layer should have a clear responsibility and be loosely coupled with others.

1.3 Wrap Common Utilities as npm Packages​

In a large app that constitutes a large codebase, cross-cutting-concern utilities like logger, encryption, and other helpers should be wrapped by your own code and exposed as private npm packages. This allows sharing them among multiple codebases and projects.

1.4 Separate Express 'app' and 'server'​

Avoid defining the entire Express app in a single huge file - separate your 'Express' definition to at least two files: the API declaration (app.js) and the networking concerns (WWW). For better structure, locate your API declaration within components.

1.5 Use Environment-Aware, Secure Configuration​

A perfect and flawless configuration setup should ensure:

  • Keys can be read from file AND from environment variable
  • Secrets are kept outside committed code
  • Config is hierarchical for easier findability
  • Validation of config at startup to fail fast

2. Error Handling​

2.1 Use Async-Await or Promises for Async Error Handling​

Handling async errors in callback style is probably the fastest way to hell (a.k.a the pyramid of doom). The best gift you can give to your code is using a reputable promise library or async-await instead which enables a much more compact and familiar code syntax like try-catch.

✅ Good: Using async/await

async function executeAsyncTask() {
  try {
    const result = await someAsyncOperation();
    return result;
  } catch (error) {
    logger.error('Error in executeAsyncTask', error);
    throw error;
  }
}

2.2 Use Only the Built-in Error Object​

Many throw errors as a string or as some custom type – this complicates the error handling logic and the interoperability between modules. Instead, use the built-in Error object or extend it to gain better consistency across modules.

✅ Good: Throwing an Error object

class AppError extends Error {
  constructor(name, httpCode, description, isOperational) {
    super(description);
    Object.setPrototypeOf(this, new.target.prototype);
    this.name = name;
    this.httpCode = httpCode;
    this.isOperational = isOperational;
    Error.captureStackTrace(this);
  }
}

// Usage
throw new AppError('ValidationError', 400, 'Invalid email format', true);

2.3 Distinguish Operational vs Programmer Errors​

Operational errors (e.g., API received an invalid input) refer to known cases where the error impact is fully understood and can be handled thoughtfully. On the other hand, programmer errors (e.g., trying to read an undefined variable) refer to unknown code failures that dictate to gracefully restart the application.

2.4 Handle Errors Centrally, Not Within Middlewares​

Without one dedicated object for error handling, greater are the chances for inconsistent error handling. A single error handler object is responsible for making the error visible, writing to a well-formatted logger, firing metrics, and deciding whether the process should crash.

✅ Good: Centralized error handling

// Error handling middleware
app.use(async (err, req, res, next) => {
  await errorHandler.handleError(err, res);
});

// Centralized error handler
class ErrorHandler {
  async handleError(error, responseStream) {
    await logger.logError(error);
    await fireMonitoringMetric(error);
    await crashIfUntrustedErrorOrSendResponse(error, responseStream);
  }
}

export const handler = new ErrorHandler();

2.5 Document API Errors Using Swagger/OpenAPI​

Let your API callers know which errors might come in return so they can handle these thoughtfully without crashing. Use API documentation frameworks like Swagger to document errors.

2.6 Exit the Process Gracefully When a Stranger Comes to Town​

When an unknown error occurs (a developer error), there is uncertainty about the application healthiness. A common practice suggests restarting the process carefully using a process management tool like PM2 or Kubernetes.

2.7 Use a Mature Logger​

A mature logger like Winston or Pino increases error visibility using features like log levels, pretty colorization, and more. Avoid console.log in production.

2.8 Test Error Flows Using Your Favorite Test Framework​

Whether professional automated QA or manual developer testing – ensure that your code not only satisfies positive scenarios but also handles and returns the right errors.

2.9 Catch Unhandled Promise Rejections​

Any exception thrown within a promise will get swallowed and discarded unless a developer didn't forget to explicitly handle it. Overcome this by registering to the event unhandledRejection.

process.on('unhandledRejection', (reason, promise) => {
  logger.error('Unhandled Rejection at:', promise, 'reason:', reason);
  // Application specific logging, throwing an error, or other logic here
});

2.10 Fail Fast, Validate Arguments Using a Dedicated Library​

Assert API input to avoid nasty bugs that are much harder to track later. Validation code is usually tedious unless you use modern validation libraries like Joi, Yup, or Zod.

3. Code Style Practices​

3.1 Use ESLint and Prettier​

ESLint is the de-facto standard for checking possible code errors and fixing code style. Prettier is a powerful code formatter that focuses on consistent formatting. Together they provide a solid foundation for consistent code quality.

Integrating ESLint and Prettier

Use packages like eslint-config-prettier and eslint-plugin-prettier to integrate both tools seamlessly.

{
  "extends": ["eslint:recommended", "plugin:prettier/recommended"],
  "plugins": ["prettier"],
  "rules": {
    "prettier/prettier": "error"
  }
}

3.2 Node.js Specific Plugins​

Use Node.js specific ESLint plugins like eslint-plugin-node to catch Node.js-specific issues and anti-patterns.

3.3 Start Code Blocks' Curly Braces on the Same Line​

The opening curly braces of a code block should be on the same line as the opening statement.

// ✅ Good
function someFunction() {
  // code
}

// ❌ Bad
function someFunction() {
  // code
}

3.4 Don't Forget the Semicolon​

While the JavaScript community debates about semicolons, the truth is that they make your code more predictable and explicit. Use them consistently.

3.5 Name Your Functions​

Name all functions, including closures and callbacks. Avoid anonymous functions as they make debugging and profiling much harder.

// ✅ Good
const fetchUser = async (userId) => {
  // implementation
};

// ❌ Bad
const user = await ((userId) => {
  // implementation
})(123);

3.6 Use Naming Conventions for Variables, Constants, Functions, and Classes​

  • Use lowerCamelCase for variables and functions
  • Use UPPER_SNAKE_CASE for constants
  • Use UpperCamelCase for classes
  • Use descriptive names

3.7 Prefer const over let. Ditch the var​

Using const means that once a variable is assigned, it cannot be reassigned. This leads to more predictable code and easier refactoring.

4. Testing and Quality​

4.1 Structure Tests by the AAA Pattern​

Structure your tests with the Arrange-Act-Assert pattern for maximum readability:

✅ Good: AAA Pattern

describe('Customer classifier', () => {
  test('When customer spent more than 500$, should be classified as premium', () => {
    // Arrange
    const customerToClassify = { spent: 505, joined: new Date(), id: 1 };
    const DBStub = sinon.stub(dataAccess, 'getCustomer').reply({ id: 1, classification: 'regular' });

    // Act
    const receivedClassification = customerClassifier.classifyCustomer(customerToClassify);

    // Assert
    expect(receivedClassification).toMatch('premium');
  });
});

4.2 Name Tests with 3 Parts​

Test names should include:

  1. What is being tested
  2. Under what circumstances
  3. What is the expected result
// ✅ Good
describe('ProductService', () => {
  describe('addProduct', () => {
    test('When adding a valid product, should return success', () => {
      // test implementation
    });
  });
});

4.3 Avoid Global Test Fixtures and Seeds​

Each test should be independent and should not rely on global state or fixtures that could be modified by other tests.

4.4 Constantly Inspect for Vulnerable Dependencies​

Use tools like npm audit, Snyk, or WhiteSource to continuously monitor your dependencies for known vulnerabilities.

4.5 Tag Your Tests​

Tag tests by categories like #cold #api #sanity so you can run specific subsets when needed:

describe('#api #sanity Customer API', () => {
  // tests
});

4.6 Check Test Coverage​

Aim for at least 80% code coverage, but remember that coverage is not a goal by itself – focus on testing critical paths.

4.7 Use Mutation Testing​

Tools like Stryker can help verify that your tests actually test the logic by introducing small changes (mutations) to your code.

4.8 Refactoring is Part of Testing​

Clean code and refactoring are essential parts of the testing process. Keep your code maintainable.

4.9 Mock External Services​

Use tools like nock, sinon, or testcontainers to mock external HTTP calls, databases, and other services.

4.10 Test Five Possible Outcomes​

Every unit test should verify one of these five outcomes:

  1. Return value
  2. State change
  3. Interaction with collaborators
  4. Exception thrown
  5. Performance/timing

5. Production Best Practices​

5.1 Monitoring​

At the very basic level, monitoring means you can easily identify when bad things happen at production. Monitor:

  • CPU usage
  • Server RAM
  • Node process RAM (less than 1.4GB)
  • Number of errors in the last minute
  • Number of process restarts
  • Average response time

Popular tools: Datadog, New Relic, Prometheus, Grafana, CloudWatch, StackDriver

5.2 Increase Transparency Using Smart Logging​

Logs should tell a story and include:

  • Timestamp
  • Log level (error, warn, info, debug)
  • Correlation ID (transaction ID)
  • Contextual information
  • Stack traces for errors

✅ Good: Structured logging

logger.info('User logged in', {
  userId: user.id,
  email: user.email,
  timestamp: new Date(),
  ip: req.ip,
  correlationId: req.id,
});

5.3 Delegate Anything Possible to a Reverse Proxy​

Let a reverse proxy (Nginx, HAProxy, AWS ELB) handle:

  • SSL termination
  • Compression
  • Static file serving
  • Load balancing
  • Rate limiting

5.4 Lock Dependencies​

Use package-lock.json or yarn.lock to ensure consistent installations across environments.

5.5 Guard Process Uptime Using Process Managers​

Use a process manager like PM2, Forever, or systemd to:

  • Restart the app when it crashes
  • Provide insights into runtime performance
  • Modify settings without downtime

5.6 Utilize All CPU Cores​

Node.js runs in a single thread by default. Use the cluster module or PM2 to spawn multiple processes:

const cluster = require('cluster');
const numCPUs = require('os').cpus().length;

if (cluster.isMaster) {
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }
} else {
  // Start the app
  require('./app');
}

5.7 Create a Maintenance Endpoint​

Expose a set of system-related information like memory usage, uptime, and whether the service is healthy:

app.get('/health', (req, res) => {
  res.json({
    status: 'healthy',
    uptime: process.uptime(),
    memory: process.memoryUsage(),
    version: process.version,
  });
});

5.8 Set NODE_ENV=production​

Setting NODE_ENV=production triggers performance optimizations in many frameworks and libraries.

NODE_ENV=production node app.js

5.9 Design Automated, Atomic, and Zero-Downtime Deployments​

Deployments should be:

  • Automated via CI/CD
  • Atomic (all-or-nothing)
  • Zero-downtime (rolling updates, blue-green deployments)

5.10 Use an LTS Release of Node.js​

Stick to LTS (Long Term Support) versions of Node.js for production environments for stability and security updates.

5.11 Don't Route Logs Within the App​

Don't write logs with your application code to files or databases. Instead, write to stdout and let the environment handle log routing (using Docker, systemd, or logging agents).

5.12 Install Your Packages with npm ci​

Use npm ci in CI/CD pipelines for faster, more reliable, and reproducible builds:

npm ci --only=production

5.13 Measure and Guard Memory Usage​

Monitor memory usage and set limits to prevent memory leaks from crashing your application:

// Set max memory for Node.js
node --max-old-space-size=4096 app.js

5.14 Be Stateless, Kill Your Servers Almost Every Day​

Modern cloud-native applications should be stateless. Store session data in Redis or a database, not in server memory.

5.15 Assign a Transaction ID to Each Log Statement​

Assign a unique identifier to each transaction/request to track the flow through logs:

const { v4: uuidv4 } = require('uuid');

app.use((req, res, next) => {
  req.id = uuidv4();
  next();
});

6. Security​

6.1 Validate Incoming JSON Schemas​

Validate all incoming request payloads using libraries like Joi, Yup, or JSON Schema:

✅ Good: Using Joi for validation

const Joi = require('joi');

const userSchema = Joi.object({
  email: Joi.string().email().required(),
  password: Joi.string().min(8).required(),
  age: Joi.number().min(18).max(120),
});

router.post('/users', (req, res) => {
  const { error, value } = userSchema.validate(req.body);
  if (error) {
    return res.status(400).json({ error: error.details[0].message });
  }
  // Process valid data
});

6.2 Use Security-Related Headers​

Use packages like Helmet to set security-related HTTP headers:

const helmet = require('helmet');
app.use(helmet());

This sets headers like:

  • X-Frame-Options
  • X-Content-Type-Options
  • Strict-Transport-Security
  • Content-Security-Policy

6.3 Avoid Using the JavaScript eval Function​

Never use eval(), new Function(), setTimeout(string), or setInterval(string) with user input as they can lead to code injection.

6.4 Prevent Query Injection with ORM/ODM Libraries​

Use ORM/ODM libraries like Sequelize, TypeORM, or Mongoose with parameterized queries:

// ✅ Good: Parameterized query
const user = await User.findOne({ where: { email: req.body.email } });

// ❌ Bad: String concatenation
const query = `SELECT * FROM users WHERE email = '${req.body.email}'`;

6.5 Limit Concurrent Requests Using Middleware​

Use rate limiting to prevent DDoS and brute force attacks:

const rateLimit = require('express-rate-limit');

const limiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // limit each IP to 100 requests per windowMs
});

app.use('/api/', limiter);

6.6 Extract Secrets from Config Files​

Never commit secrets to source control. Use environment variables or secret management services:

// ✅ Good
const dbPassword = process.env.DB_PASSWORD;

// ❌ Bad
const dbPassword = 'mySecretPassword123';

6.7 Prevent Brute-Force Attacks Against Authorization​

Implement rate limiting specifically for login endpoints:

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5, // 5 login attempts
  skipSuccessfulRequests: true,
});

app.post('/login', loginLimiter, loginHandler);

6.8 Run Node.js as a Non-Root User​

Always run your Node.js process as a non-privileged user:

# In Dockerfile
USER node

6.9 Limit Payload Size​

Limit the size of incoming request bodies to prevent large payload attacks:

app.use(express.json({ limit: '10kb' }));

6.10 Escape HTML, JS, and CSS Output​

Sanitize user input before rendering to prevent XSS attacks:

const escape = require('escape-html');

app.get('/user/:id', async (req, res) => {
  const user = await getUser(req.params.id);
  res.send(`<h1>Hello ${escape(user.name)}</h1>`);
});

6.11 Validate Incoming JSON Schemas​

Already covered in 6.1 – this is critical enough to emphasize again!

6.12 Support Blacklisting JWTs​

Implement token revocation for logout and security breaches:

const blacklistedTokens = new Set();

app.post('/logout', (req, res) => {
  const token = req.headers.authorization?.split(' ')[1];
  blacklistedTokens.add(token);
  res.json({ message: 'Logged out successfully' });
});

6.13 Prevent Unsafe Redirects​

Validate redirect URLs to prevent open redirect vulnerabilities:

const allowedDomains = ['myapp.com', 'api.myapp.com'];

app.get('/redirect', (req, res) => {
  const url = new URL(req.query.url);
  if (!allowedDomains.includes(url.hostname)) {
    return res.status(400).send('Invalid redirect URL');
  }
  res.redirect(req.query.url);
});

6.14 Avoid Publishing Secrets to the npm Registry​

Use .npmignore or files in package.json to prevent accidentally publishing secrets:

{
  "files": ["dist", "lib"]
}

6.15 Use Security Linter Rules​

Enable security-focused ESLint plugins:

{
  "extends": ["plugin:security/recommended"],
  "plugins": ["security"]
}

6.16 Adjust the HTTP Response Headers for Enhanced Security​

Already covered in 6.2 with Helmet.

6.17 Constantly and Automatically Inspect for Vulnerable Dependencies​

Automate dependency checking in CI/CD:

npm audit

6.18 Hide Error Details from Clients​

Don't expose stack traces or internal errors to clients:

app.use((err, req, res, next) => {
  logger.error(err.stack);
  res.status(500).json({
    message: 'An error occurred',
    // Don't send: stack: err.stack
  });
});

6.19 Configure Secure Session Cookies​

Set secure cookie options:

app.use(
  session({
    secret: process.env.SESSION_SECRET,
    cookie: {
      secure: true, // HTTPS only
      httpOnly: true, // Not accessible via JS
      sameSite: 'strict',
      maxAge: 24 * 60 * 60 * 1000, // 24 hours
    },
  }),
);

6.20 Secure Child Processes​

When spawning child processes, validate and sanitize input:

const { execFile } = require('child_process');

// ✅ Good: Using execFile with array arguments
execFile('ls', ['-l', userInput], (error, stdout) => {
  // ...
});

// ❌ Bad: Using exec with string interpolation
exec(`ls -l ${userInput}`, (error, stdout) => {
  // Vulnerable to command injection!
});

6.21 Use Sandbox Environments​

Use VM modules or containers to isolate untrusted code execution.

6.22 Handle User Passwords with Care​

  • Never store passwords in plain text
  • Use bcrypt or argon2 for hashing
  • Enforce strong password policies
  • Implement account lockout after failed attempts
const bcrypt = require('bcrypt');
const saltRounds = 12;

const hashedPassword = await bcrypt.hash(plainPassword, saltRNumbers);
const isValid = await bcrypt.compare(inputPassword, hashedPassword);

7. Performance​

7.1 Prefer Native JS Methods Over User-Land Utils Like Lodash​

Native JavaScript methods are often faster and don't add dependencies. Modern ES6+ provides many utilities that Lodash used to fill:

Performance Comparison

// Native is ~50% faster on average
// ✅ Good: Native
const doubled = array.map((x) => x * 2);

// ❌ Slower: Lodash (unnecessary for simple operations)
const doubled = _.map(array, (x) => x * 2);

7.2 Don't Block the Event Loop​

Avoid CPU-intensive operations in the main thread:

✅ Good: Offload to worker threads

const { Worker } = require('worker_threads');

function runHeavyTask(data) {
  return new Promise((resolve, reject) => {
    const worker = new Worker('./heavy-task.js', { workerData: data });
    worker.on('message', resolve);
    worker.on('error', reject);
  });
}

❌ Bad: Blocking the event loop

// Don't do this!
function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2); // Blocks for large n
}

7.3 Use Caching​

Implement caching strategies at multiple levels:

const Redis = require('redis');
const client = Redis.createClient();

async function getUser(id) {
  // Try cache first
  const cached = await client.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  // Fetch from database
  const user = await db.users.findById(id);

  // Cache for 1 hour
  await client.setex(`user:${id}`, 3600, JSON.stringify(user));

  return user;
}

7.4 Use Gzip Compression​

Enable compression middleware:

const compression = require('compression');
app.use(compression());

7.5 Use Connection Pooling​

Reuse database connections:

const { Pool } = require('pg');

const pool = new Pool({
  max: 20,
  connectionTimeoutMillis: 2000,
  idleTimeoutMillis: 30000,
});

8. Docker Best Practices​

8.1 Use Multi-Stage Builds​

Separate build and runtime environments to reduce image size:

# Build stage
FROM node:18 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Runtime stage
FROM node:18-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY package*.json ./

USER node
EXPOSE 3000
CMD ["node", "dist/index.js"]

8.2 Use .dockerignore​

Exclude unnecessary files from your Docker context:

node_modules
npm-debug.log
.git
.env
*.md
tests
coverage
.vscode

8.3 Run as Non-Root User​

FROM node:18-alpine
USER node
WORKDIR /home/node/app

8.4 Optimize Layer Caching​

Order Dockerfile commands from least to most frequently changing:

# ✅ Good order
COPY package*.json ./
RUN npm ci
COPY . .

8.5 Install Only Production Dependencies​

RUN npm ci --only=production

8.6 Use Specific Image Tags​

# ✅ Good: Specific version
FROM node:18.17.0-alpine3.18

# ❌ Bad: Latest tag
FROM node:latest

8.7 Scan Images for Vulnerabilities​

docker scan my-image:latest
# or
trivy image my-image:latest

8.8 Set Memory Limits​

# In Dockerfile
ENV NODE_OPTIONS="--max-old-space-size=2048"

# Or in docker run
docker run --memory="512m" my-app

8.9 Use Bootstrap with Node Process​

CMD ["node", "index.js"]
# Not: CMD ["npm", "start"]

8.10 Implement Graceful Shutdown​

process.on('SIGTERM', () => {
  console.log('SIGTERM received, closing server gracefully');
  server.close(() => {
    console.log('Server closed');
    process.exit(0);
  });
});

8.11 Avoid Build-Time Secrets​

Use multi-stage builds and build arguments carefully:

# ✅ Good: Secret not in final image
ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc && \
    npm ci && \
    rm -f .npmrc

8.12 Lint Your Dockerfile​

Use hadolint to check Dockerfile best practices:

docker run --rm -i hadolint/hadolint < Dockerfile

8.13 Use Smaller Base Images​

# ✅ Better: Alpine (much smaller)
FROM node:18-alpine

# ❌ Larger: Full Debian-based image
FROM node:18

8.14 Clean npm Cache​

RUN npm ci --only=production && \
    npm cache clean --force

Conclusion​

Following these Node.js best practices will help you build:

  • Maintainable applications with clear structure
  • Secure systems that protect against common vulnerabilities
  • Performant services that scale effectively
  • Reliable production deployments
  • Testable code with high quality

Remember that best practices evolve over time. Stay updated with the Node.js community, regularly update dependencies, and continuously review and improve your codebase.
