Security Basics: IAM, Encryption, and Compliance

Overview​

This comprehensive guide covers fundamental security concepts essential for cloud infrastructure, including Identity and Access Management (IAM), encryption strategies, and compliance frameworks. Understanding these security basics is critical for building secure, compliant, and trustworthy systems.

Identity and Access Management (IAM)​

IAM Fundamentals​

Core IAM Concepts​

The Three Elements of IAM

Who (Principal):
  - User accounts (humans)
  - Service accounts (applications)
  - Groups (collections of users)
  - Domains (entire organization)

What (Permissions):
  - Actions that can be performed
  - Operations on resources
  - API methods

Which (Resources):
  - Cloud resources (VMs, databases, storage)
  - Projects, folders, organizations
  - Specific assets

IAM Policies​

Policy Structure

{
  "bindings": [
    {
      "role": "roles/storage.objectViewer",
      "members": [
        "user:alice@example.com",
        "serviceAccount:my-app@project.iam.gserviceaccount.com",
        "group:developers@example.com"
      ],
      "condition": {
        "title": "Expires in 2024",
        "description": "Access expires at end of 2024",
        "expression": "request.time < timestamp('2024-12-31T23:59:59Z')"
      }
    },
    {
      "role": "roles/storage.admin",
      "members": ["user:admin@example.com"]
    }
  ],
  "etag": "BwXhFgH0YO4=",
  "version": 3
}

IAM Roles​

Role Types

Primitive Roles (Basic):
  Owner: Full control over all resources
    - Can manage permissions
    - Can delete resources
    - Full administrative access

  Editor: Modify/delete existing resources
    - Cannot manage permissions
    - Can create, modify, delete resources

  Viewer: Read-only access
    - View resources
    - Cannot modify anything

Predefined Roles (Curated):
  Purpose: Specific job functions
  Examples:
    - roles/compute.admin: Full control of Compute Engine
    - roles/storage.objectViewer: Read objects in Cloud Storage
    - roles/cloudsql.client: Connect to Cloud SQL instances
    - roles/container.developer: Deploy to GKE clusters

  Benefits:
    - Least privilege by default
    - Maintained by cloud provider
    - Regularly updated with new permissions

Custom Roles (User-defined):
  Purpose: Tailored permissions
  Use Cases:
    - Organization-specific requirements
    - Fine-grained access control
    - Combination of specific permissions

  Limitations:
    - Cannot be used at folder level (GCP)
    - Requires maintenance
    - More complex to manage

Service Accounts​

What are Service Accounts?

Definition: Special accounts for applications/services (not humans)

Use Cases:
  - Application authentication
  - Service-to-service communication
  - Automated processes
  - CI/CD pipelines
  - Kubernetes workloads

Types:
  User-Managed:
    - Created by users
    - Full control over lifecycle
    - Custom naming

  Google-Managed:
    - Created automatically by GCP
    - Used by Google services
    - Cannot be deleted by users

  Default Service Accounts:
    - Compute Engine default
    - App Engine default
    - Created when enabling APIs

Service Account Best Practices

Security Best Practices:
  1. Principle of Least Privilege:
    - Grant minimal permissions needed
    - Use predefined roles when possible
    - Regularly audit permissions

  2. Service Account Keys:
    - Avoid downloading keys when possible
    - Use Workload Identity (GKE)
    - Rotate keys regularly (90 days)
    - Store securely (Secret Manager)

  3. Service Account Isolation:
    - One service account per application
    - Separate dev/staging/prod accounts
    - Different accounts for different environments

  4. Monitoring and Auditing:
    - Enable audit logging
    - Monitor service account usage
    - Alert on suspicious activity

GCP Service Account Management

# Create service account
gcloud iam service-accounts create my-app-sa \
  --display-name="My Application Service Account" \

# List service accounts
gcloud iam service-accounts list

gcloud projects add-iam-policy-binding my-project \

gcloud compute instances list \
  --impersonate-service-account=my-app-sa@my-project.iam.gserviceaccount.com

# Delete service account
gcloud iam service-accounts delete \
  my-app-sa@my-project.iam.gserviceaccount.com

Workload Identity (GKE)​

What is Workload Identity?

Purpose: Secure way for GKE pods to access GCP services
Benefits:
  - No service account keys needed
  - Automatic credential rotation
  - Fine-grained access control
  - Improved security posture

How it works: 1. Kubernetes Service Account (KSA) created in cluster
  2. GCP Service Account (GSA) created in project
  3. KSA bound to GSA via IAM policy
  4. Pods use KSA to authenticate as GSA

Workload Identity Setup

# Enable Workload Identity on cluster
gcloud container clusters create my-cluster \
  --workload-pool=my-project.svc.id.goog \
  --region=us-central1

# Or update existing cluster
gcloud container clusters update my-cluster \
  --workload-pool=my-project.svc.id.goog \
  --region=us-central1

# Create Kubernetes service account
kubectl create serviceaccount my-ksa -n my-namespace

# Create GCP service account
gcloud iam service-accounts create my-gsa \
  --display-name="My GSA for Workload Identity"

# Grant IAM permissions to GSA
gcloud projects add-iam-policy-binding my-project \
  --member="serviceAccount:my-gsa@my-project.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

# Bind KSA to GSA
gcloud iam service-accounts add-iam-policy-binding \
  my-gsa@my-project.iam.gserviceaccount.com \
  --role=roles/iam.workloadIdentityUser \
  --member="serviceAccount:my-project.svc.id.goog[my-namespace/my-ksa]"

# Annotate Kubernetes service account
kubectl annotate serviceaccount my-ksa \
  -n my-namespace \
  iam.gke.io/gcp-service-account=my-gsa@my-project.iam.gserviceaccount.com

Kubernetes Deployment with Workload Identity

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: my-namespace
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      serviceAccountName: my-ksa # Use KSA with Workload Identity
      containers:
        - name: app
          image: gcr.io/my-project/my-app:latest
          env:
            - name: GOOGLE_APPLICATION_CREDENTIALS
              value: /var/secrets/google/key.json # Not needed with Workload Identity
          # Application will automatically use Workload Identity
          # No need to mount service account key files

IAM Conditions​

Conditional Access Control

Purpose: Add context-aware access control
Conditions Based On:
  - Time/Date
  - IP address
  - Resource attributes
  - Request attributes

Common Use Cases:
  - Temporary access
  - Location-based access
  - Resource-specific access
  - Time-based restrictions

Resource Hierarchy and IAM Inheritance​

Inheritance Example

Organization Level:
  - user:ceo@example.com → roles/owner
  - group:security-team@example.com → roles/securityReviewer

  Inherited by ALL folders, projects, and resources

Folder Level (Production):
  - group:prod-admins@example.com → roles/editor

  Inherited by projects: prod-app, prod-data
  NOT inherited by: dev-app

Project Level (prod-app):
  - serviceAccount:app-sa@prod-app.iam.gserviceaccount.com → roles/storage.admin

  Applies only to resources in prod-app project

Resource Level (GCS Bucket):
  - user:analyst@example.com → roles/storage.objectViewer

  Applies only to this specific bucket

Effective Permissions:
  CEO: Full access everywhere (from organization)
  Prod Admin: Edit access to prod-app and prod-data (from folder)
  App SA: Storage admin only in prod-app project
  Analyst: View objects only in specific bucket

Encryption​

Encryption Fundamentals​

Encryption at Rest​

What is Encryption at Rest?

Definition: Protection of data stored on disk/storage

Protects Against:
  - Physical theft of disks
  - Unauthorized access to storage
  - Data breaches from stolen backups
  - Insider threats

Methods:
  - Full disk encryption
  - Database encryption
  - File-level encryption
  - Application-level encryption

GCP Encryption at Rest

Default Encryption:
  - All data encrypted by default
  - Google-managed encryption keys (GMEK)
  - AES-256 encryption
  - No configuration needed
  - No additional cost

Customer-Managed Encryption Keys (CMEK):
  - Customer controls key lifecycle
  - Use Cloud KMS
  - Key rotation policies
  - Audit logging
  - Regional/multi-regional keys

Customer-Supplied Encryption Keys (CSEK):
  - Customer provides encryption keys
  - Keys never stored by Google
  - Customer fully responsible for key management
  - Used with each API request

Cloud KMS (Key Management Service)

# Create key ring
gcloud kms keyrings create my-keyring \
  --location=us-central1

# Create encryption key
gcloud kms keys create my-key \
  --location=us-central1 \
  --keyring=my-keyring \
  --purpose=encryption

# Create key with automatic rotation (90 days)
gcloud kms keys create my-rotating-key \
  --location=us-central1 \
  --keyring=my-keyring \
  --purpose=encryption \
  --rotation-period=90d \
  --next-rotation-time=2024-03-01T00:00:00Z

# List keys
gcloud kms keys list \
  --location=us-central1 \
  --keyring=my-keyring

# Encrypt data
echo "sensitive data" | gcloud kms encrypt \
  --location=us-central1 \
  --keyring=my-keyring \
  --key=my-key \
  --plaintext-file=- \
  --ciphertext-file=encrypted.dat

# Decrypt data
gcloud kms decrypt \
  --location=us-central1 \
  --keyring=my-keyring \
  --key=my-key \
  --ciphertext-file=encrypted.dat \
  --plaintext-file=-

# Grant permission to use key
gcloud kms keys add-iam-policy-binding my-key \
  --location=us-central1 \
  --keyring=my-keyring \
  --member=serviceAccount:my-sa@project.iam.gserviceaccount.com \
  --role=roles/cloudkms.cryptoKeyEncrypterDecrypter

# Create Cloud Storage bucket with CMEK
gcloud storage buckets create gs://my-encrypted-bucket \
  --location=us-central1 \
  --default-encryption-key=projects/my-project/locations/us-central1/keyRings/my-keyring/cryptoKeys/my-key

# Create Compute Engine disk with CMEK
gcloud compute disks create my-encrypted-disk \
  --size=100GB \
  --zone=us-central1-a \
  --kms-key=projects/my-project/locations/us-central1/keyRings/my-keyring/cryptoKeys/my-key

Envelope Encryption

How it works:
  1. Data Encryption Key (DEK):
     - Generated for each data object
     - Used to encrypt the actual data
     - Symmetric key (AES-256)

  2. Key Encryption Key (KEK):
     - Stored in Cloud KMS
     - Used to encrypt the DEK
     - Customer-managed or Google-managed

  3. Encrypted DEK stored with data
  4. KEK never leaves KMS

Benefits:
  - Performance: Local encryption with DEK
  - Security: KEK protected in HSM
  - Scalability: New DEK for each object
  - Key rotation: Only KEK needs rotation

Example Flow:
  Encrypt:
    plaintext → encrypt with DEK → ciphertext
    DEK → encrypt with KEK → encrypted DEK
    Store: ciphertext + encrypted DEK

  Decrypt:
    encrypted DEK → decrypt with KEK → DEK
    ciphertext → decrypt with DEK → plaintext

Encryption in Transit​

TLS/SSL Encryption

Purpose: Encrypt data moving over network

Protocols:
  TLS 1.2: Minimum recommended version
  TLS 1.3: Latest, most secure version
  SSL: Deprecated, do not use

Components:
  Certificates:
    - Public key certificate
    - Issued by Certificate Authority (CA)
    - Contains domain name, organization
    - Validity period

  Private Key:
    - Kept secret by server
    - Used to decrypt client messages
    - Never shared

TLS Handshake:
  1. Client Hello: Supported cipher suites
  2. Server Hello: Selected cipher suite
  3. Certificate: Server sends certificate
  4. Key Exchange: Establish session keys
  5. Encrypted Communication: All data encrypted

Certificate Management

# Generate private key
openssl genrsa -out private.key 2048

# Generate Certificate Signing Request (CSR)
openssl req -new -key private.key -out certificate.csr \
  -subj "/C=US/ST=CA/L=San Francisco/O=My Company/CN=example.com"

# Generate self-signed certificate (dev/testing only)
openssl x509 -req -days 365 -in certificate.csr \
  -signkey private.key -out certificate.crt

# View certificate details
openssl x509 -in certificate.crt -text -noout

# Test TLS connection
openssl s_client -connect example.com:443 -showcerts

# Check certificate expiration
echo | openssl s_client -connect example.com:443 2>/dev/null | \
  openssl x509 -noout -dates

GCP Certificate Manager

# Create SSL certificate (Google-managed)
gcloud compute ssl-certificates create my-cert \
  --domains=example.com,www.example.com \
  --global

# Create SSL certificate from files
gcloud compute ssl-certificates create my-uploaded-cert \
  --certificate=certificate.crt \
  --private-key=private.key \
  --global

# List SSL certificates
gcloud compute ssl-certificates list

# Describe certificate
gcloud compute ssl-certificates describe my-cert --global

# Delete certificate
gcloud compute ssl-certificates delete my-cert --global

# Use Certificate Manager (new service)

  --location=global

# Create certificate map

  --location=global

# Add certificate to map
gcloud certificate-manager maps entries create my-entry \
  --map=my-cert-map \
  --certificates=my-cert \
  --hostname=example.com \
  --location=global

mTLS (Mutual TLS)

Purpose: Both client and server authenticate each other

Use Cases:
  - Service-to-service communication
  - API authentication
  - Zero-trust networks
  - Microservices security

How it works: 1. Server sends certificate to client
  2. Client verifies server certificate
  3. Client sends certificate to server
  4. Server verifies client certificate
  5. Both sides authenticated

Benefits:
  - Strong authentication
  - No passwords needed
  - Certificate-based trust
  - Automatic encryption

Istio mTLS Configuration

# Enable strict mTLS for namespace
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: my-namespace
spec:
  mtls:
    mode: STRICT # Enforce mTLS for all services

---
# Destination rule to use mTLS
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-mtls
  namespace: my-namespace
spec:
  host: api-service.my-namespace.svc.cluster.local
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL # Use Istio-managed mTLS

---
# Allow specific workloads to communicate
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-frontend
  namespace: my-namespace
spec:
  selector:
    matchLabels:
      app: api-service
  action: ALLOW
  rules:
    - from:
        - source:
            principals:
              - cluster.local/ns/my-namespace/sa/frontend-sa
      to:
        - operation:
            methods: ['GET', 'POST']
            paths: ['/api/*']

Secret Manager (GCP)

# Create secret
echo -n "my-database-password" | \

echo -n "new-password" | \

gcloud secrets versions access latest --secret=db-password

gcloud secrets versions access 1 --secret=db-password

gcloud secrets list

gcloud secrets versions list db-password

gcloud secrets versions disable 1 --secret=db-password

gcloud secrets versions destroy 1 --secret=db-password

gcloud secrets add-iam-policy-binding db-password \

  --role=roles/secretmanager.secretAccessor

# Delete secret
gcloud secrets delete db-password

Kubernetes Secrets with External Secrets Operator

        key: db-password # Secret name in GCP Secret Manager

---
# Use secret in deployment
apiVersion: apps/v1

    matchLabels:

Compliance and Regulatory Frameworks​

Common Compliance Standards​

GDPR (General Data Protection Regulation):
  Region: European Union
  Focus: Personal data privacy
  Key Requirements:
    - Right to access personal data
    - Right to be forgotten
    - Data portability
    - Consent management
    - Data breach notification (72 hours)
    - Data Protection Officer (DPO)

  Penalties: Up to €20M or 4% of global revenue

HIPAA (Health Insurance Portability and Accountability Act):
  Region: United States
  Focus: Healthcare data protection
  Key Requirements:
    - Administrative safeguards
    - Physical safeguards
    - Technical safeguards
    - Encryption of PHI (Protected Health Information)
    - Access controls
    - Audit logging
    - Business Associate Agreements (BAA)

  Penalties: Up to $1.5M per violation category per year

PCI DSS (Payment Card Industry Data Security Standard):
  Region: Global
  Focus: Payment card data security
  Key Requirements:
    - Network security
    - Cardholder data protection
    - Encryption of transmission over public networks
    - Access control
    - Vulnerability management
    - Regular security testing
    - Information security policy

  12 Requirements: 1. Install and maintain firewall
    2. Don't use vendor defaults
    3. Protect stored cardholder data
    4. Encrypt transmission
    5. Use anti-virus software
    6. Develop secure systems
    7. Restrict access by business need
    8. Assign unique ID to each person
    9. Restrict physical access
    10. Track and monitor network access
    11. Regularly test security systems
    12. Maintain information security policy

SOC 2 (Service Organization Control 2):
  Region: Global (primarily US)
  Focus: Service provider controls
  Trust Principles:
    - Security
    - Availability
    - Processing Integrity
    - Confidentiality
    - Privacy

  Types:
    Type I: Controls at a point in time
    Type II: Controls over a period (6-12 months)

ISO 27001:
  Region: Global
  Focus: Information security management
  Key Areas:
    - Information security policies
    - Organization of information security
    - Human resource security
    - Asset management
    - Access control
    - Cryptography
    - Physical and environmental security
    - Operations security
    - Communications security
    - System acquisition/development
    - Supplier relationships
    - Incident management
    - Business continuity
    - Compliance

GCP Compliance Features​

Compliance Resource Hierarchy

Organization Policies

# Require OS Login for all VMs
gcloud resource-manager org-policies enable-enforce \
  compute.requireOsLogin \
  --organization=ORGANIZATION_ID

# Restrict VM external IP addresses
gcloud resource-manager org-policies deny \
  compute.vmExternalIpAccess \
  --organization=ORGANIZATION_ID \
  --all

# Restrict cloud storage to specific locations
gcloud resource-manager org-policies set-policy policy.yaml \
  --organization=ORGANIZATION_ID

# policy.yaml content:
# constraint: constraints/gcp.resourceLocations
# listPolicy:
#   allowedValues:
#   - in:us-locations
#   - in:eu-locations

# Disable service account key creation

Audit Logging and Monitoring​

Cloud Audit Logs

Log Types:
  Admin Activity Logs:
    - API calls that modify configuration
    - Always enabled
    - No charge
    - 400-day retention
    Examples:
      - Creating VMs
      - Changing IAM policies
      - Deleting resources

  Data Access Logs:
    - Reading configuration/metadata
    - Reading/writing user data
    - Disabled by default (except BigQuery)
    - Charges apply
    - 30-day default retention
    Examples:
      - Listing Cloud Storage objects
      - Reading database data
      - Viewing compute instances

  System Event Logs:
    - Google Cloud system events
    - Always enabled
    - No charge
    Examples:
      - Live migration of VMs
      - Automatic key rotation

  Policy Denied Logs:
    - Access denied by security policy
    - Always enabled for VPC SC
    - No charge
    Examples:
      - VPC Service Controls violations
      - Organization policy violations

Enable Data Access Logging

# Get current IAM policy
gcloud projects get-iam-policy my-project \

Data Residency and Sovereignty​

Data Location Controls

Purpose: Ensure data stays in specific geographic locations

Methods:
  1. Resource Location Constraints:
    - Organization policies
    - Restrict to specific regions
    - Enforce at organization/folder/project level

  2. Service-Specific Configuration:
    - Choose regions for resources
    - Multi-region vs single region
    - Regional replication

  3. Network Controls:
    - VPC Service Controls
    - Private Google Access
    - Restricted VIP addresses

Common Requirements:
  GDPR:
    - Data transfer restrictions
    - Data processing agreements
    - Adequate protection level

  China Cybersecurity Law:
    - Data localization requirements
    - Cross-border transfer restrictions

  Russia Data Localization:
    - Store citizen data in Russia
    - Local data centers required

Enforce Data Residency

# Create organization policy for resource locations
cat > resource-locations.yaml <<EOF
constraint: constraints/gcp.resourceLocations
listPolicy:
  allowedValues:
  - in:eu-locations  # Only EU regions
  deniedValues:
  - in:us-locations  # Explicitly deny US
EOF

gcloud resource-manager org-policies set-policy resource-locations.yaml \
  --organization=ORGANIZATION_ID

# For specific projects, use folder-level policies
gcloud resource-manager org-policies set-policy resource-locations.yaml \
  --folder=FOLDER_ID

VPC Service Controls​

Perimeter Security

Purpose: Create security perimeters around GCP resources

Benefits:
  - Prevent data exfiltration
  - Isolate sensitive resources
  - Control API access
  - Enforce private connectivity

Use Cases:
  - Protect sensitive data
  - Comply with data residency
  - Isolate production/dev environments
  - Prevent insider threats

VPC Service Controls Setup

# Create access policy (organization level)
gcloud access-context-manager policies create \
  --organization=ORGANIZATION_ID \
  --title="My Access Policy"

# Get policy name
POLICY_NAME=$(gcloud access-context-manager policies list \
  --organization=ORGANIZATION_ID \
  --format="value(name)")

# Create access level (define who can access)
gcloud access-context-manager levels create high_trust \
  --policy=$POLICY_NAME \
  --basic-level-spec=access-level.yaml

# access-level.yaml:
# combiningFunction: AND
# conditions:
#   - ipSubnetworks:
#     - 10.0.0.0/8  # Corporate network
#     - 172.16.0.0/12
#   - members:
#     - user:admin@example.com
#     - serviceAccount:trusted-sa@project.iam.gserviceaccount.com

# Create service perimeter
gcloud access-context-manager perimeters create my_perimeter \
  --policy=$POLICY_NAME \
  --title="Production Perimeter" \
  --resources=projects/123456789 \
  --restricted-services=storage.googleapis.com,bigquery.googleapis.com \
  --access-levels=high_trust \
  --enable-vpc-accessible-services \
  --vpc-allowed-services=storage.googleapis.com

# Create dry-run mode perimeter (test before enforcing)
gcloud access-context-manager perimeters dry-run enforce \
  my_perimeter \
  --policy=$POLICY_NAME

# Check violations in dry-run
gcloud logging read \
  'protoPayload.metadata."@type"="type.googleapis.com/google.cloud.audit.VpcServiceControlAuditMetadata"'

# Enforce perimeter
gcloud access-context-manager perimeters update my_perimeter \
  --policy=$POLICY_NAME \
  --enable-vpc-accessible-services \
  --clear-dry-run

# Create ingress/egress rules
gcloud access-context-manager perimeters update my_perimeter \
  --policy=$POLICY_NAME \
  --set-ingress-policies=ingress.yaml

# ingress.yaml:
# - ingressFrom:
#     sources:
#     - accessLevel: accessPolicies/POLICY_NAME/accessLevels/high_trust
#     identities:
#     - serviceAccount:external-sa@external-project.iam.gserviceaccount.com
#   ingressTo:
#     operations:
#     - serviceName: storage.googleapis.com
#       methodSelectors:
#       - method: google.storage.objects.get
#     resources:
#     - projects/123456789

Security Best Practices​

Principle of Least Privilege​

Definition: Grant minimum permissions needed to perform a task

Implementation: 1. Start with no access
  2. Add permissions incrementally
  3. Use predefined roles when possible
  4. Create custom roles for specific needs
  5. Regular audit and review
  6. Remove unused permissions

Examples:
  Bad:
    - Grant roles/owner to service account
    - Use default service accounts
    - Share admin credentials

  Good:
    - Grant roles/storage.objectViewer for read-only
    - Create dedicated service accounts
    - Use role-specific accounts
    - Implement MFA for humans

Defense in Depth​

Definition: Multiple layers of security controls

Layers:
  1. Network Security:
    - Firewalls
    - VPC isolation
    - Private subnets
    - Security groups

  2. Identity and Access:
    - IAM policies
    - MFA enforcement
    - Service accounts
    - Workload Identity

  3. Data Protection:
    - Encryption at rest
    - Encryption in transit
    - Secret management
    - Data classification

  4. Application Security:
    - Input validation
    - Output encoding
    - Security headers
    - Dependency scanning

  5. Monitoring and Detection:
    - Audit logging
    - Anomaly detection
    - SIEM integration
    - Alerting

  6. Incident Response:
    - Response playbooks
    - Backup and recovery
    - Disaster recovery plan
    - Post-incident review

Security Checklist​

Infrastructure Security

Network: ✅ Use private subnets for sensitive resources
  ✅ Implement network segmentation
  ✅ Configure firewall rules (deny by default)
  ✅ Enable VPC Flow Logs
  ✅ Use Cloud NAT for outbound traffic
  ✅ Implement DDoS protection (Cloud Armor)

Compute: ✅ Disable default service accounts
  ✅ Use minimal OS images (COS, distroless)
  ✅ Enable OS Login
  ✅ Implement patch management
  ✅ Use confidential VMs for sensitive workloads
  ✅ Enable Secure Boot and vTPM

Storage: ✅ Enable encryption at rest (CMEK)
  ✅ Implement access controls (IAM)
  ✅ Enable versioning for critical data
  ✅ Configure lifecycle policies
  ✅ Use signed URLs for temporary access
  ✅ Enable audit logging

Kubernetes/GKE: ✅ Enable Workload Identity
  ✅ Use private clusters
  ✅ Implement network policies
  ✅ Enable Binary Authorization
  ✅ Use Pod Security Standards
  ✅ Configure RBAC properly
  ✅ Enable GKE Sandbox for untrusted workloads
  ✅ Regular image scanning

Identity and Access

IAM: ✅ Enforce MFA for all users
  ✅ Use groups for permission management
  ✅ Implement least privilege
  ✅ Regular access reviews
  ✅ Disable unused accounts
  ✅ Use service accounts for applications
  ✅ Avoid service account keys (use Workload Identity)

Authentication: ✅ Use strong password policies
  ✅ Implement SSO (SAML, OIDC)
  ✅ Enable session timeouts
  ✅ Monitor failed login attempts
  ✅ Use certificate-based auth where possible

Authorization: ✅ Implement RBAC
  ✅ Use resource-level permissions
  ✅ Apply IAM conditions
  ✅ Regular permission audits
  ✅ Separate admin and user roles

Data Protection

Encryption: ✅ Encrypt data at rest (CMEK)
  ✅ Encrypt data in transit (TLS 1.2+)
  ✅ Use strong encryption algorithms (AES-256)
  ✅ Implement key rotation policies
  ✅ Protect encryption keys (Cloud KMS)

Secrets: ✅ Use Secret Manager
  ✅ Never commit secrets to Git
  ✅ Rotate secrets regularly
  ✅ Use short-lived credentials
  ✅ Implement secret scanning

Backups: ✅ Regular automated backups
  ✅ Test restore procedures
  ✅ Encrypt backups
  ✅ Store in separate location/project
  ✅ Implement retention policies

Monitoring and Compliance

Logging: ✅ Enable Cloud Audit Logs
  ✅ Centralize log collection
  ✅ Set up log retention policies
  ✅ Implement log analysis
  ✅ Export logs to SIEM

Monitoring: ✅ Set up security alerts
  ✅ Monitor IAM changes
  ✅ Track resource modifications
  ✅ Detect anomalous behavior
  ✅ Implement uptime monitoring

Compliance: ✅ Document security controls
  ✅ Regular compliance audits
  ✅ Implement organization policies
  ✅ Enforce data residency
  ✅ Maintain compliance evidence
  ✅ Train team on compliance requirements

Practical Examples​

Complete Security Setup for GKE Application​

#!/bin/bash
# Complete security setup for production GKE application

PROJECT_ID="my-secure-project"
REGION="us-central1"
CLUSTER_NAME="production-cluster"

# 1. Enable required APIs
gcloud services enable container.googleapis.com
gcloud services enable cloudkms.googleapis.com
gcloud services enable secretmanager.googleapis.com
gcloud services enable binaryauthorization.googleapis.com

# 2. Create KMS key ring and encryption key
gcloud kms keyrings create gke-keyring --location=$REGION

gcloud kms keys create gke-key \
  --location=$REGION \
  --keyring=gke-keyring \
  --purpose=encryption \
  --rotation-period=90d \
  --next-rotation-time=$(date -u -d "+90 days" +%Y-%m-%dT%H:%M:%SZ)

# 3. Create private GKE cluster with security features
gcloud container clusters create $CLUSTER_NAME \
  --region=$REGION \
  --enable-private-nodes \
  --enable-private-endpoint \
  --master-ipv4-cidr=172.16.0.0/28 \
  --enable-ip-alias \
  --network=my-vpc \
  --subnetwork=private-subnet \
  --enable-master-authorized-networks \
  --master-authorized-networks=10.0.0.0/8 \
  --enable-workload-identity \
  --workload-pool=$PROJECT_ID.svc.id.goog \
  --database-encryption-key=projects/$PROJECT_ID/locations/$REGION/keyRings/gke-keyring/cryptoKeys/gke-key \
  --enable-shielded-nodes \
  --enable-binauthz \
  --enable-network-policy \
  --addons=HttpLoadBalancing,HorizontalPodAutoscaling,GcePersistentDiskCsiDriver \
  --logging=SYSTEM,WORKLOAD \
  --monitoring=SYSTEM \
  --maintenance-window-start=2024-01-01T00:00:00Z \
  --maintenance-window-duration=4h \
  --maintenance-window-recurrence="FREQ=WEEKLY;BYDAY=SU"

# 4. Get cluster credentials
gcloud container clusters get-credentials $CLUSTER_NAME --region=$REGION

# 5. Create namespace
kubectl create namespace production

# 6. Set up Workload Identity
# Create GCP service account
gcloud iam service-accounts create app-sa \
  --display-name="Application Service Account"

# Grant permissions
gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:app-sa@$PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"

gcloud secrets add-iam-policy-binding db-password \
  --member="serviceAccount:app-sa@$PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

# Create Kubernetes service account
kubectl create serviceaccount app-ksa -n production

# Bind KSA to GSA
gcloud iam service-accounts add-iam-policy-binding \
  app-sa@$PROJECT_ID.iam.gserviceaccount.com \
  --role=roles/iam.workloadIdentityUser \
  --member="serviceAccount:$PROJECT_ID.svc.id.goog[production/app-ksa]"

kubectl annotate serviceaccount app-ksa \
  -n production \
  iam.gke.io/gcp-service-account=app-sa@$PROJECT_ID.iam.gserviceaccount.com

# 7. Create secrets in Secret Manager
echo -n "super-secret-password" | \
  gcloud secrets create db-password --data-file=-

echo -n "api-key-value" | \
  gcloud secrets create api-key --data-file=-

# 8. Set up Pod Security Standards
kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted

# 9. Create Network Policy
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: app-network-policy
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: my-app
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: production
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: production
    ports:
    - protocol: TCP
      port: 5432  # PostgreSQL
  - to:
    - namespaceSelector: {}
    ports:
    - protocol: TCP
      port: 443  # HTTPS
    - protocol: TCP
      port: 53   # DNS
    - protocol: UDP
      port: 53
EOF

# 10. Set up Binary Authorization policy
cat > binauthz-policy.yaml <<EOF
admissionWhitelistPatterns:
- namePattern: gcr.io/$PROJECT_ID/*
defaultAdmissionRule:
  evaluationMode: REQUIRE_ATTESTATION
  enforcementMode: ENFORCED_BLOCK_AND_AUDIT_LOG
  requireAttestationsBy:
  - projects/$PROJECT_ID/attestors/prod-attestor
globalPolicyEvaluationMode: ENABLE
EOF

gcloud container binauthz policy import binauthz-policy.yaml

echo "✅ Security setup complete!"
echo "Cluster: $CLUSTER_NAME"
echo "Region: $REGION"
echo "Workload Identity: Enabled"
echo "Network Policies: Enabled"
echo "Binary Authorization: Enabled"
echo "Encryption: CMEK enabled"

Troubleshooting​

IAM Issues​

Problem: Permission Denied

# Check current user's permissions
gcloud projects get-iam-policy $PROJECT_ID \
  --flatten="bindings[].members" \
  --filter="bindings.members:user:$(gcloud config get-value account)"

# Check service account permissions
gcloud projects get-iam-policy $PROJECT_ID \
  --flatten="bindings[].members" \
  --filter="bindings.members:serviceAccount:my-sa@project.iam.gserviceaccount.com"

# Test specific permission
gcloud projects test-iam-permissions $PROJECT_ID \
  --permissions=storage.buckets.list,storage.objects.create

# Check effective policy (including inherited)
gcloud resource-manager org-policies describe \
  constraints/compute.vmExternalIpAccess \
  --project=$PROJECT_ID --effective

# Troubleshoot with Policy Troubleshooter
gcloud policy-troubleshoot iam-policy \
  --resource=//cloudresourcemanager.googleapis.com/projects/$PROJECT_ID \
  --principal-email=user@example.com \
  --permission=storage.buckets.create

Problem: Service Account Key Not Working

# Verify key is valid
gcloud iam service-accounts keys list \
  --iam-account=my-sa@project.iam.gserviceaccount.com

# Check if service account is disabled
gcloud iam service-accounts describe \
  my-sa@project.iam.gserviceaccount.com

# Test authentication with key
gcloud auth activate-service-account \
  --key-file=/path/to/key.json

gcloud auth list

Encryption Issues​

Problem: Cannot Access Encrypted Resource

# Check if key exists and is enabled
gcloud kms keys describe my-key \
  --location=$REGION \
  --keyring=my-keyring

# Check permissions on key
gcloud kms keys get-iam-policy my-key \
  --location=$REGION \
  --keyring=my-keyring

# Grant decrypt permission
gcloud kms keys add-iam-policy-binding my-key \
  --location=$REGION \
  --keyring=my-keyring \
  --member=serviceAccount:my-sa@project.iam.gserviceaccount.com \
  --role=roles/cloudkms.cryptoKeyDecrypter

# Check key versions
gcloud kms keys versions list \
  --location=$REGION \
  --keyring=my-keyring \
  --key=my-key
