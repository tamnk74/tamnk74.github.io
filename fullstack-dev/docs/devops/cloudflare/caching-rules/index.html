Cloudflare Caching Rules Guide

Overview​

Cloudflare's caching system stores copies of your website's content on its global network of data centers, dramatically reducing load times for visitors worldwide and decreasing bandwidth costs. Caching Rules allow you to customize how Cloudflare caches your content, giving you fine-grained control over what gets cached, for how long, and under what conditions.

Why Use Cloudflare Caching?​

Benefits​

  • Performance: Serve content from locations closer to your visitors
  • Reduced Origin Load: Fewer requests hit your origin server
  • Cost Savings: Lower bandwidth costs at your origin
  • Improved Reliability: Content remains available even if origin goes down
  • DDoS Protection: Cached content is served without hitting your origin
  • Global Distribution: Content available from 300+ data centers worldwide

Use Cases​

  • Static assets (images, CSS, JavaScript)
  • API responses
  • HTML pages (with proper cache invalidation)
  • Media files (videos, audio)
  • Download files
  • Fonts and icons

Cloudflare Cache Behavior​

Default Caching​

By default, Cloudflare caches static content based on file extensions:

Cached by Default:

  • .css, .js
  • .jpg, .jpeg, .png, .gif, .webp, .svg, .ico
  • .woff, .woff2, .ttf, .eot
  • .mp4, .webm, .mp3
  • .pdf, .zip

Not Cached by Default:

  • HTML files (.html, .htm)
  • Dynamic content (no file extension)
  • Content with query strings (unless configured)
  • Content with certain headers (e.g., Cache-Control: private)

Cache Rules (New)​

Cloudflare's new Cache Rules replace Page Rules for caching configuration and offer more flexibility and precision.

Accessing Cache Rules​

  1. Log in to Cloudflare Dashboard
  2. Select your domain
  3. Navigate to Caching → Cache Rules

Cache Rule Components​

1. Rule Name​

A descriptive name for your cache rule.

2. Match Criteria​

Define when the rule applies using:

  • Hostname: Specific subdomain(s)
  • URL Path: Specific paths or patterns
  • File Extension: Specific file types
  • Query String: Presence or specific values
  • HTTP Method: GET, POST, etc.
  • Request Headers: Custom header matching
  • Country: Geographic location
  • Cookie: Cookie presence or values

3. Cache Settings​

What happens when the rule matches:

  • Cache Eligibility: Eligible or Bypass cache
  • Cache TTL: How long to cache
  • Browser Cache TTL: How long browsers should cache
  • Cache Key: Customize what makes requests unique
  • Origin Cache Control: Respect or ignore origin headers
  • Cache by Device Type: Separate cache for mobile/desktop
  • Cache by Query String: Include/exclude specific parameters

Creating Cache Rules​

Example 1: Cache All Static Assets​

Rule Name: Cache Static Assets
When incoming requests match:
  - File extension is one of: jpg, jpeg, png, gif, webp, svg, css, js, woff, woff2
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 1 month
  - Browser Cache TTL: 7 days

Cloudflare Dashboard Configuration:

Field: File Extension
Operator: is in list
Value: jpg, jpeg, png, gif, webp, svg, css, js, woff, woff2

Cache eligibility: Eligible
Edge Cache TTL: 1 month (2678400 seconds)
Browser Cache TTL: 7 days (604800 seconds)

Example 2: Cache API Responses​

Rule Name: Cache API Responses
When incoming requests match:
  - Hostname equals: api.example.com
  - URL Path starts with: /v1/products
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 5 minutes
  - Respect origin cache headers: Yes
  - Cache by query string: Include specific parameters (id, category)

Configuration:

Field: Hostname
Operator: equals
Value: api.example.com

AND

Field: URI Path
Operator: starts with
Value: /v1/products

Cache eligibility: Eligible
Edge Cache TTL: 5 minutes (300 seconds)
Origin Cache Control: Respect
Cache Key: Include query strings (id, category)

Example 3: Cache HTML Pages​

Rule Name: Cache HTML Pages
When incoming requests match:
  - File extension is: html
  - Hostname equals: www.example.com
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 2 hours
  - Browser Cache TTL: 5 minutes
  - Bypass cache on cookie: user_session

Configuration:

Field: File Extension
Operator: equals
Value: html

AND

Field: Hostname
Operator: equals
Value: www.example.com

Cache eligibility: Eligible
Edge Cache TTL: 2 hours (7200 seconds)
Browser Cache TTL: 5 minutes (300 seconds)
Bypass cache when: Cookie "user_session" exists

Example 4: Bypass Cache for Dynamic Content​

Rule Name: Bypass Dynamic Content
When incoming requests match:
  - URL Path starts with: /admin
  OR
  - URL Path starts with: /api/user
Then:
  - Eligible for cache: No (Bypass)

Configuration:

Field: URI Path
Operator: starts with
Value: /admin

OR

Field: URI Path
Operator: starts with
Value: /api/user

Cache eligibility: Bypass cache

Example 5: Cache by Device Type​

Rule Name: Cache Mobile/Desktop Separately
When incoming requests match:
  - Hostname equals: www.example.com
  - File extension is: html
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 1 hour
  - Cache by device type: Separate cache for mobile and desktop

Configuration:

Field: Hostname
Operator: equals
Value: www.example.com

AND

Field: File Extension
Operator: equals
Value: html

Cache eligibility: Eligible
Edge Cache TTL: 1 hour (3600 seconds)
Cache by device type: Enabled

Cache TTL Settings​

Edge Cache TTL​

Duration Cloudflare caches content on its edge servers.

Common Values:

  • 2 minutes: Highly dynamic content (APIs, personalized content)
  • 5 minutes: Semi-dynamic content (product listings)
  • 1 hour: Frequently updated content (news articles)
  • 1 day: Regularly updated content (blog posts)
  • 1 week: Occasionally updated content (marketing pages)
  • 1 month: Rarely changed content (static assets, documentation)
  • 1 year: Versioned assets (app.v123.js)

Setting Edge Cache TTL:

2 minutes = 120 seconds
5 minutes = 300 seconds
10 minutes = 600 seconds
1 hour = 3600 seconds
1 day = 86400 seconds
7 days = 604800 seconds
1 month = 2678400 seconds
1 year = 31536000 seconds

Browser Cache TTL​

Duration browsers cache content locally.

Best Practices:

  • Lower than Edge Cache TTL for frequently changing content
  • Longer for static assets
  • Consider user experience vs. update frequency

Origin Cache Control​

Options for handling origin server cache headers:

  1. Respect Origin Headers: Use TTL from Cache-Control header
  2. Ignore Origin Headers: Use Cloudflare-defined TTL
  3. Override if Origin Missing: Use Cloudflare TTL only if no origin header

Cache Key Customization​

What is a Cache Key?​

A cache key determines what makes a request unique. By default, it includes:

  • Scheme (HTTP/HTTPS)
  • Hostname
  • URL Path
  • Query String (sorted)

Customizing Cache Keys​

Ignore Query String​

Cache the same content for all query string variations:

Cache Key Settings:
- Query String: Ignore all query strings

Use Case: Images with tracking parameters

/image.jpg?utm_source=email
/image.jpg?utm_source=social
Both serve the same cached image

Include Specific Query Strings​

Only include certain parameters in the cache key:

Cache Key Settings:
- Query String: Include only specific parameters
- Parameters: id, lang, version

Use Case: API with multiple optional parameters

/api/product?id=123&lang=en  (cached separately)
/api/product?id=123&lang=fr  (cached separately)
/api/product?id=123&lang=en&debug=true  (same cache as first)

Cache by Headers​

Include specific headers in the cache key:

Cache Key Settings:
- Custom Headers: Accept-Language, Accept-Encoding

Use Case: Serve different content based on language

Cache by Cookie​

Include specific cookies in the cache key:

Cache Key Settings:
- Cookie: currency, region

Use Case: E-commerce sites with regional pricing

Advanced Cache Rules​

Example 6: Versioned Assets with Long Cache​

Rule Name: Long Cache for Versioned Assets
When incoming requests match:
  - URL Path matches regex: .*\.(js|css)\?v=[0-9]+
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 1 year
  - Browser Cache TTL: 1 year

Configuration:

Field: URI Path
Operator: matches regex
Value: .*\.(js|css)\?v=[0-9]+

Cache eligibility: Eligible
Edge Cache TTL: 1 year (31536000 seconds)
Browser Cache TTL: 1 year (31536000 seconds)

Example 7: Geographic Caching​

Rule Name: Cache by Region
When incoming requests match:
  - Hostname equals: cdn.example.com
  - Country is in: US, CA, MX
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 1 day
  - Cache Key: Include country code

Example 8: Cache Bypass for Authenticated Users​

Rule Name: Bypass Cache for Logged-in Users
When incoming requests match:
  - Cookie exists: auth_token
Then:
  - Eligible for cache: No (Bypass)

Example 9: Cache with Stale-While-Revalidate​

Rule Name: Serve Stale Content While Updating
When incoming requests match:
  - URL Path starts with: /api/
Then:
  - Eligible for cache: Yes
  - Edge Cache TTL: 1 hour
  - Serve stale content: 1 day
  - Respect origin headers: Yes

This allows Cloudflare to serve slightly outdated content while fetching fresh content in the background.

Cache Rules vs Page Rules​

Migration from Page Rules​

If you're using legacy Page Rules for caching, here's how they map to Cache Rules:

Page Rule SettingCache Rule Equivalent
Cache Level: BypassCache eligibility: Bypass cache
Cache Level: Standard(Default behavior)
Cache Level: Cache EverythingCache eligibility: Eligible + All file types
Edge Cache TTLEdge Cache TTL
Browser Cache TTLBrowser Cache TTL
Cache Deception Armor(Built-in to Cache Rules)
Cache on CookieBypass cache when cookie exists
Cache KeyCache Key customization

Advantages of Cache Rules​

  1. More Rules: Up to 125 cache rules (vs 3 page rules on Free plan)
  2. Better Matching: More flexible match criteria
  3. No Priority Ordering: Rules evaluated independently
  4. Easier Management: More intuitive interface
  5. Performance: Faster evaluation

Cache Headers​

Response Headers from Cloudflare​

CF-Cache-Status: HIT
CF-Ray: 7a1b2c3d4e5f6g7h-ORD
Cache-Control: public, max-age=3600
Age: 1200

CF-Cache-Status Values:

  • HIT: Served from Cloudflare cache
  • MISS: Not in cache, fetched from origin
  • EXPIRED: Was in cache but expired
  • STALE: Served stale content (origin unavailable)
  • BYPASS: Caching rules caused bypass
  • REVALIDATED: Cached but revalidated with origin
  • UPDATING: Serving stale while updating
  • DYNAMIC: Not cacheable

Setting Cache Headers at Origin​

# Cache for 1 hour at Cloudflare, 5 minutes in browser
Cache-Control: public, max-age=300, s-maxage=3600

# Don't cache
Cache-Control: private, no-cache, no-store, must-revalidate

# Cache but revalidate
Cache-Control: public, max-age=0, must-revalidate

# Cache with conditional requests
ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"
Last-Modified: Wed, 21 Oct 2024 07:28:00 GMT

Testing Cache Rules​

Using curl​

# Check if content is cached
curl -I https://example.com/image.jpg

# Force cache miss
curl -I https://example.com/image.jpg -H "Cache-Control: no-cache"

# Check specific header
curl -I https://example.com/api/data | grep CF-Cache-Status

# Test with different query strings
curl -I https://example.com/page?param1=value1
curl -I https://example.com/page?param2=value2

Using Browser DevTools​

  1. Open DevTools (F12)
  2. Go to Network tab
  3. Reload page
  4. Check response headers:
    • CF-Cache-Status
    • Age
    • Cache-Control

Using Cloudflare Dashboard​

  1. Go to Caching → Configuration
  2. Click Test Cache (if available)
  3. Enter URL to test
  4. View cache status and headers

Cache Purging​

Purge Everything​

# Using Cloudflare API
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  --data '{"purge_everything":true}'

Purge by URL​

# Purge specific URLs
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  --data '{
    "files": [
      "https://example.com/image.jpg",
      "https://example.com/style.css"
    ]
  }'

Purge by Tag​

# Purge by cache tag
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  --data '{
    "tags": ["product-images", "homepage"]
  }'

Purge by Prefix (Enterprise)​

# Purge by URL prefix
curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  --data '{
    "prefixes": [
      "https://example.com/images/",
      "https://example.com/api/v1/"
    ]
  }'

Best Practices​

1. Start Conservative​

Begin with shorter TTLs and increase as you understand your content update patterns.

Initial Setup:
  Static Assets: 1 day
  API Responses: 5 minutes
  HTML Pages: 10 minutes

After Monitoring:
  Static Assets: 1 month
  API Responses: 1 hour
  HTML Pages: 2 hours

2. Use Versioned Assets​

For long cache times, version your assets:

<!-- Bad: Will be cached for a long time -->
<script src="/app.js"></script>

<!-- Good: Version allows cache busting -->
<script src="/app.v123.js"></script>
<script src="/app.js?v=123"></script>

3. Separate Static and Dynamic Content​

Static: cdn.example.com/assets/*
Dynamic: api.example.com/*

4. Use Appropriate TTLs​

Frequently changing: 2-5 minutes
Hourly updates: 30-60 minutes
Daily updates: 6-24 hours
Weekly updates: 3-7 days
Static assets: 30 days to 1 year

5. Cache API Responses Carefully​

Safe to Cache:
  - GET requests
  - Public data
  - Data without user-specific info
  - Idempotent endpoints

Don't Cache:
  - POST/PUT/DELETE requests
  - User-specific data
  - Authentication endpoints
  - Real-time data

6. Implement Cache Tags​

Set cache tags at origin:

Cache-Tag: product-123, category-electronics, homepage

Then purge by tag:

# Purge all product-123 pages
curl -X POST ".../purge_cache" --data '{"tags":["product-123"]}'

7. Monitor Cache Performance​

Track these metrics:

  • Cache Hit Ratio: Target >80%
  • Bandwidth Savings: Cached vs Origin
  • Origin Load: Requests hitting origin
  • Cache Purge Frequency: Avoid excessive purging

8. Handle Query Strings Wisely​

Ignore for Static Assets:
  /image.jpg?utm_source=email
  /image.jpg?utm_source=social
  # Both serve same cached image

Respect for Dynamic Content:
  /api/products?category=electronics
  /api/products?category=clothing
  # Different cache entries

9. Use Stale Content Strategies​

Edge Cache TTL: 1 hour
Serve Stale: 1 day
# Serves stale content if origin is down
# Users get slightly outdated but working content

10. Document Your Rules​

Rule: cache-static-assets
Purpose: Cache all static assets for 1 month
Created: 2024-01-15
Last Updated: 2024-03-20
Owner: DevOps Team
Related: CDN optimization project

Troubleshooting​

Content Not Caching​

Possible Causes:

  1. Origin headers prevent caching:

    Cache-Control: private
    Cache-Control: no-cache
    Set-Cookie: session=abc123

    Solution: Override with Cache Rules

  2. Query strings not handled:

    /page.html?utm_source=email  (not cached by default)

    Solution: Configure cache key to ignore query strings

  3. File extension not cached by default:

    /api/data  (no extension)

    Solution: Create cache rule for the path

Stale Content Served​

Possible Causes:

  1. Long TTL: Solution: Reduce Edge Cache TTL

  2. Cache not purged: Solution: Implement cache purging strategy

  3. Browser cache: Solution: Reduce Browser Cache TTL or use cache busting

High Origin Load​

Possible Causes:

  1. Low cache hit ratio: Solution: Review cache rules, increase TTL

  2. Excessive cache purging: Solution: Purge selectively (by URL or tag)

  3. Uncacheable content: Solution: Make content cacheable where possible

API Configuration​

Creating Cache Rules via API​

curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/rulesets/phases/http_request_cache_settings/entrypoint" \
  -H "Authorization: Bearer {api_token}" \
  -H "Content-Type: application/json" \
  --data '{
    "rules": [
      {
        "expression": "(http.request.uri.path matches \"^/api/products/\")",
        "action": "set_cache_settings",
        "action_parameters": {
          "cache": true,
          "edge_ttl": {
            "mode": "override_origin",
            "default": 300
          },
          "browser_ttl": {
            "mode": "override_origin",
            "default": 60
          },
          "cache_key": {
            "ignore_query_strings_order": false,
            "include_query_string": {
              "include": ["id", "category"]
            }
          }
        },
        "description": "Cache API products with specific query strings"
      }
    ]
  }'

Terraform Configuration​

resource "cloudflare_ruleset" "cache_rules" {
  zone_id     = var.zone_id
  name        = "Cache Rules"
  description = "Custom cache rules for example.com"
  kind        = "zone"
  phase       = "http_request_cache_settings"

  rules {
    action = "set_cache_settings"
    action_parameters {
      cache = true
      edge_ttl {
        mode    = "override_origin"
        default = 3600
      }
      browser_ttl {
        mode    = "override_origin"
        default = 1800
      }
    }
    expression  = "(http.request.uri.path matches \"^/static/\")"
    description = "Cache static assets"
    enabled     = true
  }
}

Summary​

Cloudflare Caching Rules provide powerful, flexible control over content caching:

Key Takeaways​

  1. Use Cache Rules for fine-grained control (not Page Rules)
  2. Set appropriate TTLs based on content update frequency
  3. Customize cache keys for optimal cache hit ratios
  4. Monitor performance regularly
  5. Implement purging strategy for content updates
  6. Test thoroughly before deploying to production
  7. Document your rules for team reference
