Traffic Sequence: Life of a Request

Understanding the order in which Cloudflare processes requests is critical for configuring security and routing rules effectively. A rule set "upstream" (earlier in the sequence) will always override or block traffic before it reaches a rule set "downstream" (later).

This document outlines the complete journey of a request through Cloudflare's infrastructure.

Traffic Flow Diagram​

1. The Connection Phase (Before Security)​

Before the request is even processed by your rules, the connection must be established.

DNS Resolution​

The user's browser asks "Where is example.com?" Cloudflare's DNS answers with an Anycast IP address, directing the request to the nearest Cloudflare data center.

DDoS Protection (L3/L4)​

Cloudflare's edge immediately filters out volumetric attacks (SYN floods, UDP floods) before they touch the application layer. This happens at the network and transport layers, protecting your infrastructure from massive traffic floods.

2. The Security Phase (The "Shields")​

This is where the request is inspected. If a request is blocked here, it stops immediately. It never reaches your Redirects, Cache, or Origin.

IP Access Rules (Global)​

What it is: The legacy "Block/Allow" list found under WAF > Tools.

Priority: High. If you block an IP here, it is dropped instantly. If you "Allow" an IP here, it often skips the WAF entirely (depending on settings).

Use case: Quick blocking of known malicious IPs or allowlisting trusted sources.

Bot Management / Super Bot Fight Mode​

Checks if the visitor is a known automated bot or scraper. This layer identifies and mitigates bot traffic before it reaches your application.

WAF Custom Rules (Formerly Firewall Rules)​

What it is: Your specific rules (e.g., "Block traffic to /admin if not from VPN").

Order: These run after IP Access Rules but before Managed Rules.

Use case: Custom security policies tailored to your application's specific needs.

Rate Limiting Rules​

Counts requests per visitor. If a user exceeds the configured limit, they are blocked at this stage.

Use case: Protecting against brute force attacks, API abuse, or excessive scraping.

WAF Managed Rules​

The "Cloudflare Managed" and "OWASP" rulesets that look for generic attacks (SQLi, XSS, RCE).

Order: These run last in the security phase, after custom rules.

3. The Transformation Phase (The "Traffic Control")​

Once the request is deemed "Safe," Cloudflare decides where it should go or what it should look like.

Redirect Rules (Bulk & Single)​

Example: Redirect example.com/store to shop.example.com.

Important: Because this happens after Security, a blocked attacker cannot trigger a redirect. This prevents redirect abuse and ensures only legitimate traffic is redirected.

URL Rewrite (Transform Rules)​

Example: Rewrite example.com/api/v1 to /v1 before sending to the server.

Key difference: The user doesn't see this change in their browser; only your server receives the modified URL. This is useful for maintaining clean public URLs while using different internal routing.

4. The Compute & Content Phase​

Cloudflare Workers​

If you have a Worker script, it runs here. Workers can:

  • Intercept the request and modify it
  • Return a response immediately (bypassing the Cache and Origin entirely)
  • Add custom logic for A/B testing, authentication, or content manipulation

Cache Rules​

Cloudflare checks: "Do I have this file in the cache?"

Cache Rules determine what gets cached and for how long.

  • Cache HIT: Cloudflare serves the file immediately from the edge, never touching your origin server.
  • Cache MISS: The request proceeds to the Origin phase.

5. The Origin Phase (The "Handover")​

The request is about to leave Cloudflare and go to your physical server (GCP, AWS, on-premises).

Origin Rules​

What it is: Last-minute changes to how Cloudflare connects to your server.

Examples:

  • "For admin.example.com, talk to my server on port 8080 instead of 443"
  • "Change the Host header to internal-app.local"
  • Override SNI for specific routes

Load Balancing​

If you have multiple origin servers, Cloudflare picks the best one based on:

  • Health checks
  • Geographic proximity
  • Configured weights and priorities

The Origin Server​

Your server receives the request, processes it, and sends the response back up the chain. The response then flows back through Cloudflare's edge, where it may be cached, transformed, or modified by Workers before reaching the end user.

Summary: Order of Operations​

1. DNS Resolution
2. DDoS Protection (L3/L4)
   ↓
3. IP Access Rules
4. Bot Management
5. WAF Custom Rules
6. Rate Limiting Rules
7. WAF Managed Rules
   ↓
   [REQUEST ALLOWED]
   ↓
8. Redirect Rules
9. URL Rewrite (Transform Rules)
   ↓
10. Cloudflare Workers
11. Cache Rules (HIT → Return; MISS → Continue)
   ↓
12. Origin Rules
13. Load Balancing
14. Origin Server

Key Takeaways​

  1. Security rules execute first - If a request is blocked in the Security Phase, it never reaches your redirects, cache, or origin.

  2. Order matters - A rule upstream can prevent downstream rules from ever being evaluated.

  3. Use the right tool for the job:

    • Block malicious traffic early with IP Access Rules or WAF Custom Rules
    • Use Rate Limiting for abuse prevention
    • Use Redirects for URL management (knowing they run after security)
    • Use Transform Rules for internal URL modifications
    • Use Workers for complex logic and dynamic content

  4. Cache is powerful - A cache HIT means your origin server is never contacted, improving performance and reducing costs.

  5. Test thoroughly - Understanding this sequence helps you troubleshoot why a rule might not be working as expected.
