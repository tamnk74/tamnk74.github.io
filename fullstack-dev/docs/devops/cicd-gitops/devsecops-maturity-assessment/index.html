DevSecOps Maturity Assessment

Overview​

This document outlines the DevSecOps maturity assessment framework based on our success criteria scorecard. The assessment evaluates teams across four key categories with a maximum score of 200 points.

Scoring System​

Rating Scale:

  • 0: None - Not implemented
  • 1: Rarely present - Minimal implementation
  • 2: Somewhat present - Basic implementation
  • 3: Partially established - Moderate implementation
  • 4: Mostly established - Advanced implementation
  • 5: Fully established - Complete implementation

Assessment Categories​

1. Tool Adoption (Maximum: 40 points)​

1.1 SonarQube Cloud SAST - Pull Request Analysis​

Criteria: SonarQube Cloud SAST runs automatically on every PR

Description: CI workflow includes sonar-scanner on pull_request trigger

Measurement: All production repos must have successful SonarQube PR analysis on every PR in the last 30 days

Implementation:

# .github/workflows/sonarqube.yml
name: SonarQube Analysis

on:
  pull_request:
    branches: [main, develop]

jobs:
  sonarqube:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      
      - name: SonarQube Scan
        uses: sonarsource/sonarqube-scan-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}

1.2 SonarQube Cloud SAST - Default Branch Analysis​

Criteria: SonarQube Cloud SAST runs on default branch (push)

Description: CI workflow YAML triggers include on: push with branches configuration

Measurement: All production repos must have analysis on every push to default branch

Implementation:

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

1.3 Sonar IDE Plugin Integration​

Criteria: Sonar IDE plugin guidance published and org ruleset applied

Description: Sonar IDE installed in each developer's IDE and connected to Sonar projects

Measurement: All core teams informed and org Quality Profile bound to 100% of production projects

Setup Guide:

  1. Install SonarLint extension in VS Code/IntelliJ
  2. Connect to SonarQube Cloud organization
  3. Bind local projects to SonarQube projects
  4. Enable connected mode for real-time feedback

1.4 DAST Pipeline for Web Services​

Criteria: DAST pipeline (e.g., ZAP) exists for web services

Description: CI template file referenced by web services

Measurement: 100% of internet-facing services have DAST job running at least once per release candidate on staging

Implementation:

# .github/workflows/dast-zap.yml
name: DAST Security Scan

on:
  workflow_dispatch:
  push:
    branches: [staging]

jobs:
  zap-scan:
    runs-on: ubuntu-latest
    steps:
      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.10.0
        with:
          target: 'https://staging.example.com'
          rules_file_name: '.zap/rules.tsv'
          cmd_options: '-a'

1.5 DAST Quality Gate​

Criteria: DAST gate blocks deploy when below threshold

Description: Pipeline stage parses ZAP thresholds and fails on breach

Measurement: Gate enforced on all internet-facing services with zero unapproved bypasses

1.6 Dependabot Security​

Criteria: Dependabot enabled in GitHub security

Description: Dependency graph enabled in GitHub

Measurement: All repositories must have Dependabot enabled

Configuration:

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    reviewers:
      - "security-team"
    labels:
      - "dependencies"
      - "security"

1.7 External Secrets Operator (ESO)​

Criteria: External Secrets Operator installed and running

Description: Check deployed ExternalSecret app in Argo CD

Measurement: Controller logs show successful syncs

1.8 GKE Workload Identity​

Criteria: GKE Workload Identity enabled for workloads

Description: GKE cluster has Workload Identity enabled

Measurement: Pod spec uses projected tokens (no JSON keys)

2. Policy Compliance (Maximum: 65 points)​

2.1 Secret Detection Quality Gate​

Criteria: Apply secret detection Quality Gate setting in SonarQube Cloud

Measurement: Secret detection rules configured and enforced within Quality Gate

2.2 SonarQube Monthly PDF Reports​

Criteria: Project PDF Report monthly email subscription configured

Measurement: Screenshot of project notification/subscription settings showing monthly PDF configuration

2.3 SonarQube Portfolios​

Criteria: Portfolios defined per Scrum team

Measurement: Services/repositories logically mapped into defined Portfolios

2.4 Security Report Downloads​

Criteria: Security Report created and monthly download performed

Measurement: Screenshot of saved report preset and evidence of monthly download

2.5 Regulatory Report Downloads​

Criteria: Project Regulatory Report (ZIP) monthly download performed

Measurement: Verify presence of "Regulatory Report" ZIP file in designated evidence store path

2.6 Branch Protection - Quality Gate Required​

Criteria: SonarQube Quality Gate set as Required status check

Measurement: Check GitHub repository settings → Branches → Branch protection rules

Configuration:

# GitHub Branch Protection Settings
Required status checks:
  ✓ SonarQube Quality Gate
  ✓ Strict status checks

2.7 Branch Protection - No Direct Pushes​

Criteria: Disallow direct pushes to protected branches

Measurement: Confirm "Require a pull request before merging" is enabled

2.8 GitHub Actions Minimal Permissions​

Criteria: Minimal permissions configured for workflows

Measurement: Verify permissions: read-all or explicit minimal writes in workflow YAML

Implementation:

name: CI Pipeline

permissions:
  contents: read
  pull-requests: write
  security-events: write

jobs:
  build:
    runs-on: ubuntu-latest
    # ...

2.9 No Personal Access Tokens (PATs)​

Criteria: No Personal Access Tokens used in CI/CD

Measurement: Review org security policy and search workflow environment variables for PAT usage

2.10 Secret Scanning - Push Protection​

Criteria: No plaintext secrets in Git (push blocked/scanned)

Measurement: Confirm secret scanning/push protection features are enabled

2.11 Runtime Secrets - GSM + ESO​

Criteria: GSM + ESO enforced for runtime secrets

Measurement: Verify manual K8s Secrets are disallowed and all secrets enforced via GSM + ESO

Example:

# external-secret.yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secrets
spec:
  secretStoreRef:
    name: gcpsm-secret-store
    kind: SecretStore
  target:
    name: app-secrets
  data:
    - secretKey: database-password
      remoteRef:
        key: db-password

2.12 Workload Identity Required​

Criteria: Workload Identity required for GCP access

Measurement: Check for absence of JSON key files in CI secret store scans and GitHub repos

2.13 CI GCP Access via OIDC Only​

Criteria: Service Account JSON keys not used for CI/CD authentication

Measurement: Workflow logs show OIDC token exchange for GCP access

Implementation:

- name: Authenticate to Google Cloud
  uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: 'projects/PROJECT_ID/locations/global/workloadIdentityPools/POOL_ID/providers/PROVIDER_ID'
    service_account: 'SERVICE_ACCOUNT@PROJECT_ID.iam.gserviceaccount.com'

3. Workflow Completion (Maximum: 30 points)​

3.1 Quality Gate Status - Mandatory PASS​

Criteria: Achieving PASS (Green) status on SonarQube Quality Gate

Measurement: Verify SonarQube status check is Green for every merged PR in last 30 days

3.2 New Code Critical Security Elimination​

Criteria: All "New Code" has ZERO Critical security issues

Measurement:

  • New Bugs = 0
  • New Vulnerabilities = 0
  • New Security Hotspots = 0 on default branch

3.3 Blocker & High Issue Debt Reduction​

Criteria: All existing Blocker and High severity issues actively reduced

Measurement: Existing Blocker and High issues should be none across all production projects

3.4 Priority Security Hotspots Resolution​

Criteria: Security Hotspots reviewed, prioritizing High/Critical Priority

Measurement: All High-Priority Security Hotspots must be reviewed (Status: Fixed or Safe)

3.5 Overall Security Rating Maintenance​

Criteria: Maintain highest possible Security Rating

Measurement: Maintain overall 'A' Security Rating on default branch for 100% of production repos

3.6 Code Maintainability & Quality Rating​

Criteria: Maintain overall code quality and standards

Measurement: Maintain overall 'A' Maintainability Rating and 'A' Reliability Rating on default branch

4. Governance Participation (Maximum: 15 points)​

4.1 Monthly Onboarding Progress Review​

Criteria: Successful completion of scheduled monthly progress review

Measurement: Documented evidence confirming monthly review of Assessment Sheet

4.2 Timely Action Item Execution​

Criteria: Action Items completed by due dates

Measurement: Review Action Item comparing due date vs. completion date

4.3 DevOps Governance Communication Responsiveness​

Criteria: Response from DevSecOps Governance team via communication channels

Measurement: Median response time less than 1 business day for official inquiries

Maturity Levels​

Based on total weighted score percentage:

LevelScore RangeDescription
Level 1 - Initial0-20%Ad-hoc processes, minimal security controls
Level 2 - Developing21-40%Some security tools adopted, inconsistent practices
Level 3 - Defined41-60%Documented processes, most tools implemented
Level 4 - Managed61-80%Measured and controlled processes, strong compliance
Level 5 - Optimized81-100%Continuous improvement, full automation, proactive security

Improvement Roadmap​

Phase 1: Foundation (0-3 months)​

  • Enable Dependabot on all repositories
  • Configure SonarQube Cloud for all projects
  • Set up branch protection rules
  • Enable secret scanning

Phase 2: Automation (3-6 months)​

  • Implement DAST pipelines for web services
  • Deploy External Secrets Operator
  • Configure Workload Identity
  • Migrate to OIDC authentication

Phase 3: Optimization (6-12 months)​

  • Achieve Quality Gate PASS on all PRs
  • Eliminate all Critical/High issues
  • Implement monthly reporting automation
  • Establish governance review cadence

Phase 4: Excellence (12+ months)​

  • Maintain 'A' ratings across all projects
  • Zero security debt
  • Proactive threat detection
  • Continuous compliance monitoring

Best Practices​

  1. Regular Assessments: Conduct monthly assessments to track progress
  2. Team Accountability: Assign ownership for each criterion
  3. Incremental Improvement: Focus on one category at a time
  4. Documentation: Maintain evidence for all measurements
  5. Automation: Automate compliance checks where possible
  6. Training: Provide ongoing DevSecOps training for teams
  7. Feedback Loop: Use assessment results to drive improvements
