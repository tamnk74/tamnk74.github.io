Operational Readiness Review (ORR) - Comprehensive Guide

Overview​

An Operational Readiness Review (ORR) is a structured process to evaluate whether a system, service, or workload is prepared for production deployment. It validates that processes, people, and systems meet the standards required for safe, stable, and reliable operations.

The ORR is inspired by the AWS Well-Architected Framework and industry best practices for operational excellence. It brings together stakeholders from engineering, operations, security, and business to systematically assess production readiness.

Why ORR Matters​

Without ORRWith ORR
Undetected gaps in monitoringVerified monitoring and alerting coverage
Unclear incident response ownershipDefined roles, escalation paths, and runbooks
Untested disaster recoveryValidated backup/recovery with tested RPO/RTO
Security vulnerabilities in productionPre-deployment security assessment
Performance issues at scaleLoad-tested and capacity-planned services
Knowledge silosDocumented procedures and trained teams

When to Conduct an ORR​

  • New service launches — before first production deployment
  • Major feature releases — significant changes to architecture or data flow
  • Infrastructure migrations — cloud migrations, Kubernetes upgrades, database changes
  • Post-incident improvements — after a major incident to prevent recurrence
  • Periodic reviews — quarterly or semi-annually for critical services

ORR Process Workflow​

  • Use the RED method for services: Rate, Errors, Duration
  • Use the USE method for resources: Utilization, Saturation, Errors

  • Set up anomaly detection in addition to static thresholds
  • Create service dependency maps to understand blast radius

  ◄─────────────►               ◄────────────────►

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // ramp-up
    { duration: '5m', target: 100 },   // sustained load
    { duration: '2m', target: 300 },   // peak load
    { duration: '5m', target: 300 },   // sustained peak
    { duration: '2m', target: 0 },     // ramp-down
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],   // P99 < 500ms
    http_req_failed: ['rate<0.01'],     // Error rate < 1%
    http_reqs: ['rate>100'],            // Throughput > 100 RPS
  },
};

export default function () {
  const res = http.get('https://api.example.com/products');
  check(res, {
    'status is 200': (r) => r.status === 200,
    'response time < 500ms': (r) => r.timings.duration < 500,
  });
  sleep(1);
}

# .github/workflows/orr-check.yml
name: Operational Readiness Check

on:
  pull_request:
    branches: [main]

      - 'k8s/**'

  orr-validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check monitoring configuration

          # Verify Prometheus rules exist
          if [ ! -d "k8s/monitoring/rules" ]; then
            echo "❌ Missing monitoring rules"
            exit 1
          fi
          echo "✅ Monitoring rules found"

      - name: Check health endpoints
        run: |
          # Verify health check configuration in deployments
          for file in k8s/deployments/*.yaml; do
            if ! grep -q "livenessProbe" "$file"; then
              echo "❌ Missing livenessProbe in $file"
              exit 1
            fi
            if ! grep -q "readinessProbe" "$file"; then
              echo "❌ Missing readinessProbe in $file"
              exit 1
            fi
          done
          echo "✅ All deployments have health checks"

      - name: Check resource limits
        run: |
          for file in k8s/deployments/*.yaml; do
            if ! grep -q "resources:" "$file"; then
              echo "❌ Missing resource limits in $file"
              exit 1
            fi
          done
          echo "✅ All deployments have resource limits"

      - name: Check HPA configuration
        run: |
          if [ ! -d "k8s/hpa" ] || [ -z "$(ls k8s/hpa/)" ]; then

            echo "✅ HPA configurations found"
          fi

6.2 Kubernetes Readiness Validation Script​

#!/bin/bash
# orr-k8s-validate.sh - Validate Kubernetes cluster readiness

set -euo pipefail

NAMESPACE="${1:-default}"
PASS=0
FAIL=0
WARN=0

check() {
    local name="$1"
    local result="$2"
    if [ "$result" = "pass" ]; then
        echo "✅ PASS: $name"
        ((PASS++))
    elif [ "$result" = "warn" ]; then
        echo "⚠️  WARN: $name"
        ((WARN++))
    else
        echo "❌ FAIL: $name"
        ((FAIL++))
    fi
}

echo "=== ORR Kubernetes Validation ==="
echo "Namespace: $NAMESPACE"
echo "Date: $(date -u +%Y-%m-%dT%H:%M:%SZ)"
echo "================================="

# Check all pods are running
UNHEALTHY=$(kubectl get pods -n "$NAMESPACE" --no-headers | grep -v "Running\|Completed" | wc -l)
[ "$UNHEALTHY" -eq 0 ] && check "All pods healthy" "pass" || check "Unhealthy pods: $UNHEALTHY" "fail"

# Check HPA exists
HPA_COUNT=$(kubectl get hpa -n "$NAMESPACE" --no-headers 2>/dev/null | wc -l)
[ "$HPA_COUNT" -gt 0 ] && check "HPA configured ($HPA_COUNT)" "pass" || check "No HPA configured" "warn"

# Check PDB exists
PDB_COUNT=$(kubectl get pdb -n "$NAMESPACE" --no-headers 2>/dev/null | wc -l)
[ "$PDB_COUNT" -gt 0 ] && check "PDB configured ($PDB_COUNT)" "pass" || check "No PDB configured" "warn"

# Check resource limits
NO_LIMITS=$(kubectl get pods -n "$NAMESPACE" -o json | \
    jq -r '.items[].spec.containers[] | select(.resources.limits == null) | .name' | wc -l)
[ "$NO_LIMITS" -eq 0 ] && check "All containers have resource limits" "pass" || \
    check "Containers without limits: $NO_LIMITS" "fail"

# Check network policies
NETPOL=$(kubectl get networkpolicy -n "$NAMESPACE" --no-headers 2>/dev/null | wc -l)
[ "$NETPOL" -gt 0 ] && check "Network policies exist ($NETPOL)" "pass" || \
    check "No network policies" "warn"

# Check service monitors
SM_COUNT=$(kubectl get servicemonitor -n "$NAMESPACE" --no-headers 2>/dev/null | wc -l)
[ "$SM_COUNT" -gt 0 ] && check "ServiceMonitors configured ($SM_COUNT)" "pass" || \
    check "No ServiceMonitors" "fail"

echo ""
echo "=== Summary ==="
echo "Pass: $PASS | Warn: $WARN | Fail: $FAIL"
echo ""
if [ "$FAIL" -gt 0 ]; then
    echo "❌ ORR VALIDATION FAILED - $FAIL issues require remediation"
    exit 1
elif [ "$WARN" -gt 0 ]; then
    echo "⚠️  ORR VALIDATION PASSED WITH WARNINGS - $WARN items to review"
    exit 0
else
    echo "✅ ORR VALIDATION PASSED"
    exit 0
fi

7. ORR Maturity Model​

Organizations can progressively improve their ORR process across maturity levels:

Level 1: Ad Hoc​

  • ORR is informal or nonexistent
  • No standardized checklists
  • Reviews happen reactively after incidents

Level 2: Defined​

  • Standardized ORR checklist exists
  • Reviews conducted before major deployments
  • Basic monitoring and alerting in place
  • Manual review process

Level 3: Managed​

  • ORR is mandatory for all production changes
  • Automated checks supplement manual reviews
  • Metrics tracked (MTTR, change failure rate)
  • Regular review cycles established
  • Integration with CI/CD pipelines

Level 4: Optimized​

  • Continuous readiness validation
  • Chaos engineering integrated into ORR
  • Machine learning-based anomaly detection
  • Self-healing infrastructure
  • ORR feedback loop drives architecture improvements
  • Error budgets and SLO-driven decision making

┌─────────────────────────── ORR Quick Reference ───────────────────────────┐
│                                                                           │
│  📋 BEFORE THE REVIEW                                                     │
│  ├── Identify service owner and review team                               │
│  ├── Complete all ORR checklist items                                     │
│  ├── Gather evidence (test results, configs, docs)                        │
│  └── Pre-fill the ORR report template                                     │
│                                                                           │
│  🔍 DURING THE REVIEW                                                     │
│  ├── Walk through each checklist category                                 │
│  ├── Assess Pass / Fail / Needs Improvement                               │
│  ├── Identify risks and assign severity                                   │
│  └── Create action items with owners and dates                            │
│                                                                           │
│  ✅ AFTER THE REVIEW                                                      │
│  ├── Publish ORR report to team wiki                                      │
│  ├── Track action items to completion                                     │
│  ├── Issue certification if criteria met                                  │
│  └── Schedule next review date                                            │
│                                                                           │
│  🚫 BLOCKING CRITERIA (must resolve before go-live)                       │
│  ├── No monitoring or alerting configured                                 │
│  ├── No incident response plan                                            │
│  ├── Untested backup/recovery                                             │
│  ├── Critical security vulnerabilities                                    │
│  └── No rollback strategy                                                 │
│                                                                           │
└───────────────────────────────────────────────────────────────────────────┘
