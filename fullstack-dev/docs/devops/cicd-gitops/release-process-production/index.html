Release Process to Production - Comprehensive Guide

Overview​

A well-defined release process is the backbone of reliable software delivery. It establishes the repeatable, auditable, and safe path that code follows from a developer's branch to production. This guide covers the end-to-end release lifecycle — from branching strategy and version management, through build/test gates, environment promotion, deployment strategies, to post-release validation and incident response.

Why a Formal Release Process Matters​

Without ProcessWith Process
"Works on my machine" deploysReproducible, immutable artifacts
Friday 5 PM YOLO pushesScheduled, predictable release windows
No one knows what's in productionFull traceability from commit to deploy
Hours-long rollbacksOne-click automated rollback
Finger-pointing after incidentsClear ownership at every stage
Manual, error-prone stepsAutomated gates with human approval where needed

Guiding Principles​

  1. Automate everything that can be automated — humans approve, machines execute
  2. Immutable artifacts — build once, deploy everywhere
  3. Progressive delivery — promote through environments, never skip stages
  4. Fast rollback — every deployment must be reversible in minutes
  5. Observability first — if you can't measure it, don't release it
  6. Shift left — catch issues as early and cheaply as possible

2. Versioning​

Semantic Versioning (SemVer)​

MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]

Examples:
  1.0.0           → Initial release
  1.1.0           → New feature added (backward compatible)
  1.1.1           → Bug fix
  2.0.0           → Breaking change
  1.2.0-rc.1      → Release candidate
  1.2.0-beta.3    → Beta pre-release
  1.2.0+build.456 → Build metadata
Change TypeVersion BumpExampleWhen
Breaking API changeMAJOR1.x.x → 2.0.0Removed endpoint, changed response schema
New feature (backward compatible)MINOR1.1.x → 1.2.0New API endpoint, new optional field
Bug fixPATCH1.1.1 → 1.1.2Security patch, defect correction
Pre-releasePRERELEASE1.2.0-rc.1Release candidate, beta, alpha

Automated Version Bumping​

# .github/workflows/release.yml
name: Release

on:
  push:
    branches: [main]

jobs:
  version:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Determine version bump
        id: version
        run: |
          # Analyze commit messages since last tag
          LAST_TAG=$(git describe --tags --abbrev=0 2>/dev/null || echo "v0.0.0")
          COMMITS=$(git log "$LAST_TAG"..HEAD --oneline)

          if echo "$COMMITS" | grep -qiE "^.*(BREAKING CHANGE|!:)"; then
            echo "bump=major" >> $GITHUB_OUTPUT
          elif echo "$COMMITS" | grep -qiE "^.*(feat|feature)"; then
            echo "bump=minor" >> $GITHUB_OUTPUT
          else
            echo "bump=patch" >> $GITHUB_OUTPUT
          fi

      - name: Bump version and tag
        run: |
          npm version ${{ steps.version.outputs.bump }} --no-git-tag-version
          VERSION=$(node -p "require('./package.json').version")
          git tag "v${VERSION}"
          git push origin "v${VERSION}"

3. CI Pipeline — Build & Quality Gates​

Pipeline Architecture​

GitHub Actions CI Pipeline​

# .github/workflows/ci.yml
name: CI Pipeline

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  NODE_VERSION: "20"
  REGISTRY: gcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ──────────────────────────────────────
  # Stage 1: Code Quality
  # ──────────────────────────────────────
  lint:
    name: Lint & Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: "pnpm"
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm type-check
      - run: pnpm format:check

  # ──────────────────────────────────────
  # Stage 2: Testing
  # ──────────────────────────────────────
  unit-test:
    name: Unit Tests
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: "pnpm"
      - run: pnpm install --frozen-lockfile
      - run: pnpm test:unit -- --coverage
      - name: Upload coverage
        uses: codecov/codecov-action@v4
        with:
          token: ${{ secrets.CODECOV_TOKEN }}

  integration-test:
    name: Integration Tests
    runs-on: ubuntu-latest
    needs: lint
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
          POSTGRES_DB: testdb
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: "pnpm"
      - run: pnpm install --frozen-lockfile
      - run: pnpm test:integration
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/testdb
          REDIS_URL: redis://localhost:6379

  # ──────────────────────────────────────
  # Stage 3: Security Scanning
  # ──────────────────────────────────────
  security:
    name: Security Scan
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - uses: actions/checkout@v4

      - name: Run SAST (Semgrep)
        uses: semgrep/semgrep-action@v1
        with:
          config: >-
            p/owasp-top-ten
            p/nodejs
            p/typescript

      - name: Dependency audit
        run: pnpm audit --audit-level=high

      - name: Secret detection
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  # ──────────────────────────────────────
  # Stage 4: Build & Push
  # ──────────────────────────────────────
  build:
    name: Build & Push Image
    runs-on: ubuntu-latest
    needs: [unit-test, integration-test, security]
    if: github.ref == 'refs/heads/main'
    permissions:
      contents: read
      id-token: write
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
      image-digest: ${{ steps.build-push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - name: Authenticate to GCP
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
          service_account: ${{ secrets.WIF_SA }}

      - name: Configure Docker for GCR
        run: gcloud auth configure-docker

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=
            type=semver,pattern={{version}}
            type=ref,event=branch

      - name: Build and push
        id: build-push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Scan image with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
          format: "sarif"
          output: "trivy-results.sarif"
          severity: "CRITICAL,HIGH"

      - name: Generate SBOM
        run: |
          syft packages \
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ steps.build-push.outputs.digest }} \
            -o cyclonedx-json > sbom.json

      - name: Upload SBOM
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

5.1 Rolling Update (Kubernetes Default)​

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1      # At most 1 pod unavailable
      maxSurge: 2            # At most 2 extra pods during update
  template:
    spec:
      containers:
        - name: order-service
          image: gcr.io/my-project/order-service:v1.2.0
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 3000
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 3000
            initialDelaySeconds: 30
            periodSeconds: 10
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]
      terminationGracePeriodSeconds: 60

5.2 Canary Deployment (Argo Rollouts)​

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: order-service
spec:
  replicas: 5
  strategy:
    canary:
      # Traffic splitting steps
      steps:
        - setWeight: 5
        - pause: { duration: 5m }        # 5% for 5 minutes
        - analysis:
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: order-service
        - setWeight: 25
        - pause: { duration: 10m }       # 25% for 10 minutes
        - analysis:
            templates:
              - templateName: success-rate
        - setWeight: 50
        - pause: { duration: 10m }       # 50% for 10 minutes
        - setWeight: 100                 # Full rollout

      # Auto-rollback on failure
      maxUnavailable: 1
      maxSurge: 2

      # Traffic routing via Istio
      trafficRouting:
        istio:
          virtualServices:
            - name: order-service-vsvc
              routes:
                - primary

      # Anti-affinity: keep canary and stable on separate nodes
      antiAffinity:
        preferredDuringSchedulingIgnoredDuringExecution:
          weight: 100

---

6. Release Approval & Change Management​

Release Approval Flow​

Release Checklist Template​

Below is the high-level release checklist. For the full technical breakdown, see Section 6.1 — Technical Release Checklist.

## Release v[X.Y.Z] — [Service Name]

### Pre-Release
- [ ] All CI checks pass on the release branch
- [ ] Release notes / changelog drafted
- [ ] Database migrations tested in staging
- [ ] Feature flags configured for new features
- [ ] Rollback plan documented and tested
- [ ] On-call engineer identified and notified
- [ ] Monitoring dashboards reviewed
- [ ] Dependent services notified of changes
- [ ] Load test results reviewed (if applicable)
- [ ] Security scan clean (no Critical/High)

### Approval
- [ ] QA sign-off: @qa-lead
- [ ] Security sign-off: @security-team
- [ ] Ops sign-off: @sre-team
- [ ] Engineering Manager approval: @eng-manager

### Deployment
- [ ] Change record created in ITSM tool
- [ ] Release deployed to pre-production
- [ ] Pre-production smoke tests passed
- [ ] Release deployed to production (canary)
- [ ] Canary metrics verified (error rate, latency, throughput)
- [ ] Full rollout completed
- [ ] Post-deployment smoke tests passed

### Post-Release
- [ ] Verify monitoring and alerts are active
- [ ] Confirm no increase in error rates
- [ ] Update release status in tracking system
- [ ] Communicate release completion to stakeholders
- [ ] Schedule release retrospective (if needed)

7. Database Migrations​

Safe Migration Principles​

┌─────────────────────── DATABASE MIGRATION RULES ─────────────────────────┐
│                                                                          │
│  ✅ DO                                 ❌ DON'T                          │
│  ├── Add new columns as nullable       ├── Drop columns in same release  │
│  ├── Add new tables freely             ├── Rename columns directly       │
│  ├── Add indexes concurrently          ├── Change column types in-place  │
│  ├── Use expand-contract pattern       ├── Run long-locking DDL in peak  │
│  ├── Test migrations on prod copy      ├── Deploy code + migration       │
│  ├── Make migrations idempotent        │   simultaneously                │
│  └── Always have a rollback script     └── Skip testing on real data     │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘

Expand-Contract Pattern​

This pattern allows zero-downtime schema changes by splitting changes into multiple releases:

Example: Renaming a column from username to display_name

-- Release 1: Expand (add new column, dual-write)
ALTER TABLE users ADD COLUMN display_name VARCHAR(255);
UPDATE users SET display_name = username WHERE display_name IS NULL;

-- Application code writes to BOTH columns for backward compatibility

-- Release 2: Migrate (read from new column)
-- Application code reads from display_name, still writes to both

-- Release 3: Contract (drop old column)
ALTER TABLE users DROP COLUMN username;

Migration Tooling​

// Example: TypeORM migration with safety checks
import { MigrationInterface, QueryRunner } from "typeorm";

export class AddDisplayName1709139200000 implements MigrationInterface {
  name = "AddDisplayName1709139200000";

  public async up(queryRunner: QueryRunner): Promise<void> {
    // Add new column (nullable - safe for existing rows)
    await queryRunner.query(`
      ALTER TABLE "users"
      ADD COLUMN "display_name" VARCHAR(255)
    `);

    // Backfill from existing data
    await queryRunner.query(`
      UPDATE "users"
      SET "display_name" = "username"
      WHERE "display_name" IS NULL
    `);

    // Add index concurrently (non-blocking in PostgreSQL)
    await queryRunner.query(`
      CREATE INDEX CONCURRENTLY "IDX_users_display_name"
      ON "users" ("display_name")
    `);
  }

  public async down(queryRunner: QueryRunner): Promise<void> {
    await queryRunner.query(`
      DROP INDEX IF EXISTS "IDX_users_display_name"
    `);
    await queryRunner.query(`
      ALTER TABLE "users" DROP COLUMN "display_name"
    `);
  }
}

import { Injectable } from "@nestjs/common";
import * as LaunchDarkly from "launchdarkly-node-server-sdk";

interface FeatureContext {
  userId: string;
  email: string;
  country?: string;
  plan?: string;
  percentage?: number;
}

@Injectable()
export class FeatureFlagService {
  private client: LaunchDarkly.LDClient;

  constructor() {
    this.client = LaunchDarkly.init(process.env.LAUNCHDARKLY_SDK_KEY);
  }

  async isEnabled(flag: string, context: FeatureContext): Promise<boolean> {
    const ldContext: LaunchDarkly.LDContext = {
      kind: "user",
      key: context.userId,
      email: context.email,
      country: context.country,
      plan: context.plan,
    };
    return this.client.variation(flag, ldContext, false);
  }

  async getVariation<T>(
    flag: string,
    context: FeatureContext,
    defaultValue: T
  ): Promise<T> {
    const ldContext: LaunchDarkly.LDContext = {
      kind: "user",
      key: context.userId,
    };
    return this.client.variation(flag, ldContext, defaultValue);
  }
}

// Usage in controller
@Controller("checkout")
export class CheckoutController {
  constructor(
    private readonly featureFlags: FeatureFlagService,
    private readonly checkoutV1: CheckoutServiceV1,
    private readonly checkoutV2: CheckoutServiceV2,
  ) {}

  @Post()
  async processCheckout(@Req() req: Request) {
    const useNewCheckout = await this.featureFlags.isEnabled(
      "new-checkout-flow",
      { userId: req.user.id, email: req.user.email },
    );

    if (useNewCheckout) {
      return this.checkoutV2.process(req.body);
    }
    return this.checkoutV1.process(req.body);
  }
}

Rollback Methods​

#!/bin/bash
# rollback.sh — Production rollback script

set -euo pipefail

SERVICE=$1
TARGET_VERSION=${2:-"previous"}

echo "╔══════════════════════════════════════╗"
echo "║     PRODUCTION ROLLBACK INITIATED    ║"
echo "╠══════════════════════════════════════╣"
echo "║ Service:  $SERVICE"
echo "║ Target:   $TARGET_VERSION"
echo "║ Time:     $(date -u +%Y-%m-%dT%H:%M:%SZ)"
echo "║ Operator: $(whoami)"
echo "╚══════════════════════════════════════╝"

# Method 1: Kubernetes rollback
rollback_k8s() {
  echo "→ Rolling back Kubernetes deployment..."
  if [ "$TARGET_VERSION" = "previous" ]; then
    kubectl rollout undo deployment/"$SERVICE" -n production
  else
    # Rollback to specific revision
    REVISION=$(kubectl rollout history deployment/"$SERVICE" -n production \
      | grep "$TARGET_VERSION" | awk '{print $1}')
    kubectl rollout undo deployment/"$SERVICE" \
      -n production --to-revision="$REVISION"
  fi
  kubectl rollout status deployment/"$SERVICE" \
    -n production --timeout=300s
}

# Method 2: ArgoCD rollback
rollback_argocd() {
  echo "→ Rolling back via ArgoCD..."
  HISTORY=$(argocd app history "$SERVICE" -o json | jq '.[1].id')
  argocd app rollback "$SERVICE" "$HISTORY"
  argocd app wait "$SERVICE" --health --timeout 300
}

# Method 3: Argo Rollouts abort
rollback_argo_rollouts() {
  echo "→ Aborting Argo Rollout..."
  kubectl argo rollouts abort "$SERVICE" -n production
  kubectl argo rollouts undo "$SERVICE" -n production
  echo "Waiting for stable state..."
  kubectl argo rollouts status "$SERVICE" -n production --timeout 300s
}

# Execute rollback
rollback_k8s

# Verify
echo ""
echo "=== Post-Rollback Verification ==="
echo "Pods:"
kubectl get pods -n production -l app="$SERVICE" --no-headers
echo ""
echo "Current image:"
kubectl get deployment "$SERVICE" -n production \
  -o jsonpath='{.spec.template.spec.containers[0].image}'
echo ""

# Health check
STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
  "https://api.example.com/$SERVICE/health")
if [ "$STATUS" = "200" ]; then
  echo "✅ Health check PASSED ($STATUS)"
else
  echo "❌ Health check FAILED ($STATUS) — ESCALATE IMMEDIATELY"
  exit 1
fi

echo ""
echo "✅ Rollback complete. Create incident ticket and notify stakeholders."

if [ "$FAIL" -gt 0 ]; then
  echo "🚫 PRE-RELEASE CHECK FAILED — Do not proceed with release"
  exit 1
else
  echo "✅ PRE-RELEASE CHECK PASSED — Safe to proceed"
fi

Deployment Execution (T-0)​

#!/bin/bash
# deploy-production.sh
set -euo pipefail

SERVICE=$1
VERSION=$2
STRATEGY=${3:-canary}  # canary | blue-green | rolling

echo "╔══════════════════════════════════════════════════╗"
echo "║         PRODUCTION DEPLOYMENT                    ║"
echo "╠══════════════════════════════════════════════════╣"
echo "║ Service:    $SERVICE"
echo "║ Version:    $VERSION"
echo "║ Strategy:   $STRATEGY"
echo "║ Operator:   $(whoami)"
echo "║ Timestamp:  $(date -u +%Y-%m-%dT%H:%M:%SZ)"
echo "╚══════════════════════════════════════════════════╝"

# Step 1: Create change record
echo ""
echo "Step 1/6: Creating change record..."
CHANGE_ID="CHG-$(date +%Y%m%d%H%M%S)"
echo "  Change record: $CHANGE_ID"

# Step 2: Notify team
echo ""
echo "Step 2/6: Notifying team..."
curl -s -X POST "$SLACK_WEBHOOK" -H 'Content-Type: application/json' \
  -d "{\"text\": \"🚀 Deploying $SERVICE v$VERSION to production ($STRATEGY) — $CHANGE_ID\"}" \
  > /dev/null

# Step 3: Update GitOps repo with new image tag
echo ""
echo "Step 3/6: Updating GitOps repository..."
cd /tmp && rm -rf gitops-repo
git clone "$GITOPS_REPO_URL" gitops-repo
cd gitops-repo

# Update image tag in kustomization
cd "services/$SERVICE/overlays/production"
kustomize edit set image \
  "gcr.io/my-project/$SERVICE=gcr.io/my-project/$SERVICE:$VERSION"
git add .
git commit -m "release($SERVICE): deploy v$VERSION to production [$CHANGE_ID]"
git push origin main

# Step 4: Wait for ArgoCD sync
echo ""
echo "Step 4/6: Waiting for ArgoCD sync..."
argocd app sync "$SERVICE-production" --prune
argocd app wait "$SERVICE-production" --health --timeout 600

# Step 5: Verify deployment
echo ""
echo "Step 5/6: Post-deployment verification..."
sleep 30  # Allow metrics to accumulate

HEALTH=$(curl -s -o /dev/null -w "%{http_code}" \
  "https://api.example.com/$SERVICE/health")
CURRENT_IMAGE=$(kubectl get deployment "$SERVICE" -n production \
  -o jsonpath='{.spec.template.spec.containers[0].image}')

echo "  Health check: $HEALTH"
echo "  Running image: $CURRENT_IMAGE"

if [ "$HEALTH" != "200" ]; then
  echo "❌ Health check failed! Initiating rollback..."
  kubectl rollout undo deployment/"$SERVICE" -n production
  curl -s -X POST "$SLACK_WEBHOOK" -H 'Content-Type: application/json' \
    -d "{\"text\": \"🚨 ROLLBACK: $SERVICE v$VERSION failed health check — rolled back\"}"
  exit 1
fi

# Step 6: Final status
echo ""
echo "Step 6/6: Deployment complete!"
echo "✅ $SERVICE v$VERSION deployed successfully to production"

curl -s -X POST "$SLACK_WEBHOOK" -H 'Content-Type: application/json' \
  -d "{\"text\": \"✅ $SERVICE v$VERSION deployed to production — all checks passed\"}" \
  > /dev/null

echo ""
echo "📊 Monitor dashboards for the next 30 minutes:"
echo "   Grafana: https://grafana.example.com/d/$SERVICE"
echo "   Logs:    https://logging.example.com/explore?service=$SERVICE"
echo "   Alerts:  https://pagerduty.example.com/services/$SERVICE"

Release Process in a Nutshell​

┌─────────────────────── RELEASE QUICK REFERENCE ───────────────────────────┐
│                                                                           │
│  📝 BEFORE CODING                                                         │
│  ├── Create feature branch from develop/main                              │
│  ├── Follow conventional commit messages                                  │
│  └── Write tests alongside code                                          │
│                                                                           │
│  🔀 BEFORE MERGING                                                        │
│  ├── All CI checks green                                                  │
│  ├── 2+ code review approvals                                             │
│  ├── Security scans clean                                                 │
│  └── Squash commits (clean history)                                       │
│                                                                           │
│  📦 BEFORE RELEASING                                                      │
│  ├── Version bumped (SemVer)                                              │
│  ├── Changelog / release notes written                                    │
│  ├── Staging validation complete                                          │
│  ├── Pre-release checklist signed off                                     │
│  └── Release window confirmed (MTWTh, not Friday)                         │
│                                                                           │
│  🚀 DURING RELEASE                                                        │
│  ├── Deploy canary (5% → 25% → 50% → 100%)                              │
│  ├── Monitor error rate, latency, throughput                              │
│  ├── Auto-rollback on analysis failure                                    │
│  └── Notify #releases channel at each stage                               │
│                                                                           │
│  ✅ AFTER RELEASE                                                         │
│  ├── Post-deploy health checks pass                                       │
│  ├── Monitor for 30 minutes                                               │
│  ├── Update release status                                                │
│  └── Run retrospective (if issues occurred)                               │
│                                                                           │
│  🚫 NEVER                                                                 │
│  ├── Deploy on Friday afternoon                                           │
│  ├── Skip staging                                                         │
│  ├── Deploy without a rollback plan                                       │
│  ├── Deploy during code freeze                                            │
│  └── Deploy without monitoring in place                                   │
│                                                                           │
└───────────────────────────────────────────────────────────────────────────┘
