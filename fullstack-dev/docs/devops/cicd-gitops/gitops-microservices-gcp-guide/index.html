GitOps Microservices Deployment Guide: Node.js on GCP GKE with Kustomize and ArgoCD

This comprehensive guide demonstrates how to implement GitOps workflows for deploying Node.js microservices to Google Cloud Platform (GCP) Google Kubernetes Engine (GKE) using Infrastructure as Code principles with Kustomize for configuration management and ArgoCD for continuous deployment.

Architecture Overview​

GitOps Flow Architecture​

graph TD
    A[Developer] --> B[Source Code Repository]
    B --> C[CI Pipeline - GitHub Actions]
    C --> D[Build & Test]
    D --> E[Container Build]
    E --> F[Security Scanning]
    F --> G[Push to Registry]
    G --> H[Update GitOps Repository]
    H --> I[ArgoCD Sync]
    I --> J[GKE Cluster Deployment]

    K[Infrastructure Repository] --> L[Terraform]
    L --> M[GCP Resources]
    M --> N[GKE Cluster]
    M --> O[Cloud SQL]
    M --> P[Cloud Storage]

    Q[GitOps Repository] --> R[Kustomize Base]
    Q --> S[Environment Overlays]
    S --> T[Development]
    S --> U[Staging]
    S --> V[Production]

    W[ArgoCD] --> X[Application Sync]
    X --> Y[Health Monitoring]
    Y --> Z[Automated Rollback]

Repository Strategy​

Our GitOps implementation follows a multi-repository pattern:

  1. Application Repositories: Source code for each microservice
  2. Infrastructure Repository: Terraform configurations for GCP resources
  3. GitOps Repository: Kubernetes manifests and Kustomize configurations
  4. Shared Libraries Repository: Common configurations and utilities

GKE Cluster Module​

# terraform/modules/gke/main.tf
resource "google_container_cluster" "primary" {
  name     = var.cluster_name
  location = var.region

  # Remove default node pool
  remove_default_node_pool = true
  initial_node_count       = 1

  # Network configuration
  network    = var.vpc_name
  subnetwork = var.subnet_name

  # Enable workload identity
  workload_identity_config {
    workload_pool = "${var.project_id}.svc.id.goog"
  }

  # Enable network policy
  network_policy {
    enabled = true
  }

  # Private cluster configuration
  private_cluster_config {
    enable_private_nodes    = true
    enable_private_endpoint = false
    master_ipv4_cidr_block  = "172.16.0.0/28"
  }

  # Master authorized networks
  master_authorized_networks_config {
    cidr_blocks {
      cidr_block   = "10.0.0.0/8"
      display_name = "internal"
    }
  }

  # Enable logging and monitoring
  logging_service    = "logging.googleapis.com/kubernetes"
  monitoring_service = "monitoring.googleapis.com/kubernetes"

  # Addons
  addons_config {
    horizontal_pod_autoscaling {
      disabled = false
    }
    network_policy_config {
      disabled = false
    }
    istio_config {
      disabled = false
      auth     = "AUTH_MUTUAL_TLS"
    }
  }
}

resource "google_container_node_pool" "primary_nodes" {
  name       = "${var.cluster_name}-node-pool"
  location   = var.region
  cluster    = google_container_cluster.primary.name
  node_count = var.node_count

  node_config {
    preemptible  = var.preemptible
    machine_type = var.machine_type
    disk_size_gb = var.disk_size_gb
    disk_type    = "pd-ssd"

    # Google service account
    service_account = google_service_account.gke_nodes.email
    oauth_scopes = [
      "https://www.googleapis.com/auth/logging.write",
      "https://www.googleapis.com/auth/monitoring",
      "https://www.googleapis.com/auth/devstorage.read_only"
    ]

    # Workload Identity
    workload_metadata_config {
      mode = "GKE_METADATA"
    }

    labels = var.node_labels
    tags   = var.node_tags
  }

  autoscaling {
    min_node_count = var.min_node_count
    max_node_count = var.max_node_count
  }

  management {
    auto_repair  = true
    auto_upgrade = true
  }
}

resource "google_service_account" "gke_nodes" {
  account_id   = "${var.cluster_name}-nodes"
  display_name = "GKE Nodes Service Account"
}

kind: Deployment
metadata:
  name: user-service
  labels:
    app: user-service
    version: v1
spec:
  replicas: 2
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
        version: v1
    spec:
      serviceAccountName: user-service
      containers:
        - name: user-service
          image: gcr.io/PROJECT_ID/user-service:latest
          ports:
            - containerPort: 3000
              name: http
          env:
            - name: NODE_ENV
              value: production
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: user-service-secrets
                  key: database-url
            - name: JWT_SECRET
              valueFrom:
                secretKeyRef:
                  name: user-service-secrets
                  key: jwt-secret
          resources:
            requests:
              memory: '256Mi'
              cpu: '250m'
            limits:
              memory: '512Mi'
              cpu: '500m'
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 30
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 5
          securityContext:
            allowPrivilegeEscalation: false
            runAsNonRoot: true
            runAsUser: 1000
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
---
apiVersion: v1
kind: Service
metadata:
  name: user-service
  labels:
    app: user-service

  ports:

Pod Disruption Budget​

Pod Disruption Budgets (PDB) ensure high availability during voluntary disruptions like node maintenance, cluster upgrades, or deployments.

# applications/user-service/overlays/production/pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb
  labels:
    app: user-service
    component: backend
spec:
  # Ensure at least 2 pods are always running
  minAvailable: 2

  # Alternative: Allow maximum 1 pod to be disrupted at a time
  # maxUnavailable: 1

  selector:
    matchLabels:
      app: user-service
PDB Configuration Examples​

Option 1: Minimum Available Pods

# Best for critical services - guarantees minimum capacity
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-min-available
spec:
  minAvailable: 2 # Always keep at least 2 pods running
  selector:
    matchLabels:
      app: user-service

Option 2: Maximum Unavailable Pods

# More flexible - allows percentage-based disruptions
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-max-unavailable
spec:
  maxUnavailable: 1 # Allow maximum 1 pod disruption
  selector:
    matchLabels:
      app: user-service

Option 3: Percentage-Based PDB

# Scales with deployment size
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-percentage
spec:
  minAvailable: 75% # Keep 75% of pods available
  # Alternative: maxUnavailable: 25%
  selector:
    matchLabels:
      app: user-service

Option 4: Environment-Specific PDB

# Different strategies per environment
# Production - Conservative approach
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-prod
  namespace: microservices-prod
spec:
  minAvailable: 80% # Keep 80% available in production
  selector:
    matchLabels:
      app: user-service
      environment: production
---
# Staging - More aggressive updates allowed
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-staging
  namespace: microservices-staging
spec:
  maxUnavailable: 50% # Allow 50% disruption in staging
  selector:
    matchLabels:
      app: user-service
      environment: staging
Advanced PDB with Multiple Selectors​
# applications/user-service/overlays/production/pdb-advanced.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb-advanced
  labels:
    app: user-service
    component: backend
    managed-by: argocd
spec:
  # Use percentage for better scaling
  minAvailable: 66% # At least 2/3 of pods must remain available

  selector:
    matchLabels:
      app: user-service
      tier: backend
    matchExpressions:
      - key: version
        operator: In
        values: ['v1', 'v2'] # Apply to specific versions only

# applications/user-service/base/pdb-template.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: user-service-pdb
  labels:
    app: user-service
    component: backend
  annotations:
    # Document the rationale
    description: 'Ensures high availability during cluster maintenance'
    contact: 'platform-team@company.com'
    runbook: 'https://runbooks.company.com/pdb-user-service'
spec:
  # Start conservative, tune based on SLO requirements
  minAvailable: 2

  selector:
    matchLabels:
      app: user-service

  # Note: PDB only protects against voluntary disruptions
  # - Node maintenance
  # - Cluster upgrades
  # - kubectl drain
  # - Deployment updates with rolling strategy
  #
  # Does NOT protect against:
  # - Node failures
  # - Pod crashes
  # - Resource exhaustion

PDB Monitoring and Alerting​
# monitoring/pdb-alerts.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: pdb-alerts
  namespace: microservices-prod
spec:
  groups:
    - name: pdb.rules
      rules:
        - alert: PodDisruptionBudgetViolation
          expr: |
            kube_poddisruptionbudget_status_current_healthy < 
            kube_poddisruptionbudget_status_desired_healthy
          for: 5m
          labels:
            severity: warning
            component: pdb
          annotations:
            summary: 'Pod Disruption Budget violated for {{ $labels.poddisruptionbudget }}'
            description: 'PDB {{ $labels.poddisruptionbudget }} in namespace {{ $labels.namespace }} has {{ $value }} healthy pods, but requires {{ $labels.desired_healthy }}'

        - alert: PodDisruptionBudgetAtLimit
          expr: |
            kube_poddisruptionbudget_status_current_healthy == 
            kube_poddisruptionbudget_status_desired_healthy
          for: 2m
          labels:
            severity: info
            component: pdb
          annotations:
            summary: 'Pod Disruption Budget at minimum for {{ $labels.poddisruptionbudget }}'
            description: 'PDB {{ $labels.poddisruptionbudget }} is at its minimum healthy pod count. Any disruption will violate the budget.'
Validation and Testing​
# Check PDB status
kubectl get pdb -n microservices-prod
kubectl describe pdb user-service-pdb -n microservices-prod

# Test PDB during deployment
kubectl rollout status deployment/user-service -n microservices-prod

# Simulate disruption (be careful in production!)
kubectl drain NODE_NAME --ignore-daemonsets --delete-emptydir-data

# Check if PDB prevents disruption
kubectl get pdb user-service-pdb -n microservices-prod -o yaml

# Validate PDB covers your pods
kubectl get pods -n microservices-prod -l app=user-service
kubectl get pdb user-service-pdb -n microservices-prod -o jsonpath='{.status}'
Troubleshooting PDB Issues​
# Common PDB problems and solutions

# 1. PDB preventing all disruptions
kubectl get pdb -n microservices-prod
# Solution: Increase replica count or adjust minAvailable

# 2. Pods not matching PDB selector
kubectl get pods -n microservices-prod --show-labels
kubectl get pdb user-service-pdb -n microservices-prod -o yaml
# Solution: Fix label selectors

# 3. PDB with zero disruptions allowed
kubectl describe pdb user-service-pdb -n microservices-prod
# Solution: Adjust minAvailable or maxUnavailable values

# 4. Check PDB events
kubectl get events -n microservices-prod --field-selector involvedObject.kind=PodDisruptionBudget

# 5. Force bypass PDB (emergency only!)
kubectl delete pdb user-service-pdb -n microservices-prod
# Remember to recreate after emergency maintenance

Pod Disruption Budget for StatefulSets​

StatefulSets require special consideration for PDB configuration due to their stateful nature and ordered deployment/scaling requirements. This is particularly important for distributed systems like Kafka, Elasticsearch, or databases.

Kafka StatefulSet PDB Configuration​

# infrastructure/kafka/base/kafka-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  labels:
    app: kafka
    component: broker
spec:
  serviceName: kafka-headless
  replicas: 3
  podManagementPolicy: Parallel # Important for Kafka
  selector:
    matchLabels:
      app: kafka
  template:
    metadata:
      labels:
        app: kafka
        component: broker
    spec:
      containers:
        - name: kafka
          image: confluentinc/cp-kafka:7.4.0
          ports:
            - containerPort: 9092
              name: kafka
            - containerPort: 9093
              name: kafka-internal
          env:
            - name: KAFKA_BROKER_ID
              valueFrom:
                fieldRef:
                  fieldPath: metadata.annotations['kafka.apache.org/broker-id']
            - name: KAFKA_ZOOKEEPER_CONNECT
              value: 'zookeeper:2181'
            - name: KAFKA_ADVERTISED_LISTENERS
              value: 'PLAINTEXT://$(POD_NAME).kafka-headless:9092'
          volumeMounts:
            - name: kafka-data
              mountPath: /var/lib/kafka/data
          resources:
            requests:
              memory: '1Gi'
              cpu: '500m'
            limits:
              memory: '2Gi'
              cpu: '1000m'
          readinessProbe:
            tcpSocket:
              port: 9092
            initialDelaySeconds: 30
            periodSeconds: 10
          livenessProbe:
            tcpSocket:
              port: 9092
            initialDelaySeconds: 60
            periodSeconds: 30
  volumeClaimTemplates:
    - metadata:
        name: kafka-data
      spec:
        accessModes: ['ReadWriteOnce']
        resources:
          requests:
            storage: 100Gi
        storageClassName: fast-ssd

Kafka PDB - Conservative Approach​

# infrastructure/kafka/base/kafka-pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: kafka-pdb
  labels:
    app: kafka
    component: broker
  annotations:
    description: 'Ensures Kafka cluster maintains quorum during maintenance'

#!/bin/bash
# scripts/validate-kafka-pdb.sh

set -euo pipefail

NAMESPACE=${1:-kafka-prod}
KAFKA_CLUSTER=${2:-kafka}

echo "=== Validating Kafka PDB Configuration ==="

# Check if PDB exists
echo "1. Checking PDB existence..."
kubectl get pdb ${KAFKA_CLUSTER}-pdb -n $NAMESPACE

# Check PDB status
echo "2. Checking PDB status..."
PDB_STATUS=$(kubectl get pdb ${KAFKA_CLUSTER}-pdb -n $NAMESPACE -o jsonpath='{.status}')
echo "PDB Status: $PDB_STATUS"

# Check current healthy pods
CURRENT_HEALTHY=$(kubectl get pdb ${KAFKA_CLUSTER}-pdb -n $NAMESPACE -o jsonpath='{.status.currentHealthy}')
DESIRED_HEALTHY=$(kubectl get pdb ${KAFKA_CLUSTER}-pdb -n $NAMESPACE -o jsonpath='{.status.desiredHealthy}')

echo "3. PDB Health Status:"
echo "   Current Healthy: $CURRENT_HEALTHY"
echo "   Desired Healthy: $DESIRED_HEALTHY"

# Validate pod labels match PDB selector
echo "4. Validating pod selector matching..."
kubectl get pods -n $NAMESPACE -l app=$KAFKA_CLUSTER --show-labels

# Check StatefulSet ready replicas
READY_REPLICAS=$(kubectl get statefulset $KAFKA_CLUSTER -n $NAMESPACE -o jsonpath='{.status.readyReplicas}')
TOTAL_REPLICAS=$(kubectl get statefulset $KAFKA_CLUSTER -n $NAMESPACE -o jsonpath='{.spec.replicas}')

echo "5. StatefulSet Status:"
echo "   Ready Replicas: $READY_REPLICAS"
echo "   Total Replicas: $TOTAL_REPLICAS"

# Test disruption simulation (dry-run)
echo "6. Testing disruption simulation (dry-run)..."
kubectl drain $(kubectl get nodes -o name | head -1) --dry-run=client --ignore-daemonsets --delete-emptydir-data

echo "=== Validation Complete ==="

# applications/user-service/base/monitoring.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: user-service
  labels:
    app: user-service

  selector:
    matchLabels:
      app: user-service
  endpoints:

      path: /metrics
      interval: 30s
      scrapeTimeout: 10s

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: user-service-alerts
  labels:
    app: user-service
spec:
  groups:
    - name: user-service.rules
      rules:
        - alert: UserServiceHighErrorRate
          expr: |
            (
              rate(http_requests_total{app="user-service",code=~"5.."}[5m]) /
              rate(http_requests_total{app="user-service"}[5m])
            ) > 0.1
          for: 5m
          labels:
            severity: warning
            service: user-service
          annotations:
            summary: 'High error rate for user service'
            description: 'Error rate is {{ $value | humanizePercentage }} for user service'

        - alert: UserServiceHighLatency
          expr: |
            histogram_quantile(0.95,
              rate(http_request_duration_seconds_bucket{app="user-service"}[5m])
            ) > 0.5
          for: 5m
          labels:
            severity: warning
            service: user-service
          annotations:
            summary: 'High latency for user service'
            description: '95th percentile latency is {{ $value }}s for user service'

Troubleshooting​

Common Issues and Solutions​

ArgoCD Application Not Syncing​

# Check application status
argocd app get user-service-prod

# Force sync
argocd app sync user-service-prod

# Check for differences
argocd app diff user-service-prod

# View application logs
kubectl logs -n argocd deployment/argocd-application-controller

Kustomize Build Errors​

# Validate kustomization
kustomize build applications/user-service/overlays/production

# Check for syntax errors
kustomize build applications/user-service/overlays/production --enable-alpha-plugins

# Debug with verbose output
kustomize build applications/user-service/overlays/production -v 10

Image Pull Errors​

# Check image exists
gcloud container images list --repository=gcr.io/PROJECT_ID

# Verify service account permissions
kubectl describe pod POD_NAME

# Check imagePullSecrets
kubectl get secret -n NAMESPACE

Debugging Commands​

# ArgoCD CLI commands
argocd app list
argocd app get APP_NAME
argocd app sync APP_NAME --dry-run
argocd app history APP_NAME
argocd app rollback APP_NAME REVISION

# Kubernetes debugging
kubectl get applications -n argocd
kubectl describe application APP_NAME -n argocd
kubectl logs -f deployment/DEPLOYMENT_NAME -n NAMESPACE
kubectl get events --sort-by=.metadata.creationTimestamp

# Kustomize debugging
kustomize build PATH --enable-alpha-plugins
kustomize edit set image IMAGE_NAME:TAG
kustomize cfg tree PATH

Health Checks and Validation​

# Check cluster health
kubectl get nodes
kubectl get pods --all-namespaces
kubectl top nodes
kubectl top pods --all-namespaces

# Validate deployments
kubectl rollout status deployment/DEPLOYMENT_NAME -n NAMESPACE
kubectl get hpa -n NAMESPACE
kubectl describe service SERVICE_NAME -n NAMESPACE

# Network troubleshooting
kubectl exec -it POD_NAME -- nslookup SERVICE_NAME
kubectl exec -it POD_NAME -- curl http://SERVICE_NAME/health
