GKE Fleet: Multi-Cluster Management

Google Kubernetes Engine (GKE) Fleet is a unified way to manage multiple Kubernetes clusters—across regions, projects, and even clouds—as a single logical fleet. It enables centralized policy, configuration, and workload management, supporting hybrid and multi-cloud environments.

Use Cases​

  • Centralized security and policy enforcement across clusters
  • Consistent configuration and GitOps (Config Sync)
  • Multi-cluster service discovery and load balancing
  • Workload identity and access management
  • Hybrid and multi-cloud application deployment

Architecture Overview​

Key Features​

  • Centralized Identity & Access: Manage users and permissions across clusters.
  • Config Sync: Enforce consistent configuration and policy using GitOps.
  • Multi-Cluster Services: Expose and discover services across clusters.
  • Workload Identity: Securely manage service accounts and identities.
  • Anthos Integration: Seamless integration with Anthos for hybrid/multi-cloud.

Prerequisites​

  • Google Cloud project with billing enabled
  • GKE clusters (zonal, regional, or on-prem)
  • gcloud CLI installed and authenticated

Step 1: Enable Fleet API​

gcloud services enable gkehub.googleapis.com

Step 2: Register Clusters to the Fleet​

For GKE Clusters​

gcloud container hub memberships register <CLUSTER_NAME> \
  --gke-cluster=<REGION>/<CLUSTER_NAME> \
  --project=<PROJECT_ID>

For Non-GKE (On-Prem/Other Cloud) Clusters​

gcloud container hub memberships register <CLUSTER_NAME> \
  --context=<KUBECONFIG_CONTEXT> \
  --kubeconfig=<KUBECONFIG_PATH> \
  --project=<PROJECT_ID>

See Registering non-GKE clusters for details.

Step 3: Verify Fleet Membership​

gcloud container hub memberships list

Step 4: Enable Config Sync (Optional)​

gcloud beta container hub config-management enable

Step 5: Enable Multi-Cluster Service Discovery (Optional)​

gcloud container hub multi-cluster-services enable

Cross-Cluster Service Communication​

One of the key benefits of GKE Fleet is the ability for services in one cluster to communicate with services in another cluster. This enables advanced architectures like:

  • Geographic distribution: Frontend in one region, backend in another
  • Environment isolation: Dev services calling shared staging databases
  • High availability: Failover between clusters in different regions
  • Specialized workloads: GPU cluster accessing data from general-purpose cluster

Architecture: Service A (Cluster A) → Service B (Cluster B)​

Prerequisites for Cross-Cluster Communication​

  1. Fleet Membership: Both clusters must be registered to the same fleet
  2. Multi-Cluster Services Enabled: Enable MCS feature on the fleet
  3. Network Connectivity: Clusters must be able to reach each other (same VPC or VPC peering)
  4. Firewall Rules: Allow traffic between cluster pod CIDR ranges

Step-by-Step Setup​

1. Verify Fleet and Enable Multi-Cluster Services​

# Verify both clusters are in the fleet
gcloud container fleet memberships list

# Enable Multi-Cluster Services
gcloud container fleet multi-cluster-services enable

# Verify MCS is enabled
gcloud container fleet multi-cluster-services describe

2. Configure Network Connectivity​

Option A: Clusters in Same VPC (Recommended)

# When creating clusters, use the same VPC
gcloud container clusters create cluster-a \
  --region=us-central1 \
  --network=shared-vpc \
  --subnetwork=subnet-central \
  --enable-ip-alias \
  --cluster-secondary-range-name=pods-central \
  --services-secondary-range-name=services-central

gcloud container clusters create cluster-b \
  --region=us-east1 \
  --network=shared-vpc \
  --subnetwork=subnet-east \
  --enable-ip-alias \
  --cluster-secondary-range-name=pods-east \
  --services-secondary-range-name=services-east

Option B: VPC Peering for Existing Clusters

# Create VPC peering between cluster networks
gcloud compute networks peerings create cluster-a-to-b \
  --network=vpc-cluster-a \
  --peer-network=vpc-cluster-b \
  --auto-create-routes

gcloud compute networks peerings create cluster-b-to-a \
  --network=vpc-cluster-b \
  --peer-network=vpc-cluster-a \
  --auto-create-routes

3. Configure Firewall Rules​

# Get pod CIDR ranges for both clusters
CLUSTER_A_POD_CIDR=$(gcloud container clusters describe cluster-a \
  --region=us-central1 \
  --format="value(clusterIpv4Cidr)")

CLUSTER_B_POD_CIDR=$(gcloud container clusters describe cluster-b \
  --region=us-east1 \
  --format="value(clusterIpv4Cidr)")

# Allow traffic from Cluster A pods to Cluster B pods
gcloud compute firewall-rules create allow-cluster-a-to-b \
  --network=shared-vpc \
  --allow=tcp,udp,icmp,esp,ah,sctp \
  --source-ranges=${CLUSTER_A_POD_CIDR} \
  --destination-ranges=${CLUSTER_B_POD_CIDR} \
  --description="Allow Cluster A to Cluster B communication"

# Allow traffic from Cluster B pods to Cluster A pods
gcloud compute firewall-rules create allow-cluster-b-to-a \
  --network=shared-vpc \
  --allow=tcp,udp,icmp,esp,ah,sctp \
  --source-ranges=${CLUSTER_B_POD_CIDR} \
  --destination-ranges=${CLUSTER_A_POD_CIDR} \
  --description="Allow Cluster B to Cluster A communication"

Application Code Example (Node.js/NestJS)​

// service-a/src/services/service-b-client.service.ts
import { Injectable, HttpService } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

@Injectable()
export class ServiceBClient {
  private readonly serviceBUrl: string;

  constructor(private readonly httpService: HttpService, private readonly configService: ConfigService) {
    // Multi-cluster DNS: service-b.backend.svc.clusterset.local
    this.serviceBUrl = this.configService.get('SERVICE_B_URL');
  }

  async getUserData(userId: string) {
    try {
      const response = await this.httpService.get(`${this.serviceBUrl}/api/users/${userId}`).toPromise();

      return response.data;
    } catch (error) {
      console.error('Error calling Service B:', error.message);
      throw error;
    }
  }

  async createOrder(orderData: any) {
    try {
      const response = await this.httpService.post(`${this.serviceBUrl}/api/orders`, orderData).toPromise();

      return response.data;
    } catch (error) {
      console.error('Error creating order in Service B:', error.message);
      throw error;
    }
  }
}

apiVersion: networking.istio.io/v1beta1
kind: VirtualService

  name: service-b-routing
  namespace: backend
spec:
  hosts:
    - service-b.backend.svc.clusterset.local

        - destination:
            host: service-b.backend.svc.cluster.local # Local cluster
          weight: 70
        - destination:
            host: service-b.backend.svc.clusterset.local # Remote cluster
          weight: 30

Ingress → NGINX Proxy → Cross-Cluster Service​

This example shows how to expose an external Ingress in Cluster A that routes to an NGINX proxy, which then forwards traffic to Service B in Cluster B. In this scenario, the two clusters belong to different GCP projects but share the same Fleet.

  • API Gateway: Central entry point with routing logic
  • SSL Termination: Handle TLS at the proxy level
  • Load Balancing: Advanced routing and canary deployments
  • Request Transformation: Add headers, modify paths, etc.
  • Multi-Project Architecture: Clusters in separate projects for isolation

Architecture Details:

  • Fleet Host Project: fleet-management - Centralized fleet management
  • Project A: frontend-project - Contains Cluster A with Ingress and NGINX proxy
  • Project B: backend-project - Contains Cluster B with Service B
  • Both clusters are registered to the same fleet for multi-cluster service discovery

Step 0: Setup Multi-Project Fleet

First, configure the fleet and register both clusters from their respective projects:

# ============================================
# Fleet Host Project Configuration
# ============================================
export FLEET_PROJECT_ID="fleet-management"
export FLEET_PROJECT_NUMBER=$(gcloud projects describe ${FLEET_PROJECT_ID} --format="value(projectNumber)")

# Project A (Frontend/Ingress)
export PROJECT_A_ID="frontend-project"
export CLUSTER_A_NAME="cluster-a"
export CLUSTER_A_REGION="us-central1"

# Project B (Backend Services)
export PROJECT_B_ID="backend-project"
export CLUSTER_B_NAME="cluster-b"
export CLUSTER_B_REGION="us-east1"

# ============================================
# 1. Enable APIs in Fleet Host Project
# ============================================
gcloud config set project ${FLEET_PROJECT_ID}

gcloud services enable \
  gkehub.googleapis.com \
  multiclusterservicediscovery.googleapis.com \
  multiclusteringress.googleapis.com \
  --project=${FLEET_PROJECT_ID}

# ============================================
# 2. Grant Permissions for Project A
# ============================================
# Enable GKE Hub API in Project A
gcloud services enable gkehub.googleapis.com --project=${PROJECT_A_ID}

# Grant fleet host project access to Project A
gcloud projects add-iam-policy-binding ${PROJECT_A_ID} \
  --member="serviceAccount:service-${FLEET_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
  --role="roles/gkehub.connect" \
  --project=${PROJECT_A_ID}

gcloud projects add-iam-policy-binding ${PROJECT_A_ID} \
  --member="serviceAccount:service-${FLEET_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
  --role="roles/container.viewer" \
  --project=${PROJECT_A_ID}

# ============================================
# 3. Grant Permissions for Project B
# ============================================
# Enable GKE Hub API in Project B
gcloud services enable gkehub.googleapis.com --project=${PROJECT_B_ID}

# Grant fleet host project access to Project B
gcloud projects add-iam-policy-binding ${PROJECT_B_ID} \
  --member="serviceAccount:service-${FLEET_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
  --role="roles/gkehub.connect" \
  --project=${PROJECT_B_ID}

gcloud projects add-iam-policy-binding ${PROJECT_B_ID} \
  --member="serviceAccount:service-${FLEET_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
  --role="roles/container.viewer" \
  --project=${PROJECT_B_ID}

# ============================================
# 4. Register Cluster A to Fleet
# ============================================
gcloud container fleet memberships register ${CLUSTER_A_NAME} \
  --gke-cluster=${CLUSTER_A_REGION}/${CLUSTER_A_NAME} \
  --project=${PROJECT_A_ID} \
  --fleet-project=${FLEET_PROJECT_ID}

# ============================================
# 5. Register Cluster B to Fleet
# ============================================
gcloud container fleet memberships register ${CLUSTER_B_NAME} \
  --gke-cluster=${CLUSTER_B_REGION}/${CLUSTER_B_NAME} \
  --project=${PROJECT_B_ID} \
  --fleet-project=${FLEET_PROJECT_ID}

# ============================================
# 6. Enable Multi-Cluster Services
# ============================================
gcloud container fleet multi-cluster-services enable \
  --project=${FLEET_PROJECT_ID}

# ============================================
# 7. Verify Fleet Membership
# ============================================
gcloud container fleet memberships list --project=${FLEET_PROJECT_ID}

# Expected output:
# NAME       EXTERNAL_ID                                           LOCATION
# cluster-a  xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx                  us-central1
# cluster-b  yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy                  us-east1

# ============================================
# 8. Configure Network Connectivity
# ============================================
# Option 1: Use Shared VPC (Recommended)
# Create shared VPC in fleet project or separate networking project

# Option 2: VPC Peering between Project A and Project B
gcloud compute networks peerings create project-a-to-b \
  --network=vpc-cluster-a \
  --peer-project=${PROJECT_B_ID} \
  --peer-network=vpc-cluster-b \
  --project=${PROJECT_A_ID}

gcloud compute networks peerings create project-b-to-a \
  --network=vpc-cluster-b \
  --peer-project=${PROJECT_A_ID} \
  --peer-network=vpc-cluster-a \
  --project=${PROJECT_B_ID}

# ============================================
# 9. Configure Firewall Rules
# ============================================
# Get pod CIDR ranges
CLUSTER_A_POD_CIDR=$(gcloud container clusters describe ${CLUSTER_A_NAME} \
  --region=${CLUSTER_A_REGION} \

CLUSTER_B_POD_CIDR=$(gcloud container clusters describe ${CLUSTER_B_NAME} \

# Allow Project A pods to reach Project B pods
gcloud compute firewall-rules create allow-cluster-a-to-b \
  --network=vpc-cluster-b \

# Allow Project B pods to reach Project A pods (if needed)
gcloud compute firewall-rules create allow-cluster-b-to-a \
  --network=vpc-cluster-a \
  --allow=tcp,udp,icmp \
  --source-ranges=${CLUSTER_B_POD_CIDR} \

echo "✅ Multi-project fleet setup complete!"
echo "Fleet Project: ${FLEET_PROJECT_ID}"

Step 2: Deploy NGINX Proxy in Cluster A (Project A)

# cluster-a/nginx-proxy-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-proxy-config
  namespace: proxy
  labels:
    app: nginx-proxy
    project: frontend-project
data:
  nginx.conf: |
    events {
      worker_connections 1024;
    }

    http {
      # Logging
      access_log /var/log/nginx/access.log;
      error_log /var/log/nginx/error.log;
      
      # Upstream to Service B in Cluster B (different project)
      # This uses multi-cluster DNS provided by GKE Fleet
      upstream service_b_backend {
        # Multi-cluster DNS name - resolves across projects via fleet
        server service-b.backend.svc.clusterset.local:80;
        
        # Connection settings
        keepalive 32;
        keepalive_timeout 60s;
      }
      
      # Server block
      server {
        listen 8080;
        server_name _;
        
        # Health check endpoint
        location /health {
          access_log off;
          return 200 "healthy\n";
          add_header Content-Type text/plain;
        }
        
        # Proxy to Service B
        location /api/ {
          # Remove /api prefix before forwarding
          rewrite ^/api/(.*)$ /$1 break;
          
          proxy_pass http://service_b_backend;
          
          # Headers
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
          proxy_set_header X-Forwarded-Proto $scheme;
          proxy_set_header X-Cluster-Source "cluster-a";
          
          # Timeouts
          proxy_connect_timeout 5s;
          proxy_send_timeout 60s;
          proxy_read_timeout 60s;
          
          # Buffering
          proxy_buffering on;
          proxy_buffer_size 4k;
          proxy_buffers 8 4k;
          
          # Connection reuse
          proxy_http_version 1.1;
          proxy_set_header Connection "";
        }
        
        # WebSocket support (if needed)
        location /ws/ {
          rewrite ^/ws/(.*)$ /$1 break;
          
          proxy_pass http://service_b_backend;
          proxy_http_version 1.1;
          proxy_set_header Upgrade $http_upgrade;
          proxy_set_header Connection "upgrade";
          proxy_set_header Host $host;
          proxy_read_timeout 86400;
        }
      }
    }
---

kind: Deployment

  namespace: proxy

  selector:
    matchLabels:
      app: nginx-proxy

            - containerPort: 8080
              name: http

Advanced NGINX Configuration with Caching

# Enhanced nginx.conf with caching and load balancing
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-proxy-config-advanced
  namespace: proxy
data:
  nginx.conf: |
    events {
      worker_connections 2048;
    }

    http {
      # Cache configuration
      proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m 
                       max_size=100m inactive=60m use_temp_path=off;
      
      # Rate limiting
      limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
      
      # Upstream with health checks
      upstream service_b_backend {
        server service-b.backend.svc.clusterset.local:80 max_fails=3 fail_timeout=30s;
        keepalive 32;
      }
      
      server {
        listen 8080;
        
        # Rate limiting
        limit_req zone=api_limit burst=20 nodelay;
        
        location /health {
          access_log off;
          return 200 "healthy\n";
        }
        
        # Cached endpoints
        location /api/public/ {
          rewrite ^/api/public/(.*)$ /public/$1 break;
          
          proxy_pass http://service_b_backend;
          
          # Caching
          proxy_cache api_cache;
          proxy_cache_valid 200 10m;
          proxy_cache_valid 404 1m;
          proxy_cache_key "$scheme$request_method$host$request_uri";
          proxy_cache_bypass $http_cache_control;
          add_header X-Cache-Status $upstream_cache_status;
          
          # Headers
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
          proxy_set_header X-Cluster-Source "cluster-a";
        }
        
        # Non-cached endpoints
        location /api/private/ {
          rewrite ^/api/private/(.*)$ /private/$1 break;
          
          proxy_pass http://service_b_backend;
          proxy_cache_bypass 1;
          proxy_no_cache 1;
          
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
          proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
          proxy_set_header X-Cluster-Source "cluster-a";
          
          # Longer timeout for private APIs
          proxy_read_timeout 120s;
        }
      }
    }

import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';

@Injectable()
export class ClusterInfoMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    // Log the source cluster
    const sourceCluster = req.header('X-Cluster-Source');
    const realIp = req.header('X-Real-IP');
    const forwardedFor = req.header('X-Forwarded-For');

    console.log({
      sourceCluster,
      realIp,
      forwardedFor,
      path: req.path,
      method: req.method,
    });

    // Add cluster info to response headers
    res.setHeader('X-Served-By', 'cluster-b');
    res.setHeader('X-Service', 'service-b');

    next();
  }
}

  configure(consumer: MiddlewareConsumer) {
    consumer.apply(ClusterInfoMiddleware).forRoutes('*');
  }

Benefits of This Pattern

  1. Centralized Entry Point: Single Ingress manages all external traffic
  2. Flexible Routing: NGINX provides advanced routing, rewriting, caching
  3. Security: SSL termination, rate limiting, request filtering at proxy
  4. Observability: Centralized logging and metrics from NGINX
  5. Performance: Caching frequently accessed endpoints
  6. Decoupling: Change backend services without updating Ingress
  7. Multi-Cluster Abstraction: Clients don't need to know about cluster topology
  8. Project Isolation: Separate billing, IAM, and resource quotas per project
  9. Organizational Boundaries: Frontend and backend teams can manage their own projects
  10. Compliance: Meet regulatory requirements for data and workload separation

Multi-Project Architecture Benefits

Project Separation Benefits:
  Security & Compliance:
    - ✅ Separate IAM policies per project
    - ✅ Independent security audits
    - ✅ Data residency compliance per region/project
    - ✅ Blast radius containment

  Operational:
    - ✅ Independent billing and cost tracking
    - ✅ Separate resource quotas and limits
    - ✅ Team autonomy (frontend vs backend teams)
    - ✅ Environment isolation (dev/staging/prod)

  Technical:
    - ✅ Cross-project service discovery via fleet
    - ✅ Centralized policy management
    - ✅ Unified observability across projects
    - ✅ Simplified multi-region deployments

Cost Considerations:
  - Network egress between regions (if clusters in different regions)
  - VPC peering charges (if not using shared VPC)
  - Load balancer costs per project
  - GKE Fleet management overhead (minimal)

Network Architecture Options:
  1. Shared VPC (Recommended):
    - Single VPC across all projects
    - Lower latency, no egress charges within VPC
    - Centralized network management

  2. VPC Peering:
    - Separate VPCs per project
    - Flexible but requires peering setup
    - Potential egress charges between VPCs

  3. VPN/Interconnect:
    - For on-premises or multi-cloud scenarios
    - Higher latency but more secure

// Add latency tracking for cross-cluster calls
import { Injectable } from '@nestjs/common';
import { PrometheusService } from './prometheus.service';

@Injectable()
export class ServiceBClient {
  private readonly latencyHistogram = this.prometheus.createHistogram({
    name: 'service_b_request_duration_seconds',
    help: 'Duration of Service B requests',
    labelNames: ['method', 'status', 'cluster'],
  });

  async getUserData(userId: string) {
    const timer = this.latencyHistogram.startTimer();

    try {
      const response = await this.httpService.get(`${this.serviceBUrl}/api/users/${userId}`).toPromise();

      timer({ method: 'GET', status: '200', cluster: 'cluster-b' });
      return response.data;
    } catch (error) {
      timer({ method: 'GET', status: error.response?.status || '500', cluster: 'cluster-b' });
      throw error;
    }
  }
}

Best Practices for Cross-Cluster Communication​

  1. Use Descriptive DNS Names: service-name.namespace.svc.clusterset.local
  2. Implement Retries: Network calls can fail; use exponential backoff
  3. Set Appropriate Timeouts: Cross-cluster calls have higher latency
  4. Monitor Latency: Track p50, p95, p99 metrics for cross-cluster calls
  5. Use Circuit Breakers: Prevent cascade failures
  6. Cache When Possible: Reduce cross-cluster traffic
  7. Security: Use Workload Identity and mTLS (with service mesh)
  8. Cost Awareness: Cross-region traffic incurs egress charges

Multi-Project Fleet Setup​

When managing multiple GCP projects with one cluster each under a single fleet, you need to designate one project as the Fleet Host Project and register clusters from other projects as fleet members.

Architecture: Multi-Project Fleet​

Prerequisites for Multi-Project Fleet​

  1. Fleet Host Project: A dedicated project to host the fleet (recommended)
  2. Member Projects: Projects containing GKE clusters (dev, staging, prod, etc.)
  3. IAM Permissions: Proper cross-project permissions
  4. Billing: All projects must have billing enabled

Step-by-Step Setup​

1. Choose or Create a Fleet Host Project​

Designate one project as the fleet host. This can be:

  • A dedicated fleet management project (recommended for production)
  • One of your existing projects (e.g., production project)
# Set the fleet host project ID
export FLEET_HOST_PROJECT_ID="my-fleet-host-project"
export FLEET_ID="my-multi-project-fleet"

# Switch to the fleet host project
gcloud config set project ${FLEET_HOST_PROJECT_ID}

2. Enable Required APIs in Fleet Host Project​

# Enable Fleet API in the host project
gcloud services enable gkehub.googleapis.com \
  --project=${FLEET_HOST_PROJECT_ID}

# Enable additional fleet features
gcloud services enable \
  multiclusterservicediscovery.googleapis.com \
  multiclusteringress.googleapis.com \
  anthosconfigmanagement.googleapis.com \
  --project=${FLEET_HOST_PROJECT_ID}

3. Create the Fleet in Host Project​

# Create a fleet (if not using the default fleet)
gcloud container fleet create ${FLEET_ID} \
  --project=${FLEET_HOST_PROJECT_ID}

Note: Each project has a default fleet. For multi-project setups, you can either:

  • Use the default fleet of the host project
  • Create a named fleet for better organization

4. Grant Cross-Project IAM Permissions​

For each member project, grant the fleet host project permission to register clusters:

# Set member project variables
export MEMBER_PROJECT_ID="my-dev-project"

# Grant gkehub.connect permission to the fleet host project

  --member="serviceAccount:service-${FLEET_HOST_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
  --role="roles/container.viewer" \
  --project=${MEMBER_PROJECT_ID}

export FLEET_HOST_PROJECT_NUMBER=$(gcloud projects describe ${FLEET_HOST_PROJECT_ID} --format="value(projectNumber)")

Here's a complete bash script for setting up a multi-project fleet:

#!/bin/bash
set -e

# Configuration
FLEET_HOST_PROJECT_ID="my-fleet-host"
FLEET_ID="production-fleet"

# Member projects and clusters
declare -A PROJECTS=(
  ["dev"]="my-dev-project:dev-cluster:us-central1"
  ["staging"]="my-staging-project:staging-cluster:us-east1"
  ["prod"]="my-prod-project:prod-cluster:us-west1"
)

# Get fleet host project number
FLEET_HOST_PROJECT_NUMBER=$(gcloud projects describe ${FLEET_HOST_PROJECT_ID} \
  --format="value(projectNumber)")

echo "Setting up fleet in host project: ${FLEET_HOST_PROJECT_ID}"

# Step 1: Enable APIs in fleet host
gcloud services enable gkehub.googleapis.com \
  multiclusterservicediscovery.googleapis.com \
  multiclusteringress.googleapis.com \
  anthosconfigmanagement.googleapis.com \
  --project=${FLEET_HOST_PROJECT_ID}

# Step 2: Create fleet (optional, if not using default)
# gcloud container fleet create ${FLEET_ID} --project=${FLEET_HOST_PROJECT_ID}

# Step 3: Configure member projects
for env in "${!PROJECTS[@]}"; do
  IFS=':' read -r PROJECT_ID CLUSTER_NAME REGION <<< "${PROJECTS[$env]}"

  echo "Configuring ${env} environment: ${PROJECT_ID}"

  # Enable GKE Hub API in member project
  gcloud services enable gkehub.googleapis.com --project=${PROJECT_ID}

  # Grant IAM permissions
  gcloud projects add-iam-policy-binding ${PROJECT_ID} \
    --member="serviceAccount:service-${FLEET_HOST_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
    --role="roles/gkehub.connect" \
    --project=${PROJECT_ID}

  gcloud projects add-iam-policy-binding ${PROJECT_ID} \
    --member="serviceAccount:service-${FLEET_HOST_PROJECT_NUMBER}@gcp-sa-gkehub.iam.gserviceaccount.com" \
    --role="roles/container.viewer" \
    --project=${PROJECT_ID}

  # Register cluster to fleet
  gcloud container fleet memberships register ${CLUSTER_NAME} \
    --gke-cluster=${REGION}/${CLUSTER_NAME} \
    --project=${PROJECT_ID} \
    --fleet-project=${FLEET_HOST_PROJECT_ID}

  echo "✓ ${env} cluster registered successfully"
done

# Step 4: Verify fleet membership
echo "Fleet membership summary:"
gcloud container fleet memberships list --project=${FLEET_HOST_PROJECT_ID}

# Step 5: Enable fleet features
echo "Enabling Config Sync..."
gcloud container fleet config-management enable \
  --project=${FLEET_HOST_PROJECT_ID}

echo "Enabling Multi-Cluster Services..."
gcloud container fleet multi-cluster-services enable \
  --project=${FLEET_HOST_PROJECT_ID}

echo "✓ Multi-project fleet setup complete!"

Managing Multi-Project Fleet​

Applying Policies Across All Projects​

Use Config Sync to apply consistent policies across all clusters:

# config-management.yaml
apiVersion: configmanagement.gke.io/v1
kind: ConfigManagement
metadata:
  name: config-management
spec:
  clusterName: CLUSTER_NAME
  git:
    syncRepo: https://github.com/your-org/fleet-config
    syncBranch: main
    secretType: none
    policyDir: 'policies'
  policyController:
    enabled: true

Apply to all clusters:

for cluster in dev-cluster staging-cluster prod-cluster; do
  kubectl apply -f config-management.yaml --context=${cluster}
done

Monitoring Fleet Health​

# View fleet status
gcloud container fleet memberships list \
  --project=${FLEET_HOST_PROJECT_ID} \
  --format="table(name,state.code,uniqueId)"

# Check Config Sync status
gcloud container fleet config-management status \
  --project=${FLEET_HOST_PROJECT_ID}

Unregistering a Cluster​

gcloud container fleet memberships unregister ${CLUSTER_NAME} \
  --project=${MEMBER_PROJECT_ID} \
  --fleet-project=${FLEET_HOST_PROJECT_ID}

Best Practices for Multi-Project Fleets​

  1. Use a Dedicated Fleet Host Project: Keep fleet management separate from workloads
  2. Consistent Naming Convention: Use clear names like {env}-{region}-cluster
  3. Label Your Clusters: Add environment labels for easy filtering 
    gcloud container fleet memberships update ${CLUSTER_NAME} \
      --update-labels=environment=dev,region=us-central1 \
      --project=${FLEET_HOST_PROJECT_ID}
  4. Implement RBAC: Use Workload Identity and IAM for secure cross-project access
  5. Centralized Logging: Send logs from all clusters to a central project
  6. GitOps for Config: Use Config Sync with a single Git repository
  7. Regular Audits: Periodically review fleet membership and permissions

Troubleshooting Multi-Project Setup​

Issue: Registration fails with permission denied

  • Solution: Verify IAM bindings for gkehub.connect role
  • Check project numbers match correctly

Issue: Cluster not appearing in fleet

  • Solution: Ensure both projects have gkehub.googleapis.com enabled
  • Verify network connectivity to GKE Hub endpoints

Issue: Config Sync not working across projects

  • Solution: Check that Config Sync is enabled at the fleet level
  • Verify Git repository access from all clusters

Common Operational Tasks​

  • Apply Policy Across Fleet:
    • Use Config Sync to push RBAC, NetworkPolicy, or other YAMLs to all clusters.
  • Workload Identity Federation:
    • Map GCP IAM to Kubernetes service accounts for secure, cross-cluster identity.
  • Monitor Fleet Health:
    • Use GKE Hub and Cloud Console for fleet-wide status and alerts.

Best Practices​

  • Use unique cluster names and labels for easy identification.
  • Regularly audit fleet membership and permissions.
  • Use Config Sync for GitOps-driven, consistent configuration.
  • Enable workload identity for secure service-to-service communication.
  • Test multi-cluster services in a staging environment before production.

Troubleshooting​

  • If a cluster does not appear in the fleet, check registration logs and IAM permissions.
  • Ensure all clusters have network connectivity to GKE Hub endpoints.
  • Use gcloud container hub memberships describe <CLUSTER_NAME> for detailed status.
