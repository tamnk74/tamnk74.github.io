Kubernetes Deployment Resource Guide

Overview​

A Deployment is one of the most important Kubernetes resources for managing stateless applications. It provides declarative updates for Pods and ReplicaSets, enabling you to describe the desired state of your application and have Kubernetes manage the transition from the current state to the desired state.

Why Use Deployments?​

Deployments provide several critical capabilities:

  • Declarative Updates: Define the desired state and let Kubernetes handle the rest
  • Rolling Updates: Update applications with zero downtime
  • Rollback: Easily revert to previous versions
  • Scaling: Scale applications up or down effortlessly
  • Self-Healing: Automatically replace failed pods
  • Version History: Track and manage deployment revisions

Basic Deployment Structure​

Minimal Deployment Example​

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80

Key Components Explained​

Metadata Section​

metadata:
  name: nginx-deployment # Deployment name (must be unique in namespace)
  namespace: default # Namespace (optional, defaults to 'default')
  labels: # Labels for the deployment itself
    app: nginx
    environment: production
    version: v1
  annotations: # Additional metadata
    description: 'Production nginx deployment'

Spec Section​

spec:
  replicas: 3 # Number of pod replicas
  revisionHistoryLimit: 10 # Number of old ReplicaSets to retain
  progressDeadlineSeconds: 600 # Max time for deployment to make progress
  minReadySeconds: 0 # Min seconds for pod to be considered available

  selector: # Label selector for pods
    matchLabels:
      app: nginx

  strategy: # Update strategy
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Max pods above desired count during update
      maxUnavailable: 0 # Max pods unavailable during update

Creating a Deployment​

Method 1: Using kubectl with YAML​

# Create deployment from YAML file
kubectl apply -f deployment.yaml

# Create deployment in specific namespace
kubectl apply -f deployment.yaml -n my-namespace

# Validate YAML without creating resources
kubectl apply -f deployment.yaml --dry-run=client

# View what will be created
kubectl apply -f deployment.yaml --dry-run=server -o yaml

Method 2: Using kubectl Imperative Commands​

# Create a basic deployment
kubectl create deployment nginx --image=nginx:1.25

# Create deployment with replicas
kubectl create deployment nginx --image=nginx:1.25 --replicas=3

# Create deployment with port exposed
kubectl create deployment nginx --image=nginx:1.25 --port=80

# Create deployment and save to file
kubectl create deployment nginx --image=nginx:1.25 \
  --dry-run=client -o yaml > deployment.yaml

Method 3: Using Helm Charts​

# Install deployment using Helm
helm install my-app ./my-chart

# Install with custom values
helm install my-app ./my-chart -f values.yaml

Complete Production-Ready Example​

apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-api
  namespace: production
  labels:
    app: backend-api
    tier: backend
    environment: production
    version: v2.1.0
  annotations:
    kubernetes.io/change-cause: 'Update to version 2.1.0 with bug fixes'
spec:
  # Replica configuration
  replicas: 5
  revisionHistoryLimit: 10
  progressDeadlineSeconds: 600
  minReadySeconds: 10

  # Selector for pods
  selector:
    matchLabels:
      app: backend-api
      tier: backend

  # Update strategy
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 1

  # Pod template
  template:
    metadata:
      labels:
        app: backend-api
        tier: backend
        version: v2.1.0
      annotations:
        prometheus.io/scrape: 'true'
        prometheus.io/port: '9090'
    spec:
      # Service account
      serviceAccountName: backend-api-sa

      # Security context
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 1000

      # Init containers
      initContainers:
        - name: db-migration
          image: myapp/db-migrator:2.1.0
          env:
            - name: DB_HOST
              valueFrom:
                configMapKeyRef:
                  name: backend-config
                  key: database.host
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: backend-secrets
                  key: database.password

      # Main containers
      containers:
        - name: backend-api
          image: myapp/backend-api:2.1.0
          imagePullPolicy: IfNotPresent

          # Ports
          ports:
            - name: http
              containerPort: 8080
              protocol: TCP
            - name: metrics
              containerPort: 9090
              protocol: TCP

          # Environment variables
          env:
            - name: NODE_ENV
              value: 'production'
            - name: PORT
              value: '8080'
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: backend-config
                  key: log.level
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: backend-secrets
                  key: database.url

          # Environment from ConfigMap/Secret
          envFrom:
            - configMapRef:
                name: backend-config
            - secretRef:
                name: backend-secrets

          # Resource requests and limits
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi

          # Liveness probe
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3
            successThreshold: 1

          # Readiness probe
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 3
            successThreshold: 1

          # Startup probe (for slow-starting containers)
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            initialDelaySeconds: 0
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 30
            successThreshold: 1

          # Volume mounts
          volumeMounts:
            - name: config
              mountPath: /app/config
              readOnly: true
            - name: cache
              mountPath: /app/cache
            - name: logs
              mountPath: /app/logs

      # Volumes
      volumes:
        - name: config
          configMap:
            name: backend-config
            items:
              - key: app.yaml
                path: application.yaml
        - name: cache
          emptyDir: {}
        - name: logs
          emptyDir: {}

      # Node selection
      nodeSelector:
        disktype: ssd
        workload: backend

      # Affinity rules
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - backend-api
                topologyKey: kubernetes.io/hostname

      # Tolerations
      tolerations:
        - key: 'dedicated'
          operator: 'Equal'
          value: 'backend'
          effect: 'NoSchedule'

Deployment Strategies​

1. RollingUpdate (Default)​

Gradually replaces old pods with new ones.

spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Can add 1 extra pod during update
      maxUnavailable: 0 # Must keep all pods available

Use Cases:

  • Zero-downtime deployments
  • Gradual rollouts
  • Most common strategy

2. Recreate​

Terminates all old pods before creating new ones.

spec:
  strategy:
    type: Recreate

Use Cases:

  • When you can tolerate downtime
  • When running multiple versions simultaneously causes issues
  • Database migrations requiring exclusive access

3. Blue-Green Deployment​

Uses labels and services to switch traffic between versions.

# Blue deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
      version: blue
  template:
    metadata:
      labels:
        app: backend
        version: blue
    spec:
      containers:
        - name: backend
          image: myapp:v1.0

---
# Green deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
      version: green
  template:
    metadata:
      labels:
        app: backend
        version: green
    spec:
      containers:
        - name: backend
          image: myapp:v2.0

---
# Service (switch between blue/green)
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend
    version: blue # Change to 'green' to switch
  ports:
    - port: 80
      targetPort: 8080

4. Canary Deployment​

Gradually rolls out to a subset of users.

# Stable deployment (90% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: backend
      track: stable
  template:
    metadata:
      labels:
        app: backend
        track: stable
    spec:
      containers:
        - name: backend
          image: myapp:v1.0

---
# Canary deployment (10% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend
      track: canary
  template:
    metadata:
      labels:
        app: backend
        track: canary
    spec:
      containers:
        - name: backend
          image: myapp:v2.0

Managing Deployments​

Viewing Deployments​

# List all deployments
kubectl get deployments

# List deployments in all namespaces
kubectl get deployments --all-namespaces

# Detailed view
kubectl get deployments -o wide

# View specific deployment
kubectl describe deployment nginx-deployment

# View deployment YAML
kubectl get deployment nginx-deployment -o yaml

# View deployment status
kubectl rollout status deployment/nginx-deployment

Scaling Deployments​

# Scale to 5 replicas
kubectl scale deployment nginx-deployment --replicas=5

# Autoscale based on CPU
kubectl autoscale deployment nginx-deployment \
  --min=2 --max=10 --cpu-percent=80

# View autoscaler
kubectl get hpa

Updating Deployments​

# Update image
kubectl set image deployment/nginx-deployment \
  nginx=nginx:1.26

# Edit deployment
kubectl edit deployment nginx-deployment

# Apply changes from file
kubectl apply -f deployment.yaml

# Replace deployment
kubectl replace -f deployment.yaml

# Patch deployment
kubectl patch deployment nginx-deployment \
  -p '{"spec":{"replicas":3}}'

Rolling Back Deployments​

# View rollout history
kubectl rollout history deployment/nginx-deployment

# View specific revision
kubectl rollout history deployment/nginx-deployment --revision=2

# Rollback to previous version
kubectl rollout undo deployment/nginx-deployment

# Rollback to specific revision
kubectl rollout undo deployment/nginx-deployment --to-revision=2

# Pause rollout
kubectl rollout pause deployment/nginx-deployment

# Resume rollout
kubectl rollout resume deployment/nginx-deployment

# Restart deployment (recreate all pods)
kubectl rollout restart deployment/nginx-deployment

Deleting Deployments​

# Delete deployment
kubectl delete deployment nginx-deployment

# Delete deployment from file
kubectl delete -f deployment.yaml

# Delete all deployments with label
kubectl delete deployments -l app=nginx

# Delete and wait for cascade
kubectl delete deployment nginx-deployment --cascade=foreground

Advanced Configurations​

Health Checks​

Liveness Probe​

Determines if the container is running.

livenessProbe:
  # HTTP check
  httpGet:
    path: /healthz
    port: 8080
    httpHeaders:
      - name: Custom-Header
        value: Awesome
  initialDelaySeconds: 30
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3
  successThreshold: 1
livenessProbe:
  # TCP check
  tcpSocket:
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 20
livenessProbe:
  # Command execution
  exec:
    command:
      - cat
      - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5

Readiness Probe​

Determines if the container can accept traffic.

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 3
  successThreshold: 1

Startup Probe​

Handles slow-starting containers.

startupProbe:
  httpGet:
    path: /startup
    port: 8080
  initialDelaySeconds: 0
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 30 # 30 * 10 = 5 minutes max startup time

Resource Management​

resources:
  requests:
    cpu: 100m # Minimum CPU
    memory: 128Mi # Minimum memory
  limits:
    cpu: 500m # Maximum CPU
    memory: 512Mi # Maximum memory

Environment Variables​

env:
  # Direct value
  - name: ENV_NAME
    value: 'production'

  # From ConfigMap
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: log_level

  # From Secret
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: app-secrets
        key: database_password

  # From field reference
  - name: POD_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name

  - name: POD_IP
    valueFrom:
      fieldRef:
        fieldPath: status.podIP

  # From resource field
  - name: MEMORY_LIMIT
    valueFrom:
      resourceFieldRef:
        containerName: app
        resource: limits.memory

Volume Mounts​

volumes:
  # ConfigMap
  - name: config-volume
    configMap:
      name: app-config

  # Secret
  - name: secret-volume
    secret:
      secretName: app-secrets

  # EmptyDir (temporary storage)
  - name: cache-volume
    emptyDir: {}

  # HostPath (node filesystem)
  - name: host-volume
    hostPath:
      path: /data
      type: Directory

  # PersistentVolumeClaim
  - name: data-volume
    persistentVolumeClaim:
      claimName: app-pvc

volumeMounts:
  - name: config-volume
    mountPath: /etc/config
    readOnly: true
  - name: cache-volume
    mountPath: /cache

Security Context​

securityContext:
  # Pod-level security
  runAsNonRoot: true
  runAsUser: 1000
  runAsGroup: 1000
  fsGroup: 2000
  fsGroupChangePolicy: 'OnRootMismatch'
  seccompProfile:
    type: RuntimeDefault

containers:
  - name: app
    securityContext:
      # Container-level security
      allowPrivilegeEscalation: false
      capabilities:
        drop:
          - ALL
        add:
          - NET_BIND_SERVICE
      readOnlyRootFilesystem: true
      runAsNonRoot: true
      runAsUser: 1000

Pod Affinity and Anti-Affinity​

affinity:
  # Pod Anti-Affinity (spread pods across nodes)
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - backend
        topologyKey: kubernetes.io/hostname

    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values:
                  - backend
          topologyKey: topology.kubernetes.io/zone

  # Node Affinity (prefer certain nodes)
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/arch
              operator: In
              values:
                - amd64

    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
            - key: disktype
              operator: In
              values:
                - ssd

Multi-Container Deployments​

Sidecar Pattern​

spec:
  containers:
    # Main application
    - name: app
      image: myapp:1.0
      ports:
        - containerPort: 8080

    # Logging sidecar
    - name: log-collector
      image: fluent/fluent-bit:2.0
      volumeMounts:
        - name: logs
          mountPath: /var/log/app

    # Metrics exporter sidecar
    - name: metrics-exporter
      image: prom/statsd-exporter:v0.22.0
      ports:
        - containerPort: 9102

  volumes:
    - name: logs
      emptyDir: {}

Ambassador Pattern​

spec:
  containers:
    # Main application
    - name: app
      image: myapp:1.0
      env:
        - name: DATABASE_URL
          value: 'localhost:5432' # Connect via ambassador

    # Database proxy ambassador
    - name: db-proxy
      image: cloud-sql-proxy:1.33
      command:
        - '/cloud_sql_proxy'
        - '-instances=project:region:instance=tcp:5432'
      securityContext:
        runAsNonRoot: true

Adapter Pattern​

spec:
  containers:
    # Main application (legacy format)
    - name: app
      image: legacy-app:1.0
      volumeMounts:
        - name: logs
          mountPath: /var/log

    # Adapter to convert logs to standard format
    - name: log-adapter
      image: log-adapter:1.0
      volumeMounts:
        - name: logs
          mountPath: /var/log
          readOnly: true

  volumes:
    - name: logs
      emptyDir: {}

Deployment with ConfigMap and Secret​

Complete Example​

# ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.properties: |
    server.port=8080
    log.level=INFO
  nginx.conf: |
    server {
      listen 80;
      server_name example.com;
    }

---
# Secret
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
stringData:
  database.url: 'postgresql://db:5432/mydb'
  database.password: 'supersecret'
  api.key: 'abc123xyz'

---
# Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: app
          image: myapp:1.0
          env:
            - name: SERVER_PORT
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: server.port
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: app-secrets
                  key: database.password
          volumeMounts:
            - name: config
              mountPath: /etc/config
            - name: secrets
              mountPath: /etc/secrets
              readOnly: true
      volumes:
        - name: config
          configMap:
            name: app-config
        - name: secrets
          secret:
            secretName: app-secrets

Common Issues and Solutions​

Pods Stuck in Pending​

# Check events
kubectl describe pod <pod-name>

# Common causes:
# - Insufficient resources
# - PersistentVolumeClaim not bound
# - Image pull errors
# - Node selector/affinity not matching

Pods Crashing (CrashLoopBackOff)​

# View logs
kubectl logs <pod-name> --previous

# Common causes:
# - Application error
# - Missing dependencies
# - Configuration issues
# - Resource limits too low

Image Pull Errors​

# Check image pull secret
kubectl get secret

# Create image pull secret
kubectl create secret docker-registry regcred \
  --docker-server=<registry-url> \
  --docker-username=<username> \
  --docker-password=<password> \
  --docker-email=<email>

# Add to deployment
spec:
  imagePullSecrets:
  - name: regcred

Best Practices​

1. Always Set Resource Requests and Limits​

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi

2. Use Health Checks​

Always define liveness and readiness probes:

livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5

3. Implement Proper Update Strategy​

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0 # Ensures zero downtime

4. Use Labels and Annotations​

metadata:
  labels:
    app: myapp
    tier: backend
    environment: production
    version: v1.0.0
  annotations:
    kubernetes.io/change-cause: 'Update to version 1.0.0'
    documentation: 'https://docs.example.com/myapp'

5. Security Hardening​

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  readOnlyRootFilesystem: true
  capabilities:
    drop:
      - ALL

6. Use ConfigMaps and Secrets​

Don't hardcode configuration in images:

env:
  - name: CONFIG_VALUE
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: config_value

7. Set Appropriate Replica Counts​

spec:
  replicas: 3 # Minimum for high availability

8. Use Pod Disruption Budgets​

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: myapp

9. Implement Proper Logging​

containers:
  - name: app
    image: myapp:1.0
    # Log to stdout/stderr
    command: ['./app', '--log-to-stdout']

10. Version Control Your Manifests​

  • Store YAML files in Git
  • Use GitOps tools like ArgoCD or Flux
  • Implement CI/CD pipelines

Real-World Examples​

Node.js Application Deployment​

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-app
  labels:
    app: nodejs-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nodejs-app
  template:
    metadata:
      labels:
        app: nodejs-app
    spec:
      containers:
        - name: nodejs
          image: node:18-alpine
          workingDir: /app
          command: ['node', 'server.js']
          ports:
            - containerPort: 3000
          env:
            - name: NODE_ENV
              value: 'production'
            - name: PORT
              value: '3000'
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 30
            periodSeconds: 10
          readinessProbe:
            httpGet:

            - name: DB_PORT
              value: '5432'
            - name: DB_NAME
              valueFrom:
                configMapKeyRef:
                  name: db-config
                  key: database
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: password
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi

        # Cloud SQL Proxy sidecar
        - name: cloud-sql-proxy
          image: gcr.io/cloudsql-docker/gce-proxy:latest
          command:
            - '/cloud_sql_proxy'
            - '-instances=project:region:instance=tcp:5432'
          securityContext:
            runAsNonRoot: true
          resources:
            requests:
              memory: 64Mi
              cpu: 50m
            limits:
              memory: 128Mi
              cpu: 100m

Summary​

Kubernetes Deployments are essential for managing stateless applications with:

  • Declarative management of desired state
  • Rolling updates and easy rollbacks
  • Self-healing capabilities
  • Scaling options (manual and automatic)
  • Health monitoring with probes

Key takeaways:

  1. Always use Deployments instead of creating Pods directly
  2. Implement proper health checks and resource limits
  3. Use appropriate update strategies for your use case
  4. Leverage ConfigMaps and Secrets for configuration
  5. Monitor and debug using kubectl commands
  6. Follow security best practices
  7. Keep deployment manifests in version control
