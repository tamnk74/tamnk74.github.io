Kafka Setup with Kubernetes

Overview​

This guide covers deploying Apache Kafka on Kubernetes with various architectures including standalone, clustered, and production-ready configurations. Learn how to set up Kafka for high availability, scalability, and fault tolerance using StatefulSets, persistent storage, and monitoring.

Architecture Patterns​

ZooKeeper vs KRaft Comparison​

Overview Comparison​

AspectZooKeeper ModeKRaft Mode
MaturityProduction-ready since 2011Production-ready since Kafka 3.3.1 (2022)
ArchitectureRequires separate ZooKeeper clusterSelf-contained, no external dependencies
Consensus ProtocolZooKeeper Atomic Broadcast (ZAB)Raft consensus algorithm
Metadata StorageZooKeeper ensembleKafka controller quorum
Controller ElectionVia ZooKeeper leader electionVia Raft leader election
Recommended SinceLegacy (deprecated in Kafka 3.5+)Kafka 2.8+ (production since 3.3.1)
EOL TimelineExpected removal in Kafka 4.0Long-term future of Kafka

Detailed Comparison​

1. Architecture Complexity​

ZooKeeper Mode:

┌─────────────────────────────────────┐
│  Application Layer                   │
│  ┌──────────┐  ┌──────────┐         │
│  │ Producer │  │ Consumer │         │
│  └────┬─────┘  └─────┬────┘         │
│       │              │               │
├───────┼──────────────┼───────────────┤
│  Kafka Cluster Layer                 │
│  ┌────▼────┐  ┌─────▼────┐          │
│  │ Broker 1│  │ Broker 2 │          │
│  │         │  │          │          │
│  └────┬────┘  └─────┬────┘          │
│       │             │                │
├───────┼─────────────┼────────────────┤
│  Metadata Layer                      │
│  ┌────▼─────────────▼────┐           │
│  │  ZooKeeper Cluster    │           │
│  │  (3-5 separate nodes) │           │
│  └───────────────────────┘           │
└─────────────────────────────────────┘
Total Components: Kafka brokers + ZooKeeper ensemble

KRaft Mode:

┌─────────────────────────────────────┐
│  Application Layer                   │
│  ┌──────────┐  ┌──────────┐         │
│  │ Producer │  │ Consumer │         │
│  └────┬─────┘  └─────┬────┘         │
│       │              │               │
├───────┼──────────────┼───────────────┤
│  Kafka Cluster (Self-contained)      │
│  ┌────▼────────────▼────┐            │
│  │ Controller + Broker 1│            │
│  │ (metadata + data)    │            │
│  ├──────────────────────┤            │
│  │ Controller + Broker 2│            │
│  │ (metadata + data)    │            │
│  └──────────────────────┘            │
└─────────────────────────────────────┘
Total Components: Only Kafka nodes

Advantages:

  • ZooKeeper: Proven stability, extensive production history
  • KRaft: Simpler architecture, fewer moving parts, easier operations

Partition Limit~200,000 partitions1,000,000+ partitions🏆 KRaft
Metadata PropagationSlower (ZK bottleneck)Faster (event-driven)🏆 KRaft

Performance Benchmarks:

# Controller failover comparison
ZooKeeper Mode:
  - Average failover: 15 seconds
  - Downtime during failover: Yes
  - Partition reassignment during failover: Blocked

KRaft Mode:
  - Average failover: 2 seconds
  - Downtime during failover: Minimal
  - Partition reassignment during failover: Continues

3. Operational Complexity​

ZooKeeper Mode Operations:

# Requires managing two separate systems

# ZooKeeper operations
kubectl scale statefulset zookeeper --replicas=5 -n kafka
kubectl exec -it zookeeper-0 -n kafka -- zkCli.sh
kubectl logs zookeeper-0 -n kafka

# Kafka operations
kubectl scale statefulset kafka --replicas=5 -n kafka
kubectl exec -it kafka-0 -n kafka -- kafka-topics --list
kubectl logs kafka-0 -n kafka

# Two sets of monitoring, backup, upgrades

KRaft Mode Operations:

# Single system to manage

# Kafka operations (includes metadata management)
kubectl scale statefulset kafka-kraft --replicas=5 -n kafka
kubectl exec -it kafka-kraft-0 -n kafka -- kafka-metadata-shell
kubectl logs kafka-kraft-0 -n kafka

# Single monitoring stack, simpler backups, easier upgrades

Initial Setup2 systems to configure1 system to configure

UpgradesCoordinate ZK + Kafka versionsOnly Kafka version
BackupZK snapshots + Kafka dataOnly Kafka data
TroubleshootingCheck ZK + Kafka logsOnly Kafka logs
Resource PlanningZK nodes + Kafka brokersOnly Kafka nodes

4. Scalability Limits​

ZooKeeper Mode Limitations:

Partition Limits:
  - Hard limit: ~200,000 partitions per cluster
  - Reason: ZooKeeper metadata overhead
  - Impact: Cluster instability beyond this limit

Controller Limits:
  - Single active controller (ZK-elected)
  - Bottleneck for metadata operations
  - Slow partition reassignments at scale

Cluster Size:
  - Recommended max brokers: 100-200
  - ZooKeeper becomes bottleneck

KRaft Mode Capabilities:

Partition Limits:
  - Tested: 1,000,000+ partitions
  - Reason: Efficient metadata log storage
  - Impact: Linear scaling performance

Controller Quorum:
  - Multiple controllers in quorum
  - Distributed metadata management
  - Fast parallel operations

Cluster Size:
  - Tested with 1000+ brokers
  - No ZooKeeper bottleneck
  - Better horizontal scaling

5. Deployment Modes​

ZooKeeper Mode - Deployment Options:

# Option 1: Separate clusters
- ZooKeeper: 3-5 dedicated nodes
- Kafka: 3+ broker nodes
- Total: 6-8+ nodes minimum

# Option 2: Co-located (not recommended)
- ZooKeeper + Kafka on same nodes
- Resource contention issues
- Not production-ready

# Resource Requirements:
ZooKeeper:
  replicas: 3
  cpu: 500m per node
  memory: 1Gi per node

Kafka:
  replicas: 3
  cpu: 2000m per node
  memory: 4Gi per node

Total: 6 nodes, 7.5 CPU, 15Gi memory

KRaft Mode - Deployment Options:

# Option 1: Combined mode (controller + broker)
- Single set of nodes handles both roles
- Recommended for small-medium clusters
- Simpler to manage

kafka:
  replicas: 3
  process.roles: "broker,controller"
  cpu: 2000m per node
  memory: 4Gi per node

Total: 3 nodes, 6 CPU, 12Gi memory

# Option 2: Separated mode (dedicated controllers)
- Dedicated controller nodes
- Separate broker nodes
- Recommended for large clusters (100+ brokers)

controllers:
  replicas: 3
  process.roles: "controller"
  cpu: 1000m per node
  memory: 2Gi per node

brokers:
  replicas: 10
  process.roles: "broker"
  cpu: 4000m per node
  memory: 8Gi per node

Total: 13 nodes, optimized for role

6. Metadata Management​

ZooKeeper Mode:

Metadata Storage: ZooKeeper znodes
  ├── /brokers
  │   ├── /ids (broker registrations)
  │   ├── /topics (topic configurations)
  │   └── /seqid (sequential IDs)
  ├── /config
  │   ├── /topics
  │   └── /brokers
  ├── /controller (active controller)
  └── /admin (admin operations)

Characteristics:
  - Synchronous writes to ZK
  - Network overhead for every metadata change
  - ZK watch notifications for changes
  - Limited throughput (~1000 ops/sec)
  - Metadata size limited by ZK

KRaft Mode:

Metadata Storage: Internal Kafka topic (__cluster_metadata)
  - Event-driven metadata log
  - Replicated via Raft consensus
  - No external dependencies
  - Append-only log structure
  - Compacted topic for efficiency

Characteristics:
  - Asynchronous metadata replication
  - No network calls to external system
  - Event sourcing pattern
  - High throughput (10,000+ ops/sec)
  - Scalable metadata storage

8. When to Choose Each​

Choose ZooKeeper Mode if:

  • ✅ You have existing ZooKeeper expertise
  • ✅ Running older Kafka versions (< 3.3)
  • ✅ Need proven stability for conservative environments
  • ✅ Have existing ZooKeeper infrastructure to reuse
  • ✅ Regulatory requirements mandate proven technology

Choose KRaft Mode if:

  • ✅ Starting a new Kafka deployment
  • ✅ Running Kafka 3.3.1 or later
  • ✅ Need high partition counts (>200k)
  • ✅ Want faster recovery and failover
  • ✅ Prefer simpler operational model
  • ✅ Building for future (ZooKeeper deprecated)

9. Migration Path​

ZooKeeper to KRaft Migration (Kafka 3.4+):

# Phase 1: Dual-mode cluster
- Run brokers in migration mode
- Metadata synced between ZK and KRaft
- ZooKeeper still authoritative

# Phase 2: Transfer leadership
- Make KRaft controllers authoritative
- ZooKeeper becomes follower
- Test thoroughly in this state

# Phase 3: ZooKeeper removal
- Decommission ZooKeeper nodes
- Full KRaft mode active
- Remove ZooKeeper dependencies

Migration command:
kafka-metadata.sh --snapshot /path/to/zk-snapshot --output /path/to/kraft-metadata

Migration Checklist:

Pre-migration:
  - ✅ Upgrade to Kafka 3.4+
  - ✅ Test in non-production environment
  - ✅ Document current ZooKeeper state
  - ✅ Plan rollback strategy
  - ✅ Backup metadata

During migration:
  - ✅ Enable migration mode
  - ✅ Monitor both systems
  - ✅ Validate metadata consistency
  - ✅ Test client connectivity
  - ✅ Perform gradual rollover

Post-migration:
  - ✅ Verify all features working
  - ✅ Update monitoring dashboards
  - ✅ Remove ZooKeeper references
  - ✅ Update documentation
  - ✅ Train operations team

10. Cost Comparison (GKE Example)​

ZooKeeper Mode - Monthly Cost:

ZooKeeper Cluster:
  - 3 nodes × n1-standard-2 (2 vCPU, 7.5GB)
  - $97.92 × 3 = $293.76/month
  - 30GB SSD storage × 3 = $18/month

Kafka Cluster:
  - 3 nodes × n1-standard-4 (4 vCPU, 15GB)
  - $195.84 × 3 = $587.52/month
  - 150GB SSD storage × 3 = $90/month

Total: $989.28/month

KRaft Mode - Monthly Cost:

Kafka KRaft Cluster:
  - 3 nodes × n1-standard-4 (4 vCPU, 15GB)
  - $195.84 × 3 = $587.52/month
  - 150GB SSD storage × 3 = $90/month

Total: $677.52/month

Savings: $311.76/month (31.5% cost reduction)

Recommendation​

For new deployments in 2024 and beyond:

  • Use KRaft mode (Kafka 3.3.1+)
  • Simpler, faster, more scalable
  • Future-proof (ZooKeeper support ending)

For existing deployments:

  • Plan migration to KRaft before Kafka 4.0
  • Test migration in non-production first
  • Consider migration during next major upgrade

apiVersion: v1
kind: ConfigMap

  namespace: kafka
data:

    node.id=${NODE_ID}

    # Listeners

    listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
    controller.listener.names=CONTROLLER
    inter.broker.listener.name=PLAINTEXT

    # Log directories
    log.dirs=/var/lib/kafka/data

    default.replication.factor=3
    min.insync.replicas=2
    offsets.topic.replication.factor=3

// kafka-producer.service.ts
import { Injectable, OnModuleInit, Inject } from '@nestjs/common';
import { ClientKafka } from '@nestjs/microservices';

@Injectable()
export class KafkaProducerService implements OnModuleInit {
  constructor(
    @Inject('KAFKA_SERVICE')
    private readonly kafkaClient: ClientKafka,
  ) {}

  async onModuleInit() {
    await this.kafkaClient.connect();
  }

  async sendMessage(topic: string, message: any) {
    return this.kafkaClient.emit(topic, message);
  }

  async sendMessageWithKey(topic: string, key: string, message: any) {
    return this.kafkaClient.emit(topic, {
      key,
      value: message,
    });
  }
}

2. Snapshot Backups​

#!/bin/bash
# backup-kafka-data.sh

NAMESPACE="kafka"
BACKUP_DIR="/backup/kafka"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)

# Create backup directory
mkdir -p ${BACKUP_DIR}/${TIMESTAMP}

# Backup each Kafka broker's PVC
for i in 0 1 2; do
  POD_NAME="kafka-${i}"
  PVC_NAME="data-kafka-${i}"

  echo "Backing up ${POD_NAME}..."

  # Create snapshot of PVC
  kubectl exec -n ${NAMESPACE} ${POD_NAME} -- tar czf /tmp/backup.tar.gz /var/lib/kafka/data

  # Copy to backup location
  kubectl cp ${NAMESPACE}/${POD_NAME}:/tmp/backup.tar.gz ${BACKUP_DIR}/${TIMESTAMP}/${POD_NAME}.tar.gz

  # Upload to GCS
  gcloud storage cp ${BACKUP_DIR}/${TIMESTAMP}/${POD_NAME}.tar.gz gs://your-backup-bucket/kafka/${TIMESTAMP}/
done

echo "Backup completed: ${TIMESTAMP}"

Troubleshooting​

Common Issues​

1. Broker not joining cluster:

# Check broker logs
kubectl logs kafka-0 -n kafka

# Check ZooKeeper connection
kubectl exec -it kafka-0 -n kafka -- kafka-broker-api-versions --bootstrap-server localhost:9092

# Verify ZooKeeper cluster
kubectl exec -it zookeeper-0 -n kafka -- zkCli.sh ls /brokers/ids

2. Under-replicated partitions:

# Check partition status
kubectl exec -it kafka-0 -n kafka -- kafka-topics --bootstrap-server localhost:9092 --describe --under-replicated-partitions

# Trigger leader election
kubectl exec -it kafka-0 -n kafka -- kafka-leader-election --bootstrap-server localhost:9092 --election-type preferred --all-topic-partitions

3. Consumer lag issues:

# Check consumer group status
kubectl exec -it kafka-0 -n kafka -- kafka-consumer-groups --bootstrap-server localhost:9092 --describe --group my-consumer-group

# Reset consumer group offsets
kubectl exec -it kafka-0 -n kafka -- kafka-consumer-groups --bootstrap-server localhost:9092 --group my-consumer-group --reset-offsets --to-earliest --topic my-topic --execute
