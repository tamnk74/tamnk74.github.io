Load Balancing with Ingress and Kustomize

Learn how to configure and manage Kubernetes Ingress load balancing using Kustomize for different environments and use cases.

⚠️ Important: This guide focuses on GCE Ingress for GKE. GCE Ingress does NOT support regex patterns in paths like NGINX Ingress does. Use simple prefix paths (/api, /api/*) instead of regex patterns (/api(/|$)(.*)).

Overview​

Kubernetes Ingress provides HTTP and HTTPS routing to services within a cluster, offering built-in load balancing capabilities. Kustomize enables declarative management of Kubernetes configurations across multiple environments without templating.

This guide specifically covers GCE Ingress (Google Cloud's native Ingress controller for GKE), which integrates seamlessly with Google Cloud Load Balancing, Cloud Armor, and Cloud CDN.

Key Concepts​

  • Ingress Controller: Implements the Ingress resource (e.g., GCE, NGINX, Traefik, HAProxy)
  • Ingress Resource: Defines routing rules and load balancing configuration
  • Kustomize: Manages configuration variations across environments using overlays
  • Load Balancing: Distributes traffic across multiple backend pods
  • GCE Ingress: Google Cloud's native Ingress controller with integrated load balancing

Prerequisites​

  • Google Kubernetes Engine (GKE) cluster (1.19+)
  • kubectl configured
  • GCE Ingress controller (default on GKE)
  • Basic understanding of Kubernetes Services and Deployments
  • Google Cloud Load Balancer knowledge helpful

GCE vs NGINX Ingress: Key Differences​

When migrating from NGINX to GCE Ingress, be aware of these critical differences:

FeatureNGINX IngressGCE Ingress
Path Regex✅ Supported (/api(/|$)(.*))❌ Not supported - use Prefix paths
Path Rewriting✅ rewrite-target annotation❌ Handle in app or sidecar proxy
IngressClassnginxgce or gce-internal
SSL Certificatescert-manager or manualGoogle-managed certificates
Rate LimitingAnnotationsCloud Armor security policies
Session AffinityAnnotationsBackendConfig resource
CORSAnnotationsBackendConfig or app-level
Load Balancer TypeInternal/External NodePortGoogle Cloud Load Balancer
Health ChecksAnnotationsBackendConfig resource
CDNNot nativeCloud CDN integration

Migration Checklist:

  • Replace regex paths with simple prefix paths
  • Convert annotations to BackendConfig resources
  • Replace cert-manager with ManagedCertificate
  • Update rate limiting to Cloud Armor
  • Change ingressClassName from nginx to gce
  • Remove path rewriting annotations (handle in app)

Base Configuration​

Base Deployment​

Create base/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
  labels:
    app: webapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      containers:
        - name: webapp
          image: myapp:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10

Base Service​

Create base/service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: webapp-service
  labels:
    app: webapp
spec:
  type: ClusterIP
  ports:
    - port: 80
      targetPort: 8080
      protocol: TCP
      name: http
  selector:
    app: webapp
  sessionAffinity: None

Base Ingress​

Create base/ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: webapp-ingress
  annotations:
    kubernetes.io/ingress.class: 'gce'
    kubernetes.io/ingress.allow-http: 'false'
spec:
  ingressClassName: gce
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: webapp-service
                port:
                  number: 80

Base Kustomization​

Create base/kustomization.yaml:

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml
  - ingress.yaml

commonLabels:
  app: webapp
  managed-by: kustomize

namespace: default

Session Affinity (Sticky Sessions)​

For GCE Ingress, session affinity is configured using BackendConfig.

Create base/backend-config.yaml:

  name: webapp-backend-config

Rate Limiting​

For GCE Ingress, rate limiting is configured using Cloud Armor security policies:

apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: webapp-backend-config
spec:
  securityPolicy:
    name: 'rate-limit-policy'

Cloud Armor policy (created via gcloud):

gcloud compute security-policies create rate-limit-policy \
    --description "Rate limiting policy"

gcloud compute security-policies rules create 1000 \
    --security-policy rate-limit-policy \
    --expression "true" \
    --action "rate-based-ban" \
    --rate-limit-threshold-count 100 \
    --rate-limit-threshold-interval-sec 60 \
    --ban-duration-sec 600

Create overlays/dev/kustomization.yaml:

  - name: webapp

Multi-Service Load Balancing​

Path-Based Routing​

Important: GCE Ingress does not support regex patterns like NGINX. Use simple prefix paths instead.

Create base/ingress-multi-service.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-service-ingress
  annotations:
    kubernetes.io/ingress.class: 'gce'
spec:
  ingressClassName: gce
  rules:
    - host: example.com
      http:
        paths:
          - path: /api/*
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
          - path: /frontend/*
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
          - path: /admin/*
            pathType: Prefix
            backend:
              service:
                name: admin-service
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: default-service
                port:
                  number: 80

Path Matching in GCE:

  • /api/* matches /api/ and /api/anything
  • Paths are matched in order of specificity (longest match wins)
  • GCE does NOT strip path prefixes by default
  • For path rewriting, configure your backend service to handle the full path

Path Rewriting Alternative:

If you need path rewriting (e.g., /api/users → /users), handle it in your application or use a sidecar proxy:

apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-rewrite-config
data:
  default.conf: |
    server {
      listen 8080;
      location /api/ {
        rewrite ^/api/(.*)$ /$1 break;
        proxy_pass http://localhost:3000;
      }
    }

GCE Path Matching Behavior​

GCE Ingress uses Google Cloud Load Balancer URL maps with specific path matching rules:

PathType Options​

  1. Prefix (Recommended for GCE):

    - path: /api
      pathType: Prefix
    • Matches /api, /api/, /api/users, etc.
    • Most common and flexible option

  2. Exact:

    - path: /api
      pathType: Exact
    • Only matches exactly /api (not /api/ or /api/users)
    • Use for specific endpoints

  3. ImplementationSpecific (Not recommended for GCE):

    • Behavior depends on the Ingress controller
    • Avoid using with GCE for predictable behavior

Path Matching Rules​

# ✅ CORRECT: Simple prefix paths
paths:
  - path: /api
    pathType: Prefix
  - path: /users
    pathType: Prefix
  - path: /
    pathType: Prefix

# ❌ INCORRECT: Regex patterns (NGINX-style, not supported by GCE)
paths:
  - path: /api(/|$)(.*)      # Won't work with GCE
  - path: /api/.*            # Won't work with GCE
  - path: ~^/api/            # Won't work with GCE

# ✅ CORRECT: Wildcard for prefix matching
paths:
  - path: /api/*
    pathType: Prefix

# ✅ CORRECT: Order matters - most specific first
paths:
  - path: /api/v2/users
    pathType: Prefix
  - path: /api/v2
    pathType: Prefix
  - path: /api
    pathType: Prefix
  - path: /
    pathType: Prefix

Path Rewriting Solutions​

Since GCE doesn't support path rewriting natively, here are alternatives:

Option 1: Handle in Application

// Your backend application handles the full path
app.use('/api', (req, res) => {
  // req.url includes '/api' prefix
  // Handle routing accordingly
});

Option 2: Use Nginx Sidecar for Path Rewriting

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-with-rewrite
spec:
  template:
    spec:
      containers:
        - name: nginx-rewrite
          image: nginx:alpine
          ports:
            - containerPort: 8080
          volumeMounts:
            - name: nginx-config
              mountPath: /etc/nginx/conf.d
        - name: app
          image: myapp:latest
          ports:
            - containerPort: 3000
      volumes:
        - name: nginx-config
          configMap:
            name: nginx-rewrite-config
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-rewrite-config
data:
  default.conf: |
    server {
      listen 8080;
      location /api/ {
        rewrite ^/api/(.*)$ /$1 break;
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
      }
    }
---
apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector:
    app: api-with-rewrite
  ports:
    - port: 80
      targetPort: 8080 # Nginx port, not app port

Option 3: Use Separate Ingress per Service

# No path prefix needed
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80

apiVersion: cloud.google.com/v1

Route requests from the same client IP to the same backend:

Health Checks and Backend Configuration​

Custom Backend Configuration​

BackendConfig is a GKE-specific Custom Resource Definition (CRD) that provides fine-grained control over Google Cloud Load Balancer features. It allows you to configure backend services without modifying Ingress resources.

Complete BackendConfig Reference​

Create base/backend-config.yaml with all available options:

apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: webapp-backend-config
  namespace: production
spec:
  # ============================================
  # Health Check Configuration
  # ============================================
  healthCheck:
    # Check interval in seconds (default: 5)
    checkIntervalSec: 10
    # Timeout for each health check probe (default: 5)
    timeoutSec: 5
    # Number of consecutive successful checks to mark healthy (default: 2)
    healthyThreshold: 2
    # Number of consecutive failed checks to mark unhealthy (default: 2)
    unhealthyThreshold: 3
    # Health check type: HTTP, HTTPS, HTTP2, TCP, SSL
    type: HTTP
    # Path for HTTP(S) health checks
    requestPath: /health
    # Port for health check (default: service port)
    port: 8080

  # ============================================
  # Connection Draining
  # ============================================
  connectionDraining:
    # Time to wait for connections to drain before removing backend (0-3600)
    drainingTimeoutSec: 60

  # ============================================
  # Timeout Configuration
  # ============================================
  # Backend service timeout in seconds (default: 30, max: 86400)
  timeoutSec: 30

  # ============================================
  # Session Affinity (Sticky Sessions)
  # ============================================
  sessionAffinity:
    # Affinity type: NONE, CLIENT_IP, GENERATED_COOKIE, CLIENT_IP_PROTO, CLIENT_IP_PORT_PROTO
    affinityType: 'CLIENT_IP'
    # Cookie TTL in seconds (only for GENERATED_COOKIE, default: 0)
    affinityCookieTtlSec: 3600

  # ============================================
  # Cloud CDN Configuration
  # ============================================
  cdn:
    # Enable Cloud CDN
    enabled: true
    # Cache mode: CACHE_ALL_STATIC, USE_ORIGIN_HEADERS, FORCE_CACHE_ALL
    cacheMode: 'USE_ORIGIN_HEADERS'
    # Default TTL for cached content (seconds)
    defaultTtl: 3600
    # Maximum TTL for cached content (seconds)
    maxTtl: 86400
    # Client TTL for cached content (seconds)
    clientTtl: 1800
    # Negative caching (cache error responses)
    negativeCaching: true
    negativeCachingPolicy:
      - code: 404
        ttl: 120
      - code: 410
        ttl: 120
      - code: 500
        ttl: 30
      - code: 502
        ttl: 30
      - code: 503
        ttl: 10
      - code: 504
        ttl: 10
    # Cache key policy
    cacheKeyPolicy:
      # Include protocol (http/https) in cache key
      includeProtocol: true
      # Include host in cache key
      includeHost: true
      # Include query string in cache key
      includeQueryString: true
      # Specific query parameters to include/exclude
      queryStringWhitelist:
        - 'version'
        - 'locale'
      # queryStringBlacklist:
      #   - 'session'
      #   - 'token'
      # Include specific headers in cache key
      includeNamedCookies:
        - 'session_id'
    # Request coalescing (collapse simultaneous requests)
    requestCoalescing: true
    # Serve stale content while revalidating
    serveWhileStale: 86400
    # Bypass cache for specific conditions
    bypassCacheOnRequestHeaders:
      - headerName: 'Authorization'
      - headerName: 'X-No-Cache'

  # ============================================
  # Custom Request Headers
  # ============================================
  customRequestHeaders:
    headers:
      - 'X-Client-Region:{client_region}'
      - 'X-Client-City:{client_city}'
      - 'X-Forwarded-Proto:https'
      - 'X-Custom-Header:custom-value'

  # ============================================
  # Custom Response Headers
  # ============================================
  customResponseHeaders:
    headers:
      - 'X-Cache-Status:{cdn_cache_status}'
      - 'X-Served-By:gcp-lb'
      - 'Strict-Transport-Security:max-age=31536000; includeSubDomains'

  # ============================================
  # Security Policy (Cloud Armor)
  # ============================================
  securityPolicy:
    # Name of Cloud Armor security policy
    name: 'webapp-security-policy'

  # ============================================
  # Identity-Aware Proxy (IAP)
  # ============================================
  iap:
    enabled: true
    # OAuth2 client credentials
    oauthclientCredentials:
      secretName: 'iap-oauth-credentials'

  # ============================================
  # Logging Configuration
  # ============================================
  logging:
    # Enable access logging
    enable: true
    # Sample rate (0.0 - 1.0)
    sampleRate: 1.0

  # ============================================
  # Custom Request/Response Timeout
  # ============================================
  # Note: timeoutSec at root level controls backend timeout

  # ============================================
  # Backend Protocol (HTTP/HTTPS/HTTP2)
  # ============================================
  # Controlled via Service port protocol annotation

Session Affinity Types​

# No affinity (round-robin)
sessionAffinity:
  affinityType: 'NONE'

# Client IP affinity (based on source IP)
sessionAffinity:
  affinityType: 'CLIENT_IP'

# Generated cookie affinity
sessionAffinity:
  affinityType: 'GENERATED_COOKIE'
  affinityCookieTtlSec: 3600

# Client IP and protocol affinity
sessionAffinity:
  affinityType: 'CLIENT_IP_PROTO'

# Client IP, port, and protocol affinity
sessionAffinity:
  affinityType: 'CLIENT_IP_PORT_PROTO'

CDN Cache Modes​

# Use origin headers (Cache-Control, Expires, etc.)
cdn:
  enabled: true
  cacheMode: 'USE_ORIGIN_HEADERS'

# Cache all static content regardless of headers
cdn:
  enabled: true
  cacheMode: 'CACHE_ALL_STATIC'

# Force cache everything (use with caution)
cdn:
  enabled: true
  cacheMode: 'FORCE_CACHE_ALL'

Custom Headers with Variables​

GCP Load Balancer supports dynamic variables in custom headers:

customRequestHeaders:
  headers:
    # Client information
    - 'X-Client-IP:{client_ip}'
    - 'X-Client-Region:{client_region}'
    - 'X-Client-City:{client_city}'
    - 'X-Client-CityLatLong:{client_city_lat_long}'

    # Request information
    - 'X-Original-URL:{original_url}'
    - 'X-Request-Start:{timestamp}'

    # Static values
    - 'X-Environment:production'
    - 'X-Version:v1.2.3'

customResponseHeaders:
  headers:
    # Cache information
    - 'X-Cache-Status:{cdn_cache_status}'
    - 'X-Cache-ID:{cdn_cache_id}'

    # Static security headers
    - 'Strict-Transport-Security:max-age=31536000; includeSubDomains; preload'
    - 'X-Content-Type-Options:nosniff'
    - 'X-Frame-Options:DENY'
    - 'X-XSS-Protection:1; mode=block'
    - 'Referrer-Policy:strict-origin-when-cross-origin'

Best Practices​

Security​

  1. Always use TLS in production with Google-managed certificates

    networking.gke.io/managed-certificates: 'webapp-cert'
    kubernetes.io/ingress.allow-http: 'false'

  2. Enable Cloud Armor for DDoS protection and WAF

    apiVersion: cloud.google.com/v1
    kind: BackendConfig
    metadata:
      name: webapp-backend-config
    spec:
      securityPolicy:
        name: 'webapp-security-policy'

  3. Implement rate limiting via Cloud Armor

    gcloud compute security-policies create rate-limit-policy
    gcloud compute security-policies rules create 1000 \
        --security-policy rate-limit-policy \
        --action "rate-based-ban" \
        --rate-limit-threshold-count 100

Performance​

  1. Enable Cloud CDN for static content

    apiVersion: cloud.google.com/v1
    kind: BackendConfig
    metadata:
      name: webapp-backend-config
    spec:
      cdn:
        enabled: true
        cachePolicy:
          includeHost: true
          includeProtocol: true
          includeQueryString: false
        negativeCaching: true
        negativeCachingPolicy:
          - code: 404
            ttl: 120

  2. Configure connection draining

    spec:
      connectionDraining:
        drainingTimeoutSec: 60

  3. Optimize timeouts

    spec:
      timeoutSec: 30
      healthCheck:
        timeoutSec: 5

  4. Use Network Endpoint Groups (NEGs) for pod-level load balancing

    metadata:
      annotations:
        cloud.google.com/neg: '{\"ingress\": true}'

Reliability​

  1. Configure readiness and liveness probes

    • Ensures traffic only goes to healthy pods

  2. Set resource limits

    • Prevents resource exhaustion

  3. Use HPA (Horizontal Pod Autoscaler)

    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    metadata:
      name: webapp-hpa
    spec:
      scaleTargetRef:
        apiVersion: apps/v1
        kind: Deployment
        name: webapp
      minReplicas: 3
      maxReplicas: 10
      metrics:
        - type: Resource
          resource:
            name: cpu
            target:
              type: Utilization
              averageUtilization: 70

Troubleshooting​

Common Issues​

1. 503 Service Unavailable​

# Check pod status
kubectl get pods -n production

# Check service endpoints
kubectl get endpoints webapp-service -n production

# Check pod logs
kubectl logs -n production deployment/webapp

2. 404 Not Found​

# Verify Ingress rules
kubectl describe ingress webapp-ingress -n production

# Check service name matches
kubectl get svc -n production

# Test path matching
curl -v https://example.com/api/test

# Check URL map in GCP (shows actual routing rules)
gcloud compute url-maps describe <url-map-name> --global

Common causes:

  • Path doesn't match (remember: GCE uses prefix matching, not regex)
  • Service name mismatch
  • Wrong pathType (use Prefix for most cases)

2a. Path Routing Issues (GCE-specific)​

If paths aren't routing correctly:

# Check the URL map to see actual path rules
gcloud compute url-maps list
gcloud compute url-maps describe <url-map-name> --global

# Look for the pathMatchers section to see how paths are configured

Important: GCE Ingress path matching rules:

  • ✅ /api with pathType: Prefix matches /api, /api/, /api/users
  • ✅ /api/* with pathType: Prefix is valid but /* is redundant with Prefix
  • ❌ /api(/|$)(.*) regex patterns do NOT work with GCE
  • ❌ Path rewriting annotations from NGINX do NOT work with GCE

Quick Fix for Path Issues:

# Instead of complex regex, use simple prefixes
paths:
  # Most specific first
  - path: /api/v2
    pathType: Prefix
    backend:
      service:
        name: api-v2-service
  - path: /api
    pathType: Prefix
    backend:
      service:
        name: api-service
  # Catch-all last
  - path: /
    pathType: Prefix
    backend:
      service:
        name: frontend-service

3. SSL Certificate Issues​

# Check GKE managed certificate status
kubectl get managedcertificate -n production

# Describe certificate
kubectl describe managedcertificate webapp-cert -n production

# Check certificate provisioning status (can take 10-15 minutes)
kubectl get managedcertificate webapp-cert -n production -o yaml

4. Load Not Distributing Evenly​

# Check pod readiness
kubectl get pods -n production -o wide

# Verify service selector
kubectl describe service webapp-service -n production

# Check BackendConfig
kubectl describe backendconfig webapp-backend-config -n production

# View GCP Load Balancer backend health
gcloud compute backend-services get-health BACKEND_SERVICE_NAME --global

kubectl get backendconfig -n production

Advanced Patterns​

Blue-Green Deployment​

Create separate services for blue and green:

# Blue service (current)
apiVersion: v1
kind: Service
metadata:
  name: webapp-blue
spec:
  selector:
    app: webapp
    version: blue
  ports:
    - port: 80
---
# Green service (new)
apiVersion: v1
kind: Service
metadata:
  name: webapp-green
spec:
  selector:
    app: webapp
    version: green
  ports:
    - port: 80
---
# Ingress switches between them
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: webapp-ingress
spec:
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: webapp-blue # Switch to webapp-green when ready
                port:
                  number: 80

A/B Testing with Header-Based Routing​

For GCE Ingress, A/B testing is implemented using multiple backend services with traffic splitting:

# Service for version A (existing)
apiVersion: v1
kind: Service
metadata:
  name: webapp-service-a
  annotations:
    cloud.google.com/backend-config: '{"default": "webapp-backend-config-a"}'
spec:
  selector:
    app: webapp
    version: a
  ports:
    - port: 80
---
# Service for version B (new feature)
apiVersion: v1
kind: Service
metadata:
  name: webapp-service-b
  annotations:
    cloud.google.com/backend-config: '{"default": "webapp-backend-config-b"}'
spec:
  selector:
    app: webapp
    version: b
  ports:
    - port: 80
---
# BackendConfig with traffic splitting
apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: webapp-backend-config-a
spec:
  customRequestHeaders:
    headers:
      - 'X-Version:A'
---
apiVersion: cloud.google.com/v1
kind: BackendConfig
metadata:
  name: webapp-backend-config-b
spec:
  customRequestHeaders:
    headers:
      - 'X-Version:B'
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: webapp-ingress-ab
  annotations:
    kubernetes.io/ingress.class: 'gce'
spec:
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: webapp-service-new-feature
                port:
                  number: 80

Conclusion​

Using Kustomize with GCE Ingress on GKE provides a powerful, cloud-native approach to managing load balancing configurations across multiple environments. Key benefits include:

  • Declarative Configuration: All changes tracked in Git
  • Environment Parity: Consistent base with environment-specific overlays
  • No Templating: Simple YAML patches instead of complex templates
  • Native Kubernetes: Works directly with kubectl
  • Google Cloud Integration: Seamless integration with Cloud Load Balancing, Cloud Armor, and Cloud CDN
  • Managed Certificates: Automatic SSL/TLS certificate provisioning

For production deployments with GCE Ingress, always:

  • Use simple prefix paths - No regex patterns (e.g., use /api not /api(/|$)(.*))
  • Use Google-managed SSL certificates for automatic renewal
  • Enable Cloud Armor for DDoS protection and WAF
  • Configure BackendConfig for advanced load balancing features
  • Monitor traffic using Cloud Monitoring and Cloud Logging
  • Use Network Endpoint Groups (NEGs) for pod-level load balancing
  • Test configurations in lower environments first
  • Implement proper observability and alerting
  • Use GitOps practices for deployment automation
  • Regularly review and optimize configurations

Path Configuration Checklist​

✅ Do:

  • Use pathType: Prefix for most routes
  • Order paths from most specific to least specific
  • Use simple paths: /api, /users, /admin
  • Handle path rewriting in your application
  • Test path matching with gcloud compute url-maps describe

❌ Don't:

  • Use regex patterns like /api(/|$)(.*)
  • Use NGINX rewrite-target annotations
  • Rely on path stripping (GCE forwards full path)
  • Use pathType: ImplementationSpecific with GCE
