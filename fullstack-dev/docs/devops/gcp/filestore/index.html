Top 10 Filestore Architecture Patterns for Production

Overview​

Google Cloud Filestore provides fully managed NFS file servers that can be mounted by GKE clusters, Compute Engine VMs, and other services. This guide explores the top 10 architecture patterns for implementing Filestore in production environments.

How to Set Up Filestore​

Prerequisites​

Before setting up Filestore, ensure you have:

  • A Google Cloud Platform (GCP) project with billing enabled
  • gcloud CLI installed and configured
  • Appropriate IAM permissions:
    • roles/file.editor or roles/owner
    • roles/compute.networkAdmin (for VPC configuration)
  • A VPC network in the same region where you plan to deploy Filestore
  • Compute Engine instances or GKE cluster to mount the Filestore instance

Step 1: Enable the Filestore API​

# Enable the Filestore API
gcloud services enable file.googleapis.com

# Verify API is enabled
gcloud services list --enabled | grep file

Step 2: Create a Filestore Instance​

Option A: Using gcloud CLI​

# Basic setup - Create a Filestore instance
gcloud filestore instances create my-filestore \
    --project=PROJECT_ID \
    --zone=us-central1-a \
    --tier=BASIC_HDD \
    --file-share=name="data",capacity=1TB \
    --network=name="default"

# Standard tier with higher performance
gcloud filestore instances create production-filestore \
    --project=PROJECT_ID \
    --zone=us-central1-a \
    --tier=STANDARD \
    --file-share=name="production_data",capacity=2TB \
    --network=name="production-vpc" \
    --description="Production filestore instance"

# Enterprise tier with high availability
gcloud filestore instances create enterprise-filestore \
    --project=PROJECT_ID \
    --location=us-central1 \
    --tier=ENTERPRISE \
    --file-share=name="enterprise_data",capacity=1TB \
    --network=name="enterprise-vpc"

# High Scale tier for maximum throughput
gcloud filestore instances create highscale-filestore \
    --project=PROJECT_ID \
    --zone=us-central1-a \
    --tier=HIGH_SCALE_SSD \
    --file-share=name="highscale_data",capacity=10TB \
    --network=name="default"

    environment = "production"

  }

# Enterprise tier with high availability

  2. Click Create Instance
  3. Configure the instance:

# List all Filestore instances

gcloud filestore instances describe my-filestore \
    --zone=us-central1-a \

FILESTORE_IP=$(gcloud filestore instances describe my-filestore \
    --zone=us-central1-a \

Step 4: Configure Network and Firewall Rules​

# Create firewall rule to allow NFS traffic
gcloud compute firewall-rules create allow-nfs-from-compute \
    --network=default \
    --allow=tcp:2049 \
    --source-ranges=10.0.0.0/24 \
    --target-tags=filestore-client \
    --description="Allow NFS traffic to Filestore"

# For more restrictive access, use specific source IPs
gcloud compute firewall-rules create allow-nfs-from-specific-vms \
    --network=default \
    --allow=tcp:2049,udp:2049 \
    --source-tags=needs-filestore-access \
    --description="Allow NFS from tagged VMs only"

# Verify firewall rules
gcloud compute firewall-rules list --filter="name~nfs"

Step 5: Mount Filestore on Compute Engine VM​

On Linux (Ubuntu/Debian)​

# SSH into your VM
gcloud compute ssh VM_NAME --zone=us-central1-a

# Install NFS client
sudo apt-get update
sudo apt-get install -y nfs-common

# Create mount point
sudo mkdir -p /mnt/filestore

# Mount the Filestore instance
sudo mount -t nfs -o rw,hard,nfsvers=3,tcp,rsize=1048576,wsize=1048576 \
    FILESTORE_IP:/FILE_SHARE_NAME /mnt/filestore

# Example with actual values
sudo mount -t nfs -o rw,hard,nfsvers=3,tcp,rsize=1048576,wsize=1048576 \
    10.0.0.2:/data /mnt/filestore

# Verify mount
df -h | grep filestore
mount | grep nfs

# Test write access
sudo touch /mnt/filestore/test-file.txt
ls -la /mnt/filestore/

On Linux (CentOS/RHEL)​

# Install NFS utilities
sudo yum install -y nfs-utils

# Create mount point
sudo mkdir -p /mnt/filestore

# Mount the Filestore instance
sudo mount -t nfs -o rw,hard,nfsvers=3,tcp,rsize=1048576,wsize=1048576 \
    FILESTORE_IP:/FILE_SHARE_NAME /mnt/filestore

# Verify mount
df -h | grep filestore

Make Mount Persistent (Survive Reboots)​

# Add entry to /etc/fstab
echo "FILESTORE_IP:/FILE_SHARE_NAME /mnt/filestore nfs defaults,_netdev,nfsvers=3,hard,rsize=1048576,wsize=1048576 0 0" | \
    sudo tee -a /etc/fstab

# Example with actual values
echo "10.0.0.2:/data /mnt/filestore nfs defaults,_netdev,nfsvers=3,hard,rsize=1048576,wsize=1048576 0 0" | \
    sudo tee -a /etc/fstab

# Test the fstab entry
sudo umount /mnt/filestore
sudo mount -a
df -h | grep filestore

Automated Mount Script​

#!/bin/bash
# mount-filestore.sh

set -e

FILESTORE_IP="$1"
FILE_SHARE_NAME="$2"
MOUNT_POINT="${3:-/mnt/filestore}"

if [ -z "$FILESTORE_IP" ] || [ -z "$FILE_SHARE_NAME" ]; then
    echo "Usage: $0 <filestore-ip> <file-share-name> [mount-point]"
    exit 1
fi

echo "Installing NFS client..."
if [ -f /etc/debian_version ]; then
    sudo apt-get update
    sudo apt-get install -y nfs-common
elif [ -f /etc/redhat-release ]; then
    sudo yum install -y nfs-utils
fi

echo "Creating mount point: $MOUNT_POINT"
sudo mkdir -p "$MOUNT_POINT"

echo "Mounting Filestore..."
sudo mount -t nfs -o rw,hard,nfsvers=3,tcp,rsize=1048576,wsize=1048576 \
    "${FILESTORE_IP}:/${FILE_SHARE_NAME}" "$MOUNT_POINT"

echo "Verifying mount..."
if mount | grep -q "$MOUNT_POINT"; then
    echo "✓ Filestore mounted successfully at $MOUNT_POINT"
    df -h "$MOUNT_POINT"
else
    echo "✗ Mount failed"
    exit 1
fi

echo "Adding to /etc/fstab for persistence..."
FSTAB_ENTRY="${FILESTORE_IP}:/${FILE_SHARE_NAME} ${MOUNT_POINT} nfs defaults,_netdev,nfsvers=3,hard,rsize=1048576,wsize=1048576 0 0"
if ! grep -q "$FSTAB_ENTRY" /etc/fstab; then
    echo "$FSTAB_ENTRY" | sudo tee -a /etc/fstab
    echo "✓ Added to /etc/fstab"
else
    echo "✓ Already in /etc/fstab"
fi

echo "Setup complete!"

Step 6: Mount Filestore on GKE​

Create Persistent Volume (PV)​

# filestore-pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: filestore-pv
spec:
  capacity:
    storage: 1Ti
  accessModes:
    - ReadWriteMany
  nfs:
    server: FILESTORE_IP # e.g., 10.0.0.2
    path: /FILE_SHARE_NAME # e.g., /data
  mountOptions:
    - hard
    - nfsvers=3
    - rsize=1048576
    - wsize=1048576

Create Persistent Volume Claim (PVC)​

# filestore-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: filestore-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: ''
  volumeName: filestore-pv
  resources:
    requests:
      storage: 1Ti

Deploy to GKE​

# Apply PV and PVC
kubectl apply -f filestore-pv.yaml
kubectl apply -f filestore-pvc.yaml

# Verify
kubectl get pv filestore-pv
kubectl get pvc filestore-pvc

# Create a test deployment
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: filestore-test
spec:
  replicas: 3
  selector:
    matchLabels:
      app: filestore-test
  template:
    metadata:
      labels:
        app: filestore-test
    spec:
      containers:
      - name: busybox
        image: busybox
        command: ['sh', '-c', 'while true; do echo "$(date) - $(hostname)" >> /data/log.txt; sleep 5; done']
        volumeMounts:
        - name: filestore-volume

      - name: filestore-volume

# Verify pods are running
kubectl get pods -l app=filestore-test

# Check that data is being written
kubectl exec -it $(kubectl get pod -l app=filestore-test -o jsonpath='{.items[0].metadata.name}') -- cat /data/log.txt

Step 7: Configure Advanced Settings​

Set Custom NFS Export Options​

# Update Filestore instance with custom NFS export options
gcloud filestore instances update my-filestore \
    --zone=us-central1-a \
    --file-share=name="data",capacity=2TB,nfs-export-options="access-mode=READ_WRITE,squash-mode=NO_ROOT_SQUASH,anon-uid=1000,anon-gid=1000"

Configure Multiple NFS Export Options (using Terraform)​

resource "google_filestore_instance" "multi_export" {
  name     = "multi-export-filestore"
  location = "us-central1-a"
  tier     = "STANDARD"

  file_shares {
    capacity_gb = 2560
    name        = "shared_data"

    # Read-write access for private subnet
    nfs_export_options {
      ip_ranges   = ["10.0.1.0/24"]
      access_mode = "READ_WRITE"
      squash_mode = "NO_ROOT_SQUASH"
    }

    # Read-only access for public subnet
    nfs_export_options {
      ip_ranges   = ["10.0.2.0/24"]
      access_mode = "READ_ONLY"
      squash_mode = "ROOT_SQUASH"
    }
  }

  networks {
    network = "default"
    modes   = ["MODE_IPV4"]
  }
}

Step 8: Set Up Snapshots for Backup​

# Create a snapshot
gcloud filestore snapshots create snapshot-$(date +%Y%m%d-%H%M%S) \
    --instance=my-filestore \
    --instance-location=us-central1-a \
    --file-share=data \
    --description="Daily backup snapshot"

# List snapshots
gcloud filestore snapshots list \
    --instance=my-filestore \
    --instance-location=us-central1-a

# Create snapshot schedule (using Cloud Scheduler)
gcloud scheduler jobs create http daily-filestore-snapshot \
    --location=us-central1 \
    --schedule="0 2 * * *" \
    --uri="https://file.googleapis.com/v1/projects/PROJECT_ID/locations/us-central1-a/instances/my-filestore/snapshots" \
    --http-method=POST \
    --message-body='{"snapshotId":"daily-'$(date +%Y%m%d)'","description":"Automated daily snapshot"}' \
    --oauth-service-account-email=SERVICE_ACCOUNT@PROJECT_ID.iam.gserviceaccount.com

# Restore from snapshot
gcloud filestore instances restore my-filestore \
    --source-snapshot=snapshot-20260115-120000 \
    --source-snapshot-region=us-central1 \
    --file-share=data

Troubleshooting Common Setup Issues​

Issue: Cannot mount Filestore​

# Check if NFS client is installed
dpkg -l | grep nfs-common  # Ubuntu/Debian
rpm -qa | grep nfs-utils    # CentOS/RHEL

# Check if Filestore instance is ready
gcloud filestore instances describe my-filestore --zone=us-central1-a

# Test connectivity
ping FILESTORE_IP
telnet FILESTORE_IP 2049

# Check firewall rules
gcloud compute firewall-rules list | grep nfs

# View system logs
sudo journalctl -u nfs-client.target -f

Issue: Permission denied on mounted directory​

# Check current user and group
id

# Check directory permissions
ls -la /mnt/filestore

# Fix ownership (if needed)
sudo chown -R $USER:$USER /mnt/filestore

# Or use specific UID/GID
sudo chown -R 1000:1000 /mnt/filestore

Issue: Stale NFS file handle​

# Unmount and remount
sudo umount -l /mnt/filestore
sudo mount -a

# Or force unmount
sudo umount -f /mnt/filestore
sudo mount /mnt/filestore

Complete Setup Example Script​

#!/bin/bash
# complete-filestore-setup.sh

set -e

PROJECT_ID="your-project-id"
ZONE="us-central1-a"
INSTANCE_NAME="my-filestore"
FILE_SHARE_NAME="data"
CAPACITY="1TB"
TIER="STANDARD"
NETWORK="default"
MOUNT_POINT="/mnt/filestore"

echo "=== Filestore Complete Setup ==="

# 1. Enable API
echo "Enabling Filestore API..."
gcloud services enable file.googleapis.com --project=$PROJECT_ID

# 2. Create Filestore instance
echo "Creating Filestore instance..."
gcloud filestore instances create $INSTANCE_NAME \
    --project=$PROJECT_ID \
    --zone=$ZONE \
    --tier=$TIER \
    --file-share=name="$FILE_SHARE_NAME",capacity=$CAPACITY \
    --network=name="$NETWORK"

echo "Waiting for Filestore instance to be ready..."
sleep 30

# 3. Get Filestore IP
FILESTORE_IP=$(gcloud filestore instances describe $INSTANCE_NAME \
    --zone=$ZONE \
    --project=$PROJECT_ID \
    --format="value(networks[0].ipAddresses[0])")

echo "Filestore IP: $FILESTORE_IP"

# 4. Create firewall rule
echo "Creating firewall rule..."
gcloud compute firewall-rules create allow-nfs-$INSTANCE_NAME \
    --project=$PROJECT_ID \
    --network=$NETWORK \
    --allow=tcp:2049,udp:2049 \
    --source-ranges=10.0.0.0/8 \
    --description="Allow NFS for $INSTANCE_NAME" || echo "Firewall rule may already exist"

# 5. Install NFS client (run on VM)
echo "Install NFS client with: sudo apt-get install -y nfs-common"

# 6. Generate mount commands
echo ""
echo "=== Setup Complete ==="
echo ""
echo "To mount on your VM, run:"
echo "  sudo mkdir -p $MOUNT_POINT"
echo "  sudo mount -t nfs -o rw,hard,nfsvers=3 ${FILESTORE_IP}:/${FILE_SHARE_NAME} $MOUNT_POINT"
echo ""
echo "To make it persistent, add to /etc/fstab:"
echo "  ${FILESTORE_IP}:/${FILE_SHARE_NAME} $MOUNT_POINT nfs defaults,_netdev,nfsvers=3,hard 0 0"
echo ""
echo "Filestore instance: $INSTANCE_NAME"
echo "IP Address: $FILESTORE_IP"
echo "File Share: /$FILE_SHARE_NAME"
echo ""

Architecture Patterns​

1. Shared Application State Architecture​

Use Case​

Multiple application instances need to share configuration files, cached data, or session information.

Architecture​

┌─────────────────────────────────────┐
│     GKE Cluster / VM Group          │
│  ┌──────┐  ┌──────┐  ┌──────┐      │
│  │ App1 │  │ App2 │  │ App3 │      │
│  └───┬──┘  └───┬──┘  └───┬──┘      │
│      │         │         │          │
│      └─────────┼─────────┘          │
│                │                    │
└────────────────┼────────────────────┘
                 │
                 ▼
         ┌──────────────┐
         │  Filestore   │
         │  (Standard)  │
         │   /shared    │
         └──────────────┘

Implementation​

  • Tier: Standard tier for cost-effective shared storage
  • Capacity: 1-63.9 TB based on requirements
  • Mount Path: /mnt/shared
  • Access Pattern: Multiple readers and writers

Best Practices​

  • Use file locking mechanisms for concurrent writes
  • Implement retry logic for NFS operations
  • Monitor IOPS and throughput metrics
  • Set appropriate file permissions (chmod, chown)

2. Media Processing Pipeline Architecture​

Use Case​

Video encoding, image processing, or batch media transformation workflows.

Architecture​

┌───────────┐      ┌──────────────┐      ┌───────────┐
│  Upload   │─────>│  Filestore   │─────>│ Worker    │
│  Service  │      │  (High Scale)│      │  Pool     │
└───────────┘      │              │      └─────┬─────┘
                   │  /input      │            │
                   │  /output     │            │
                   │  /temp       │<───────────┘
                   └──────────────┘
                          │
                          ▼
                   ┌──────────────┐
                   │ GCS Archive  │
                   └──────────────┘

Implementation​

  • Tier: High Scale for high throughput (320 MB/s+)
  • Capacity: 10-100 TB depending on pipeline volume
  • Directory Structure:
    • /input - Incoming files
    • /processing - Active work
    • /output - Completed files
    • /temp - Temporary artifacts

Best Practices​

  • Implement lifecycle policies to archive to GCS
  • Use Cloud Tasks or Pub/Sub for job coordination
  • Monitor disk space and implement cleanup jobs
  • Optimize chunk sizes for network transfer

3. Container Persistent Storage Architecture​

Use Case​

Kubernetes StatefulSets requiring persistent, shared file storage.

Architecture​

┌─────────────────────────────────────────┐
│         GKE Cluster (Regional)          │
│                                         │
│  ┌────────────────────────────────┐    │

Performance Best Practices​

  1. Mount Options

    # Recommended mount options
    mount -t nfs -o rw,hard,nfsvers=3,tcp,rsize=1048576,wsize=1048576 \
      10.0.0.2:/data /mnt/filestore

  2. Parallel Operations

    • Use multiple threads for large file transfers
    • Implement connection pooling
    • Consider parallel NFS (pNFS) for supported operations

  3. Caching Strategies

    • Enable attribute caching: ac,actimeo=30
    • Use application-level caching
    • Implement read-ahead for sequential access

  4. Network Optimization

    • Use VPC peering for low-latency access
    • Collocate compute and Filestore in same region
    • Monitor network throughput and adjust MTU if needed

gcloud access-context-manager perimeters create filestore-perimeter \

Encryption​

  • Customer-Managed Keys: Use Cloud KMS for CMEK

Cost Optimization​

Pricing Considerations​

  1. Tier Selection

    • Basic: Development/testing (0.20−0.20-0.20−0.25/GB/month)
    • Standard: General production ($0.20/GB/month)
    • High Scale: High throughput workloads ($0.30/GB/month)
    • Enterprise: Mission-critical ($0.35/GB/month)

  2. Capacity Right-Sizing

    • Monitor actual usage vs provisioned capacity
    • Use Cloud Monitoring dashboards
    • Scale up/down based on trends

  3. Snapshot Management

    • Snapshots cost $0.02/GB/month
    • Implement retention policies
    • Delete unused snapshots

  4. Data Lifecycle

    • Archive cold data to Cloud Storage
    • Use Cloud Storage Nearline/Coldline for backups
    • Implement automated cleanup jobs

Migration Strategies​

From On-Premises NFS​

# Initial sync
gsutil -m rsync -r -d /on-prem/nfs gs://temp-bucket/
gsutil -m rsync -r -d gs://temp-bucket/ /mnt/filestore/

# Incremental sync
rsync -avz --progress /on-prem/nfs/ /mnt/filestore/

From Cloud Storage​

# Use Storage Transfer Service
gcloud transfer jobs create gs://source-bucket/ \
  file:///mnt/filestore/destination/ \
  --name="gcs-to-filestore-migration"

From Other Cloud Providers​

  1. Provision Filestore with adequate capacity
  2. Establish VPN/interconnect
  3. Use multi-threaded transfer tools (rclone, parallel rsync)
  4. Verify checksums and data integrity
  5. Update application configurations
  6. Perform cutover during maintenance window

Troubleshooting​

Common Issues​

Issue 1: Slow Performance

# Check mount options
mount | grep nfs

# Verify network connectivity
ping [FILESTORE_IP]

# Check IOPS and throughput
gcloud filestore instances describe INSTANCE_NAME \
  --location=LOCATION

Issue 2: Mount Failures

# Check firewall rules
gcloud compute firewall-rules list --filter="name~nfs"

# Verify NFS service
showmount -e [FILESTORE_IP]

# Check system logs
sudo journalctl -u nfs-client.target

Issue 3: Permission Denied

# Check file permissions
ls -la /mnt/filestore

# Verify UID/GID mapping
id username

# Set appropriate permissions
sudo chown -R user:group /mnt/filestore/dir

Conclusion​

Choosing the right Filestore architecture depends on your specific use case, performance requirements, and budget constraints. Consider the following when designing your solution:

  • Performance needs: Throughput and IOPS requirements
  • Capacity: Current and projected storage needs
  • High availability: Regional vs zonal deployment
  • Security: Access controls and encryption requirements
  • Cost: TCO including storage, snapshots, and network egress
  • Compliance: Data residency and regulatory requirements

For mission-critical workloads, use Enterprise tier with automated snapshots and cross-region backups. For development environments, Basic or Standard tier provides cost-effective shared storage.
