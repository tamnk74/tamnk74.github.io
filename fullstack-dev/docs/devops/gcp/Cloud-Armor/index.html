Top 10 Cloud Armor Architectures for Enterprise Security

Overview​

Google Cloud Armor is a DDoS defense and web application firewall (WAF) service that provides protection for applications running on Google Cloud Platform. This guide covers the top 10 architectural patterns for implementing Cloud Armor to secure your infrastructure.

Architecture Patterns​

1. Global Load Balancer with Cloud Armor Protection​

Description​

The most common architecture pattern integrates Cloud Armor directly with Google Cloud Load Balancing to provide a first line of defense against attacks.

Architecture Components​

  • Global HTTPS Load Balancer: Entry point for all traffic
  • Cloud Armor Security Policy: Attached to the backend service
  • Backend Services: Protected application instances
  • Cloud CDN: Optional caching layer

Implementation Steps​

# Create a security policy
gcloud compute security-policies create edge-security-policy \
    --description "Primary edge security policy"

# Add rules to block specific IP ranges
gcloud compute security-policies rules create 1000 \
    --security-policy edge-security-policy \
    --expression "origin.ip == '203.0.113.0/24'" \
    --action "deny-403"

# Attach policy to backend service
gcloud compute backend-services update web-backend-service \
    --security-policy edge-security-policy \
    --global

Use Cases​

  • E-commerce websites with global customer base
  • SaaS applications requiring global availability
  • Content delivery platforms

Benefits​

  • Automatic DDoS protection at Google's edge
  • Low latency for legitimate users
  • Integrated with Cloud Logging

2. Multi-Region Architecture with Regional Policies​

Description​

Deploy Cloud Armor policies at regional level to provide customized protection based on geographic requirements and compliance needs.

Architecture Components​

  • Regional Load Balancers: Separate load balancers per region
  • Region-Specific Security Policies: Tailored rules for each region
  • Regional Backend Services: Localized application instances
  • Cloud DNS: Traffic distribution

Implementation Steps​

# Create regional security policy for EU
gcloud compute security-policies create eu-security-policy \
    --description "GDPR compliant security policy" \
    --region europe-west1

# Add GDPR-specific rules
gcloud compute security-policies rules create 100 \
    --security-policy eu-security-policy \
    --expression "origin.region_code == 'CN'" \
    --action "deny-403" \
    --region europe-west1

# Create regional security policy for APAC
gcloud compute security-policies create apac-security-policy \
    --description "APAC security policy" \
    --region asia-southeast1

Use Cases​

  • Multi-national enterprises with regional compliance requirements
  • Applications with data residency requirements
  • Region-specific content restrictions

Benefits​

  • Compliance with local regulations (GDPR, CCPA, etc.)
  • Optimized performance per region
  • Granular control over regional traffic

3. Rate Limiting Architecture​

Description​

Implement sophisticated rate limiting to protect against application-layer attacks and ensure fair resource usage.

Architecture Components​

  • Cloud Armor Rate Limiting Rules: Throttle requests per client
  • Custom Rate Limit Keys: IP, headers, or custom expressions
  • Ban Thresholds: Automatic blocking of abusive clients
  • Monitoring Dashboard: Track rate limit violations

Implementation Steps​

# Create policy with rate limiting
gcloud compute security-policies create rate-limit-policy \
    --description "Rate limiting protection"

# Add rate limit rule - 100 requests per minute per IP
gcloud compute security-policies rules create 200 \
    --security-policy rate-limit-policy \
    --expression "true" \
    --action "rate-based-ban" \
    --rate-limit-threshold-count 100 \
    --rate-limit-threshold-interval-sec 60 \
    --ban-duration-sec 600 \
    --conform-action allow \
    --exceed-action deny-429 \
    --enforce-on-key IP

# Rate limit based on URL path
gcloud compute security-policies rules create 210 \
    --security-policy rate-limit-policy \
    --expression "request.path.matches('/api/.*')" \
    --action "rate-based-ban" \
    --rate-limit-threshold-count 50 \
    --rate-limit-threshold-interval-sec 60 \
    --ban-duration-sec 300 \
    --conform-action allow \
    --exceed-action deny-429 \
    --enforce-on-key IP

Use Cases​

  • API endpoints protection
  • Login page brute force prevention
  • Resource-intensive operation protection

Benefits​

  • Prevents credential stuffing attacks
  • Protects against API abuse
  • Ensures fair usage of resources
  • Automatic ban of repeat offenders

4. WAF with OWASP Top 10 Protection​

Description​

Leverage Cloud Armor's preconfigured WAF rules to protect against OWASP Top 10 vulnerabilities.

Architecture Components​

  • Preconfigured WAF Rules: SQL injection, XSS, RCE protection
  • Custom Expression Rules: Application-specific protections
  • Request Inspection: Header, body, and cookie analysis
  • Security Event Logging: Detailed attack logs

Implementation Steps​

# Create WAF policy
gcloud compute security-policies create owasp-protection-policy \
    --description "OWASP Top 10 protection"

# Enable SQL injection protection
gcloud compute security-policies rules create 1000 \
    --security-policy owasp-protection-policy \
    --expression "evaluatePreconfiguredExpr('sqli-stable')" \
    --action "deny-403"

# Enable XSS protection
gcloud compute security-policies rules create 1100 \
    --security-policy owasp-protection-policy \
    --expression "evaluatePreconfiguredExpr('xss-stable')" \
    --action "deny-403"

# Enable Remote Code Execution protection
gcloud compute security-policies rules create 1200 \
    --security-policy owasp-protection-policy \
    --expression "evaluatePreconfiguredExpr('rce-stable')" \
    --action "deny-403"

# Enable Local File Inclusion protection
gcloud compute security-policies rules create 1300 \
    --security-policy owasp-protection-policy \
    --expression "evaluatePreconfiguredExpr('lfi-stable')" \
    --action "deny-403"

# Enable protocol attack protection
gcloud compute security-policies rules create 1400 \
    --security-policy owasp-protection-policy \
    --expression "evaluatePreconfiguredExpr('protocolattack-stable')" \
    --action "deny-403"

Use Cases​

  • Web applications with user input
  • Legacy applications with known vulnerabilities
  • Compliance requirements (PCI-DSS, SOC 2)

Benefits​

  • Protection against common web attacks
  • Regularly updated rule sets
  • Reduces attack surface
  • Simplifies security management

5. Bot Management Architecture​

Description​

Implement intelligent bot detection and mitigation to distinguish between good bots and malicious automated traffic.

Architecture Components​

  • reCAPTCHA Enterprise: Advanced bot detection
  • Cloud Armor Bot Management: Integration with reCAPTCHA
  • User-Agent Analysis: Automated traffic identification
  • Behavior Analytics: Pattern recognition

Implementation Steps​

# Create bot management policy
gcloud compute security-policies create bot-protection-policy \
    --description "Bot management and protection"

# Block known bad bots
gcloud compute security-policies rules create 500 \
    --security-policy bot-protection-policy \
    --expression "request.headers['user-agent'].contains('badbot')" \
    --action "deny-403"

# Challenge suspicious traffic with reCAPTCHA
gcloud compute security-policies rules create 510 \
    --security-policy bot-protection-policy \
    --expression "origin.asn == 12345" \
    --action redirect \
    --redirect-type google-recaptcha

# Allow verified search engine bots
gcloud compute security-policies rules create 100 \
    --security-policy bot-protection-policy \
    --expression "request.headers['user-agent'].contains('Googlebot')" \
    --action "allow"

Use Cases​

  • Content scraping prevention
  • Inventory hoarding protection (e-commerce)
  • API abuse prevention
  • Ad fraud mitigation

Benefits​

  • Protects against automated attacks
  • Preserves legitimate bot access (SEO)
  • Reduces infrastructure costs
  • Improves user experience

6. Geo-Fencing and Access Control​

Description​

Control access based on geographic location to comply with regulations or prevent attacks from specific regions.

Architecture Components​

  • Geographic IP Database: Country and region identification
  • Cloud Armor Geo Rules: Location-based access control
  • Allowlist/Denylist Management: IP range control
  • Access Logging: Geographic traffic analysis

Implementation Steps​

# Create geo-fencing policy
gcloud compute security-policies create geo-fence-policy \
    --description "Geographic access control"

# Allow only specific countries
gcloud compute security-policies rules create 1000 \
    --security-policy geo-fence-policy \
    --expression "origin.region_code in ['US', 'CA', 'GB', 'DE', 'FR']" \
    --action "allow"

# Block high-risk regions
gcloud compute security-policies rules create 2000 \
    --security-policy geo-fence-policy \
    --expression "origin.region_code in ['CN', 'RU', 'KP']" \
    --action "deny-403"

# Allow corporate IP ranges regardless of location
gcloud compute security-policies rules create 100 \
    --security-policy geo-fence-policy \
    --expression "inIpRange(origin.ip, '203.0.113.0/24')" \
    --action "allow"

# Default deny for all other traffic
gcloud compute security-policies rules create 3000 \
    --security-policy geo-fence-policy \
    --expression "true" \
    --action "deny-403"

Use Cases​

  • Export control compliance
  • Regional service availability
  • Attack mitigation from specific regions
  • Content licensing restrictions

Benefits​

  • Regulatory compliance
  • Reduced attack surface
  • Simple geographic access control
  • Protection against nation-state attacks

7. Adaptive Protection with Machine Learning​

Description​

Leverage Cloud Armor's Adaptive Protection feature that uses machine learning to detect and mitigate sophisticated Layer 7 DDoS attacks automatically.

Architecture Components​

  • Adaptive Protection Engine: ML-based attack detection
  • Traffic Baseline: Normal traffic pattern learning
  • Automated Rule Generation: Dynamic rule creation
  • Alert Notifications: Real-time attack alerts
  • Cloud Monitoring Integration: Metrics and dashboards

Implementation Steps​

# Create policy with Adaptive Protection
gcloud compute security-policies create adaptive-protection-policy \
    --description "ML-based DDoS protection"

# Enable Adaptive Protection
gcloud compute security-policies update adaptive-protection-policy \
    --enable-layer7-ddos-defense \
    --layer7-ddos-defense-rule-visibility=STANDARD

# Configure alert notifications
gcloud compute security-policies update adaptive-protection-policy \
    --layer7-ddos-defense-alert-threshold 0.5

# Create monitoring alert
gcloud alpha monitoring policies create \
    --notification-channels=CHANNEL_ID \
    --display-name="Cloud Armor Adaptive Protection Alert" \
    --condition-display-name="Potential Layer 7 DDoS Attack" \
    --condition-threshold-value=1 \
    --condition-threshold-duration=60s

Use Cases​

  • Applications under constant attack
  • High-value targets requiring maximum protection
  • Dynamic attack pattern mitigation
  • Zero-day attack protection

Benefits​

  • Automatic attack detection and mitigation
  • No manual rule configuration needed
  • Adapts to evolving attack patterns
  • Reduces response time to attacks

8. Hybrid Cloud Architecture with Cloud Armor​

Description​

Extend Cloud Armor protection to hybrid environments using Cloud Interconnect or VPN connections.

Architecture Components​

  • Cloud Interconnect: Dedicated connection
  • Cloud Armor at Edge: Protection before on-premises
  • Backend Services: Mix of GCP and on-premises backends
  • Health Checks: Monitor backend availability
  • Network Endpoint Groups (NEGs): Hybrid backend configuration

Implementation Steps​

# Create hybrid backend service
gcloud compute backend-services create hybrid-backend \
    --global \
    --protocol HTTPS \
    --health-checks https-health-check

# Add GCP backend
gcloud compute backend-services add-backend hybrid-backend \
    --instance-group gcp-instances \
    --instance-group-zone us-central1-a \
    --global

# Add on-premises backend via NEG
gcloud compute network-endpoint-groups create onprem-neg \
    --network-endpoint-type NON_GCP_PRIVATE_IP_PORT \
    --zone us-central1-a

gcloud compute network-endpoint-groups update onprem-neg \
    --add-endpoint "ip=10.0.1.100,port=443" \
    --zone us-central1-a

gcloud compute backend-services add-backend hybrid-backend \
    --network-endpoint-group onprem-neg \
    --network-endpoint-group-zone us-central1-a \
    --global

# Apply Cloud Armor policy
gcloud compute backend-services update hybrid-backend \
    --security-policy edge-security-policy \
    --global

Use Cases​

  • Migration from on-premises to cloud
  • Hybrid cloud deployments
  • Disaster recovery configurations

Benefits​

  • Consistent security across environments
  • Protection before traffic reaches on-premises

  • Simplifies security management

9. Named IP Lists for Dynamic Threat Intelligence​

Description​

Use Cloud Armor's named IP lists to manage large sets of IP addresses and integrate with threat intelligence feeds.

Architecture Components​

  • Named IP Lists: Centralized IP list management
  • Threat Intelligence Feeds: External threat data
  • Automated Updates: CI/CD pipeline for list updates
  • Multi-Policy Reuse: Share lists across policies

Implementation Steps​

# Create a named IP list for blocklist
gcloud compute security-policies list-configs create blocklist-ips \
    --description "Dynamically updated blocklist" \
    --ip-ranges "192.0.2.0/24,198.51.100.0/24"

# Create a named IP list for allowlist (trusted partners)
gcloud compute security-policies list-configs create partner-ips \
    --description "Trusted partner IP ranges" \
    --ip-ranges "203.0.113.0/24,198.18.0.0/15"

# Create security policy using named lists
gcloud compute security-policies create threat-intel-policy \
    --description "Threat intelligence based protection"

# Allow trusted partners
gcloud compute security-policies rules create 100 \
    --security-policy threat-intel-policy \
    --expression "inIPList(origin.ip, 'partner-ips')" \
    --action "allow"

# Block known threats
gcloud compute security-policies rules create 1000 \
    --security-policy threat-intel-policy \
    --expression "inIPList(origin.ip, 'blocklist-ips')" \
    --action "deny-403"

# Update named IP list (can be automated)
gcloud compute security-policies list-configs update blocklist-ips \
    --add-ip-ranges "192.0.2.100/32"

Automation Script​

#!/usr/bin/env python3
# update_threat_intel.py - Update Cloud Armor with threat intelligence

import requests
from google.cloud import compute_v1

def fetch_threat_intelligence():
    """Fetch IPs from threat intelligence feed"""
    # Example: Fetch from threat feed API
    response = requests.get('https://threat-feed.example.com/api/malicious-ips')
    return response.json()['ips']

def update_cloud_armor_list(project_id, list_name, ip_ranges):
    """Update Cloud Armor named IP list"""
    client = compute_v1.SecurityPoliciesClient()

    # Update the named IP list
    request = compute_v1.UpdateSecurityPolicyListConfigRequest(
        project=project_id,
        security_policy_list_config=list_name,
        body={
            'ip_ranges': ip_ranges
        }
    )

    operation = client.update_list_config(request=request)
    operation.result()
    print(f"Updated {list_name} with {len(ip_ranges)} IP ranges")

if __name__ == '__main__':
    project_id = 'your-project-id'
    malicious_ips = fetch_threat_intelligence()
    update_cloud_armor_list(project_id, 'blocklist-ips', malicious_ips)

Benefits​

10. Multi-Layer Defense with Cloud Armor and Identity-Aware Proxy (IAP)​

Description​

Combine Cloud Armor's network-layer protection with IAP's identity-based access control for defense in depth.

Architecture Components​

  • Cloud Armor: First layer - network/application security
  • Identity-Aware Proxy (IAP): Second layer - identity verification
  • Cloud Load Balancer: Entry point
  • IAM Policies: Fine-grained access control
  • Cloud Identity: User authentication

Implementation Steps​

# 1. Create and configure Cloud Armor policy
gcloud compute security-policies create multi-layer-policy \
    --description "First layer - network security"

# Add basic protections
gcloud compute security-policies rules create 1000 \
    --security-policy multi-layer-policy \
    --expression "evaluatePreconfiguredExpr('sqli-stable') || evaluatePreconfiguredExpr('xss-stable')" \
    --action "deny-403"

# Rate limiting
gcloud compute security-policies rules create 2000 \
    --security-policy multi-layer-policy \
    --expression "true" \
    --action "rate-based-ban" \
    --rate-limit-threshold-count 1000 \
    --rate-limit-threshold-interval-sec 60 \
    --ban-duration-sec 600 \
    --conform-action allow \
    --exceed-action deny-429 \
    --enforce-on-key IP

# 2. Apply Cloud Armor to backend service
gcloud compute backend-services update app-backend \
    --security-policy multi-layer-policy \
    --global

# 3. Enable IAP on the backend service
gcloud compute backend-services update app-backend \
    --iap=enabled \
    --global

# 4. Configure OAuth consent screen (done via Console or API)

# 5. Grant IAP access to authorized users
gcloud iap web add-iam-policy-binding \
    --resource-type=backend-services \
    --service=app-backend \
    --member='user:alice@example.com' \
    --role='roles/iap.httpsResourceAccessor'

# 6. Grant access to groups
gcloud iap web add-iam-policy-binding \
    --resource-type=backend-services \
    --service=app-backend \
    --member='group:engineering@example.com' \
    --role='roles/iap.httpsResourceAccessor'

Implementation Best Practices​

1. Policy Ordering​

Order rules from most specific to least specific, with lower priority numbers evaluated first:

  • Priority 0-999: Allowlist rules (trusted IPs, partners)
  • Priority 1000-1999: Threat mitigation rules (WAF, bot protection)
  • Priority 2000-2999: Rate limiting rules
  • Priority 3000+: Default rules

2. Testing and Validation​

# Create policy in preview mode first
gcloud compute security-policies create test-policy \
    --description "Testing new rules"

# Add rule in preview mode
gcloud compute security-policies rules create 1000 \
    --security-policy test-policy \
    --expression "origin.region_code == 'XX'" \
    --action "deny-403" \
    --preview

# Check preview metrics before enabling
gcloud compute security-policies rules describe 1000 \
    --security-policy test-policy

# Remove preview mode after testing
gcloud compute security-policies rules update 1000 \
    --security-policy test-policy \
    --no-preview

3. Monitoring and Alerting​

# Export logs to BigQuery for analysis
gcloud logging sinks create cloud-armor-logs \
    bigquery.googleapis.com/projects/PROJECT_ID/datasets/cloud_armor_logs \
    --log-filter='resource.type="http_load_balancer" AND jsonPayload.enforcedSecurityPolicy.name!=""'

# Create alert for high number of blocked requests
gcloud alpha monitoring policies create \
    --notification-channels=CHANNEL_ID \
    --display-name="Cloud Armor - High Block Rate" \
    --condition-threshold-value=1000 \
    --condition-threshold-duration=300s \
    --condition-threshold-filter='resource.type="http_load_balancer" AND metric.type="loadbalancing.googleapis.com/https/request_count" AND metric.label.response_code_class="400"'

4. Performance Optimization​

  • Use preconfigured WAF rules instead of complex custom expressions
  • Combine related conditions using logical operators (&&, ||)
  • Place most frequently matched rules at lower priority numbers
  • Use named IP lists for large IP ranges

5. Cost Optimization​

  • Start with essential rules, add more as needed
  • Use Cloud Armor Standard for basic protection
  • Upgrade to Cloud Armor Managed Protection for advanced features
  • Monitor request evaluation costs in billing

Integration with Cloud Functions for Auto-Remediation​

# Cloud Function to automatically update blocklist
from google.cloud import compute_v1
import json

def update_blocklist(event, context):
    """Triggered by Pub/Sub when malicious IP is detected"""

    # Parse event data
    pubsub_message = base64.b64decode(event['data']).decode('utf-8')
    data = json.loads(pubsub_message)
    malicious_ip = data['ip']

    # Update Cloud Armor named IP list
    client = compute_v1.SecurityPoliciesClient()
    project = 'your-project-id'
    list_name = 'blocklist-ips'

    # Get current list
    current_list = client.get_list_config(
        project=project,
        security_policy_list_config=list_name
    )

    # Add new IP
    ip_ranges = list(current_list.ip_ranges)
    if malicious_ip not in ip_ranges:
        ip_ranges.append(f"{malicious_ip}/32")

        # Update list
        client.update_list_config(
            project=project,
            security_policy_list_config=list_name,
            body={'ip_ranges': ip_ranges}
        )

        print(f"Added {malicious_ip} to blocklist")

Troubleshooting Guide​

Common Issues and Solutions​

1. Legitimate traffic being blocked​

# Check which rule is blocking traffic
gcloud logging read 'resource.type="http_load_balancer" AND jsonPayload.enforcedSecurityPolicy.outcome="DENY"' \
    --limit 50 \
    --format json

# Add allowlist rule with higher priority
gcloud compute security-policies rules create 50 \
    --security-policy your-policy \
    --expression "inIpRange(origin.ip, 'TRUSTED_IP_RANGE')" \
    --action "allow"

2. High false positive rate​

  • Use preview mode to test rules
  • Adjust sensitivity levels on preconfigured rules
  • Add specific exceptions for known patterns

3. Performance issues​

  • Simplify complex expressions
  • Use named IP lists instead of large inline ranges
  • Reduce number of rules by combining related conditions

4. Policy not taking effect​

# Verify policy is attached
gcloud compute backend-services describe your-backend-service --global \
    | grep securityPolicy

# Check rule configuration
gcloud compute security-policies describe your-policy

# Verify rule priority order
gcloud compute security-policies rules list --security-policy your-policy

Security Considerations​

1. Defense in Depth​

Always combine Cloud Armor with other security measures:

  • IAM for access control
  • VPC Service Controls for data perimeter
  • Cloud IDS for intrusion detection
  • Binary Authorization for container security

2. Regular Updates​

  • Review and update rules quarterly
  • Monitor security advisories
  • Test new preconfigured rule versions
  • Update threat intelligence feeds

3. Compliance​

  • Log all blocked requests
  • Retain logs per compliance requirements
  • Document policy changes
  • Regular security audits

4. Principle of Least Privilege​

  • Start with deny-all, add allows as needed
  • Use specific expressions over wildcards
  • Regular access reviews
  • Remove unused rules

Conclusion​

Cloud Armor provides flexible and powerful security capabilities for protecting Google Cloud resources. By implementing these architectural patterns, you can build a robust security posture that protects against DDoS attacks, application-layer threats, and automated abuse while maintaining performance and availability for legitimate users.

Choose the architectures that best fit your security requirements, compliance needs, and operational capabilities. Start with foundational protections and gradually add more sophisticated defenses as your security maturity grows.
