Top 10 Cloud Run Architecture Patterns

Cloud Run is Google Cloud's fully managed serverless platform that automatically scales your containerized applications. This guide explores the top 10 architecture patterns for leveraging Cloud Run effectively in production environments.

1. API Gateway with Multiple Cloud Run Services​

Architecture Overview​

Client → Cloud Load Balancer → API Gateway → Multiple Cloud Run Services
                                              ├── Auth Service
                                              ├── User Service
                                              ├── Product Service
                                              └── Order Service

Implementation​

This pattern uses Cloud Run as a microservices backend with API Gateway or Cloud Load Balancer as the entry point.

# Cloud Run service configuration
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: user-service
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/maxScale: '100'
        autoscaling.knative.dev/minScale: '1'
    spec:
      containers:
        - image: gcr.io/project/user-service:latest
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: url
          resources:
            limits:
              cpu: '2'
              memory: 512Mi

Benefits​

  • Service isolation: Each service can scale independently
  • Easy deployment: Deploy services separately without downtime
  • Cost optimization: Pay only for active request time
  • Language flexibility: Each service can use different tech stacks

Use Cases​

  • E-commerce platforms with multiple business domains
  • SaaS applications with modular features
  • Mobile app backends with distinct API endpoints

2. Event-Driven Architecture with Pub/Sub​

Architecture Overview​

Event Source → Pub/Sub Topic → Cloud Run Service
                              ↓
                         Process Event
                              ↓
                    Cloud Storage / Database

Implementation​

// Cloud Run service handling Pub/Sub messages
import express from 'express';

const app = express();
app.use(express.json());

app.post('/', async (req, res) => {
  const pubsubMessage = req.body.message;
  const data = Buffer.from(pubsubMessage.data, 'base64').toString();

  try {
    const event = JSON.parse(data);
    await processEvent(event);
    res.status(200).send('OK');
  } catch (error) {
    console.error('Error processing event:', error);
    res.status(500).send('Error');
  }
});

async function processEvent(event: any) {
  // Process the event
  console.log('Processing event:', event);
  // Store results, trigger other actions, etc.
}

const port = process.env.PORT || 8080;
app.listen(port, () => {
  console.log(`Listening on port ${port}`);
});

Pub/Sub Push Subscription Configuration​

# Create Pub/Sub topic
gcloud pubsub topics create order-events

# Create push subscription to Cloud Run
gcloud pubsub subscriptions create order-processor \
  --topic=order-events \
  --push-endpoint=https://order-processor-xyz.run.app/ \
  --push-auth-service-account=pubsub-invoker@project.iam.gserviceaccount.com

Benefits​

  • Asynchronous processing: Decouple event producers from consumers
  • Automatic retry: Pub/Sub handles retries on failures
  • Scalability: Cloud Run scales based on message volume
  • Reliability: At-least-once delivery guarantee

Use Cases​

  • Order processing pipelines
  • Real-time data streaming
  • Notification systems
  • ETL workflows

5. BFF (Backend for Frontend) Pattern​

Architecture Overview​

Web Client → Web BFF (Cloud Run) → Microservices
Mobile Client → Mobile BFF (Cloud Run) → Microservices

Implementation​

// Web BFF Service
import express from 'express';
import axios from 'axios';

const app = express();

// Aggregate data from multiple services for web
app.get('/api/dashboard', async (req, res) => {
  try {
    // Parallel requests to multiple services
    const [userProfile, recentOrders, recommendations] = await Promise.all([
      axios.get('https://user-service.run.app/profile', {
        headers: { Authorization: req.headers.authorization },
      }),
      axios.get('https://order-service.run.app/recent', {
        headers: { Authorization: req.headers.authorization },
      }),
      axios.get('https://recommendation-service.run.app/products', {
        headers: { Authorization: req.headers.authorization },
      }),
    ]);

    // Transform and combine data optimized for web UI
    res.json({
      user: transformUserData(userProfile.data),
      orders: transformOrdersForWeb(recentOrders.data),
      recommendations: transformRecommendations(recommendations.data),
      layout: 'desktop-grid',
    });
  } catch (error) {
    res.status(500).json({ error: 'Failed to load dashboard' });
  }
});

function transformUserData(data: any) {
  // Web-specific transformation
  return {
    ...data,
    avatar: data.avatar + '?size=large',
  };
}

  // Include more details for web
  return orders.map((order) => ({

Benefits​

  • Optimized responses: Tailor API responses for each client type
  • Reduced chattiness: Aggregate multiple backend calls
  • Independent evolution: Change backends without affecting clients
  • Security: Add client-specific authentication/authorization

Use Cases​

  • Multi-platform applications (web, mobile, desktop)
  • Complex aggregation requirements
  • Different data needs per client type

6. Serverless Data Processing Pipeline​

Architecture Overview​

Cloud Storage → Cloud Function → Cloud Run (Processing) → BigQuery
     ↓                                ↓
  Upload Event              Transform & Analyze

Implementation​

# Cloud Run service for data processing
from flask import Flask, request, jsonify
import pandas as pd
from google.cloud import bigquery, storage
import io

app = Flask(__name__)
storage_client = storage.Client()
bq_client = bigquery.Client()

@app.route('/process', methods=['POST'])
def process_data():
    # Receive event from Cloud Storage via Pub/Sub
    envelope = request.get_json()

    if not envelope:
        return 'Bad Request: no Pub/Sub message received', 400

    if 'message' not in envelope:
        return 'Bad Request: invalid Pub/Sub message format', 400

    pubsub_message = envelope['message']

    if 'data' not in pubsub_message:
        return 'Bad Request: missing data in message', 400

    # Decode the Pub/Sub message
    import base64
    data = base64.b64decode(pubsub_message['data']).decode('utf-8')
    event = eval(data)

    bucket_name = event['bucket']
    file_name = event['name']

    try:
        # Download file from Cloud Storage
        bucket = storage_client.bucket(bucket_name)
        blob = bucket.blob(file_name)
        content = blob.download_as_text()

        # Process data
        df = pd.read_csv(io.StringIO(content))

        # Transform data
        df_transformed = transform_data(df)

        # Load to BigQuery
        table_id = 'project.dataset.processed_data'
        job = bq_client.load_table_from_dataframe(df_transformed, table_id)
        job.result()

        return jsonify({
            'status': 'success',
            'rows_processed': len(df_transformed)
        }), 200

    except Exception as e:
        print(f'Error processing file: {e}')
        return jsonify({'status': 'error', 'message': str(e)}), 500

def transform_data(df):
    # Apply transformations
    df['processed_date'] = pd.Timestamp.now()
    df['total'] = df['quantity'] * df['price']
    return df

if __name__ == '__main__':
    import os
    port = int(os.environ.get('PORT', 8080))
    app.run(host='0.0.0.0', port=port)

// Server-Sent Events (SSE) implementation
const express = require('express');
const app = express();

// SSE endpoint for real-time updates
app.get('/stream', (req, res) => {
  // Set headers for SSE
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');
  res.setHeader('X-Accel-Buffering', 'no'); // Disable nginx buffering

  // Send initial connection message
  res.write('data: {"type":"connected","timestamp":' + Date.now() + '}\n\n');

  // Simulate real-time updates
  const intervalId = setInterval(() => {
    const data = {
      type: 'update',
      message: 'New data available',
      timestamp: Date.now(),
    };
    res.write(`data: ${JSON.stringify(data)}\n\n`);
  }, 5000);

  // Clean up on client disconnect
  req.on('close', () => {
    clearInterval(intervalId);
    console.log('Client disconnected');
  });
});

// Health check endpoint
app.get('/health', (req, res) => {
  res.json({ status: 'healthy' });
});

const PORT = process.env.PORT || 8080;

  console.log(`SSE server listening on port ${PORT}`);

    --network-endpoint-group=${SERVICE_NAME}-neg \
    --network-endpoint-group-region=${REGION}

9. Hybrid Authentication Architecture​

Architecture Overview​

Client → Cloud Load Balancer → Cloud Run (Auth Service)
                                      ↓
                        ├── Firebase Auth (Social)
                        ├── Identity Platform (Enterprise)
                        └── Custom JWT (Legacy)
                                      ↓
                              Protected Services

Implementation​

// auth-middleware.ts
import { Request, Response, NextFunction } from 'express';
import { OAuth2Client } from 'google-auth-library';
import * as admin from 'firebase-admin';
import jwt from 'jsonwebtoken';

admin.initializeApp();

const oauth2Client = new OAuth2Client();

export async function authMiddleware(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;

  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Unauthorized' });
  }

  const token = authHeader.split('Bearer ')[1];

  try {
    // Try Firebase Authentication
    const decodedToken = await verifyFirebaseToken(token);
    if (decodedToken) {
      req.user = decodedToken;
      return next();
    }
  } catch (e) {
    // Continue to next verification method
  }

  try {
    // Try Google OAuth
    const ticket = await oauth2Client.verifyIdToken({
      idToken: token,
      audience: process.env.GOOGLE_CLIENT_ID,
    });
    const payload = ticket.getPayload();
    if (payload) {
      req.user = payload;
      return next();
    }
  } catch (e) {
    // Continue to next verification method
  }

  try {
    // Try custom JWT
    const decoded = jwt.verify(token, process.env.JWT_SECRET!);
    req.user = decoded;
    return next();
  } catch (e) {
    return res.status(401).json({ error: 'Invalid token' });
  }
}

async function verifyFirebaseToken(token: string) {
  try {
    return await admin.auth().verifyIdToken(token);
  } catch (error) {
    return null;
  }
}

// Protected route example
import express from 'express';
const app = express();

app.use(express.json());

app.get('/api/profile', authMiddleware, (req, res) => {
  res.json({
    user: req.user,
    message: 'Authenticated successfully',
  });
});

const port = process.env.PORT || 8080;
app.listen(port);

10. Blue-Green Deployment with Traffic Splitting​

Architecture Overview​

Traffic Manager
    ├── 90% → Blue Version (Stable)
    └── 10% → Green Version (Canary)

Implementation​

#!/bin/bash
# blue-green-deploy.sh

SERVICE_NAME="api-service"
REGION="us-central1"
NEW_IMAGE="gcr.io/project/api-service:v2.0.0"

# Deploy new version without traffic
echo "Deploying green version..."
gcloud run deploy ${SERVICE_NAME} \
  --image ${NEW_IMAGE} \
  --platform managed \
  --region ${REGION} \
  --no-traffic \
  --tag green

# Get the green revision name
GREEN_REVISION=$(gcloud run revisions list \
  --service ${SERVICE_NAME} \
  --region ${REGION} \
  --filter "metadata.labels.cloud.googleapis.com/service-name=${SERVICE_NAME}" \
  --format "value(metadata.name)" \
  --limit 1)

echo "Green revision: ${GREEN_REVISION}"

# Gradually shift traffic
echo "Starting canary deployment..."
gcloud run services update-traffic ${SERVICE_NAME} \
  --region ${REGION} \
  --to-revisions ${GREEN_REVISION}=10

# Monitor metrics
echo "Monitoring for 10 minutes..."
sleep 600

# Check error rates
ERROR_RATE=$(check_error_rate ${SERVICE_NAME} ${GREEN_REVISION})

if [ ${ERROR_RATE} -lt 1 ]; then
  echo "Canary successful, shifting 50% traffic..."
  gcloud run services update-traffic ${SERVICE_NAME} \
    --region ${REGION} \
    --to-revisions ${GREEN_REVISION}=50

  sleep 300

  echo "Completing deployment..."
  gcloud run services update-traffic ${SERVICE_NAME} \
    --region ${REGION} \
    --to-revisions ${GREEN_REVISION}=100
else
  echo "Canary failed, rolling back..."
  gcloud run services update-traffic ${SERVICE_NAME} \
    --region ${REGION} \
    --to-latest
fi

1. Security​

4. Monitoring and Observability​

// structured-logging.ts
import { Logging } from '@google-cloud/logging';

const logging = new Logging();
const log = logging.log('app-logs');

export function logRequest(req: Request, responseTime: number) {
  const metadata = {
    resource: { type: 'cloud_run_revision' },
    severity: 'INFO',
  };

  const entry = log.entry(metadata, {
    httpRequest: {
      requestMethod: req.method,
      requestUrl: req.url,
      status: res.statusCode,
      latency: `${responseTime}ms`,
    },
    trace: req.header('x-cloud-trace-context'),
    user: req.user?.id,
  });

  log.write(entry);
}

Common Pitfalls to Avoid​

1. Cold Start Issues​

Problem: Long initialization times affect user experience.

Solution:

  • Keep minimum instances warm: --min-instances=1
  • Optimize container size
  • Move heavy initialization to global scope
  • Use lighter base images

2. Connection Pooling​

Problem: Creating new database connections per request.

Solution:

// Bad: New connection per request
app.get('/users', async (req, res) => {
  const db = await createConnection(); // Slow!
  const users = await db.query('SELECT * FROM users');
  res.json(users);
});

// Good: Reuse connection pool
const pool = createConnectionPool(); // Global scope

app.get('/users', async (req, res) => {
  const users = await pool.query('SELECT * FROM users');
  res.json(users);
});

3. Timeout Management​

Problem: Default 5-minute timeout not suitable for long operations.

Solution:

  • Split long operations into smaller chunks
  • Use Pub/Sub for async processing
  • Increase timeout for specific services: --timeout=3600
  • Implement proper retry logic

4. Secret Management​

Problem: Hard-coded credentials in code or environment variables.

Solution:

# Use Secret Manager
gcloud secrets create api-key --data-file=./key.txt

# Reference in Cloud Run
gcloud run deploy service \
  --set-secrets API_KEY=api-key:latest

Setting Up Alerts​

# alert-policy.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: cloudrun-alerts
spec:
  groups:
    - name: cloudrun
      interval: 30s
      rules:
        - alert: HighErrorRate
          expr: |
            rate(cloudrun_request_count{response_code_class="5xx"}[5m]) > 0.05
          annotations:
            summary: 'High error rate detected'
        - alert: HighLatency
          expr: |
            cloudrun_request_latency{percentile="0.95"} > 1000
          annotations:
            summary: '95th percentile latency > 1s'

Conclusion​

Cloud Run offers powerful serverless capabilities for building modern, scalable applications. By implementing these architecture patterns, you can:

  • Build resilient systems with automatic scaling and fault tolerance
  • Optimize costs by paying only for actual usage
  • Deploy faster with container-based deployments
  • Scale globally with multi-region architectures
  • Ensure security with built-in authentication and encryption

Choose the pattern that best fits your use case, and combine multiple patterns for complex applications. Start simple with a single service, then gradually adopt more sophisticated patterns as your needs evolve.
