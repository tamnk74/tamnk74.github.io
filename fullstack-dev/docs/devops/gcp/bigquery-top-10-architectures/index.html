Top 10 BigQuery Architectures for Modern Data Platforms

BigQuery is Google Cloud's serverless, highly scalable data warehouse that enables super-fast SQL queries using the processing power of Google's infrastructure. This guide explores the top 10 architectural patterns for leveraging BigQuery in production environments.

1. Real-Time Streaming Analytics Architecture​

Overview​

Ingest and analyze streaming data in real-time using Cloud Pub/Sub and BigQuery streaming inserts.

Architecture Components​

Data Sources → Cloud Pub/Sub → Dataflow → BigQuery → Data Studio/Looker
                                    ↓
                              Cloud Functions
                                    ↓
                          Real-time Alerting

Key Features​

  • Low Latency: Data available for querying within seconds
  • High Throughput: Supports millions of rows per second
  • Scalability: Auto-scales based on ingestion rate

Implementation Example​

from google.cloud import pubsub_v1, bigquery
import json

# Pub/Sub to BigQuery Streaming
def stream_to_bigquery(event, context):
    """Cloud Function triggered by Pub/Sub"""
    pubsub_message = base64.b64decode(event['data']).decode('utf-8')
    data = json.loads(pubsub_message)

    client = bigquery.Client()
    table_id = "project.dataset.table"

    rows_to_insert = [data]
    errors = client.insert_rows_json(table_id, rows_to_insert)

    if errors:
        print(f"Errors: {errors}")
    else:
        print("Data streamed successfully")

Use Cases​

  • IoT sensor data processing
  • Real-time user behavior analytics
  • Financial transaction monitoring
  • Live dashboards and reporting

Best Practices​

  • Use streaming buffer for immediate data availability
  • Implement deduplication logic for at-least-once delivery
  • Monitor streaming insert quotas and costs
  • Consider batch loading for non-time-sensitive data

2. Data Lake to Data Warehouse Architecture​

Overview​

Build a hybrid architecture combining Cloud Storage (data lake) with BigQuery (data warehouse) for flexible analytics.

Architecture Components​

Raw Data → Cloud Storage (Parquet/Avro) → BigQuery External Tables
              ↓                                    ↓
        Data Catalog                        Materialized Views
              ↓                                    ↓
        Data Lineage                      Optimized Queries

Key Features​

  • Cost Optimization: Store raw data in cheaper Cloud Storage
  • Flexibility: Query data without loading into BigQuery
  • Schema Evolution: Easy to handle changing schemas

Implementation Example​

-- Create External Table
CREATE EXTERNAL TABLE `project.dataset.external_sales`
OPTIONS (
  format = 'PARQUET',
  uris = ['gs://my-bucket/sales/*.parquet'],
  hive_partitioning_options = JSON '{
    "mode": "AUTO",
    "sourceUriPrefix": "gs://my-bucket/sales"
  }'
);

-- Create Materialized View for Performance
CREATE MATERIALIZED VIEW `project.dataset.sales_summary`
CLUSTER BY customer_id
AS
SELECT
  customer_id,
  DATE(order_date) as order_date,
  SUM(amount) as total_amount,
  COUNT(*) as order_count
FROM `project.dataset.external_sales`
GROUP BY customer_id, DATE(order_date);

Use Cases​

  • Multi-format data storage (CSV, JSON, Parquet, Avro)
  • Long-term archival with occasional queries
  • Data science workloads requiring raw data access
  • Cost-sensitive analytics workloads

Best Practices​

  • Use columnar formats (Parquet/Avro) for better performance
  • Implement partitioning and clustering
  • Create materialized views for frequently accessed data
  • Use Data Catalog for metadata management

3. ELT Pipeline with Cloud Composer (Airflow)​

Overview​

Orchestrate complex ELT (Extract, Load, Transform) pipelines using Cloud Composer and BigQuery.

Architecture Components​

Source Systems → Cloud Composer (Airflow)
                       ↓
                 Cloud Storage (Staging)
                       ↓
                   BigQuery (Raw)
                       ↓
              DBT/BigQuery SQL (Transform)
                       ↓
                BigQuery (Curated)
                       ↓
                 BI Tools/APIs

Key Features​

  • Orchestration: Complex workflow management
  • Lineage: Track data transformations
  • Scheduling: Time-based and event-driven triggers
  • Monitoring: Built-in logging and alerting

Implementation Example​

from airflow import DAG
from airflow.providers.google.cloud.operators.bigquery import (
    BigQueryCreateEmptyDatasetOperator,
    BigQueryInsertJobOperator,
)
from airflow.providers.google.cloud.transfers.gcs_to_bigquery import (
    GCSToBigQueryOperator,
)
from datetime import datetime, timedelta

default_args = {
    'owner': 'data-team',
    'depends_on_past': False,
    'start_date': datetime(2024, 1, 1),
    'email_on_failure': True,
    'email_on_retry': False,
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
}

with DAG(
    'bigquery_elt_pipeline',
    default_args=default_args,
    schedule_interval='0 2 * * *',
    catchup=False,
) as dag:

    # Extract and Load
    load_raw_data = GCSToBigQueryOperator(
        task_id='load_raw_data',
        bucket='source-bucket',
        source_objects=['data/*.csv'],
        destination_project_dataset_table='project.raw.sales',
        write_disposition='WRITE_TRUNCATE',
        autodetect=True,
    )

    # Transform - Stage 1
    transform_stage1 = BigQueryInsertJobOperator(
        task_id='transform_stage1',
        configuration={
            'query': {
                'query': '''
                    CREATE OR REPLACE TABLE `project.staging.sales_cleaned` AS
                    SELECT
                        CAST(order_id AS INT64) as order_id,
                        PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%S', order_date) as order_date,
                        customer_id,
                        CAST(amount AS FLOAT64) as amount
                    FROM `project.raw.sales`
                    WHERE order_id IS NOT NULL
                ''',
                'useLegacySql': False,
            }
        },
    )

    # Transform - Stage 2
    transform_stage2 = BigQueryInsertJobOperator(
        task_id='transform_stage2',
        configuration={
            'query': {
                'query': '''
                    CREATE OR REPLACE TABLE `project.analytics.daily_sales`
                    PARTITION BY order_date
                    CLUSTER BY customer_id
                    AS
                    SELECT
                        DATE(order_date) as order_date,
                        customer_id,
                        COUNT(*) as order_count,
                        SUM(amount) as total_amount,
                        AVG(amount) as avg_amount
                    FROM `project.staging.sales_cleaned`
                    GROUP BY order_date, customer_id
                ''',
                'useLegacySql': False,
            }
        },
    )

    load_raw_data >> transform_stage1 >> transform_stage2

Use Cases​

  • Daily batch processing pipelines
  • Multi-source data integration
  • Complex data transformations
  • Data quality validation workflows

Best Practices​

  • Implement idempotent transformations
  • Use partitioning for incremental processing
  • Monitor DAG execution times and costs
  • Implement data quality checks at each stage
  • Use DBT for SQL-based transformations

4. Multi-Region Data Replication Architecture​

Overview​

Replicate BigQuery datasets across multiple regions for disaster recovery and reduced latency.

Architecture Components​

Primary Region (US)                Secondary Region (EU)
       ↓                                    ↓
   BigQuery Dataset  →  Transfer Jobs  → BigQuery Dataset
       ↓                                    ↓
   Application (US)                   Application (EU)

Key Features​

  • Disaster Recovery: Automatic failover capabilities
  • Low Latency: Serve queries from nearest region
  • Compliance: Meet data residency requirements
  • High Availability: 99.99% SLA

Implementation Example​

from google.cloud import bigquery_datatransfer_v1

def create_cross_region_transfer():
    """Create scheduled transfer between regions"""
    client = bigquery_datatransfer_v1.DataTransferServiceClient()

    parent = client.common_project_path("project-id")

    transfer_config = bigquery_datatransfer_v1.TransferConfig(
        destination_dataset_id="eu_dataset",
        display_name="US to EU Replication",
        data_source_id="cross_region_copy",
        schedule="every day 02:00",
        params={
            "source_project_id": "project-id",
            "source_dataset_id": "us_dataset",
        }
    )

    response = client.create_transfer_config(
        parent=parent,
        transfer_config=transfer_config
    )

    print(f"Transfer created: {response.name}")

SQL Implementation​

-- Create dataset in secondary region
CREATE SCHEMA IF NOT EXISTS `project.eu_dataset`
OPTIONS (
  location = 'EU'
);

-- Copy specific tables
CREATE OR REPLACE TABLE `project.eu_dataset.sales`
CLUSTER BY customer_id
AS SELECT * FROM `project.us_dataset.sales`;

-- Create automated snapshot
CREATE SNAPSHOT TABLE `project.eu_dataset.sales_snapshot`
CLONE `project.eu_dataset.sales`
OPTIONS (
  expiration_timestamp = TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
);

Use Cases​

  • Global applications with multi-region users
  • Disaster recovery and business continuity
  • Data sovereignty and compliance requirements
  • Load distribution across regions

Best Practices​

  • Use scheduled transfers during off-peak hours
  • Implement monitoring for replication lag
  • Consider costs of cross-region data transfer
  • Use table snapshots for point-in-time recovery
  • Test failover procedures regularly

5. Federated Query Architecture​

Overview​

Query data across multiple sources (BigQuery, Cloud SQL, Sheets) without data movement.

Architecture Components​

BigQuery
   ↓
External Connections
   ↓
├─ Cloud SQL (PostgreSQL/MySQL)
├─ Cloud Spanner
├─ Google Sheets
└─ Cloud Storage

Key Features​

  • Zero ETL: Query without data movement
  • Unified Analytics: Single SQL interface
  • Cost Effective: No data duplication
  • Real-time: Query live operational data

Implementation Example​

-- Create external connection to Cloud SQL
CREATE EXTERNAL TABLE `project.dataset.cloud_sql_customers`
OPTIONS (
  connection = 'project.region.cloud-sql-connection',
  type = 'EXTERNAL',
  uris = ['CLOUD_SQL'],
  format = 'CLOUD_SQL',
  options = {
    'query': 'SELECT * FROM customers'
  }
);

-- Federated query combining BigQuery and Cloud SQL
SELECT
  o.order_id,
  o.order_date,
  o.amount,
  c.customer_name,
  c.email
FROM `project.dataset.orders` o
JOIN `project.dataset.cloud_sql_customers` c
  ON o.customer_id = c.customer_id
WHERE o.order_date >= CURRENT_DATE() - 30;

-- Query Google Sheets data
SELECT
  A, B, C
FROM
  EXTERNAL_QUERY(
    'project.region.sheets-connection',
    'SELECT * FROM "Sheet1!A1:C100"'
  );

Python Implementation​

from google.cloud import bigquery

Use Cases​

  • Joining operational and analytical data
  • Ad-hoc queries on transactional databases
  • Spreadsheet data analysis at scale
  • Cross-database analytics

Best Practices​

  • Use for read-only analytical queries
  • Cache frequently accessed external data
  • Monitor query performance and costs
  • Limit result set sizes from external sources
  • Consider network latency impact

                       ↓

7. Data Mesh Architecture with BigQuery​

Overview​

Implement domain-oriented decentralized data ownership using BigQuery as the analytical data platform.

Architecture Components​

Domain 1 (Sales)        Domain 2 (Marketing)      Domain 3 (Support)
       ↓                        ↓                        ↓
BigQuery Dataset 1      BigQuery Dataset 2      BigQuery Dataset 3
       ↓                        ↓                        ↓
Domain-owned Tables     Domain-owned Tables     Domain-owned Tables
       ↓                        ↓                        ↓
    Analytics Views     ←   Shared Views   →     Analytics Views
                                ↓
                        Central Data Catalog
                        Data Quality Framework
                        Access Management

Key Features​

  • Domain Ownership: Teams own their analytical data
  • Self-Service: Enable domain teams to publish data products
  • Discoverability: Centralized data catalog
  • Governance: Consistent policies across domains

Implementation Example​

-- Domain 1: Sales Department owns sales data
CREATE SCHEMA IF NOT EXISTS `project.sales_domain`
OPTIONS (
  description = "Sales domain analytical data",
  labels = [("domain", "sales"), ("owner", "sales-team")]
);

-- Sales domain creates data product
CREATE OR REPLACE VIEW `project.sales_domain.customer_orders_v1`
OPTIONS (
  description = "Customer orders data product - Version 1",
  labels = [("data_product", "true"), ("version", "v1")]
)
AS
SELECT
  order_id,
  customer_id,
  order_date,
  total_amount,
  -- Mask sensitive data
  CONCAT('XXX-', SUBSTR(credit_card, -4)) as masked_credit_card
FROM `project.sales_domain.raw_orders`
WHERE order_date >= '2024-01-01';

-- Grant access to other domains
GRANT `roles/bigquery.dataViewer`
ON TABLE `project.sales_domain.customer_orders_v1`
TO "group:marketing-team@company.com";

-- Domain 2: Marketing creates cross-domain view
CREATE OR REPLACE VIEW `project.marketing_domain.customer_360`
AS
SELECT
  c.customer_id,
  c.customer_name,
  o.total_orders,
  o.total_spent,
  m.campaign_responses,
  m.last_interaction_date
FROM `project.marketing_domain.customers` c
LEFT JOIN (
  SELECT customer_id,
         COUNT(*) as total_orders,
         SUM(total_amount) as total_spent
  FROM `project.sales_domain.customer_orders_v1`
  GROUP BY customer_id
) o ON c.customer_id = o.customer_id
LEFT JOIN `project.marketing_domain.campaigns` m
  ON c.customer_id = m.customer_id;

from google.cloud import bigquery, datacatalog_v1

def implement_data_mesh_governance():
    """Implement governance for data mesh"""
    bq_client = bigquery.Client()
    catalog_client = datacatalog_v1.DataCatalogClient()

    # Define policy tags for data classification
    taxonomy = {
        'display_name': 'Data Sensitivity',
        'policy_tags': [
            {'display_name': 'Public'},
            {'display_name': 'Internal'},
            {'display_name': 'Confidential'},
            {'display_name': 'Restricted'}
        ]
    }

    # Apply column-level security
    schema = [
        bigquery.SchemaField("customer_id", "STRING"),
        bigquery.SchemaField(
            "email",
            "STRING",
            policy_tags=bigquery.PolicyTagList(
                names=["projects/project/taxonomies/12345/policyTags/67890"]
            )
        ),
        bigquery.SchemaField("order_amount", "FLOAT64"),
    ]

    # Create data quality rules
    quality_rules = """
        CREATE OR REPLACE TABLE FUNCTION
        `project.governance.validate_customer_data`(input_table STRING)
        AS (
          WITH quality_checks AS (
            SELECT
              *,
              CASE
                WHEN customer_id IS NULL THEN 'Missing customer_id'
                WHEN email NOT LIKE '%@%' THEN 'Invalid email'
                WHEN order_amount < 0 THEN 'Negative amount'
                ELSE 'PASS'
              END as quality_status
            FROM input_table
          )
          SELECT * FROM quality_checks
          WHERE quality_status = 'PASS'
        );
    """

    bq_client.query(quality_rules).result()
    print("Data quality framework implemented")

Implementation Example​

-- Create partitioned and clustered table
CREATE OR REPLACE TABLE `project.analytics.sales_optimized`

Cost Monitoring and Alerting​

from google.cloud import bigquery, monitoring_v3
import datetime

def implement_cost_controls():
    """Implement BigQuery cost controls"""
    client = bigquery.Client()

    # Set custom quota for project
    quota_config = {
        'query': {
            'maximumBytesBilled': 100 * 1024 * 1024 * 1024  # 100 GB
        }
    }

    # Create cost monitoring query
    cost_analysis_query = """
        SELECT
          user_email,
          DATE(creation_time) as query_date,
          COUNT(*) as query_count,
          SUM(total_bytes_processed) / POW(10, 12) as total_tb_processed,
          SUM(total_bytes_processed) / POW(10, 12) * 5 as estimated_cost_usd
        FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
        WHERE creation_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
          AND job_type = 'QUERY'
          AND state = 'DONE'
        GROUP BY user_email, query_date
        ORDER BY estimated_cost_usd DESC
    """

    df = client.query(cost_analysis_query).to_dataframe()
    print("Cost analysis:", df)

    # Create budget alert
    monitoring_client = monitoring_v3.AlertPolicyServiceClient()
    project_name = f"projects/{client.project}"

    alert_policy = monitoring_v3.AlertPolicy(
        display_name="BigQuery Cost Alert",
        conditions=[
            monitoring_v3.AlertPolicy.Condition(
                display_name="High Query Cost",
                condition_threshold=monitoring_v3.AlertPolicy.Condition.MetricThreshold(
                    filter='metric.type="bigquery.googleapis.com/query/scanned_bytes"',
                    comparison=monitoring_v3.ComparisonType.COMPARISON_GT,
                    threshold_value=500 * 1024 * 1024 * 1024 * 1024,  # 500 TB
                    duration={"seconds": 3600}
                )
            )
        ]
    )

    print("Cost monitoring implemented")

def optimize_query_patterns():
    """Demonstrate query optimization techniques"""

    optimizations = {
        'use_partitioning': """
            -- BAD: Full table scan
            SELECT * FROM sales WHERE order_date = '2024-01-15';

            -- GOOD: Partition pruning
            SELECT * FROM sales
            WHERE DATE(order_date) = '2024-01-15';  -- Assumes PARTITION BY DATE(order_date)
        """,

        'use_clustering': """
            -- BAD: Full partition scan
            SELECT * FROM sales WHERE customer_id = 'C123';

            -- GOOD: Cluster pruning
            -- Table CLUSTERED BY customer_id
            SELECT * FROM sales
            WHERE DATE(order_date) = '2024-01-15'
              AND customer_id = 'C123';
        """,

        'select_specific_columns': """
            -- BAD: Reads all columns
            SELECT * FROM large_table;

            -- GOOD: Only reads needed columns
            SELECT customer_id, amount FROM large_table;
        """,

        'use_approximate_functions': """
            -- BAD: Exact count (more expensive)
            SELECT COUNT(DISTINCT user_id) FROM events;

            -- GOOD: Approximate count (faster, cheaper)
            SELECT APPROX_COUNT_DISTINCT(user_id) FROM events;
        """,

        'use_result_caching': """
            -- Enable 24-hour result caching
            SELECT * FROM sales
            WHERE order_date >= CURRENT_DATE() - 7;
            -- Subsequent identical queries use cached results (no cost)
        """,

        'use_bi_engine': """
            -- Reserve BI Engine capacity for acceleration
            -- Fast, cached queries for dashboards
            ALTER BI_CAPACITY `project.region.default`
            SET OPTIONS (
              size_gb = 100,  -- Reserve 100 GB
              preferred_tables = [
                'project.dataset.popular_view',
                'project.dataset.dashboard_data'
              ]
            );
        """
    }

    return optimizations

### Table Design

- [ ] Use partitioning for time-series data
- [ ] Implement clustering on filter/join columns
- [ ] Set partition expiration for old data
- [ ] Enable require_partition_filter option
- [ ] Use appropriate data types (INT64 vs STRING)

### Query Optimization

- [ ] Select only required columns
- [ ] Use WHERE clause to filter early
- [ ] Avoid SELECT DISTINCT on large datasets
- [ ] Use APPROX functions for large counts
- [ ] Leverage result caching (24 hours)
- [ ] Use materialized views for aggregations

### Storage Optimization

- [ ] Enable long-term storage (90+ days)
- [ ] Remove unused tables and views
- [ ] Use table expiration
- [ ] Compress data in Cloud Storage
- [ ] Archive old data to cheaper storage

### Monitoring

- [ ] Set up cost alerts and budgets
- [ ] Monitor slot usage
- [ ] Track query costs by user/team
- [ ] Review INFORMATION_SCHEMA.JOBS regularly
- [ ] Use query dry run to estimate costs

# scripts/deploy.py
import argparse
import yaml
from google.cloud import bigquery
from pathlib import Path

def deploy_schemas(client, config):
    """Deploy table schemas"""
    schemas_dir = Path('sql/schemas')

    for schema_file in schemas_dir.glob('*.json'):
        with open(schema_file) as f:
            schema_config = json.load(f)

        table_id = f"{config['project']}.{config['dataset']}.{schema_config['table_name']}"

        schema = [
            bigquery.SchemaField(field['name'], field['type'], mode=field.get('mode', 'NULLABLE'))
            for field in schema_config['schema']
        ]

        table = bigquery.Table(table_id, schema=schema)

        # Set partitioning
        if 'partitioning' in schema_config:
            table.time_partitioning = bigquery.TimePartitioning(
                field=schema_config['partitioning']['field']
            )

        # Set clustering
        if 'clustering' in schema_config:
            table.clustering_fields = schema_config['clustering']['fields']

        table = client.create_table(table, exists_ok=True)
        print(f"Deployed table: {table_id}")

def deploy_views(client, config):
    """Deploy views"""
    views_dir = Path('sql/views')

    for view_file in views_dir.glob('*.sql'):
        with open(view_file) as f:
            view_sql = f.read()

        # Replace placeholders
        view_sql = view_sql.replace('${PROJECT}', config['project'])
        view_sql = view_sql.replace('${DATASET}', config['dataset'])

        view_name = view_file.stem
        view_id = f"{config['project']}.{config['dataset']}.{view_name}"

        view = bigquery.Table(view_id)
        view.view_query = view_sql

        view = client.create_table(view, exists_ok=True)
        print(f"Deployed view: {view_id}")

def deploy_procedures(client, config):
    """Deploy stored procedures"""
    procedures_dir = Path('sql/procedures')

    for proc_file in procedures_dir.glob('*.sql'):
        with open(proc_file) as f:
            proc_sql = f.read()

        proc_sql = proc_sql.replace('${PROJECT}', config['project'])
        proc_sql = proc_sql.replace('${DATASET}', config['dataset'])

        client.query(proc_sql).result()
        print(f"Deployed procedure: {proc_file.name}")

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument('--env', required=True, choices=['dev', 'staging', 'prod'])
    args = parser.parse_args()

    # Load configuration
    with open(f'config/{args.env}.yaml') as f:
        config = yaml.safe_load(f)

    client = bigquery.Client(project=config['project'])

    print(f"Deploying to {args.env} environment...")

    deploy_schemas(client, config)
    deploy_views(client, config)
    deploy_procedures(client, config)

    print("Deployment completed successfully!")

if __name__ == '__main__':
    main()

from google.cloud import bigquery, datacatalog_v1

def implement_column_level_security():
    """Implement policy tags for column-level security"""

    datacatalog_client = datacatalog_v1.PolicyTagManagerClient()
    bq_client = bigquery.Client()

    project = "my-project"
    location = "us"

    # Create taxonomy
    taxonomy = datacatalog_v1.Taxonomy(
        display_name="Data Classification",
        description="Classification levels for sensitive data"
    )

    parent = f"projects/{project}/locations/{location}"
    taxonomy = datacatalog_client.create_taxonomy(
        parent=parent,
        taxonomy=taxonomy
    )

    # Create policy tags
    policy_tags = [
        {"display_name": "Public", "description": "Publicly accessible data"},
        {"display_name": "Internal", "description": "Internal company data"},
        {"display_name": "Confidential", "description": "Confidential business data"},
        {"display_name": "Restricted", "description": "PII and highly sensitive data"}
    ]

    created_tags = {}
    for tag_config in policy_tags:
        policy_tag = datacatalog_v1.PolicyTag(
            display_name=tag_config["display_name"],
            description=tag_config["description"]
        )

        created_tag = datacatalog_client.create_policy_tag(
            parent=taxonomy.name,
            policy_tag=policy_tag
        )
        created_tags[tag_config["display_name"]] = created_tag
        print(f"Created policy tag: {created_tag.name}")

    # Apply policy tags to table columns
    table_id = "project.dataset.customers"
    table = bq_client.get_table(table_id)

    # Update schema with policy tags
    new_schema = []
    for field in table.schema:
        if field.name == "email":
            field = field.to_api_repr()
            field["policyTags"] = {
                "names": [created_tags["Restricted"].name]
            }
            field = bigquery.SchemaField.from_api_repr(field)
        elif field.name == "ssn":
            field = field.to_api_repr()
            field["policyTags"] = {
                "names": [created_tags["Restricted"].name]
            }
            field = bigquery.SchemaField.from_api_repr(field)

        new_schema.append(field)

    table.schema = new_schema
    table = bq_client.update_table(table, ["schema"])
    print(f"Applied policy tags to {table_id}")

    # Grant access to specific policy tag
    # Users without this permission cannot see the columns
    datacatalog_client.set_iam_policy(
        resource=created_tags["Restricted"].name,
        policy={
            "bindings": [
                {
                    "role": "roles/datacatalog.categoryFineGrainedReader",
                    "members": ["group:pii-authorized@company.com"]
                }
            ]
        }

CREATE OR REPLACE VIEW `project.analytics.customers_masked` AS
SELECT
  customer_id,
  -- Mask email
  CONCAT(
    SUBSTR(email, 1, 2),
    '***@',

  TO_HEX(SHA256(ssn)) as ssn_hash,

  • Conduct regular security audits

Conclusion​

These top 10 BigQuery architectures provide comprehensive patterns for building scalable, performant, and cost-effective data platforms. Choose the architecture that best fits your specific use case, and consider combining multiple patterns for complex requirements.

Key Takeaways​

  1. Start Simple: Begin with basic architectures and add complexity as needed
  2. Cost Awareness: Always implement partitioning and clustering
  3. Security First: Apply appropriate security controls from day one
  4. Monitor Everything: Track costs, performance, and data quality
  5. Automate: Use CI/CD for reproducible deployments
  6. Scale Gradually: Test at small scale before going big
  7. Document: Maintain clear documentation of your architecture
