GCP Global Infrastructure: Regions, Zones, and Edge Network

Overview​

This comprehensive guide covers Google Cloud Platform's global infrastructure, including regions, zones, edge locations, and network architecture. Understanding GCP's infrastructure is essential for designing highly available, low-latency, and resilient applications.

GCP Infrastructure Overview​

Global Infrastructure Components​

Infrastructure Hierarchy​

Organization Level:
  Global Network:
    - Private fiber network
    - 200+ Edge locations worldwide
    - 100+ Points of Presence (PoPs)
    - Submarine cables
    - Peering relationships

Regional Level:
  Regions (40+ worldwide):
    - Independent geographic areas
    - Multiple zones (minimum 3)
    - Region-specific resources
    - Data residency boundaries
    - Regional pricing

Zone Level:
  Zones (120+ worldwide):
    - Isolated deployment areas
    - Within a region
    - Single data center or cluster
    - Independent failure domains
    - Low-latency within region

Resource Level:
  Resources:
    - Zonal: Tied to specific zone
    - Regional: Span multiple zones in region
    - Multi-regional: Span multiple regions
    - Global: Available worldwide

Regions​

What is a Region?​

Definition: Independent geographic area containing multiple zones

Characteristics:
  - Minimum 3 zones per region
  - 100+ miles apart (minimum)
  - Independent power and cooling
  - Separate network infrastructure
  - Data residency boundaries
  - Region-specific pricing

Purpose:
  - Geographic distribution
  - Data sovereignty compliance
  - Disaster recovery
  - Latency optimization
  - Regulatory requirements

Region Selection Criteria​

Factors to Consider:

1. Latency:
   - Proximity to users
   - Network performance
   - Round-trip time (RTT)

   Example:
     Users in Europe → Choose europe-west regions
     Users in Asia → Choose asia-* regions

2. Data Residency:
   - Legal requirements (GDPR, etc.)
   - Compliance regulations
   - Data sovereignty laws

   Example:
     EU data must stay in EU → europe-* regions only
     China requirements → Special considerations

3. Cost:
   - Regional pricing varies
   - Network egress costs
   - Currency considerations

   Example:
     us-central1: Often lowest cost
     europe-west2: Higher cost due to UK
     Check pricing calculator

4. Service Availability:
   - Not all services in all regions
   - New services launch in select regions
   - Check service availability

   Example:
     AI/ML services: Limited regions initially
     Specialized hardware: Select regions

5. Disaster Recovery:
   - Geographic diversity
   - Natural disaster risks
   - Regional failures

   Example:
     Primary: us-central1 (Iowa)
     DR: us-east1 (South Carolina)
     Avoid: Same coast for DR

6. Network Performance:
   - Premium vs Standard tier
   - Interconnect availability
   - Peering locations

Regional Resources​

Regional Resources (span multiple zones in region):
  Compute:
    - Regional Managed Instance Groups (MIG)
    - Regional persistent disks
    - Regional external IP addresses

  Storage:
    - Cloud Storage (regional buckets)
    - Regional Cloud SQL replicas

  Networking:
    - Subnets (always regional)
    - Regional load balancers
    - Cloud NAT
    - Cloud Router

  Kubernetes:
    - Regional GKE clusters
    - Node pools across zones

Benefits:
  - Higher availability than zonal
  - Automatic zone distribution
  - Survive zone failures
  - Load balancing across zones

Zones​

What is a Zone?​

Definition: Deployment area within a region, isolated failure domain

Characteristics:
  - Single data center or cluster of data centers
  - Independent power, cooling, networking
  - Connected via low-latency links within region
  - Typically < 5ms latency between zones in region
  - Minimum 3 zones per region
  - Named with region + letter (e.g., us-central1-a)

Purpose:
  - Fault isolation
  - High availability within region
  - Resource placement control
  - Disaster recovery within region

Zone Architecture​

Zonal Resources​

Zonal Resources (tied to specific zone):
  Compute:
    - VM instances
    - Zonal persistent disks
    - Instance templates (zone-specific)
    - Sole-tenant nodes

  Storage:
    - Zonal persistent disks (SSD, Standard)
    - Local SSD

  Kubernetes:
    - Zonal GKE clusters
    - Node pools in specific zone

Important Notes:
  - Cannot move zonal resources between zones
  - Must create snapshot and recreate in new zone
  - Zone failures affect zonal resources
  - Plan for zone redundancy

Zone Selection and Best Practices​

Selection Criteria:

1. High Availability:
   - Distribute across multiple zones
   - Use regional resources when possible
   - Implement health checks

   Example Architecture:
     Zone A: 33% of instances
     Zone B: 33% of instances
     Zone C: 34% of instances

2. Affinity/Anti-Affinity:
   - Spread policy: Different zones
   - Compact policy: Same zone (lower latency)

   Use Cases:
     Web tier: Spread across zones
     Database cluster: Consider zone locality
     Batch processing: Same zone for speed

3. Resource Availability:
   - Some machine types limited to specific zones
   - GPU availability varies by zone
   - Check quota per zone

   Example:
     gcloud compute machine-types list --zones=us-central1-a

4. Cost Optimization:
   - Inter-zone traffic: Free within region
   - Same zone: Lowest latency, free traffic
   - Cross-region: Charges apply

5. Disaster Recovery:
   - Never use single zone for production
   - Distribute stateful and stateless apps
   - Test zone failure scenarios

Zone Failures and Recovery​

Common Zone Failure Scenarios:

1. Planned Maintenance:
   - Live migration (most VMs)
   - Notification in advance
   - Automatic or manual scheduling

   Impact:
     - Minimal for most workloads
     - Brief performance degradation possible

2. Unplanned Outages:
   - Hardware failures
   - Network issues
   - Power problems

   Recovery:
     - Automatic failover (regional resources)
     - Manual intervention (zonal resources)
     - Load balancer redirects traffic

3. Mitigation Strategies:
   - Use regional managed instance groups
   - Implement health checks
   - Auto-healing enabled
   - Multi-zone database replicas
   - Regular disaster recovery drills

Example Failure Scenario:
  Situation: Zone us-central1-a fails

  Impact:
    ❌ Zonal VMs in zone-a: Down
    ❌ Zonal disks in zone-a: Unavailable
    ✅ Regional MIG: Auto-creates in zone-b/c
    ✅ Regional LB: Routes to healthy zones
    ✅ Regional persistent disk: Continues operating

  Recovery:
    - Auto-healing creates new instances
    - Load balancer updates backend health
    - Traffic flows to remaining zones
    - RTO: 5-10 minutes (typical)

Edge Locations and CDN​

Google's Edge Network​

Edge Network Components:

1. Points of Presence (PoPs):
   - 200+ locations worldwide
   - Network interconnection points
   - Peering with ISPs
   - Entry to Google network

   Purpose:
     - Reduce latency
     - Improve performance
     - Better user experience

2. Cloud CDN:
   - Content caching at edge
   - 200+ edge locations
   - Integrated with Load Balancer
   - HTTPS support

   Use Cases:
     - Static content (images, CSS, JS)
     - Video streaming
     - Software downloads
     - API responses (cacheable)

3. Media CDN:
   - Specialized for media delivery
   - Video on demand (VOD)
   - Live streaming
   - Large file delivery

4. Premium Network Tier:
   - Traffic enters Google network at edge
   - Travels on Google's network
   - Lower latency, better performance
   - Higher cost

5. Standard Network Tier:
   - Traffic on public internet
   - Enters Google network near region
   - Higher latency, lower cost
   - Regional egress

Edge Caching Architecture​

Cloud CDN Configuration​

# Enable Cloud CDN on backend service

# 1. Create backend bucket for static content
gcloud compute backend-buckets create static-backend \
  --gcs-bucket-name=my-static-content \
  --enable-cdn \
  --cache-mode=CACHE_ALL_STATIC \
  --default-ttl=3600 \
  --max-ttl=86400 \
  --client-ttl=3600

# 2. Create backend service with CDN for dynamic content
gcloud compute backend-services create web-backend \
  --protocol=HTTP \
  --global \
  --enable-cdn \
  --cache-mode=USE_ORIGIN_HEADERS \
  --default-ttl=0 \
  --max-ttl=3600 \
  --client-ttl=3600 \
  --negative-caching \
  --negative-caching-policy=404=300,500=60

# 3. Cache key configuration
gcloud compute backend-services update web-backend \
  --global \
  --cache-key-include-protocol \
  --cache-key-include-host \
  --cache-key-include-query-string \
  --cache-key-query-string-whitelist=param1,param2

# 4. Create URL map with CDN backend
gcloud compute url-maps create cdn-lb \
  --default-backend-bucket=static-backend

# Add path rules
gcloud compute url-maps add-path-matcher cdn-lb \
  --path-matcher-name=paths \
  --default-backend-bucket=static-backend \
  --backend-service-path-rules="/api/*=web-backend,/dynamic/*=web-backend"

# 5. Invalidate cache
gcloud compute url-maps invalidate-cdn-cache cdn-lb \
  --path="/images/*"

# Invalidate specific files
gcloud compute url-maps invalidate-cdn-cache cdn-lb \
  --path="/css/style.css" \
  --path="/js/app.js"

# Check CDN cache statistics
gcloud monitoring time-series list \
  --filter='metric.type="loadbalancing.googleapis.com/https/backend_request_count"'

Cache Control Headers​

HTTP Headers for CDN Control:

Cache-Control:
  public: Can be cached by CDN and browser
  private: Only browser cache, not CDN
  no-cache: Revalidate with origin
  no-store: Do not cache anywhere
  max-age=3600: Cache for 1 hour
  s-maxage=7200: CDN cache for 2 hours (overrides max-age)

  Examples:
    # Cache static assets for 1 year
    Cache-Control: public, max-age=31536000, immutable

    # Cache API response for 5 minutes
    Cache-Control: public, max-age=300, s-maxage=300

    # Don't cache sensitive data
    Cache-Control: private, no-cache, no-store, must-revalidate

Expires:
  Absolute expiration time
  Less flexible than Cache-Control

  Example:
    Expires: Wed, 01 Jan 2025 00:00:00 GMT

ETag:
  Validates if content changed
  Enables conditional requests

  Example:
    ETag: "abc123def456"
    If-None-Match: "abc123def456" (returns 304 if unchanged)

Vary:
  Cache different versions based on headers

  Examples:
    Vary: Accept-Encoding (cache gzip/brotli separately)
    Vary: Accept-Language (cache per language)
    Vary: User-Agent (cache per device type)

Network Infrastructure​

Google's Global Network​

Network Architecture:

1. Private Fiber Network:
   - Google-owned fiber cables
   - Submarine cables (investments)
   - Dedicated infrastructure
   - 100 Tbps+ capacity

   Submarine Cables:
     - Dunant (USA-France)
     - Grace Hopper (USA-UK-Spain)
     - Curie (USA-Chile)
     - Junior (Brazil-Argentina)

2. Network Tiers:

   Premium Tier (default):
     - Traffic enters at nearest edge location
     - Travels on Google's network
     - Lower latency, better performance
     - Global load balancing
     - SLA: 99.99% availability

     Use Cases:
       - Production applications
       - Global services
       - Low-latency requirements
       - Multi-region deployments

   Standard Tier:
     - Traffic on public internet
     - Enters Google network at region
     - Regional routing
     - Lower cost (up to 60% cheaper)
     - SLA: 99.9% availability

     Use Cases:
       - Cost-sensitive workloads
       - Regional applications
       - Non-critical services
       - Batch processing

3. Network Service Tiers Comparison:

   Feature              | Premium    | Standard
   ---------------------|------------|------------
   Global Routing       | Yes        | No
   Entry Point          | Edge PoP   | Region
   Latency              | Lower      | Higher
   Performance          | Better     | Good
   Cost                 | Higher     | Lower
   Load Balancing       | Global     | Regional
   SLA                  | 99.99%     | 99.9%

Network Topology​

Inter-Region Connectivity​

Region-to-Region Communication:

Within GCP:
  Same Region, Different Zones:
    - Free
    - Low latency (<5ms)
    - High bandwidth

  Different Regions, Same Continent:
    - Egress charges apply
    - Low latency (10-50ms)
    - $0.01/GB (approximate)

  Different Continents:
    - Egress charges apply
    - Higher latency (100-300ms)
    - $0.08-$0.12/GB (varies by region)

VPC Peering:
  - Connect VPCs privately
  - No internet traversal
  - Reduced latency
  - Free within same region
  - Egress charges cross-region

VPN/Interconnect:
  - Hybrid connectivity
  - On-premises to GCP
  - Encrypted tunnels (VPN)
  - Dedicated connection (Interconnect)

High Availability Architecture​

Multi-Zone Architecture​

Architecture Pattern: Active-Active across zones

Components:
  Load Balancer (Regional):
    - Distributes traffic across zones
    - Health checks for automatic failover
    - Session affinity support

  Compute (Regional MIG):
    - Instances distributed across zones
    - Auto-scaling per zone
    - Auto-healing on failures

  Database:
    - Regional Cloud SQL (HA config)
    - Cross-zone replication
    - Automatic failover

  Storage:
    - Regional Cloud Storage buckets
    - Multi-zone redundancy
    - Automatic replication

Benefits:
  - Survive zone failures
  - No manual intervention
  - Automatic failover
  - RTO: Minutes
  - RPO: Near-zero

Multi-Zone Deployment Example

#!/bin/bash
# Deploy highly available application across zones

PROJECT_ID="my-project"
REGION="us-central1"
ZONES=("us-central1-a" "us-central1-b" "us-central1-c")

# 1. Create instance template
gcloud compute instance-templates create web-template \
  --machine-type=e2-medium \
  --image-family=debian-11 \
  --image-project=debian-cloud \
  --boot-disk-size=10GB \
  --boot-disk-type=pd-balanced \
  --tags=web-server,http-server \
  --metadata=startup-script='#!/bin/bash
    apt-get update
    apt-get install -y nginx
    systemctl enable nginx
    systemctl start nginx
    echo "Zone: $(curl -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/zone)" > /var/www/html/index.html'

# 2. Create regional managed instance group
gcloud compute instance-groups managed create web-mig \
  --template=web-template \
  --size=3 \
  --region=$REGION \
  --health-check=web-health-check \
  --initial-delay=300

# Distribute across zones
gcloud compute instance-groups managed set-target-pools web-mig \
  --region=$REGION \
  --target-distribution-shape=EVEN

# 3. Configure auto-scaling
gcloud compute instance-groups managed set-autoscaling web-mig \
  --region=$REGION \
  --min-num-replicas=3 \
  --max-num-replicas=10 \
  --target-cpu-utilization=0.75 \
  --cool-down-period=90

# 4. Create health check
gcloud compute health-checks create http web-health-check \
  --port=80 \
  --check-interval=10s \
  --timeout=5s \
  --healthy-threshold=2 \
  --unhealthy-threshold=3

# 5. Create regional backend service
gcloud compute backend-services create web-backend \
  --protocol=HTTP \
  --health-checks=web-health-check \
  --region=$REGION \
  --load-balancing-scheme=EXTERNAL_MANAGED

# Add instance group as backend
gcloud compute backend-services add-backend web-backend \
  --instance-group=web-mig \
  --instance-group-region=$REGION \
  --balancing-mode=UTILIZATION \
  --max-utilization=0.8 \
  --region=$REGION

# 6. Create URL map
gcloud compute url-maps create web-lb \
  --default-service=web-backend \
  --region=$REGION

# 7. Create HTTP proxy
gcloud compute target-http-proxies create web-http-proxy \
  --url-map=web-lb \
  --region=$REGION

# 8. Create forwarding rule (gets external IP)
gcloud compute forwarding-rules create web-http-rule \
  --load-balancing-scheme=EXTERNAL_MANAGED \
  --target-http-proxy=web-http-proxy \
  --ports=80 \
  --region=$REGION

# Get external IP
LB_IP=$(gcloud compute forwarding-rules describe web-http-rule \
  --region=$REGION \
  --format="get(IPAddress)")

echo "✅ Multi-zone deployment complete!"
echo "Load Balancer IP: $LB_IP"
echo "Test: curl http://$LB_IP"
echo ""
echo "Instances are distributed across zones:"
gcloud compute instance-groups managed list-instances web-mig \
  --region=$REGION

Disaster Recovery Strategies​

DR Strategy Levels​

Level 1: Backup and Restore (RTO: Hours-Days, RPO: Hours):
  Implementation:
    - Regular snapshots of disks
    - Database backups to Cloud Storage
    - Configuration backups
    - Automated backup schedules

  Pros:
    - Lowest cost
    - Simple implementation
    - Good for non-critical workloads

  Cons:
    - High RTO (hours to days)
    - High RPO (hours of data loss)
    - Manual recovery process

  Use Cases:
    - Development environments
    - Non-critical applications
    - Archival storage

Level 2: Pilot Light (RTO: Hours, RPO: Minutes):
  Implementation:
    - Minimal resources running in DR region
    - Data replication active
    - Quick scale-up capability
    - Automated failover scripts

  Pros:
    - Lower RTO than backup/restore
    - Cost-effective
    - Faster recovery

  Cons:
    - Still some downtime
    - Requires manual activation
    - Testing needed

  Use Cases:
    - Business-critical applications
    - Moderate RTO requirements
    - Cost-sensitive deployments

Level 3: Warm Standby (RTO: Minutes, RPO: Seconds):
  Implementation:
    - Scaled-down version running in DR region
    - Real-time replication
    - Ready to scale up
    - Automated failover possible

  Pros:
    - Low RTO (minutes)
    - Low RPO (seconds)
    - Can serve read traffic

  Cons:
    - Higher cost than pilot light
    - Complexity in management
    - Still requires scaling

  Use Cases:
    - Mission-critical applications
    - Low RTO requirements
    - Read-heavy workloads

Level 4: Active-Active (RTO: Seconds, RPO: Near-zero):
  Implementation:
    - Full deployment in multiple regions
    - Global load balancing
    - Real-time bi-directional replication
    - Automatic failover

  Pros:
    - Near-zero RTO
    - Near-zero RPO
    - Best performance
    - No manual intervention

  Cons:
    - Highest cost
    - Complex to implement
    - Data consistency challenges

  Use Cases:
    - Critical global applications
    - Zero-tolerance for downtime
    - Global user base

Disaster Recovery Implementation​

#!/bin/bash
# DR Strategy: Warm Standby

PRIMARY_REGION="us-central1"
DR_REGION="us-east1"
PROJECT_ID="my-project"

# ============================================
# PRIMARY REGION SETUP
# ============================================

# 1. Create production MIG in primary region
gcloud compute instance-groups managed create prod-mig \
  --template=app-template \
  --size=10 \
  --region=$PRIMARY_REGION \
  --health-check=app-health-check

# 2. Create Cloud SQL with HA
gcloud sql instances create prod-db \
  --database-version=POSTGRES_14 \
  --tier=db-n1-standard-4 \
  --region=$PRIMARY_REGION \
  --availability-type=REGIONAL \
  --backup-start-time=03:00 \
  --enable-bin-log \
  --retained-backups-count=30

# 3. Create read replica in DR region
gcloud sql instances create dr-db-replica \
  --master-instance-name=prod-db \
  --tier=db-n1-standard-4 \
  --region=$DR_REGION \
  --replica-type=READ \
  --availability-type=ZONAL

# ============================================
# DR REGION SETUP (Warm Standby)
# ============================================

# 4. Create smaller MIG in DR region (30% capacity)
gcloud compute instance-groups managed create dr-mig \
  --template=app-template \
  --size=3 \
  --region=$DR_REGION \
  --health-check=app-health-check

# 5. Configure auto-scaling for quick scale-up
gcloud compute instance-groups managed set-autoscaling dr-mig \
  --region=$DR_REGION \
  --min-num-replicas=3 \
  --max-num-replicas=10 \
  --target-cpu-utilization=0.75

# ============================================
# GLOBAL LOAD BALANCER
# ============================================

# 6. Create global backend service
gcloud compute backend-services create global-backend \
  --protocol=HTTP \
  --health-checks=app-health-check \
  --global \
  --enable-cdn

# 7. Add primary region backend
gcloud compute backend-services add-backend global-backend \
  --instance-group=prod-mig \
  --instance-group-region=$PRIMARY_REGION \
  --balancing-mode=UTILIZATION \
  --max-utilization=0.8 \
  --capacity-scaler=1.0 \
  --global

# 8. Add DR region backend (lower capacity scaler for standby)
gcloud compute backend-services add-backend global-backend \
  --instance-group=dr-mig \
  --instance-group-region=$DR_REGION \
  --balancing-mode=UTILIZATION \
  --max-utilization=0.8 \
  --capacity-scaler=0.5 \
  --global

# 9. Create URL map and global forwarding rule
gcloud compute url-maps create global-lb \
  --default-service=global-backend

gcloud compute target-http-proxies create global-proxy \
  --url-map=global-lb

gcloud compute forwarding-rules create global-http-rule \
  --global \
  --target-http-proxy=global-proxy \
  --ports=80

# ============================================
# FAILOVER AUTOMATION
# ============================================

# 10. Create Cloud Function for automated failover
cat > failover.py <<'EOF'
import googleapiclient.discovery

def failover_to_dr(request):
    """Promote DR replica to primary and scale DR MIG"""
    compute = googleapiclient.discovery.build('compute', 'v1')
    sql = googleapiclient.discovery.build('sqladmin', 'v1beta4')

    project = 'my-project'
    dr_region = 'us-east1'

    # 1. Promote read replica to standalone
    sql.instances().promoteReplica(
        project=project,
        instance='dr-db-replica'
    ).execute()

    # 2. Scale up DR MIG to full capacity
    compute.regionInstanceGroupManagers().patch(
        project=project,
        region=dr_region,
        instanceGroupManager='dr-mig',
        body={'targetSize': 10}
    ).execute()

    # 3. Update backend service capacity scaler
    compute.backendServices().patch(
        project=project,
        backendService='global-backend',
        body={
            'backends': [{
                'balancingMode': 'UTILIZATION',
                'capacityScaler': 1.0  # Full traffic to DR
            }]
        }
    ).execute()

    return 'Failover completed'
EOF

# Deploy Cloud Function
gcloud functions deploy failover \
  --runtime=python39 \
  --trigger-http \
  --entry-point=failover_to_dr \
  --region=$DR_REGION

# ============================================
# MONITORING AND ALERTS
# ============================================

# 11. Create alerting policy for regional failure
gcloud alpha monitoring policies create \
  --notification-channels=CHANNEL_ID \
  --display-name="Primary Region Failure" \
  --condition-display-name="High error rate in primary" \
  --condition-threshold-value=0.1 \
  --condition-threshold-duration=300s \
  --condition-threshold-comparison=COMPARISON_GT \
  --condition-threshold-filter='metric.type="loadbalancing.googleapis.com/https/request_count" AND resource.label.region="'$PRIMARY_REGION'"'

echo "✅ DR setup complete!"
echo "Primary: $PRIMARY_REGION (10 instances)"
echo "DR: $DR_REGION (3 instances, warm standby)"
echo "Automatic failover configured"

Practical Examples​

Example 1: Global E-commerce Platform​

Requirements:
  - Users worldwide
  - 99.99% uptime
  - Low latency globally
  - PCI-DSS compliance
  - Data sovereignty (EU data in EU)

Architecture:
  Regions:
    - us-central1 (Primary - North America)
    - europe-west1 (Primary - Europe)
    - asia-southeast1 (Primary - Asia)

  Services:
    Frontend:
      - Regional GKE clusters
      - Cloud CDN for static assets
      - Global Load Balancer

    Backend API:
      - Regional GKE clusters
      - Regional load balancers
      - Service mesh for inter-region

    Database:
      - Cloud Spanner (multi-region)
      - Automatic replication
      - Strong consistency

    Storage:
      - Multi-regional buckets per continent
      - eu-data in EU regions only
      - us-data in US regions only

    Payment Processing:
      - Dedicated project per region
      - VPC Service Controls
      - Isolated network

Example 2: SaaS Application with Regional Isolation​

Requirements:
  - Multi-tenant SaaS
  - Regional data isolation
  - GDPR compliance
  - Tenant-specific regions

Architecture:
  Tenant Deployment Model:
    - Each tenant in specific region
    - No cross-region data sharing
    - Separate VPCs per region

  Regions:
    - us-central1 (US tenants)
    - europe-west1 (EU tenants)
    - asia-southeast1 (APAC tenants)

  Per Region:
    - Dedicated VPC
    - Regional GKE cluster
    - Regional Cloud SQL
    - Regional storage buckets
    - Isolated networking

  Global:
    - Cloud Armor for DDoS
    - Cloud CDN for assets
    - Identity platform for auth
    - Billing and metering service

Best Practices​

Infrastructure Design​

1. Multi-Zone Deployment: ✅ Always use minimum 3 zones for production
  ✅ Use regional managed instance groups
  ✅ Implement health checks
  ✅ Test zone failure scenarios
  ❌ Never run production in single zone

2. Multi-Region Strategy: ✅ Deploy in multiple regions for global apps
  ✅ Use global load balancing
  ✅ Replicate data across regions
  ✅ Plan for regional failures
  ❌ Don't assume regions never fail

3. Resource Distribution: ✅ Spread resources evenly across zones
  ✅ Use auto-scaling for demand changes
  ✅ Monitor zone-level metrics
  ✅ Balance cost vs. availability
  ❌ Don't over-provision unnecessarily

4. Network Design: ✅ Use Premium tier for global apps
  ✅ Consider Standard tier for regional apps
  ✅ Plan for inter-region traffic costs
  ✅ Use Cloud CDN for static content
  ❌ Don't ignore egress costs

5. Data Management: ✅ Use regional storage for single-region data
  ✅ Use multi-regional for global data
  ✅ Implement proper backup strategies
  ✅ Test restore procedures
  ❌ Don't forget about data residency requirements

Disaster Recovery Planning​

1. Define Objectives:
  - RTO (Recovery Time Objective): How long can you be down?
  - RPO (Recovery Point Objective): How much data loss acceptable?
  - Document requirements per application

2. Choose DR Strategy:
  - Critical apps: Active-active or warm standby
  - Important apps: Pilot light
  - Non-critical apps: Backup and restore

3. Implementation: ✅ Automate failover procedures
  ✅ Document runbooks
  ✅ Regular DR testing (quarterly minimum)
  ✅ Monitor replication lag
  ✅ Test recovery procedures
  ✅ Train team on DR processes

4. Testing:
  - Monthly: Automated backup verification
  - Quarterly: Full DR drill
  - Annually: Comprehensive disaster simulation
  - Document results and improve

5. Documentation:
  - Architecture diagrams
  - Failover procedures
  - Rollback procedures
  - Contact information
  - Post-mortem template

Cost Optimization​

1. Region Selection: ✅ Use us-central1 for lowest cost (when possible)
  ✅ Consider network egress costs
  ✅ Check regional pricing differences
  ❌ Don't choose region only on cost

2. Network Tiers: ✅ Use Premium tier for latency-sensitive apps
  ✅ Use Standard tier for regional apps
  ✅ Mix tiers based on workload
  ❌ Don't use Premium if Standard suffices

3. Resource Placement: ✅ Keep communicating resources in same zone (when possible)
  ✅ Use regional resources for HA
  ✅ Minimize cross-region traffic
  ❌ Don't optimize only for cost

4. Storage: ✅ Use Nearline/Coldline for infrequent access
  ✅ Implement lifecycle policies
  ✅ Use appropriate storage class
  ❌ Don't use multi-regional if regional suffices

5. Monitoring: ✅ Set up billing alerts
  ✅ Use cost breakdown reports
  ✅ Monitor egress costs
  ✅ Regular cost reviews
  ❌ Don't ignore small recurring costs

Summary​

Key Takeaways​

Regions:

  • ✅ 40+ regions worldwide
  • ✅ Independent geographic areas
  • ✅ Minimum 3 zones per region
  • ✅ Choose based on latency, compliance, cost
  • ✅ Always deploy multi-region for global apps

Zones:

  • ✅ Isolated failure domains within regions
  • ✅ Always use multiple zones for HA
  • ✅ Test zone failure scenarios
  • ✅ Use regional resources when possible
  • ✅ Monitor zone-level metrics

Edge Network:

  • ✅ 200+ edge locations worldwide
  • ✅ Use Cloud CDN for static content
  • ✅ Premium tier for global performance
  • ✅ Standard tier for cost savings
  • ✅ Configure cache controls properly

High Availability:

  • ✅ Multi-zone: Survive zone failures
  • ✅ Multi-region: Survive regional failures
  • ✅ Implement health checks
  • ✅ Auto-healing and auto-scaling
  • ✅ Regular DR testing
