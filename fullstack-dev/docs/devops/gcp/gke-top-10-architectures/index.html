Top 10 GKE Architecture Patterns

This guide explores the top 10 architecture patterns for Google Kubernetes Engine (GKE) that are proven to work in production environments, from simple deployments to complex multi-region systems.

1. Multi-Tier Application Architecture​

Overview​

The classic three-tier architecture adapted for Kubernetes, separating presentation, business logic, and data layers across different deployments and services.

Architecture Components​

┌─────────────────────────────────────────────────────────┐
│                    GCP Load Balancer                     │
└────────────────────┬────────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────────┐
│                 Ingress Controller                       │
│              (nginx/GKE Ingress)                         │
└──────┬──────────────────────────────┬───────────────────┘
       │                              │
┌──────▼─────────┐           ┌────────▼──────────┐
│  Frontend Pods │           │   API Gateway      │
│  (React/Vue)   │           │   (Service Mesh)   │
└────────────────┘           └────────┬───────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    │                 │                 │
            ┌───────▼──────┐  ┌──────▼──────┐  ┌──────▼──────┐
            │ Service A    │  │ Service B    │  │ Service C    │
            │ (Backend)    │  │ (Backend)    │  │ (Backend)    │
            └───────┬──────┘  └──────┬──────┘  └──────┬──────┘
                    │                │                 │
                    └────────────────┼─────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │   Cloud SQL         │
                          │   (Managed DB)      │
                          └─────────────────────┘

Implementation​

# frontend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
      tier: presentation
  template:

      labels:
        app: frontend
        tier: presentation
    spec:
      containers:
        - name: frontend
          image: gcr.io/project-id/frontend:v1.0.0
          ports:
            - containerPort: 3000
          resources:
            requests:
              memory: '256Mi'
              cpu: '250m'
            limits:
              memory: '512Mi'
              cpu: '500m'
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 30
            periodSeconds: 10
---
apiVersion: v1

metadata:
  name: frontend-service
  namespace: production
spec:
  selector:
    app: frontend
    tier: presentation
  ports:
    - port: 80
      targetPort: 3000

---

      targetPort: 8080

Best Practices​

  • Use namespaces to separate environments (dev, staging, prod)
  • Implement resource quotas and limits
  • Use CloudSQL Auth Proxy for secure database connections
  • Configure horizontal pod autoscaling (HPA) based on CPU/memory metrics
  • Use network policies to restrict inter-pod communication

2. Microservices with Service Mesh (Istio/Anthos)​

Overview​

A sophisticated architecture leveraging service mesh for advanced traffic management, observability, and security between microservices.

Architecture Components​

┌───────────────────────────────────────────────────────────┐
│                  Cloud Load Balancer                      │
└────────────────────┬──────────────────────────────────────┘
                     │
┌────────────────────▼──────────────────────────────────────┐
│            Istio Ingress Gateway                          │
└────────────────────┬──────────────────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │    Istio Service Mesh   │
        │   (Envoy Sidecars)      │
        └────────────┬─────────────┘
                     │
    ┌────────────────┼────────────────┐
    │                │                │
┌───▼────┐      ┌────▼───┐      ┌────▼───┐
│Service1│      │Service2│      │Service3│
│+ Envoy │      │+ Envoy │      │+ Envoy │
└────────┘      └────────┘      └────────┘

Implementation​

# istio-installation.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: istio-system
---
# Service deployment with istio sidecar injection
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: user-service
      version: v1
  template:
    metadata:
      labels:
        app: user-service
        version: v1
      annotations:
        sidecar.istio.io/inject: 'true'
    spec:
      containers:
        - name: user-service
          image: gcr.io/project-id/user-service:v1.0.0
          ports:
            - containerPort: 8080
---
# Virtual Service for traffic management
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: user-service
  namespace: production
spec:
  hosts:
    - user-service
  http:
    - match:
        - headers:
            x-version:
              exact: 'v2'
      route:
        - destination:
            host: user-service
            subset: v2
    - route:
        - destination:
            host: user-service
            subset: v1
          weight: 90
        - destination:
            host: user-service
            subset: v2
          weight: 10
---
# Destination Rule
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: user-service
  namespace: production
spec:
  host: user-service
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 50
        http2MaxRequests: 100
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
---
# Gateway configuration
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: main-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - '*.example.com'
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: gateway-tls-cert
      hosts:
        - '*.example.com'

Benefits​

  • Advanced traffic routing and canary deployments
  • Automatic mutual TLS between services
  • Distributed tracing with Cloud Trace
  • Circuit breaking and retry logic
  • Fine-grained access control

3. Multi-Region High Availability Architecture​

Overview​

A geo-distributed architecture across multiple GCP regions for maximum availability and disaster recovery.

Architecture Components​

                    ┌──────────────────┐
                    │  Cloud DNS       │
                    │  Global LB       │
                    └────────┬─────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
    ┌───────▼──────┐  ┌──────▼──────┐  ┌─────▼────────┐
    │ us-central1  │  │  us-east1   │  │  europe-west1│
    │ GKE Cluster  │  │ GKE Cluster │  │  GKE Cluster │
    └───────┬──────┘  └──────┬──────┘  └──────┬───────┘
            │                │                 │
    ┌───────▼──────┐  ┌──────▼──────┐  ┌──────▼───────┐
    │ Regional     │  │ Regional    │  │  Regional    │
    │ Cloud SQL    │  │ Cloud SQL   │  │  Cloud SQL   │
    └──────────────┘  └─────────────┘  └──────────────┘

Terraform Implementation​

# multi-region-gke.tf
variable "regions" {
  default = ["us-central1", "us-east1", "europe-west1"]
}

# GKE Clusters in multiple regions
resource "google_container_cluster" "regional_clusters" {
  for_each = toset(var.regions)

  name     = "gke-${each.value}"
  location = each.value

  # Regional cluster for high availability
  node_locations = [
    "${each.value}-a",
    "${each.value}-b",
    "${each.value}-c"
  ]

  initial_node_count = 1

  network    = google_compute_network.vpc.name
  subnetwork = google_compute_subnetwork.subnets[each.value].name

  # Enable workload identity
  workload_identity_config {
    workload_pool = "${var.project_id}.svc.id.goog"
  }

  # Enable network policy
  network_policy {
    enabled  = true
    provider = "CALICO"
  }

  # Master authorized networks
  master_authorized_networks_config {
    cidr_blocks {
      cidr_block   = "0.0.0.0/0"
      display_name = "All networks"
    }
  }

  # Maintenance window
  maintenance_policy {
    daily_maintenance_window {
      start_time = "03:00"
    }
  }

  # Enable Cloud Logging and Monitoring
  logging_service    = "logging.googleapis.com/kubernetes"
  monitoring_service = "monitoring.googleapis.com/kubernetes"

  release_channel {
    channel = "REGULAR"
  }
}

# Node pool configuration
resource "google_container_node_pool" "primary_nodes" {
  for_each   = google_container_cluster.regional_clusters

  name       = "primary-node-pool"
  location   = each.value.location
  cluster    = each.value.name

  autoscaling {
    min_node_count = 2
    max_node_count = 10
  }

  node_config {
    machine_type = "e2-standard-4"

    oauth_scopes = [
      "https://www.googleapis.com/auth/cloud-platform"
    ]

    labels = {
      environment = "production"
      region      = each.value.location
    }

    tags = ["gke-node", "production"]

    workload_metadata_config {
      mode = "GKE_METADATA"
    }
  }
}

# Global HTTP Load Balancer
resource "google_compute_global_address" "default" {
  name = "global-lb-ip"
}

# Backend service
resource "google_compute_backend_service" "default" {
  name                  = "multi-region-backend"
  protocol              = "HTTP"
  port_name             = "http"
  timeout_sec           = 30
  enable_cdn            = true

  dynamic "backend" {
    for_each = google_container_cluster.regional_clusters
    content {
      group = google_compute_region_network_endpoint_group.neg[backend.key].id
      balancing_mode = "RATE"
      max_rate_per_endpoint = 100
    }
  }

  health_checks = [google_compute_health_check.default.id]
}

Best Practices​

  • Use Cloud SQL cross-region replication
  • Implement global load balancing with Cloud CDN
  • Configure Cloud DNS for automatic failover
  • Use Config Connector for multi-region resource management
  • Monitor latency per region and implement traffic steering

Node.js Consumer Example​

// consumer.js
const { PubSub } = require('@google-cloud/pubsub');

const pubsub = new PubSub({
  projectId: process.env.PUBSUB_PROJECT_ID,
});

const subscriptionName = process.env.PUBSUB_SUBSCRIPTION;
const subscription = pubsub.subscription(subscriptionName);

// Message handler
function messageHandler(message) {
  console.log(`Received message ${message.id}:`);
  console.log(`Data: ${message.data}`);
  console.log(`Attributes: ${JSON.stringify(message.attributes)}`);

  try {
    const orderData = JSON.parse(message.data.toString());

    // Process the order
    processOrder(orderData);

    // Acknowledge the message
    message.ack();
  } catch (error) {
    console.error('Error processing message:', error);
    // Nack the message to retry
    message.nack();
  }
}

// Error handler
function errorHandler(error) {
  console.error('Subscription error:', error);
}

// Listen for new messages
subscription.on('message', messageHandler);
subscription.on('error', errorHandler);

console.log(`Listening for messages on ${subscriptionName}`);

// Graceful shutdown
process.on('SIGTERM', () => {
  console.log('Shutting down gracefully...');
  subscription.close();
  process.exit(0);
});

5. CI/CD with GitOps (Cloud Build + ArgoCD)​

Overview​

Automated deployment pipeline using Cloud Build for CI and ArgoCD for GitOps-based CD on GKE.

Architecture Components​

┌──────────┐    ┌─────────────┐    ┌──────────────┐
│  GitHub  │───▶│ Cloud Build │───▶│  Artifact    │
│          │    │   (CI)      │    │  Registry    │
└──────────┘    └─────────────┘    └──────┬───────┘
                                           │
                                           ▼
┌──────────┐    ┌─────────────┐    ┌──────────────┐
│  GitOps  │◀───│   ArgoCD    │◀───│  GKE Cluster │
│  Repo    │    │   (CD)      │    │              │
└──────────┘    └─────────────┘    └──────────────┘

Cloud Build Configuration​

# cloudbuild.yaml
steps:
  # Build the Docker image
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA'
      - '-t'
      - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:latest'
      - '.'
    id: 'build-image'

  # Push the image to Artifact Registry
  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'push'
      - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA'
    id: 'push-image'
    waitFor: ['build-image']

  # Run security scan
  - name: 'gcr.io/cloud-builders/gcloud'
    args:
      - 'container'
      - 'images'
      - 'scan'
      - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA'
    id: 'security-scan'
    waitFor: ['push-image']

  # Run tests
  - name: 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA'
    args: ['npm', 'test']
    id: 'run-tests'
    waitFor: ['build-image']

  # Update GitOps repository
  - name: 'gcr.io/cloud-builders/git'
    secretEnv: ['SSH_KEY']
    entrypoint: 'bash'
    args:
      - '-c'
      - |
        echo "$$SSH_KEY" >> /root/.ssh/id_rsa
        chmod 400 /root/.ssh/id_rsa
        ssh-keyscan -t rsa github.com >> /root/.ssh/known_hosts

        git clone git@github.com:org/gitops-repo.git
        cd gitops-repo

        # Update image tag in kustomization
        cd overlays/${_ENVIRONMENT}
        kustomize edit set image gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA

        git config user.email "ci@example.com"
        git config user.name "Cloud Build"
        git add .
        git commit -m "Update ${_SERVICE_NAME} to $SHORT_SHA"
        git push origin main
    id: 'update-gitops-repo'
    waitFor: ['run-tests', 'security-scan']

availableSecrets:
  secretManager:
    - versionName: projects/$PROJECT_ID/secrets/github-ssh-key/versions/latest
      env: 'SSH_KEY'

substitutions:
  _SERVICE_NAME: 'api-service'
  _ENVIRONMENT: 'production'

options:
  machineType: 'N1_HIGHCPU_8'
  logging: CLOUD_LOGGING_ONLY

images:
  - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:$SHORT_SHA'
  - 'gcr.io/$PROJECT_ID/${_SERVICE_NAME}:latest'

kind: K8sRequiredLabels
metadata:
  name: all-must-have-owner
spec:
  match:
    kinds:
      - apiGroups: ['apps']
        kinds: ['Deployment', 'StatefulSet']
  parameters:
    labels:
      - 'owner'
      - 'environment'
      - 'app'

Best Practices Across All Patterns​

1. Security​

  • Enable Binary Authorization
  • Use Workload Identity instead of service account keys
  • Implement network policies
  • Regular security scanning
  • Enable GKE Sandbox for untrusted workloads

2. Cost Optimization​

  • Use Spot VMs for fault-tolerant workloads
  • Enable cluster autoscaling
  • Use preemptible nodes for batch jobs
  • Implement resource quotas and limits
  • Use committed use discounts

3. Reliability​

  • Deploy across multiple zones (regional clusters)
  • Implement pod disruption budgets
  • Use health checks and readiness probes
  • Configure proper resource requests/limits
  • Implement retry logic and circuit breakers

4. Performance​

  • Use SSD persistent disks for databases
  • Enable HTTP/2 and gRPC
  • Implement caching layers
  • Use CDN for static content
  • Optimize container images

5. Operations​

  • Use GitOps for configuration management
  • Implement comprehensive monitoring
  • Set up proper logging aggregation
  • Create runbooks for common incidents
  • Automate routine tasks

Conclusion​

These 10 GKE architecture patterns cover the most common production scenarios, from simple deployments to complex multi-region, multi-cloud systems. Choose the pattern that best fits your requirements, and don't hesitate to combine multiple patterns for more sophisticated architectures.

Each pattern has been battle-tested in production environments and represents current best practices for GKE workloads. Start with simpler patterns and gradually adopt more advanced architectures as your requirements and team expertise grow.
