Networking Fundamentals: Complete Guide

Overview​

This comprehensive guide covers essential networking concepts including TCP/IP, DNS, and Load Balancing. Understanding these fundamentals is crucial for designing, deploying, and troubleshooting cloud infrastructure and applications.

TCP/IP Networking​

OSI Model and TCP/IP Stack​

The OSI (Open Systems Interconnection) model provides a conceptual framework for understanding network communications.

Layer Breakdown​

Layer 7: Application Layer​

Purpose: User-facing protocols and services
Common Protocols:
  HTTP/HTTPS:
    Port: 80/443
    Use: Web traffic
    Example: curl https://example.com

  FTP/SFTP:
    Port: 21/22
    Use: File transfers
    Example: scp file.txt user@server:/path/

  DNS:
    Port: 53
    Use: Name resolution
    Example: nslookup example.com

  SSH:
    Port: 22
    Use: Secure remote access
    Example: ssh user@server

  SMTP:
    Port: 25/587
    Use: Email sending
    Example: Email servers

Example: HTTP Request/Response

# Make HTTP request with detailed output
curl -v https://www.example.com

# Output shows:
# > GET / HTTP/1.1
# > Host: www.example.com
# > User-Agent: curl/7.68.0
# > Accept: */*
#
# < HTTP/1.1 200 OK
# < Content-Type: text/html; charset=UTF-8
# < Content-Length: 1256

Layer 4: Transport Layer​

TCP (Transmission Control Protocol)

Characteristics:
  - Connection-oriented
  - Reliable delivery (acknowledgments)
  - Ordered data transfer
  - Error checking
  - Flow control
  - Congestion control

Use Cases:
  - Web browsing (HTTP/HTTPS)
  - Email (SMTP, IMAP)
  - File transfers (FTP, SFTP)
  - Database connections

TCP Three-Way Handshake:
  1. SYN: Client sends synchronization packet
  2. SYN-ACK: Server acknowledges and sends its own SYN
  3. ACK: Client acknowledges server's SYN
  Connection Established!

UDP (User Datagram Protocol)

Characteristics:
  - Connectionless
  - No guaranteed delivery
  - No ordering
  - Minimal overhead
  - Fast

Use Cases:
  - DNS queries
  - Video streaming
  - Online gaming
  - VoIP (Voice over IP)
  - IoT sensor data

TCP vs UDP Comparison

Layer 3: Network Layer (IP)​

IPv4 Addressing

Format: 32-bit address (4 octets)
Example: 192.168.1.100

Address Classes:
  Class A: 1.0.0.0 to 126.255.255.255 (Large networks)
  Class B: 128.0.0.0 to 191.255.255.255 (Medium networks)
  Class C: 192.0.0.0 to 223.255.255.255 (Small networks)

Private IP Ranges (RFC 1918):
  10.0.0.0/8: 10.0.0.0 to 10.255.255.255 (16,777,216 addresses)
  172.16.0.0/12: 172.16.0.0 to 172.31.255.255 (1,048,576 addresses)
  192.168.0.0/16: 192.168.0.0 to 192.168.255.255 (65,536 addresses)

Special Addresses:
  127.0.0.1: Loopback (localhost)
  0.0.0.0: Default route / Any address
  255.255.255.255: Broadcast

CIDR Notation (Classless Inter-Domain Routing)

Format: IP/prefix_length
Example: 10.0.0.0/24

Common CIDR Blocks:
  /32: 1 address (single host)
  /31: 2 addresses (point-to-point links)
  /30: 4 addresses (2 usable)
  /29: 8 addresses (6 usable)
  /28: 16 addresses (14 usable)
  /27: 32 addresses (30 usable)
  /26: 64 addresses (62 usable)
  /25: 128 addresses (126 usable)
  /24: 256 addresses (254 usable) - Standard subnet
  /23: 512 addresses (510 usable)
  /22: 1,024 addresses (1,022 usable)
  /21: 2,048 addresses (2,046 usable)
  /20: 4,096 addresses (4,094 usable)
  /16: 65,536 addresses (65,534 usable) - Large network
  /8: 16,777,216 addresses - Very large network

Subnet Mask Conversion: /24 = 255.255.255.0
  /25 = 255.255.255.128
  /26 = 255.255.255.192
  /27 = 255.255.255.224
  /28 = 255.255.255.240
  /29 = 255.255.255.248
  /30 = 255.255.255.252
  /31 = 255.255.255.254
  /32 = 255.255.255.255

Subnetting Example

Scenario: Divide 10.0.0.0/16 into subnets for different tiers

Network: 10.0.0.0/16 (65,536 addresses)

Subnet Plan:
  Web Tier (needs 500 hosts):
    Subnet: 10.0.1.0/23

  Database Tier (needs 50 hosts):
    Subnet: 10.0.4.0/26
    Addresses: 64 (62 usable)
    Range: 10.0.4.0 - 10.0.4.63
    Gateway: 10.0.4.1
    Broadcast: 10.0.4.63

  Management (needs 20 hosts):
    Subnet: 10.0.255.0/27
    Addresses: 32 (30 usable)
    Range: 10.0.255.0 - 10.0.255.31
    Gateway: 10.0.255.1
    Broadcast: 10.0.255.31

IPv6 Addressing

Format: 128-bit address (8 groups of 4 hex digits)
Example: 2001:0db8:85a3:0000:0000:8a2e:0370:7334

Shortened Format:
  Full: 2001:0db8:0000:0000:0000:0000:0000:0001
  Short: 2001:db8::1

Special Addresses:
  ::1/128: Loopback (localhost)
  ::/0: Default route
  fe80::/10: Link-local addresses
  fc00::/7: Unique local addresses (private)
  2000::/3: Global unicast addresses

Dual Stack:
  - Run IPv4 and IPv6 simultaneously
  - Gradual migration strategy
  - DNS returns both A (IPv4) and AAAA (IPv6) records

DNS (Domain Name System)​

DNS Architecture​

DNS Record Types​

A Record (Address Record)

Purpose: Map domain to IPv4 address
Format: domain.com. IN A 93.184.216.34
TTL: Time to Live (how long to cache)

Example: example.com.        3600    IN  A       93.184.216.34
  www.example.com.    3600    IN  A       93.184.216.34
  mail.example.com.   3600    IN  A       93.184.216.50

AAAA Record (IPv6 Address)

Purpose: Map domain to IPv6 address
Format: domain.com. IN AAAA 2606:2800:220:1:248:1893:25c8:1946

Example: example.com.        3600    IN  AAAA    2606:2800:220:1:248:1893:25c8:1946

CNAME Record (Canonical Name)

Purpose: Create alias for another domain
Format: alias.com. IN CNAME canonical.com.
Note: Cannot coexist with other records on same name

Example: www.example.com.    3600    IN  CNAME   example.com.
  blog.example.com.   3600    IN  CNAME   hosting.wordpress.com.
  cdn.example.com.    3600    IN  CNAME   cdn.cloudflare.net.

MX Record (Mail Exchange)

Purpose: Specify mail servers for domain
Format: domain.com. IN MX priority mailserver.com.
Priority: Lower number = higher priority

Example: example.com.        3600    IN  MX      10 mail1.example.com.
  example.com.        3600    IN  MX      20 mail2.example.com.
  example.com.        3600    IN  MX      30 mail3.example.com.

TXT Record (Text)

Purpose: Store text information
Use Cases:
  - SPF (Sender Policy Framework)
  - DKIM (DomainKeys Identified Mail)
  - DMARC (Domain-based Message Authentication)
  - Domain verification
  - General metadata

Example: example.com.        3600    IN  TXT     "v=spf1 include:_spf.google.com ~all"
  _dmarc.example.com. 3600    IN  TXT     "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
  example.com.        3600    IN  TXT     "google-site-verification=abc123xyz"

NS Record (Name Server)

Purpose: Delegate subdomain to name servers
Format: subdomain.domain.com. IN NS nameserver.com.

Example: example.com.        86400   IN  NS      ns1.example.com.
  example.com.        86400   IN  NS      ns2.example.com.
  subdomain.example.  86400   IN  NS      ns1.hosting.com.

PTR Record (Pointer)

Purpose: Reverse DNS lookup (IP to domain)
Format: IP-reversed.in-addr.arpa. IN PTR domain.com.

Example: 34.216.184.93.in-addr.arpa.     3600    IN  PTR     example.com.

SRV Record (Service)

Purpose: Define location of services
Format: _service._proto.name. TTL IN SRV priority weight port target.

Example: _sip._tcp.example.com.  3600  IN  SRV  10 60 5060 sipserver.example.com.
  _xmpp._tcp.example.com. 3600  IN  SRV  10 60 5222 chat.example.com.

CAA Record (Certification Authority Authorization)

Purpose: Specify which CAs can issue certificates
Format: domain.com. IN CAA flags tag "value"

Example: example.com.        3600    IN  CAA     0 issue "letsencrypt.org"
  example.com.        3600    IN  CAA     0 issuewild "letsencrypt.org"
  example.com.        3600    IN  CAA     0 iodef "mailto:security@example.com"

DNS Security​

DNSSEC (DNS Security Extensions)

Purpose: Authenticate DNS responses
Components:
  - Digital signatures
  - Chain of trust
  - Public key cryptography

Benefits:
  - Prevents DNS spoofing
  - Ensures data integrity
  - Authenticates source

Record Types:
  RRSIG: Resource Record Signature
  DNSKEY: DNS Public Key
  DS: Delegation Signer
  NSEC/NSEC3: Next Secure (proof of non-existence)

Check DNSSEC

# Verify DNSSEC
dig example.com +dnssec

# Trace with DNSSEC
dig +trace +dnssec example.com

# Validate DNSSEC
delv example.com

DNS over HTTPS (DoH)

Purpose: Encrypt DNS queries
Port: 443 (HTTPS)
Benefits:
  - Privacy protection
  - Bypass censorship
  - Prevent eavesdropping

Providers:
  Cloudflare: https://1.1.1.1/dns-query
  Google: https://dns.google/dns-query
  Quad9: https://dns.quad9.net/dns-query

DNS over TLS (DoT)

Purpose: Encrypt DNS queries
Port: 853
Benefits:
  - Privacy protection
  - Authentication
  - Integrity

Providers:
  Cloudflare: 1.1.1.1, 1.0.0.1
  Google: 8.8.8.8, 8.8.4.4
  Quad9: 9.9.9.9

Load Balancing​

Load Balancing Concepts​

Why Load Balancing?

Benefits:
  Scalability:
    - Handle more traffic
    - Add/remove servers dynamically
    - Horizontal scaling

  High Availability:
    - Eliminate single point of failure
    - Automatic failover
    - Health checks

  Performance:
    - Distribute workload
    - Reduce server load
    - Lower response times

  Flexibility:
    - Zero-downtime deployments
    - A/B testing
    - Gradual rollouts

Load Balancing Algorithms​

Round Robin

Description: Distribute requests evenly across servers
How it works: 1. Request 1 → Server A
  2. Request 2 → Server B
  3. Request 3 → Server C
  4. Request 4 → Server A (repeat)

Pros:
  - Simple implementation
  - Fair distribution
  - No state required

Cons:
  - Doesn't consider server load
  - Doesn't consider server capacity
  - Sessions not sticky

Best for:
  - Stateless applications
  - Similar server capacities
  - Simple setups

Weighted Round Robin

Description: Distribute based on server capacity
How it works:
  Server A (weight: 3): Gets 3 requests
  Server B (weight: 2): Gets 2 requests
  Server C (weight: 1): Gets 1 request

Example:
  A, A, A, B, B, C (repeat)

Best for:
  - Servers with different capacities
  - Gradual traffic migration
  - Canary deployments

Least Connections

Description: Send to server with fewest active connections
How it works:
  Server A: 10 connections
  Server B: 5 connections  ← Next request goes here
  Server C: 15 connections

Pros:
  - Better for long-lived connections
  - Considers actual load
  - Dynamic distribution

Cons:
  - Requires connection tracking
  - More complex than round robin

Best for:
  - Long-lived connections
  - Variable request duration
  - WebSocket connections

IP Hash

Description: Hash client IP to determine server
How it works: hash(client_IP) % server_count = server_index

Example: hash(192.168.1.100) % 3 = 2 → Server C
  hash(192.168.1.101) % 3 = 0 → Server A

Pros:
  - Session persistence
  - Same client → same server
  - No session storage needed

Cons:
  - Uneven distribution possible
  - Adding/removing servers disrupts sessions

Best for:
  - Session-based applications
  - Applications requiring stickiness
  - Without shared session store

Least Response Time

Description: Send to server with lowest response time
How it works:
  Server A: 50ms average
  Server B: 30ms average  ← Next request goes here
  Server C: 80ms average

Pros:
  - Optimal user experience
  - Considers actual performance
  - Adapts to load

Cons:
  - Complex monitoring required
  - Overhead of measuring

Best for:
  - Performance-sensitive apps
  - Heterogeneous infrastructure
  - Geographic distribution

Load Balancer Types​

Layer 4 Load Balancer (Transport Layer)​

Operates at: TCP/UDP level
Makes decisions based on:
  - Source IP
  - Destination IP
  - Source Port
  - Destination Port

Characteristics:
  - Fast (no packet inspection)
  - Protocol agnostic
  - Cannot read HTTP headers
  - Lower latency

Use Cases:
  - Any TCP/UDP traffic
  - Non-HTTP protocols
  - Maximum performance
  - Simple load distribution

Example: HAProxy Layer 4 Config

# haproxy.cfg - Layer 4 TCP load balancing
global
    maxconn 50000
    log /dev/log local0

defaults
    mode tcp
    timeout connect 5000ms
    timeout client  50000ms
    timeout server  50000ms
    option tcplog

frontend tcp_front
    bind *:80
    mode tcp
    default_backend tcp_back

backend tcp_back
    mode tcp
    balance roundrobin
    option tcp-check
    server server1 10.0.1.10:8080 check
    server server2 10.0.1.11:8080 check
    server server3 10.0.1.12:8080 check

Layer 7 Load Balancer (Application Layer)​

Operates at: HTTP/HTTPS level
Makes decisions based on:
  - URL path
  - HTTP headers
  - Cookies
  - Request method
  - Query parameters

Characteristics:
  - Content-based routing
  - SSL termination
  - Request modification
  - Session persistence
  - Higher latency (packet inspection)

Use Cases:
  - Web applications
  - Microservices routing
  - A/B testing
  - API gateways

Example: NGINX Layer 7 Config

# nginx.conf - Layer 7 HTTP load balancing

http {
    upstream backend_api {
        least_conn;  # Least connections algorithm

        server 10.0.1.10:8080 weight=3 max_fails=3 fail_timeout=30s;
        server 10.0.1.11:8080 weight=2;
        server 10.0.1.12:8080 weight=1;

        # Health check
        keepalive 32;
    }

    upstream backend_static {
        server 10.0.2.10:8080;
        server 10.0.2.11:8080;
        server 10.0.2.12:8080;
    }

    server {
        listen 80;
        server_name example.com;

        # Redirect to HTTPS
        return 301 https://$server_name$request_uri;
    }

    server {
        listen 443 ssl http2;
        server_name example.com;

        ssl_certificate /etc/nginx/ssl/cert.pem;
        ssl_certificate_key /etc/nginx/ssl/key.pem;

        # API traffic
        location /api/ {
            proxy_pass http://backend_api;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Timeouts
            proxy_connect_timeout 5s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
        }

        # Static content
        location /static/ {
            proxy_pass http://backend_static;
            proxy_cache my_cache;
            proxy_cache_valid 200 1h;
            add_header X-Cache-Status $upstream_cache_status;
        }

        # WebSocket support
        location /ws/ {
            proxy_pass http://backend_api;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "upgrade";
        }

        # Health check endpoint
        location /health {
            access_log off;
            return 200 "healthy\n";
            add_header Content-Type text/plain;
        }
    }

    # Cache configuration
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m
                     max_size=1g inactive=60m use_temp_path=off;
}

  --named-ports=http:80

# 3. Create backend service with CDN
gcloud compute backend-services create web-backend \
  --protocol=HTTP \
  --health-checks=web-health-check \
  --global \
  --enable-cdn \
  --cache-mode=CACHE_ALL_STATIC \
  --default-ttl=3600 \
  --client-ttl=3600 \
  --max-ttl=86400

# 4. Add backends
gcloud compute backend-services add-backend web-backend \
  --instance-group=web-us-mig \

  --capacity-scaler=1.0 \
  --global

gcloud compute backend-services add-backend web-backend \
  --instance-group=web-eu-mig \
  --instance-group-zone=europe-west1-b \
  --balancing-mode=UTILIZATION \
  --max-utilization=0.8 \
  --capacity-scaler=1.0 \
  --global

# 5. Create URL map with path-based routing
gcloud compute url-maps create web-url-map \
  --default-service=web-backend

# Add path rules
gcloud compute url-maps add-path-matcher web-url-map \
  --path-matcher-name=api-matcher \
  --default-service=web-backend \
  --path-rules="/api/*=api-backend,/admin/*=admin-backend"

# 6. Create SSL certificate
gcloud compute ssl-certificates create web-ssl-cert \
  --domains=example.com,www.example.com \
  --global

# 7. Create target HTTPS proxy
gcloud compute target-https-proxies create web-https-proxy \
  --url-map=web-url-map \
  --ssl-certificates=web-ssl-cert

# 8. Create forwarding rule (gets external IP)
gcloud compute forwarding-rules create web-https-rule \
  --global \
  --target-https-proxy=web-https-proxy \
  --ports=443

# 9. Create HTTP to HTTPS redirect
gcloud compute url-maps import web-http-redirect \
  --source=/dev/stdin <<EOF
name: web-http-redirect
defaultUrlRedirect:
  httpsRedirect: true
  redirectResponseCode: MOVED_PERMANENTLY_DEFAULT
EOF

gcloud compute target-http-proxies create web-http-proxy \
  --url-map=web-http-redirect

gcloud compute forwarding-rules create web-http-rule \
  --global \
  --target-http-proxy=web-http-proxy \
  --ports=80

# 10. Get external IP
EXTERNAL_IP=$(gcloud compute forwarding-rules describe web-https-rule \
  --global \
  --format="get(IPAddress)")

echo "Load Balancer IP: $EXTERNAL_IP"
echo "Configure DNS: example.com A $EXTERNAL_IP"

Health Checks​

Purpose and Types

Purpose:
  - Detect unhealthy servers
  - Remove from rotation
  - Automatic recovery
  - Zero-downtime deployments

Types:
  HTTP Health Check:
    - Send HTTP request
    - Check status code (200 OK)
    - Check response body

  TCP Health Check:
    - Establish TCP connection
    - Check if port is open

  HTTPS Health Check:
    - Same as HTTP with TLS
    - Verify SSL certificate

  gRPC Health Check:
    - Use gRPC protocol
    - Check service status

Health Check Configuration

Parameters:
  Check Interval: 10s
    How often to check

  Timeout: 5s
    Max time to wait for response

  Healthy Threshold: 2
    Consecutive successes to mark healthy

  Unhealthy Threshold: 3
    Consecutive failures to mark unhealthy

Example Timeline:
  t=0s: Server fails (1st failure)
  t=10s: Server fails (2nd failure)
  t=20s: Server fails (3rd failure) → Marked unhealthy, removed
  t=30s: Server recovers (1st success)
  t=40s: Server healthy (2nd success) → Marked healthy, added back

Health Check Endpoint Example

// Express.js health check endpoint
const express = require('express');
const app = express();

let isHealthy = true;
let dbConnected = false;
let redisConnected = false;

// Health check endpoint
app.get('/health', (req, res) => {
  // Check all dependencies
  const checks = {
    status: isHealthy ? 'up' : 'down',
    timestamp: new Date().toISOString(),
    uptime: process.uptime(),
    checks: {
      database: dbConnected ? 'connected' : 'disconnected',
      redis: redisConnected ? 'connected' : 'disconnected',
      memory: getMemoryStatus(),
    }
  };

  // Return 200 if healthy, 503 if not
  const status Code = isHealthy && dbConnected && redisConnected ? 200 : 503;
  res.status(statusCode).json(checks);
});

// Liveness probe - Is the app running?
app.get('/health/live', (req, res) => {
  res.status(200).send('OK');
});

// Readiness probe - Is the app ready to serve traffic?
app.get('/health/ready', (req, res) => {
  if (dbConnected && redisConnected) {
    res.status(200).send('Ready');
  } else {
    res.status(503).send('Not Ready');
  }
});

function getMemoryStatus() {
  const used = process.memoryUsage();
  return {
    rss: `${Math.round(used.rss / 1024 / 1024)}MB`,
    heapUsed: `${Math.round(used.heapUsed / 1024 / 1024)}MB`,
    heapTotal: `${Math.round(used.heapTotal / 1024 / 1024)}MB`,
  };
}

app.listen(8080);
