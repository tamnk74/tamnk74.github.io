Internal Load Balancer Traffic Flow

Overview​

Internal Load Balancing (ILB) is used for distributing traffic within a private network, typically for service-to-service communication, microservices architectures, and backend systems that don't need to be exposed to the internet. This guide provides a detailed walkthrough of traffic flow through internal load balancers in cloud environments.

Key Characteristics of Internal Load Balancing​

Why Use Internal Load Balancing?​

  • Private Communication: Traffic never leaves your VPC/private network
  • Security: No public IP addresses, reducing attack surface
  • Performance: Lower latency for internal communications
  • Cost: Often cheaper than external load balancers
  • Microservices: Ideal for service mesh architectures
  • Database Clusters: Load balance connections to database replicas

Internal vs External Load Balancing​

AspectInternal Load BalancerExternal Load Balancer
IP AddressPrivate (RFC 1918)Public (Internet-routable)
AccessWithin VPC onlyInternet-facing
Use CaseService-to-serviceClient-to-service
SecurityNetwork isolationRequires WAF, DDoS protection
LatencyLower (no internet hop)Higher (internet routing)
CostLowerHigher
SSL/TLSOptional (often terminated at service)Required for public access

Security Layers​

Multi-Tier Security:

Layer 1 - Edge (Cloudflare):
  - DDoS Protection: 100+ Tbps mitigation
  - WAF: OWASP Top 10 protection
  - Bot Management: Challenge suspicious bots
  - Rate Limiting: 100 req/min per IP
  - Geographic Filtering: Block specific countries

Layer 2 - External LB (Cloud Armor):
  - Adaptive Protection: ML-based threat detection
  - IP Allowlist: Cloudflare IP ranges
  - Rate Limiting: 1000 req/min per IP
  - SQLi/XSS Protection: Signature-based rules

Layer 3 - VPC Firewall:
  - Ingress Rules:
    * Allow 443 from External LB only
    * Allow 8080 from Frontend subnet to Internal LB subnet
    * Allow 8080 from Internal LB to Backend subnet
    * Allow 5432 from Backend subnet to Database subnet
  - Egress Rules:
    * Deny all by default
    * Allow specific internal routes

Layer 4 - Service Authentication:
  - JWT Tokens: Frontend validates user tokens
  - Service-to-Service: mTLS certificates (optional)
  - API Keys: Internal service authentication

Layer 5 - Database:
  - Connection pooling with limits
  - SSL/TLS encrypted connections
  - Read-only replica for SELECT queries
  - Row-level security policies

Traffic Flow Stages​

Stage 1: Client Request Initiation​

Scenario: Frontend service needs to call backend API

Frontend Service (10.0.1.10)
    ↓
Request: GET /api/users
Destination: backend-api.internal (10.0.2.100)
Port: 8080

What Happens:

  1. DNS Resolution (if using internal DNS):

    Query: backend-api.internal
    Response: 10.0.2.100 (Internal LB IP)
    TTL: 60 seconds

  2. Client Connection:

    Source: 10.0.1.10:54321 (ephemeral port)
    Destination: 10.0.2.100:8080
    Protocol: TCP

  3. Network Routing:

    • Packet routed through VPC subnet routes
    • Firewall rules evaluated
    • Traffic stays within private network

Stage 2: Load Balancer Processing​

Load Balancer Receives Request

Load Balancing Algorithm Selection:

  1. Round Robin (Default in most systems):

    Request 1 → Backend 1 (10.0.3.10)
    Request 2 → Backend 2 (10.0.3.11)
    Request 3 → Backend 3 (10.0.3.12)
    Request 4 → Backend 1 (10.0.3.10)

  2. Least Connections:

    Backend 1: 10 active connections
    Backend 2: 5 active connections  ← Selected
    Backend 3: 8 active connections

  3. IP Hash (Session Affinity):

    Hash(Source IP: 10.0.1.10) % 3 = 1
    → Always routes to Backend 2 (10.0.3.11)

  4. Weighted Distribution:

    Backend 1: Weight 3 (30%)
    Backend 2: Weight 5 (50%)
    Backend 3: Weight 2 (20%)

  Timeout: 5 seconds

  Unhealthy Threshold: 3 consecutive failures

Service Type: ClusterIP (Default)​

Architecture:

Service Configuration:

apiVersion: v1
kind: Service
metadata:
  name: backend-api
  namespace: backend
spec:
  type: ClusterIP
  selector:
    app: backend
    tier: api
  ports:
    - name: http
      port: 8080
      targetPort: 8080
      protocol: TCP
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800

Traffic Flow:

1. Frontend pod (10.244.1.10) calls backend-api.backend.svc.cluster.local
2. CoreDNS resolves to ClusterIP: 10.96.100.50
3. Packet sent to 10.96.100.50:8080
4. kube-proxy iptables rule intercepts
5. DNAT to backend pod: 10.244.2.11:8080
6. Backend pod processes request
7. Response returns directly to frontend pod

iptables Rules (Generated by kube-proxy):

# Service chain
-A KUBE-SERVICES -d 10.96.100.50/32 -p tcp -m tcp --dport 8080 -j KUBE-SVC-BACKEND-API

# Load balancing to endpoints
-A KUBE-SVC-BACKEND-API -m statistic --mode random --probability 0.33 -j KUBE-SEP-BACKEND-1
-A KUBE-SVC-BACKEND-API -m statistic --mode random --probability 0.50 -j KUBE-SEP-BACKEND-2
-A KUBE-SVC-BACKEND-API -j KUBE-SEP-BACKEND-3

# DNAT to specific pods

    service.beta.kubernetes.io/aws-load-balancer-scheme: 'internal'

    service.beta.kubernetes.io/azure-load-balancer-internal: 'true'

  type: LoadBalancer

  selector:
    app: backend
    tier: api
  ports:
    - name: http
      port: 8080
      targetPort: 8080
      protocol: TCP

Advanced Load Balancing Features​

Session Affinity (Sticky Sessions)​

IP-based Affinity:

Client IP: 10.0.1.10
Hash(10.0.1.10) = 42
Backend Selection: 42 % 3 = 0 → Backend 1

All subsequent requests from 10.0.1.10 → Backend 1

Cookie-based Affinity (Layer 7 only):

Request 1:
GET /api/users HTTP/1.1
Host: backend-api.internal

Response 1:
HTTP/1.1 200 OK
Set-Cookie: SERVERID=backend-2; Path=/; HttpOnly

Request 2:
GET /api/orders HTTP/1.1
Host: backend-api.internal
Cookie: SERVERID=backend-2

→ Routed to same backend (Backend 2)

Traffic Flow Scenarios​

Scenario 1: Normal Request Flow​

Setup:

  • Frontend: 10.0.1.10
  • ILB: 10.0.2.100
  • Backend selected: 10.0.3.11

Complete Flow:

T+0ms:    Client initiates connection
          SYN → 10.0.2.100:8080

T+1ms:    ILB receives SYN
          - Checks backend health
          - Selects backend (10.0.3.11)
          - Creates connection tracking entry
          - Forwards SYN → 10.0.3.11:8080

T+2ms:    Backend receives SYN
          - Accepts connection
          - Sends SYN-ACK

T+3ms:    ILB receives SYN-ACK
          - Updates connection tracking
          - Forwards SYN-ACK → Client

T+4ms:    Client receives SYN-ACK
          - Sends ACK
          - Connection ESTABLISHED

T+5ms:    Client sends HTTP request
          GET /api/users HTTP/1.1

T+6ms:    ILB forwards request to backend

T+7ms:    Backend processes request
          - Database query (40ms)

T+47ms:   Backend sends response

T+48ms:   ILB forwards response to client

T+49ms:   Client receives complete response

Total Round-trip Time: 49ms

Troubleshooting​

Common Issues and Solutions​

Issue 1: Connection Timeouts​

Symptoms:

Error: Connection timeout to 10.0.2.100:8080

Diagnosis:

# Check if ILB is reachable
ping 10.0.2.100

# Check if port is open
nc -zv 10.0.2.100 8080

# Check firewall rules
gcloud compute firewall-rules list
aws ec2 describe-security-groups
az network nsg list

# Check backend health
gcloud compute backend-services get-health backend-api-ilb --region=us-central1

Common Causes:

  • Firewall blocking traffic
  • Backend all unhealthy
  • Network routing issue
  • ILB not configured properly

Issue 2: Intermittent 502/503 Errors​

Symptoms:

HTTP/1.1 502 Bad Gateway

Diagnosis:

# Check backend health status
kubectl get endpoints backend-api

# Check pod logs
kubectl logs -l app=backend --tail=100

# Check for recent changes
kubectl rollout history deployment/backend

# Monitor in real-time
watch -n 1 'kubectl get pods -l app=backend'

Common Causes:

  • Backend pods crashing
  • Health check path misconfigured
  • Resource limits too low
  • Backend deployment rolling out

Issue 3: Uneven Traffic Distribution​

Symptoms:

Backend 1: 800 req/s (80%)
Backend 2: 150 req/s (15%)
Backend 3: 50 req/s (5%)

Diagnosis:

# Check connection distribution
# GCP
gcloud compute backend-services describe backend-api-ilb \
  --region=us-central1 \
  --format="table(backends[].group, backends[].balancingMode)"

# Check if session affinity is enabled
kubectl get service backend-api -o yaml | grep sessionAffinity

Common Causes:

  • Session affinity enabled
  • Long-lived connections
  • Connection draining in progress
  • Backend capacity differences

Issue 4: High Latency​

Symptoms:

Average latency: 500ms (expected: 50ms)

Diagnosis:

# Trace request path
traceroute 10.0.2.100

# Check ILB metrics
# GCP
gcloud monitoring time-series list \
  --filter='metric.type="loadbalancing.googleapis.com/internal/l3/request_latency"'

# Test direct backend connection
curl -w "@curl-format.txt" http://10.0.3.11:8080/api/users

# Where curl-format.txt contains:
#   time_namelookup: %{time_namelookup}\n
#   time_connect: %{time_connect}\n
#   time_appconnect: %{time_appconnect}\n
#   time_total: %{time_total}\n

Common Causes:

  • Backend processing slow
  • Network congestion
  • Too many hops
  • ILB overloaded

Best Practices​

1. Health Check Configuration​

Recommendations:

Health Checks:
  # Use dedicated health endpoint
  Path: /health (not /)

  # Appropriate intervals
  Check Interval: 10 seconds
  Timeout: 5 seconds

  # Balanced thresholds
  Healthy Threshold: 2 consecutive successes
  Unhealthy Threshold: 3 consecutive failures

  # Include dependencies
  Health Endpoint Response:
    - Service status: OK
    - Database connection: OK
    - External API: OK
    - Disk space: OK

2. Security Best Practices​

Security:
  # Network isolation
  - Use private subnets
  - No public IPs on backends
  - Firewall rules: principle of least privilege

  # Access control
  - VPC peering for cross-VPC access
  - PrivateLink/Private Service Connect
  - Service mesh for mTLS

  # Monitoring
  - Enable flow logs
  - Monitor unauthorized access attempts
  - Alert on unusual traffic patterns

3. High Availability​

High Availability:
  # Multi-zone deployment
  - Deploy backends in multiple availability zones
  - Enable cross-zone load balancing

  # Redundancy
  - Minimum 2 backends per zone
  - Auto-scaling policies

  # Graceful handling
  - Connection draining
  - Slow start for new backends
  - Circuit breakers

4. Performance Optimization​

Performance:
  # Connection reuse
  - Enable HTTP keep-alive
  - Connection pooling on clients

  # Reduce latency
  - Deploy close to clients
  - Optimize backend response time
  - Use appropriate backend instance sizes

  # Load balancing algorithm
  - Least connections for varying request durations
  - Round robin for uniform requests
  - IP hash for session affinity needs

5. Capacity Planning​

Capacity Planning:
  # Sizing
  - Backend count: (Peak RPS / Backend Capacity) * 1.5
  - Instance size: Based on CPU/memory requirements

  # Auto-scaling
  - Scale-out threshold: 70% CPU
  - Scale-in threshold: 30% CPU
  - Cooldown period: 300 seconds

  # Load testing
  - Regular load tests
  - Chaos engineering
  - Failure scenario testing

Comparison with Service Mesh​

Internal LB vs Service Mesh​

FeatureInternal Load BalancerService Mesh (Istio/Linkerd)
DeploymentCentralized LBSidecar per pod
OverheadLowHigher (sidecar resources)
FeaturesBasic L4/L7 LBAdvanced: mTLS, retries, circuit breaking
ObservabilityBasic metricsDetailed tracing, metrics
ConfigurationSimpleComplex
Use CaseSimple internal routingMicroservices, zero-trust

When to use Internal LB:

  • Simple service-to-service communication
  • Lower complexity requirements
  • Resource-constrained environments
  • Traditional VM-based deployments

When to use Service Mesh:

  • Complex microservices architecture
  • Require mTLS between all services
  • Need advanced traffic management
  • Detailed observability requirements

Summary​

Internal load balancing is essential for:

✅ Private Communication: Keep traffic within your network
✅ Service Discovery: Route to dynamic backend pools
✅ High Availability: Distribute load across multiple backends
✅ Health Management: Automatic unhealthy backend removal
✅ Scalability: Support auto-scaling backend pools
✅ Performance: Lower latency than external routing

Key Takeaways​

  1. Traffic stays private - Never exposed to internet
  2. Health checks critical - Ensure only healthy backends receive traffic
  3. Session affinity - Use when necessary but understand tradeoffs
  4. Monitor actively - Track backend health and connection metrics
  5. Plan for failure - Design for backend failures and recovery
  6. Right-size backends - Match capacity to load requirements
