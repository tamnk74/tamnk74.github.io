PostgreSQL Architecture

PostgreSQL is a powerful, open-source object-relational database system with a robust architecture designed for reliability, data integrity, and extensibility.

Overview​

PostgreSQL uses a client-server model consisting of:

  • Server Process: Manages database files, accepts connections, and performs database actions
  • Client Applications: Connect to the server to perform database operations

Core Architecture Components​

1. Process Architecture​

Postmaster (Main Process)​

  • The main PostgreSQL daemon process
  • Listens for client connections
  • Spawns backend processes for each connection
  • Manages background worker processes

Backend Processes​

  • One process per client connection
  • Executes SQL queries
  • Manages transactions
  • Handles authentication and authorization

Background Processes​

Writer Process

  • Periodically writes dirty buffers from shared memory to disk
  • Helps prevent checkpoint spikes

WAL Writer

  • Writes Write-Ahead Logging (WAL) records to disk
  • Ensures durability and crash recovery

Checkpointer

  • Performs periodic checkpoints
  • Writes all dirty pages to disk
  • Creates recovery points

Autovacuum Launcher/Workers

  • Automatically performs VACUUM operations
  • Prevents transaction ID wraparound
  • Reclaims storage space
  • Updates statistics

Stats Collector

  • Collects usage statistics
  • Tracks table access patterns
  • Provides data for query optimization

Logical Replication Workers

  • Handle logical replication tasks
  • Apply changes from publishers

2. Memory Architecture​

Shared Memory​

Shared Buffers

-- Configuration example
shared_buffers = 256MB  -- Typically 25% of RAM for dedicated servers
  • Caches data pages from disk
  • Reduces I/O operations
  • Default: 128MB (often too small for production)

WAL Buffers

wal_buffers = 16MB
  • Temporary storage for WAL records
  • Flushed to disk by WAL writer

Lock Space

  • Manages locks for concurrent access
  • Tracks lock information for all transactions

Shared Memory for Background Processes

  • Communication area for background workers
  • Maintains system catalogs cache

Process-Local Memory​

work_mem

work_mem = 4MB  -- Per operation memory
  • Used for sorting and hash operations
  • Allocated per operation (not per connection)
  • Multiple operations can use multiple allocations

maintenance_work_mem

maintenance_work_mem = 64MB
  • Used for VACUUM, CREATE INDEX, ALTER TABLE
  • Can be set higher than work_mem

temp_buffers

temp_buffers = 8MB
  • Caches temporary tables

3. Storage Architecture​

Database Cluster Structure​

$PGDATA/
├── base/                 # Database files
│   └── [database_oid]/   # One directory per database
│       └── [relation_oid] # Data files for tables/indexes
├── global/               # Cluster-wide tables
├── pg_wal/              # Write-Ahead Log files
├── pg_xact/             # Transaction commit status
├── pg_multixact/        # Multi-transaction status
├── pg_stat_tmp/         # Statistics files
└── postgresql.conf      # Configuration

Data File Organization​

Heap Files

  • Tables stored in 8KB pages (default)
  • Each page contains tuple (row) data
  • Files automatically split into 1GB segments

Page Structure

┌─────────────────────────────────┐
│      Page Header (24 bytes)      │
├─────────────────────────────────┤
│    Line Pointers (4 bytes each)  │
├─────────────────────────────────┤
│         Free Space               │
├─────────────────────────────────┤
│         Tuple Data               │
├─────────────────────────────────┤
│      Special Space (indexes)     │
└─────────────────────────────────┘

TOAST (The Oversized-Attribute Storage Technique)

  • Stores large attribute values separately
  • Automatically compresses and chunks large data
  • Triggered when tuple size exceeds page size
-- Example: Large text stored in TOAST
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255),
    content TEXT  -- Will use TOAST if > ~2KB
);

4. Transaction Management​

MVCC (Multi-Version Concurrency Control)​

Core Concepts

  • Each transaction sees a snapshot of the database
  • Writers don't block readers
  • Readers don't block writers
  • Dead tuples cleaned by VACUUM

Transaction IDs (XIDs)

-- View transaction IDs
SELECT txid_current();
SELECT txid_current_snapshot();

Tuple Visibility

  • Each tuple has xmin (creating XID) and xmax (deleting XID)
  • Visibility determined by transaction snapshot
  • No undo logs needed (unlike Oracle/MySQL)
-- View tuple versions
SELECT ctid, xmin, xmax, * FROM my_table;

Write-Ahead Logging (WAL)​

Purpose

  • Ensures durability (D in ACID)
  • Enables crash recovery
  • Foundation for replication

Configuration

-- WAL settings
wal_level = replica              -- minimal, replica, or logical
fsync = on                       -- Force writes to disk
synchronous_commit = on          -- Wait for WAL write
wal_compression = on             -- Compress WAL records
max_wal_size = 1GB              -- Checkpoint trigger
min_wal_size = 80MB             -- Recycle WAL files

WAL Process

  1. Transaction modifies data in shared buffers
  2. WAL record written to WAL buffers
  3. WAL writer flushes to disk (fsync)
  4. Transaction commits
  5. Later: checkpointer writes data pages to disk

5. Query Processing​

Query Execution Pipeline​

SQL Query
    ↓
Parser (syntax tree)
    ↓
Analyzer (parse tree)
    ↓
Rewriter (rules)
    ↓
Planner/Optimizer (execution plan)
    ↓
Executor (results)

Parser

  • Validates SQL syntax
  • Builds abstract syntax tree

Analyzer

  • Semantic analysis
  • Resolves table/column names
  • Type checking

Rewriter

  • Applies rules and views
  • Transforms queries

Planner/Optimizer

  • Generates possible execution plans
  • Estimates costs using statistics
  • Selects optimal plan
-- View query plan
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 123;

Executor

  • Executes the chosen plan
  • Fetches data from storage
  • Returns results to client

6. Indexes​

Index Types​

B-tree (Default)

CREATE INDEX idx_email ON users(email);
  • Good for equality and range queries
  • Supports sorting

Hash

CREATE INDEX idx_hash ON users USING HASH(email);
  • Only equality comparisons
  • Smaller than B-tree

GiST (Generalized Search Tree)

CREATE INDEX idx_location ON locations USING GIST(coordinates);
  • Geometric data types
  • Full-text search
  • Custom data types

GIN (Generalized Inverted Index)

CREATE INDEX idx_tags ON articles USING GIN(tags);
  • Array and JSONB columns
  • Full-text search
  • Fast for multiple value queries

BRIN (Block Range Index)

CREATE INDEX idx_created ON events USING BRIN(created_at);
  • Very large tables
  • Physically sorted data
  • Minimal storage

SP-GiST (Space-Partitioned GiST)

CREATE INDEX idx_phone ON contacts USING SPGIST(phone_number);
  • Non-balanced partitioned data
  • Phone numbers, IP addresses

7. Vacuum and Maintenance​

VACUUM Process​

Purpose

  • Reclaim storage from dead tuples
  • Update statistics
  • Prevent transaction ID wraparound
  • Freeze old tuples

Types

-- Standard VACUUM
VACUUM my_table;

-- VACUUM with statistics update
VACUUM ANALYZE my_table;

-- Full VACUUM (locks table, rewrites)
VACUUM FULL my_table;

Autovacuum Configuration

-- Enable autovacuum
autovacuum = on
autovacuum_max_workers = 3
autovacuum_naptime = 1min

-- Thresholds
autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.2
autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.1

Monitoring

-- Check last vacuum/analyze
SELECT schemaname, relname, last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze
FROM pg_stat_user_tables;

-- Dead tuples
SELECT schemaname, relname, n_dead_tup, n_live_tup
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

8. Replication​

Streaming Replication​

Primary Server

-- Configuration
wal_level = replica
max_wal_senders = 10
wal_keep_size = 1GB

Standby Server

-- Configuration
hot_standby = on
max_standby_streaming_delay = 30s

Types

  • Synchronous: Wait for standby confirmation
  • Asynchronous: Don't wait for standby
-- Synchronous replication
synchronous_commit = on
synchronous_standby_names = 'standby1,standby2'

Logical Replication​

Features

  • Selective replication (specific tables)
  • Different PostgreSQL versions
  • Bi-directional replication possible
-- Publisher
CREATE PUBLICATION my_pub FOR TABLE users, orders;

-- Subscriber
CREATE SUBSCRIPTION my_sub
CONNECTION 'host=primary dbname=mydb'
PUBLICATION my_pub;

Performance Tuning​

Key Configuration Parameters​

-- Connection settings
max_connections = 100
superuser_reserved_connections = 3

-- Memory settings (for 16GB RAM server)
shared_buffers = 4GB
effective_cache_size = 12GB
work_mem = 64MB
maintenance_work_mem = 512MB

-- Query planner
random_page_cost = 1.1  -- For SSD (default 4.0 for HDD)
effective_io_concurrency = 200  -- For SSD

-- WAL settings
wal_buffers = 16MB
checkpoint_completion_target = 0.9
max_wal_size = 2GB

Monitoring Queries​

-- Active queries
SELECT pid, now() - query_start as duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY duration DESC;

-- Cache hit ratio (aim for > 99%)
SELECT
  sum(heap_blks_read) as heap_read,
  sum(heap_blks_hit) as heap_hit,
  sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) as ratio
FROM pg_statio_user_tables;

-- Table sizes
SELECT schemaname, tablename,
       pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS size
FROM pg_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 10;

-- Index usage
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;

Best Practices​

1. Connection Pooling​

// Use connection pooler like PgBouncer
// Node.js example with pg-pool
const { Pool } = require('pg');
const pool = new Pool({
  max: 20,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
});

2. Prepared Statements​

-- Prevents SQL injection, improves performance
PREPARE get_user (int) AS
  SELECT * FROM users WHERE id = $1;
EXECUTE get_user(123);

3. Index Strategy​

  • Index foreign keys
  • Index columns used in WHERE, JOIN, ORDER BY
  • Use partial indexes for filtered queries
  • Avoid over-indexing (slows writes)
-- Partial index
CREATE INDEX idx_active_users ON users(email) WHERE active = true;

4. Query Optimization​

  • Use EXPLAIN ANALYZE
  • Avoid SELECT *
  • Use appropriate data types
  • Partition large tables
-- Table partitioning
CREATE TABLE events (
    id SERIAL,
    created_at TIMESTAMP,
    data JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2024 PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

5. Regular Maintenance​

-- Update statistics
ANALYZE;

-- Reindex if needed
REINDEX INDEX CONCURRENTLY idx_name;

-- Monitor bloat
SELECT schemaname, tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as size
FROM pg_tables
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;

Security Considerations​

1. Authentication​

-- pg_hba.conf examples
# TYPE  DATABASE    USER    ADDRESS         METHOD
local   all         all                     peer
host    all         all     127.0.0.1/32   scram-sha-256
host    mydb        myuser  10.0.0.0/8     scram-sha-256

2. Row-Level Security​

ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;

CREATE POLICY account_policy ON accounts
  USING (user_id = current_user_id());

3. SSL Connections​

-- postgresql.conf
ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file = 'server.key'

Common Pitfalls​

  1. Not setting shared_buffers appropriately

    • Too low: excessive disk I/O
    • Too high: OS has less cache memory

  2. Ignoring VACUUM warnings

    • Can lead to transaction ID wraparound
    • Monitor autovacuum effectiveness

  3. Missing indexes on foreign keys

    • Slows down JOINs and cascading operations

  4. Not using connection pooling

    • Each connection consumes resources
    • Use PgBouncer or application-level pooling

  5. Poor query patterns

    • N+1 queries
    • Not using bulk operations
    • Selecting unnecessary columns
