ACID Properties in Databases

Overview​

ACID is a set of properties that guarantee database transactions are processed reliably. ACID stands for Atomicity, Consistency, Isolation, and Durability. These properties ensure data integrity even in the face of errors, power failures, and concurrent access.

The Four ACID Properties​

flowchart LR
    ACID[ACID Properties]
    
    ACID --> A[Atomicity<br/>All or Nothing]
    ACID --> C[Consistency<br/>Valid State]
    ACID --> I[Isolation<br/>Concurrent Execution]
    ACID --> D[Durability<br/>Permanent Storage]
    
    A --> A1[Transaction succeeds completely<br/>or fails completely]
    C --> C1[Database constraints<br/>are always satisfied]
    I --> I1[Concurrent transactions<br/>don't interfere]
    D --> D1[Committed data<br/>survives failures]
    
    style A fill:#ff6b6b
    style C fill:#4ecdc4
    style I fill:#ffd93d
    style D fill:#95e1d3

1. Atomicity​

Definition: A transaction is an atomic unit of work. Either all operations within the transaction succeed, or none of them do. There is no partial completion.

The Problem Without Atomicity​

// ❌ Without atomicity - dangerous!
async function transferMoney(fromAccount: number, toAccount: number, amount: number) {
  // Step 1: Deduct from source
  await db.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromAccount]);
  
  // 💥 System crashes here!
  
  // Step 2: Add to destination (never executes)
  await db.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toAccount]);
}
// Result: Money disappears! 😱

Solution: Use Transactions​

PostgreSQL Example:

BEGIN TRANSACTION;

-- Deduct from source account
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- Add to destination account
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT; -- Or ROLLBACK if error

MySQL Example:

START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT; -- Or ROLLBACK

Node.js with TypeORM:

import { DataSource } from 'typeorm';
import { Account } from './entities/account.entity';

@Injectable()
export class BankService {
  constructor(private dataSource: DataSource) {}

  async transferMoney(
    fromAccountId: number,
    toAccountId: number,
    amount: number,
  ): Promise<void> {
    // Create a query runner for transaction management
    const queryRunner = this.dataSource.createQueryRunner();
    
    // Connect and start transaction
    await queryRunner.connect();
    await queryRunner.startTransaction();

    try {
      // Deduct from source account
      await queryRunner.manager.decrement(
        Account,
        { id: fromAccountId },
        'balance',
        amount,
      );

      // Add to destination account
      await queryRunner.manager.increment(
        Account,
        { id: toAccountId },
        'balance',
        amount,
      );

      // Commit transaction - both operations succeed
      await queryRunner.commitTransaction();
      
    } catch (error) {
      // Rollback transaction - both operations fail
      await queryRunner.rollbackTransaction();
      throw error;
      
    } finally {
      // Release query runner
      await queryRunner.release();
    }
  }
}

Sequelize Example:

import { Transaction } from 'sequelize';
import { Account } from './models/account.model';

async function transferMoney(
  fromAccountId: number,
  toAccountId: number,
  amount: number,
) {
  const t = await sequelize.transaction();

  try {
    const fromAccount = await Account.findByPk(fromAccountId, { transaction: t });
    const toAccount = await Account.findByPk(toAccountId, { transaction: t });

    if (fromAccount.balance < amount) {
      throw new Error('Insufficient funds');
    }

    await fromAccount.decrement('balance', { by: amount, transaction: t });
    await toAccount.increment('balance', { by: amount, transaction: t });

    await t.commit();
  } catch (error) {
    await t.rollback();
    throw error;
  }
}

Real-World Scenario: E-commerce Order​

@Injectable()
export class OrderService {
  constructor(private dataSource: DataSource) {}

  async createOrder(userId: number, items: OrderItem[]): Promise<Order> {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();

    try {
      // 1. Create order
      const order = await queryRunner.manager.save(Order, {
        userId,
        status: 'pending',
        total: items.reduce((sum, item) => sum + item.price * item.quantity, 0),
      });

      // 2. Add order items
      for (const item of items) {
        await queryRunner.manager.save(OrderItem, {
          orderId: order.id,
          productId: item.productId,
          quantity: item.quantity,
          price: item.price,
        });

        // 3. Decrease product inventory
        await queryRunner.manager.decrement(
          Product,
          { id: item.productId },
          'stock',
          item.quantity,
        );
      }

      // 4. Deduct from user wallet
      await queryRunner.manager.decrement(
        Wallet,
        { userId },
        'balance',
        order.total,
      );

      // All operations succeed together
      await queryRunner.commitTransaction();
      return order;
      
    } catch (error) {
      // Any failure rolls back everything
      await queryRunner.rollbackTransaction();
      throw error;
    } finally {
      await queryRunner.release();
    }
  }
}

2. Consistency​

Definition: A transaction brings the database from one valid state to another valid state, maintaining all defined rules, constraints, and triggers.

Database Constraints​

Types of Consistency Rules:

  1. NOT NULL constraints
  2. UNIQUE constraints
  3. CHECK constraints
  4. FOREIGN KEY constraints
  5. Custom business rules

Example: Account Balance Constraint​

PostgreSQL:

CREATE TABLE accounts (
  id SERIAL PRIMARY KEY,
  account_number VARCHAR(20) UNIQUE NOT NULL,
  balance DECIMAL(15, 2) NOT NULL CHECK (balance >= 0),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- This will fail - violates CHECK constraint
BEGIN;
UPDATE accounts SET balance = -100 WHERE id = 1;
-- ERROR: new row violates check constraint "accounts_balance_check"
ROLLBACK;

MySQL:

CREATE TABLE accounts (
  id INT AUTO_INCREMENT PRIMARY KEY,
  account_number VARCHAR(20) UNIQUE NOT NULL,
  balance DECIMAL(15, 2) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT balance_positive CHECK (balance >= 0)
) ENGINE=InnoDB;

TypeORM Entity with Constraints​

import { Entity, Column, PrimaryGeneratedColumn, Check } from 'typeorm';

@Entity('accounts')
@Check('"balance" >= 0')
export class Account {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  accountNumber: string;

  @Column('decimal', { precision: 15, scale: 2 })
  balance: number;

  @Column({ type: 'timestamp', default: () => 'CURRENT_TIMESTAMP' })
  createdAt: Date;
}

Application-Level Consistency​

@Injectable()
export class AccountService {
  async withdraw(accountId: number, amount: number): Promise<void> {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();

    try {
      const account = await queryRunner.manager.findOne(Account, {
        where: { id: accountId },
        lock: { mode: 'pessimistic_write' },
      });

      // Business rule: Cannot withdraw more than balance
      if (account.balance < amount) {
        throw new Error('Insufficient funds');
      }

      // Business rule: Minimum balance of $10
      if (account.balance - amount < 10) {
        throw new Error('Minimum balance requirement not met');
      }

      account.balance -= amount;
      await queryRunner.manager.save(account);

      await queryRunner.commitTransaction();
    } catch (error) {
      await queryRunner.rollbackTransaction();
      throw error;
    } finally {
      await queryRunner.release();
    }
  }
}

Foreign Key Consistency​

-- PostgreSQL
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL,
  total DECIMAL(10, 2) NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- This fails - user_id 999 doesn't exist
INSERT INTO orders (user_id, total) VALUES (999, 100.00);
-- ERROR: insert or update on table "orders" violates foreign key constraint

TypeORM:

@Entity('orders')
export class Order {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  userId: number;

  @ManyToOne(() => User, user => user.orders, { onDelete: 'CASCADE' })
  @JoinColumn({ name: 'user_id' })
  user: User;

  @Column('decimal', { precision: 10, scale: 2 })
  total: number;
}

3. Isolation​

Definition: Concurrent transactions execute independently without interfering with each other. The intermediate state of one transaction is invisible to other transactions.

Isolation Problems​

flowchart TB
    subgraph "Isolation Problems"
        DR[Dirty Read]
        NR[Non-Repeatable Read]
        PR[Phantom Read]
    end
    
    DR --> DR1[Reading uncommitted<br/>changes from another<br/>transaction]
    NR --> NR1[Same query returns<br/>different values<br/>within transaction]
    PR --> PR1[New rows appear<br/>in subsequent reads<br/>within transaction]
    
    style DR fill:#ff6b6b
    style NR fill:#ffd93d
    style PR fill:#95e1d3

Isolation Levels​

Isolation LevelDirty ReadNon-Repeatable ReadPhantom Read
Read Uncommitted✗ Possible✗ Possible✗ Possible
Read Committed✓ Prevented✗ Possible✗ Possible
Repeatable Read✓ Prevented✓ Prevented✗ Possible*
Serializable✓ Prevented✓ Prevented✓ Prevented

*PostgreSQL prevents phantom reads even in Repeatable Read due to MVCC implementation.

Example: Dirty Read Problem​

Transaction 1:

-- PostgreSQL/MySQL
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;

UPDATE accounts SET balance = balance + 1000 WHERE id = 1;
-- Not committed yet!

Transaction 2 (simultaneously):

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;

-- Reads the uncommitted change!
SELECT balance FROM accounts WHERE id = 1; -- Shows +1000

COMMIT;

Transaction 1 (rollback):

ROLLBACK; -- Oops! The change is undone

Result: Transaction 2 read "dirty" data that was never committed!

Solution: Higher Isolation Level​

// TypeORM with isolation level
async function safeRead(accountId: number): Promise<number> {
  const queryRunner = dataSource.createQueryRunner();
  await queryRunner.connect();
  
  // Set isolation level
  await queryRunner.startTransaction('READ COMMITTED');

  try {
    const account = await queryRunner.manager.findOne(Account, {
      where: { id: accountId },
    });

    await queryRunner.commitTransaction();
    return account.balance;
  } catch (error) {
    await queryRunner.rollbackTransaction();
    throw error;
  } finally {
    await queryRunner.release();
  }
}

Setting Isolation Levels​

PostgreSQL:

-- Session level
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Transaction level
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

MySQL:

-- Session level
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Transaction level
START TRANSACTION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

TypeORM:

await queryRunner.startTransaction('SERIALIZABLE');
// Options: 'READ UNCOMMITTED', 'READ COMMITTED', 'REPEATABLE READ', 'SERIALIZABLE'

Real-World: Ticket Booking System​

@Injectable()
export class TicketService {
  async bookTicket(eventId: number, userId: number): Promise<Ticket> {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    
    // Use SERIALIZABLE to prevent double booking
    await queryRunner.startTransaction('SERIALIZABLE');

    try {
      // Lock the event row
      const event = await queryRunner.manager.findOne(Event, {
        where: { id: eventId },
        lock: { mode: 'pessimistic_write' },
      });

      if (event.availableSeats <= 0) {
        throw new Error('No seats available');
      }

      // Create ticket
      const ticket = await queryRunner.manager.save(Ticket, {
        eventId,
        userId,
        seatNumber: event.totalSeats - event.availableSeats + 1,
      });

      // Decrease available seats
      event.availableSeats--;
      await queryRunner.manager.save(event);

      await queryRunner.commitTransaction();
      return ticket;
      
    } catch (error) {
      await queryRunner.rollbackTransaction();
      throw error;
    } finally {
      await queryRunner.release();
    }
  }
}

4. Durability​

Definition: Once a transaction is committed, the changes are permanent and survive system failures, crashes, or power outages.

How Databases Ensure Durability​

  1. Write-Ahead Logging (WAL) - Changes logged before applied
  2. Checkpoints - Periodic flush to disk
  3. Replication - Copy data to multiple servers
  4. Backups - Regular snapshots

PostgreSQL WAL​

-- Check WAL settings
SHOW wal_level;           -- Usually 'replica'
SHOW fsync;               -- Should be 'on'
SHOW synchronous_commit;  -- 'on' for max durability

-- Force WAL write
SELECT pg_switch_wal();

MySQL InnoDB​

-- Check durability settings
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
-- 1 = Full durability (flush on each commit)
-- 2 = Flush every second (faster, less durable)
-- 0 = Write to log buffer only

SHOW VARIABLES LIKE 'sync_binlog';
-- 1 = Synchronous (safest)

Example: Crash Recovery​

// Transaction guaranteed to persist
async function recordPayment(orderId: number, amount: number): Promise<void> {
  const queryRunner = dataSource.createQueryRunner();
  await queryRunner.connect();
  await queryRunner.startTransaction();

  try {
    // Record payment
    await queryRunner.manager.save(Payment, {
      orderId,
      amount,
      status: 'completed',
      paidAt: new Date(),
    });

    // Update order
    await queryRunner.manager.update(
      Order,
      { id: orderId },
      { status: 'paid' },
    );

    // Once committed, these changes survive any crash
    await queryRunner.commitTransaction();
    
    // Even if server crashes here, data is safe!
    
  } catch (error) {
    await queryRunner.rollbackTransaction();
    throw error;
  } finally {
    await queryRunner.release();
  }
}

Durability vs Performance Trade-off​

// Maximum durability (slower)
await queryRunner.query('SET LOCAL synchronous_commit = on');

// Faster, but small risk of data loss on crash
await queryRunner.query('SET LOCAL synchronous_commit = off');

Complete ACID Example: Bank Transfer​

import { Injectable } from '@nestjs/common';
import { DataSource } from 'typeorm';
import { Account } from './entities/account.entity';
import { Transaction as TxnEntity } from './entities/transaction.entity';

@Injectable()
export class BankingService {
  constructor(private dataSource: DataSource) {}

  async transfer(
    fromAccountId: number,
    toAccountId: number,
    amount: number,
    description: string,
  ): Promise<{ success: boolean; transactionId: number }> {
    // Validate input
    if (amount <= 0) {
      throw new Error('Amount must be positive');
    }

    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    
    // ISOLATION: Set appropriate isolation level
    await queryRunner.startTransaction('REPEATABLE READ');

    try {
      // Lock both accounts (pessimistic locking)
      const fromAccount = await queryRunner.manager.findOne(Account, {
        where: { id: fromAccountId },
        lock: { mode: 'pessimistic_write' },
      });

      const toAccount = await queryRunner.manager.findOne(Account, {
        where: { id: toAccountId },
        lock: { mode: 'pessimistic_write' },
      });

      if (!fromAccount || !toAccount) {
        throw new Error('Account not found');
      }

      // CONSISTENCY: Check business rules
      if (fromAccount.balance < amount) {
        throw new Error('Insufficient funds');
      }

      if (fromAccount.balance - amount < fromAccount.minimumBalance) {
        throw new Error('Transfer would violate minimum balance');
      }

      // ATOMICITY: All operations succeed or all fail
      
      // 1. Deduct from source
      fromAccount.balance -= amount;
      await queryRunner.manager.save(fromAccount);

      // 2. Add to destination  
      toAccount.balance += amount;
      await queryRunner.manager.save(toAccount);

      // 3. Record transaction
      const transaction = await queryRunner.manager.save(TxnEntity, {
        fromAccountId,
        toAccountId,
        amount,
        description,
        status: 'completed',
        createdAt: new Date(),
      });

      // 4. Create audit log
      await queryRunner.manager.save('AuditLog', {
        action: 'TRANSFER',
        userId: fromAccount.userId,
        details: `Transferred ${amount} from ${fromAccountId} to ${toAccountId}`,
        timestamp: new Date(),
      });

      // DURABILITY: Commit ensures changes survive crashes
      await queryRunner.commitTransaction();

      return {
        success: true,
        transactionId: transaction.id,
      };
      
    } catch (error) {
      // ATOMICITY: Rollback all changes on error
      await queryRunner.rollbackTransaction();
      
      throw new Error(`Transfer failed: ${error.message}`);
      
    } finally {
      await queryRunner.release();
    }
  }
}

Database-Specific Implementations​

PostgreSQL​

Strengths:

  • Full ACID compliance
  • MVCC (Multi-Version Concurrency Control)
  • No dirty reads even at READ UNCOMMITTED
  • Serializable Snapshot Isolation (SSI)
-- PostgreSQL transaction example
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Your operations here
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- Check for serialization failures
COMMIT; -- May fail with serialization error

MySQL (InnoDB)​

Strengths:

  • ACID compliant with InnoDB engine
  • Row-level locking
  • MVCC support

Important: Only InnoDB engine is ACID-compliant!

-- MySQL transaction example
START TRANSACTION;

-- Lock rows
SELECT * FROM accounts WHERE id IN (1, 2) FOR UPDATE;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;

Best Practices​

1. Keep Transactions Short​

// ❌ Bad: Long transaction
async badExample() {
  await queryRunner.startTransaction();
  
  const data = await fetchFromExternalAPI(); // Slow!
  await processData(data); // CPU intensive!
  await queryRunner.manager.save(Result, data);
  
  await queryRunner.commitTransaction();
}

// ✅ Good: Minimal transaction
async goodExample() {
  // Do expensive work outside transaction
  const data = await fetchFromExternalAPI();
  const processed = await processData(data);
  
  // Quick transaction
  await queryRunner.startTransaction();
  await queryRunner.manager.save(Result, processed);
  await queryRunner.commitTransaction();
}

2. Use Appropriate Isolation Levels​

// Read-heavy, better performance
await queryRunner.startTransaction('READ COMMITTED');

// Critical operations, need consistency
await queryRunner.startTransaction('SERIALIZABLE');

3. Handle Deadlocks​

async function retryOnDeadlock<T>(
  operation: () => Promise<T>,
  maxRetries: number = 3,
): Promise<T> {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await operation();
    } catch (error) {
      if (error.code === '40P01' && attempt < maxRetries) {
        // Deadlock detected, retry
        await new Promise(resolve => setTimeout(resolve, attempt * 100));
        continue;
      }
      throw error;
    }
  }
}

4. Use Savepoints for Partial Rollback​

await queryRunner.startTransaction();

try {
  await queryRunner.manager.save(Order, orderData);
  
  // Create savepoint
  await queryRunner.query('SAVEPOINT item_insert');
  
  try {
    await queryRunner.manager.save(OrderItem, items);
  } catch (error) {
    // Rollback to savepoint only
    await queryRunner.query('ROLLBACK TO SAVEPOINT item_insert');
    // Order is still saved, just items failed
  }
  
  await queryRunner.commitTransaction();
} catch (error) {
  await queryRunner.rollbackTransaction();
}

Summary​

PropertyPurposeExample Violation
AtomicityAll-or-nothing executionMoney deducted but not credited
ConsistencyMaintain valid stateNegative account balance
IsolationIndependent executionReading uncommitted changes
DurabilityPermanent storageLost data after crash

Key Takeaways:

  • 🔒 Always use transactions for multi-step operations
  • ✅ Enforce constraints at database level
  • 🎯 Choose appropriate isolation level
  • 💾 Trust the database's durability mechanisms
  • ⚡ Keep transactions short and focused
  • 🔄 Handle deadlocks gracefully

Remember: ACID properties work together to ensure data integrity. Compromising one property can jeopardize the entire system's reliability!
