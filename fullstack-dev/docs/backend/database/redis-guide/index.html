Redis as a Database

Overview​

Redis is an open-source, in-memory data structure store that can be used as a database, cache, message broker, and streaming engine. Unlike traditional relational databases, Redis stores data in memory for extremely fast access with optional persistence to disk.

Key Characteristics:

  • 🚀 In-memory storage (sub-millisecond latency)
  • 📊 Rich data structures (String, Hash, List, Set, Sorted Set, etc.)
  • 💾 Optional persistence (RDB snapshots, AOF logs)
  • 🔄 Replication and high availability
  • 📈 Horizontal scaling with Redis Cluster
  • 🔒 Atomic operations and transactions

When to Use Redis as a Database​

✅ Good Use Cases​

  1. Session Store - User sessions with TTL
  2. Real-time Analytics - Counters, metrics, dashboards
  3. Leaderboards - Gaming scores, rankings
  4. Cache Layer - Frequently accessed data
  5. Rate Limiting - API throttling, request control
  6. Pub/Sub Systems - Real-time messaging
  7. Temporary Data - Shopping carts, job queues
  8. Time-Series Data - Recent events, logs (with Redis TimeSeries)

❌ When NOT to Use Redis​

  1. Large datasets - Data larger than available RAM
  2. Complex queries - Multi-table joins, complex aggregations
  3. Strong ACID requirements - Banking transactions, financial records
  4. Long-term archival - Historical data storage
  5. Relational data - Complex relationships requiring SQL

Data Structures​

1. String​

Basic key-value pairs. Maximum size: 512MB.

// Set/Get
await redis.set('user:1000:name', 'John Doe');
await redis.get('user:1000:name'); // "John Doe"

// With expiration (TTL)
await redis.setex('session:abc123', 3600, 'user_data'); // Expires in 1 hour

// Atomic increment
await redis.incr('page:views'); // 1
await redis.incr('page:views'); // 2

// Store JSON
await redis.set('user:1000', JSON.stringify({ name: 'John', age: 30 }));

2. Hash​

Maps between string fields and values (like objects).

// Set multiple fields
await redis.hset('user:1000', 
  'name', 'John',
  'email', 'john@example.com',
  'age', '30'
);

// Get all fields
await redis.hgetall('user:1000');
// { name: 'John', email: 'john@example.com', age: '30' }

// Get specific field
await redis.hget('user:1000', 'email'); // "john@example.com"

// Increment numeric field
await redis.hincrby('user:1000', 'login_count', 1);

Use Cases:

  • User profiles
  • Shopping carts
  • Object storage

3. List​

Ordered collection of strings (linked list).

// Push to left (prepend)
await redis.lpush('queue:emails', 'email1', 'email2');

// Push to right (append)
await redis.rpush('queue:emails', 'email3');

// Pop from right
await redis.rpop('queue:emails'); // "email3"

// Get range
await redis.lrange('queue:emails', 0, -1); // All items

// Blocking pop (wait for item)
await redis.brpop('queue:emails', 5); // Wait up to 5 seconds

Use Cases:

  • Message queues
  • Activity feeds
  • Recent items list

4. Set​

Unordered collection of unique strings.

// Add members
await redis.sadd('tags:post:1', 'redis', 'database', 'cache');

// Check membership
await redis.sismember('tags:post:1', 'redis'); // 1 (true)

// Get all members
await redis.smembers('tags:post:1'); // ['redis', 'database', 'cache']

// Set operations
await redis.sadd('tags:post:2', 'redis', 'nodejs');
await redis.sinter('tags:post:1', 'tags:post:2'); // ['redis'] (intersection)
await redis.sunion('tags:post:1', 'tags:post:2'); // All unique tags

Use Cases:

  • Tags
  • Unique visitors
  • Relationships

5. Sorted Set (ZSet)​

Set ordered by score. Members unique, scores can repeat.

// Add with scores
await redis.zadd('leaderboard', 
  100, 'player1',
  200, 'player2',
  150, 'player3'
);

// Get top players (highest scores)
await redis.zrevrange('leaderboard', 0, 9, 'WITHSCORES');
// ['player2', '200', 'player3', '150', 'player1', '100']

// Get rank
await redis.zrevrank('leaderboard', 'player2'); // 0 (1st place)

// Increment score
await redis.zincrby('leaderboard', 50, 'player1'); // New score: 150

// Get players in score range
await redis.zrangebyscore('leaderboard', 100, 200);

Use Cases:

  • Leaderboards
  • Priority queues
  • Time-series data (using timestamp as score)

6. Bitmap​

Bit-level operations on strings.

// Mark user as active (bit = 1)
await redis.setbit('users:active:2024-01-25', 1000, 1);

// Check if user is active
await redis.getbit('users:active:2024-01-25', 1000); // 1

// Count active users
await redis.bitcount('users:active:2024-01-25'); // Total 1s

// Combine multiple days (OR operation)
await redis.bitop('OR', 'users:active:week', 
  'users:active:2024-01-25',
  'users:active:2024-01-26',
  'users:active:2024-01-27'
);

Use Cases:

  • User analytics (DAU/MAU)
  • Feature flags
  • User permissions

7. HyperLogLog​

Probabilistic data structure for cardinality estimation.

// Add elements
await redis.pfadd('unique:visitors:2024-01-25', 'user1', 'user2', 'user1');

// Count unique elements (~0.81% error)
await redis.pfcount('unique:visitors:2024-01-25'); // 2

// Merge multiple HyperLogLogs
await redis.pfmerge('unique:visitors:week',
  'unique:visitors:2024-01-25',
  'unique:visitors:2024-01-26'
);

Use Cases:

  • Unique visitor counting
  • Cardinality estimation with minimal memory

Persistence Strategies​

RDB (Redis Database Snapshot)​

Point-in-time snapshots of your dataset.

# redis.conf
save 900 1      # After 900 sec (15 min) if at least 1 key changed
save 300 10     # After 300 sec (5 min) if at least 10 keys changed
save 60 10000   # After 60 sec if at least 10000 keys changed

Pros:

  • Compact single-file backups
  • Faster restarts
  • Good for disaster recovery

Cons:

  • Data loss possible (last snapshot to crash)
  • Fork can be slow for large datasets

AOF (Append Only File)​

Log of every write operation.

# redis.conf
appendonly yes
appendfsync everysec  # fsync every second (default)
# appendfsync always   # fsync after every write (slow, safest)
# appendfsync no       # Let OS decide when to sync

Pros:

  • More durable (minimal data loss)
  • AOF rewrite compacts the file

Cons:

  • Larger file size than RDB
  • Slower than RDB for recovery

Hybrid Persistence (Recommended)​

Use both RDB and AOF for best durability and performance.

Replication​

Setup Master-Replica​

# On replica server
redis-cli
127.0.0.1:6379> replicaof 192.168.1.100 6379

# Or in redis.conf
replicaof 192.168.1.100 6379

Read from Replicas​

import { Cluster } from 'ioredis';

const cluster = new Cluster([
  { host: 'master.redis', port: 6379 },
  { host: 'replica1.redis', port: 6379 },
  { host: 'replica2.redis', port: 6379 },
], {
  scaleReads: 'slave', // Read from replicas
  redisOptions: {
    password: 'your-password',
  },
});

// Writes go to master, reads from replicas
await cluster.set('key', 'value'); // Master
await cluster.get('key'); // Replica

High Availability with Redis Sentinel​

Sentinel provides:

  • Monitoring
  • Automatic failover
  • Configuration management
# sentinel.conf
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000

Redis Cluster (Horizontal Scaling)​

Setup​

import { Cluster } from 'ioredis';

const cluster = new Cluster([
  { host: 'node1.redis', port: 6379 },
  { host: 'node2.redis', port: 6379 },
  { host: 'node3.redis', port: 6379 },
]);

// Cluster automatically handles key distribution
await cluster.set('user:1000', 'data'); // Goes to appropriate node

Hash Tags​

Force keys to same slot:

// Both keys in same slot
await cluster.set('{user:1000}:profile', 'data');
await cluster.set('{user:1000}:settings', 'data');

// Enables multi-key operations
await cluster.mget('{user:1000}:profile', '{user:1000}:settings');

Memory Management​

Eviction Policies​

# redis.conf
maxmemory 2gb
maxmemory-policy allkeys-lru

Policies:

  • noeviction - Return errors when memory limit reached
  • allkeys-lru - Remove least recently used keys
  • allkeys-lfu - Remove least frequently used keys
  • volatile-lru - LRU among keys with TTL
  • volatile-ttl - Remove keys with shortest TTL
  • allkeys-random - Remove random keys

Memory Optimization​

// Use hashes for objects (more memory efficient)
// ❌ Bad: Multiple strings
await redis.set('user:1000:name', 'John');
await redis.set('user:1000:email', 'john@example.com');

// ✅ Good: Single hash
await redis.hset('user:1000', 'name', 'John', 'email', 'john@example.com');

// Check memory usage
await redis.memory('usage', 'user:1000');

Transactions​

// Using MULTI/EXEC
const multi = redis.multi();
multi.set('key1', 'value1');
multi.set('key2', 'value2');
multi.incr('counter');
await multi.exec();

// With watch (optimistic locking)
await redis.watch('balance');
const balance = parseInt(await redis.get('balance'));

if (balance >= 100) {
  const multi = redis.multi();
  multi.decrby('balance', 100);
  multi.incrby('spent', 100);
  await multi.exec();
}

Lua Scripting​

Execute atomic operations on server side:

const script = `
  local current = redis.call('GET', KEYS[1])
  if not current then
    redis.call('SET', KEYS[1], ARGV[1])
    return 1
  end
  if tonumber(current) < tonumber(ARGV[1]) then
    redis.call('SET', KEYS[1], ARGV[1])
    return 1
  end
  return 0
`;

// Execute script
const result = await redis.eval(script, 1, 'max_score', 100);

Best Practices​

1. Use Appropriate Data Structures​

// ❌ Bad: String for list of items
await redis.set('cart', JSON.stringify(['item1', 'item2']));

// ✅ Good: Use List or Set
await redis.sadd('cart', 'item1', 'item2');

2. Set Expiration for Temporary Data​

// Session with 1-hour TTL
await redis.setex('session:abc123', 3600, sessionData);

// Update TTL
await redis.expire('session:abc123', 7200);

3. Use Pipelining for Bulk Operations​

// ❌ Bad: Individual commands
for (let i = 0; i < 1000; i++) {
  await redis.set(`key:${i}`, `value:${i}`);
}

// ✅ Good: Pipeline
const pipeline = redis.pipeline();
for (let i = 0; i < 1000; i++) {
  pipeline.set(`key:${i}`, `value:${i}`);
}
await pipeline.exec();

4. Avoid KEYS Command in Production​

// ❌ Bad: Blocks server
const keys = await redis.keys('user:*');

// ✅ Good: Use SCAN
const stream = redis.scanStream({ match: 'user:*', count: 100 });
stream.on('data', (keys) => {
  // Process keys
});

5. Monitor Memory Usage​

const info = await redis.info('memory');
const stats = await redis.info('stats');

// Check specific key memory
const memory = await redis.memory('usage', 'large:key');

Comparison with SQL Databases​

Data Modeling Differences​

SQL (PostgreSQL):

CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  email VARCHAR(100) UNIQUE,
  created_at TIMESTAMP
);

SELECT * FROM users WHERE email = 'john@example.com';

Redis:

// Store as hash
await redis.hset('user:1000', {
  name: 'John',
  email: 'john@example.com',
  created_at: Date.now()
});

// Index for email lookup
await redis.set('email:john@example.com', '1000');

// Query
const userId = await redis.get('email:john@example.com');
const user = await redis.hgetall(`user:${userId}`);

Trade-offs​

AspectRedisPostgreSQL
Speed10-100x fasterSlower but acceptable
Data SizeLimited by RAMLimited by disk
QueriesSimple key-valueComplex SQL
DurabilityOptionalStrong ACID
RelationshipsManual indexesForeign keys, joins
CostHigher (RAM)Lower (disk)

Hybrid Approach (Redis + PostgreSQL)​

Best practice: Use both!

@Injectable()
export class UserService {
  constructor(
    @InjectRepository(User) private userRepo: Repository<User>,
    @InjectRedis() private redis: Redis,
  ) {}

  async getUser(id: string): Promise<User> {
    // Try cache first
    const cached = await this.redis.get(`user:${id}`);
    if (cached) {
      return JSON.parse(cached);
    }

    // Cache miss - query database
    const user = await this.userRepo.findOne({ where: { id } });
    
    // Cache for 1 hour
    await this.redis.setex(`user:${id}`, 3600, JSON.stringify(user));
    
    return user;
  }

  async updateUser(id: string, updates: Partial<User>): Promise<User> {
    // Update database
    await this.userRepo.update(id, updates);
    
    // Invalidate cache
    await this.redis.del(`user:${id}`);
    
    return this.userRepo.findOne({ where: { id } });
  }
}

Summary​

Use Redis as a database when:

  • ✅ Data fits in memory
  • ✅ Need sub-millisecond latency
  • ✅ Simple key-value access patterns
  • ✅ Temporary or ephemeral data
  • ✅ Real-time requirements

Use PostgreSQL/MySQL when:

  • ✅ Complex relationships and queries
  • ✅ Strong consistency requirements
  • ✅ Large datasets (> available RAM)
  • ✅ Long-term data storage
  • ✅ ACID transactions critical

Best approach: Use Redis as a cache layer in front of your primary database for optimal performance!
