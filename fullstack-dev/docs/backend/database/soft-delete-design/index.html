Soft Delete Design

A comprehensive guide to implementing the soft delete pattern — marking records as deleted instead of permanently removing them from the database.

What is Soft Delete?​

Soft delete is a data management pattern where records are marked as deleted rather than physically removed from the database. The data remains in the table but is excluded from normal queries via application-level or database-level filtering.

Hard Delete vs Soft Delete​

AspectHard DeleteSoft Delete
Data removalPermanentLogical (flagged)
RecoveryRequires backup restoreSimple UPDATE query
Audit trailLost unless logged externallyPreserved in-place
Performance impactKeeps tables leanTables grow over time
Foreign keysCan cascade and break relationsRelations preserved
Compliance (GDPR)Satisfies right to erasureMay need additional hard delete

When to Use Soft Delete​

✅ Good Candidates​

  • User accounts — allow reactivation, preserve order history
  • Orders & invoices — legal/financial audit trail requirements
  • Content (posts, comments) — moderation, undo capability
  • Products & catalog items — historical references in past orders
  • Subscriptions — track churn, allow resubscription

❌ Bad Candidates​

  • Session data — ephemeral, no retention value
  • Temporary tokens — OTP, password reset tokens
  • Cache entries — should be evicted, not soft-deleted
  • High-volume logs — use TTL or log rotation instead
  • PII under GDPR "right to erasure" — may require actual deletion

Implementation Strategies​

Strategy 1: Boolean Flag (is_deleted)​

The simplest approach. A boolean column indicates whether a record is active.

ALTER TABLE users ADD COLUMN is_deleted BOOLEAN NOT NULL DEFAULT FALSE;

-- Soft delete
UPDATE users SET is_deleted = TRUE WHERE id = 1;

-- Query active records
SELECT * FROM users WHERE is_deleted = FALSE;

Pros: Simple and fast.
Cons: No information about when or who deleted the record.

Strategy 2: Timestamp Column (deleted_at) ⭐ Recommended​

A nullable timestamp column. NULL means active; a date means soft-deleted.

ALTER TABLE users ADD COLUMN deleted_at TIMESTAMP NULL DEFAULT NULL;

-- Soft delete
UPDATE users SET deleted_at = NOW() WHERE id = 1;

-- Query active records
SELECT * FROM users WHERE deleted_at IS NULL;

-- Restore
UPDATE users SET deleted_at = NULL WHERE id = 1;

Pros: Records when deletion occurred (audit trail), widely supported by ORMs.
Cons: Slightly more complex queries.

Strategy 3: Status Enum​

Use a status column with multiple lifecycle states.

ALTER TABLE users ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'active';

-- Possible values: 'active', 'suspended', 'deleted', 'archived'
UPDATE users SET status = 'deleted' WHERE id = 1;

Pros: Models richer lifecycles beyond just active/deleted.
Cons: More complex filtering; requires careful enum management.

Strategy 4: Archive Table​

Move deleted records to a separate table for cold storage.

-- Move to archive
INSERT INTO users_archive SELECT *, NOW() as archived_at FROM users WHERE id = 1;
DELETE FROM users WHERE id = 1;

-- Restore from archive
INSERT INTO users SELECT * FROM users_archive WHERE id = 1;
DELETE FROM users_archive WHERE id = 1;

Pros: Keeps active tables lean and performant.
Cons: More complex restore logic; schema changes must be synced across tables.

CriteriaBoolean FlagTimestampStatus EnumArchive Table
Simplicity⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐

[!TIP] Recommendation: Use the Timestamp (deleted_at) strategy for most applications. It is the industry standard, supported natively by TypeORM, Prisma, Sequelize, and most ORMs.

Handling Common Challenges​

1. Unique Constraints​

Problem: A user soft-deletes their account with email john@example.com. A new user tries to register with the same email — the unique constraint blocks it.

Solution A: Partial Unique Index (PostgreSQL)

-- Only enforce uniqueness on non-deleted records
CREATE UNIQUE INDEX idx_users_email_active
ON users (email)
WHERE deleted_at IS NULL;

Solution B: Composite Unique Index

-- Include deleted_at to make soft-deleted records unique
CREATE UNIQUE INDEX idx_users_email_unique
ON users (email, COALESCE(deleted_at, '1970-01-01'));

Solution C: Modify Value on Delete

-- Append a unique suffix when soft-deleting
UPDATE users
SET email = CONCAT(email, '_deleted_', id),
    deleted_at = NOW()
WHERE id = 1;

2. Foreign Key Relationships​

Problem: When a parent record is soft-deleted, child records may reference a "deleted" parent.

Solution: Cascade Soft Delete

Implement cascade logic at the application layer or via database triggers:

-- Database trigger for cascade soft delete
CREATE OR REPLACE FUNCTION cascade_soft_delete_orders()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.deleted_at IS NOT NULL AND OLD.deleted_at IS NULL THEN
        UPDATE orders SET deleted_at = NEW.deleted_at WHERE user_id = NEW.id AND deleted_at IS NULL;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_cascade_soft_delete_orders
AFTER UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION cascade_soft_delete_orders();

3. Query Performance​

Problem: Over time, soft-deleted rows accumulate and slow down queries.

Solutions:

  1. Index the deleted_at column:
CREATE INDEX idx_users_deleted_at ON users (deleted_at);
  1. Use a partial index for active records:
CREATE INDEX idx_users_active ON users (email, created_at)
WHERE deleted_at IS NULL;
  1. Archive old soft-deleted records periodically:
-- Move soft-deleted records older than 90 days to archive
INSERT INTO users_archive
SELECT * FROM users WHERE deleted_at < NOW() - INTERVAL '90 days';

DELETE FROM users WHERE deleted_at < NOW() - INTERVAL '90 days';

Database Views for Transparency​

Create views so developers don't need to remember the filter:

-- View for active records only
CREATE VIEW active_users AS
SELECT * FROM users WHERE deleted_at IS NULL;

-- View for deleted records (admin use)
CREATE VIEW deleted_users AS
SELECT * FROM users WHERE deleted_at IS NOT NULL;

Implementation with NestJS + TypeORM​

TypeORM has first-class support for soft deletes via @DeleteDateColumn().

Entity Definition​

import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  CreateDateColumn,
  UpdateDateColumn,
  DeleteDateColumn,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column({ unique: true })
  email: string;

  @Column()
  name: string;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;

  @DeleteDateColumn()  // 👈 This enables soft delete
  deletedAt: Date | null;
}

Repository Usage​

import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { User } from './user.entity';

@Injectable()
export class UserService {
  constructor(
    @InjectRepository(User)
    private readonly userRepo: Repository<User>,
  ) {}

  // ✅ Soft delete — sets deleted_at = NOW()
  async remove(id: string): Promise<void> {
    await this.userRepo.softDelete(id);
  }

  // ✅ Restore — sets deleted_at = NULL
  async restore(id: string): Promise<void> {
    await this.userRepo.restore(id);
  }

  // ✅ Find active records only (default behavior with @DeleteDateColumn)
  async findAll(): Promise<User[]> {
    return this.userRepo.find();
  }

  // ✅ Find including soft-deleted records
  async findAllWithDeleted(): Promise<User[]> {
    return this.userRepo.find({ withDeleted: true });
  }

  // ✅ Find only soft-deleted records
  async findDeleted(): Promise<User[]> {
    return this.userRepo
      .createQueryBuilder('user')
      .withDeleted()
      .where('user.deletedAt IS NOT NULL')
      .getMany();
  }

  // ⚠️ Permanently delete (use with caution)
  async hardDelete(id: string): Promise<void> {
    await this.userRepo.delete(id);
  }
}

Global Soft Delete Filter (Interceptor)​

Ensure all queries automatically exclude soft-deleted records:

import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
} from '@nestjs/common';
import { Observable } from 'rxjs';

@Injectable()
export class SoftDeleteInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    // TypeORM automatically filters @DeleteDateColumn entities
    // This interceptor can add custom response headers or logging
    return next.handle();
  }
}

Base Entity for Reuse​

Create a base entity so every entity gets soft delete automatically:

import {
  PrimaryGeneratedColumn,
  CreateDateColumn,
  UpdateDateColumn,
  DeleteDateColumn,
  BaseEntity,
} from 'typeorm';

export abstract class SoftDeletableEntity extends BaseEntity {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;

  @DeleteDateColumn()
  deletedAt: Date | null;
}

// Usage
@Entity('products')
export class Product extends SoftDeletableEntity {
  @Column()
  name: string;

  @Column('decimal')
  price: number;
}

Implementation with Prisma​

Prisma does not have built-in soft delete but supports it via middleware.

Schema Definition​

model User {
  id        String    @id @default(uuid())
  email     String    @unique
  name      String
  deletedAt DateTime? @map("deleted_at")
  createdAt DateTime  @default(now()) @map("created_at")
  updatedAt DateTime  @updatedAt @map("updated_at")

  @@map("users")
}

Prisma Middleware​

import { PrismaClient } from '@prisma/client';

const prisma = new PrismaClient();

// Middleware to automatically filter soft-deleted records
prisma.$use(async (params, next) => {
  // Override "delete" to be a soft delete
  if (params.action === 'delete') {
    params.action = 'update';
    params.args.data = { deletedAt: new Date() };
  }

  if (params.action === 'deleteMany') {
    params.action = 'updateMany';
    if (params.args.data !== undefined) {
      params.args.data.deletedAt = new Date();
    } else {
      params.args.data = { deletedAt: new Date() };
    }
  }

  // Automatically exclude soft-deleted on find
  if (params.action === 'findUnique' || params.action === 'findFirst') {
    params.action = 'findFirst';
    if (params.args.where) {
      params.args.where.deletedAt = null;
    }
  }

  if (params.action === 'findMany') {
    if (params.args.where) {
      if (params.args.where.deletedAt === undefined) {
        params.args.where.deletedAt = null;
      }
    } else {
      params.args.where = { deletedAt: null };
    }
  }

  return next(params);
});

API Design for Soft Delete​

RESTful Endpoints​

# Soft delete a resource
DELETE /api/v1/users/:id

# Restore a soft-deleted resource
PATCH  /api/v1/users/:id/restore

# Permanently delete (admin only)
DELETE /api/v1/users/:id/purge

# List including deleted (admin only)
GET    /api/v1/users?include_deleted=true

# List only deleted (admin only)
GET    /api/v1/users/trash

Controller Example (NestJS)​

@Controller('users')
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  async remove(@Param('id') id: string): Promise<void> {
    await this.userService.remove(id);
  }

  @Patch(':id/restore')
  async restore(@Param('id') id: string): Promise<User> {
    return this.userService.restore(id);
  }

  @Delete(':id/purge')
  @Roles('admin')
  @HttpCode(HttpStatus.NO_CONTENT)
  async purge(@Param('id') id: string): Promise<void> {
    await this.userService.hardDelete(id);
  }

  @Get('trash')
  @Roles('admin')
  async listDeleted(): Promise<User[]> {
    return this.userService.findDeleted();
  }
}

Architecture Decision Flow​

Best Practices Checklist​

Design​

  • ✅ Use deleted_at timestamp over boolean flag
  • ✅ Create a reusable base entity with soft delete columns
  • ✅ Define clear data retention and purge policies
  • ✅ Document which entities use soft delete vs hard delete

Database​

  • ✅ Add partial unique indexes for active records
  • ✅ Index the deleted_at column
  • ✅ Create database views for active-only queries
  • ✅ Plan for periodic archival of old soft-deleted data

Application​

  • ✅ Use ORM-level soft delete features (TypeORM @DeleteDateColumn)
  • ✅ Never bypass the soft delete filter without explicit intent
  • ✅ Implement cascade soft delete for parent-child relationships
  • ✅ Add restore endpoints alongside delete endpoints

Security & Compliance​

  • ✅ Ensure admin-only access to deleted records and purge endpoints
  • ✅ Implement scheduled hard purge for GDPR compliance
  • ✅ Log who performed the delete and restore actions
  • ✅ Encrypt sensitive data even in soft-deleted records

Summary​

DecisionRecommendation
Strategydeleted_at timestamp (nullable)
ORMTypeORM @DeleteDateColumn()
Unique constraintsPartial unique index on WHERE deleted_at IS NULL
PerformanceIndex deleted_at + periodic archival
APIDELETE for soft delete, PATCH /restore, DELETE /purge
GDPRScheduled hard purge job for expired soft-deleted data
