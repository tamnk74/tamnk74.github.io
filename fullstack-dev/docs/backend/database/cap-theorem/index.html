CAP Theorem

Introduction​

The CAP Theorem, also known as Brewer's Theorem, is a fundamental principle in distributed systems that states it's impossible for a distributed data store to simultaneously provide all three of the following guarantees:

  • Consistency (C): Every read receives the most recent write or an error
  • Availability (A): Every request receives a response (without guarantee of the most recent data)
  • Partition Tolerance (P): The system continues to operate despite network partitions

According to the CAP Theorem, a distributed system can only guarantee two out of three properties at any given time.

Understanding Each Component​

Consistency (C)​

Consistency means that all nodes in the system see the same data at the same time. When a write operation completes, all subsequent read operations will return that value.

Example:

Client A writes "value = 100" to the system
Client B immediately reads "value" and gets "100"
Client C reads "value" from any node and also gets "100"

Availability (A)​

Availability means that every request to the system receives a response, regardless of the state of any individual node. The system remains operational even if some nodes fail.

Example:

Node 1 is down
Client sends a read request
The system still responds (possibly from Node 2 or Node 3)
Client receives a response (though it might not be the latest data)

Partition Tolerance (P)​

Partition tolerance means the system continues to function even when network failures prevent communication between nodes. The system can handle arbitrary network partitions.

Example:

Network split separates Node 1 from Nodes 2 and 3
The system continues to operate on both sides of the partition
Requests are still processed despite the network failure

CAP Trade-offs​

Since you can only choose two of the three properties, distributed systems typically fall into one of these categories:

CP Systems (Consistency + Partition Tolerance)​

These systems prioritize consistency over availability. When a network partition occurs, the system may become unavailable to maintain consistency.

Characteristics:

  • Strong consistency guarantees
  • May reject requests during partitions
  • No stale data
  • Higher latency

Real-World Examples:

MongoDB (with appropriate settings)​

// MongoDB with majority write concern
db.collection.insertOne(
  { name: "Product A", price: 99.99 },
  { writeConcern: { w: "majority", j: true } }
);

// This ensures data is written to majority of nodes before confirming
// If partition occurs, writes may fail to maintain consistency

HBase​

  • Provides strong consistency
  • Uses single master for coordination
  • May become unavailable during network partitions

Redis Cluster (with wait command)​

# Redis WAIT command ensures replication before confirming
SET key "value"
WAIT 2 1000  # Wait for 2 replicas, timeout 1000ms
# If partition occurs, write fails rather than accepting inconsistent data

Use Cases:

  • Financial transactions
  • Banking systems
  • Inventory management
  • Systems where data accuracy is critical

AP Systems (Availability + Partition Tolerance)​

These systems prioritize availability over consistency. During network partitions, all nodes remain available but may return stale data.

Characteristics:

  • Always available
  • Eventual consistency
  • May return stale data temporarily
  • Lower latency

Real-World Examples:

Cassandra​

-- Cassandra with eventual consistency
CREATE KEYSPACE store WITH replication = {
  'class': 'SimpleStrategy',
  'replication_factor': 3
};

-- Write to one node, read from another
-- Data eventually propagates, but reads might be stale

DynamoDB (with eventual consistency reads)​

// AWS DynamoDB eventual consistency
const params = {
  TableName: 'Users',
  Key: { userId: '123' },
  ConsistentRead: false  // Eventual consistency for availability
};

dynamodb.getItem(params);

CouchDB​

  • Multi-master replication
  • Accepts writes on any node
  • Resolves conflicts later

Use Cases:

  • Social media feeds
  • Product catalogs
  • Caching systems
  • Real-time analytics dashboards
  • Content delivery networks

CA Systems (Consistency + Availability)​

These systems provide consistency and availability but cannot tolerate network partitions. In practice, true CA systems don't exist in distributed environments because network partitions are inevitable.

Note: CA systems are typically single-node or same-datacenter systems where partitions are assumed not to occur.

Examples:

  • Traditional RDBMS (single instance): PostgreSQL, MySQL
  • Single-node Redis

Practical Examples​

Example 1: E-commerce Shopping Cart (AP System)​

// AP System - Prioritize availability for shopping cart
class ShoppingCartService {
  async addToCart(userId, productId, quantity) {
    try {
      // Write to local node immediately
      await localNode.write({
        userId,
        productId,
        quantity,
        timestamp: Date.now()
      });
      
      // Asynchronously replicate to other nodes
      this.replicateAsync(userId, productId, quantity);
      
      // Return success immediately (availability)
      return { success: true };
    } catch (error) {
      // Even if some nodes are down, accept the write
      return { success: true, warning: 'partial-write' };
    }
  }
  
  async getCart(userId) {
    // Read from any available node
    // Might get slightly stale data, but always available
    return await localNode.read(userId);
  }
}

Why AP? Users expect shopping carts to always work. Temporary inconsistency (seeing an old cart state for a few seconds) is acceptable, but the service being down is not.

Example 2: Bank Account Balance (CP System)​

// CP System - Prioritize consistency for financial data
class BankAccountService {
  async transfer(fromAccount, toAccount, amount) {
    // Start distributed transaction
    const transaction = await this.beginTransaction();
    
    try {
      // Lock accounts across all nodes
      await this.lockAccounts([fromAccount, toAccount]);
      
      // Read with strong consistency
      const fromBalance = await this.readConsistent(fromAccount);
      
      if (fromBalance < amount) {
        throw new Error('Insufficient funds');
      }
      
      // Write to majority of nodes before confirming
      await this.writeToMajority(fromAccount, fromBalance - amount);
      await this.writeToMajority(toAccount, 
        await this.readConsistent(toAccount) + amount
      );
      
      await transaction.commit();
      return { success: true };
      
    } catch (error) {
      // If network partition occurs, reject the transaction
      await transaction.rollback();
      throw new Error('Transaction failed - system unavailable');
    }
  }
}

Why CP? Financial accuracy is critical. It's better to reject a transaction than to allow inconsistent account balances.

Example 3: Social Media Feed (AP System)​

// AP System - Eventual consistency for social feeds
class SocialFeedService {
  async postUpdate(userId, content) {
    const post = {
      id: generateId(),
      userId,
      content,
      timestamp: Date.now()
    };
    
    // Write to nearest datacenter
    await localDatacenter.write(post);
    
    // Replicate asynchronously to other regions
    this.replicateToRegions(post);
    
    // Return immediately - don't wait for global consistency
    return { success: true, postId: post.id };
  }
  
  async getFeed(userId, region) {
    // Read from regional node
    // Some users might see the post before others
    // That's acceptable for social media
    return await regionalNode.getFeed(userId);
  }
}

Why AP? Users expect social media to always be available. If some users see a post a few seconds later than others, that's acceptable.

Decision Guide​

Choose CP When:​

  • ✅ Data accuracy is critical (financial, medical, inventory)
  • ✅ Inconsistent data could cause serious problems
  • ✅ Users can tolerate brief unavailability
  • ✅ Transactions must be atomic
  • ✅ Regulatory compliance requires consistency

Examples: Banking, stock trading, booking systems, inventory management

Choose AP When:​

  • ✅ Availability is more important than immediate consistency
  • ✅ Eventual consistency is acceptable
  • ✅ System must handle high traffic loads
  • ✅ User experience depends on always being available
  • ✅ Data conflicts can be resolved later

Examples: Social media, product catalogs, user profiles, content delivery, caching

PACELC Theorem Extension​

The PACELC theorem extends CAP by addressing what happens when there's no partition:

  • Partition: If there is a partition (P), choose between availability (A) and consistency (C)
  • Else: Else (E), when the system is running normally, choose between latency (L) and consistency (C)

This provides a more complete picture:

  • PA/EL: Available during partition, low latency normally (Cassandra, DynamoDB)
  • PC/EC: Consistent during partition, consistent normally (HBase, MongoDB)
  • PA/EC: Available during partition, consistent normally (Some configurations)

Common Misconceptions​

Misconception 1: "CAP means you must sacrifice one entirely"​

Reality: You can tune the trade-off. For example, you can have strong consistency for critical operations and eventual consistency for others.

Misconception 2: "NoSQL databases are always AP"​

Reality: Many NoSQL databases allow you to configure consistency levels:

// Cassandra - Configurable consistency
// Strong consistency (CP-like)
session.execute(query, [], { consistency: cassandra.types.consistencies.quorum });

// Eventual consistency (AP-like)
session.execute(query, [], { consistency: cassandra.types.consistencies.one });

Misconception 3: "You make one choice for the entire system"​

Reality: You can make different choices for different parts of your system:

// Hybrid approach
class HybridEcommerceSystem {
  // CP for inventory
  async updateInventory(productId, quantity) {
    return await this.cpDatabase.updateWithConsistency(productId, quantity);
  }
  
  // AP for product views
  async getProductDetails(productId) {
    return await this.apDatabase.getWithAvailability(productId);
  }
}

Best Practices​

1. Understand Your Requirements​

Questions to ask:
- What happens if users see stale data?
- What happens if the system is temporarily unavailable?
- Can we resolve conflicts later?
- What are the regulatory requirements?

2. Design for Partition Tolerance​

Since network partitions are inevitable in distributed systems, always design for partition tolerance. Then choose between consistency and availability based on your use case.

3. Use Different Strategies for Different Data​

const dataStrategies = {
  criticalData: 'CP',    // User balances, orders, payments
  normalData: 'AP',      // Product catalogs, reviews
  cacheData: 'AP'        // Session data, temporary data
};

4. Implement Monitoring​

// Monitor partition events and consistency lag
class CAPMonitor {
  async checkPartitionStatus() {
    const nodes = await this.getAllNodes();
    const partitions = this.detectPartitions(nodes);
    
    if (partitions.length > 0) {
      this.alert('Network partition detected', partitions);
      this.logCurrentBehavior(); // Are we choosing C or A?
    }
  }
  
  async checkConsistencyLag() {
    const lag = await this.measureReplicationLag();
    
    if (lag > threshold) {
      this.alert('High replication lag', { lag });
    }
  }
}

Summary​

The CAP Theorem is a fundamental concept for understanding distributed systems:

  1. Partition tolerance is mandatory in distributed systems
  2. Choose between consistency and availability based on your use case
  3. Different data types can have different strategies within the same system
  4. Tuneable consistency levels provide flexibility in many modern databases
  5. Consider PACELC for a more complete understanding of trade-offs

Understanding CAP helps you make informed decisions about database selection, system architecture, and handling failures in distributed environments.
