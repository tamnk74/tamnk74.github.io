DevSecOps Maturity Assessment Guide

Overview​

This comprehensive guide provides a structured framework for assessing and advancing your organization's DevSecOps maturity. The assessment is organized into four key pillars, each with specific criteria and actionable steps to achieve excellence in security integration throughout the software development lifecycle.

Maturity Model Framework​

The DevSecOps maturity model progresses through five levels:

LevelStageDescription
Level 0InitialAd-hoc security practices, no standardization
Level 1DevelopingBasic security tools adopted, limited automation
Level 2DefinedStandardized processes, automated security gates
Level 3ManagedComprehensive security coverage, proactive monitoring
Level 4OptimizingContinuous improvement, security-first culture

Assessment Template​

Assessment Instructions​

For each criterion below:

  1. Review the success criteria description
  2. Assess your current status (Not Started / In Progress / Completed)
  3. Document evidence of implementation
  4. Note any blockers or challenges
  5. Assign action items with owners and due dates

Pillar 1: Tool Adoption​

Tool adoption ensures that security is automated and integrated into every stage of development.

1.1 Static Application Security Testing (SAST)​

Criterion 1.1.1: SAST on Pull Requests​

Success Criteria: SonarQube Cloud SAST runs automatically on every PR to ensure all production repos have successful analysis.

Maturity Level: Level 2 (Defined)

Assessment Questions:

  • Is SonarQube Cloud configured for all production repositories?
  • Does every PR trigger an automatic SAST scan?
  • Are scan results visible in the PR interface?
  • Are Quality Gates enforced before merge approval?

Evidence Required:

  • SonarQube Cloud project list
  • Sample PR with successful SAST scan
  • CI/CD pipeline configuration showing SAST integration

Guideline Actions to Achieve:

  1. Initial Setup (Week 1-2)

    # Action 1: Enable SonarQube Cloud organization
    - Sign up for SonarQube Cloud (sonarcloud.io)
    - Create organization linked to your GitHub org
    - Grant SonarQube GitHub App permissions

  2. Repository Integration (Week 2-3)

    # Action 2: Add SonarQube to CI/CD pipeline
    # Example GitHub Actions workflow
    name: SonarQube Analysis
    on:
      pull_request:
        types: [opened, synchronize, reopened]

    jobs:
      sonarqube:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v3
            with:
              fetch-depth: 0
          - name: SonarQube Scan
            uses: SonarSource/sonarqube-scan-action@master
            env:
              SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
              SONAR_HOST_URL: https://sonarcloud.io

  3. Configuration (Week 3-4)

    • Create sonar-project.properties in each repository
    • Configure analysis scope (include/exclude patterns)
    • Set up Quality Gate conditions
    • Define code coverage thresholds

  4. Validation

    • Create a test PR and verify SAST scan executes
    • Review scan results in SonarQube dashboard
    • Confirm Quality Gate status appears in PR checks

Common Blockers & Solutions:

  • Blocker: High false positive rate
    • Solution: Tune Quality Gate rules, mark false positives as "Won't Fix"
  • Blocker: Long scan times
    • Solution: Use incremental analysis, optimize project structure
  • Blocker: Token management
    • Solution: Use GitHub organization secrets, rotate tokens quarterly

Criterion 1.1.2: SAST on Default Branch​

Success Criteria: SonarQube Cloud SAST runs on the default branch for every push trigger to ensure continuous analysis of the production codebase.

Maturity Level: Level 2 (Defined)

Assessment Questions:

  • Does every push to main/master trigger SAST?
  • Are main branch quality metrics tracked over time?

  2. Trend Monitoring

    • Configure Slack/Teams integration for alerts

  3. Baseline Establishment

    • Document initial quality metrics
    • Set realistic improvement targets
    • Schedule quarterly metric reviews

Criterion 1.1.3: IDE Integration​

Success Criteria: Sonar IDE plugins are installed and connected in each developer's environment.

Maturity Level: Level 1 (Developing)

Assessment Questions:

  • Are IDE plugins available for all supported IDEs?
  • Is there documentation for installation?

1.2 Dynamic Application Security Testing (DAST)​

Criterion 1.2.1: DAST Pipeline Existence​

Success Criteria: A DAST pipeline (e.g., OWASP ZAP) exists for web services where 100% of internet-facing services run a DAST job.

Maturity Level: Level 3 (Managed)

Assessment Questions:

  • Is DAST tooling selected and configured?
  • Are all internet-facing services identified?
  • Does each service have a DAST job?
  • Are DAST scans running on a defined schedule?

Guideline Actions to Achieve:

  1. Service Inventory (Week 1)

    Create a service catalog:
    | Service Name | URL | Environment | DAST Status |
    |--------------|-----|-------------|-------------|
    | Frontend API | api.example.com | Production | Not Started |
    | Admin Portal | admin.example.com | Production | Not Started |

  2. OWASP ZAP Setup (Week 2-3)

    # GitHub Actions - OWASP ZAP Baseline Scan
    name: DAST Scan
    on:
      schedule:
        - cron: '0 2 * * 1' # Weekly on Monday 2 AM
      workflow_dispatch:

    jobs:
      zap_scan:
        runs-on: ubuntu-latest
        steps:
          - name: ZAP Baseline Scan
            uses: zaproxy/action-baseline@v0.7.0
            with:
              target: 'https://api.example.com'
              rules_file_name: '.zap/rules.tsv'
              cmd_options: '-a'

  3. Configuration Files (Week 3)

    • Create .zap/rules.tsv for scan customization
    • Define authentication mechanisms
    • Configure scan policies per service

  4. Integration (Week 4)

    • Deploy to staging environment first
    • Run full scan during off-peak hours
    • Configure result archival

Implementation Timeline:

  • Week 1: Service inventory + tool selection
  • Week 2: ZAP setup + first service pilot
  • Week 3: Expand to 50% of services
  • Week 4: Full coverage + validation

Criterion 1.2.2: DAST Quality Gates​

Success Criteria: DAST gates are enforced on all internet-facing services to fail the pipeline if ZAP thresholds are breached.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Define Thresholds (Week 1)

    # ZAP alert thresholds
    fail_pipeline:
      - High severity: 0 allowed
      - Medium severity: 5 allowed
      - Low severity: 10 allowed

  2. Implement Gates (Week 2)

    - name: ZAP Scan with Gates
      uses: zaproxy/action-baseline@v0.7.0
      with:
        target: ${{ env.TARGET_URL }}
        fail_action: true
        allow_issue_writing: true

  3. Exception Process (Week 2)

    • Document false positive handling
    • Create waiver request template
    • Define approval workflow

1.3 Dependency Management​

Criterion 1.3.1: Dependabot Enablement​

Success Criteria: Dependabot is enabled in GitHub security settings for all repositories to automate dependency graph tracking and security updates.

Maturity Level: Level 2 (Defined)

Assessment Questions:

  • Is Dependabot enabled on all repositories?
  • Are security update PRs being created?
  • Is there a defined SLA for reviewing Dependabot PRs?
  • Are version updates also enabled?

Guideline Actions to Achieve:

  1. Bulk Enablement (Week 1)

    # GitHub CLI script to enable Dependabot
    #!/bin/bash
    REPOS=$(gh repo list YOUR_ORG --limit 1000 --json name --jq '.[].name')

    for repo in $REPOS; do
      echo "Enabling Dependabot for YOUR_ORG/$repo"
      gh api -X PUT "/repos/YOUR_ORG/$repo/vulnerability-alerts"
      gh api -X PUT "/repos/YOUR_ORG/$repo/automated-security-fixes"
    done

  2. Configuration (Week 2)

    # .github/dependabot.yml
    version: 2
    updates:
      - package-ecosystem: 'npm'
        directory: '/'
        schedule:
          interval: 'weekly'
        open-pull-requests-limit: 10
        reviewers:
          - 'security-team'
        labels:
          - 'dependencies'
          - 'security'

      - package-ecosystem: 'docker'
        directory: '/'
        schedule:
          interval: 'weekly'

  3. PR Review Process (Week 2-3)

    • Define review SLA: Security updates within 2 business days
    • Assign default reviewers
    • Document merge criteria
    • Set up automated testing for dependency updates

  4. Monitoring (Ongoing)

    • Track mean time to merge Dependabot PRs
    • Monitor open security vulnerability count
    • Generate monthly dependency health report

1.4 Secret Management​

Criterion 1.4.1: External Secrets Operator​

Success Criteria: External Secrets Operator (ESO) is installed and running to securely sync secrets from external managers to the Kubernetes cluster.

Maturity Level: Level 3 (Managed)

Assessment Questions:

  • Is ESO installed in all clusters?
  • Are secrets syncing from Google Secret Manager?
  • Are applications consuming secrets from ESO?
  • Is there monitoring for ESO health?

Guideline Actions to Achieve:

  1. ESO Installation (Week 1)

    # Install External Secrets Operator via Helm
    helm repo add external-secrets https://charts.external-secrets.io
    helm repo update

    helm install external-secrets \
      external-secrets/external-secrets \
      -n external-secrets-system \
      --create-namespace \
      --set installCRDs=true

  2. GCP Secret Manager Integration (Week 2)

    # SecretStore configuration
    apiVersion: external-secrets.io/v1beta1
    kind: SecretStore
    metadata:
      name: gcpsm-secret-store
      namespace: default
    spec:
      provider:
        gcpsm:
          projectID: 'your-gcp-project'
          auth:
            workloadIdentity:
              clusterLocation: us-central1
              clusterName: production-cluster
              serviceAccountRef:
                name: external-secrets-sa

  3. ExternalSecret Creation (Week 3)

    apiVersion: external-secrets.io/v1beta1
    kind: ExternalSecret
    metadata:
      name: app-secrets
      namespace: production
    spec:
      refreshInterval: 1h
      secretStoreRef:
        name: gcpsm-secret-store
        kind: SecretStore
      target:
        name: app-secrets
        creationPolicy: Owner
      data:
        - secretKey: database-password
          remoteRef:
            key: prod-db-password
        - secretKey: api-key
          remoteRef:
            key: prod-api-key

  4. Application Migration (Week 4-6)

    • Audit current secret usage
    • Migrate secrets to Google Secret Manager
    • Update application manifests
    • Remove hardcoded secrets

  5. Validation & Monitoring

    # Verify ESO is syncing
    kubectl get externalsecrets -A
    kubectl describe externalsecret app-secrets -n production

    # Check secret sync status
    kubectl get secret app-secrets -n production -o yaml

Criterion 1.4.2: Secret Scanning in Code​

Success Criteria: All repositories have the secret scanning conditions active in SonarQube to prevent any sensitive credentials from being committed.

Maturity Level: Level 2 (Defined)

Guideline Actions to Achieve:

  1. SonarQube Configuration (Week 1)

    • Enable secret detection rules in Quality Gates
    • Configure secret patterns for your tech stack
    • Set severity to "Blocker" for secret detection

  2. GitHub Secret Scanning (Week 1)

      gh api -X PUT "/repos/YOUR_ORG/$repo/secret-scanning"
    done

  3. Pre-commit Hooks (Week 2)

          - id: detect-secrets

  4. Historical Scan (Week 3-4)

    • Document secret leak response plan

      },
      "restrictions": null
    }
    EOF

  2. Bulk Application Script (Week 2)

    # Python script to apply to all repos
    import requests

    repos = ['repo1', 'repo2', 'repo3']
    for repo in repos:
        # Apply branch protection
        # Log success/failure

  3. Verification (Week 2)

    • Test with sample PR
    • Verify quality gate blocks merge if failing

Criterion 2.2.2: Branch Protection - No Direct Pushes​

Success Criteria: Branch protection rules strictly disallow direct pushes to protected branches to ensure all code is reviewed.

Maturity Level: Level 2 (Defined)

Guideline Actions to Achieve:

  1. Enable Protection (Week 1)

    • Apply to main, master, production branches
    • Include administrators in enforcement
    • Remove any push exceptions

  2. Team Communication (Week 1)

    # Email Template:

    Subject: Branch Protection Update - All Changes via PR

    Team,

    Effective immediately, direct pushes to main branches are disabled.

    New workflow:

    1. Create feature branch from main
    2. Make changes and commit
    3. Open Pull Request
    4. Pass all checks (tests, SAST, quality gate)

Criterion 2.2.3: Least Privilege for CI/CD​

Success Criteria: GitHub Actions are configured with minimal required permissions to follow the principle of least privilege.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Default Permissions (Week 1)

    # Add to all workflow files
    permissions:
      contents: read
      pull-requests: read

    jobs:
      build:
        runs-on: ubuntu-latest
        # Inherit default permissions (read-only)

  2. Audit Existing Workflows (Week 1-2)

    # Find workflows with write permissions
    grep -r "permissions:" .github/workflows/

    # Review each workflow:
    # - Does it need write access?
    # - Can it be scoped to specific resources?
    # - Can it use a more specific token?

  3. Workflow-Specific Permissions (Week 2)

    # Example: Release workflow needs write
    name: Release
    on:
      push:
        tags:
          - 'v*'

    permissions:
      contents: write # Only for creating releases
      packages: write # Only for publishing packages

    jobs:
      release:
        runs-on: ubuntu-latest
        steps:
          - name: Create Release
            uses: actions/create-release@v1

  4. Organization Defaults (Week 3)

    • Set organization-level default permissions to read
    • Review all repository permission settings
    • Document permission escalation process

Criterion 2.2.4: No PAT Tokens in Actions​

Success Criteria: No Personal Access Tokens (PATs) are used in GitHub Actions, favoring GitHub Apps or OIDC instead.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Audit Current PAT Usage (Week 1)

    # Search for PAT usage in workflows
    grep -r "secrets.GH_TOKEN\|secrets.GITHUB_PAT\|secrets.PAT" .github/workflows/

    # Search in repository secrets
    gh secret list --repo YOUR_ORG/YOUR_REPO

  2. Migration Strategy (Week 2-4)

    Option A: Use Built-in GITHUB_TOKEN

    # Before (using PAT)
    - name: Checkout
      uses: actions/checkout@v3
      with:
        token: ${{ secrets.GH_PAT }}

    # After (using GITHUB_TOKEN)
    - name: Checkout
      uses: actions/checkout@v3
      with:
        token: ${{ secrets.GITHUB_TOKEN }}

    Option B: GitHub App Authentication

    - name: Generate GitHub App Token
      id: generate_token
      uses: tibdex/github-app-token@v1
      with:
        app_id: ${{ secrets.APP_ID }}
        private_key: ${{ secrets.APP_PRIVATE_KEY }}

    - name: Use App Token
      run: |
        gh api /repos/${{ github.repository }} \
          --header "Authorization: Bearer ${{ steps.generate_token.outputs.token }}"

    Option C: OIDC for Cloud Resources

    - name: Configure AWS Credentials
      uses: aws-actions/configure-aws-credentials@v2
      with:
        role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
        aws-region: us-east-1

  3. Deprecation Timeline (Week 4-6)

    • Identify all PAT dependencies
    • Migrate critical workflows first
    • Deprecate PATs in secret store
    • Document new authentication patterns

2.3 Secret Management Policies​

Criterion 2.3.1: No Plaintext Secrets​

Success Criteria: A strict secret policy is enforced where no plaintext secrets exist in Git, with active push blocking or scanning.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Detection Tools (Week 1)

    • Enable GitHub secret scanning (push protection)
    • Configure SonarQube secret detection
    • Implement pre-commit hooks

  2. Push Protection (Week 1)

    # Enable GitHub push protection (Enterprise/Advanced Security)
    gh api -X PUT "/repos/YOUR_ORG/YOUR_REPO/secret-scanning/push-protection"

  3. Pre-commit Hook Setup (Week 2)

    # Install detect-secrets
    pip install detect-secrets

    # Initialize baseline
    detect-secrets scan > .secrets.baseline

    # Add to .pre-commit-config.yaml
    repos:
      - repo: https://github.com/Yelp/detect-secrets
        rev: v1.4.0
        hooks:
          - id: detect-secrets
            args: ['--baseline', '.secrets.baseline']
            exclude: package-lock.json

    # Install hooks
    pre-commit install

  4. Policy Documentation (Week 2)

    # Secret Management Policy

    ## Prohibited:

    - ❌ Committing passwords in code
    - ❌ API keys in configuration files
    - ❌ Private keys in repository
    - ❌ Database credentials in environment files

    ## Required:

    - ✅ Use secret management systems (GSM, AWS Secrets Manager)
    - ✅ Reference secrets by identifier/name
    - ✅ Rotate secrets quarterly
    - ✅ Use environment variables for local development

    ## If Secret Committed:

    1. DO NOT just remove from latest commit
    2. Report to security team immediately
    3. Rotate the exposed secret
    4. Use git-filter-repo to remove from history
    5. Document incident

Criterion 2.3.2: Runtime Secret Management​

Success Criteria: Runtime secrets are managed and enforced through Google Secret Manager (GSM) and External Secrets Operator (ESO).

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

(See Criterion 1.4.1 for ESO setup)

  1. Secret Migration Plan (Week 1)

    ## Migration Priority:

    1. Production database credentials (Week 1)
    2. External API keys (Week 2)
    3. Internal service tokens (Week 3)
    4. Certificate private keys (Week 4)

  2. Create Secrets in GSM (Week 1-2)

    # Create secret in Google Secret Manager
    echo -n "super-secret-password" | \
      gcloud secrets create prod-db-password \
      --data-file=- \
      --replication-policy="automatic"

    # Grant access to service account
    gcloud secrets add-iam-policy-binding prod-db-password \
      --member="serviceAccount:external-secrets@PROJECT_ID.iam.gserviceaccount.com" \
      --role="roles/secretmanager.secretAccessor"

  3. Application Integration (Week 3-4)

    # Kubernetes Deployment consuming secret
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: myapp
    spec:
      template:
        spec:
          containers:
            - name: myapp
              env:
                - name: DB_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: app-secrets # Created by ESO
                      key: database-password

Criterion 2.3.3: Workload Identity​

Success Criteria: Workload Identity is required for all applications to authenticate securely without using static service account keys.

Maturity Level: Level 4 (Optimizing)

Guideline Actions to Achieve:

  1. Enable Workload Identity (Week 1)

    # Enable on GKE cluster
    gcloud container clusters update CLUSTER_NAME \
      --workload-pool=PROJECT_ID.svc.id.goog

    # Enable on node pool
    gcloud container node-pools update NODEPOOL_NAME \
      --cluster=CLUSTER_NAME \
      --workload-metadata=GKE_METADATA

  2. Create IAM Binding (Week 1-2)

    # Create Kubernetes Service Account
    kubectl create serviceaccount myapp-sa -n production

    # Create GCP Service Account
    gcloud iam service-accounts create myapp-sa \
      --display-name="MyApp Service Account"

    # Bind them
    gcloud iam service-accounts add-iam-policy-binding \
      myapp-sa@PROJECT_ID.iam.gserviceaccount.com \
      --role roles/iam.workloadIdentityUser \
      --member "serviceAccount:PROJECT_ID.svc.id.goog[production/myapp-sa]"

    # Annotate K8s SA
    kubectl annotate serviceaccount myapp-sa \
      iam.gke.io/gcp-service-account=myapp-sa@PROJECT_ID.iam.gserviceaccount.com \
      -n production

  3. Application Migration (Week 2-4)

    # Update Deployment to use Workload Identity
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: myapp
      namespace: production
    spec:
      template:
        spec:
          serviceAccountName: myapp-sa # Use WI-enabled SA
          containers:
            - name: myapp
              image: myapp:latest
              # No need to mount GCP key file!

  4. Remove Service Account Keys (Week 5)

    # List and delete old keys
    gcloud iam service-accounts keys list \
      --iam-account=myapp-sa@PROJECT_ID.iam.gserviceaccount.com

    gcloud iam service-accounts keys delete KEY_ID \
      --iam-account=myapp-sa@PROJECT_ID.iam.gserviceaccount.com

Criterion 2.3.4: OIDC for CI/CD​

Success Criteria: CI access to GCP is strictly managed via OIDC only to ensure secure and short-lived credential usage.

Maturity Level: Level 4 (Optimizing)

Guideline Actions to Achieve:

  1. Configure Workload Identity Federation (Week 1)

    # Create Workload Identity Pool
    gcloud iam workload-identity-pools create github-pool \
      --location="global" \
      --display-name="GitHub Actions Pool"

    # Create Workload Identity Provider
    gcloud iam workload-identity-pools providers create-oidc github-provider \
      --location="global" \
      --workload-identity-pool="github-pool" \
      --issuer-uri="https://token.actions.githubusercontent.com" \
      --attribute-mapping="google.subject=assertion.sub,attribute.actor=assertion.actor,attribute.repository=assertion.repository" \
      --attribute-condition="assertion.repository_owner=='YOUR_ORG'"

  2. Grant Permissions (Week 1)

    # Allow GitHub Actions from specific repo to impersonate SA
    gcloud iam service-accounts add-iam-policy-binding \
      github-actions@PROJECT_ID.iam.gserviceaccount.com \
      --role="roles/iam.workloadIdentityUser" \
      --member="principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github-pool/attribute.repository/YOUR_ORG/YOUR_REPO"

  3. Update GitHub Actions Workflows (Week 2)

    name: Deploy to GCP
    on:
      push:
        branches: [main]

    permissions:
      contents: read
      id-token: write # Required for OIDC

    jobs:
      deploy:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v3

          - id: auth
            uses: google-github-actions/auth@v1
            with:
              workload_identity_provider: 'projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github-pool/providers/github-provider'
              service_account: 'github-actions@PROJECT_ID.iam.gserviceaccount.com'

          - name: Deploy
            run: |
              gcloud run deploy myservice \
                --image gcr.io/PROJECT_ID/myapp:latest

  4. Remove Static Credentials (Week 3)

    # Remove all GCP_SA_KEY secrets from GitHub
    gh secret list --repo YOUR_ORG/YOUR_REPO
    gh secret remove GCP_SA_KEY --repo YOUR_ORG/YOUR_REPO

Pillar 3: Workflow Completion​

Workflow completion ensures security checks produce actionable results that are systematically addressed.

3.1 Quality Gate Enforcement​

Criterion 3.1.1: Mandatory Quality Gate Pass​

Success Criteria: The Quality Gate Status must result in a mandatory PASS for all code changes before they are considered deployable.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Quality Gate Configuration (Week 1)

    Recommended Quality Gate Conditions:

    On New Code:

    - Coverage: >= 80%
    - Duplications: <= 3%
    - Maintainability Rating: A
    - Reliability Rating: A
    - Security Rating: A
    - Security Hotspots Reviewed: 100%

    On Overall Code:

    - Security Issues: 0 (Blocker, Critical)
    - Reliability Issues: 0 (Blocker)

  2. Branch Protection Integration (Week 1)

    # Ensure Quality Gate is required status check
    # See Criterion 2.2.1 for implementation

  3. Team Training (Week 2)

    • Host workshop on fixing common issues
    • Share playbook for quality gate failures
    • Document exception process

  4. Monitoring (Ongoing)

    • Track quality gate pass rate
    • Analyze most common failure reasons
    • Iterate on gate thresholds if needed

Criterion 3.1.2: Zero Critical Security Bugs in New Code​

Success Criteria: All critical security bugs and vulnerabilities in new code must be eliminated before the PR is merged.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Quality Gate Rule (Week 1)

    • Set "Security Issues on New Code" = 0
    • Severity: Blocker, Critical
    • Make it a blocking condition

  2. Developer Workflow (Week 2)

    ## When SonarQube Finds Security Issue:

    1. Review issue in SonarQube dashboard
    2. Understand the vulnerability (read explanation)
    3. Fix the issue:
       - Apply SonarQube suggested fix, OR
       - Implement secure alternative
    4. If false positive:
       - Document why it's false positive
       - Request review from security team
       - Mark as "Won't Fix" with justification
    5. Re-run scan to verify fix
    6. Proceed with PR merge once passing

  3. Training Resources (Week 2)

    • Create security issue playbook
    • Link to OWASP guidelines
    • Provide code examples for common vulnerabilities

Criterion 3.1.3: Technical Debt Reduction​

Success Criteria: There is an active effort to reduce technical debt by resolving Blocker and High priority issues in the backlog.

Maturity Level: Level 2 (Defined)

Guideline Actions to Achieve:

  1. Establish Baseline (Week 1)

    # Generate technical debt report
    - Login to SonarQube Cloud
    - Go to Portfolio view
    - Export technical debt metrics
    - Document current state:
      * Total technical debt hours
      * Count of Blocker issues
      * Count of Critical issues
      * Count of Major issues

  2. Set Reduction Targets (Week 1)

    ## Q1 Goals:

    - Eliminate 100% of Blocker issues
    - Reduce Critical issues by 50%
    - Reduce overall tech debt by 20%

    ## Monthly Sprint Allocation:

    - 20% of sprint capacity dedicated to tech debt
    - At least 2 issues per developer per sprint

  3. Create Remediation Backlog (Week 2)

    # Export issues from SonarQube
    # Create Jira/GitHub issues for each
    # Tag with: tech-debt, security, priority
    # Assign to teams

  4. Track Progress (Weekly)

    • Review tech debt metrics in standup
    • Celebrate wins (closed issues)
    • Adjust allocation if not meeting targets

Criterion 3.1.4: Security Hotspot Review​

Success Criteria: All high-priority Security Hotspots must be reviewed and resolved to maintain a secure codebase.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Hotspot Review Process (Week 1)

    ## Security Hotspot Workflow:

    1. SonarQube identifies potential security-sensitive code
    2. Assigned developer reviews:
       - Is this actually vulnerable?
       - Is there user input validation?
       - Are proper security controls in place?
    3. Mark hotspot status:
       - Safe: Code is secure as-is
       - Fixed: Vulnerability resolved
       - To Review: Needs security team assessment
    4. Document decision rationale

  2. SLA Definition (Week 1)

    ## Review Timeline:

    - High priority hotspots: 3 business days
    - Medium priority: 1 week
    - Low priority: 2 weeks

  3. Assignment (Week 2)

    • Assign hotspots to code owners
    • Create Jira tickets for tracking
    • Link to SonarQube hotspot

  4. Training (Week 2-3)

    • Host security hotspot training
    • Cover common patterns:
      • SQL injection risks
      • XSS vulnerabilities
      • Weak cryptography
      • Insecure deserialization
    • Hands-on review exercises

Criterion 3.1.5: Security Rating Maintenance​

Success Criteria: All production projects must maintain an overall 'A' Security Rating on their main branches.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Current State Assessment (Week 1)

    # Generate security rating report for all projects
    # Identify projects below 'A' rating
    # Prioritize by business criticality

  2. Improvement Roadmap (Week 2)

    ## Project: Payment Service (Current: C)

    Issues to fix:

    1. 3 Critical SQL injection vulnerabilities
    2. 5 Major authentication bypasses
    3. 12 Minor issues

    Timeline:

    - Week 1-2: Fix Critical issues
    - Week 3: Fix Major issues
    - Week 4: Achieve 'A' rating

  3. Maintain 'A' Rating (Ongoing)

    • Monitor security rating in CI/CD
    • Alert on rating degradation
    • Block deployments if rating drops below 'A'

Criterion 3.1.6: Code Quality Metrics​

Success Criteria: Code Maintainability and overall Quality Ratings are monitored to ensure the long-term health of the software.

Maturity Level: Level 2 (Defined)

Guideline Actions to Achieve:

  1. Define Quality Metrics (Week 1)

    ## Key Metrics:

    - Maintainability Rating: A (tech debt ratio < 5%)
    - Reliability Rating: A (no bugs)
    - Code Coverage: >= 80%
    - Code Duplication: < 3%
    - Cognitive Complexity: < 15 per function

  2. Dashboard Setup (Week 1)

    • Configure SonarQube Portfolio view
    • Add quality widgets to team dashboard
    • Set up weekly email reports

  3. Quality Reviews (Monthly)

    ## Monthly Quality Review Agenda:

    1. Review quality trends
    2. Identify deteriorating projects
    3. Assign improvement tasks
    4. Recognize quality improvements
    5. Adjust quality standards if needed

Success Criteria: All action items assigned during governance activities are executed and closed by their respective due dates.

Maturity Level: Level 3 (Managed)

Guideline Actions to Achieve:

  1. Action Item Tracking System (Week 1)

Assessment Scoring​

Scoring Methodology​

Each criterion is scored as follows:

ScoreStatusDescription
0Not StartedNo implementation, no planning
1PlannedPlanning in progress, timeline defined
2In ProgressActive implementation, < 50% complete
3Mostly Complete>50% complete, minor gaps remain
4CompleteFully implemented, evidence provided

Maturity Level Calculation​

Calculate maturity level per pillar:

Pillar Score = (Sum of Criterion Scores) / (Max Possible Score) × 100%

Maturity Level:
- Level 0: 0-20%
- Level 1: 21-40%
- Level 2: 41-60%
- Level 3: 61-80%
- Level 4: 81-100%

Overall Maturity Score​

Overall Maturity = Average of all pillar scores

Deliverables:

  • Branch protection rules enforced
  • Dependency scanning active
  • Secret detection in place

Focus: DAST, secret management, workflow enforcement

Priority Criteria:

  1. DAST pipeline (1.2.1, 1.2.2)
  2. External Secrets Operator (1.4.1)
  3. Quality gate enforcement (3.1.1, 3.1.2)
  4. Security hotspot reviews (3.1.4)
  5. Portfolio configuration (2.1.3)

Deliverables:

  • DAST running on all services
  • Secrets managed via ESO + GSM
  • Quality gates blocking bad code
  • Organized project portfolios

Focus: Advanced security, least privilege, workload identity

Priority Criteria:

  1. Workload Identity (2.3.3)

Deliverables:

  • Zero static credentials
  • All services use Workload Identity

  • CI/CD uses OIDC exclusively

Focus: Governance, continuous improvement, culture

Priority Criteria:

Deliverables:

  • Structured governance process
