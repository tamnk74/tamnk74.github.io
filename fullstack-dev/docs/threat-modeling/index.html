E-commerce Application Threat Model

This document outlines the threat model for the e-commerce application based on the provided C4 model and architecture diagrams.

The model uses the STRIDE methodology (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) to identify and mitigate threats at each layer of the system.

1. Key Assets & Trust Boundaries​

Before analyzing threats, let's identify what we're protecting (assets) and where the system's trust levels change (boundaries).

Key Assets​

  • Data:
    • Customer PII: Names, addresses, contact info (from UserService).
    • Authentication Data: Password hashes, refresh tokens, user IDs (from AuthService, PostgreSQL, Redis).
    • Payment Data: Payment method tokens/references (from PaymentService).
    • Business Data: Order history, product details, sales analytics (from OrderService, ProductService).
  • Infrastructure & Code:
    • API Keys: Secrets for Auth0, Stripe, SendGrid, and Cloud Storage.
    • CI/CD Pipeline: The ability to build and deploy code (GitHub Actions, ArgoCD).
    • System Availability: The ability of the platform to remain online and process orders.

Primary Trust Boundaries​

  1. Internet ↔ Cloud Armor/LB: The primary external boundary. Untrusted users (Customers, Admins) interact with the system.
  2. Web App ↔ API Gateway: The boundary between the client-side browser and the server-side backend.
  3. API Gateway ↔ Microservices: An internal boundary. The gateway is the single entry point, but services must trust (or verify) that requests from it are legitimate.
  4. Microservices ↔ Data Layer: The boundary between the application logic and its state (databases, caches, queues).
  5. Microservices ↔ External APIs: The boundary where your system calls out to third-party services (Auth0, Stripe, SendGrid).
  6. DevOps Pipeline ↔ GKE Cluster: A critical administrative boundary. The CI/CD system has privileged access to deploy applications.

2. Threat Analysis by Component​

Here is a breakdown of potential threats (STRIDE) for each major component and boundary, along with planned and recommended mitigations.

Component 1: Public-Facing & Edge (Web App, LB, Cloud Armor)​

This layer is the first line of defense against all external traffic.

  • [S] Spoofing: An attacker impersonates a user via session hijacking.
    • Mitigation (Planned): Use of JWTs.
    • Mitigation (Recommended): Store tokens in Secure, HttpOnly cookies to prevent access from client-side scripts (XSS). Implement strict CSRF (Cross-Site Request Forgery) protection.
  • [T] Tampering: An attacker intercepts and modifies traffic (Man-in-the-Middle).
    • Mitigation (Planned): Global HTTP(S) Load Balancer.
    • Mitigation (Recommended): Enforce HTTPS-only traffic with HSTS (HTTP Strict Transport Security) headers.
  • [I] Information Disclosure: Client-side code in the Next.js app or Microfrontends leaks sensitive information (e.g., internal API paths, non-public keys).
    • Mitigation (Recommended): Use Next.js environment variables correctly (prefixing with NEXT_PUBLIC_ only for non-sensitive, public-facing keys). All other keys must be server-side only.
  • [D] Denial of Service: An attacker floods the application with traffic (L3/L4 or L7 DDoS).
    • Mitigation (Planned): Cloud Armor (WAF & DDoS Protection) and Rate Limiter (in API Gateway).
    • Mitigation (Recommended): Configure Cloud Armor rules to block known-bad IPs and geographic locations. Implement CDN caching via Cloud Storage for all static assets to reduce origin load.
  • [E] Elevation of Privilege: An attacker injects a malicious script via Cross-Site Scripting (XSS) to steal a user's or admin's session cookie/token.
    • Mitigation (Planned): React automatically escapes content, providing a baseline defense.
    • Mitigation (Recommended): Implement a strict Content Security Policy (CSP) header to control which scripts, styles, and media can be loaded. Sanitize all user-generated content (e.g., product reviews, user profiles) before rendering.

Component 2: API Gateway​

This is the central chokepoint for all backend logic.

  • [S] Spoofing: An attacker forges a JWT or replays a stolen one.
    • Mitigation (Planned): JWT Middleware validates the token's signature, expiration (exp), and issuer (iss).
    • Mitigation (Recommended): Use short-lived access tokens (e.g., 15 minutes) and longer-lived refresh tokens. Store refresh tokens in Redis (as hinted by your diagram) to allow for instant revocation (logout) or to detect token reuse.
  • [T] Tampering: An attacker modifies a request payload after it passes the firewall (e.g., changing quantity to a negative number).
    • Mitigation (Recommended): Implement rigorous DTO (Data Transfer Object) validation in NestJS (using class-validator) on all incoming requests at the controller level.
  • [R] Repudiation: An admin or user denies performing a critical action (e.g., "I never deleted that product").
    • Mitigation (Planned): Request Logger (Audit & Monitoring).
    • Mitigation (Recommended): Ensure logs capture the authenticated userId, source IP, timestamp, and the full request body for all state-changing operations (POST, PUT, DELETE, PATCH).
  • [D] Denial of Service: An attacker bypasses Cloud Armor with requests that are valid but resource-intensive (e.g., a complex search query).
    • Mitigation (Planned): Rate Limiter (Request Throttling).
    • Mitigation (Recommended): Implement rate limiting based on IP, user ID, and API key. Add pagination and complexity limits to all list/search endpoints (e.g., ProductController).
  • [E] Elevation of Privilege: A regular user attempts to access an admin-only endpoint (e.g., /api/products/delete/123).
    • Mitigation (Planned): Auth Guard (checks for authentication) and Role Guard (checks for authorization/RBAC). This is the correct approach.
    • Mitigation (Recommended): Ensure the RoleGuard is applied to all sensitive endpoints and that roles are derived from the validated JWT, not from a parameter in the request body.

Component 3: Microservices (Internal)​

These components trust requests from the API Gateway.

  • [S] Spoofing: A compromised microservice (e.g., NotificationService) calls another microservice directly (e.g., OrderService), bypassing the API Gateway's authorization.
    • Mitigation (Recommended): Do not allow direct inter-service communication by default. If required, implement service-to-service authentication (e.g., mutual TLS (mTLS) within the GKE cluster or signed internal-use-only JWTs).
  • [T] Tampering: An attacker finds a way to inject malicious data into the Message Queue (Kafka), (e.g., a fake "payment_success" event).
    • Mitigation (Recommended): Secure Kafka topics with ACLs. Only the PaymentService pod's service account should have write access to payment topics. All consuming services (OrderService, NotificationService) must validate the schema of incoming messages before processing.
  • [I] Information Disclosure: A microservice leaks internal data in an error message (e.g., ProductService returns a full database stack trace).
    • Mitigation (Planned): NestJS framework conventions.
    • Mitigation (Recommended): Implement global exception filters in each microservice to catch all unhandled errors and return a standardized, generic error message. Log the full details internally for debugging.
  • [E] Elevation of Privilege: An attacker exploits an Insecure Direct Object Reference (IDOR). For example, an authenticated user A calls /api/orders/123 (their own order) but then changes the request to /api/orders/124 (user B's order).
    • Mitigation (Recommended): This is a critical business logic flaw. The OrderService (and UserService, etc.) must not trust the ID from the URL alone. It must perform a check like: SELECT * FROM orders WHERE id = 124 AND user_id = {authenticated_user_id_from_jwt}.

Component 4: Data & Storage Layer​

This is where your most valuable assets are stored.

  • [T] Tampering: An attacker gains database access and modifies data directly (e.g., changes an order status to "Shipped").
    • Mitigation (Planned): Cloud SQL is in a separate data namespace.
    • Mitigation (Recommended):
      1. Network: Use private IP for Cloud SQL and configure firewall rules so it only accepts connections from your GKE pod network.
      2. Auth: Do not use static database passwords. Use GCP Workload Identity to map GKE service accounts (e.g., order-service-sa) to GCP service accounts that have IAM permissions to access Cloud SQL.
      3. ORM: The use of TypeORM is a good defense against SQL Injection.
  • [I] Information Disclosure:
    1. A database backup or Cloud Storage bucket is made public.
    2. Redis cache is exposed, leaking session tokens.
    • Mitigation (Recommended):
      1. Storage: Enforce "Encryption at Rest" (default on GCP, but verify). Make all Cloud Storage buckets private by default. Use signed URLs for temporary access to media if needed.
      2. Redis: Deploy Redis within the GKE private network. Enable Redis authentication (AUTH command) with a strong password stored in a secret manager.
  • [D] Denial of Service: A malicious query to Elasticsearch overloads the search cluster.
    • Mitigation (Planned): Elasticsearch is used by ProductService.
    • Mitigation (Recommended): The ProductService must sanitize, validate, and place limits on all search parameters (e.g., max query length, no leading wildcards) before passing them to Elasticsearch.

Component 5: Third-Party Integrations (External)​

Your system is vulnerable to threats originating from or targeting these external partners.

  • [S] Spoofing: An attacker sends a fake webhook to your PaymentService, spoofing a successful payment from Stripe.
    • Mitigation (Recommended): Validate all webhook signatures. Stripe (and most other providers) includes a signature in the request headers. Your service must verify this signature using your shared secret before trusting the payload.
  • [I] Information Disclosure: Your secret API keys for Stripe, Auth0, or SendGrid are leaked (e.g., committed to Git).
    • Mitigation (Planned): Use of SonarQube (SAST) can help detect this.
    • Mitigation (Recommended): Store all secrets in GCP Secret Manager. Use Workload Identity to grant GKE pods access to read specific secrets at runtime. Never store secrets in config files, environment variables in your Git repo, or Docker images.
  • [R] Repudiation: Auth0 claims they never authenticated a user, or Stripe claims a payment was never made.
    • Mitigation (Recommended): Log all outgoing API requests and the core details of the incoming responses (e.g., stripe_charge_id, auth0_user_id). This provides an audit trail for dispute resolution.

Component 6: CI/CD & Infrastructure (DevOps)​

A compromised pipeline means a compromised application.

  • [T] Tampering: An attacker with access to your GitHub repo injects malicious code into a branch, which is then automatically built and deployed by ArgoCD.
    • Mitigation (Planned): GitHub Actions CI/CD, ArgoCD (GitOps), SonarQube (SAST), OWASP ZAP (DAST).
    • Mitigation (Recommended):
      1. GitHub: Enforce branch protection rules on main. Require PRs, mandatory code reviews from at least one other developer, and successful SonarQube and ZAP scans before merging.
      2. Image Security: Scan Docker images for known vulnerabilities (e.g., with GCR's built-in scanner or a tool like Trivy) before they are deployed.
  • [E] Elevation of Privilege: An attacker compromises a GitHub Actions runner or ArgoCD and uses its credentials to take over the GKE cluster.
    • Mitigation (Recommended): Apply the principle of least privilege. The service account used by ArgoCD should only have permission to deploy to the Frontend and Backend namespaces, not kube-system or default. The GitHub Actions service account should only have permissions to push images to GCR and trigger ArgoCD syncs.

3. Summary of Key Recommendations​

Your architecture has many strong, modern controls. The highest-priority risks to address are in business logic and configuration.

  1. Implement IDOR Protection: Ensure every microservice validates that the authenticated user (sub from JWT) is authorized to access or modify the specific resource they are requesting (e.g., their own order, their own profile).
  2. Validate All Webhooks: This is non-negotiable. Use signature validation for Stripe and any other webhook provider.
  3. Secure All Secrets: Use GCP Secret Manager + Workload Identity. Remove all static keys and passwords from code, configs, and environment variables.
  4. Enforce Strict CI/CD Security: Use GitHub branch protection rules. A PR and a successful security scan (SAST/DAST) must be mandatory to merge to main.
  5. Implement Service-to-Service Auth: If microservices need to call each other directly, secure that internal traffic with mTLS or internal JWTs.
  6. Apply a Strict CSP: This is your best defense against XSS, which is a primary vector for session/token theft.
