Non-Functional Requirements — E-Commerce Platform (Million-User Scale)

Detailed NFR specification for the production e-commerce platform: measurable targets, architectural decisions that achieve them, verification methods, and SLO budgets.

How to Use This Document​

Each NFR follows the structure:

Target → Architectural mechanism → How to verify → Alert threshold

NFRs are owned by the relevant service team and are verified in CI (load tests), staging gates, and production SLO dashboards.

Verification​

# k6 load test: p99 latency gate in CI
k6 run --env BASE_URL=https://staging.ecom.io \
  --threshold 'http_req_duration{name:product_detail}[p(99)] < 200' \
  tests/load/product-latency.js
# Datadog SLO: product page p99 < 200 ms, 99.9% of 30-day rolling window
slos:
  - name: "Product Page Latency SLO"
    type: metric
    query:
      numerator: "sum:trace.web.request.duration.by.resource_service.99p{service:product-service,resource_name:GET /products/:id}.rollup(avg,60) < 200"
      denominator: "sum:trace.web.request.duration.by.resource_service.99p{service:product-service,resource_name:GET /products/:id}.rollup(avg,60)"
    target: 99.9
    timeframe: 30d

SLO Burn Rate Alerts​

# Datadog: multi-window burn rate alert (Google SRE approach)
# Fast burn: 14.4× in 1 hour → consumes 2% of monthly error budget
# Slow burn: 6× in 6 hours → consumes 5% of monthly error budget
monitors:
  - name: "Checkout Availability SLO Burn — Fast"
    type: slo_alert
    slo_id: "checkout-availability-slo"
    alert_type: "burn_rate"
    burn_rate_threshold: 14.4
    time_windows: ["1h", "5m"]   # both windows must be burning

  - name: "Checkout Availability SLO Burn — Slow"
    type: slo_alert
    slo_id: "checkout-availability-slo"
    alert_type: "burn_rate"
    burn_rate_threshold: 6
    time_windows: ["6h", "30m"]

Required spans per checkout request​

// Each service MUST create these spans (OTel instrumentation contract)
const spans = [
  'http.server POST /checkout',           // API Gateway + Cart Service
  'db.query SELECT cart_items',           // Cart Service → Redis
  'http.client POST /orders',             // Cart → Order Service
  'db.query INSERT orders',               // Order Service → PostgreSQL
  'messaging.publish order.created',      // Order → Kafka
  'messaging.consume order.created',      // Inventory → Kafka consumer
  'db.query DECRBY stock:{sku}',          // Inventory → Redis Lua
  'messaging.publish inventory.reserved', // Inventory → Kafka
  'messaging.consume inventory.reserved', // Payment → Kafka
  'http.client POST stripe/charges',      // Payment → Stripe API
];

Statelessness Requirements​

All services must be stateless — session state lives in Redis, not in-process:

  • No in-memory caches that diverge between replicas
  • No local file writes (use Cloud Storage for uploads)
  • No sticky sessions (load balancer distributes randomly)
  • DB connection pools re-established on pod restart (PgBouncer handles pool externally)

Database Scaling Plan​

StageUsersMechanism
0–100 K—Single Cloud SQL instance per service
100 K–1 MNow1 primary + 2 read replicas; PgBouncer
1 M–5 MFuturePartition Orders by created_at month; archive old partitions to BigQuery
5 M+FutureEvaluate Spanner for Order service (unlimited horizontal scale, strong consistency)

8. Recovery (RTO / RPO)​

ScenarioRTORPOMechanism
GKE pod crash<30 s0 (stateless)Kubernetes restart policy; readiness probe gates traffic
GKE node failure<60 s0Pod anti-affinity spreads replicas; new pod scheduled on healthy node
Cloud SQL primary failure<60 s<30 sCloud SQL HA automatic failover; binlog replication lag
GKE regional outage<2 min<30 sGCLB health-check failover to DR region; Cloud SQL replica promoted
Kafka broker failure<30 s0RF=3 — surviving brokers re-elect leader; in-flight messages replicated
Redis primary failure<30 ssecondsCloud Memorystore HA; replica promoted automatically
Full region disaster<5 min<30 sManual runbook: update DNS TTL → DR region; promote Cloud SQL replica

DR Runbook (Region Failover)​

# scripts/dr-failover.sh
# Prerequisite: DR GKE cluster is pre-warmed with latest image tags

# 1. Promote Cloud SQL read replica in DR region to primary
gcloud sql instances promote-replica order-db-replica --project="${PROJECT_ID}"

# 2. Update GCP GCLB backend to point to DR region only
gcloud compute backend-services update ecom-backend \
  --global --no-enable-cdn \
  --remove-backend=us-central1-neg \
  --project="${PROJECT_ID}"

# 3. Verify DR cluster is serving traffic
kubectl --context=gke_${PROJECT_ID}_us-east1_ecom-dr \
  rollout status deployment/order-service -n production

echo "DR failover complete. Monitor error rates in Datadog."
