Unit Testing Documentation Guide

Establish clear, accessible documentation that helps all developers understand how to implement unit tests for your technology stack.

Overview​

This guide helps you create and maintain comprehensive unit testing documentation that serves as the single source of truth for testing practices in your project. Well-documented testing practices ensure consistency, reduce onboarding time, and improve code quality across the team.

Why Unit Testing Documentation Matters​

  • Consistency: Ensures all developers follow the same testing patterns
  • Onboarding: New team members can quickly understand testing expectations
  • Quality: Clear examples reduce testing mistakes and improve coverage
  • Efficiency: Developers spend less time figuring out how to test
  • Knowledge Sharing: Captures team knowledge and best practices

Documentation Structure​

1. Overview Section​

Start with a high-level overview of your testing strategy:

# Unit Testing Guide - [Project Name]

## Testing Philosophy

We follow Test-Driven Development (TDD) principles and aim for:

- **Coverage Target**: Minimum 80% code coverage
- **Test Speed**: All unit tests should run in < 5 seconds
- **Independence**: Each test should be independent and idempotent
- **Clarity**: Tests serve as living documentation

## Technology Stack

- **Language**: TypeScript/JavaScript
- **Framework**: Jest 29.x
- **Assertion Library**: Jest expect
- **Mocking**: Jest mocks
- **Coverage Tool**: Jest coverage (Istanbul)

## Quick Start

```bash
# Run all tests
npm test

# Run tests in watch mode
npm test -- --watch

# Run tests with coverage
npm test -- --coverage

# Run specific test file
npm test -- user.service.spec.ts
```

Create jest.config.js in the project root:

  preset: 'ts-jest',
  testEnvironment: 'node',
  roots: ['<rootDir>/src'],
  testMatch: ['**/__tests__/**/*.ts', '**/?(*.)+(spec|test).ts'],
  transform: {
    '^.+\\.ts$': 'ts-jest',
  },
  collectCoverageFrom: ['src/**/*.ts', '!src/**/*.d.ts', '!src/**/*.interface.ts', '!src/index.ts'],

## Testing Services

### Basic Service Test

```typescript
// user.service.spec.ts
import { Test, TestingModule } from '@nestjs/testing';
import { UserService } from './user.service';
import { UserRepository } from './user.repository';
import { User } from './user.entity';

describe('UserService', () => {
  let service: UserService;
  let repository: jest.Mocked<UserRepository>;

  beforeEach(async () => {
    const mockRepository = {
      findById: jest.fn(),
      save: jest.fn(),
      delete: jest.fn(),
    };

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        UserService,
        {
          provide: UserRepository,
          useValue: mockRepository,
        },
      ],
    }).compile();

    service = module.get<UserService>(UserService);
    repository = module.get(UserRepository);
  });

  afterEach(() => {
    jest.clearAllMocks();
  });

  describe('findUserById', () => {
    it('should return a user when found', async () => {
      // Arrange
      const userId = '123';
      const expectedUser: User = {
        id: userId,
        email: 'test@example.com',
        name: 'Test User',
      };
      repository.findById.mockResolvedValue(expectedUser);

      // Act
      const result = await service.findUserById(userId);

      // Assert
      expect(result).toEqual(expectedUser);
      expect(repository.findById).toHaveBeenCalledWith(userId);
      expect(repository.findById).toHaveBeenCalledTimes(1);
    });

    it('should throw NotFoundException when user not found', async () => {
      // Arrange
      const userId = 'non-existent';
      repository.findById.mockResolvedValue(null);

      // Act & Assert
      await expect(service.findUserById(userId)).rejects.toThrow(
        'User not found'
      );
    });
  });

  describe('createUser', () => {
    it('should create and return a new user', async () => {
      // Arrange
      const createDto = {
        email: 'new@example.com',
        name: 'New User',
      };
      const savedUser = { id: '456', ...createDto };
      repository.save.mockResolvedValue(savedUser);

      // Act
      const result = await service.createUser(createDto);

      // Assert
      expect(result).toEqual(savedUser);
      expect(repository.save).toHaveBeenCalledWith(
        expect.objectContaining(createDto)
      );
    });

    it('should throw error when email already exists', async () => {
      // Arrange
      const createDto = {
        email: 'existing@example.com',
        name: 'User',
      };
      repository.save.mockRejectedValue(new Error('Duplicate email'));

      // Act & Assert
      await expect(service.createUser(createDto)).rejects.toThrow(
        'Duplicate email'
      );
    });
  });
});

import { render, screen, waitFor } from '@testing-library/react';
import { UserProfile } from './UserProfile';
import { userService } from '../services/user.service';

jest.mock('../services/user.service');

describe('UserProfile', () => {

  };

    jest.clearAllMocks();

  });

    (userService.getUser as jest.Mock).mockResolvedValue(mockUser);

    render(<UserProfile userId="1" />);

      expect(screen.getByText(mockUser.name)).toBeInTheDocument();
      expect(screen.getByText(mockUser.email)).toBeInTheDocument();

    (userService.getUser as jest.Mock).mockRejectedValue(new Error('Failed to fetch'));

    await waitFor(() => {
      expect(screen.getByText(/error loading user/i)).toBeInTheDocument();

### 4. Common Testing Patterns

```markdown
## Testing Patterns

### Arrange-Act-Assert (AAA)

Structure all tests using the AAA pattern:

```typescript
it('should calculate total price with tax', () => {
  // Arrange - Set up test data and dependencies
  const items = [
    { price: 10, quantity: 2 },
    { price: 15, quantity: 1 },
  ];
  const taxRate = 0.1;

  // Act - Execute the function being tested
  const total = calculateTotal(items, taxRate);

  // Assert - Verify the result
  expect(total).toBe(38.5); // (10*2 + 15*1) * 1.1
});

Test Data Builders​

Create reusable test data builders:

// test-helpers/user.builder.ts
export class UserBuilder {
  private user: Partial<User> = {
    id: '123',
    email: 'test@example.com',
    name: 'Test User',
    role: 'user',
    createdAt: new Date(),
  };

  withId(id: string): this {
    this.user.id = id;
    return this;
  }

  withEmail(email: string): this {
    this.user.email = email;
    return this;
  }

  withRole(role: string): this {
    this.user.role = role;
    return this;
  }

  asAdmin(): this {
    this.user.role = 'admin';
    return this;
  }

  build(): User {
    return this.user as User;
  }
}

// Usage in tests
const user = new UserBuilder().withEmail('admin@example.com').asAdmin().build();

// ❌ BAD: Over-mocking
it('should process order', () => {

## Code Coverage Standards

### Coverage Thresholds

Maintain these minimum coverage levels:

- **Statements**: 80%
- **Branches**: 75%
- **Functions**: 80%
- **Lines**: 80%

### What to Test

✅ **Must Test**:
- Business logic functions
- Data transformations
- Validation logic
- Error handling paths
- API endpoints
- State management

❌ **Can Skip**:
- Type definitions (`.d.ts` files)
- Configuration files
- Constants and enums
- Simple getters/setters
- Third-party library wrappers (test integration instead)

### 7. Common Pitfalls and Solutions

```markdown
## Common Testing Mistakes

### 1. Testing Implementation Details

```typescript
// ❌ BAD: Testing internal state
it('should set loading to true', () => {
  component.fetchData();
  expect(component.isLoading).toBe(true);
});

// ✅ GOOD: Testing observable behavior
it('should show loading spinner when fetching', () => {
  render(<Component />);
  expect(screen.getByTestId('loading-spinner')).toBeInTheDocument();
});

2. Fragile Selectors​

// ❌ BAD: Using implementation-specific selectors
const button = container.querySelector('.btn-primary-lg');

// ✅ GOOD: Using accessible queries
const button = screen.getByRole('button', { name: /submit/i });

3. Sharing State Between Tests​

// ❌ BAD: Shared mutable state
let sharedUser: User;

beforeAll(() => {
  sharedUser = new User('123');
});

it('test 1', () => {
  sharedUser.name = 'Changed'; // Affects other tests!
});

// ✅ GOOD: Fresh state for each test
beforeEach(() => {
  const user = new User('123');
});

4. Not Cleaning Up​

// ❌ BAD: Leaving mocks/spies active
it('test 1', () => {
  jest.spyOn(service, 'method');
});

// ✅ GOOD: Clean up after each test
afterEach(() => {
  jest.restoreAllMocks();
  jest.clearAllMocks();
});

5. Testing Too Much in One Test​

// ❌ BAD: Multiple assertions for different behaviors
it('should handle user operations', () => {
  service.createUser(data);
  expect(repository.save).toHaveBeenCalled();

  service.updateUser(id, data);
  expect(repository.update).toHaveBeenCalled();

  service.deleteUser(id);
  expect(repository.delete).toHaveBeenCalled();
});

// ✅ GOOD: Separate test for each behavior
describe('UserService', () => {
  it('should create user', () => {
    service.createUser(data);
    expect(repository.save).toHaveBeenCalled();
  });

  it('should update user', () => {
    service.updateUser(id, data);
    expect(repository.update).toHaveBeenCalled();
  });

  it('should delete user', () => {
    service.deleteUser(id);
    expect(repository.delete).toHaveBeenCalled();
  });
});

### 8. Testing Checklist

```markdown
## Pre-Commit Testing Checklist

Before committing code, ensure:

- [ ] All new code has corresponding unit tests
- [ ] All tests pass locally (`npm test`)
- [ ] Code coverage meets threshold (minimum 80%)
- [ ] Tests follow AAA pattern
- [ ] Tests are independent and can run in any order
- [ ] Mock external dependencies appropriately
- [ ] Test names clearly describe what is being tested
- [ ] Edge cases and error scenarios are covered
- [ ] No console errors or warnings in tests
- [ ] Tests run quickly (< 5 seconds for unit tests)

## Review Checklist

When reviewing test code:

- [ ] Tests are easy to understand
- [ ] Tests verify behavior, not implementation
- [ ] Mocks are used appropriately (not over-mocked)
- [ ] Test data is clear and minimal
- [ ] Assertions are specific and meaningful
- [ ] Error messages are descriptive
- [ ] No duplicate test code (use helpers/builders)
- [ ] Tests don't rely on execution order

Maintenance Guidelines​

Keeping Documentation Updated​

  1. Assign Ownership: Designate a team member as the documentation owner
  2. Review Schedule: Review and update quarterly or when tech stack changes
  3. Version Control: Keep documentation in the same repository as code
  4. Change Process: Update docs as part of PR when adding new testing patterns

Documentation Formats​

Choose the format that works best for your team:

Option 1: Wiki (Recommended)

  • Easy to update and search
  • Good for collaborative editing
  • Examples: Confluence, GitHub Wiki, Notion

Option 2: Markdown in Repository

  • Version controlled with code
  • Easy to keep in sync
  • Examples: docs/testing/ folder, README files

Option 3: Living Documentation

  • Auto-generated from code
  • Always up-to-date
  • Examples: Storybook, JSDoc, TypeDoc

Test Template​

import { [Component/Service] } from './[file]';

describe('[Component/Service Name]', () => {
  // Setup
  beforeEach(() => {
    // Arrange common setup
  });

  // Cleanup
  afterEach(() => {
    jest.clearAllMocks();
  });

  describe('[method/feature name]', () => {
    it('should [expected behavior]', () => {
      // Arrange
      const input = 'test';

      // Act
      const result = methodUnderTest(input);

      // Assert
      expect(result).toBe(expected);
    });
  });
});

FAQ​

Q: How much time should I spend writing tests? A: Aim for a 1:1 ratio - if you spend 1 hour writing code, spend 1 hour writing tests.

Q: When should I write tests - before or after the code? A: Ideally before (TDD), but writing tests immediately after is also acceptable.

Q: What if I can't reach 80% coverage? A: Document why in the code and discuss with the team. Some code may be exempt.

Q: Should I test private methods? A: No, test the public API. Private methods are tested indirectly through public methods.

Q: How do I test legacy code without tests? A: Start by adding characterization tests, then refactor gradually.

Conclusion​

Well-documented unit testing practices are essential for maintaining code quality and team productivity. Keep this documentation:

  • Accessible: Easy to find and navigate
  • Up-to-date: Review and update regularly
  • Practical: Include real examples from your codebase
  • Collaborative: Encourage team contributions

Remember: Good tests serve as living documentation of how your code should behave!
