Smoke Test Scripts for Deployment Status Verification

Smoke testing is a software testing process that determines whether a newly deployed build is stable enough for further testing and traffic. Smoke tests are a minimal set of automated checks that answer: “Did the deployment work?”

Smoke testing is also known as Build Verification Testing (BVT) or Confidence Testing.

This guide defines how to use smoke test scripts to verify deployment status for a Next.js microfrontend frontend and NestJS services on Google Cloud Platform (GCP), with automation in GitHub Actions.

What This Practice Ensures​

It is possible to check deployment status through smoke test scripts because:

  • Every deployment produces an environment URL (preview/staging/prod).
  • A deterministic set of scripts runs against that URL.
  • The pipeline marks the deployment as successful only if smoke tests pass.
  • Results are stored as artifacts and linked to the deployment.

Scope​

Applies to:

  • Next.js microfrontend shell + remotes
  • NestJS API gateway and critical domain services
  • GCP runtime (Cloud Run or GKE) and load balancing
  • GitHub Actions deployment workflows

Smoke Tests vs. Health Checks​

  • Health checks answer: “Is the container/process alive?”
  • Smoke tests answer: “Can a user complete the most basic flows and can the system serve critical paths?”

Both are required. A healthy process can still be functionally broken.

Minimal Smoke Test Coverage (Recommended)​

Keep smoke tests small and fast. A good default is 5–15 checks.

Frontend (Next.js microfrontends)​

  • Home route loads (shell renders)
  • One remote route loads (e.g., product listing)
  • Static assets load (no 404 for JS/CSS chunks)

Backend (NestJS)​

  • /health (or equivalent) returns expected status
  • Auth endpoint reachable (if used by UI)
  • A read-only core endpoint works (e.g., product search)

Cross-service behavior​

  • A request can traverse: Next.js → API gateway → downstream service
  • Error budget guardrails (basic: no elevated 5xx rate in the first minutes)

Where Smoke Tests Run​

Typical environments:

  • Preview (per PR): validates integration early
  • Staging: validates production-like integration
  • Production: validates new release after deploy

Recommended rule:

  • Run smoke tests on every deploy to any environment.

Implementation: Smoke Test Scripts​

Repository layout (example)​

scripts/
  smoke/
    smoke.sh
    endpoints.json
    README.md

Option A: Bash + curl (fastest)​

Example script (conceptual) that fails the pipeline if any required endpoint is not healthy.

#!/usr/bin/env bash
set -euo pipefail

BASE_URL="${BASE_URL:?BASE_URL is required}"

check_url () {
  local url="$1"
  local expected="$2"

  echo "Checking: ${url}"
  status=$(curl -s -o /dev/null -w "%{http_code}" "${url}")

  if [ "${status}" != "${expected}" ]; then
    echo "Smoke test failed: ${url} returned ${status} (expected ${expected})"
    exit 1
  fi
}

# Frontend routes
check_url "${BASE_URL}/" "200"
check_url "${BASE_URL}/products" "200"

# Backend health (through same LB if applicable)
check_url "${BASE_URL}/api/health" "200"

echo "Smoke tests passed"

Option B: Node.js script (richer assertions)​

Use Node when you need JSON assertions (e.g., ensure a response contains required fields).

GitHub Actions: Run Smoke Tests After Deploy​

The deployment job should only pass if smoke tests pass.

Example pattern:

  1. Deploy to GCP
  2. Capture service URL
  3. Run smoke scripts against that URL
  4. Upload logs as artifacts
name: deploy-and-smoke

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install
        run: pnpm install --frozen-lockfile

      - name: Build
        run: pnpm build

      - name: Auth to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SA_EMAIL }}

      - name: Deploy (Cloud Run example)
        id: deploy
        uses: google-github-actions/deploy-cloudrun@v2
        with:
          service: mfe-web
          region: ${{ secrets.GCP_REGION }}
          source: .

      - name: Smoke tests
        run: bash scripts/smoke/smoke.sh
        env:
          BASE_URL: ${{ steps.deploy.outputs.url }}

      - name: Upload smoke logs (optional)
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: smoke-logs
          path: |
            ./*.log
            ./smoke-results/**

Making Smoke Tests Reliable​

  • Prefer idempotent, read-only checks.
  • Avoid depending on third-party systems unless necessary.
  • Use stable test data (seeded fixtures) for predictable responses.
  • Keep runtime short (target: under 2 minutes).

Deployment Status Definition​

A deployment is considered successful when all are true:

  • Platform health checks pass (container is serving)
  • Smoke test scripts pass against the deployed URL
  • No immediate regression signals (basic error rate spike) are detected during the initial watch window

Evidence​

To demonstrate this practice exists:

  • Smoke scripts are committed to the repo.
  • Deployment workflow runs smoke tests after deploy.
  • CI stores smoke logs and links them to the deployment.
  • Team can point to recent deployments where smoke tests determined pass/fail.
