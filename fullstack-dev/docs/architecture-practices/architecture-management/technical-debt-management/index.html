Technical Debt Monitoring & Reduction Plan (Next.js Microfrontends)

Technical debt (also known as tech debt or code debt) is the cost of prioritizing speed of delivery over “doing it right” (refactoring, automation, quality, and maintainability). In a Next.js microfrontend architecture, debt accumulates across the shell and each remote; unmanaged debt typically increases incident rate, slows feature delivery, and degrades user experience.

This document defines a practical approach to continuously monitor technical debt and to reduce it through a planned backlog, sprint capacity allocation, and automated enforcement in GitHub Actions.

Objectives​

  • Make technical debt visible and measurable.
  • Prevent debt from increasing over time (quality gates).
  • Maintain an explicit plan to reduce debt in upcoming sprints.
  • Ensure every item has an owner and is tracked in Jira/ADO.

Scope​

Applies to:

  • Next.js microfrontend shell + each remote (Module Federation or equivalent)
  • Shared UI/component libraries used by multiple remotes
  • Tooling and platform code that affects frontend delivery (build pipeline, caching, CDN config)
  • GCP runtime and edge setup affecting user-perceived performance (Cloud Run/GKE, Load Balancer, Cloud CDN)

What Counts as Technical Debt​

Debt should be recorded when it has a clear “interest payment” (time or risk) and there is a known better option.

Common categories:

  • Code debt: complexity, duplication, inconsistent patterns, poor modular boundaries
  • Test debt: missing unit/integration tests, flaky tests, missing contract tests between microfrontends
  • Dependency debt: outdated packages, security patches pending, multiple versions of React/shared libs across remotes
  • Performance debt: oversized bundles, long main-thread tasks, unnecessary client JS, unoptimized images/fonts
  • Platform/CI debt: slow builds, missing caching, manual release steps, unreliable preview environments
  • Observability debt: missing frontend error reporting, missing Core Web Vitals tracking, weak SLO alignment

Monitoring Sources (Signals)​

CI signals (GitHub Actions)​

  • ESLint/TypeScript: lint and typecheck must be clean
  • Unit tests: stable + fast feedback
  • Dependency and vulnerability scanning (npm audit / SCA)
  • Bundle size tracking per microfrontend (per route when possible)
  • Frontend performance budgets (Lighthouse CI / PageSpeed)

Production signals (GCP + RUM)​

  • Error rate and JS exceptions (RUM / logging)
  • Core Web Vitals (field): LCP / INP / CLS trends
  • TTFB and cache-hit ratio at the edge (LB/CDN logs)
  • Incident and support ticket volume linked to frontend releases

Technical Debt Register (Ticket System)​

Every technical debt item must be a ticket (Jira or Azure DevOps). A “list in a doc” is not sufficient.

Minimum required ticket fields:

  • Type: Tech Debt
  • Component: Shell / Remote name / Shared library
  • Owner: individual + owning team
  • Why it exists: trade-off made, context, constraints
  • Impact: user impact, delivery impact, operational risk
  • Evidence: link to CI report, Lighthouse report, error dashboard, or incident
  • Definition of done: measurable outcome (e.g., bundle reduced, test added, deprecation removed)
  • Target sprint / milestone: explicit plan

Recommended labels:

  • tech-debt, mfe-shell, mfe-remote:<name>, performance, dependencies, tests, ci.

Planning: How Debt Gets Fixed​

Capacity allocation​

  • Allocate a standing budget each sprint for debt reduction (typical starting point: 10–20%).
  • Debt items must compete with features using a consistent prioritization method (impact vs. effort).

Triage cadence​

  • Weekly: review newly detected debt (from CI scans, incidents, regression reports)
  • Sprint planning: commit debt items into the sprint backlog with clear owners
  • Monthly: review debt trends (is the total debt increasing?) and adjust gates/budgets

Prioritization model (simple)​

  • High impact + low effort: fix immediately
  • High impact + high effort: create an epic/initiative; split into increments
  • Low impact + low effort: bundle with nearby work
  • Low impact + high effort: defer, but keep visible with rationale

GitHub Actions Enforcement (Examples)​

The goal is not “fail PRs for everything,” but to stop new debt and to expose trends early.

Example 1: Debt signals + artifacts​

name: frontend-quality-gates

on:
	pull_request:

permissions:
	contents: read

jobs:
	quality:
		runs-on: ubuntu-latest
		steps:
			- uses: actions/checkout@v4

			- uses: actions/setup-node@v4
				with:
					node-version: 20
					cache: pnpm

			- name: Install
				run: pnpm install --frozen-lockfile

			- name: Lint
				run: pnpm lint

			- name: Typecheck
				run: pnpm typecheck

			- name: Unit tests
				run: pnpm test -- --ci

			- name: Bundle analysis (example)
				run: pnpm build:analyze

			- name: Upload bundle report
				uses: actions/upload-artifact@v4
				with:
					name: bundle-report
					path: .next/analyze

Example 2: Enforce “no new high severity debt”​

If you use SonarQube/SonarCloud or an equivalent static analysis tool, configure it so PRs fail when new issues exceed thresholds.

Minimum recommended gates:

  • Block on new critical vulnerabilities
  • Block on new high complexity hotspots in changed files
  • Block on new bundle size regression beyond agreed budget

Microfrontend-Specific Debt Controls​

  • Shared dependency alignment: enforce single React version and shared libs across remotes.
  • Ownership boundaries: each remote owns its routes and performance budgets.
  • Integration contracts: define a stable interface between shell and remotes (events, props, runtime contracts) and test it.

Reporting: Are We Getting Better?​

Track trends monthly (at minimum):

  • Count of debt tickets opened vs. closed
  • Total time-to-close for debt tickets
  • Bundle size trends per microfrontend
  • Performance budgets pass rate on PRs
  • Production regressions correlated to releases

Success Criteria​

  • Debt backlog is visible (ticketed) and reviewed regularly.
  • Debt does not trend upward over time.
  • Each sprint includes committed debt reduction work.
  • New high-severity debt is prevented via CI gates.
