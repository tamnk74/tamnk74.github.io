Test Automation Strategy Plan & Periodic Review (Next.js/NestJS + Playwright)

This document defines how to plan, implement, and continuously improve test automation for a Next.js microfrontend application and NestJS backend services running on Google Cloud Platform (GCP), with Playwright-based E2E automation and enforcement through GitHub Actions.

This item is satisfied when:

  • There is an explicit plan for what automation to build next (not ad-hoc tests).
  • The plan is followed (work is ticketed and delivered incrementally).
  • The plan is reviewed periodically in recurring meetings, and the outcome updates the plan.

Reference: Martin Fowler’s Practical Test Pyramid: https://martinfowler.com/articles/practical-test-pyramid.html

Principles​

  • Automation is a product capability: it is planned, prioritized, and reviewed.
  • Prefer fast feedback: automate as low in the pyramid as possible.
  • Automate critical business flows first.
  • Prevent regressions in PRs via CI gates.
  • Keep tests reliable: reduce flakiness before adding more tests.

Scope​

Applies to:

  • Next.js microfrontend shell and each remote
  • Shared UI libraries and cross-MFE navigation/events
  • NestJS API endpoints and service-to-service contracts
  • GCP preview environments (ephemeral) and production verification signals

Test Pyramid for This Stack​

Use the pyramid to decide what to automate first.

LayerWhat it validatesTypical tools (examples)Target share
UnitFunctions/classes/components in isolationJest/Vitest, Testing Library~60–80%
IntegrationComponent/module + real dependencies (DB, Redis) or API-level integrationSupertest, Testcontainers, contract tests~15–30%
E2EFull user flows across MFEs + backendPlaywright~5–15%

The exact percentage is less important than the intent: build most confidence cheaply (unit/integration) and reserve E2E for the highest-value flows.

What “Having a Plan” Means (Artifacts)​

Required artifacts​

  • Test Automation Strategy doc (this doc) with priorities and guardrails
  • Automation backlog in Jira/ADO (epics + stories) with owners
  • Coverage map for critical journeys (what is automated at which layer)
  • CI pipeline definition in GitHub Actions (as code)

Recommended repository structure​

apps/
  shell/
  product-remote/
  cart-remote/
  checkout-remote/
services/
  api-gateway/
  catalog-service/
  order-service/
e2e/
  playwright.config.ts
  tests/
  pages/
  fixtures/

Prioritization: What to Automate First​

Start with the smallest set that protects revenue and user trust.

Critical business flows (baseline)​

  • Login / session refresh
  • Product search + product detail
  • Add to cart
  • Checkout (happy path)
  • Payment confirmation

Next tier flows​

  • Returns/refunds (if applicable)
  • Address management
  • Promotions/coupons
  • Order history

Microfrontend-specific cases​

  • Shell-to-remote navigation (routing, shared layout)
  • Cross-remote state propagation (cart count, auth state)
  • Remote failure handling (timeout, degraded mode)

Implementation Plan (Phased)​

Phase 0: Foundations (1–2 sprints)​

  • Define environments: local, preview (PR), staging (optional), production
  • Establish test data strategy (seeded fixtures, deterministic IDs)
  • Implement stable selectors (data-testid) and page objects
  • Add CI workflow scaffolding (Playwright install, artifacts)

Deliverable:

  • Playwright can run headless in CI for at least one smoke flow.

Phase 1: Protect critical flows (2–4 sprints)​

  • Implement smoke suite (5–10 tests) that runs on every PR
  • Implement nightly/regression suite for broader coverage
  • Add flake tracking (quarantine tests with ticket + owner)

Deliverable:

  • PRs are blocked if a critical flow breaks.

Phase 2: Expand coverage and reduce cost (ongoing)​

  • Move assertions down the pyramid when possible
  • Replace expensive E2E checks with integration/contract tests
  • Add visual regression only for high-risk pages/components

Deliverable:

  • E2E suite stays small and stable; confidence increases over time.

GCP Preview Environments for E2E​

E2E tests are most valuable when run against a preview deployment that matches production configuration.

Recommended approach:

  • Deploy an ephemeral preview per PR (Cloud Run or GKE)
  • Use a dedicated test tenant/project or isolated namespace
  • Inject config via environment variables and Secret Manager
  • Make preview URLs discoverable to CI (outputs)

GitHub Actions (Playwright) Example​

This is a reference workflow showing the minimum expected behaviors:

  • Install dependencies
  • Deploy preview to GCP
  • Run Playwright
  • Upload artifacts for debugging
name: e2e-playwright

on:
  pull_request:

permissions:
  contents: read
  id-token: write

jobs:
  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 60

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install
        run: pnpm install --frozen-lockfile

      - name: Build
        run: pnpm build

      - name: Auth to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WIF_PROVIDER }}
          service_account: ${{ secrets.GCP_SA_EMAIL }}

      - name: Deploy preview (example)
        uses: google-github-actions/deploy-cloudrun@v2
        with:
          service: mfe-preview-${{ github.event.number }}
          region: ${{ secrets.GCP_REGION }}
          source: .

      - name: Install Playwright browsers
        run: pnpm exec playwright install --with-deps

      - name: Run Playwright smoke suite
        run: pnpm exec playwright test --grep @smoke
        env:
          BASE_URL: ${{ steps.deploy.outputs.url }}

      - name: Upload Playwright report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/

Notes:

  • Keep @smoke small (fast, stable, high-signal).
  • Store the preview URL as an output and pass it via BASE_URL.
  • Always upload artifacts to debug flakes quickly.

Periodic Review (Meetings)​

Required cadence​

  • Weekly (15–30 min): Automation Triage

    • Review flakiness and failures
    • Decide what to fix, quarantine, or delete
    • Confirm upcoming sprint automation items are ready

  • Monthly (45–60 min): Automation Strategy Review

    • Review pyramid balance (are we over-relying on E2E?)
    • Review critical flow coverage and gaps
    • Review CI runtime and cost
    • Update the automation plan and backlog priorities

Review inputs (required)​

  • CI metrics: pass rate, flake rate, duration
  • List of top failing tests and root causes
  • Coverage map for critical flows
  • Recent incidents/bugs that escaped (and what automation would have caught them)

Review outputs (required)​

  • Updated automation backlog (Jira/ADO)
  • Updated test suite scope (smoke vs nightly)
  • Decisions recorded (what to stop doing, what to invest in next)

Evidence Checklist​

To prove this practice is in place, provide:

  • Link to automation backlog epic(s) in Jira/ADO
  • Last 2 meeting notes (weekly triage + monthly review)
  • CI workflow links and recent runs
  • Playwright report artifacts (example run)
  • A small, stable smoke suite protecting critical flows
