Infrastructure Alerting & Incident Response (24/7)

This guide defines how a NestJS-based platform on GCP monitors infrastructure 24/7 and ensures the team can take action immediately when alerts fire (acknowledge, escalate, fix, and document).

Goal​

  • Detect infrastructure issues quickly (CPU, memory, disk, availability, response time, saturation).
  • Alert the right people with the right severity.
  • Provide an actionable workflow (runbooks + ownership + escalation) so alerts result in remediation.

Scope (GCP)​

  • Compute: GKE / Cloud Run / VM-based workloads
  • Data: Cloud SQL / Memorystore
  • Network: Load Balancer / Cloud Armor / VPC
  • Messaging: Pub/Sub backlog (if used)
  • Observability: Cloud Monitoring, Cloud Logging, Error Reporting

Operating Model (What “team can take action” means)​

When an alert fires:

  1. Acknowledge within the target time (e.g., 5 minutes for P1/P2).
  2. Triage: confirm impact, identify likely component(s).
  3. Escalate if needed (page on-call, add service owner, open incident bridge).
  4. Mitigate: roll back / scale / restart / failover / apply runbook.
  5. Communicate: post status updates to the agreed channel.
  6. Close & learn: incident summary + follow-ups (postmortem for P1/P2).

Alert Severity & SLAs​

Define severity consistently so responders know what to do.

SeverityExampleAcknowledgeMitigateNotes
P1Total outage / checkout down5 min30 minPage on-call immediately
P2Partial outage / major latency10 min2 hoursEscalate to service owner
P3Degradation / rising error rate30 min1 business dayTicket is acceptable
P4Informational / capacity trendN/AN/ANo paging; track trend

Reference Architecture​

What To Monitor (Baseline)​

1) Availability & Latency​

  • Public endpoints: uptime checks (HTTP 200 + content match)
  • API latency: P95/P99 response time
  • Load balancer: backend health

2) Compute Saturation​

  • CPU utilization
  • Memory utilization
  • Container restarts / crash loops
  • GKE node pressure / pod scheduling failures

3) Disk / Storage​

  • Cloud SQL disk usage / auto-storage nearing limits
  • Persistent volumes usage

4) Data Layer​

  • Cloud SQL connection count, replica lag, slow queries
  • Memorystore evictions / memory pressure

5) Messaging / Queue Backlog​

  • Pub/Sub unacked messages and oldest unacked age

GCP Cloud Monitoring: Alert Policy Examples​

Example: Cloud Run High Latency (P2)​

# terraform/monitoring/alert_cloud_run_latency.tf
resource "google_monitoring_alert_policy" "cloud_run_latency_p95" {
  display_name = "P2 - Cloud Run latency p95 high"
  combiner     = "OR"

  conditions {
    display_name = "Latency p95 > 800ms for 10m"
    condition_threshold {
      filter          = "resource.type=\"cloud_run_revision\" AND metric.type=\"run.googleapis.com/request_latencies\""
      duration        = "600s"
      comparison      = "COMPARISON_GT"
      threshold_value = 0.8

      aggregations {
        alignment_period     = "60s"
        per_series_aligner   = "ALIGN_PERCENTILE_95"
        cross_series_reducer = "REDUCE_MEAN"
      }
    }
  }

  notification_channels = [
    google_monitoring_notification_channel.pagerduty.id,
    google_monitoring_notification_channel.slack.id,
  ]

  user_labels = {
    severity = "P2"
    owner    = "platform"
    runbook  = "https://runbooks.example.com/cloud-run/latency"
  }
}

Notification Channels (Actionable Routing)​

Use at least two channels:

  • Paging (PagerDuty/Opsgenie): P1/P2 only
  • Chat (Slack/Google Chat): all severities

Optional but recommended:

  • Pub/Sub notification channel to route alerts into automation (ticket creation, incident system).

NestJS: Incident Intake API (So alerts become tasks)​

Use a small NestJS “incident gateway” that receives alert payloads (via Cloud Function router) and turns them into:

  • a persisted incident record
  • an assignment (team/owner)
  • a Slack message thread link
  • a ticket (Jira/Linear)

Controller + Service (minimal)​

// src/incident/incident.controller.ts
import { Body, Controller, Post } from '@nestjs/common';

export type AlertSeverity = 'P1' | 'P2' | 'P3' | 'P4';

export interface AlertEventDto {
  source: 'cloud-monitoring';
  policyName: string;
  severity: AlertSeverity;
  summary: string;
  resource?: Record<string, string>;
  runbookUrl?: string;
  incidentUrl?: string;
  startedAt: string;
}

@Controller('api/incidents')
export class IncidentController {
  constructor(private readonly incidentService: IncidentService) {}

  @Post('from-alert')
  async ingest(@Body() dto: AlertEventDto) {
    return this.incidentService.ingestAlert(dto);
  }
}

// src/incident/incident.service.ts
import { Injectable, Logger } from '@nestjs/common';

@Injectable()
export class IncidentService {
  private readonly logger = new Logger(IncidentService.name);

  async ingestAlert(dto: any) {
    // 1) Validate + normalize
    // 2) Deduplicate (same policy + resource + active window)
    // 3) Persist incident (DB)
    // 4) Notify the right channel (Slack/PagerDuty)

    this.logger.warn(`[${dto.severity}] ${dto.policyName}: ${dto.summary}`);

    return {
      status: 'accepted',
      severity: dto.severity,
      policyName: dto.policyName,
      runbookUrl: dto.runbookUrl,
    };
  }
}

Cloud Function “Alert Router” (Recommended)​

If you use Pub/Sub notification channel, route alerts through a Cloud Function:

  • Parse Cloud Monitoring incident payload
  • Map policy → severity/team
  • Post to Slack
  • Call NestJS incident intake
// functions/alert-router/index.js
const fetch = global.fetch;

exports.routeAlert = async (message, context) => {
  const payload = JSON.parse(Buffer.from(message.data, 'base64').toString('utf8'));

  // Normalize (shape differs depending on channel)
  const event = {
    source: 'cloud-monitoring',
    policyName: payload.incident?.policy_name || 'unknown',
    severity: payload.incident?.policy_user_labels?.severity || 'P3',
    summary: payload.incident?.summary || 'No summary',
    incidentUrl: payload.incident?.url,
    startedAt: payload.incident?.started_at || new Date().toISOString(),
    runbookUrl: payload.incident?.policy_user_labels?.runbook,
  };

  // Send to NestJS
  await fetch(process.env.INCIDENT_API_URL, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(event),
  });

  // Optional: post to Slack
  if (process.env.SLACK_WEBHOOK_URL) {
    await fetch(process.env.SLACK_WEBHOOK_URL, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        text: `[${event.severity}] ${event.policyName} — ${event.summary}\n${event.incidentUrl || ''}`,
      }),
    });
  }
};

Runbooks (Make Alerts Fixable)​

Every P1/P2 alert must include a runbook link. A runbook should answer:

  • What does this alert mean?
  • How to confirm impact?
  • Immediate mitigations (scale, restart, rollback)
  • Long-term fix and owner

Example runbook template:

# Runbook: Cloud SQL Disk Usage High

## Symptoms

- Alert: disk utilization > 85% for 15m

## Confirm

- Check Cloud SQL metrics: disk utilization, storage auto-increase
- Check recent migrations / large backfills

## Mitigate (order)

1. Pause heavy jobs/backfills
2. Increase storage / enable auto storage increase
3. Purge old data if safe

## Escalate

- Data Platform on-call

## Recovery Verification

- Disk < 75% for 30m
- No app errors / DB latency normal

GitHub Actions: Monitoring-as-Code Validation​

Track alert policies/dashboards in code (Terraform recommended). In CI, validate that monitoring config changes are reviewed and syntactically correct.

# .github/workflows/monitoring-validation.yml
name: Monitoring Validation

on:
  pull_request:
    paths:
      - 'terraform/monitoring/**'
      - '.github/workflows/monitoring-validation.yml'

jobs:
  terraform-validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - name: Terraform fmt
        run: terraform fmt -check -recursive
      - name: Terraform validate (monitoring)
        working-directory: terraform/monitoring
        run: |
          terraform init -backend=false
          terraform validate

Optional: Require at least one of (pager + chat) notification channels for P1/P2 policies via code review checklist or policy-as-code.

Minimum Acceptance Criteria​

  • 24/7 alert coverage for availability, latency, CPU, memory, disk, and error rates.
  • P1/P2 pages an on-call responder and posts to a team channel.
  • Every P1/P2 alert includes an owner + runbook link.
  • Alerts are deduplicated and actionable (no noisy flapping).
  • Incidents are tracked (ticket or incident record) with postmortems for P1/P2.
