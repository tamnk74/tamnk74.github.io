OWASP Top 10 2025 Training

Overview​

This document defines how to implement an OWASP Top 10 2025 training track with module definitions, hands-on labs, and assessments aligned to common NestJS/Next.js application risks.

Updated for OWASP Top 10 2025: This training reflects the latest 2025 release with updated rankings, two new categories (Software Supply Chain Failures, Mishandling of Exceptional Conditions), and renamed categories.

Objectives​

  • Build shared language for OWASP Top 10 risks and mitigations
  • Teach engineers to spot issues during design, implementation, and code review
  • Practice secure patterns in NestJS (APIs) and Next.js (web)
  • Establish measurable outcomes (completion rate, pass rate, remediation impact)

If you are implementing a training platform/service, pair this track with training-management-service.md for the training catalog and progress tracking contract.

Audience and prerequisites​

Audience:

  • Backend engineers (NestJS)
  • Frontend engineers (Next.js)
  • QA/automation engineers
  • SRE/DevOps (reviewers of auth, secrets, and deployment practices)

Prerequisites (recommended):

  • Basic web security concepts (HTTP, cookies, sessions, tokens)
  • Familiarity with the team's auth model and API patterns
  • Ability to run the application locally and execute tests

Track structure​

Format:

  • 10 modules aligned to OWASP Top 10 (A01-A10)
  • Each module includes: concept briefing, examples, lab, and short assessment

Suggested delivery:

  • New joiners: complete A01-A10 within 30-60 days
  • Ongoing: 1 module per month (or 2 per quarter)

Passing standard (default):

  • Quiz: at least 80%
  • Lab: completed checklist plus reviewer sign-off

Evidence captured:

  • Learner identity, module ID, completion date
  • Score (quiz) and lab completion record (checklist, PR link, or reviewer sign-off)
  • Optional certificate ID if your program issues certificates

A01:2025 - Broken Access Control (includes SSRF)​

Note: In OWASP 2025, Server-Side Request Forgery (SSRF) has been rolled into this category.

Focus:

  • Enforce authorization server-side for every sensitive action
  • Prevent IDOR (Insecure Direct Object References)
  • Avoid client-side only checks
  • NEW: Prevent SSRF attacks through URL validation and network access controls

NestJS/Next.js patterns to practice:

  • Centralized authorization (guards/policies) with resource-based checks
  • Tenant isolation checks for multi-tenant systems
  • Consistent 401/403 behavior and tests

Lab (suggested):

  • Pick a resource endpoint (read and write).
  • Add explicit authorization checks for: owner, role, and tenant.
  • Add tests for: unauthenticated, wrong-tenant, wrong-role.
  • NEW: If endpoint fetches external URLs, add URL validation and allowlist checks.

Assessment prompts:

  • Identify an IDOR risk in a handler and propose the fix.
  • Explain why UI checks are insufficient.
  • NEW: List three SSRF attack vectors and their mitigations.

A02:2025 - Security Misconfiguration​

Note: Moved from #5 to #2 in 2025 due to increased prevalence as software becomes more configuration-driven.

Focus:

  • Secure defaults and hardened configurations across app, infra, and CI/CD
  • Disabling debug endpoints and unsafe error disclosure
  • Proper environment separation and secrets management

NestJS/Next.js patterns to practice:

  • Error handling that does not leak stack traces or secrets
  • Security headers baseline appropriate for your application
  • Least-privilege runtime configuration and environment separation
  • Never expose sensitive environment variables to client

Lab (suggested):

  • Verify production defaults (debug off, safe error pages).
  • Add/verify HTTP security headers (Helmet.js).
  • Confirm no sensitive debug endpoints are exposed.
  • Audit environment variable exposure (server-side only).

Assessment prompts:

  • Identify a configuration that increases attack surface and propose a safer default.
  • List common misconfiguration risks in cloud storage, containers, and APIs.

A03:2025 - Software Supply Chain Failures​

Note: NEW category in 2025. Expands "Vulnerable and Outdated Components" to cover broader supply chain risks including build systems and distribution infrastructure.

Focus:

  • Reduce risk from vulnerable dependencies and compromised build systems
  • Understand transitive dependency exposure and supply chain attacks
  • Secure CI/CD pipelines and artifact distribution
  • Verify package integrity and provenance

NestJS/Next.js patterns to practice:

  • Lockfile discipline and reproducible installs
  • Dependency scanning in CI with defined triage process
  • SBOM (Software Bill of Materials) generation
  • Package integrity verification (checksums, signatures)
  • Secure CI/CD with protected branches and required checks
  • SLSA framework implementation for supply chain security

Lab (suggested):

  • Pick a dependency alert (or create a simulated one).
  • Upgrade the package and document: impact assessment, tests run, rollback plan.
  • Add CI gate to verify lockfile integrity on changes.
  • Configure Dependabot or Renovate for automated updates.
  • Generate SBOM for your application.

Assessment prompts:

  • Explain direct vs transitive dependency risk.
  • Describe how to decide between patching, upgrading, or replacing.
  • List three supply chain attack vectors (e.g., typosquatting, compromised maintainer, malicious package).
  • How does SLSA framework improve supply chain security?

A04:2025 - Cryptographic Failures​

Note: Moved from #2 to #4 in 2025 rankings.

Focus:

  • Secure transport and storage of sensitive data
  • Correct use of modern crypto primitives and key management
  • Avoid weak hashing for passwords or secrets

NestJS/Next.js patterns to practice:

  • TLS-only endpoints and secure cookie attributes
  • Password hashing with bcrypt/Argon2 (not MD5/SHA1)
  • Key management via secret manager/KMS (not in code or env files)
  • AES-256-GCM for encryption (not weak algorithms)

Lab (suggested):

  • Identify data fields that should be encrypted at rest (or tokenized).
  • Verify secure cookie settings for session/auth cookies.
  • Rotate a non-production secret and document the operational steps.
  • Audit password hashing implementation.

Assessment prompts:

  • When do you hash vs encrypt?
  • Where do keys live and how are they rotated?
  • Why are MD5 and SHA1 insufficient for passwords?

A05:2025 - Injection​

Note: Moved from #3 to #5 in 2025 rankings.

Focus:

  • SQL/NoSQL injection, command injection, and unsafe templating patterns
  • Input validation and safe query construction

NestJS/Next.js patterns to practice:

  • Parameterized queries/ORM safe APIs
  • Validation and normalization at boundaries (DTO validation)
  • Escaping/encoding rules for template output

Lab (suggested):

  • Fix an injected query example and add regression tests.
  • Add validation to an endpoint and confirm correct rejection behavior.

Assessment prompts:

  • Spot string concatenation risks in data access code.
  • Explain defense in depth (validation plus parameterization).

A06:2025 - Insecure Design​

Note: Moved from #4 to #6 in 2025. Industry showing improvements in threat modeling and secure design.

Focus:

  • Threat modeling and secure-by-design requirements
  • Abuse case thinking for flows like checkout, login, refunds, promotions

NestJS/Next.js patterns to practice:

  • Document trust boundaries and invariants (what must always be true)
  • Rate limits and anti-automation controls on high-risk flows
  • Replay protection for sensitive actions (idempotency)

Lab (suggested):

  • Create a lightweight threat model for one feature:
    • assets, entry points, trust boundaries, top threats, mitigations.
  • Add at least one mitigation (e.g., rate limit, invariant checks) and tests.

Assessment prompts:

  • Given a feature, list 3 abuse cases and mitigations.

A07:2025 - Authentication Failures​

Note: Remains at #7, renamed from "Identification and Authentication Failures" to better reflect the category focus. Industry showing improvements due to increased use of standardized authentication frameworks.

Focus:

  • Correct authentication flows and session handling
  • Prevent account takeover through secure defaults

NestJS/Next.js patterns to practice:

  • Secure cookie/session settings aligned to your deployment
  • Consistent token validation and expiration handling
  • Brute-force protections and MFA support where applicable

Lab (suggested):

  • Validate secure cookie attributes for auth/session cookies.
  • Add tests for invalid/expired tokens and replay attempts.

Assessment prompts:

  • When should you use cookies vs bearer tokens?
  • List three common auth implementation mistakes and mitigations.

A08:2025 - Software or Data Integrity Failures​

Note: Continues at #8. Focuses on lower-level integrity verification compared to A03 Supply Chain Failures.

Focus:

  • Protect build and deployment integrity (supply chain)
  • Prevent unsafe updates and untrusted artifacts

NestJS/Next.js patterns to practice:

  • Protected branches and required CI checks
  • Artifact provenance and immutable builds
  • Least-privilege deploy credentials and separation of duties

Lab (suggested):

  • Add a CI gate that enforces required checks before deploy.
  • Add an integrity check for lockfile changes (policy + review).

Assessment prompts:

  • Identify common CI/CD misconfigurations that enable tampering.

A09:2025 - Security Logging & Alerting Failures​

Note: Remains at #9, renamed from "Security Logging and Monitoring Failures" to emphasize the importance of alerting. Great logging without alerting has minimal value in identifying security incidents.

Focus:

  • Detect and respond to suspicious activity
  • Ensure logs are useful for investigations without leaking secrets
  • Implement real-time alerting - crucial for timely incident response

NestJS/Next.js patterns to practice:

  • Structured security event logging (auth failures, access denials, admin actions)
  • Correlation identifiers for traceability
  • Real-time alerting on anomalous patterns (rate spikes, repeated failures)
  • Automated alerting workflows and runbooks

Lab (suggested):

  • Add structured logs for failed authz decisions.
  • Define an alert for repeated suspicious events and document runbook steps.

Assessment prompts:

  • Explain how logs support incident response and forensics.

A10:2025 - Mishandling of Exceptional Conditions​

Note: NEW category in 2025. Focuses on improper error handling, logical errors, and failing open scenarios (24 CWEs).

Focus:

  • Fail securely (default to deny on errors)
  • Proper error handling without information disclosure
  • Handle race conditions and null/undefined safely
  • Prevent application crashes from unhandled exceptions

NestJS/Next.js patterns to practice:

  • Secure error handling that defaults to deny access on failures
  • Generic error messages for users, detailed logs server-side only
  • TypeScript strict mode and proper null/undefined checks
  • Exception handling in all async operations
  • Circuit breakers for external dependencies
  • Proper handling of edge cases and boundary conditions

Lab (suggested):

  • Identify "fail open" patterns in access control code and fix to "fail closed".
  • Audit error messages for sensitive information disclosure (stack traces, SQL queries, file paths).
  • Add proper error handling to async operations with tests for error paths.
  • Implement TypeScript strict mode and fix null/undefined issues.

Assessment prompts:

  • What is "failing open" vs "failing closed"? Which is more secure?
  • Why should production error messages be generic?
  • List three ways improper error handling can lead to security issues.
  • How do race conditions relate to security?

Track-level assessment​

Recommended track-level checkpoint (choose one):

  • Code review exercise: learner reviews a PR that includes multiple OWASP issues and writes the review
  • Practical exercise: learner implements two mitigations (e.g., authz + input validation) with tests

Passing rule (default):

  • Completed module quizzes and labs, plus passed the track-level checkpoint

Operational checklist​

  • Define required modules per role (developer, QA, SRE/DevOps, security)
  • Define passing scores and certification rules per module/track
  • Track evidence (completion date, score, reviewer sign-off, certificate ID)
  • Publish cadence (monthly sessions + annual refresh)
  • Generate weekly/monthly reports for managers and security champions

  • Team secure coding standards and code review checklists
  • Recent incident/postmortem learnings to prioritize modules
