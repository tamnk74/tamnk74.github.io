SANS CWE Top 25 Training

Overview​

This document provides a comprehensive reference implementation for a secure coding training track aligned to the 2025 SANS/CWE Top 25 Most Dangerous Software Weaknesses. The training program includes modular content, hands-on labs, assessments, and workshop formats designed for e-commerce development teams.

The CWE Top 25 list is compiled by MITRE and SANS Institute based on real-world vulnerability data from the National Vulnerability Database (NVD). These weaknesses are responsible for the majority of serious software vulnerabilities exploited in the wild.

Training Objectives​

  • Identify the most critical security weaknesses in modern web applications
  • Understand exploitation techniques and real-world attack scenarios
  • Implement secure coding practices to prevent CWE Top 25 vulnerabilities
  • Apply defense-in-depth strategies across the application stack
  • Validate security controls through code review and testing

Web Application Focus​

For e-commerce and web applications (Node.js, React, NestJS stack), we prioritize training on the most relevant CWEs:

  • Injection Flaws: CWE-79, CWE-89, CWE-78, CWE-77, CWE-94
  • Authentication/Authorization: CWE-352, CWE-862, CWE-863, CWE-306, CWE-284, CWE-639
  • Input Validation & File Handling: CWE-20, CWE-22, CWE-434
  • Data Security: CWE-502, CWE-918, CWE-200
  • Resource Management: CWE-770
  • Memory Safety (for native modules): CWE-787, CWE-125, CWE-416, CWE-476, CWE-120, CWE-121, CWE-122

Key Changes in 2025 Rankings​

Notable movements in the 2025 CWE Top 25:

  • CWE-352 (CSRF) moved up to #3 (from #4)

  • CWE-120 (Classic Buffer Overflow) is new to the list at #11

  • CWE-287, CWE-190, CWE-119, CWE-798, CWE-362, CWE-269, CWE-276 are no longer in the top 25

Detailed CWE Explanations​

1. CWE-79: Cross-site Scripting (XSS)​

Explanation: XSS occurs when an application includes untrusted data in a web page without proper validation or escaping. Attackers can execute malicious scripts in the victim's browser to steal session tokens, deface websites, or redirect users to malicious sites.

Example:

// ❌ VULNERABLE: Direct insertion of user input
function displayComment(comment: string) {
  document.getElementById('comments').innerHTML = comment;
}

// ✅ SECURE: Use React's JSX auto-escaping
function CommentDisplay({ comment }: { comment: string }) {
  return <div>{comment}</div>; // Automatically escaped
}

// ✅ SECURE: Manual sanitization when needed
import DOMPurify from 'dompurify';
function displayRichComment(htmlComment: string) {
  const clean = DOMPurify.sanitize(htmlComment);
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

Reference: CWE-79: Cross-site Scripting

2. CWE-89: SQL Injection​

Explanation: SQL Injection occurs when an application constructs SQL queries using untrusted input without proper sanitization, allowing attackers to manipulate database queries to access, modify, or delete data.

Example:

// ❌ VULNERABLE: String concatenation
async function getUser(username: string) {
  const query = `SELECT * FROM users WHERE username = '${username}'`;
  return await db.query(query);
}

// ✅ SECURE: Parameterized queries with TypeORM
async function getUser(username: string) {
  return await this.userRepository.findOne({
    where: { username },
  });
}

// ✅ SECURE: Query builder with parameters
async function searchUsers(name: string) {
  return await this.userRepository.createQueryBuilder('user').where('user.name = :name', { name }).getMany();
}

Reference: CWE-89: SQL Injection

3. CWE-787: Out-of-bounds Write​

Explanation: Writing data outside the bounds of allocated memory can corrupt data, crash programs, or allow code execution. This is primarily a concern in lower-level languages but can occur in Node.js native modules.

Example:

// ❌ VULNERABLE: Buffer overflow in native module (C++)
// Not common in pure TypeScript/JavaScript

// ✅ SECURE: Use Buffer.alloc with size checks
function createBuffer(size: number, data: string) {
  if (size <= 0 || size > 1024 * 1024) {
    throw new Error('Invalid buffer size');
  }
  const buffer = Buffer.alloc(size);
  buffer.write(data, 0, Math.min(data.length, size));
  return buffer;
}

Reference: CWE-787: Out-of-bounds Write

4. CWE-20: Improper Input Validation​

Explanation: Failure to validate input can lead to various attacks including injection, buffer overflows, and logic errors. All input should be validated against expected format, type, length, and range.

Example:

// ❌ VULNERABLE: No validation
@Post('user')
async createUser(@Body() userData: any) {
  return await this.userService.create(userData);
}

// ✅ SECURE: DTO with validation decorators
import { IsEmail, IsString, Length, Matches } from 'class-validator';

export class CreateUserDto {
  @IsEmail()
  email: string;

  @IsString()
  @Length(8, 100)
  @Matches(/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)/, {
    message: 'Password must contain uppercase, lowercase, and number'
  })
  password: string;

  @IsString()
  @Length(2, 50)
  @Matches(/^[a-zA-Z\s]+$/)
  name: string;
}

@Post('user')
async createUser(@Body() userData: CreateUserDto) {
  return await this.userService.create(userData);
}

Reference: CWE-20: Improper Input Validation

5. CWE-125: Out-of-bounds Read​

Explanation: Reading data outside allocated memory boundaries can expose sensitive information or cause crashes. Like CWE-787, this is more common in native code but can affect Node.js applications using native modules.

Example:

// ✅ SECURE: Safe array access with bounds checking
function getArrayElement<T>(array: T[], index: number): T | undefined {
  if (index < 0 || index >= array.length) {
    return undefined;
  }
  return array[index];
}

// ✅ SECURE: Safe buffer reading
function readBufferSafely(buffer: Buffer, offset: number, length: number): Buffer | null {
  if (offset < 0 || length < 0 || offset + length > buffer.length) {
    return null;
  }
  return buffer.slice(offset, offset + length);
}

Reference: CWE-125: Out-of-bounds Read

6. CWE-78: OS Command Injection​

Explanation: Executing system commands with untrusted input allows attackers to run arbitrary commands on the host operating system.

Example:

// ❌ VULNERABLE: Shell execution with user input
import { exec } from 'child_process';

function processFile(filename: string) {
  exec(`convert ${filename} output.png`, (error, stdout) => {
    // Attacker could use: "file.jpg; rm -rf /"
  });
}

// ✅ SECURE: Use execFile with argument array
import { execFile } from 'child_process';

function processFile(filename: string) {
  // Validate filename first
  if (!/^[a-zA-Z0-9._-]+$/.test(filename)) {
    throw new Error('Invalid filename');
  }

  execFile('convert', [filename, 'output.png'], (error, stdout) => {
    // Safe - no shell interpretation
  });
}

// ✅ BETTER: Use dedicated libraries instead of shell commands
import sharp from 'sharp';

async function processFile(filename: string) {
  await sharp(filename).png().toFile('output.png');
}

Reference: CWE-78: OS Command Injection

7. CWE-416: Use After Free​

Explanation: Accessing memory after it has been freed can lead to crashes or code execution. This is primarily a concern in languages with manual memory management but can occur in native Node.js modules.

Example:

// This is primarily a C/C++ issue, not directly applicable to TypeScript
// However, be aware when using native modules

// ✅ SECURE: Proper resource cleanup in Node.js
class DatabaseConnection {
  private connection: any = null;

  async connect() {
    this.connection = await createConnection();
  }

  async disconnect() {
    if (this.connection) {
      await this.connection.close();
      this.connection = null; // Clear reference
    }
  }

  async query(sql: string) {
    if (!this.connection) {
      throw new Error('Connection not established');
    }
    return await this.connection.query(sql);
  }
}

Reference: CWE-416: Use After Free

8. CWE-22: Path Traversal​

Explanation: Improper limitation of pathname to a restricted directory allows attackers to access files outside the intended directory using sequences like ../.

Example:

// ❌ VULNERABLE: Direct path concatenation
import * as fs from 'fs';
import * as path from 'path';

function readUserFile(filename: string) {
  const filePath = `./uploads/${filename}`;
  return fs.readFileSync(filePath); // Attacker: "../../../etc/passwd"
}

// ✅ SECURE: Path validation
function readUserFile(filename: string) {
  const uploadsDir = path.resolve('./uploads');
  const filePath = path.resolve(uploadsDir, filename);

  // Ensure the resolved path is within uploads directory
  if (!filePath.startsWith(uploadsDir)) {
    throw new Error('Invalid file path');
  }

  return fs.readFileSync(filePath);
}

// ✅ SECURE: Additional filename validation
function readUserFile(filename: string) {
  // Only allow alphanumeric, dash, underscore, and dot
  if (!/^[a-zA-Z0-9._-]+$/.test(filename)) {
    throw new Error('Invalid filename');
  }

  const uploadsDir = path.resolve('./uploads');
  const filePath = path.join(uploadsDir, filename);

  if (!filePath.startsWith(uploadsDir)) {
    throw new Error('Invalid file path');
  }

  return fs.readFileSync(filePath);
}

Reference: CWE-22: Path Traversal

9. CWE-352: Cross-Site Request Forgery (CSRF)​

Explanation: CSRF tricks authenticated users into performing unwanted actions by exploiting their existing session. Attackers craft malicious requests that appear to come from legitimate users.

Example:

// ❌ VULNERABLE: No CSRF protection
@Controller('account')
export class AccountController {
  @Post('transfer')
  async transfer(@Body() data: TransferDto, @Req() req: Request) {
    // Anyone can make this request with user's session
    return await this.bankService.transfer(req.user, data);
  }
}

// ✅ SECURE: CSRF token validation
import * as csurf from 'csurf';

// Enable CSRF middleware
app.use(csurf({ cookie: true }));

@Controller('account')
export class AccountController {
  @Post('transfer')
  async transfer(@Body() data: TransferDto, @Req() req: Request, @Headers('x-csrf-token') csrfToken: string) {
    // Token automatically validated by middleware
    return await this.bankService.transfer(req.user, data);
  }
}

// ✅ SECURE: SameSite cookie attribute
app.use(
  session({
    cookie: {
      sameSite: 'strict',
      httpOnly: true,
      secure: true,
    },
  }),
);

Reference: CWE-352: Cross-Site Request Forgery

10. CWE-434: Unrestricted Upload of File with Dangerous Type​

Explanation: Allowing users to upload files without proper validation can enable attackers to upload malicious files (executables, scripts, web shells) that can be executed on the server.

Example:

// ❌ VULNERABLE: No file type validation
@Post('upload')
@UseInterceptors(FileInterceptor('file'))
async uploadFile(@UploadedFile() file: Express.Multer.File) {
  await fs.writeFile(`./uploads/${file.originalname}`, file.buffer);
  return { filename: file.originalname };
}

// ✅ SECURE: Multi-layer validation
import { FileTypeResult, fileTypeFromBuffer } from 'file-type';
import * as path from 'path';
import { v4 as uuidv4 } from 'uuid';

const ALLOWED_MIME_TYPES = ['image/jpeg', 'image/png', 'image/webp'];
const MAX_FILE_SIZE = 5 * 1024 * 1024; // 5MB

@Post('upload')
@UseInterceptors(FileInterceptor('file', {
  limits: { fileSize: MAX_FILE_SIZE }
}))
async uploadFile(@UploadedFile() file: Express.Multer.File) {
  // 1. Check file size
  if (file.size > MAX_FILE_SIZE) {
    throw new BadRequestException('File too large');
  }

  // 2. Validate MIME type from content (magic bytes)
  const fileType: FileTypeResult = await fileTypeFromBuffer(file.buffer);
  if (!fileType || !ALLOWED_MIME_TYPES.includes(fileType.mime)) {
    throw new BadRequestException('Invalid file type');
  }

  // 3. Generate safe filename
  const ext = fileType.ext;
  const safeFilename = `${uuidv4()}.${ext}`;

  // 4. Store in isolated directory with no execute permissions
  const uploadPath = path.join('./uploads', safeFilename);
  await fs.writeFile(uploadPath, file.buffer);

  return { filename: safeFilename };
}

Reference: CWE-434: Unrestricted Upload of File with Dangerous Type

11. CWE-862: Missing Authorization​

Explanation: Failing to verify that users have permission to access resources or perform actions allows unauthorized access to functionality and data.

Example:

// ❌ VULNERABLE: No authorization check
@Controller('orders')
export class OrderController {
  @Get(':id')
  async getOrder(@Param('id') id: string) {
    return await this.orderService.findById(id);
    // Any authenticated user can view any order!
  }
}

// ✅ SECURE: Resource ownership validation
@Controller('orders')
export class OrderController {
  @Get(':id')
  @UseGuards(JwtAuthGuard)
  async getOrder(@Param('id') id: string, @CurrentUser() user: User) {
    const order = await this.orderService.findById(id);

    if (!order) {
      throw new NotFoundException('Order not found');
    }

    // Verify ownership
    if (order.userId !== user.id && !user.roles.includes('admin')) {
      throw new ForbiddenException('Access denied');
    }

    return order;
  }
}

// ✅ SECURE: Role-based guard
@Injectable()
export class RolesGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const roles = this.reflector.get<string[]>('roles', context.getHandler());
    if (!roles) return true;

    const request = context.switchToHttp().getRequest();
    const user = request.user;

    return roles.some((role) => user.roles?.includes(role));
  }
}

@Controller('admin')
export class AdminController {
  @Get('users')
  @Roles('admin', 'superadmin')
  @UseGuards(JwtAuthGuard, RolesGuard)
  async getAllUsers() {
    return await this.userService.findAll();
  }
}

Reference: CWE-862: Missing Authorization

12. CWE-476: NULL Pointer Dereference​

Explanation: Attempting to access or use a null/undefined reference causes crashes. In TypeScript, this manifests as accessing properties of null or undefined values.

Example:

// ❌ VULNERABLE: No null check
function getUserEmail(userId: string): string {
  const user = this.users.find((u) => u.id === userId);
  return user.email; // Crashes if user is undefined
}

// ✅ SECURE: Null checks
function getUserEmail(userId: string): string | null {
  const user = this.users.find((u) => u.id === userId);
  if (!user) {
    return null;
  }
  return user.email;
}

// ✅ SECURE: Optional chaining
function getUserEmail(userId: string): string | undefined {
  const user = this.users.find((u) => u.id === userId);
  return user?.email;
}

// ✅ SECURE: TypeScript strict null checks
// tsconfig.json: "strictNullChecks": true
function processUser(user: User | null) {
  // TypeScript error if we don't check for null
  if (user === null) {
    throw new Error('User is null');
  }
  console.log(user.email); // Safe
}

Reference: CWE-476: NULL Pointer Dereference

13. CWE-287: Improper Authentication​

Explanation: Weak authentication mechanisms allow attackers to impersonate legitimate users through password guessing, credential stuffing, or bypassing authentication entirely.

Example:

// ❌ VULNERABLE: Weak authentication
import * as crypto from 'crypto';

function login(username: string, password: string) {
  const user = findUser(username);
  const hash = crypto.createHash('md5').update(password).digest('hex');

  if (user && user.passwordHash === hash) {
    return { token: user.id }; // Predictable token
  }
  return null;
}

// ✅ SECURE: Strong authentication
import * as bcrypt from 'bcrypt';
import * as jwt from 'jsonwebtoken';

async function login(username: string, password: string) {
  // Rate limiting (use express-rate-limit or similar)

  const user = await findUser(username);
  if (!user) {
    // Generic error to prevent user enumeration
    throw new UnauthorizedException('Invalid credentials');
  }

  // Check account status
  if (user.locked || !user.emailVerified) {
    throw new UnauthorizedException('Account unavailable');
  }

  // Verify password with bcrypt
  const isValid = await bcrypt.compare(password, user.passwordHash);
  if (!isValid) {
    await this.incrementFailedAttempts(user.id);
    throw new UnauthorizedException('Invalid credentials');
  }

  // Reset failed attempts
  await this.resetFailedAttempts(user.id);

  // Generate secure JWT token
  const accessToken = jwt.sign({ userId: user.id, email: user.email }, process.env.JWT_SECRET, { expiresIn: '15m' });

  const refreshToken = jwt.sign({ userId: user.id, type: 'refresh' }, process.env.JWT_REFRESH_SECRET, {
    expiresIn: '7d',
  });

  return { accessToken, refreshToken };
}

Reference: CWE-287: Improper Authentication

14. CWE-190: Integer Overflow or Wraparound​

Explanation: When integer arithmetic exceeds maximum values, it can wrap around to negative numbers or zero, causing logic errors, buffer overflows, or security bypasses.

Example:

// ❌ VULNERABLE: No overflow checking
function calculateTotal(price: number, quantity: number): number {
  return price * quantity; // Can exceed Number.MAX_SAFE_INTEGER
}

// ✅ SECURE: Validate ranges and use safe operations
function calculateTotal(price: number, quantity: number): number {
  // Validate inputs
  if (price < 0 || quantity < 0) {
    throw new Error('Invalid input: negative values');
  }

  if (price > Number.MAX_SAFE_INTEGER || quantity > Number.MAX_SAFE_INTEGER) {
    throw new Error('Invalid input: values too large');
  }

  const total = price * quantity;

  // Check for overflow
  if (total > Number.MAX_SAFE_INTEGER || !Number.isSafeInteger(total)) {
    throw new Error('Calculation overflow');
  }

  return total;
}

// ✅ SECURE: Use BigInt for large numbers
function calculateTotal(price: bigint, quantity: bigint): bigint {
  if (price < 0n || quantity < 0n) {
    throw new Error('Invalid input: negative values');
  }
  return price * quantity;
}

Reference: CWE-190: Integer Overflow or Wraparound

15. CWE-502: Deserialization of Untrusted Data​

Explanation: Deserializing untrusted data can lead to remote code execution if the serialized data contains malicious payloads that execute during deserialization.

Example:

// ❌ VULNERABLE: Using eval or unsafe deserialization
function processData(serializedData: string) {
  const data = eval(`(${serializedData})`); // Never use eval!
  return data;
}

// ❌ VULNERABLE: node-serialize vulnerability
import * as serialize from 'node-serialize';
function processData(serializedData: string) {
  return serialize.unserialize(serializedData); // Can execute code
}

// ✅ SECURE: Use JSON.parse with validation
import { z } from 'zod';

const UserSchema = z.object({
  id: z.string().uuid(),
  email: z.string().email(),
  age: z.number().min(0).max(150),
});

function processUserData(jsonString: string) {
  try {
    const rawData = JSON.parse(jsonString);
    const validatedData = UserSchema.parse(rawData);
    return validatedData;
  } catch (error) {
    throw new BadRequestException('Invalid data format');
  }
}

// ✅ SECURE: For complex objects, use class-validator
import { plainToClass } from 'class-transformer';
import { validate } from 'class-validator';

async function processUserData(jsonString: string) {
  const rawData = JSON.parse(jsonString);
  const userDto = plainToClass(CreateUserDto, rawData);

  const errors = await validate(userDto);
  if (errors.length > 0) {
    throw new BadRequestException('Validation failed');
  }

  return userDto;
}

Reference: CWE-502: Deserialization of Untrusted Data

16. CWE-77: Command Injection​

Explanation: Similar to CWE-78 but more general, including any type of command injection (shell, SQL, LDAP, XPath, etc.). Occurs when untrusted data is passed to a command interpreter.

Example:

// ❌ VULNERABLE: Command injection via template literals
import { exec } from 'child_process';

function pingHost(hostname: string) {
  exec(`ping -c 4 ${hostname}`, (error, stdout) => {
    // Attacker: "google.com; cat /etc/passwd"
    console.log(stdout);
  });
}

// ✅ SECURE: Input validation and safe execution
import { execFile } from 'child_process';

function pingHost(hostname: string) {
  // Validate hostname format
  const hostnameRegex = /^[a-zA-Z0-9.-]+$/;
  if (!hostnameRegex.test(hostname)) {
    throw new Error('Invalid hostname');
  }

  // Use execFile with argument array
  execFile('ping', ['-c', '4', hostname], (error, stdout) => {
    if (error) {
      throw new Error('Ping failed');
    }
    console.log(stdout);
  });
}

// ✅ BETTER: Use dedicated libraries
import * as ping from 'ping';

async function pingHost(hostname: string) {
  const result = await ping.promise.probe(hostname);
  return result;
}

Reference: CWE-77: Command Injection

17. CWE-119: Improper Restriction of Operations within Memory Bounds​

Explanation: Memory safety issues including buffer overflows and out-of-bounds access. Primarily affects native code but can impact Node.js applications using C/C++ addons.

Example:

// JavaScript/TypeScript has automatic bounds checking
// This is primarily a concern for native modules

// ✅ SECURE: Safe buffer operations
function createSafeBuffer(size: number, data?: string): Buffer {
  if (size <= 0 || size > 10 * 1024 * 1024) {
    // 10MB limit
    throw new Error('Invalid buffer size');
  }

  const buffer = Buffer.alloc(size); // Allocates with zeros

  if (data) {
    const bytesWritten = buffer.write(data, 0, size);
    console.log(`Wrote ${bytesWritten} bytes`);
  }

  return buffer;
}

// ✅ SECURE: Safe array operations
function safeArrayAccess<T>(arr: T[], index: number): T | undefined {
  if (index < 0 || index >= arr.length) {
    return undefined;
  }
  return arr[index];
}

Reference: CWE-119: Operations within Memory Bounds

18. CWE-798: Use of Hard-coded Credentials​

Explanation: Embedding credentials directly in source code makes them accessible to anyone with code access and difficult to change when compromised.

Example:

// ❌ VULNERABLE: Hardcoded credentials
const dbConfig = {
  host: 'localhost',
  user: 'admin',
  password: 'SuperSecret123!', // Never do this!

import { URL } from 'url';

async function fetchUrl(urlString: string) {

    if (order.userId !== user.id && !user.roles.includes('admin')) {
      throw new ForbiddenException('Cannot access this order');
    }

    return order;
  }
}

Reference: CWE-639: Authorization Bypass Through User-Controlled Key

32. CWE-770: Allocation of Resources Without Limits or Throttling​

Explanation: The software allocates resources (memory, disk space, connections, etc.) based on user input without limiting the maximum size or rate, allowing attackers to exhaust resources and cause denial of service.

Example:

// ❌ VULNERABLE: Unlimited resource allocation
@Post('upload')
async uploadFile(@UploadedFile() file: Express.Multer.File) {
  // No file size limit - attacker can upload huge files
  await fs.writeFile(`./uploads/${file.originalname}`, file.buffer);
  return { success: true };
}

@Post('process')
async processData(@Body() data: { items: any[] }) {
  // No limit on array size - can cause memory exhaustion
  const results = data.items.map(item => this.expensiveOperation(item));
  return results;
}

@Get('search')
async search(@Query('q') query: string) {
  // No limit on query complexity or result size
  return await this.db.query(`SELECT * FROM products WHERE name LIKE '%${query}%'`);
}

// ✅ SECURE: Implement resource limits and throttling
import * as rateLimit from 'express-rate-limit';

// Rate limiting middleware
const uploadLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 10, // Limit each IP to 10 upload requests per windowMs
  message: 'Too many upload requests, please try again later'
});

@Post('upload')
@UseInterceptors(FileInterceptor('file', {
  limits: {
    fileSize: 10 * 1024 * 1024, // 10MB max
    files: 1
  }
}))
@UseGuards(ThrottlerGuard)
async uploadFile(@UploadedFile() file: Express.Multer.File) {
  if (!file) {
    throw new BadRequestException('No file provided');
  }

  if (file.size > 10 * 1024 * 1024) {
    throw new BadRequestException('File too large');
  }

  await fs.writeFile(`./uploads/${file.originalname}`, file.buffer);
  return { success: true };
}

@Post('process')
@UseGuards(ThrottlerGuard)
async processData(@Body() data: { items: any[] }) {
  // Limit array size
  if (!Array.isArray(data.items) || data.items.length > 1000) {
    throw new BadRequestException('Items array too large (max 1000)');
  }

  // Process in batches to limit memory usage
  const batchSize = 100;
  const results = [];

  for (let i = 0; i < data.items.length; i += batchSize) {
    const batch = data.items.slice(i, i + batchSize);
    const batchResults = batch.map(item => this.expensiveOperation(item));
    results.push(...batchResults);
  }

  return results;
}

@Get('search')
@UseGuards(ThrottlerGuard)
async search(@Query('q') query: string) {
  // Limit query length
  if (query.length > 100) {
    throw new BadRequestException('Query too long');
  }

  // Limit result size
  const results = await this.db.query(
    'SELECT * FROM products WHERE name LIKE ? LIMIT 100',
    [`%${query}%`]
  );

  return results;
}

// ✅ SECURE: Connection pool limits
const dbConfig = {
  host: process.env.DB_HOST,
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  max: 20, // Maximum pool size
  min: 5,  // Minimum pool size
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
};

// ✅ SECURE: Memory usage monitoring
import * as os from 'os';

@Injectable()
export class ResourceMonitorService {
  private readonly MAX_MEMORY_PERCENT = 80;

  checkMemoryUsage(): void {
    const totalMem = os.totalmem();
    const freeMem = os.freemem();
    const usedPercent = ((totalMem - freeMem) / totalMem) * 100;

    if (usedPercent > this.MAX_MEMORY_PERCENT) {
      throw new ServiceUnavailableException('System resources exhausted');
    }
  }
}

Reference: CWE-770: Allocation of Resources Without Limits

Certification Levels​

Based on the 2025 CWE Top 25, we offer three certification tiers focused on web application security:

  1. CWE Fundamentals (6 core modules completed)

    • CWE-79 (XSS), CWE-89 (SQL Injection), CWE-20 (Input Validation)
    • CWE-352 (CSRF), CWE-862 (Missing Authorization), CWE-434 (File Upload)

  2. CWE Practitioner (12 modules completed)

    • All Fundamentals modules plus:
    • CWE-22 (Path Traversal), CWE-78 (OS Command Injection), CWE-77 (Command Injection)
    • CWE-94 (Code Injection), CWE-863 (Incorrect Authorization), CWE-284 (Improper Access Control)

  3. CWE Expert (18+ modules completed)

    • All Practitioner modules plus:
    • CWE-502 (Deserialization), CWE-918 (SSRF), CWE-306 (Missing Authentication)
    • CWE-200 (Information Exposure), CWE-639 (Authorization Bypass), CWE-770 (Resource Throttling)

Note: Memory safety CWEs (CWE-787, CWE-125, CWE-416, CWE-476, CWE-120, CWE-121, CWE-122) are covered in advanced training for developers working with native Node.js modules.
