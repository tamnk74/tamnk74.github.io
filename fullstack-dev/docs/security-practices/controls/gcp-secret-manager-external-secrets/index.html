GCP Secret Manager + External Secrets Operator

Zero-secrets-in-Git: bridging GCP Secret Manager into Kubernetes workloads without static credentials, environment variable leakage, or manual rotation.

Problem Statement​

A GitOps-managed platform stores all desired state in Git. That creates a hard constraint:

  • No credentials may live in Git repos (including environment variables in YAML manifests)
  • No secrets in container image layers or build artifacts
  • No long-lived service-account keys distributed to pods

Kubernetes-native Secret objects solve the delivery problem but not the lifecycle or audit problem — they are base64-encoded, not encrypted, and offer no rotation automation.

This guide implements the canonical GCP solution:

ConcernSolution
Secret storage & encryptionGCP Secret Manager (CMEK, versioned)
Kubernetes deliveryExternal Secrets Operator (ESO)
Authentication (no static keys)GCP Workload Identity via pod service account
RotationGCP automatic rotation + ESO refreshInterval
Audit trailCloud Audit Logs (Data Access on Secret Manager)
IaC provisioningTerraform (google_secret_manager_secret)

Architecture​

Key invariant: pods consume Kubernetes Secret objects as mounted files — they never call GCP Secret Manager directly and have no GCP credentials of their own.

Workload Identity Setup​

ESO authenticates to GCP using Workload Identity — the ESO controller's Kubernetes Service Account (KSA) is bound to a GCP Service Account (GSA) with minimum Secret Manager IAM permissions.

Terraform: GSA + IAM binding​

# terraform/modules/secrets/workload-identity.tf

# GCP Service Account for ESO
resource "google_service_account" "eso" {
  account_id   = "external-secrets-operator"
  display_name = "External Secrets Operator"
  project      = var.project_id
}

# Allow ESO to read secrets (not create/delete)
resource "google_project_iam_member" "eso_secret_accessor" {
  project = var.project_id
  role    = "roles/secretmanager.secretAccessor"
  member  = "serviceAccount:${google_service_account.eso.email}"
}

# Workload Identity binding: KSA → GSA
resource "google_service_account_iam_member" "eso_workload_identity" {
  service_account_id = google_service_account.eso.name
  role               = "roles/iam.workloadIdentityUser"
  member = "serviceAccount:${var.project_id}.svc.id.goog[external-secrets/external-secrets]"
}

Provisioning Secrets in GCP Secret Manager​

Terraform: secret lifecycle​

# terraform/modules/secrets/secrets.tf

locals {
  secrets = {
    "order-db-url"         = { rotation_days = 90 }
    "stripe-secret-key"    = { rotation_days = 0  }  # manual rotation
    "stripe-webhook-secret"= { rotation_days = 0  }
    "jwt-signing-key"      = { rotation_days = 30 }
    "sendgrid-api-key"     = { rotation_days = 0  }
    "redis-auth-token"     = { rotation_days = 90 }
  }
}

resource "google_secret_manager_secret" "app_secrets" {
  for_each  = local.secrets
  project   = var.project_id
  secret_id = each.key

  replication {
    user_managed {
      replicas {
        location = "us-central1"
        customer_managed_encryption {
          kms_key_name = google_kms_crypto_key.secrets_key.id
        }
      }
      replicas {
        location = "us-east1"
        customer_managed_encryption {
          kms_key_name = google_kms_crypto_key.secrets_key.id
        }
      }
    }
  }

  dynamic "rotation" {
    for_each = each.value.rotation_days > 0 ? [1] : []
    content {
      rotation_period   = "${each.value.rotation_days * 86400}s"
      next_rotation_time = timeadd(timestamp(), "${each.value.rotation_days * 24}h")
    }
  }

  labels = {
    env     = var.environment
    managed = "terraform"
  }
}

# KMS key for envelope encryption of secrets
resource "google_kms_key_ring" "secrets" {
  name     = "secrets-keyring-${var.environment}"
  location = "us-central1"
  project  = var.project_id
}

resource "google_kms_crypto_key" "secrets_key" {
  name            = "secrets-cmek"
  key_ring        = google_kms_key_ring.secrets.id
  rotation_period = "7776000s"  # 90 days

  version_template {
    algorithm        = "GOOGLE_SYMMETRIC_ENCRYPTION"
    protection_level = "HSM"
  }
}

Seeding initial secret values (CI/CD — never in Git)​

# scripts/seed-secrets.sh  (run once via Cloud Build, not committed with values)
gcloud secrets versions add order-db-url \
  --data-file=- <<< "${DATABASE_URL}"

gcloud secrets versions add stripe-secret-key \
  --data-file=- <<< "${STRIPE_SECRET_KEY}"

Secret values are injected via CI environment variables sourced from a secure bootstrap process (e.g., Cloud Build substitutions stored in the Cloud Build trigger, not in source code).

ClusterSecretStore (GCP provider)​

# k8s/external-secrets/cluster-secret-store.yaml
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: gcp-secret-manager
spec:
  provider:
    gcpsm:
      projectID: "my-gcp-project"
      # ESO controller KSA has Workload Identity annotation → no key file needed

This single ClusterSecretStore serves all namespaces. Individual teams create ExternalSecret resources in their own namespaces — they never need GCP credentials.

ExternalSecret Resources​

Order Service — database URL​

# k8s/production/order-service/external-secret.yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-db-secret
  namespace: production
spec:
  refreshInterval: 1h          # re-sync from Secret Manager hourly
  secretStoreRef:
    name: gcp-secret-manager
    kind: ClusterSecretStore
  target:
    name: order-db-secret      # resulting Kubernetes Secret name
    creationPolicy: Owner      # ESO owns the lifecycle; deleting ES deletes K8s Secret
    template:
      engineVersion: v2
      data:
        # Render as a connection string consumed by the app
        DATABASE_URL: "{{ .orderDbUrl }}"
  data:
    - secretKey: orderDbUrl
      remoteRef:
        key: order-db-url      # GCP Secret Manager secret name
        # omit 'version' → always fetch the latest enabled version

Consuming Secrets in Pods (file-based, not env vars)​

Mounting secrets as files is safer than environment variables: process inspection (/proc/<pid>/environ) cannot expose them, and accidental logging of process.env is prevented.

# k8s/production/order-service/deployment.yaml (relevant sections)
spec:
  template:
    spec:
      volumes:
        - name: db-secret
          secret:
            secretName: order-db-secret
            defaultMode: 0400       # read-only, owner only
      containers:
        - name: order-service
          image: gcr.io/my-project/order-service:${IMAGE_TAG}
          volumeMounts:
            - name: db-secret
              mountPath: /run/secrets/db
              readOnly: true
          # No DATABASE_URL in env — read from file at runtime

NestJS: reading secret from mounted file​

// src/config/database.config.ts
import { readFileSync } from 'fs';

function readSecret(path: string, fallbackEnv?: string): string {
  try {
    return readFileSync(path, 'utf-8').trim();
  } catch {
    if (fallbackEnv && process.env[fallbackEnv]) {
      return process.env[fallbackEnv]!;  // local dev only
    }
    throw new Error(`Secret not found at ${path} and no fallback env set`);
  }
}

export const databaseConfig = () => ({
  database: {
    url: readSecret('/run/secrets/db/DATABASE_URL', 'DATABASE_URL'),
  },
});
// src/app.module.ts
import { ConfigModule } from '@nestjs/config';
import { databaseConfig } from './config/database.config';

@Module({
  imports: [

      isGlobal: true,

        type: 'postgres',
        url: config.get<string>('database.url'),

      }),
    }),
  ],
})

Secret Rotation​

Automatic rotation flow​

Zero-Downtime Rotation: Dual-Version Overlap​

The critical failure mode is disabling the old secret version before ESO has synced the new one and pods have consumed it. The safe sequence uses an overlap window:

t=0   Add new secret version v2 (SM keeps v1 enabled — pods still work)
t=0   ESO refreshInterval tick → syncs v2 → updates K8s Secret
t=~5s K8s Secret update propagates to pod's mounted file
t=30s Grace period — confirm pods are healthy
t=60s Disable v1 in Secret Manager

Rule: Never disable the old version until ESO has confirmed the new version is written. Set overlap window ≥ refreshInterval + 2 min.

Database credentials: two-phase rotation​

Database secrets require an extra constraint — the new credential must exist in the DB before apps switch to it:

Phase 1 — Provision new DB credential, add as SM v2 (v1 still active)
Phase 2 — Wait for ESO sync + pod mount refresh
Phase 3 — Disable SM v1, revoke old DB credential

Cloud Function: database credential rotator (safe)​

// functions/rotate-db-secret/index.ts
import { SecretManagerServiceClient } from '@google-cloud/secret-manager';
import { KubeConfig, CoreV1Api } from '@kubernetes/client-node';
import { CloudSqlIamClient } from './cloud-sql-client';

const REFRESH_INTERVAL_SECONDS = 3600; // match ExternalSecret refreshInterval

export async function rotateDbSecret(message: PubSubMessage) {
  const { secretName, projectId } = JSON.parse(
    Buffer.from(message.data, 'base64').toString()
  );

  const smClient = new SecretManagerServiceClient();
  const sqlClient = new CloudSqlIamClient();

  // Phase 1: provision new credential in DB
  const newPassword = crypto.randomBytes(32).toString('base64url');
  const newUrl = buildConnectionUrl(newPassword);
  await sqlClient.setUserPassword('app_user', newPassword);

  // Phase 1: add new version — old version stays ENABLED
  const [newVersion] = await smClient.addSecretVersion({
    parent: `projects/${projectId}/secrets/${secretName}`,
    payload: { data: Buffer.from(newUrl) },
  });

  // Phase 2: wait for ESO refreshInterval + propagation buffer
  await sleep((REFRESH_INTERVAL_SECONDS + 120) * 1000);

  // Phase 2: verify ESO actually synced the new version before proceeding
  await verifyKubernetesSecretSynced(secretName);

  // Phase 3: disable all older versions
  const [{ versions }] = await smClient.listSecretVersions({
    parent: `projects/${projectId}/secrets/${secretName}`,
    filter: 'state=ENABLED',
  });
  for (const v of versions ?? []) {
    if (v.name !== newVersion.name) {
      await smClient.disableSecretVersion({ name: v.name! });
    }
  }

  // Phase 3: revoke old DB credential
  await sqlClient.revokeOldUser('app_user_previous');
}

/** Confirm ESO has written a K8s Secret with a recent sync annotation */
async function verifyKubernetesSecretSynced(secretName: string): Promise<void> {
  const kc = new KubeConfig();
  kc.loadFromDefault();
  const k8s = kc.makeApiClient(CoreV1Api);

  const { body } = await k8s.readNamespacedSecret(secretName, 'production');
  const lastSync = body.metadata?.annotations?.['reconcile.external-secrets.io/data-hash'];

  if (!lastSync) {
    throw new Error(
      `ESO has not synced ${secretName} — aborting old version disable to prevent downtime`
    );
  }
}

function sleep(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

Rolling restart for connection-pool apps​

Some apps (e.g. NestJS with TypeORM connection pools) read credentials only at startup — reloading the mounted file is not enough. After ESO confirms sync, trigger a zero-downtime rolling restart:

# Triggered by rotation Cloud Function or a CronJob watching ExternalSecret LastSyncTime
kubectl rollout restart deployment/order-service -n production
kubectl rollout status deployment/order-service -n production --timeout=5m

Or automate via a Kubernetes Job that the rotation Cloud Function submits after verifyKubernetesSecretSynced succeeds:

# k8s/jobs/post-rotation-restart.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: post-rotation-restart-order
  namespace: production
spec:
  template:
    spec:
      serviceAccountName: rotation-restarter  # needs deployments/patch RBAC
      containers:
        - name: kubectl
          image: bitnami/kubectl:latest
          command:
            - kubectl
            - rollout
            - restart
            - deployment/order-service
            - -n
            - production
      restartPolicy: OnFailure

## GitHub Actions: CI/CD Without Secrets in Git

GitHub Actions authenticates to GCP via **OIDC** — no service account key files stored in Git or GitHub secrets beyond the project ID.

```yaml
# .github/workflows/deploy.yml (relevant steps)
jobs:
  deploy:
    permissions:
      id-token: write    # required for OIDC
      contents: read

    steps:
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: "projects/123456/locations/global/workloadIdentityPools/github/providers/github"
          service_account: "ci-deployer@my-gcp-project.iam.gserviceaccount.com"
          # No key file — GCP verifies GitHub's OIDC JWT token

      - name: Seed secret (first-time only, gated by env check)
        if: ${{ github.event_name == 'workflow_dispatch' && inputs.seed_secrets }}
        run: |
          # Values sourced from GitHub Actions environment secrets (not committed)
          echo -n "${{ secrets.ORDER_DB_URL }}" | \
            gcloud secrets versions add order-db-url --data-file=-

Terraform for OIDC Workload Identity Pool​

# terraform/modules/ci/github-oidc.tf

Cloud Audit Logs — Secret Access Trail​

Enable Data Access audit logs on Secret Manager to record every AccessSecretVersion call with the calling identity.

# terraform/modules/secrets/audit-logs.tf
resource "google_project_iam_audit_config" "secret_manager_audit" {
  project = var.project_id
  service = "secretmanager.googleapis.com"

  audit_log_config {
    log_type = "DATA_READ"    # captures AccessSecretVersion
  }
  audit_log_config {
    log_type = "DATA_WRITE"   # captures AddSecretVersion, UpdateSecret
  }
  audit_log_config {
    log_type = "ADMIN_READ"   # captures GetSecret, ListSecretVersions
  }
}

# Export audit logs to BigQuery for long-term analysis
resource "google_logging_project_sink" "secret_audit_bq" {
  name        = "secret-manager-audit"
  project     = var.project_id
  destination = "bigquery.googleapis.com/projects/${var.project_id}/datasets/security_audit"

  filter = <<EOT
    resource.type="audited_resource"
    protoPayload.serviceName="secretmanager.googleapis.com"
  EOT

  unique_writer_identity = true
}

OPA: reject Secret objects with hardcoded data​

# policies/no-secret-data.rego
package kubernetes.admission

deny[msg] {
  input.request.kind.kind == "Secret"
  count(input.request.object.data) > 0
  not input.request.object.metadata.annotations["external-secrets.io/controller-class"]
  msg := sprintf("Secret '%v' must be managed by External Secrets Operator (no hardcoded .data)", [
    input.request.object.metadata.name
  ])
}

Failure Modes​

FailureDetectionMitigation
ESO cannot reach GCP Secret ManagerExternalSecret status SecretSyncedError; Datadog alert on ESO error metricExisting Kubernetes Secret (last sync) stays mounted — pods keep running; investigate Workload Identity binding
GCP Secret Manager quota exceeded429 response; ESO backs off with exponential retryIncrease quota via GCP console; ESO retries automatically
Secret version disabled before ESO refreshesPod reads stale version from mounted fileEnsure disableSecretVersion is called only after ESO has synced the new version; use rotation delay
Leaked secret detected in Git historyTruffleHog in CI; SIEM alertImmediately rotate secret in Secret Manager (add new version, disable old); invalidate any active sessions
