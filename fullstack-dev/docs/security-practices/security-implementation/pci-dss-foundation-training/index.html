PCI DSS Foundation Training & Assessment (Banking Projects)

Overview​

This document defines the baseline PCI DSS foundation training requirement for development teams working on banking projects (or any project that stores, processes, or transmits payment card data, or can impact the Cardholder Data Environment (CDE)). The goal is to ensure engineers understand PCI DSS fundamentals and can demonstrate competence by passing an assessment after training.

Policy Statement​

  • Team members who build, review, deploy, or operate systems in scope for PCI DSS must complete PCI DSS foundation training.
  • Team members must pass the post-training assessment within the required time window.
  • Training must be completed during onboarding and refreshed on a defined cadence.

Scope​

Applies to:

  • Backend engineers (NestJS), frontend engineers (Next.js), SRE/DevOps, QA, and security engineers
  • Contractors and vendors with access to in-scope environments or logs

In-scope systems typically include:

  • the CDE (systems that store/process/transmit cardholder data)
  • systems connected to the CDE, or that can impact CDE security (CI/CD, logging, monitoring, identity, network controls)

Training Requirements​

1) Training content (minimum)​

PCI DSS foundation training must cover:

  • PCI DSS goals and what the standard is trying to achieve (reduce payment card fraud via consistent controls)
  • Key concepts and definitions:
    • cardholder data (CHD), sensitive authentication data (SAD)
    • CDE scope and segmentation
    • SAQ (high level), ROC (high level)
  • Why minimizing scope matters (reduce attack surface and audit cost)
  • Core control domains (high level):
    • network security controls and segmentation
    • secure configuration and hardening
    • vulnerability management and patching
    • access control and least privilege
    • logging, monitoring, and alerting
    • secure software development (SDLC)
    • incident response expectations
  • Engineering behaviors:
    • never store SAD (e.g., CVV)
    • avoid handling PAN directly; prefer tokenization
    • don’t log PAN/PII/secrets; use redaction
    • secure secrets management and key rotation

1a) Comprehensive training curriculum (recommended)​

This curriculum can be used to build an internal LMS course (60–120 minutes total) plus a short practical exercise.

Module A — PCI DSS fundamentals and scope​

Learning objectives:

  • Explain what PCI DSS covers and why CDE scope must be controlled.
  • Identify where payment data flows (frontend → gateway → backend → storage).

Key topics:

  • CHD vs. SAD
  • Tokenization and hosted payment pages
  • Segmentation and “systems that can impact the CDE”

Hands-on exercise:

  • Draw a simple payment flow diagram and mark which components are in-scope vs. out-of-scope.

Module B — Data handling rules for card data​

Learning objectives:

  • Know what must never be stored and what can be stored with controls.
  • Recognize common leak paths (logs, errors, URLs, analytics).

Key topics:

  • Prohibited storage: SAD (e.g., CVV)
  • PAN storage minimization and masking
  • Data retention principles for payment-related logs

Hands-on exercise:

  • Review sample logs and remove/replace any sensitive fields (PAN, tokens, secrets).

Module C — Access control and operational discipline​

Learning objectives:

  • Apply least privilege to access card-related systems.
  • Understand privileged access monitoring expectations.

Key topics:

  • Role-based access, break-glass, approvals
  • MFA requirements for admins
  • Access reviews and separation of duties (high level)

Hands-on exercise:

  • Propose a minimal set of roles for “payment support access” and what should be auditable.

Module D — Vulnerability management and secure SDLC​

Learning objectives:

  • Understand how PCI DSS pushes continuous vulnerability management.
  • Know how secure SDLC controls support PCI.

Key topics:

  • dependency scanning, SAST, container scanning
  • patch SLAs for critical vulnerabilities
  • change management and peer review

Hands-on exercise:

  • Given a critical CVE in a payment service image, decide the remediation plan and how to prove closure.

Module E — Logging, monitoring, and incident response​

Learning objectives:

  • Know what to log, how to protect logs, and how monitoring supports detection.
  • Understand incident response expectations for suspected card data exposure.

Key topics:

  • security event logging and alerting
  • retention and access controls for logs
  • evidence preservation and incident escalation

Hands-on exercise:

  • Draft an “incident trigger” checklist for suspected payment data leakage.

2) Assessment (pass/fail)​

  • Engineers must pass a knowledge check after training.
  • Recommended passing score: ≥ 80%.
  • Failed attempts must be remediated with a re-take after reviewing incorrect topics.

Assessment blueprint (recommended)​

  • Format: 20–30 questions (multiple-choice + scenario-based)
  • Time limit: 20–30 minutes
  • Passing score: ≥ 80%
  • Coverage (example weighting):
    • 25%: scope and definitions (CDE, CHD, SAD)
    • 25%: data handling rules (what not to store/log)
    • 25%: access control + monitoring expectations
    • 25%: vulnerability management + SDLC expectations

Scenario examples:

  • A developer proposes logging full request bodies for the payment webhook handler. What risks does this create and how do you design safe logging?
  • A new microservice needs to call the payment gateway. What’s the minimal secret-handling approach and what should be audited?
  • An alert indicates unusual access to payment logs. What is the immediate containment action and who must be notified?

Operational Process​

Onboarding​

  • New joiners complete training within 30 days of start date (or before production access to in-scope systems is granted, whichever is earlier).
  • Access to in-scope production systems requires either:
    • confirmed completion + passing assessment, or
    • an approved, time-bound exception with compensating controls.

Refresher cadence​

  • Refresh training annually, and additionally when:
    • PCI scope changes (new payment flow, new vendor, new environment),
    • major incidents occur (or near-miss events),
    • internal standards change (logging policy, access policy, SDLC gates).

Ownership​

  • Security/Compliance owns the training curriculum and assessment maintenance.
  • Engineering managers ensure completion for their teams.
  • Platform/SRE enforces access gating where feasible.

Evidence & Auditability​

Maintain evidence for audit and internal governance:

  • Training completion records (user, course, date)
  • Assessment result (score, pass/fail, date)
  • Exceptions and expiry dates (if any)

Recommended storage locations:

  • LMS export or compliance tracker (GRC tool)
  • Ticket references for exceptions

Website Resources (Recommended)​

  • PCI Security Standards Council (PCI SSC): https://www.pcisecuritystandards.org/
  • PCI DSS document library: https://www.pcisecuritystandards.org/document_library
  • OWASP Cheat Sheet Series (secure practices supporting PCI outcomes): https://cheatsheetseries.owasp.org/
  • Google Cloud Security documentation (for platform controls): https://cloud.google.com/security
  • Kubernetes Security documentation: https://kubernetes.io/docs/concepts/security/

Acceptance Criteria (Definition of Done)​

  • 100% of in-scope team members have completed PCI DSS foundation training.
  • 100% have passed the assessment (or have an approved, time-bound exception).
  • Training completion and scores are retrievable for audits.
  • Access to in-scope production systems is gated by completion status where feasible.
