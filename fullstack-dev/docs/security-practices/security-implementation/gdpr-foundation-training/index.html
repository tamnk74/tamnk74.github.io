GDPR Foundation Training & Assessment (Engineering)

Overview​

This document defines the baseline GDPR training requirement for development teams building NestJS/Next.js applications on GCP/Kubernetes. The goal is to ensure everyone who builds, reviews, deploys, or operates systems that process personal data understands GDPR fundamentals and can demonstrate competence by passing an assessment.

Policy Statement​

  • All engineers (and any role with access to personal data or production systems) must complete GDPR foundation training.
  • Team members must pass the post-training assessment within the required time window.
  • Training must be completed during onboarding and refreshed on a defined cadence.

Scope​

Applies to:

  • Backend engineers (NestJS), frontend engineers (Next.js), SRE/DevOps, QA, and security engineers
  • Contractors and vendors who can access personal data or production logs

Training Requirements​

1) Training content (minimum)​

GDPR foundation training must cover:

  • What “personal data” means and common examples in ecommerce
  • Controller vs. processor roles (high level)
  • Core principles: lawfulness, fairness, transparency, purpose limitation, data minimization, accuracy, storage limitation, integrity/confidentiality, accountability
  • Lawful bases (overview) and consent basics
  • Data subject rights (overview): access, rectification, erasure, portability, restriction, objection
  • Security expectations for personal data: least privilege, encryption, logging hygiene, breach reporting basics
  • Practical engineering behaviors: avoid over-collection, retention, safe logging, safe analytics identifiers, incident escalation

1a) Comprehensive training curriculum (recommended)​

This section can be used as the course outline for an internal LMS module (60–120 minutes total) plus a short practical exercise.

Module A — GDPR fundamentals for engineers​

Learning objectives:

  • Explain what “personal data” is in day-to-day engineering terms (direct + indirect identifiers).
  • Recognize when data becomes personal data due to linkability (account IDs, device IDs, pseudonymous IDs).
  • Understand “processing” broadly (collect, store, transform, log, analyze, share).

Key topics:

  • Personal data vs. anonymized data vs. pseudonymized data
  • Data lifecycle: collection → storage → access → sharing → retention → deletion

Hands-on exercise:

  • Given a sample “user profile + order” schema, mark which fields are personal data and identify which are high-risk (e.g., government ID, payment identifiers, support attachments).

Module B — Roles, responsibilities, and vendor boundaries​

Learning objectives:

  • Distinguish controller vs. processor at a high level.
  • Identify what changes when using third parties (payments, analytics, email/SMS).

Key topics:

  • Vendor data flows and “where does the data go” mapping
  • Minimizing data sent to third parties (only what is necessary)

Hands-on exercise:

  • Review a typical ecommerce flow (signup → checkout → shipping updates) and document which services receive personal data.

Module C — GDPR principles applied to product and engineering decisions​

Learning objectives:

  • Apply GDPR principles to everyday implementation choices.
  • Translate principles into actionable design constraints.

Key topics:

  • Purpose limitation: avoid “collect now, use later”
  • Data minimization: do we need this field/event/log?
  • Storage limitation: retention + deletion policies
  • Integrity and confidentiality: secure-by-default expectations

Hands-on exercise:

  • For a proposed new tracking event, decide: what fields are needed, how long to keep them, and how to avoid collecting personal data unnecessarily.

Module D — Lawful bases & consent (engineering perspective)​

Learning objectives:

  • Understand that processing needs a lawful basis (without turning engineers into lawyers).
  • Implement consent-aware behavior and “consent changes everything” workflows.

Key topics:

  • Consent vs. legitimate interests vs. contract (overview)
  • Consent tracking: when it was given, what it covered, and withdrawal
  • Feature flags and consent gates for analytics/marketing tags

Hands-on exercise:

  • Identify which client-side scripts require consent and ensure they are gated behind a consent state.

Module E — Data subject rights: engineering workflows​

Learning objectives:

  • Map data subject rights to system operations (export, delete, rectify).
  • Understand where rights requests fail in practice (logs, backups, third-party systems).

Key topics:

  • Data access/export format and identity verification
  • Erasure vs. retention obligations (e.g., invoices) and “deletion by design”
  • Deletion across microservices and asynchronous systems

Hands-on exercise:

  • Sketch a deletion workflow across services: what is hard-deleted, what is pseudonymized, and what is retained with justification.

Module F — Security expectations for personal data (implementation-level)​

Learning objectives:

  • Implement least-privilege access and separate “PII access” roles.
  • Avoid leaking personal data through logs, error messages, analytics, and URLs.
  • Use encryption and secrets management appropriately.

Key topics:

  • Access control patterns: admin endpoints, break-glass, approvals
  • Secure logging: no secrets/PII in logs; redact by default
  • Encryption in transit + at rest; key management basics
  • Common pitfalls:
    • putting emails/phones in URLs
    • storing tokens in localStorage
    • logging request bodies for debugging in production

Hands-on exercise (choose one):

  • Review a sample API handler and remove/replace unsafe logging.
  • Add a redaction layer for structured logs (e.g., redact email/phone/address keys).

Module G — Privacy by design in the NestJS/Next.js + GCP stack​

Learning objectives:

  • Apply privacy controls where they naturally belong in the stack.
  • Identify privacy-sensitive storage and transmission points.

Key topics:

  • NestJS: DTO validation, serialization, role guards for PII endpoints, audit events
  • Next.js: server-side rendering data minimization, safe caching, safe error pages
  • GCP/Kubernetes: secret handling, restricted logs, access to databases, service accounts

Hands-on exercise:

  • Identify where personal data may be cached (CDN, server cache, browser cache) and apply a safe caching strategy.

1b) Role-based emphasis (who focuses on what)​

  • Backend (NestJS): access control, audit logging, retention/deletion workflows, data exports, service-to-service authorization
  • Frontend (Next.js): consent gating, analytics minimization, avoiding personal data in URLs, safe caching, secure session handling
  • SRE/DevOps: production access controls, log sinks & retention, backup access, incident response runbooks, key and secret management
  • QA: test cases for consent flows, rights requests, deletion verification, regression checks for PII leaks in logs/UI

2) Assessment (pass/fail)​

  • Engineers must pass a knowledge check after training.
  • Recommended passing score: ≥ 80%.
  • Failed attempts must be remediated with a re-take after reviewing incorrect topics.

Assessment blueprint (recommended)​

  • Format: 20–30 questions (mix of multiple-choice + scenario-based)
  • Time limit: 20–30 minutes
  • Passing score: ≥ 80%
  • Question coverage (example weighting):
    • 20%: personal data identification and linkability
    • 15%: principles and data minimization
    • 15%: lawful bases/consent basics
    • 20%: data subject rights workflows
    • 30%: security practices (logging, access control, encryption, incident escalation)

Scenario-style questions (examples)​

  • A debug log line currently prints request bodies for a “profile update” endpoint. What is the risk and what should be changed?
  • A frontend change proposes putting email in a URL query parameter for convenience. What’s wrong with this and what’s a safer alternative?
  • A user requests deletion. Which systems must be considered beyond the primary database (e.g., logs, analytics, third parties), and how do you verify completion?

Practical mini-exercise (optional but strong)​

  • Provide a small code snippet or log sample and require the learner to:
    • identify the personal data fields
    • propose redaction
    • propose least-privilege access for the endpoint

Operational Process​

Website Resources (Recommended)​

Use these websites as the “source of truth” references for course material, refreshers, and scenario questions.

Official GDPR text and EU guidance​

  • GDPR legal text (EUR-Lex): https://eur-lex.europa.eu/eli/reg/2016/679/oj
  • European Data Protection Board (EDPB) guidelines: https://www.edpb.europa.eu/our-work-tools/our-documents/guidelines_en

Regulator guidance (practical explanations)​

  • UK ICO (Guide to the GDPR): https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/
  • CNIL (France, guidance and tools): https://www.cnil.fr/en
  • Irish DPC (guidance, case studies): https://www.dataprotection.ie/

Engineering-focused privacy/security resources​

  • OWASP Cheat Sheet Series (privacy-adjacent secure practices): https://cheatsheetseries.owasp.org/
  • OWASP ASVS (security requirements that support privacy): https://owasp.org/www-project-application-security-verification-standard/

Cloud and platform references (for GCP/Kubernetes teams)​

  • Google Cloud Security documentation: https://cloud.google.com/security
  • Google Cloud Privacy resources: https://cloud.google.com/privacy
  • Kubernetes Security documentation: https://kubernetes.io/docs/concepts/security/

Internal (recommended to maintain)​

  • Link your internal pages here for faster onboarding:
    • Data classification policy
    • Data retention schedule
    • Data subject request (DSR) runbook (export/delete)
    • Incident escalation runbook

Onboarding​

  • New joiners complete training within 30 days of start date (or before production access is granted, whichever is earlier).
  • Production access to systems containing personal data requires either:
    • confirmed completion + passing assessment, or
    • an approved time-bound exception with compensating controls.

Refresher cadence​

  • Refresh training annually, and additionally when:
    • major privacy incidents occur,
    • significant product changes introduce new personal data collection/processing,
    • regulations or internal policy changes materially affect practices.

Ownership​

  • Security/Compliance owns the training curriculum and assessment maintenance.
  • Engineering managers ensure completion for their teams.
  • Platform/SRE enforces access gating where feasible (e.g., role assignments, break-glass procedures).

Evidence & Auditability​

Maintain evidence for audit and internal governance:

  • Training completion records (user, course, date)
  • Assessment result (score, pass/fail, date)
  • Exception approvals (if any) and expiry dates

Recommended storage locations:

  • HR/LMS export, or a compliance tracker (e.g., GRC tool)
  • Ticket references for exceptions

Acceptance Criteria (Definition of Done)​

  • 100% of in-scope team members have completed GDPR foundation training.
  • 100% have passed the assessment (or have an approved, time-bound exception).
  • Training completion and scores are retrievable for audits.
  • Access to production personal data is gated by completion status where feasible.
