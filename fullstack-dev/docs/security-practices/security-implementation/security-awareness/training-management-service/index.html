Training Management Service (Reference)

This page documents the reference TrainingManagementService implementation used in this guide. The goal is to describe the behavior and operational contract (catalog, enrollment, progress, certification, and reporting) without embedding a large code listing.

Purpose​

A training management service provides:

  • A training catalog (modules) grouped by category (OWASP, CWE, compliance, general)
  • A progress ledger per user (enrolled modules, status, scores, completion dates)
  • Certification issuance when a user passes a certifying module
  • A training plan view tailored to a role
  • Reporting views for managers/security leaders

Core data model​

The reference implementation uses simple in-memory data structures:

  • modules: Map<string, TrainingModule>
  • userProgress: Map<string, UserProgress[]>

In production, these should be backed by persistent storage (e.g., Postgres) and should produce auditable evidence.

TrainingModule​

A module represents a single training unit.

Required fields:

  • id: stable identifier (used for enrollment and reporting)
  • title: human name
  • category: OWASP | CWE | COMPLIANCE | GENERAL
  • level: BEGINNER | INTERMEDIATE | ADVANCED
  • duration: minutes (used for planning)
  • prerequisites: module IDs that must be completed first
  • objectives: learning objectives
  • content: ordered items (videos/docs/labs/quizzes)
  • assessment: how passing is measured
  • certification: whether passing also issues a certificate

TrainingContent​

Content items are the pieces a learner consumes.

  • type: VIDEO | DOCUMENT | LAB | QUIZ | DEMO
  • title, url, duration, description

Assessment and Question​

Assessments define the passing rule.

  • type: QUIZ | PRACTICAL | PROJECT
  • passingScore: numeric threshold
  • timeLimit: minutes
  • questions: set of Question

A Question supports multiple formats:

  • type: MULTIPLE_CHOICE | TRUE_FALSE | CODE_REVIEW | SCENARIO
  • correctAnswer: string or string[]
  • explanation: required for learning reinforcement and auditability

UserProgress​

UserProgress is the evidence trail for an individual’s training.

  • userId, moduleId
  • status: NOT_STARTED | IN_PROGRESS | COMPLETED | CERTIFIED
  • score?, completedDate?, certificateId?
  • timeSpent: accumulated minutes (or seconds)

Recommended evidence extensions (for real-world auditability):

  • enrolledDate, startedDate
  • attempts (per assessment)
  • contentCompletions (per content item)
  • immutable event log (TRAINING_ENROLLED, MODULE_STARTED, ASSESSMENT_PASSED, ...)

Primary workflows​

1) Enroll user in module​

Method: enrollUser(userId, moduleId)

Contract:

  • Validates that moduleId exists in the catalog
  • Ensures the user isn’t already enrolled
  • Creates a new UserProgress record with:
    • status: NOT_STARTED
    • timeSpent: 0

Operational notes:

  • In production, enrollment should be idempotent (safe to retry)
  • Consider enforcing prerequisites at enrollment time (or at module start time)

2) Start module​

Method: startModule(userId, moduleId)

Contract:

  • Requires the user to be enrolled (otherwise error)
  • Sets status: IN_PROGRESS

Operational notes:

  • Starting a module is a useful “commit point” for due-date calculations and reminders

3) Complete module and evaluate passing​

Method: completeModule(userId, moduleId, score)

Contract:

  • Requires enrollment
  • Loads module metadata to read assessment.passingScore
  • Sets:
    • score
    • completedDate = now
  • If score >= passingScore, sets status: COMPLETED
  • If the module is certification: true, issues a certificate and sets:
    • certificateId
    • status: CERTIFIED

Operational notes:

  • Persist the raw assessment artifact (answers, rubric, grader identity) if you need stronger evidence
  • Decide whether failing attempts are stored and how retakes are governed

4) Training plan generation​

Method: getTrainingPlan(userId, role)

Goal:

  • Return a curated list of modules appropriate for a user’s role (developer/QA/SRE/security champion)

Typical selection logic (keep simple and deterministic):

  • Baseline general security module(s)
  • OWASP modules for application developers
  • CWE modules for broader secure coding coverage
  • Compliance modules based on project/domain requirements (see the industry-specific training docs)

5) Reporting​

Method: generateTrainingReport(teamId)

Goal:

  • Produce team-level view(s):
    • completion rates
    • average scores
    • number of certifications
    • overdue training (if you model due dates)

Operational notes:

  • Reporting should be filterable by time window (monthly/quarterly) and by module category
  • Consider output formats that work well for audits (CSV export, PDF report, signed snapshots)

Certification issuance​

Method: issueCertificate(userId, moduleId)

The reference implementation generates a certificate ID of the form:

  • CERT-${userId}-${moduleId}-${Date.now()}

For real use:

  • Store certificate metadata (issuer, issue time, validity, revocation)
  • Prefer opaque IDs and avoid embedding user identifiers if certificates are shared externally

Module catalog initialization​

Method: initializeTrainingModules()

The reference implementation populates the module catalog by calling:

  • createOWASPModules()
  • createCWEModules()
  • createComplianceModules()

This structure keeps the “platform” service stable while content definitions live alongside the relevant guide sections.

Production hardening checklist​

If you implement this beyond a reference example:

  • Use persistent storage + migrations; treat progress changes as append-only events
  • Add authorization (who can enroll whom, who can issue certificates, who can view team reports)
  • Add idempotency keys for enrollment/completion endpoints
  • Add observability: structured logs + metrics (completion rate, pass rate, overdue rate)
  • Define evidence retention and export paths for audits
