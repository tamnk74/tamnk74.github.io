OWASP Web Application Security Testing Checklist

The Open Web Application Security Project (OWASP) is a global non-profit organization that provides educational resources to improve software security. Its flagship project, the OWASP Top 10, identifies the most critical security risks to web applications based on their incident rate, exploitability, and potential impact. It is important to note that this list serves as a resource for awareness and is not intended to be a standard or a checklist.

OWASP Top 10 Web Application Security Risks (2021) — Detailed Guidelines (A01–A10)​

The 2021 OWASP Top 10 expanded its scope significantly, mapping to hundreds of CWEs. Use this section as a practical guide for how each risk typically shows up in modern web systems (including Next.js microfrontends and NestJS APIs) and what “good controls” look like.

Each risk below includes:

  • What it is
  • How it commonly appears in a Next.js/NestJS microfrontend system
  • Preventive controls
  • Verification guidance (manual + automated)

A01:2021 — Broken Access Control​

What it is: Authorization is missing or incorrectly enforced, allowing users to perform actions or access data they should not.

Common in Next.js/NestJS microfrontends:

  • IDOR (Insecure Direct Object Reference): accessing /api/orders/123 belonging to another user
  • Missing object-level checks in NestJS controllers/services
  • Admin-only functions exposed via client routes or insufficient server-side role checks
  • Multi-tenant isolation gaps (tenant ID not enforced server-side)

Preventive controls:

  • Enforce authorization server-side for every request (deny by default)
  • Centralize policy (RBAC/ABAC) in guards/interceptors, not in UI only
  • Apply object-level authorization (resource ownership checks)
  • Separate admin APIs, strong role checks, and environment gating

Verification:

  • Integration tests: forbidden for wrong user/tenant, forbidden for missing roles
  • DAST: run ZAP/Burp tests for IDOR patterns on critical endpoints
  • Review: confirm client does not make security decisions (UI controls are not authorization)

A02:2021 — Cryptographic Failures​

What it is: Sensitive data is not properly protected in transit, at rest, or during processing.

Common in Next.js/NestJS microfrontends:

  • Cookies missing Secure, HttpOnly, or SameSite attributes
  • Tokens, passwords, or API keys logged or stored in local storage
  • Weak password hashing or missing password peppering strategy
  • Misuse of encryption (homegrown crypto, wrong modes, key reuse)

Preventive controls:

  • TLS everywhere (including internal service calls where appropriate)
  • Store secrets in Secret Manager; never commit secrets to repo
  • Hash passwords with modern algorithms (Argon2/bcrypt) and safe parameters
  • Use KMS-managed keys for encryption; define rotation strategy

Verification:

  • Automated checks: secret scanning and dependency scanning in CI
  • Runtime checks: security headers and cookie attribute validation
  • Review: verify logs do not contain sensitive fields

A03:2021 — Injection​

What it is: Untrusted data is interpreted as commands/queries due to insufficient validation or unsafe composition.

Common in Next.js/NestJS microfrontends:

  • SQL/NoSQL injection in search/filter endpoints
  • Command injection in image/video processing or “export” features
  • Template injection in server-side rendering contexts
  • Log injection (untrusted strings used in logs without sanitization)

Preventive controls:

  • Parameterize queries (ORM query builders, prepared statements)
  • Validate and canonicalize inputs at API boundaries
  • Use allowlists for accepted values (enums, strict schemas)
  • Avoid dynamic code execution, shelling out, or unsafe interpreters

Verification:

  • SAST: add a scanner (Semgrep/CodeQL) for injection patterns
  • DAST: ZAP active scan focused on injection points
  • Unit tests: validation rejects malicious payloads

A04:2021 — Insecure Design​

What it is: Security is not designed into the system, leading to missing controls even if code is “correct.”

Common in Next.js/NestJS microfrontends:

  • Missing threat modeling and abuse cases for critical flows (checkout, refunds)
  • No rate limiting, leading to credential stuffing or inventory hoarding
  • Weak trust boundaries between MFEs (assumptions about identity/roles)
  • Missing secure-by-default patterns for new services or endpoints

Preventive controls:

  • Threat model critical flows and define abuse cases
  • Apply defense-in-depth: rate limiting, fraud controls, step-up auth
  • Define secure reference architectures and reusable security components
  • Add “security acceptance criteria” to epics for high-risk features

Verification:

  • Architecture review: confirm abuse cases are addressed
  • Chaos/abuse testing in non-prod for high-risk flows
  • Security design review as a required step for certain changes

A05:2021 — Security Misconfiguration​

What it is: Insecure defaults, overly permissive settings, exposed debug endpoints, or misconfigured cloud resources.

Common in Next.js/NestJS microfrontends (GCP):

  • Public buckets or overly broad IAM roles
  • CORS overly permissive (*) on sensitive APIs
  • Missing HTTP security headers
  • Debug endpoints enabled in production

Preventive controls:

  • Infrastructure as code with review gates
  • Principle of least privilege for IAM and service accounts
  • Centralized security headers (CSP, HSTS, etc.)
  • Separate configs per environment and strict production hardening

Verification:

  • IaC scanning (policy checks) and container scanning in CI
  • Automated config tests (headers, CORS policy)
  • Periodic cloud posture reviews

A06:2021 — Vulnerable and Outdated Components​

What it is: Using libraries, frameworks, or runtimes with known vulnerabilities, or without a patch/upgrade strategy.

Common in Next.js/NestJS microfrontends:

  • Stale dependencies across multiple MFEs (version drift)
  • Unpinned transitive dependencies
  • Unsupported Node.js or base images

Preventive controls:

  • Automate dependency updates (Dependabot/Renovate)
  • Maintain an SBOM and define patch SLAs
  • Prefer minimal base images and keep runtimes current

Verification:

  • Dependency scanning in GitHub Actions
  • CI gate on critical vulnerabilities
  • Periodic “upgrade sprint” or rolling maintenance capacity

A07:2021 — Identification and Authentication Failures​

What it is: Weaknesses in authentication, session management, or identity lifecycle.

Common in Next.js/NestJS microfrontends:

  • Weak password policy or missing MFA for admin
  • Session fixation or insecure cookie configuration
  • Missing brute-force protections
  • Broken logout or token revocation

Preventive controls:

  • Use proven auth frameworks and secure defaults
  • Enforce MFA for privileged users
  • Add rate limiting, lockouts, and anomaly detection
  • Use short-lived access tokens with refresh rotation where appropriate

Verification:

  • Automated tests for auth flows (login, refresh, logout)
  • Security testing for session and cookie handling
  • Monitor auth anomalies and alert on suspicious patterns

A08:2021 — Software and Data Integrity Failures​

What it is: Integrity of code, artifacts, updates, or critical data is not verified, enabling tampering or supply-chain attacks.

Common in Next.js/NestJS microfrontends:

  • Untrusted CI actions or dependencies executed during builds
  • Remote microfrontend assets updated without integrity controls
  • Unsigned containers or unverified build provenance

Preventive controls:

  • Pin GitHub Actions by commit SHA where feasible
  • Use lockfiles and verify dependency integrity
  • Sign container images and verify at deploy time
  • Protect release branches and require reviews

Verification:

  • CI policy checks for allowed actions and branch protection
  • Artifact signing verification in deployment pipeline
  • Periodic supply-chain review

A09:2021 — Security Logging and Monitoring Failures​

What it is: Missing or insufficient logging/monitoring to detect, investigate, and respond to attacks.

Common in Next.js/NestJS microfrontends (GCP):

  • Security events not logged (auth failures, permission denials)
  • Logs without correlation IDs (hard to investigate)
  • No alerts for suspicious patterns

Preventive controls:

  • Log security events with correlation IDs and consistent schemas
  • Define alert rules for auth anomalies and suspicious behaviors
  • Ensure logs are retained and searchable (with access controls)

Verification:

  • Run incident drills and confirm investigators can reconstruct events
  • Validate alert routing and on-call ownership
  • Monitor logging coverage and drop rates

A10:2021 — Server-Side Request Forgery (SSRF)​

What it is: The server can be tricked into making network requests to unintended destinations (including internal services).

Common in NestJS services:

  • Features that fetch URLs from user input (webhooks, image import, URL preview)
  • Access to cloud metadata endpoints from server-side code

Preventive controls:

  • Allowlist outbound destinations; block private ranges by default
  • Use safe URL parsing and reject unusual schemes
  • Add egress controls (firewall rules) for sensitive environments
  • Protect metadata endpoints and service-to-service identity

Verification:

  • Security tests for URL fetch endpoints (private IPs, metadata hostnames)
  • E2E tests for “URL import” flows with malicious inputs

Comparison of Security Frameworks Understanding the relationship between different frameworks is essential for a comprehensive security posture: • OWASP: Provides broad educational resources and categorizes high-level software security risks. • CWE (Common Weakness Enumeration): Identifies and categorizes the specific technical root causes of vulnerabilities. • CVE (Common Vulnerabilities and Exposures): Lists specific, publicly known instances of vulnerabilities in particular products.

A comprehensive security testing checklist for web applications based on OWASP (Open Web Application Security Project) standards.

Information Gathering​

Reconnaissance and Discovery
  • Manually explore the site
  • Spider/crawl for missed or hidden content
  • Check for files that expose content, such as robots.txt, sitemap.xml, .DS_Store
  • Check the caches of major search engines for publicly accessible sites
  • Check for differences in content based on User Agent (e.g., Mobile sites, access as a Search engine Crawler)
  • Perform Web Application Fingerprinting
  • Identify technologies used
  • Identify user roles
  • Identify application entry points
  • Identify client-side code
  • Identify multiple versions/channels (e.g., web, mobile web, mobile app, web services)
  • Identify co-hosted and related applications
  • Identify all hostnames and ports
  • Identify third-party hosted content
Why This Matters

Information gathering is the first phase of security testing. Understanding the application's architecture, technologies, and attack surface is crucial for identifying potential vulnerabilities.

Configuration Management​

Server and Application Configuration
  • Check for commonly used application and administrative URLs
  • Check for old, backup and unreferenced files
  • Check HTTP methods supported and Cross Site Tracing (XST)
  • Test file extensions handling
  • Test for security HTTP headers (e.g., CSP, X-Frame-Options, HSTS)
  • Test for policies (e.g., Flash, Silverlight, robots)
  • Test for non-production data in live environment, and vice-versa
  • Check for sensitive data in client-side code (e.g., API keys, credentials)
Common Misconfigurations
  • Exposed backup files (.bak, .old, .backup)
  • Default admin URLs (/admin, /administrator, /wp-admin)
  • Missing security headers
  • API keys in client-side code

Secure Transmission​

SSL/TLS and Data Transmission Security
  • Check SSL Version, Algorithms, Key length
  • Check for Digital Certificate Validity (Duration, Signature and CN)
  • Check credentials only delivered over HTTPS
  • Check that the login form is delivered over HTTPS
  • Check session tokens only delivered over HTTPS
  • Check if HTTP Strict Transport Security (HSTS) in use

Recommended Tools:

  • SSL Labs SSL Test
  • testssl.sh
  • Mozilla Observatory

Authentication​

Identity Verification and Access Control
  • Test for user enumeration
  • Test for authentication bypass
  • Test for bruteforce protection
  • Test password quality rules
  • Test remember me functionality
  • Test for autocomplete on password forms/input
  • Test password reset and/or recovery
  • Test password change process
  • Test CAPTCHA
  • Test multi-factor authentication
  • Test for logout functionality presence
  • Test for cache management on HTTP (e.g., Pragma, Expires, Max-age)
  • Test for default logins
  • Test for user-accessible authentication history
  • Test for out-of-channel notification of account lockouts and successful password changes
  • Test for consistent authentication across applications with shared authentication schema / SSO
Critical Authentication Issues

High Priority:

  • Weak password policies
  • Missing bruteforce protection
  • Insecure password recovery
  • No multi-factor authentication
  • User enumeration vulnerabilities

Session Management​

Session Handling and Token Security
  • Establish how session management is handled in the application (e.g., tokens in cookies, token in URL)
  • Check session tokens for cookie flags (httpOnly and secure)
  • Check session cookie scope (path and domain)
  • Check session cookie duration (expires and max-age)
  • Check session termination after a maximum lifetime
  • Check session termination after relative timeout
  • Check session termination after logout
  • Test to see if users can have multiple simultaneous sessions
  • Test session cookies for randomness
  • Confirm that new session tokens are issued on login, role change and logout
  • Test for consistent session management across applications with shared session management
  • Test for session puzzling
  • Test for CSRF and clickjacking

Session Cookie Best Practices:

// Example: Secure session cookie configuration
Set-Cookie: sessionId=abc123;
  Secure;
  HttpOnly;
  SameSite=Strict;
  Path=/;
  Max-Age=3600

Authorization​

Access Control and Privilege Management
  • Test for path traversal
  • Test for bypassing authorization schema
  • Test for vertical Access control problems (a.k.a. Privilege Escalation)
  • Test for horizontal Access control problems (between two users at the same privilege level)
  • Test for missing authorization
Authorization Anti-Patterns

Common Mistakes:

  • Client-side only authorization checks
  • Insecure Direct Object References (IDOR)
  • Missing function-level access control
  • Confused deputy problems

Data Validation​

Input Validation and Injection Prevention

Cross-Site Scripting (XSS)​

  • Test for Reflected Cross Site Scripting
  • Test for Stored Cross Site Scripting
  • Test for DOM based Cross Site Scripting
  • Test for Cross Site Flashing
  • Test for HTML Injection

Injection Attacks​

  • Test for SQL Injection
  • Test for SOQL Injection
  • Test for LDAP Injection
  • Test for ORM Injection
  • Test for XML Injection
  • Test for XXE Injection
  • Test for SSI Injection
  • Test for XPath Injection
  • Test for XQuery Injection
  • Test for IMAP/SMTP Injection
  • Test for Code Injection
  • Test for Expression Language Injection
  • Test for Command Injection
  • Test for NoSQL injection

Other Validation Issues​

  • Test for Overflow (Stack, Heap and Integer)
  • Test for Format String
  • Test for incubated vulnerabilities
  • Test for HTTP Splitting/Smuggling
  • Test for HTTP Verb Tampering
  • Test for Open Redirection
  • Test for Local File Inclusion
  • Test for Remote File Inclusion
  • Compare client-side and server-side validation rules
  • Test for HTTP parameter pollution
  • Test for auto-binding
  • Test for Mass Assignment
  • Test for NULL/Invalid Session Cookie
OWASP Top 10 Injection Risks

Injection flaws (SQL, NoSQL, OS, LDAP) consistently rank in the OWASP Top 10. Always validate and sanitize user input on the server side.

Denial of Service​

Availability and Resource Exhaustion
  • Test for anti-automation
  • Test for account lockout
  • Test for HTTP protocol DoS
  • Test for SQL wildcard DoS

Mitigation Strategies:

  • Rate limiting
  • Request throttling
  • CAPTCHA implementation
  • Resource quotas
  • Input size limits

Business Logic​

Application Logic and Workflow Security
  • Test for feature misuse
  • Test for lack of non-repudiation
  • Test for trust relationships
  • Test for integrity of data
  • Test segregation of duties
Business Logic Examples
  • Price manipulation in e-commerce
  • Workflow bypassing (e.g., checkout without payment)
  • Race conditions in concurrent operations
  • Time-of-check to time-of-use (TOCTOU) issues

Cryptography​

Encryption and Cryptographic Controls
  • Check if data which should be encrypted is not
  • Check for wrong algorithms usage depending on context
  • Check for weak algorithms usage
  • Check for proper use of salting
  • Check for randomness functions
  • ✅ Strong Crypto
  • ❌ Weak Crypto

Recommended:

  • AES-256 for symmetric encryption
  • RSA-2048+ or ECC for asymmetric encryption
  • SHA-256+ for hashing
  • bcrypt, scrypt, or Argon2 for passwords
  • Properly seeded CSPRNG for random values

Avoid:

  • DES, 3DES, RC4
  • MD5, SHA-1 for security purposes
  • ECB mode
  • Hardcoded encryption keys
  • Weak random number generators

Risky Functionality - File Uploads​

File Upload Security Controls
  • Test that acceptable file types are whitelisted
  • Test that file size limits, upload frequency and total file counts are defined and are enforced
  • Test that file contents match the defined file type
  • Test that all file uploads have Anti-Virus scanning in-place
  • Test that unsafe filenames are sanitized
  • Test that uploaded files are not directly accessible within the web root
  • Test that uploaded files are not served on the same hostname/port
  • Test that files and other media are integrated with the authentication and authorization schemas
File Upload Attack Vectors

Common Exploits:

  • Malicious file execution (web shells)
  • Path traversal via filename
  • File type confusion attacks
  • ZIP bombs and decompression attacks
  • XXE via SVG/XML files
  • XSS via SVG files

Risky Functionality - Card Payment​

PCI DSS Compliance and Payment Security
  • Test for known vulnerabilities and configuration issues on Web Server and Web Application
  • Test for default or guessable password
  • Test for non-production data in live environment, and vice-versa
  • Test for Injection vulnerabilities
  • Test for Buffer Overflows
  • Test for Insecure Cryptographic Storage
  • Test for Insufficient Transport Layer Protection
  • Test for Improper Error Handling
  • Test for all vulnerabilities with a CVSS v2 score > 4.0
  • Test for Authentication and Authorization issues
  • Test for CSRF
PCI DSS Requirements

If you handle, process, or transmit credit card information, you must comply with PCI DSS standards. Consider using third-party payment processors (Stripe, PayPal) to reduce PCI scope.

HTML 5​

Modern Web API Security
  • Test Web Messaging (postMessage)
  • Test for Web Storage SQL injection
  • Check CORS implementation
  • Check Offline Web Application security

Security Testing Tools​

Automated Scanners​

  • OWASP ZAP - Open source web application security scanner
  • Burp Suite - Web vulnerability scanner and proxy
  • Nikto - Web server scanner
  • SQLMap - SQL injection testing tool
  • Nmap - Network scanner

Browser Extensions​

  • Wappalyzer - Technology detection
  • Cookie Editor - Cookie manipulation
  • ModHeader - HTTP header modification
  • EditThisCookie - Cookie management

Command-Line Tools​

# SSL/TLS Testing
testssl.sh https://example.com

# Directory Brute-forcing
gobuster dir -u https://example.com -w wordlist.txt

# Subdomain Enumeration
subfinder -d example.com

# Security Headers Check
curl -I https://example.com | grep -i "x-"

Testing Methodology​

1. Planning Phase​

  • Define scope and objectives
  • Identify critical functionality
  • Gather authorization and permissions

2. Reconnaissance​

  • Information gathering
  • Technology identification
  • Attack surface mapping

3. Vulnerability Assessment​

  • Automated scanning
  • Manual testing
  • Code review

4. Exploitation​

  • Proof of concept development
  • Impact assessment
  • Risk prioritization

5. Reporting​

  • Document findings
  • Provide remediation guidance
  • Create executive summary
