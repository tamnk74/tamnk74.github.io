E-Commerce Platform — Million-User Scale Design

A Solution Architect's guide to designing a production-grade distributed e-commerce platform using microservices, microfrontends, GCP Kubernetes, and ArgoCD.

Problem Statement​

Design an e-commerce platform that:

  • Serves 1 million+ concurrent users with p99 latency < 200 ms for product pages
  • Handles flash sales with 10× traffic spikes without degradation
  • Supports independent team deployments — 8+ squads shipping without coordination
  • Provides real-time inventory, pricing, and order status
  • Achieves 99.99% availability (< 52 min downtime/year)

Scale Envelope​

Monthly Active Users10 million
Peak Concurrent Users1 million
Product Catalog5 million SKUs
Orders / day500,000
Page views / second (peak)50,000
Checkout throughput5,000 TPS
Message events / day50 million

Microfrontend Architecture​

Why Microfrontends at this Scale​

Problem: 8 squads, one monolithic Next.js app → merge conflicts, long CI pipelines, coupled deployments, inability to A/B test independently.

Solution: Module Federation (Webpack 5) — each domain owns its own deployable Next.js remote.

Module Federation Config (Shell)​

// shell/next.config.ts
import { NextFederationPlugin } from '@module-federation/nextjs-mf';

module.exports = {
  webpack(config) {
    config.plugins.push(
      new NextFederationPlugin({
        name: 'shell',
        remotes: {
          catalog: `catalog@${process.env.CATALOG_REMOTE_URL}/_next/static/chunks/remoteEntry.js`,
          cart:    `cart@${process.env.CART_REMOTE_URL}/_next/static/chunks/remoteEntry.js`,
          account: `account@${process.env.ACCOUNT_REMOTE_URL}/_next/static/chunks/remoteEntry.js`,
          search:  `search@${process.env.SEARCH_REMOTE_URL}/_next/static/chunks/remoteEntry.js`,
        },
        shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
      })
    );
    return config;
  },
};

MFE Integration Contract​

Each remote must expose the following contract — no implicit global state:

RemoteExposed ComponentProps InEvents Out
catalog<ProductListingPage />categoryId, filtersonAddToCart(sku, qty)
catalog<ProductDetailPage />productIdonAddToCart, onWishlist
cart<CartWidget />userIdonCheckoutComplete(orderId)
cart<CheckoutFlow />cartId, addressIdonOrderPlaced(orderId)
search<SearchBar />placeholderonSearch(query)
account<OrderHistory />userId—

Rule: MFEs communicate via custom DOM events or URL routing only — never via shared mutable store. See MFE Communication Patterns for implementation examples.

Outbox Pattern (reliable event publishing)​

// order.service.ts — atomic write + outbox in one transaction
await this.dataSource.transaction(async (em) => {
  const order = em.create(Order, { ...dto, status: 'PENDING' });
  await em.save(order);

  await em.save(Outbox, {
    aggregateType: 'Order',
    aggregateId: order.id,
    eventType: 'order.created',
    payload: JSON.stringify(order),
  });
});

Flash Sale Inventory — Redis Atomic Decrement​

// inventory.service.ts
async reserveStock(sku: string, qty: number): Promise<boolean> {
  const key = `stock:${sku}`;
  // Lua script: atomic check-and-decrement
  const script = `
    local stock = tonumber(redis.call('GET', KEYS[1]))
    if stock == nil or stock < tonumber(ARGV[1]) then return 0 end
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
  `;
  const result = await this.redis.eval(script, 1, key, qty.toString());
  return result === 1;
}

Handles 50,000 concurrent reservation attempts without database pressure. See Flash Sale Inventory: Redis Atomic Decrement for the full implementation guide (Lua scripts, pre-sale stock loading, per-user limits, KEDA pre-scaling, and post-sale reconciliation).

kind: IngressRoute
metadata:
  name: ecommerce-api
  namespace: production

  entryPoints: [websecure]
  routes:
    - match: Host(`api.ecom.io`) && PathPrefix(`/products`)
      kind: Rule
      services: [{ name: product-service, port: 3000 }]
      middlewares:
        - name: rate-limit-products    # 10,000 req/min per IP
        - name: jwt-auth
        - name: circuit-breaker        # open at 50% failure rate
    - match: Host(`api.ecom.io`) && PathPrefix(`/orders`)

      services: [{ name: order-service, port: 3001 }]

        - name: rate-limit-orders      # 500 req/min per user

ArgoCD ApplicationSet (Multi-Service)​

# apps/production/ecommerce-services.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: ecommerce-services
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - service: order-service
            port: "3001"
          - service: product-service
            port: "3000"
          - service: cart-service
            port: "3002"
          - service: payment-service
            port: "3003"
  template:
    metadata:
      name: "{{service}}-production"
    spec:
      project: ecommerce
      source:
        repoURL: https://github.com/org/infra
        targetRevision: main
        path: overlays/production/{{service}}
      destination:
        server: https://kubernetes.default.svc
        namespace: production
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
        retry:
          limit: 3
          backoff: { duration: 5s, factor: 2, maxDuration: 3m }

Progressive Delivery (Canary)​

For high-risk services (payment, order), use Argo Rollouts:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-service
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5      # 5% traffic to new version
        - pause: { duration: 5m }
        - analysis:         # auto-rollback if error rate > 1%
            templates: [{ templateName: success-rate }]
        - setWeight: 20
        - pause: { duration: 10m }
        - setWeight: 100

Observability Stack​

SLO Dashboards per Service​

// NestJS: custom metrics with OpenTelemetry
import { metrics } from '@opentelemetry/api';

const meter = metrics.getMeter('order-service', '1.0.0');
const checkoutDuration = meter.createHistogram('checkout.duration.ms', {
  description: 'End-to-end checkout latency',
  boundaries: [50, 100, 200, 500, 1000, 3000],
});
const checkoutErrors = meter.createCounter('checkout.errors.total');

// In checkout handler:
const start = Date.now();
try {
  await this.processCheckout(dto);
  checkoutDuration.record(Date.now() - start, { status: 'success' });
} catch (err) {
  checkoutErrors.add(1, { reason: err.constructor.name });
  checkoutDuration.record(Date.now() - start, { status: 'error' });
  throw err;
}

Security Architecture​

  • Edge: Cloudflare WAF blocks OWASP Top 10, DDoS protection — see Cloudflare WAF & DDoS Protection
  • API Gateway: Auth0 JWT validation on every request; rate limiting per user/IP
  • Service-to-service: mTLS via Cilium service mesh; no service can call payment without explicit network policy — see Cilium mTLS & Service-to-Service Authorization
  • Secrets: GCP Secret Manager + External Secrets Operator; no secrets in environment variables or Git — see GCP Secret Manager + External Secrets Operator
  • PCI-DSS: Payment service in isolated namespace; no card data stored (tokenized by Stripe) — see PCI-DSS: Payment Service Isolation & Stripe Tokenization
  • PII: User data encrypted at rest (CMEK); audit log on all data access — see PII Encryption (CMEK) & Audit Logging

Automatic Secret Rotation (Zero Downtime)​

Secrets are rotated automatically without redeployment using a dual-version overlap strategy:

Key rule: never disable the old secret version until ESO has confirmed the new one is synced. Set the overlap window ≥ refreshInterval + 2 min. For apps with connection pools (NestJS/TypeORM), trigger a rolling restart after sync — kubectl rollout restart deployment/<svc> — so the pool reconnects with the new credential.

For the full implementation (Cloud Function with verifyKubernetesSecretSynced, two-phase DB rotation, rolling restart Job, refreshInterval tuning per secret type), see GCP Secret Manager + External Secrets Operator — Zero-Downtime Rotation.
