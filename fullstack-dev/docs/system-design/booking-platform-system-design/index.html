Booking.com: Hotel Booking Platform — System Design

Overview​

Design a hotel booking platform similar to Booking.com that allows users to search for accommodations by location/date/guests, view property details with photos and reviews, and complete reservations with payment. The system must handle high-volume search traffic, maintain real-time inventory accuracy to prevent double-bookings, and support millions of concurrent users during peak travel seasons.

Scope: hotel/accommodation booking (not flights, car rental, or experiences). Focus on the core search → select → book → confirm flow.

Scale Estimates​

Users:

  • 30M MAU, 5M DAU, 500k peak concurrent sessions
  • 80% of traffic is search/browse (read-heavy workload)

Properties:

  • 2M properties × avg 20 room types = 40M inventory units
  • 1M+ price updates/day (dynamic pricing, seasonal rates)

Bookings:

  • 1.5M bookings/day = ~17 bookings/s average, 200 bookings/s peak
  • Avg booking value: 180;dailyGMV:180; daily GMV: 180;dailyGMV:270M

Search:

  • 500M searches/day = ~6k/s average, 50k/s peak (holiday season)
  • Avg result set: 200 properties filtered to top 25 per page

Storage:

  • Property data: ~5 KB/property × 2M = 10 GB (metadata, descriptions)
  • Photos: 50 photos/property × 2M × 500 KB = 50 TB (CDN-backed)
  • Booking records: ~2 KB × 1.5M/day × 365 = ~1 TB/year
  • Search index: ~100 GB (Elasticsearch/Solr cluster)

Step 4: Core Service Design​

4.1 Search Service​

Responsibilities: full-text search, geo-based search, filtering, sorting, ranking, autocomplete, search result caching.

Elasticsearch index design:

Ranking factors: relevance score × availability × review score × conversion rate × commission tier.

4.2 Inventory Service​

Responsibilities: maintain real-time room availability, handle allotment management, prevent double-bookings, support rate plans and restrictions.

This is the most consistency-critical service — it must guarantee zero overselling.

Inventory data model:

-- Room availability per night
room_inventory (
  id              UUID PRIMARY KEY,
  property_id     UUID NOT NULL,
  room_type_id    UUID NOT NULL,
  date            DATE NOT NULL,
  total_rooms     INT NOT NULL,       -- base allotment
  sold_rooms      INT NOT NULL DEFAULT 0,
  held_rooms      INT NOT NULL DEFAULT 0,  -- temporary holds (pending payment)
  available       INT GENERATED ALWAYS AS (total_rooms - sold_rooms - held_rooms) STORED,
  min_stay        INT DEFAULT 1,
  closed          BOOLEAN DEFAULT FALSE,
  UNIQUE(property_id, room_type_id, date)
);

-- Temporary hold (released if payment fails within TTL)
reservation_holds (
  id              UUID PRIMARY KEY,
  booking_ref     UUID NOT NULL,
  property_id     UUID NOT NULL,
  room_type_id    UUID NOT NULL,
  date            DATE NOT NULL,
  qty             INT NOT NULL,
  expires_at      TIMESTAMPTZ NOT NULL,
  status          VARCHAR(20) DEFAULT 'active'  -- active | confirmed | expired
);

Double-booking prevention strategy:

  1. Pessimistic locking — SELECT ... FOR UPDATE at the DB level per (property, room_type, date) tuple.
  2. Redis distributed lock — coarse-grained lock prevents thundering herd on the same room.
  3. Hold + confirm — two-phase: a 15-minute hold is placed, then confirmed on payment success; expired holds are released by a sweeper job.
  4. Idempotency — booking_ref is unique per hold; retries are safe.

4.4 Pricing Service​

Responsibilities: dynamic pricing, rate plan management, tax/fee calculations, currency conversion, promotional codes.

Price calculation formula:

NightlyRate=BaseRate×DemandMultiplier×SeasonalFactor×LOSDiscount\text{NightlyRate} = \text{BaseRate} \times \text{DemandMultiplier} \times \text{SeasonalFactor} \times \text{LOSDiscount}NightlyRate=BaseRate×DemandMultiplier×SeasonalFactor×LOSDiscount Total=∑i=1nNightlyRatei+CleaningFee+ServiceFee+Taxes\text{Total} = \sum_{i=1}^{n} \text{NightlyRate}_i + \text{CleaningFee} + \text{ServiceFee} + \text{Taxes}Total=i=1∑n​NightlyRatei​+CleaningFee+ServiceFee+Taxes

Rate caching strategy:

  • Redis hash per property-room: rate:{property_id}:{room_type_id} → { "2026-06-15": 189.00, "2026-06-16": 199.00, ... }
  • TTL: 5 minutes (invalidated on host rate update)
  • Stale reads are acceptable for search results; final price is recalculated at checkout.

4.5 Payment Service​

Responsibilities: PCI-compliant payment capture, refunds, split payouts to property owners, fraud scoring.

Payout flow (T+1 after checkout):

  • Daily batch job calculates commission split (platform fee: 15–25%).
  • Initiates payout to property owner's bank account via payment gateway transfer.
  • Records in payouts table with reconciliation ID.

4.6 Property Service​

Responsibilities: property listings CRUD, room types, amenities, photo management, property verification.

Data model:

properties (
  id              UUID PRIMARY KEY,
  owner_id        UUID NOT NULL,
  name            VARCHAR(255) NOT NULL,
  description     TEXT,
  property_type   VARCHAR(50),     -- hotel, apartment, villa, hostel
  star_rating     DECIMAL(2,1),
  address         TEXT NOT NULL,
  city            VARCHAR(100),
  country         VARCHAR(3),      -- ISO 3166
  location        GEOGRAPHY(POINT, 4326),  -- PostGIS
  amenities       TEXT[],          -- wifi, pool, parking, etc.
  check_in_time   TIME DEFAULT '15:00',
  check_out_time  TIME DEFAULT '11:00',
  cancellation_policy VARCHAR(50),
  is_active       BOOLEAN DEFAULT TRUE,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);

room_types (
  id              UUID PRIMARY KEY,
  property_id     UUID REFERENCES properties(id),
  name            VARCHAR(100),    -- "Deluxe Double", "Standard Twin"
  max_guests      INT NOT NULL,
  bed_config      JSONB,           -- [{type: "king", qty: 1}]
  base_rate       DECIMAL(10,2),
  amenities       TEXT[],
  photos          TEXT[],          -- URLs in object storage
  size_sqm        INT
);

Photo pipeline:

  1. Manager uploads via Extranet → API Gateway → Property Service.
  2. Photo stored in GCS/S3 with UUID filename.
  3. Async worker generates multiple resolutions: thumbnail (150px), card (400px), gallery (1200px), full (2400px).
  4. Served via CDN with Cache-Control: public, max-age=31536000, immutable.

Step 6: Key Design Decisions​

Search Architecture​

DecisionChoiceRationale
Search engineElasticsearchGeo queries, full-text, facets, nested objects, proven at scale
Index updateNear-real-time (async via Kafka)Property/rate changes published → consumer re-indexes; < 30 s lag acceptable
Cache layerRedis (60 s TTL)Same search within a minute returns instantly; reduces ES load by 70%
AutocompleteElasticsearch completion suggesterSub-50 ms response, handles typos

Inventory Consistency​

ApproachTrade-off
Pessimistic lock (FOR UPDATE)Serialises writes per room-night; ensures zero oversell; bottleneck under extreme contention
Distributed Redis lock + DB lockRedis lock reduces contention reaching Postgres; DB lock is the final authority
Hold + confirm (2-phase)15-min hold prevents blocking inventory indefinitely during payment flow
Compensation (release on failure)If payment fails or times out, hold is released; sweeper job handles orphans

Eventual Consistency (Acceptable)​

DomainWhy eventual is OK
Search resultsOK to show a sold-out room for ≤ 30 s; user gets "sold out" at booking time
Review scoresUpdated async after new review; sub-minute lag is fine
Pricing displayStale by ≤ 5 min in search; recalculated at checkout

Step 7: Infrastructure and Deployment​

Multi-region strategy:

  • Writes (bookings, inventory) always go to the primary region.
  • Reads (search, property details) served from the nearest region via read replicas.
  • Latency-based routing at the CDN/load-balancer level routes users to the closest PoP.
  • Failover: if primary region fails, promote read replica to primary (RTO < 5 min).

Scaling targets:

ComponentStrategy
API GatewayHPA on CPU (target 60%)
Search ServiceHPA on request rate + ES connection pool saturation
Booking ServiceHPA on queue depth + CPU
Elasticsearch3 master + N data nodes; scale data nodes on disk/query load
PostgreSQLVertical scale for writes; read replicas for reads
RedisCluster mode (6+ shards); scale on memory + connections
KafkaAdd partitions per topic as consumer lag grows

Step 10: Failure Modes and Resilience​

FailureImpactMitigation
Payment gateway timeoutBooking stuck in pendingRetry with idempotency key (max 3); if still timeout, mark as payment_timeout, notify user to retry
Elasticsearch cluster downSearch unavailableCircuit breaker → return degraded results from Redis cache; alert on-call
Redis failureCache miss, rate limit bypassFallback to DB queries (slower); rate limiting degrades gracefully
Inventory lock contentionBooking latency spikeRedis lock has 5 s TTL; exponential backoff with jitter; max 3 retries
Hold expiry race conditionDouble-booking riskSweeper job runs every 60 s; CHECK (available >= 0) constraint at DB level is the final guard
Kafka consumer lagDelayed notifications, stale search indexAuto-scale consumers; alert on lag > 60 s; notifications are non-critical path
Primary DB failureWrite unavailabilityAutomated failover to replica (< 5 min); bookings queue in Kafka until writes resume

Notes​

  • This design covers the accommodation booking vertical. Adding flights/car rental introduces GDS integration (Amadeus/Sabre) and significantly different data models.
  • The zero-oversell guarantee is the single hardest technical challenge. The hold + confirm pattern with DB-level constraints is the industry standard approach.
  • SEO is critical for a booking platform — property pages must be server-rendered with structured data (Schema.org LodgingBusiness), meta tags, and canonical URLs.
  • Rate parity agreements with hotel chains may require real-time price matching logic — this is a Phase 3+ concern.
