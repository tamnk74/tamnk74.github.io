Auth0 System Design: Identity-as-a-Service Platform

Overview​

Auth0 (now part of Okta) is a cloud-based Identity-as-a-Service (IDaaS) platform that provides authentication, authorization, and user management for web, mobile, and API applications. This document explores the system design principles, architecture patterns, and scalability considerations behind building a platform like Auth0.

System Requirements & Assumptions​

Functional Requirements​

  • Authentication: Support multiple identity protocols (OAuth 2.0, OpenID Connect, SAML, WS-Federation)
  • Universal Login: Centralized, customizable login page serving all applications under a tenant
  • Social Connections: Federate identity with 30+ social providers (Google, Facebook, GitHub, etc.)
  • Enterprise Federation: SAML, LDAP, Active Directory, Azure AD integration
  • Multi-Factor Authentication (MFA): TOTP, SMS OTP, push notifications, WebAuthn/FIDO2
  • Single Sign-On (SSO): Seamless authentication across multiple applications
  • User Management: CRUD operations on user profiles, metadata, and roles
  • Role-Based Access Control (RBAC): Permissions and role assignment
  • Fine-Grained Authorization (FGA): Relationship-based access control (Zanzibar-style)
  • Actions/Extensibility: Custom Node.js functions executed at specific points in the authentication pipeline
  • Anomaly Detection: Brute-force protection, breached password detection, suspicious IP blocking
  • Token Management: JWT issuance, refresh token rotation, token revocation

Non-Functional Requirements​

NFRTarget
Availability99.99% SLA for authentication endpoints
Latency (p99)< 200ms for token issuance, < 500ms for login page render
ThroughputMillions of authentications per day across all tenants
Data ConsistencyStrong consistency for credential verification; eventual for analytics
SecuritySOC 2 Type II, HIPAA, PCI DSS, GDPR compliant
ScalabilityHorizontal scaling; multi-region with automatic failover
Multi-tenancyFull tenant isolation with configurable data residency

Scale Assumptions​

  • Tenants: 100,000+ active tenants (each = one customer organization)
  • Users: Billions of user profiles across all tenants
  • Peak RPS: 100,000+ authentication requests per second globally
  • Token Operations: Millions of JWT minting/validation per minute
  • Regions: Deployed across US, EU, AU, JP, UK, CA

Core Components Deep Dive​

1. Universal Login​

The Universal Login page is the centralized authentication UI that all tenant applications redirect to.

Design Decisions:

  • Server-rendered + client-hydrated — fast initial paint, then interactive
  • Tenant-specific theming — branding, colors, logos loaded from tenant config
  • Lock widget — embeddable JS widget for tenants preferring in-app login
  • PKCE by default — Authorization Code + PKCE for all public clients

2. Token Service​

Responsible for minting, validating, and revoking JWTs following the OAuth 2.0 / OIDC specs.

Key Design Patterns:

  • Asymmetric signing — RS256 (RSA) or ES256 (ECDSA) with automatic key rotation
  • JWKS endpoint — /.well-known/jwks.json for public key distribution
  • Refresh token rotation — each use invalidates the previous token (replay detection)
  • Token binding — optional DPoP (Demonstrating Proof-of-Possession)

3. Multi-Tenancy Model​

Auth0's multi-tenancy is the cornerstone of its architecture — each customer operates in a fully isolated tenant.

AspectImplementation
Data IsolationLogical isolation per tenant within sharded PostgreSQL; physical isolation for Private Cloud
ConfigurationEach tenant has independent connections, rules, actions, branding
Domain{tenant}.{region}.auth0.com or custom domain
Rate LimitingPer-tenant rate limits to prevent noisy-neighbor effects
EncryptionTenant-specific encryption keys for sensitive data (secrets, client_secrets)

4. Connection Broker​

The Connection Broker abstracts the complexity of connecting to diverse identity providers behind a unified interface.

5. Actions Runtime (Extensibility)​

Actions are tenant-specific serverless functions executed at defined trigger points in the authentication pipeline.

Trigger Points:

  • post-login — after successful authentication
  • pre-user-registration — before creating a user
  • post-user-registration — after creating a user
  • post-change-password — after password change
  • send-phone-message — custom SMS delivery
  • credentials-exchange — M2M token customization

Isolation Model:

  • V8 isolates (not full containers) for microsecond cold starts
  • 20-second execution timeout
  • Sandboxed require() with allow-listed npm modules
  • Network egress allowed (for calling external APIs)
  • Secrets management via event.secrets

Data Architecture​

Storage Partitioning Strategy​

Database Schema (Simplified)​

-- Tenant isolation via tenant_id in every table
CREATE TABLE tenants (
    id UUID PRIMARY KEY,
    name VARCHAR(63) UNIQUE NOT NULL,
    region VARCHAR(10) NOT NULL,
    plan VARCHAR(20) NOT NULL,
    custom_domain VARCHAR(255),
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE users (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    email VARCHAR(320),
    email_verified BOOLEAN DEFAULT FALSE,
    phone VARCHAR(20),
    password_hash VARCHAR(256), -- bcrypt/argon2id
    mfa_enabled BOOLEAN DEFAULT FALSE,
    blocked BOOLEAN DEFAULT FALSE,
    metadata JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    last_login TIMESTAMPTZ,
    UNIQUE(tenant_id, email)
);

CREATE TABLE connections (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    name VARCHAR(128) NOT NULL,
    strategy VARCHAR(64) NOT NULL, -- 'google-oauth2', 'samlp', 'auth0'
    options JSONB NOT NULL,        -- provider-specific config (encrypted)
    enabled BOOLEAN DEFAULT TRUE,
    UNIQUE(tenant_id, name)
);

CREATE TABLE refresh_tokens (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    user_id UUID NOT NULL,
    client_id VARCHAR(64) NOT NULL,
    token_hash VARCHAR(128) NOT NULL, -- SHA-256 of token
    family_id UUID NOT NULL,          -- for rotation detection
    expires_at TIMESTAMPTZ NOT NULL,
    revoked BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

Infrastructure & Deployment​

Multi-Region Architecture​

Key Infrastructure Decisions:

  • 3 Availability Zones per region — survives single AZ failure
  • Active-Active multi-region — latency-based DNS routing; failover on regional outage
  • Zero-downtime deployments — rolling deploys with canary analysis
  • Deployment frequency — multiple times daily
  • Data residency — tenant data pinned to selected region (GDPR compliance)

Deployment Options​

Security Architecture​

Defense in Depth​

Key Security Mechanisms​

MechanismImplementation
Password storagebcrypt (cost 10) or argon2id; never reversible
Token signingRS256/ES256 with automatic key rotation (90-day cycle)
Breached password detectionBloom filter over known breach datasets
Bot detectionCAPTCHA integration, device fingerprinting, IP reputation
Rate limitingToken bucket per tenant/IP/endpoint; 429 with Retry-After
PKCEEnforced for all public clients (SPAs, mobile)
Refresh token rotationAutomatic reuse detection invalidates entire token family

Scalability Patterns​

Horizontal Scaling Strategy​

Scaling Dimensions:

  1. Compute — Stateless API pods auto-scale on CPU/RPS; Actions runtime scales on invocation count
  2. Database — Horizontal sharding by tenant_id; read replicas for Management API reads
  3. Cache — Redis Cluster with consistent hashing; session affinity not required
  4. Event Processing — Kafka partitions by tenant; consumer groups scale independently

Rate Limiting & Throttling​

Global Limits → Tenant Limits → Endpoint Limits → IP Limits
  • Token bucket algorithm per dimension
  • Graduated response: 429 → temporary block → CAPTCHA → account lock
  • Burst allowance for legitimate traffic spikes (login floods after outage recovery)

Failure Modes & Resilience​

Failure ScenarioImpactMitigation
Single AZ failure~33% capacity loss in regionAuto-failover to remaining AZs; no user impact
Full region outageRegion unavailableDNS failover to secondary region (< 60s)
Database primary failureWrite unavailabilityAutomated failover to synchronous replica (< 30s)
Redis cluster failureSession/rate-limit state lossGraceful degradation; re-authenticate users; allow temporary rate-limit bypass
External IdP outageSocial/enterprise login unavailableCircuit breaker + cached IdP metadata; fallback to database login
Action runtime failureCustom logic not executedFail-open option (configurable per tenant); retry with backoff
Key rotation failureToken validation errorsKeep previous key active for overlap period (grace window)

Trade-offs & Design Decisions​

DecisionRationaleTrade-off
Multi-tenant shared infra (Public Cloud)Lower cost, faster deploys, shared innovationNoisy neighbor risk (mitigated by rate limiting)
V8 isolates for Actions (not containers)Microsecond cold start, high densityLimited runtime capabilities vs. full containers
JWT (stateless tokens)No DB lookup on every API call at resource serverCannot revoke instantly (mitigated by short expiry + refresh rotation)
Universal Login (redirect-based)Security (credentials never touch client app), SSO supportExtra redirect = slight UX friction
Eventual consistency for logsDecouples auth hot path from analyticsLog events may lag by seconds
bcrypt for password hashingWell-understood, GPU-resistantSlower than alternatives (acceptable for auth workload)

When to Use Auth0​

Good fit:

  • Applications needing enterprise SSO (SAML, OIDC federation)
  • Multi-application ecosystem requiring unified identity
  • Teams without dedicated identity/security engineers
  • Compliance requirements (SOC 2, HIPAA, GDPR) without building in-house
  • Rapid prototyping with production-grade auth

Consider alternatives when:

  • Extreme cost sensitivity (high MAU on free/essentials tier)
  • Full control over every identity flow is required
  • Air-gapped environments with no external network access
  • Simple, single-app scenarios where a framework's built-in auth suffices
