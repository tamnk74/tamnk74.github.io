Design the Twitter Timeline and Search

A comprehensive guide to designing a social media feed and search system at scale

Overview​

This document outlines the system design for Twitter's timeline and search functionality. The design patterns discussed here also apply to Facebook feed and search systems. We'll explore how to handle billions of tweets, manage fan-out to millions of followers, and provide fast search capabilities.

Step 1: Outline Use Cases and Constraints​

Use Cases​

In Scope​

  • User posts a tweet
    • Service pushes tweets to followers, sending push notifications and emails
  • User views the user timeline (activity from the user)
  • User views the home timeline (activity from people the user is following)
  • User searches keywords
  • Service has high availability

Out of Scope​

  • Service pushes tweets to the Twitter Firehose and other streams
  • Service strips out tweets based on users' visibility settings
    • Hide @reply if the user is not also following the person being replied to
    • Respect 'hide retweets' setting
  • Analytics

Constraints and Assumptions​

####State Assumptions

General:

  • Traffic is not evenly distributed
  • Posting a tweet should be fast
    • Fanning out a tweet to all of your followers should be fast, unless you have millions of followers
  • 100 million active users
  • 500 million tweets per day or 15 billion tweets per month
    • Each tweet averages a fanout of 10 deliveries
    • 5 billion total tweets delivered on fanout per day
    • 150 billion tweets delivered on fanout per month
  • 250 billion read requests per month
  • 10 billion searches per month

Timeline:

  • Viewing the timeline should be fast
  • Twitter is more read heavy than write heavy
    • Optimize for fast reads of tweets
  • Ingesting tweets is write heavy

Search:

  • Searching should be fast
  • Search is read-heavy

Calculate Usage​

Size per tweet:

  • tweet_id - 8 bytes
  • user_id - 32 bytes
  • text - 140 bytes
  • media - 10 KB average
  • Total: ~10 KB

Storage:

  • 150 TB of new tweet content per month
    • 10 KB per tweet × 500 million tweets per day × 30 days per month
  • 5.4 PB of new tweet content in 3 years

Traffic:

  • 100 thousand read requests per second
    • 250 billion read requests per month × (400 requests per second / 1 billion requests per month)
  • 6,000 tweets per second
    • 15 billion tweets per month × (400 requests per second / 1 billion requests per month)
  • 60 thousand tweets delivered on fanout per second
    • 150 billion tweets delivered on fanout per month × (400 requests per second / 1 billion requests per month)
  • 4,000 search requests per second
    • 10 billion searches per month × (400 requests per second / 1 billion requests per month)

Handy conversion guide:

  • 2.5 million seconds per month
  • 1 request per second = 2.5 million requests per month
  • 40 requests per second = 100 million requests per month
  • 400 requests per second = 1 billion requests per month

Step 2: Create a High Level Design​

The high-level architecture consists of:

  • Client - Web/mobile interface
  • Web Server - Reverse proxy
  • Write API Server - Handles tweet creation
  • Read API Server - Handles timeline and search queries
  • Fan Out Service - Distributes tweets to followers' timelines
  • User Graph Service - Manages follower relationships
  • Timeline Service - Retrieves and formats timelines
  • Search Service - Indexes and searches tweets
  • Tweet Info Service - Stores tweet metadata
  • User Info Service - Stores user metadata
  • SQL Database - Stores user and tweet data
  • Memory Cache (Redis) - Caches timelines and frequently accessed data
  • Object Store (S3) - Stores media files
  • Search Cluster (Lucene/Elasticsearch) - Full-text search index
  • Notification Service - Sends push notifications and emails

Step 3: Design Core Components​

Use Case: User Posts a Tweet​

We'll store the user's own tweets to populate the user timeline in a relational database. Discuss the use cases and tradeoffs between choosing SQL or NoSQL.

Delivering tweets and building the home timeline is trickier. Fanning out tweets to all followers (60 thousand tweets delivered on fanout per second) will overload a traditional relational database. We'll use a data store with fast writes such as a NoSQL database or Memory Cache.

Flow:

  1. The Client posts a tweet to the Web Server (running as a reverse proxy)
  2. The Web Server forwards the request to the Write API server
  3. The Write API stores the tweet in the user's timeline on a SQL database
  4. The Write API contacts the Fan Out Service, which does the following:
    • Queries the User Graph Service to find the user's followers stored in the Memory Cache
    • Stores the tweet in the home timeline of the user's followers in a Memory Cache
      • O(n) operation: 1,000 followers = 1,000 lookups and inserts
    • Stores the tweet in the Search Index Service to enable fast searching
    • Stores media in the Object Store
    • Uses the Notification Service to send out push notifications to followers:
      • Uses a Queue to asynchronously send out notifications

Memory Cache Structure (Redis)​

If our Memory Cache is Redis, we could use a native Redis list with the following structure:

           tweet n+2                   tweet n+1                   tweet n
| 8 bytes   8 bytes  1 byte | 8 bytes   8 bytes  1 byte | 8 bytes   8 bytes  1 byte |
| tweet_id  user_id  meta   | tweet_id  user_id  meta   | tweet_id  user_id  meta   |

The new tweet would be placed in the Memory Cache, which populates the user's home timeline.

REST API​

curl -X POST --data '{ "user_id": "123", "auth_token": "ABC123", \
    "status": "hello world!", "media_ids": "ABC987" }' \
    https://twitter.com/api/v1/tweet

Response:

{
  "created_at": "Wed Sep 05 00:37:15 +0000 2012",
  "status": "hello world!",
  "tweet_id": "987",
  "user_id": "123"
}

For internal communications, we could use Remote Procedure Calls (RPC).

Use Case: User Views the Home Timeline​

Flow:

  1. The Client posts a home timeline request to the Web Server
  2. The Web Server forwards the request to the Read API server
  3. The Read API server contacts the Timeline Service, which does the following:
    • Gets the timeline data stored in the Memory Cache, containing tweet ids and user ids - O(1)
    • Queries the Tweet Info Service with a multiget to obtain additional info about the tweet ids - O(n)
    • Queries the User Info Service with a multiget to obtain additional info about the user ids - O(n)

REST API​

curl https://twitter.com/api/v1/home_timeline?user_id=123

Response:

{
    "user_id": "456",
    "tweet_id": "123",
    "status": "foo"
},
{
    "user_id": "789",
    "tweet_id": "456",
    "status": "bar"
},
{
    "user_id": "789",
    "tweet_id": "579",
    "status": "baz"
}

Use Case: User Views the User Timeline​

Flow:

  1. The Client posts a user timeline request to the Web Server
  2. The Web Server forwards the request to the Read API server
  3. The Read API retrieves the user timeline from the SQL Database

The REST API would be similar to the home timeline, except all tweets would come from the user as opposed to the people the user is following.

Use Case: User Searches Keywords​

Flow:

  1. The Client sends a search request to the Web Server
  2. The Web Server forwards the request to the Search API server
  3. The Search API contacts the Search Service, which does the following:
    • Parses/tokenizes the input query, determining what needs to be searched
      • Removes markup
      • Breaks up the text into terms
      • Fixes typos
      • Normalizes capitalization
      • Converts the query to use boolean operations
    • Queries the Search Cluster (e.g., Lucene) for the results:
      • Scatter gathers each server in the cluster to determine if there are any results for the query
      • Merges, ranks, sorts, and returns the results

REST API​

curl https://twitter.com/api/v1/search?query=hello+world

The response would be similar to that of the home timeline, except for tweets matching the given query.

Step 4: Scale the Design​

Important: Do not simply jump right into the final design from the initial design!

State you would do this iteratively:

  1. Benchmark/Load Test
  2. Profile for bottlenecks
  3. Address bottlenecks while evaluating alternatives and trade-offs
  4. Repeat

Key Bottlenecks and Solutions​

Fanout Service Bottleneck​

The Fanout Service is a potential bottleneck. Twitter users with millions of followers could take several minutes to have their tweets go through the fanout process. This could lead to race conditions with @replies to the tweet.

Solutions:

  • Re-order the tweets at serve time to mitigate race conditions
  • Avoid fanning out tweets from highly-followed users
  • Instead, search to find tweets for highly-followed users
  • Merge the search results with the user's home timeline results
  • Re-order the tweets at serve time

Memory Cache Optimizations​

  • Keep only several hundred tweets for each home timeline in the Memory Cache
  • Keep only active users' home timeline info in the Memory Cache
    • If a user was not previously active in the past 30 days, rebuild the timeline from the SQL Database
      • Query the User Graph Service to determine who the user is following
      • Get the tweets from the SQL Database and add them to the Memory Cache
  • Store only a month of tweets in the Tweet Info Service
  • Store only active users in the User Info Service
  • The Search Cluster would likely need to keep the tweets in memory to keep latency low

Database Scaling​

Although the Memory Cache should reduce the load on the database, it is unlikely the SQL Read Replicas alone would be enough to handle the cache misses.

The high volume of writes would overwhelm a single SQL Write Master-Slave, pointing to a need for additional scaling techniques:

  • Federation
  • Sharding
  • Denormalization
  • SQL Tuning

We should also consider moving some data to a NoSQL Database.

Security​

Key security considerations:

  • Authentication and authorization (OAuth)

Latency Numbers​

Key metrics to know:

  • Reading 1 MB sequentially from memory takes about 250 microseconds
  • Reading from SSD takes 4x longer
  • Reading from disk takes 80x longer

Ongoing Improvements​

  • Continue benchmarking and monitoring your system to address bottlenecks as they come up
  • Scaling is an iterative process
  • Monitor key metrics:
    • Tweet creation latency
    • Timeline load time
    • Search query performance
    • Fanout completion time
    • Cache hit rates
  • A/B testing for new features
  • Gradual rollout of changes

Key Design Decisions​

Read vs Write Optimization​

Twitter is heavily read-optimized:

  • Pre-compute timelines during write (fanout)
  • Cache aggressively
  • Denormalize data for faster reads
  • Trade write complexity for read speed

Fan-Out Strategy​

Push (fan-out-on-write):

  • Pre-compute timelines when tweet is created
  • Fast reads, slower writes
  • Works well for users with moderate follower counts

Pull (fan-out-on-read):

  • Compute timeline when user requests it
  • Fast writes, slower reads
  • Better for highly-followed users (celebrities)

Hybrid Approach:

  • Use push for most users
  • Use pull for celebrity accounts
  • Merge results at read time

Search Architecture​

  • Real-time indexing for recent tweets
  • Distributed search across multiple servers
  • Scatter-gather pattern for comprehensive results
  • Relevance ranking based on multiple signals
  • Autocomplete for search suggestions

Conclusion​

Designing Twitter's timeline and search at scale requires careful consideration of read/write patterns, caching strategies, and data distribution. The key challenges are:

  1. Fan-out at scale - Distributing tweets to millions of followers
  2. Real-time search - Indexing and searching billions of tweets
  3. Timeline generation - Quickly assembling personalized feeds
  4. Data consistency - Managing eventual consistency across distributed systems

By using a hybrid fan-out strategy, aggressive caching, and distributed search, we can build a system that handles hundreds of millions of users and billions of tweets while maintaining fast response times.
