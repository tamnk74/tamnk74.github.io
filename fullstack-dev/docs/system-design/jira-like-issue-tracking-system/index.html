Jira-Like Issue Tracking System — System Design

Overview​

Design a multi-tenant issue tracking and agile project management platform (similar to Jira Core or Linear) that enables distributed teams to collaborate on work, track progress, and manage sprints. The system must support millions of issues across thousands of workspaces, provide sub-second board interactions, guarantee eventual consistency on relationships, and scale to handle real-time collaboration with WebSocket-backed updates.

Scope: workspaces, projects, issues (CRUD, filtering, search), boards (Kanban), sprints, comments, activity logs, notifications, RBAC, attachments, basic reporting. Out of scope: advanced workflows, custom fields, time tracking revenue, enterprise integrations (Slack, GitHub Actions).

Scale Estimates​

Workspaces & Projects:

  • 10k workspaces (SMB focus initially)
  • Avg 5 projects/workspace = 50k projects
  • Avg 2k active issues/project = 100M issues total

Transactions:

  • 5M issue updates/day (create, status change, comment, assign) = ~58 TPS average, 100+ TPS peak
  • 50M searches/day = ~580 search TPS average, 1k TPS peak

Data:

  • Issue record: ~500 bytes (metadata) × 100M = ~50 GB
  • Comments: avg 10 comments/issue × 200 bytes = ~200 GB
  • Activity log: ~600 bytes/entry × 5 mutations × 100M = ~300 GB
  • Total: ~500 GB baseline + ~500 GB/year growth

Realtime:

  • 100k concurrent users × 10 WebSocket connections/user = 1M connections
  • Board view broadcasts (drag-drop updates) = ~500 msgs/sec during peak

Step 5: Key Service Designs​

5.1 Issue Service — State Machine​

Every issue transition validates the state machine:

TO_DO ──→ IN_PROGRESS ──→ IN_REVIEW ──→ DONE
  ↓_________________________↓___________↓
  └─────────────── DONE (shortcut)

DONE ──→ TO_DO (reopens issue)

Update path (critical path):

  1. Load issue with row lock (SELECT ... FOR UPDATE)
  2. Validate new status is reachable from current status
  3. Check user has permission (assignee, project lead, workspace admin)
  4. UPDATE issues SET status = ?, updated_at = NOW()
  5. INSERT activity_log (who, what, when)
  6. Publish IssueUpdated event to Kafka
  7. Return updated issue to client

Concurrency control:

  • Serializable isolation prevents double-state-transitions
  • Idempotency key (If-Idempotency-Key header) deduplicates retries
  • Optimistic lock via version number (not used for MVP, eventual consistency OK for board state)

5.2 Board Service — Realtime Coordination​

The board is a eventual-consistency view of issues, not the source of truth.

Source of truth: PostgreSQL issue rows (status, assignee, sprint)
Cache layer: Redis stores board state (project_id → {TO_DO: [], IN_PROGRESS: [...]})
Realtime layer: WebSocket broadcasts delta updates

Drag-drop flow:
  1. Optimistic UI immediately reflects the drag
  2. Client sends status update to Issue Service
  3. Issue Service persists, emits Kafka event
  4. Board Service consumes event, updates Redis cache
  5. Broadcast via WebSocket to all viewers on that board
  6. If server rejects (validation error), client rolls back UI

Board cache coherence:

  • Built on-demand from issue table: SELECT * FROM issues WHERE project_id = ? AND sprint_id = ?
  • Invalidated on any issue mutation (Kafka event triggers cache bust)
  • TTL = 5 min; cache miss → rebuild from DB (consistent, not stale)

5.3 Notification Service — Event-Driven​

Notifications trigger from Kafka events:

IssueCreated     → notify workspace members
IssueAssigned    → notify assignee (email + in-app)
StatusChanged    → notify watchers (in-app)
CommentAdded     → notify issue followers + mentions (email + in-app)
MentionedInComment → high-priority, immediate email

Delivery:

  • In-app: stored in PostgreSQL, pushed via WebSocket (< 1 s)
  • Email: batched by user preferences (daily/immediate digest), queued in Redis, sent via SendGrid
  • Webhook: custom integrations (Slack, GitHub), published atomically with event

Durability via outbox pattern:

Atomic transaction:
  1. INSERT notification row + webhook event in same DB transaction
  2. Publish to Kafka as confirmation
  3. Webhook service picks up from DB, retries up to 5x

5.4 Search Service — Elasticsearch Integration​

Issues indexed in near-real-time:

Index mapping:
  {
    issue_id (keyword),
    project_id (keyword),
    key (keyword),
    title (text analyzer: standard),
    description (text analyzer: standard),
    status (keyword),
    priority (keyword),
    assignee_id (keyword),
    created_at (date),
    updated_at (date),
    comment_count (integer)
  }

Query examples:
  {
    "query": {
      "bool": {
        "must": [
          {"multi_match": {"query": "payment bug", "fields": ["title^2", "description"]}}
        ],
        "filter": [
          {"term": {"project_id": "uuid"}},
          {"term": {"status": "OPEN"}}
        ]
      }
    }
  }

Indexing lag:
  - Async via Kafka consumer (< 5 s typical)
  - Stale search results acceptable (< 5 min)

5.5 Comment Service — Threaded Discussions​

Supports nested comment threads:

Comment schema:
  id (PK)
  issue_id (FK) — ties to issue
  parent_comment_id (FK) — null if top-level, else refers to parent
  author_id (FK)
  body (markdown)
  created_at, updated_at

Queries:
  GET /issues/:id/comments → all top-level only (N+1 prevention)
  GET /issues/:id/comments/:comment_id/replies → nested replies
  POST /comments/:id/reactions → React with emoji

Mentions:
  @user_email triggers notification
  Stored as activity: parsed from markdown, email → user_id lookup, notify

Step 6: Scalability Architecture​

Database Sharding​

Shard key: workspace_id (UUID → consistent hash → 16 virtual shards → N physical nodes)

Rationale:
  - All issues, projects, sprints, comments tied to workspace
  - Cross-workspace queries rare (only admins in multi-workspace scenarios)
  - Enables independent backup/recovery per workspace

Cross-shard operations:
  - Search: broadcast query to all shards, merge results (< 100 ms acceptable)
  - User deletion: async job iterates all shards

Read scaling:
  - Replica per shard: 1 primary + 1 read replica
  - Issue reads (list, search) routed to replica
  - Board state reads from Redis (write-through cache)

High Availability (Region + Failover)​

  • RTO: ≤ 5 min (manual promotion or automated via Patroni)
  • RPO: ≤ 1 min (async ES + Redis acceptable; Kafka durable)

Step 8: Failure Modes & Mitigations​

FailureImpactMitigation
Elasticsearch downSearch unavailable; board still worksFallback to DB full-text (slower); alert SRE for recovery
Redis node failureCache miss on 1/N dataRedis Cluster gossip rebalances replicas; cache rebuild from DB (< 1 s latency spike)
Kafka broker timeoutEvent publishing fails; notifications delayedOutbox pattern: persist to DB first, async retry (webhook service)
Issue mutation race (concurrent edits)Conflicting updatesSerializable isolation + row lock; last-write-wins within transaction boundary
Realtime WebSocket disconnectClient misses updates; UI staleClient auto-reconnect + server-side event buffer (100 msgs); on reconnect, fetch latest state
Database primary failureWrite unavailabilityPatroni auto-failover ≤ 30 s; circuit breaker rejects writes during failover
Attachment upload failureFile lost; user experience brokenStore metadata in DB first; async retry S3 upload; notify user if fails after 3x
Search index lag > 5 minStale search resultsAlert and reindex; provide warning to user ("results may be outdated")

Step 9: Observability​

Instrumentation Points​

Every request spans the full stack:

Trace:  [API GW] → [IssueSvc] → [PostgreSQL] → [Kafka] → [SearchSvc]
Spans:  http.request, db.query, kafka.produce, http.outbound

Metrics (Prometheus + Datadog):
  issue.create.latency_ms             (histogram p50/p95/p99)
  issue.update.latency_ms             (histogram, tagged by field)
  board.drag_drop.latency_ms          (histogram, user-perceived)
  search.latency_ms                   (histogram, by query complexity)
  workspace.issue_count               (gauge, sampled)
  notification.delivery_latency_ms    (histogram, by channel: email, webhook)
  database.connection_pool.active     (gauge)
  elasticsearch.indexing_lag_ms       (gauge)
  websocket.active_connections        (gauge)

Logs (structured, ELK):
  level, timestamp, trace_id, user_id, issue_id, action, duration_ms, error (if failed)

Alerts​

CRITICAL:
  - Issue mutation error rate > 0.1%
  - Search latency p99 > 1000 ms
  - Kafka consumer lag > 10k messages

WARN:
  - Elasticsearch indexing lag > 5 min
  - Redis evictions increasing
  - WebSocket connection drop rate > 2%

Step 10: Trade-offs​

DecisionChosenAlternativeRationale
Consistency modelEventual (board cache)Strong (all ops hit DB)Board is UX-critical; eventual OK for 99% accuracy. Strong consistency would kill < 150 ms latency target.
Storage: DB vs. searchPostgreSQL (primary), Elasticsearch (secondary)Elasticsearch onlyFull-text search needs aggregations + facets; ES + Postgres hybrid gives best of both worlds.
Notification deliveryAsync queue (email)Sync SendGrid callEmail latency (100–500 ms) unacceptable for user-facing latency; queue + batching trades off for throughput.
Realtime: WebSocketWebSocket + Redis pub/subServer-sent events (SSE)WebSocket allows bidirectional (drag-drop coordination); SSE simpler but unidirectional.
Sharding: workspace_idWorkspace (tenant isolation)Issue ID (horizontal split)Multi-tenancy requires isolation; workspace sharding prevents cross-tenant data leak.
Issue versioningActivity log + current stateEvent sourcingEvent sourcing adds complexity; activity log gives auditability + sufficient history for MVP.
