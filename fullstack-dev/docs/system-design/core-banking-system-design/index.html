Core Banking System — System Design

Overview​

Design a core banking system (CBS) — the central nervous system of a modern bank or fintech that manages customer accounts, processes financial transactions, enforces ledger integrity, and integrates with payment networks (ACH, SWIFT, SEPA, card schemes). The system must guarantee ACID transactions, provide a fully auditable double-entry ledger, and scale to millions of accounts with sub-second transaction confirmation under strict regulatory compliance.

Scope: account lifecycle, deposit/withdrawal/transfer, payment rails integration, interest accrual, compliance (KYC/AML), fraud detection, and reporting. Out of scope: loan origination, investment products, FX trading desk.

Scale Estimates​

Accounts & Customers:

  • 5M retail customers × avg 2 accounts = 10M accounts
  • 200k corporate clients × avg 5 accounts = 1M accounts
  • Balance storage: ~2 KB/account × 11M = ~22 GB

Transactions:

  • Avg transaction record: ~1 KB → ~50 GB raw/day → ~18 TB/year
  • Ledger entries: 2 entries/transaction (double-entry) = 100M entries/day

Ledger:

  • Ledger entry: ~300 bytes × 100M entries/day = ~30 GB/day
  • Hot (30-day) ledger: ~900 GB in PostgreSQL; cold archive: ~10 TB/year in object storage

Payments:

  • ACH batches: 2M items/day
  • SWIFT messages: 50k/day
  • Card authorisations: 5M/day (peak: 500 TPS during business hours)

Step 3: Domain Model — Double-Entry Ledger​

Every money movement in the system is expressed as a journal entry that balances to zero — the fundamental invariant of double-entry bookkeeping.

Step 5: Key Service Designs​

5.1 Ledger Service — The Core Invariant​

The ledger is the source of truth. All balance mutations flow through it.

Design principles:

  • Append-only: entries are never updated or deleted — only reversed via a compensating entry
  • Atomic multi-entry commit: a journal posting writes all entries in a single DB transaction; partial posts are impossible
  • Balance snapshot pattern: materialised balance cache in Redis updated on each post; recalculated from ledger on cache miss
  • Partitioning: ledger entries table partitioned by posted_at (monthly range) for query performance; hot partition stays in memory
Ledger write path (critical path):
  1. BEGIN SERIALIZABLE transaction
  2. SELECT ... FOR UPDATE on affected account rows (deterministic lock order prevents deadlock)
  3. INSERT INTO ledger_entries (N rows)
  4. UPDATE accounts SET balance = balance + delta WHERE id IN (...)
  5. VALIDATE ΣDebits = ΣCredits (CHECK constraint or trigger)
  6. COMMIT
  7. Publish LedgerPosted event to Kafka (outbox pattern)

5.2 Idempotency​

Every mutating API accepts a client-supplied Idempotency-Key (UUID v4). The system:

  1. Stores key → {status, response_body} in Redis with 24h TTL on first receipt
  2. Returns stored response on duplicate keys without reprocessing
  3. After 24h, re-processing is safe (payments have settled or failed)

This makes all payment APIs safe for client-side retries under network failures.

5.3 Distributed Locking Strategy​

To prevent race conditions on concurrent debits from the same account:

Lock acquisition order: always sort account IDs ascending before locking
→ prevents deadlocks across concurrent transfers between the same pair

Implementation:
  - PostgreSQL advisory locks (pg_try_advisory_xact_lock) for sub-second transfers
  - Redis Redlock for cross-shard operations spanning multiple DB instances
  - Lock timeout: 5s (hard); 2s (soft with retry)

5.4 Compliance Service — AML Monitoring​

The AML engine runs two modes:

ModeTriggerLatencyAction
Real-time screeningEvery transaction< 200 msBlock/allow based on sanctions list + velocity rules
Async pattern detectionPost-posting, batch< 5 minStructuring detection, unusual behaviour ML models
Periodic reviewDaily batchHoursAggregate SAR candidates, CTR generation (≥ $10k cash)

Rules engine runs in the same JVM/Node process as the threshold checks; ML model is a separate Python sidecar called via local gRPC for isolation.

5.5 Interest Engine​

Interest is computed daily using the actual/365 (or actual/360) day-count convention:

Daily Interest=Balance×Annual Rate365\text{Daily Interest} = \frac{\text{Balance} \times \text{Annual Rate}}{365}Daily Interest=365Balance×Annual Rate​

Accrual flow (Temporal workflow):

  1. At 23:59 UTC, batch job reads all savings accounts with non-zero balance
  2. Compute accrued interest for each account
  3. Accrue to an accrued_interest sub-ledger entry (no cash movement yet)
  4. On interest payment date (monthly), post final entries: Debit Interest Expense → Credit Customer Account
  5. All accruals are reversible if rate corrections are needed

Step 6: Scalability Architecture​

Database Sharding Strategy​

Shard key: account_id (UUID v4 → consistent hash → 256 virtual shards → N physical nodes)

Cross-shard transfers:
  - Two-phase commit (2PC) via Citus distributed transactions
  - Or: async saga with compensating debit if 2PC unavailable

Read scaling:
  - Physical streaming replicas (1 primary + 2 replicas per shard)
  - Read requests routed to replica for balance reads via PgBouncer
  - Redis balance cache (write-through) eliminates 90% of DB reads

High Availability​

  • RTO ≤ 30 s: automated Patroni failover from primary to standby within same region
  • RPO = 0: synchronous replication to standby; ledger events also on Kafka (durable)
  • Cross-region: async replication with ≤ 5 s lag; DR region can serve reads immediately, writes after promotion

Step 9: Observability​

Every transaction generates structured telemetry:

Trace:  [API GW] → [TxnSvc] → [FraudSvc] → [AccountSvc] → [LedgerSvc]
Spans:  fraud_score_latency, lock_wait_ms, db_commit_ms, kafka_produce_ms

Metrics (emitted to Datadog / Prometheus):
  banking.transaction.throughput          (counter, by type)
  banking.transaction.latency_ms          (histogram p50/p95/p99, by type)
  banking.ledger.imbalance_count          (counter — alert if > 0)
  banking.account.available_balance       (gauge — sampled, for treasury)
  banking.fraud.score_latency_ms          (histogram)
  banking.kafka.consumer_lag              (gauge, by consumer group)
  banking.payment.settlement_delay_s      (histogram, by rail)

Alerts:
  - CRITICAL: ledger imbalance detected
  - CRITICAL: transaction service error rate > 0.01%
  - CRITICAL: fraud service latency p99 > 100 ms
  - WARN: ACH return rate > 2%
  - WARN: Kafka consumer lag > 10k messages

Transfer consistencySynchronous 2PC (same-shard) / saga (cross-shard)Pure saga everywhereSame-shard is 99% of traffic; 2PC acceptable latency for < 5% cross-shard
Balance cachingRedis write-through, 60s TTLNo cache (always read DB)10M accounts × 580 TPS would saturate DB without cache
AML engineDual-mode (sync rules + async ML)Sync ML onlyML latency (50–200 ms) is acceptable for background; sync path uses fast rules for < 20 ms
Interest calculationTemporal workflow (durable execution)Cron jobTemporal handles retries, timeouts, auditable history out of box
Card PAN handlingTokenisation (never store raw PAN)Encrypted PAN in DBPCI DSS scope minimisation; HSM-backed tokenization is industry standard
