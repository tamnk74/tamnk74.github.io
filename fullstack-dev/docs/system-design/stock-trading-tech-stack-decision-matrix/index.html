Stock Trading App: Architecture & System Design

Overview​

A retail stock trading application lets authenticated users view real-time market data, manage a watchlist, place and track orders via a broker API, and monitor their portfolio P&L. This design balances low-latency data delivery, strong transactional correctness for orders, and a clear compliance/audit trail — while remaining buildable by a product engineering team.

Scope: broker-integrated trading app (execution delegated to a licensed broker API such as Alpaca or Interactive Brokers). This is not a full custody/ledger platform.

Scale Estimates​

Users:

  • 50k DAU at launch, 500k DAU at scale
  • ~5% of DAU actively trading at peak market open (09:30–10:00 ET)

Orders:

  • 500k orders/day = ~6 orders/s average, 150 orders/s peak (market open burst)

Quotes:

  • 8k symbols in watchlists across active users
  • Quote update rate: ~1 update/symbol/second = 8k events/s inbound
  • Fan-out multiplier: avg 50 subscribers/symbol = 400k outbound pushes/s at peak

Storage:

  • Order row: ~500 bytes × 500k orders/day × 365 = ~90 GB/year
  • Candle data (1-minute OHLCV): ~200 bytes × 8k symbols × 390 min/trading day × 252 days = ~1.6 TB/year

Step 4: Core Service Design​

4.0 API Gateway​

Responsibilities: authenticate every inbound request, enforce rate limits, route to downstream services, inject trace context, and normalise error responses.

  • JWT validated via passport-jwt on every non-public route; public routes opt out with @Public().
  • Sliding-window rate limiter backed by Redis sorted sets — per userId:endpoint key, pruned on each request.
  • Service routing via URL prefix map (/v1/orders → Order Service, /v1/quotes → Market Data Service, etc.).
  • X-Request-Id injected on every request and echoed in the response header.
  • GlobalExceptionFilter normalises all errors to { statusCode, message, requestId } — no stack traces leak to clients.

See the full deep-dive: API Gateway →

4.1 User Service​

Responsibilities: registration, authentication, MFA, KYC handoff, account management.

POST /auth/register          → create user, trigger KYC
POST /auth/login             → issue JWT + refresh token
POST /auth/mfa/verify        → validate TOTP/SMS code
GET  /users/:id/profile      → fetch profile (auth required)
PATCH /users/:id/settings    → update notification prefs
  • Passwords hashed with bcrypt (cost factor ≥ 12).
  • JWTs are short-lived (15 min); refresh tokens are stored encrypted in Redis with rotation.
  • KYC status is a state machine: pending → approved | rejected | manual_review.

See the full deep-dive: User Service →

4.2 Market Data Service​

Responsibilities: ingest real-time quotes from provider WebSocket, normalise, cache, fan-out to subscribed clients.

  • Latest quote cached in Redis with 2-second TTL (stale-while-revalidate pattern).
  • REST endpoint /quotes/:symbol serves from Redis cache; falls back to provider REST on miss.
  • Quote fan-out uses Redis Pub/Sub per symbol channel; WebSocket gateway subscribes only to channels with active clients. Unsubscribes automatically when all clients for a symbol disconnect.

4.3 Order Service​

Responsibilities: validate, submit, and track the lifecycle of orders. This is the most consistency-critical service.

Idempotency: each POST /orders requires a client-supplied Idempotency-Key header. The key is stored with the order row and deduplicates retries for up to 24 hours.

Order status state machine:

pending → accepted → partially_filled → filled
                   ↘ cancelled
                   ↘ rejected

Failure modes:

FailureMitigation
Broker API timeoutRetry with exponential backoff (max 3); if still no response, mark order unknown, alert ops, reconcile on next heartbeat
Duplicate submitIdempotency key prevents double-insert; broker adapter checks broker-side order ID before re-submitting
DB write succeeds, broker call failsOutbox pattern: broker submission is a separate outbox row; a worker delivers it and marks it done
Fill webhook missedReconciliation job polls broker open orders every 60 s during market hours

4.4 Portfolio Service​

Responsibilities: maintain real-time positions and P&L by consuming OrderFilled events.

  • Consumes OrderFilled events from the message bus.
  • Recomputes position using weighted-average cost basis.
  • Stores Position rows in PostgreSQL; publishes PositionUpdated event back to WebSocket gateway for streaming P&L.
  • Daily snapshot job runs after market close for statement generation.

Eventual consistency is acceptable here — a 1–3 second lag between fill and portfolio update has no material impact on the user experience and avoids tight coupling to the order hot path.

4.5 Notification Service​

Responsibilities: send price alerts, order confirmations, and account events via push, email, and SMS.

  • Consumes events from the message bus.
  • Alert evaluation: a scheduled worker (every 10 s) checks Redis for alert:* keys and scans for threshold breaches against the cached quote.
  • Delivery channels: Firebase Cloud Messaging (push), SendGrid (email), Twilio (SMS).
  • Rate-limited per user per channel to prevent alert spam.

4.6 WebSocket Gateway​

Responsibilities: manage persistent client connections, multiplex symbol subscriptions, and fan-out real-time quotes and order-status events.

  • Authenticates on the HTTP Upgrade handshake (JWT validation); unauthenticated upgrades are rejected with 401.
  • Uses Redis Pub/Sub per-symbol channel (quote:{symbol}, order:{account_id}); subscribes at Redis level only while ≥ 1 client is active for that channel.
  • Enforces per-connection limits: max 50 symbols, max 3 concurrent connections per user, max 10 subscription frames/s.
  • Sends {"type":"reconnect"} to all clients before graceful shutdown (30 s drain window).

Step 6: Infrastructure and Deployment​

  • All services are stateless pods — horizontal pod autoscaler (HPA) scales on CPU + custom metric (queue depth / WebSocket connection count).
  • Database connections go through PgBouncer (connection pooling) to avoid saturating Cloud SQL.
  • Secrets (API keys, broker credentials) stored in GCP Secret Manager; injected as env vars at pod startup via Workload Identity.
  • CI/CD: GitHub Actions → build/test → push image → ArgoCD GitOps sync to GKE.

Notes​

  • This design covers a broker-integrated trading app. Holding customer funds directly adds custody, clearing, and regulatory obligations that change the architecture materially.
  • For regulated production launch, add a compliance readiness checklist: KYC/AML provider integration, order surveillance, data retention policy, incident response runbook.
