Domain-Driven Design for Microservices & Distributed Systems

Overview​

Domain-Driven Design (DDD) is a software development approach that emphasizes collaboration between technical and domain experts to create a shared understanding of the business domain. When applied to microservices and distributed systems, DDD provides powerful patterns for managing complexity and ensuring services are properly bounded and cohesive.

Core Concepts​

Ubiquitous Language​

A shared vocabulary between developers and domain experts that is used consistently in code, documentation, and conversations.

Key Principles:

  • Single Source of Truth: The domain model reflects business terminology exactly
  • Consistency: Same terms used in code, database, APIs, and conversations
  • Evolution: Language evolves as understanding deepens

Example:

// ❌ Bad: Technical jargon
class UserRecord {
  saveData(): Promise<void>;
  getData(): Record[];
}

// ✅ Good: Business language
class Customer {
  placeOrder(order: Order): Promise<void>;
  getOrderHistory(): Order[];
}

Domain Model​

The domain model is an abstract representation of the business domain, encapsulating business rules, behavior, and data.

Characteristics:

  • Focuses on business logic, not technical infrastructure
  • Rich with behavior, not just data structures
  • Validates business invariants
  • Expresses business rules through code

Strategic Design​

Strategic design focuses on high-level architecture and how to divide a large system into manageable parts.

Bounded Context​

A bounded context is an explicit boundary within which a particular domain model is defined and applicable. It's the fundamental unit of service decomposition in microservices.

Definition:

A bounded context delimits the applicability of a particular model, providing it with clear boundaries of responsibility.

How to Define Bounded Contexts​

Identifying and defining bounded contexts is crucial for successful DDD implementation. Here's a systematic approach:

1. Event Storming Workshop​

Gather domain experts and developers to map out the domain through events.

Steps:

  1. Identify Domain Events: What significant things happen in your business?
    • OrderPlaced, PaymentProcessed, ItemShipped, ProductOutOfStock
  2. Group Related Events: Events that naturally cluster together
    • All order-related events (OrderPlaced, OrderCancelled, OrderShipped)
    • All inventory events (StockReduced, StockReplenished, ProductAdded)
  3. Identify Commands: What actions trigger these events?
    • PlaceOrder → OrderPlaced
    • ProcessPayment → PaymentProcessed
  4. Draw Boundaries: Where do responsibilities naturally separate?

Example Event Storm Map:

│                    E-COMMERCE DOMAIN                         │
├─────────────────────────────────────────────────────────────┤

│  [Add to Cart] → ItemAddedToCart                            │
│  [Place Order] → OrderPlaced ◄── BOUNDARY                   │
│  [Process Payment] → PaymentProcessed                        │

Different parts of the business often use the same word to mean different things, or different words to mean the same thing.

  • Need for prefixes/suffixes to clarify: "BillingCustomer" vs "ShippingCustomer"

4. Apply Heuristics​

Use these rules of thumb to validate context boundaries:

✅ Good Bounded Context Indicators:

  • Team Autonomy: Different teams can own different contexts
  • Independent Deployment: Can release changes without coordinating with other contexts
  • Data Ownership: Context owns its data exclusively
  • Single Responsibility: Context has one clear purpose
  • Business Alignment: Maps to a business capability or department

❌ Poor Context Boundary Indicators:

  • Requires constant coordination with other contexts
  • Shares database tables with other contexts
  • Has unclear or mixed responsibilities
  • Too granular (single entity) or too coarse (entire system)

Conway's Law applies: Your architecture will mirror your organization.

6. Validate with Questions​

Ask these questions to validate your bounded context boundaries:

Core Questions:

  1. Can this context be explained in one sentence?

    • ✅ "Order Context manages customer orders from placement to fulfillment"
    • ❌ "User Context manages users, products, orders, and shipping"

  2. Does this context have a clear owner (team)?

    • ✅ Order Team owns Order Context
    • ❌ Multiple teams share "Customer" context

  3. Can I change this context without affecting others?

    • ✅ Can change order workflow independently
    • ❌ Changing product model breaks multiple contexts

  4. Does this context have its own persistence?

    • ✅ Order Context has orders database
    • ❌ Shares users table with multiple contexts

  5. What happens if this context fails?

    • ✅ Order context down = can't place orders (clear impact)
    • ❌ Generic "data" context down = entire system fails

Context Mapping​

Context mapping describes the relationships and integration patterns between bounded contexts.

Partnership​

Two contexts work together with mutual dependency and coordinated teams.

// Order Context collaborates with Payment Context
interface PaymentGateway {
  processPayment(orderId: string, amount: Money): Promise<PaymentResult>;
}

class OrderService {
  constructor(private paymentGateway: PaymentGateway) {}

  async completeOrder(order: Order): Promise<void> {
    const paymentResult = await this.paymentGateway.processPayment(order.id, order.totalAmount);

    if (paymentResult.isSuccessful) {
      order.markAsPaid();
    }
  }
}

Customer-Supplier​

Upstream (supplier) provides services to downstream (customer). Downstream depends on upstream.

// Catalog Service (Upstream/Supplier)
export interface ProductCatalogService {
  getProduct(productId: string): Promise<Product>;
  checkAvailability(productId: string): Promise<boolean>;
}

// Order Service (Downstream/Customer)
class OrderService {
  constructor(private catalogService: ProductCatalogService) {}

  async createOrder(customerId: string, items: OrderItem[]): Promise<Order> {
    // Verify products exist in catalog
    for (const item of items) {
      const available = await this.catalogService.checkAvailability(item.productId);
      if (!available) {
        throw new ProductNotAvailableError(item.productId);
      }
    }

    return Order.create(customerId, items);
  }
}

Conformist​

Downstream conforms to upstream's model without negotiation.

// Using external payment provider's model as-is
interface StripePaymentModel {
  payment_intent_id: string;
  amount_cents: number;
  currency_code: string;
}

class PaymentAdapter {
  async processPayment(order: Order): Promise<void> {
    // Conform to Stripe's model
    const stripePayment: StripePaymentModel = {
      payment_intent_id: order.paymentIntentId,
      amount_cents: order.amount.toCents(),
      currency_code: order.amount.currency,
    };

    await stripe.processPayment(stripePayment);
  }
}

Anti-Corruption Layer (ACL)​

Protects your domain model from external systems by translating between models.

// ACL protecting Order Context from legacy Inventory System
class InventoryAntiCorruptionLayer {
  constructor(private legacyInventorySystem: LegacyInventorySystem) {}

  async checkProductAvailability(productId: ProductId): Promise<boolean> {
    // Legacy system uses different model
    const legacyResponse = await this.legacyInventorySystem.checkStock({
      item_code: productId.value,
      warehouse_id: 'DEFAULT',
    });

    // Translate to domain model
    return legacyResponse.quantity_on_hand > 0;
  }

  async reserveStock(productId: ProductId, quantity: number): Promise<Reservation> {
    const legacyReservation = await this.legacyInventorySystem.createReservation({
      item_code: productId.value,
      qty: quantity,
      timestamp: Date.now(),
    });

    // Translate response to domain model
    return new Reservation(
      new ReservationId(legacyReservation.reservation_id),
      productId,
      quantity,
      new Date(legacyReservation.timestamp),
    );
  }
}

Shared Kernel​

Multiple contexts share a subset of the domain model.

// Shared kernel between Order and Billing contexts
// shared-kernel/money.ts
export class Money {
  constructor(public readonly amount: number, public readonly currency: Currency) {
    if (amount < 0) throw new Error('Amount cannot be negative');
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) {
      throw new Error('Cannot add different currencies');
    }
    return new Money(this.amount + other.amount, this.currency);
  }

  multiply(factor: number): Money {
    return new Money(this.amount * factor, this.currency);
  }
}

// Both contexts use the same Money implementation

import { Money } from '../shared-kernel/money';

class Order {
  calculateTotal(): Money {

import { Money } from '../shared-kernel/money';

class Invoice {
  calculateTotalWithTax(): Money {

    return this.subtotal.add(taxAmount);

Open Host Service​

Defines a protocol/API that gives access to your subsystem as a set of services.

// Product Catalog exposes REST API as Open Host Service
// product-catalog/api/product-api.ts
export class ProductCatalogAPI {
  @Get('/api/products/:id')
  async getProduct(@Param('id') id: string): Promise<ProductDTO> {
    const product = await this.productService.findById(new ProductId(id));
    return this.toDTO(product);
  }

  @Get('/api/products/search')
  async searchProducts(@Query() query: SearchQuery): Promise<ProductDTO[]> {
    const products = await this.productService.search(query);
    return products.map((p) => this.toDTO(p));
  }

  private toDTO(product: Product): ProductDTO {
    return {
      id: product.id.value,
      name: product.name,
      description: product.description,
      price: {
        amount: product.price.amount,
        currency: product.price.currency,
      },
      availability: product.isAvailable(),
    };
  }
}

Tactical Design​

Tactical design focuses on implementation patterns within a bounded context.

Entities​

Objects with a unique identity that persists over time.

// Entity: Customer has identity
export class Customer {
  private constructor(
    private readonly _id: CustomerId,
    private _email: Email,
    private _name: CustomerName,
    private _loyaltyPoints: number,
  ) {}

  get id(): CustomerId {
    return this._id;
  }

  get email(): Email {
    return this._email;
  }

  // Business behavior
  addLoyaltyPoints(points: number): void {
    if (points < 0) {
      throw new DomainError('Cannot add negative points');
    }
    this._loyaltyPoints += points;
  }

  redeemLoyaltyPoints(points: number): void {
    if (points > this._loyaltyPoints) {
      throw new InsufficientPointsError();
    }
    this._loyaltyPoints -= points;
  }

  // Factory method
  static create(email: Email, name: CustomerName): Customer {
    return new Customer(
      CustomerId.generate(),
      email,
      name,
      0, // Initial loyalty points
    );
  }

  // Equality based on identity
  equals(other: Customer): boolean {
    return this._id.equals(other._id);
  }
}

Value Objects​

Immutable objects defined by their attributes, not identity.

// Value Object: Money has no identity
export class Money {
  constructor(public readonly amount: number, public readonly currency: Currency) {
    if (amount < 0) {
      throw new DomainError('Money amount cannot be negative');
    }
  }

  add(other: Money): Money {
    this.ensureSameCurrency(other);
    return new Money(this.amount + other.amount, this.currency);
  }

  subtract(other: Money): Money {
    this.ensureSameCurrency(other);
    return new Money(this.amount - other.amount, this.currency);
  }

  multiply(multiplier: number): Money {
    return new Money(this.amount * multiplier, this.currency);
  }

  // Equality based on attributes
  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }

  private ensureSameCurrency(other: Money): void {
    if (this.currency !== other.currency) {
      throw new DomainError('Cannot operate on different currencies');
    }
  }
}

// Value Object: Address
export class Address {
  constructor(
    public readonly street: string,
    public readonly city: string,
    public readonly state: string,
    public readonly postalCode: string,
    public readonly country: string,
  ) {
    this.validate();
  }

  private validate(): void {
    if (!this.street || !this.city || !this.postalCode) {
      throw new DomainError('Invalid address');
    }
  }

  equals(other: Address): boolean {
    return (
      this.street === other.street &&
      this.city === other.city &&
      this.state === other.state &&
      this.postalCode === other.postalCode &&
      this.country === other.country
    );
  }
}

Aggregates​

A cluster of entities and value objects with a root entity that maintains consistency.

// Aggregate Root: Order
export class Order {
  private constructor(
    private readonly _id: OrderId,
    private readonly _customerId: CustomerId,
    private _items: OrderLine[],
    private _status: OrderStatus,
    private _shippingAddress: Address,
    private _createdAt: Date,
    private _version: number,
  ) {}

  // Aggregate root ID
  get id(): OrderId {
    return this._id;
  }

  get status(): OrderStatus {
    return this._status;
  }

  get totalAmount(): Money {
    return this._items.reduce((total, item) => total.add(item.lineTotal()), Money.zero(Currency.USD));
  }

  // Aggregate enforces invariants
  addItem(product: Product, quantity: number): void {
    this.ensureOrderIsEditable();

    if (quantity <= 0) {
      throw new DomainError('Quantity must be positive');
    }

    // Business rule: maximum 10 items per order
    if (this._items.length >= 10) {
      throw new DomainError('Order cannot have more than 10 items');
    }

    const existingItem = this._items.find((item) => item.productId.equals(product.id));

    if (existingItem) {
      existingItem.increaseQuantity(quantity);
    } else {
      this._items.push(new OrderLine(product.id, product.price, quantity));
    }
  }

  removeItem(productId: ProductId): void {
    this.ensureOrderIsEditable();

    this._items = this._items.filter((item) => !item.productId.equals(productId));

    if (this._items.length === 0) {
      throw new DomainError('Order must have at least one item');
    }
  }

  // State transitions
  confirm(): void {
    if (this._status !== OrderStatus.Draft) {
      throw new DomainError('Only draft orders can be confirmed');
    }

    if (this._items.length === 0) {
      throw new DomainError('Cannot confirm empty order');
    }

    this._status = OrderStatus.Confirmed;
  }

  ship(trackingNumber: string): void {
    if (this._status !== OrderStatus.Confirmed) {
      throw new DomainError('Only confirmed orders can be shipped');
    }

    this._status = OrderStatus.Shipped;
  }

  cancel(): void {
    if (this._status === OrderStatus.Shipped || this._status === OrderStatus.Delivered) {
      throw new DomainError('Cannot cancel shipped or delivered order');
    }

    this._status = OrderStatus.Cancelled;
  }

  private ensureOrderIsEditable(): void {
    if (this._status !== OrderStatus.Draft) {
      throw new DomainError('Order is not editable');
    }
  }

  // Factory method
  static create(customerId: CustomerId, shippingAddress: Address): Order {
    return new Order(OrderId.generate(), customerId, [], OrderStatus.Draft, shippingAddress, new Date(), 0);
  }
}

// Entity within aggregate (not directly accessible)
class OrderLine {
  constructor(public readonly productId: ProductId, public readonly price: Money, private _quantity: number) {
    if (_quantity <= 0) {
      throw new DomainError('Quantity must be positive');
    }
  }

  get quantity(): number {
    return this._quantity;
  }

  increaseQuantity(amount: number): void {
    if (amount <= 0) {
      throw new DomainError('Amount must be positive');
    }
    this._quantity += amount;
  }

  lineTotal(): Money {
    return this.price.multiply(this._quantity);
  }
}

Orchestration-Based Saga​

A central coordinator manages the saga workflow.

// Saga Orchestrator
export class OrderFulfillmentSaga {
  constructor(
    private orderService: OrderService,
    private paymentService: PaymentService,
    private inventoryService: InventoryService,
    private shippingService: ShippingService,
    private sagaRepository: SagaRepository,
  ) {}

  async execute(orderId: OrderId): Promise<void> {
    const saga = await this.sagaRepository.create(orderId);

    try {
      // Step 1: Validate order
      await saga.execute('ValidateOrder', async () => {
        await this.orderService.validateOrder(orderId);
      });

      // Step 2: Reserve inventory
      await saga.execute('ReserveInventory', async () => {
        const order = await this.orderService.getOrder(orderId);
        await this.inventoryService.reserveStock(order.items);
      });

      // Step 3: Process payment
      await saga.execute('ProcessPayment', async () => {
        const order = await this.orderService.getOrder(orderId);
        await this.paymentService.charge(order.totalAmount, order.customerId);
      });

      // Step 4: Schedule shipping
      await saga.execute('ScheduleShipping', async () => {
        const order = await this.orderService.getOrder(orderId);
        await this.shippingService.scheduleShipment(order);
      });

      // Mark saga as completed
      await saga.complete();
    } catch (error) {
      // Compensate in reverse order
      await this.compensate(saga);
      throw error;
    }
  }

  private async compensate(saga: Saga): Promise<void> {
    const completedSteps = saga.getCompletedSteps().reverse();

    for (const step of completedSteps) {
      try {
        switch (step.name) {
          case 'ScheduleShipping':
            await this.shippingService.cancelShipment(saga.orderId);
            break;
          case 'ProcessPayment':
            await this.paymentService.refund(saga.orderId);
            break;
          case 'ReserveInventory':
            await this.inventoryService.releaseStock(saga.orderId);
            break;
        }
      } catch (compensationError) {
        // Log and continue with other compensations
        console.error(`Compensation failed for step ${step.name}`, compensationError);
      }
    }

    await saga.fail();
  }
}

Event Sourcing​

Store state changes as a sequence of events.

// Event-sourced aggregate
export class Order {
  private _id: OrderId;
  private _items: Map<ProductId, OrderLine> = new Map();
  private _status: OrderStatus;
  private _version: number = 0;

  // Uncommitted events
  private _changes: DomainEvent[] = [];

  // Load from history
  static fromHistory(events: DomainEvent[]): Order {
    const order = new Order();

    for (const event of events) {
      order.apply(event);
      order._version++;
    }

    return order;
  }

  // Business methods record events
  addItem(productId: ProductId, quantity: number, price: Money): void {
    const event = new ItemAddedToOrderEvent(this._id, productId, quantity, price);

    this.applyChange(event);
  }

  confirm(): void {
    if (this._status !== OrderStatus.Draft) {
      throw new DomainError('Only draft orders can be confirmed');
    }

    const event = new OrderConfirmedEvent(this._id, Array.from(this._items.values()), this.calculateTotal());

    this.applyChange(event);
  }

  // Apply event and record as uncommitted
  private applyChange(event: DomainEvent): void {
    this.apply(event);
    this._changes.push(event);
  }

  // Apply event to update state (used for both new and historical events)
  private apply(event: DomainEvent): void {
    if (event instanceof OrderCreatedEvent) {
      this._id = event.orderId;
      this._status = OrderStatus.Draft;
    } else if (event instanceof ItemAddedToOrderEvent) {
      this._items.set(event.productId, new OrderLine(event.productId, event.price, event.quantity));
    } else if (event instanceof OrderConfirmedEvent) {
      this._status = OrderStatus.Confirmed;
    }
    // ... other event handlers
  }

  getUncommittedChanges(): DomainEvent[] {
    return [...this._changes];
  }

  markChangesAsCommitted(): void {
    this._changes = [];
  }
}

// Event store repository
export class EventStoreOrderRepository {

Isolating the Domain​

One of the most crucial aspects of Domain-Driven Design is keeping the domain layer pure and isolated from infrastructure concerns. This isolation ensures that business logic remains independent of technical implementation details, making it easier to test, maintain, and evolve.

Why Isolation Matters​

Key Benefits:

  1. Testability: Pure domain logic can be tested without databases, frameworks, or external services
  2. Maintainability: Business rules are concentrated in one place, not scattered across the codebase
  3. Flexibility: Infrastructure can be changed without affecting domain logic
  4. Clarity: Clear separation makes the codebase easier to understand
  5. Longevity: Domain logic outlives specific technologies and frameworks

The Problem Without Isolation:

// ❌ Bad: Domain logic mixed with infrastructure

Issues with this approach:

  • Cannot test without database connection
  • Cannot test without email service
  • Business logic depends on specific technologies (Stripe, SendGrid)
  • Changing email provider requires modifying domain code
  • Cannot understand business rules without reading infrastructure code

The domain layer should contain only business logic with zero infrastructure dependencies.

Characteristics of a Pure Domain Layer:

  • ✅ No HTTP clients or external API calls
  • ✅ No file system access
  • ✅ No environment variables
  • ✅ Only plain TypeScript/JavaScript classes

// domain/model/order.ts
// ✅ Pure domain model - no infrastructure dependencies

export class Order {
  private constructor(
    private readonly _id: OrderId,
    private readonly _customerId: CustomerId,
    private _items: OrderLine[],
    private _status: OrderStatus,
    private _shippingAddress: Address,
    private readonly _createdAt: Date,
  ) {}

  // Pure business logic
  addItem(productId: ProductId, quantity: number, price: Money): void {
    if (this._status !== OrderStatus.DRAFT) {
      throw new DomainError('Cannot add items to a confirmed order');
    }

    if (quantity <= 0) {
      throw new DomainError('Quantity must be positive');
    }

    const existingItem = this._items.find((item) => item.productId.equals(productId));

    if (existingItem) {
      existingItem.increaseQuantity(quantity);
    } else {
      const item = new OrderLine(productId, quantity, price);
      this._items.push(item);
    }
  }

  confirm(): OrderConfirmedEvent {
    if (this._status !== OrderStatus.DRAFT) {
      throw new DomainError('Only draft orders can be confirmed');
    }

    if (this._items.length === 0) {
      throw new DomainError('Cannot confirm empty order');
    }

    this._status = OrderStatus.CONFIRMED;

    // Return domain event instead of performing infrastructure actions
    return new OrderConfirmedEvent(this._id, this._customerId, this.calculateTotal());
  }

  calculateTotal(): Money {
    return this._items.reduce((total, item) => total.add(item.subtotal), Money.zero(Currency.USD));
  }

  // Factory method
  static create(customerId: CustomerId, shippingAddress: Address): Order {
    return new Order(OrderId.generate(), customerId, [], OrderStatus.DRAFT, shippingAddress, new Date());
  }
}

    await this.orderRepository.save(order);

    // Coordinate infrastructure services
    try {
      await this.paymentGateway.charge(order.total, order.customerId);
      await this.emailService.sendOrderConfirmation(order);
      await this.eventBus.publish(event);
    } catch (error) {
      // Handle infrastructure failures
      order.markAsFailed();
      await this.orderRepository.save(order);
      throw error;
    }
  }
}

Responsibilities:

  • Application Service: Coordinates domain objects and infrastructure (transaction boundaries, error handling)
  • Domain Model: Contains business logic and invariants
  • Infrastructure: Implements technical details

Anti-Corruption Layer (ACL)​

Protect your domain from external systems by translating between your model and external models.

// infrastructure/external/legacy-inventory-adapter.ts
// ✅ Anti-Corruption Layer protects domain from legacy system

export class LegacyInventoryAdapter implements InventoryService {
  constructor(private readonly legacyClient: LegacyInventoryClient) {}

  async checkAvailability(productId: ProductId): Promise<StockLevel> {
    // Legacy system uses different terminology and structure
    const legacyResponse = await this.legacyClient.getProductStock({
      itemCode: productId.value, // Legacy uses "itemCode"
      warehouseId: 'MAIN', // Legacy requires warehouse
    });

    // Translate legacy response to domain model
    return new StockLevel(
      productId,
      this.translateQuantity(legacyResponse), // Handle different formats
      this.translateAvailability(legacyResponse.status),
    );
  }

  private translateQuantity(response: LegacyStockResponse): number {
    // Legacy system returns quantity in different format
    return response.qtyOnHand - response.qtyReserved;
  }

  private translateAvailability(status: string): Availability {
    // Translate legacy status codes to domain concepts
    switch (status) {
      case 'A':
        return Availability.IN_STOCK;
      case 'L':
        return Availability.LOW_STOCK;
      case 'O':
        return Availability.OUT_OF_STOCK;
      default:
        return Availability.UNKNOWN;
    }
  }
}

Benefits:

  • Domain model remains clean and consistent
  • External system changes don't affect domain
  • Can swap external system without domain changes
  • Clear translation layer for debugging

Isolation Checklist​

Use this checklist to verify your domain is properly isolated:

✅ Domain Layer Should:

  • Contain only business logic and domain concepts
  • Have zero dependencies on frameworks or libraries (except language standard library)
  • Use plain classes and types
  • Define interfaces for external dependencies (ports)
  • Be testable without any infrastructure setup
  • Express business rules in code
  • Throw domain-specific exceptions
  • Return domain events for side effects

❌ Domain Layer Should NOT:

  • Import database libraries or ORM annotations
  • Make HTTP calls or API requests
  • Access file system or environment variables
  • Use framework-specific decorators
  • Contain SQL queries or database logic
  • Have direct dependencies on infrastructure code
  • Perform logging or monitoring
  • Trigger side effects directly (email, push notifications, etc.)

// Application Service (Use Case)
export class CreateOrderUseCase {
  constructor(
    private orderRepository: OrderRepository,
    private customerRepository: CustomerRepository,
    private productRepository: ProductRepository,
    private eventBus: EventBus,
  ) {}

  async execute(command: CreateOrderCommand): Promise<CreateOrderResult> {
    // Validate customer exists
    const customer = await this.customerRepository.findById(command.customerId);

    if (!customer) {
      throw new CustomerNotFoundError(command.customerId);
    }

    // Create order aggregate
    const order = Order.create(customer.id, command.shippingAddress);

    // Add items
    for (const item of command.items) {
      const product = await this.productRepository.findById(item.productId);

      if (!product) {
        throw new ProductNotFoundError(item.productId);
      }

      order.addItem(product, item.quantity);
    }

    // Persist
    await this.orderRepository.save(order);

    // Publish events
    for (const event of order.domainEvents) {
      await this.eventBus.publish(event);
    }

    return new CreateOrderResult(order.id);
  }
}

// Read Model (Query Side)
export interface OrderReadModel {
  id: string;
  customerId: string;
  customerName: string;
  status: string;
  totalAmount: number;
  currency: string;
  itemCount: number;
  createdAt: Date;
  items: Array<{
    productId: string;
    productName: string;
    quantity: number;
    price: number;
  }>;
}

export class OrderQueryService {
  constructor(private db: Database) {}

  async getOrderById(orderId: string): Promise<OrderReadModel | null> {
    // Optimized read from denormalized view
    const result = await this.db.query(
      `
      SELECT 
        o.id,
        o.customer_id,
        c.name as customer_name,
        o.status,
        o.total_amount,
        o.currency,
        o.created_at,
        json_agg(
          json_build_object(
            'productId', oi.product_id,
            'productName', p.name,
            'quantity', oi.quantity,
            'price', oi.price
          )
        ) as items
      FROM orders o
      JOIN customers c ON o.customer_id = c.id
      JOIN order_items oi ON o.id = oi.order_id
      JOIN products p ON oi.product_id = p.id
      WHERE o.id = $1
      GROUP BY o.id, c.id
    `,
      [orderId],
    );

    return result.rows[0] || null;
  }

  async searchOrders(query: SearchOrdersQuery): Promise<OrderReadModel[]> {
    // Complex queries optimized for reading
    let sql = `
      SELECT * FROM order_search_view
      WHERE 1=1
    `;
    const params: any[] = [];

    if (query.customerId) {
      params.push(query.customerId);
      sql += ` AND customer_id = $${params.length}`;
    }

    if (query.status) {
      params.push(query.status);
      sql += ` AND status = $${params.length}`;
    }

    if (query.fromDate) {
      params.push(query.fromDate);
      sql += ` AND created_at >= $${params.length}`;
    }

    sql += ` ORDER BY created_at DESC LIMIT 100`;

    const result = await this.db.query(sql, params);
    return result.rows;
  }
}

Best Practices​

1. Start with Strategic Design​

  • Map context relationships before writing code
  • Define ubiquitous language for each context

2. Design Small Aggregates​

  • Keep aggregates focused and small

  • One transaction per aggregate

Common Pitfalls​

1. Anemic Domain Model​

// ❌ Bad: Anemic model (just data)
class Order {
  id: string;
  customerId: string;
  items: OrderItem[];
  status: string;
  total: number;
}

class OrderService {
  calculateTotal(order: Order): number {
    return order.items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  }

  canConfirm(order: Order): boolean {
    return order.status === 'DRAFT' && order.items.length > 0;
  }
}

// ✅ Good: Rich domain model
class Order {
  private constructor(private readonly _id: OrderId, private _items: OrderLine[], private _status: OrderStatus) {}

  get totalAmount(): Money {
    return this._items.reduce((total, item) => total.add(item.lineTotal()), Money.zero());
  }

  confirm(): void {
    if (this._status !== OrderStatus.Draft) {
      throw new DomainError('Only draft orders can be confirmed');
    }

    if (this._items.length === 0) {
      throw new DomainError('Cannot confirm empty order');
    }

    this._status = OrderStatus.Confirmed;
  }
}

2. Ignoring Bounded Contexts​

// ❌ Bad: Shared models across contexts
// Using same Order model in Order, Billing, and Shipping services
class Order {
  // Properties needed for orders
  items: OrderItem[];

  // Properties needed for billing
  invoiceNumber: string;
  taxAmount: number;

  // Properties needed for shipping
  trackingNumber: string;
  carrier: string;
  deliveryDate: Date;
}

// ✅ Good: Separate models per context
// Order Context
class Order {
  items: OrderLine[];
  totalAmount: Money;
}

// Billing Context
class Invoice {
  orderReference: OrderId;
  lineItems: BillingLineItem[];
  taxAmount: Money;
}

// Shipping Context
class Shipment {
  orderReference: OrderId;
  trackingNumber: TrackingNumber;
  carrier: Carrier;
}

3. Large Aggregates​

// ❌ Bad: Large aggregate with many entities
class Order {
  customer: Customer; // Full customer object
  items: Array<{
    product: Product; // Full product object
    inventory: InventoryItem;
    reviews: Review[];
  }>;
  payments: Payment[];
  shipments: Shipment[];
}

// ✅ Good: Small focused aggregate
class Order {
  private readonly customerId: CustomerId; // Reference by ID
  private items: OrderLine[]; // Just what's needed
  private status: OrderStatus;
}

4. Synchronous Cross-Context Calls​

// ❌ Bad: Synchronous coupling
async confirmOrder(orderId: string): Promise<void> {
  const order = await this.orderRepository.findById(orderId)
  order.confirm()

  // Blocking calls to other services
  await this.inventoryService.reduceStock(order.items)
  await this.paymentService.charge(order.total)
  await this.shippingService.schedule(order)

  await this.orderRepository.save(order)
}

// ✅ Good: Asynchronous with events
async confirmOrder(orderId: string): Promise<void> {
  const order = await this.orderRepository.findById(orderId)
  order.confirm()
  await this.orderRepository.save(order)

  // Other services react to events
  await this.eventBus.publish(new OrderConfirmedEvent(order))
}

class OrderApplicationService {

  applyDiscount(promotion: Promotion): void {

Summary​

Domain-Driven Design provides powerful patterns for building maintainable microservices and distributed systems:

Strategic Design:

  • Identify bounded contexts that map to microservices
  • Define clear context boundaries and relationships
  • Use ubiquitous language within each context

Tactical Design:

  • Build rich domain models with entities, value objects, and aggregates
  • Encapsulate business logic in the domain layer
  • Use repositories for persistence abstraction
  • Communicate across contexts with domain events

Microservices Architecture:

  • One bounded context per service (or small cluster)
  • Prefer asynchronous communication with events
  • Use sagas for distributed transactions
  • Implement CQRS for complex read requirements

Key Principles:

  • Small, focused aggregates
  • Business logic in the domain
  • Eventual consistency across contexts
  • Testable, maintainable code

By applying DDD patterns consistently, you can build distributed systems that are easier to understand, maintain, and evolve alongside business requirements.
