Spotify System Design: A Music Streaming Platform

Overview​

Spotify is a prime example of a large-scale music streaming platform that handles millions of users and billions of songs. This document explores the system design principles, architecture patterns, and scalability considerations involved in building a platform like Spotify.

System Requirements & Assumptions​

Functional Requirements​

  • Artist Management: Artists can upload their songs to the platform
  • Content Discovery: Users can search and browse songs, artists, and playlists
  • Audio Playback: Users can stream and play songs with adaptive quality
  • Playlist Management: Users can create, modify, and manage personal playlists
  • User Profiles: Support for user accounts, preferences, and social features
  • Monitoring: Basic observability with health checks, error tracking, and performance metrics

Scale Assumptions​

  • Users: ~500,000 active users
  • Content: ~30 million songs in the catalog
  • Daily Usage: Each user streams 10-15 songs daily
  • Average Listen Time: 3.5 minutes per song
  • Audio Quality: Multiple bitrates (64kbps, 128kbps, 320kbps for premium)

Audio Format Specifications​

  • File Formats: Ogg and AAC with adaptive streaming support
  • Quality Tiers:
    • 64kbps: Mobile data saving mode
    • 128kbps: Standard quality
    • 320kbps: Premium/high-fidelity audio
  • File Size: ~3MB per song at standard quality

Capacity Planning​

Storage Requirements​

Audio Storage:

  • Raw audio: 3MB × 30M songs ≈ 90TB
  • With replicas and regional distribution: 2-3x = ~270TB
  • Multiple quality versions add additional overhead

Metadata Storage:

  • Song metadata: ~100 bytes × 30M songs ≈ 3GB
  • User profiles and playlists: ~1KB × 500K users ≈ 0.5GB
  • Total metadata: Negligible compared to audio storage

Bandwidth Considerations:

  • Average stream: 3-4MB per song (128-160kbps)
  • Daily streams per user: 10-15 songs
  • Peak traffic during commute hours and evening listening sessions
  • Significant CDN and egress costs for audio delivery

Key Insight: Audio content dominates both storage costs and bandwidth requirements, making efficient content delivery critical.

High-Level Architecture​

Architecture Overview​

The Spotify system architecture follows a distributed, scalable design with clear separation of concerns:

  1. Client Layer: Mobile and web applications handle user interfaces and local caching
  2. Load Balancing: Distributes incoming requests across multiple API servers
  3. API Layer: Stateless application servers handle business logic and authentication
  4. Data Storage: SQL database with read replicas for metadata management
  5. Audio Storage: Blob storage (S3) for large audio files with CDN caching
  6. Supporting Services: Analytics, monitoring, and search capabilities

Key Design Principles:

  • Horizontal Scalability: Each layer can scale independently
  • Fault Tolerance: Multiple replicas and fallback mechanisms
  • Performance Optimization: CDN caching and direct audio streaming
  • Cost Efficiency: Signed URLs reduce API server load for audio delivery

Core Components​

1. Mobile/Web Client​

  • Responsibilities:

    • User interface and playback controls
    • Local caching of recently played songs
    • REST API communication for metadata
    • Direct audio streaming from CDN/blob storage
    • Graceful handling of network interruptions

  • Key Features:

    • Retry logic for API calls
    • Adaptive bitrate streaming
    • Local playback state management
    • Offline mode support

2. Load Balancer​

  • Algorithm Options: Round-robin or least-connections
  • Health Monitoring: 30-second health checks
  • High Availability: Automatic removal of unhealthy instances
  • Traffic Management: Handles traffic spikes during album releases
  • Zero-Downtime Deployments: Enables rolling updates

3. API Layer (Web/Application Servers)​

  • Architecture: Stateless servers for horizontal scalability

  • Authentication: JWT token validation

  • Business Logic:

    • Song metadata retrieval
    • Signed URL generation for audio access
    • User action tracking and analytics

  • Reliability Patterns:

    • Circuit breakers for database connections
    • Connection pooling for resource management
    • Fallback responses for non-critical features

4. Blob Storage (Object Storage)​

  • Technology: AWS S3 or similar object storage

  • Organization: Hierarchical structure (/artist/album/song.ogg)

  • Security: Time-limited signed URLs (few hours expiration)

  • Benefits:

    • Virtually unlimited scalability
    • Built-in durability and regional replication
    • Cost-effective for large files

  • Trade-offs:

    • Higher latency compared to local storage
    • Potential egress cost implications

System Workflows​

Read Workflow (Song Playback)​

  1. User Action: User hits play button
  2. API Request: App sends GET /songs/{id} request
  3. Authentication: API server validates JWT token
  4. Metadata Lookup: Query SQL database for song details
  5. URL Generation: Create signed URL for blob storage access
  6. Audio Streaming: Client fetches audio chunks using HTTP range requests
  7. Adaptive Streaming: HLS/DASH protocols for quality switching
  8. Analytics: Periodic tracking of play progress and listening time

Play a Song Sequence Diagram​

Key Interactions Explained:

  1. Authentication Flow: JWT token validation ensures only authorized users can access content
  2. Metadata Retrieval: Database lookup provides song information for UI display
  3. Signed URL Security: Time-limited URLs (2-hour expiration) enable direct CDN access without exposing storage credentials
  4. CDN Optimization: Popular songs served from edge locations for faster delivery
  5. Range Requests: Audio streamed in chunks (1MB segments) for smooth playback and efficient buffering
  6. Adaptive Streaming: Quality automatically adjusts based on network conditions (64kbps → 320kbps)
  7. Analytics Tracking: Real-time progress tracking and play count updates for recommendations
  8. Fallback Strategy: CDN cache miss automatically fetches from origin storage (S3)

Performance Optimizations:

  • Parallel Processing: Audio streaming happens independently of analytics
  • Progressive Loading: Song starts playing while buffering upcoming segments
  • Smart Caching: CDN stores popular content at edge locations globally
  • Quality Adaptation: Prevents buffering by switching bitrates dynamically

Write Workflow (Song Upload)​

  1. Upload Initiation: Artist uploads via POST /songs/upload (multipart form)

  2. File Validation: Server checks format, duration, and size limits

  3. Temporary Storage: Upload to pending location (/pending/{upload_id}/song.ogg)

  4. Background Processing:

    • Extract metadata (duration, bitrate)
    • Generate preview images/thumbnails
    • Quality validation

  5. Database Operations:

    • Insert song record
    • Create/update artist information
    • Link artist to song (many-to-many relationship)

  6. File Promotion: Move from pending to organized location

  7. CDN Invalidation: Clear cached metadata for immediate availability

Artist Upload Song Sequence Diagram​

Key Process Highlights:

  1. Secure Upload: Multi-step validation (authentication, file format, size limits)
  2. Temporary Storage: Files stored in pending location during processing
  3. Background Processing: Async metadata extraction and quality encoding
  4. Database Transactions: ACID compliance ensures data consistency
  5. Multiple Quality Encoding: Automatic generation of 64k, 128k, 320k versions
  6. File Organization: Structured storage path /artist/{id}/album/{id}/{song_id}.ext
  7. Cache Management: CDN invalidation ensures immediate content availability
  8. Search Indexing: Real-time search engine updates for discoverability
  9. Status Tracking: Real-time progress updates via polling mechanism
  10. Error Handling: Transaction rollback on failures, cleanup of temporary files

Upload Flow Optimizations:

  • Parallel Processing: Background encoding while UI shows progress
  • Chunked Upload: Large files uploaded in segments for reliability
  • Quality Encoding: Multiple bitrates generated for adaptive streaming
  • Immediate Feedback: Artist gets confirmation before processing completes
  • Cleanup Strategy: Automatic removal of temporary files after processing
  • Search Integration: Songs immediately available for discovery

Error Scenarios Handled:

  • File corruption detection during validation
  • Storage failures with automatic retry logic
  • Database transaction rollbacks on errors
  • Cleanup of partial uploads on failures
  • User notification of processing errors

API Design​

Search & Discovery Endpoints​

# Multi-type search with pagination
GET /search?q={query}&type=song,artist&limit=20&offset=0

# Trending content discovery
GET /songs/trending?genre={genre}&limit=50

# Artist catalog browsing
GET /artists/{id}/songs?limit=50

Content Access Endpoints​

# Song metadata and streaming URL
GET /songs/{id}

# Direct streaming endpoint
GET /songs/{id}/stream

# Playlist details with songs
GET /playlists/{id}?include_songs=true

User Action Endpoints​

# Playlist management
POST /playlists
PUT /playlists/{id}/songs
DELETE /playlists/{id}/songs/{song_id}

# Social interactions
POST /songs/{id}/like
POST /users/me/follow/{artist_id}

User Management Endpoints​

# Personal content access
GET /users/me/playlists
GET /users/me/liked-songs?limit=50&offset=0

API Conventions:

  • Consistent JSON response structure
  • Pagination metadata (total_count, limit, offset)
  • Proper HTTP status codes
  • JWT authentication via Authorization header

Data Storage Architecture​

Blob Storage Strategy​

Organization Structure:

/artist/{artistId}/album/{albumId}/{songId}.ogg

Characteristics:

  • Immutable audio files (rarely change post-upload)
  • Source of truth for audio content
  • Efficient for large file storage and retrieval

Relational Database Schema​

Core Tables:

Users Table:

CREATE TABLE Users (
    user_id SERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    subscription_type VARCHAR(20) DEFAULT 'free',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Artists Table:

CREATE TABLE Artists (
    artist_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    bio TEXT,
    image_url VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Songs Table:

CREATE TABLE Songs (
    song_id SERIAL PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    duration INTEGER NOT NULL, -- in seconds
    file_url VARCHAR(500) NOT NULL,
    bitrate INTEGER NOT NULL,
    file_size BIGINT NOT NULL,
    upload_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    play_count INTEGER DEFAULT 0
);

Playlists Table:

CREATE TABLE Playlists (
    playlist_id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES Users(user_id),
    name VARCHAR(100) NOT NULL,
    description TEXT,
    is_public BOOLEAN DEFAULT false,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

PlaylistItems Table:

CREATE TABLE PlaylistItems (
    playlist_id INTEGER REFERENCES Playlists(playlist_id),
    song_id INTEGER REFERENCES Songs(song_id),
    position INTEGER NOT NULL,
    added_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (playlist_id, song_id)
);

ArtistSongs Table (Many-to-Many):

CREATE TABLE ArtistSongs (
    artist_id INTEGER REFERENCES Artists(artist_id),
    song_id INTEGER REFERENCES Songs(song_id),
    role VARCHAR(50) DEFAULT 'primary', -- primary, featured, etc.
    PRIMARY KEY (artist_id, song_id)
);

Database Schema Diagram​

Database Schema Key Features:

  1. Core Entities:

    • Users: Account management and subscription tracking
    • Artists: Creator profiles and metadata
    • Songs: Audio content with technical specifications
    • Albums: Logical grouping of songs
    • Playlists: User-created collections

  2. Relationship Management:

    • ArtistSongs: Many-to-many artist/song relationships (collaborations)
    • PlaylistItems: Ordered song sequences in playlists
    • SongGenres: Multi-genre classification system
    • UserFollows: Social following relationships
    • LikedSongs: User preference tracking

  3. Analytics & Tracking:

    • PlayHistory: Detailed listening analytics
    • Play count: Song popularity metrics
    • User engagement: Follow and like patterns

  4. Data Integrity Features:

    • Foreign Key Constraints: Prevent orphaned records
    • Composite Primary Keys: Ensure unique relationships
    • NOT NULL Constraints: Enforce required fields
    • Default Values: Sensible fallbacks for optional fields

  5. Performance Considerations:

    • Indexed Fields: username, email, song titles, artist names
    • Trigram Indexes: Fast fuzzy search capabilities
    • Composite Indexes: Optimized multi-column queries
    • Partitioning Ready: PlayHistory table designed for time-based partitioning

Scalability Design Patterns:

  • Horizontal Partitioning: Large tables (PlayHistory) can be partitioned by date
  • Read Replicas: Separate read/write workloads effectively
  • Denormalization Ready: Critical paths can be optimized with materialized views
  • Archive Strategy: Old play history can be moved to cold storage

Database Design Rationale​

Why SQL Database?:

  • Complex relationships requiring JOINs
  • Referential integrity to prevent orphaned records
  • ACID properties for consistent data operations
  • Strong consistency requirements for metadata

Performance Optimizations:

Indexes for Common Queries:

-- Fast search capabilities with fuzzy matching
CREATE INDEX idx_songs_title_trigram ON Songs USING gin(title gin_trgm_ops);
CREATE INDEX idx_artists_name_trigram ON Artists USING gin(name gin_trgm_ops);

-- Playlist performance optimization
CREATE INDEX idx_playlist_items_playlist_id ON PlaylistItems(playlist_id);
CREATE INDEX idx_playlist_items_song_id ON PlaylistItems(song_id);

-- User queries optimization
CREATE INDEX idx_playlists_user_id ON Playlists(user_id);
CREATE INDEX idx_songs_play_count ON Songs(play_count DESC);

Trigram Indexes: Enable fast text search with typo tolerance and partial matching capabilities that users expect in search functionality.

Complete User Journey: Playing a Song​

This section demonstrates how all the architectural components work together when a user plays a song, showing the complete end-to-end flow through the system.

User Journey Flow Diagram​

Detailed Step-by-Step Breakdown​

Phase 1: User Interaction & Authentication (Steps 1-4)​

  1. User Action: User taps the play button on a song
  2. UI Request: Mobile app sends authenticated request to API
  3. Load Balancing: Request routed to healthy API server
  4. Authentication: JWT token validated for user permissions

Phase 2: Metadata Retrieval (Steps 5-8)​

  1. Database Query: API fetches song metadata (title, artist, duration)
  2. URL Generation: Signed URL created for secure audio access (2-hour expiration)
  3. Response Formation: JSON response with metadata and streaming URL
  4. UI Update: Song information displayed to user

Phase 3: Audio Streaming Setup (Steps 9-13)​

  1. Progressive Loading: Audio streaming begins while UI updates
  2. CDN Request: First audio chunk requested from global CDN
  3. Cache Strategy: CDN serves from cache or fetches from S3
  4. Content Delivery: Audio chunks delivered to mobile app
  5. Playback Start: Music begins playing immediately

Phase 4: Continuous Streaming & Analytics (Steps 14-17)​

  1. Buffer Management: App continuously requests next audio segments
  2. Analytics Tracking: Play progress sent every 30 seconds
  3. Play Count Updates: Database updated for recommendation engine
  4. Quality Adaptation: Bitrate adjusted based on network conditions

Performance Optimizations in User Journey​

Latency Reduction​

  • CDN Edge Caching: Popular songs served from nearest edge location
  • Parallel Processing: Metadata and audio streaming happen concurrently
  • Progressive Loading: Song starts playing while buffering upcoming content
  • Signed URLs: Direct CDN access bypasses API servers for audio delivery

User Experience Enhancements​

  • Immediate Feedback: UI updates instantly on play button press
  • Adaptive Quality: Automatic bitrate switching prevents buffering
  • Offline Preparation: Recent songs cached locally for instant replay
  • Error Recovery: Graceful handling of network interruptions

Cost Optimization​

  • CDN Efficiency: Reduces origin server bandwidth costs
  • Smart Caching: Popular content cached at multiple edge locations
  • Connection Pooling: Efficient database connection management
  • Analytics Batching: Play tracking data sent in optimized intervals

Real-World Performance Metrics​

Target Response Times:

  • Time to First Byte: < 200ms for audio streaming
  • API Response Time: < 100ms for metadata requests
  • CDN Cache Hit Ratio: > 85% for popular content
  • Playback Start Time: < 500ms from play button to audio

Scalability Indicators:

  • Concurrent Streams: System handles 100,000+ simultaneous users
  • Global Reach: CDN serves from 150+ edge locations worldwide
  • Database Performance: < 50ms average query response time
  • Storage Efficiency: 99.99% uptime for audio content delivery

Error Handling in User Journey​

Network Issues:

  • Automatic retry with exponential backoff
  • Quality degradation to maintain playback
  • Local cache fallback for recently played songs

Server Failures:

  • Load balancer routes to healthy instances
  • Database replica failover for read operations
  • CDN automatically fetches from origin on cache miss

Authentication Problems:

  • Token refresh mechanisms
  • Graceful degradation to guest mode
  • Clear error messaging for user action

This complete user journey demonstrates how Spotify's architecture prioritizes user experience through optimized data flow, intelligent caching, and robust error handling while maintaining scalability and cost efficiency.

Scalability Strategies​

CDN Implementation for Audio Delivery​

Benefits:

  • Global Distribution: Popular songs cached at edge locations worldwide
  • Reduced Latency: European users served from European edge servers
  • Cost Optimization: Reduced origin server load and bandwidth costs
  • Improved User Experience: Faster load times and reduced buffering

Cache Management:

  • Eviction Policy: Least Recently Used (LRU) for automatic cache management
  • Cache Miss Handling: Automatic fetch from origin storage
  • Security: CDN uses signed URLs for secure content access

Geographic Example: Song cached in Germany serves European users much faster than fetching from US origin storage.

Database Scaling Approaches​

Leader-Follower Replication​

Architecture:

  • Leader: Handles all write operations (uploads, playlist changes)
  • Followers: Handle read traffic (searches, metadata lookups)
  • Read Bias: Music streaming is heavily read-dominant

Benefits:

  • Horizontal read scaling by adding followers
  • Automatic failover capabilities
  • Cost-effective scaling for read-heavy workloads

Challenges:

  • Replication Lag: Followers may be slightly behind leader
  • Consistency Issues: Users might not immediately see their writes
  • Operational Complexity: Managing multiple database instances

Sharding Strategies​

When to Consider:

  • Catalog growth beyond single database capacity
  • Hot partitions causing performance bottlenecks
  • Need for geographic data locality

Sharding Options:

Geographic Sharding:

  • US users → US shard
  • EU users → EU shard
  • Benefits: Regulatory compliance, reduced latency
  • Challenge: Global artists popular everywhere

Artist ID Range Sharding:

  • Artists 1-1000 → Shard 1
  • Artists 1001-2000 → Shard 2
  • Benefits: Even distribution, predictable routing
  • Challenge: Popular artists creating hot shards

Trade-offs:

  • Pros: Horizontal scalability, improved performance
  • Cons: Cross-shard queries expensive, loss of foreign keys, complex rebalancing

API Layer Horizontal Scaling​

Stateless Server Design:

  • No session state stored locally
  • JWT tokens for authentication
  • Database connections via connection pooling

Auto-Scaling Benefits:

  • Traffic Adaptability: Handle morning commutes and evening listening spikes
  • Cost Efficiency: Scale up during peak hours, down during off-peak
  • Fault Tolerance: Server failures don't impact overall availability
  • Rolling Deployments: Zero-downtime updates

Scaling Triggers:

  • CPU utilization thresholds
  • Request rate limits
  • Response time degradation
  • Queue depth monitoring

Scale Transition Example​

Initial Scale (Baseline)​

  • 500K users, 30M songs
  • Song metadata: ~3GB
  • User metadata: ~0.5GB
  • Audio storage: ~90TB (before replicas)

Large Scale (Growth Target)​

  • 50M users, 200M songs
  • Song metadata: ~20GB
  • User metadata: ~50GB
  • Audio storage: ~600TB (before replicas)

Scaled Architecture Diagram​

Key Scalability Features Shown:

  1. Geographic Distribution:

    • 3 Regions: US, EU, APAC with localized clusters
    • Regional Load Balancers: Auto-scaling based on traffic
    • 50M Users Distributed: 15M US, 20M EU, 15M APAC

  2. Database Sharding Strategy:

    • User Sharding: Users distributed by geographic regions
    • Global Song Catalog: Centralized song database with regional replicas
    • Read Replicas: 3 replicas per region for read scaling
    • Cross-Region Sync: Consistent catalog across all regions

  3. Multi-Region Storage:

    • Regional S3 Buckets: ~200TB per region
    • Cross-Region Replication: Popular content synced globally
    • CDN Integration: 150+ edge locations worldwide
    • Smart Caching: Regional CDN clusters for optimal performance

  4. Auto-Scaling Infrastructure:

    • API Clusters: N servers per region with auto-scaling
    • Elastic Load Balancing: Dynamic traffic distribution
    • Container Orchestration: Kubernetes for service management
    • Circuit Breakers: Fault tolerance across regions

  5. Supporting Infrastructure:

    • Analytics Cluster: Kafka + Elasticsearch for real-time insights
    • Monitoring Stack: Prometheus + Grafana for observability
    • Search Cluster: Distributed Elasticsearch shards
    • Distributed Cache: Redis cluster for session management

Architectural Changes Required:

  • Multiple database shards
  • Global CDN deployment
  • Auto-scaling API clusters
  • Advanced caching strategies
  • Distributed monitoring systems

Reliability & Operations​

Monitoring & Observability​

Key Metrics:

  • Audio Performance: Time to first byte for streams
  • API Health: Error rates across all endpoints
  • Cache Efficiency: CDN cache hit ratios (target: 85%+)
  • Database Performance: Query latency and connection pool usage

Health Check Strategy:

  • Service-level health endpoints
  • Automatic traffic routing from unhealthy instances
  • Dependency health verification

Fault Tolerance Patterns​

Retry Mechanisms:

  • Exponential backoff for transient failures
  • Circuit breaker pattern for failing dependencies
  • Graceful degradation for non-critical features

Fallback Strategies:

  • CDN miss → Origin storage fetch
  • Database replica failure → Leader with circuit breaker protection
  • Search service failure → Cached popular content

Example Retry Configuration​

const retryConfig = {
  maxRetries: 3,
  initialDelay: 1000, // 1 second
  maxDelay: 8000, // 8 seconds
  backoffMultiplier: 2,
  retriableErrors: ['NETWORK_ERROR', 'TIMEOUT', '503', '502'],
};

Architecture Evolution Principles​

Start Simple, Scale Incrementally​

  1. Phase 1: Single database, simple blob storage, basic CDN
  2. Phase 2: Add read replicas, implement caching
  3. Phase 3: Introduce sharding, global CDN, auto-scaling
  4. Phase 4: Microservices, advanced analytics, ML recommendations

Design Decisions Framework​

Storage Architecture:

  • Signed URLs vs Proxy Streaming: Signed URLs reduce API server load but provide less access control
  • SQL vs NoSQL: SQL chosen for complex relationships and consistency requirements
  • Blob Storage vs Distributed File System: Blob storage preferred for managed service benefits

Scalability Trade-offs:

  • Horizontal vs Vertical Scaling: Horizontal preferred for elasticity and fault tolerance
  • Consistency vs Availability: Eventual consistency acceptable for non-critical features
  • Cost vs Performance: CDN costs justified by user experience improvements

Key Takeaways​

  1. Audio Dominates Resources: Storage and bandwidth costs primarily driven by audio content, not metadata
  2. Read-Heavy Architecture: Music streaming is predominantly read-intensive, informing scaling strategies
  3. Geographic Considerations: Global content distribution requires regional CDN and data locality
  4. Gradual Complexity: Start with simple architecture and add complexity as scale demands
  5. Fault Tolerance Essential: Multiple fallback mechanisms required for reliable audio streaming
  6. Cost Optimization: CDN and efficient encoding critical for managing bandwidth costs
