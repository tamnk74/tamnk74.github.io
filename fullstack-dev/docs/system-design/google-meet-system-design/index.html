Google Meet: Video Conferencing Platform — System Design

Overview​

Design a real-time video conferencing platform similar to Google Meet that allows users to create, join, and participate in video/audio meetings with screen sharing, chat, and recording capabilities. The system must handle millions of concurrent meetings with low-latency media streaming, seamless participant management, and cross-platform support (web, mobile, desktop).

Scope: real-time video/audio conferencing with core collaboration features (screen sharing, chat, recording). Does not cover phone dial-in (PSTN), live streaming to YouTube, or breakout rooms in depth.

Scale Estimates​

Users:

  • 300M MAU, 100M DAU, 10M peak concurrent users
  • Average meeting duration: 35 minutes
  • Average participants per meeting: 4

Meetings:

  • 100M meetings/day = ~1,150 meetings/s average, 5,000 meetings/s peak
  • 10M concurrent meetings at peak hours

Media traffic:

  • Per participant: ~2.5 Mbps video send + ~2.5 Mbps video receive (720p)
  • Audio: 32 kbps per stream (Opus)
  • Peak aggregate bandwidth: ~80 Pbps across all media servers

Storage:

  • Recordings: 10% of meetings recorded × avg 35 min × ~150 MB/hour = ~8.75 PB/year
  • Chat messages: ~50 messages/meeting × 100M meetings/day × 200 bytes = ~1 TB/day
  • Meeting metadata: ~2 KB/meeting × 100M/day = ~200 GB/day

4.1 Signaling Service​

Responsibilities: WebSocket connection management, SDP offer/answer exchange, ICE candidate relay, room state synchronization, participant presence tracking.

The Signaling Service is the control plane of the meeting — it does not handle media, only the negotiation metadata needed for peers to establish WebRTC connections to the SFU.

4.2 Media Service (SFU — Selective Forwarding Unit)​

Responsibilities: receive media tracks from publishers, selectively forward to subscribers, simulcast layer selection, bandwidth estimation, audio mixing (optional), media recording tap.

The SFU is the data plane — each participant sends their media stream once to the SFU, which forwards it to all other participants. This is far more efficient than mesh (P2P) for meetings > 3 participants.

Why SFU over other topologies:

TopologyProsConsUse case
Mesh (P2P)No server cost, lowest latency for 2 peopleN×(N-1) streams, CPU scales exponentially1:1 calls
SFUEach sender uploads once, server bandwidth scales linearly, simulcast controlServer cost, more complex3–500 participants
MCU (Mixing)Single composite stream to each viewerEnormous server CPU, latency from encode/decodeLegacy systems

Simulcast & adaptive bitrate:

Each publisher sends 3 simultaneous layers (simulcast):

Layers={(720p,1.5 Mbps),(360p,500 kbps),(180p,150 kbps)}\text{Layers} = \{(720p, 1.5\text{ Mbps}), (360p, 500\text{ kbps}), (180p, 150\text{ kbps})\}Layers={(720p,1.5 Mbps),(360p,500 kbps),(180p,150 kbps)}

The SFU selects which layer to forward to each subscriber based on:

  1. Subscriber viewport size — small grid tiles get low layer, active speaker gets high
  2. Available bandwidth — estimated via REMB / Transport-CC feedback
  3. CPU constraints — mobile clients prefer lower resolution

Bandwidth estimation per participant:

DownlinkBW=∑i=1N−1SelectedLayeri+∑i=1N−1AudioBitrate\text{DownlinkBW} = \sum_{i=1}^{N-1} \text{SelectedLayer}_i + \sum_{i=1}^{N-1} \text{AudioBitrate}DownlinkBW=i=1∑N−1​SelectedLayeri​+i=1∑N−1​AudioBitrate

Example: 10-person meeting, active speaker at 720p, 8 others at 180p:

BW=(1×1500)+(8×150)+(9×32)=1500+1200+288=2988 kbps≈3 Mbps\text{BW} = (1 \times 1500) + (8 \times 150) + (9 \times 32) = 1500 + 1200 + 288 = 2988\text{ kbps} \approx 3\text{ Mbps}BW=(1×1500)+(8×150)+(9×32)=1500+1200+288=2988 kbps≈3 Mbps

4.5 Recording Service​

Responsibilities: server-side recording capture, multi-track mixing, transcoding, cloud storage upload, transcript generation.

Recording storage strategy:

  • Chunked upload every 30 s ensures no data loss on crash
  • Final output: MP4 (H.264 + AAC) for broad compatibility
  • Transcripts: WebVTT format with speaker diarization
  • Retention: configurable per organization (default 90 days)
  • Storage: gs://recordings/{org_id}/{meeting_id}/{timestamp}.mp4

Step 7: Infrastructure and Deployment​

Implementation guides: GKE Cluster Setup · Kubernetes Deployment Guide · GitOps on GCP with ArgoCD

Multi-region media strategy:

  • SFU nodes are deployed in every region close to users to minimise media latency.
  • Cascading bridges connect SFU clusters across regions — when a meeting has participants in US and EU, each group connects to their local SFU, and the SFUs forward media between themselves.
  • Signaling is region-aware — clients connect to their nearest signaling endpoint, which coordinates with the assigned SFU.
  • Failover: if a regional SFU pool is unhealthy, participants are migrated to the next-nearest region with brief media interruption.

Scaling targets:

ComponentStrategy
API GatewayHPA on concurrent WebSocket connections (target 80%)
Signaling ServiceHPA on WebSocket connections + CPU (target 60%)
SFU NodesCustom autoscaler on participant count per node (target 200 participants/node)
Recording WorkersHPA on recording queue depth
PostgreSQLVertical for writes; read replicas per region for reads
RedisCluster mode (6+ shards); scale on connection count + memory
KafkaPartition-per-region topics; scale consumers on lag
TURN serversScale with concurrent relay sessions (target 500 relays/server)

Step 12: WebRTC Protocol Stack​

Implementation guides: WebRTC Implementation Guide · Distributed Tracing & Context Propagation

Understanding the protocol layers is essential for debugging and performance tuning:

Key protocol responsibilities:

  • ICE: discovers the best network path (host → srflx → relay candidates)
  • DTLS: key exchange for SRTP encryption; mutual authentication
  • SRTP: encrypts and authenticates RTP media packets
  • SCTP/DataChannel: reliable data transport for chat (if used over WebRTC instead of WebSocket)
  • RTCP: feedback channel — receiver reports, REMB (bandwidth estimation), PLI (picture loss indication)
