How Datadog Built a Custom Database to Ingest Billions of Metrics Per Second

Introduction​

In the world of cloud monitoring, Datadog operates at a massive scale. The company's platform must ingest billions of data points every single second from millions of hosts around the globe. This constant flow of information creates an immense engineering challenge: how do you store, manage, and query this data in a way that is not only lightning-fast but also cost-effective?

For the Datadog Engineering Team, the answer was to build their own solution from the ground up.

This article explores how the Datadog engineering team built Monocle, their custom-built time series storage engine written in Rust, to power their real-time metrics platform. We'll analyze the technical decisions and clever optimizations behind this remarkable database.

High-Level Metrics Platform Architecture​

Before diving into the custom database engine, it's important to understand where it fits. Monocle is just one specialized component within a much larger "Metrics Platform" - the entire system responsible for collecting, processing, storing, and serving all customer metrics.

The Journey of a Data Point​

The journey of a single data point begins at the "Metrics Edge". This component acts as the front door, receiving the flood of data from millions of customer systems. From there, it's passed to a "Storage Router", which processes the incoming data and intelligently decides where it needs to be stored.

The Two-Store Architecture​

This is where Datadog's first major design decision becomes clear. The Datadog Engineering Team recognized that not all data queries are the same. An engineer asking for a performance report from last year has very different needs than an automated alert checking for a failure in the last 30 seconds.

To serve both use cases efficiently, they split their storage into two massive, specialized systems:

1. Long-Term Metrics Storage​

The first system is like a vast historical archive. It's built for heavy-duty analytical queries, where an engineer might want to analyze a performance trend over many months or even years. This system prioritizes:

  • Storage efficiency and cost optimization
  • Analytical queries over large time ranges
  • Historical data for trend analysis, capacity planning, and compliance

2. Real-Time Metrics Storage (RTDB)​

The second system is a high-speed, high-performance engine that holds only the most recent data - roughly the last 24 hours. While that might not sound like a lot, this system handles the vast majority of the platform's workload:

  • 99% of all queries are served by this system
  • Powers Datadog's live dashboards and critical automated monitors
  • When a user sees a graph update in real-time, this is the system at work

Splitting Metadata and Data​

A time series data point has two parts:

  1. The Data: The actual timestamp and value being measured (e.g., [12:00:01 PM, 85.5])
  2. The Metadata: Labels or "tags" that describe what the data is (e.g., service:api, host:server-10, region:us-east-1)

The Datadog Engineering Team made the critical decision to store these two parts in separate, specialized databases:

Index Database​

  • Purpose: Store only the tags (metadata)
  • Function: Incredibly fast at finding data
  • Example: When a user asks "Show me the CPU for all services in us-east", this database instantly finds all unique data streams matching those tags

Real-Time Timeseries Database (RTDB)​

  • Purpose: Store only timestamps and values
  • Function: Highly optimized storage that retrieves raw numbers
  • Process: After getting the list of streams from the Index Database, it just retrieves the raw numbers

This separation allows each system to be optimized for its specific task without compromise.

Problem Statement​

Scale Requirements​

  • Ingestion: Billions of metrics per second
  • Storage: Petabytes of time-series data
  • Query Performance: Sub-second latency for dashboards and alerts
  • Retention: Multiple retention tiers (1h, 1d, 1w, 1m, 1y)
  • Cardinality: Millions of unique time series
  • Availability: 99.99% uptime SLA

Challenges​

  1. High Write Throughput: Handle massive concurrent writes from millions of agents
  2. Storage Efficiency: Compress time-series data efficiently
  3. Query Speed: Fast aggregation across millions of time series
  4. Cost Management: Balance performance with storage costs
  5. Data Durability: Ensure no data loss despite failures
  6. Multi-tenancy: Isolate data and performance across thousands of customers

Using Kafka: The Architectural Foundation​

Perhaps the most unique architectural decision the Datadog Engineering Team made is how their database clusters are organized. In many traditional distributed databases, the server nodes (the individual computers in the cluster) constantly talk to each other. They "chatter" to coordinate who is doing what, to copy data between themselves (a process called replication), and to figure out what to do if one of them fails.

Datadog's RTDB nodes don't do this.

Instead, the entire system is designed around Apache Kafka. Here, Kafka acts as a central place where all new data is written first before it even touches the database. This Kafka-centric design is the key to the cluster's stability and speed.

Three Critical Functions of Kafka​

The Datadog Engineering Team uses Kafka to perform three critical functions that the database nodes would otherwise have to do themselves:

1. Data Distribution​

The data in Kafka is organized into "topics" (like metrics), which are split into smaller logs called "partitions". The team designed the system so that:

  • Each RTDB database node is assigned its own specific set of partitions to read from
  • This neatly divides the billions of incoming data points without the nodes ever needing to coordinate
  • No inter-node communication means no distributed consensus overhead
// Kafka partition assignment for RTDB nodes
class PartitionAssignment {
  // Each RTDB node reads from specific partitions
  private nodeToPartitions: Map<string, number[]> = new Map([
    ['rtdb-node-1', [0, 1, 2]],
    ['rtdb-node-2', [3, 4, 5]],
    ['rtdb-node-3', [6, 7, 8]],
  ]);

  // Nodes independently consume their assigned partitions
  async consumeMetrics(nodeId: string): Promise<void> {
    const partitions = this.nodeToPartitions.get(nodeId);

    for (const partition of partitions) {
      // Each node reads independently - no coordination needed
      await this.kafkaConsumer.subscribe({
        topic: 'metrics',
        partition,
        fromBeginning: false,
      });
    }
  }
}

Key Benefits:

  • Zero coordination overhead between database nodes
  • Simple scaling: Add more nodes, assign more partitions
  • Parallel processing: All nodes work simultaneously without conflicts

2. Write-Ahead Log (WAL)​

This is a standard database concept for ensuring data safety. By using Kafka as the WAL, Datadog creates a "single source of truth":

  • If an RTDB node crashes due to hardware failure, no data is lost
  • When the node restarts, it simply:
    1. Reconnects to Kafka
    2. Finds its last known reading position (offset)
    3. Catches up on all the data it missed
// Crash recovery using Kafka offsets
class CrashRecovery {
  async recoverFromCrash(nodeId: string): Promise<void> {
    // Find last committed offset before crash
    const lastOffset = await this.getLastCommittedOffset(nodeId);

    console.log(`Node ${nodeId} recovering from offset ${lastOffset}`);

    // Resume from last known position
    await this.kafkaConsumer.seek({
      topic: 'metrics',
      partition: this.getPartition(nodeId),
      offset: lastOffset,
    });

    // Process all missed data
    while (true) {
      const messages = await this.kafkaConsumer.fetch();
      for (const message of messages) {
        await this.processMetric(message.value);
        await this.commitOffset(message.offset);
      }
    }
  }
}

Key Benefits:

  • No data loss on node failures
  • Exactly-once processing with Kafka's offset mechanism
  • Replay capability for debugging or reprocessing

3. Replication Across Availability Zones​

To prevent data loss, you must have copies of your data in different physical locations. The team leverages Kafka's built-in replication, which automatically copies the data partitions to different data centers (Availability Zones).

# Kafka configuration for high availability
kafka:
  # Three copies of each partition
  replication.factor: 3

  # Require 2 out of 3 replicas to acknowledge writes
  min.insync.replicas: 2

  # Never elect out-of-sync replica as leader
  unclean.leader.election.enable: false

  # Spread replicas across availability zones
  broker.rack.awareness: enabled
  replica.placement.strategy: rack-aware

  # Each broker specifies its AZ
  broker.rack:
    broker-1: us-east-1a
    broker-2: us-east-1b
    broker-3: us-east-1c

Key Benefits:

  • Survive multiple node/AZ failures without data loss
  • Automatic failover to replica if primary fails
  • Geographic distribution for disaster recovery
  • Robust disaster recovery right out of the box

Why This Design Is Brilliant​

By centralizing these functions in Kafka, Datadog's RTDB nodes become dramatically simpler:

  1. No peer-to-peer communication - nodes don't know about each other
  2. No consensus protocols - no Raft, no Paxos complexity
  3. No replication logic - Kafka handles it
  4. Easier operations - can restart/replace nodes freely

This architectural choice allows the Monocle team to focus on one thing: making the fastest possible time-series storage engine.

Monocle: The Custom-Built Engine in Rust​

At the heart of each RTDB node is Monocle, Datadog's custom-built storage engine. While earlier versions of the platform used RocksDB, a popular and powerful open-source database engine, the team ultimately decided to build its own. By creating Monocle from scratch, they could tailor every single decision to their specific needs, unlocking a new level of efficiency.

Monocle is written in Rust, a modern programming language famous for its safety guarantees and "C-like" performance. It's built on Tokio, a popular framework in the Rust ecosystem for writing high-speed, asynchronous applications that can handle many tasks at once without getting bogged down.

The Core Data Model: Hashing Tags​

Monocle's key innovation is its simple data model. As mentioned, a time series is defined by its tags, like:

  • "system.cpu.user"
  • "host:web-01"
  • "env:prod"

This set of tags is what makes a series unique. However, these tag sets can be long and complex to search.

The Datadog Engineering Team simplified this dramatically. Instead of working with these complex strings, Monocle hashes the entire set of tags for a series, turning it into a single, unique number. The database then just stores data in a simple map:

(Organization, Metric Name, Tag Hash) → (A list of [Timestamp, Value] pairs)

This design is incredibly fast because finding all the data for any given time series becomes a direct and efficient lookup using that single hash. The separate Index Database is responsible for the human-friendly part: it tells the system that a query for env:prod corresponds to a specific list of "Tag Hashes."

// Simplified data model in Monocle
interface MonocleKey {
  orgId: number;
  metricName: string;
  tagHash: bigint; // Hash of all tags combined
}

interface MonocleSeries {
  key: MonocleKey;
  points: Array<[timestamp: number, value: number]>;
}

class MonocleDataModel {
  // Simple hash-based lookup
  private data: Map<string, MonocleSeries> = new Map();

  getKey(orgId: number, metricName: string, tags: Record<string, string>): string {
    // Sort tags for consistent hashing
    const sortedTags = Object.keys(tags)
      .sort()
      .map((k) => `${k}:${tags[k]}`)
      .join(',');

    const tagHash = murmurhash3(sortedTags);
    return `${orgId}:${metricName}:${tagHash}`;
  }

  write(orgId: number, metricName: string, tags: Record<string, string>, point: [number, number]): void {
    const key = this.getKey(orgId, metricName, tags);

    if (!this.data.has(key)) {
      this.data.set(key, {
        key: { orgId, metricName, tagHash: BigInt(murmurhash3(Object.values(tags).join(','))) },
        points: [],
      });
    }

    this.data.get(key).points.push(point);
  }

  read(orgId: number, metricName: string, tagHash: bigint): Array<[number, number]> {
    const key = `${orgId}:${metricName}:${tagHash}`;
    return this.data.get(key)?.points || [];
  }
}

Inside Monocle: Architecture and Optimizations​

Monocle's speed comes from two main areas: its concurrency model and its storage structure.

Thread-Per-Core ("Shared-Nothing") Architecture​

Monocle uses what is known as a "thread-per-core" or "shared-nothing" architecture. You can imagine each CPU core in the server has its own dedicated worker, which operates in total isolation. Each worker has:

  • Its own data
  • Its own cache
  • Its own memory
  • They don't share anything

When new data comes in from Kafka, it's hashed. The system then sends that data to the specific queue for the one worker that "owns" that hash. Since each worker is the only one who can ever access their own data, there's:

  • No need for locks
  • No coordination
  • No waiting

This eliminates a massive performance bottleneck common in traditional databases, where different threads often have to wait for each other to access the same piece of data.

LSM-Tree Storage Layout​

Monocle's storage layout is a Log-Structured Merge-Tree (LSM-Tree). This is a design that is extremely efficient for write-heavy workloads like Datadog's.

Main Concepts:

  1. Memtable: All new data is batched in memory in a structure called a Memtable
  2. Flushing: When the Memtable is full, it's "flushed" to disk as a complete, read-only file. The system never goes back to modify old files
  3. Compaction: Over time, a background process called compaction tidies up by merging these small files into larger, more organized ones
// Simplified LSM-Tree structure
struct LSMTree {
    // Hot data: in-memory
    memtable: MemTable,
    immutable_memtables: Vec<ImmutableMemTable>,

    // Cold data: on disk (read-only)
    sstables_l0: Vec<SSTable>,  // Recently flushed, may overlap
    sstables_l1: Vec<SSTable>,  // Compacted, sorted, non-overlapping
    sstables_l2: Vec<SSTable>,  // Larger, compacted files
}

// Write flow
async fn write(key: SeriesKey, point: DataPoint) {
    // 1. Write to memtable (in-memory, fast)
    memtable.insert(key, point);

    // 2. If memtable full, flush to disk
    if memtable.is_full() {
        let sstable = memtable.flush_to_disk().await;
        sstables_l0.push(sstable);
        memtable.clear();
    }
}

// Read flow
async fn read(key: SeriesKey, time_range: TimeRange) -> Vec<DataPoint> {
    let mut points = Vec::new();

    // 1. Check memtable first (most recent)
    points.extend(memtable.get(key, time_range));

    // 2. Check immutable memtables (being flushed)
    for imm in immutable_memtables {
        points.extend(imm.get(key, time_range));
    }

    // 3. Check SSTables from newest to oldest
    for sstable in sstables_l0 {
        points.extend(sstable.get(key, time_range).await);
    }

    points.sort_by_key(|p| p.timestamp);
    points
}

Critical Optimizations​

The Datadog Engineering Team added two critical optimizations to this design:

1. Arena Allocator​

Normally, when a Memtable is flushed, the database would have to free millions of tiny objects from memory, which is a slow process. Monocle uses a custom arena allocator:

  • The Memtable gets one giant chunk of memory (an "arena")
  • When it's done, the entire chunk is freed all at once
  • This is vastly more efficient than freeing millions of small allocations
// Arena allocator for efficient memory management
struct ArenaAllocator {
    arena: Vec<u8>,
    offset: usize,
}

impl ArenaAllocator {
    fn allocate(&mut self, size: usize) -> *mut u8 {
        let ptr = &mut self.arena[self.offset] as *mut u8;
        self.offset += size;
        ptr
    }

    // Free entire arena at once - O(1) operation!
    fn free_all(&mut self) {
        self.offset = 0;
        // No need to free individual allocations
        // Just reset the offset
    }
}
2. Time-Based File Pruning​

Since 99% of queries are for recent data, Monocle takes advantage of this:

  • Each file on disk has a known time range (e.g., 10:00 AM - 10:10 AM)
  • When a query comes in for the last hour, Monocle can instantly prune (ignore) all the files that aren't from that time window
  • This reduces the number of files it has to read to find the answer
struct SSTableMetadata {
    min_timestamp: i64,
    max_timestamp: i64,
    file_path: PathBuf,
}

impl SSTable {
    fn can_contain(&self, time_range: &TimeRange) -> bool {
        // Prune files outside the query time range
        !(self.metadata.max_timestamp < time_range.start ||
          self.metadata.min_timestamp > time_range.end)
    }
}

// Query optimization with time-based pruning
async fn query_with_pruning(time_range: TimeRange) -> Vec<DataPoint> {
    let mut points = Vec::new();

    for sstable in all_sstables {
        // Skip files that can't possibly contain data in range
        if !sstable.can_contain(&time_range) {
            continue;  // Pruned!
        }

        points.extend(sstable.read(time_range).await);
    }

    points
}

Impact of Optimizations:

  • Arena allocator: 10x faster memtable flushing
  • Time-based pruning: 100x reduction in files scanned for recent queries
  • Combined effect: Sub-millisecond query latency for 99% of queries

Staying Fast Under Pressure​

Handling so many queries with the "thread-per-core" design creates a unique challenge.

Since a query is fanned out to all workers, it's only as fast as its slowest worker. If one worker is busy performing a background task, like a heavy data compaction, it can stall the entire query for all the other workers. This is a classic computer science problem known as head-of-line blocking.

To solve this, the team built a two-layer system to manage the query load and stay responsive.

Layer 1: Admission Control​

This acts as a simple "gate" at the front door. If the system detects it's under extreme load, this gate will simply stop accepting new queries. This protects the database from being overwhelmed.

Admission Control Triggers:

  • Falling behind on reading data from Kafka
  • Low on memory
  • High CPU utilization
  • Too many in-flight requests
class AdmissionController {
  private maxLag: number = 1000; // Max Kafka lag in messages
  private maxMemoryUsage: number = 0.9; // 90%
  private maxCPU: number = 0.85; // 85%

  async shouldAdmitQuery(query: Query): Promise<boolean> {
    // Check Kafka consumer lag
    const kafkaLag = await this.getKafkaConsumerLag();
    if (kafkaLag > this.maxLag) {
      this.metrics.record('admission_rejected', { reason: 'kafka_lag' });
      return false;
    }

    // Check memory pressure
    const memUsage = process.memoryUsage().heapUsed / process.memoryUsage().heapTotal;
    if (memUsage > this.maxMemoryUsage) {
      this.metrics.record('admission_rejected', { reason: 'memory_pressure' });
      return false;
    }

    // Check CPU utilization
    const cpuUsage = await this.getCPUUtilization();
    if (cpuUsage > this.maxCPU) {
      this.metrics.record('admission_rejected', { reason: 'cpu_overload' });
      return false;
    }

    // Admit the query
    return true;
  }
}

Benefits:

  • Protects system stability during load spikes
  • Fails fast with clear error messages
  • Prevents cascading failures across the cluster
  • Simple to implement and reason about

Layer 2: Cost-Based Scheduling with CoDel​

This is a smarter system that uses a well-known algorithm called CoDel (Controlled Delay) to actively manage latency. It can:

  • Prioritize queries based on their cost (how much work they need to do)
  • Ensure that even under heavy, unpredictable query bursts, the database remains responsive and doesn't grind to a halt
class CoDelScheduler {
  private readonly targetDelay = 5; // 5ms target
  private readonly interval = 100; // 100ms interval
  private droppingState = false;
  private firstAboveTime = 0;

  async scheduleQuery(query: Query): Promise<void> {
    const cost = this.estimateQueryCost(query);
    const queueTime = Date.now() - query.submittedAt;

    // CoDel algorithm
    if (queueTime < this.targetDelay) {
      // Queue time is acceptable
      this.firstAboveTime = 0;
      this.droppingState = false;
    } else {
      // Queue time exceeded target
      if (this.firstAboveTime === 0) {
        this.firstAboveTime = Date.now();
      } else if (Date.now() - this.firstAboveTime > this.interval) {
        // Start dropping or deprioritizing expensive queries
        this.droppingState = true;

        if (cost.estimatedDuration > 100) {
          // Expensive query
          // Delay expensive query
          await this.delay(50);
        }
      }
    }

    // Execute query
    await this.executeQuery(query);
  }

  private estimateQueryCost(query: Query): QueryCost {
    const timeRange = query.endTime - query.startTime;
    const seriesCount = this.estimateSeriesCount(query);
    const pointsPerSeries = timeRange / query.resolution;
    const totalPoints = seriesCount * pointsPerSeries;

    return {
      estimatedDuration: totalPoints * 0.001, // 1μs per point
      complexity: seriesCount > 1000 ? 'high' : 'low',
    };
  }
}

How CoDel Works:

  1. Monitor queue delay: Track how long queries wait in queue
  2. Target delay: Try to keep queue delay below 5ms
  3. When delay exceeds target: Start dropping/deprioritizing expensive queries
  4. Adaptive: Automatically adjusts to load conditions

Benefits:

  • Maintains low latency for simple queries even during spikes
  • Prevents expensive queries from blocking cheap ones
  • Self-tuning: No manual configuration needed
  • Proven algorithm: Used in networking and databases

Conclusion: Future Evolution​

Datadog's custom time-series database represents a masterclass in building systems for extreme scale. By combining proven technologies (Kafka, LSM-Tree) with innovative designs (thread-per-core architecture, dual-store model, tag hashing), they created a system that handles billions of metrics per second while maintaining sub-100ms query latency.

Key Architectural Decisions​

The three most impactful design choices were:

  1. Kafka as the Central Nervous System - Using Kafka for WAL, replication, and data distribution eliminated complex coordination logic and provided battle-tested reliability.

  2. Thread-Per-Core Architecture - Building on Rust and Tokio's async runtime enabled massive parallelism without the overhead of traditional thread synchronization.

  3. Tag Hashing - Converting complex multi-tag queries into simple hash lookups transformed query performance from O(n) scans to O(1) lookups.

What's Next?​

The Datadog team continues to evolve the database to handle even more demanding workloads:

Smarter Query Routing:

  • Route queries to nodes that already have data cached
  • Predict which queries will be expensive and route to dedicated "heavy query" workers
  • Use machine learning to optimize data placement based on access patterns

Colocating Points and Tags:

  • Current design stores points and tags separately
  • Future versions may colocate frequently accessed tags with points for faster retrieval
  • Trade-off: More storage space vs. fewer disk seeks

Columnar Database Format:

  • Explore columnar storage (like Parquet) for better compression and analytics
  • Enable faster aggregation queries across millions of series
  • Particularly beneficial for long-term historical data

Thread-Per-Core Model Enhancements:

  • Redesign data structures to be more NUMA-aware
  • Optimize cross-worker communication for fan-out queries
  • Explore hardware-accelerated compression/decompression

Lessons for System Designers​

Building a system at this scale requires:

  • Start simple, evolve based on real workloads - Don't over-optimize prematurely
  • Measure everything - You can't improve what you don't measure
  • Embrace constraints - The thread-per-core model's constraints led to innovative solutions
  • Use proven building blocks - Kafka and LSM-Trees are battle-tested for good reason
  • Think in layers - Admission control + CoDel provides defense in depth
  • Design for failure - Multi-AZ replication and automatic failover are table stakes

Datadog's journey shows that building world-class infrastructure requires not just technical excellence, but also deep understanding of your workload characteristics and user needs.
