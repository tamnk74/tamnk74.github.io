Restaurant Management System — System Design

Overview​

Design a restaurant management system (RMS) that covers the full lifecycle of a restaurant operation: online ordering and table reservations, point-of-sale (POS) at front-of-house, kitchen display and order routing, menu and inventory management, staff scheduling, payment processing, and analytics. The system must handle peak lunch/dinner rushes with sub-second order confirmation, enforce real-time inventory deduction to prevent overselling, and support both single-outlet independents and multi-location chains from a single platform.

Scope: dine-in POS, online ordering (web + app), delivery dispatch, kitchen management, inventory, staff scheduling, and reporting. Out of scope: supplier procurement marketplace, accounting/payroll integrations (documented as future phase).

Scale Estimates​

Platform scale (SaaS):

  • 10k restaurant locations onboarded
  • Avg 200 orders/location/day = 2M orders/day platform-wide
  • Peak: lunch 12–1 pm = 30% of daily orders in 1 hour → ~167 orders/s platform-wide

Per location (large venue):

  • 500 seats, 3 seatings/night → 1,500 covers
  • Avg 4 items/order → 6,000 line items/day
  • Menu: 200 items, 50 modifiers, 30 categories

Data:

  • Order record: ~3 KB × 2M/day = ~6 GB/day
  • Inventory snapshots: ~1 KB × 500 items × 10k locations = ~5 GB/snapshot
  • Analytics: ~50 GB/day (raw events → ClickHouse OLAP)

Step 5: Key Service Designs​

5.1 Menu Service — Cache Strategy​

Menu reads are the highest-traffic path (every page load, every checkout). The read-heavy nature allows aggressive caching:

Write path:
  Manager updates menu item → POST /menu/items/{id}
  → Persist to PostgreSQL
  → Invalidate Redis key: menu:{restaurant_id}:v{version}
  → Publish MenuUpdated event to Kafka
  → POS apps receive WebSocket push to refresh local SQLite cache

Read path (cache-aside):
  GET /menu/{restaurant_id}
  → Check Redis key (TTL: 5 min)
  → Cache hit: return immediately (~1 ms)
  → Cache miss: query PostgreSQL, populate Redis, return

CacheKey: menu:{restaurant_id}:items  (full menu JSON blob, ~20 KB avg)
Invalidation: on any item/price/availability change

86 Toggle (item unavailability): When a menu item runs out mid-service, staff tap "86 this item" on the POS. This sets available=false, invalidates the cache, and within 1–2 s the item is greyed out on all customer ordering surfaces and hidden on the KDS.

5.2 Inventory Service — Recipe-Based Deduction​

Each ORDER_ITEM maps to RECIPE_COMPONENT rows that define raw ingredient consumption per unit.

On order confirm (synchronous, within 500 ms):
  1. Find recipe_components for all order items (cached in Redis)
  2. BEGIN SERIALIZABLE TX
  3. SELECT FOR UPDATE on inventory_item rows (lock by restaurant_id + item_id)
  4. FOR EACH component: quantity_on_hand -= (quantity_used × order_qty)
  5. IF quantity_on_hand < low_stock_threshold → emit InventoryLow event
  6. IF quantity_on_hand < 0 → ROLLBACK → return InsufficientStock error
  7. COMMIT

On order cancel/void:
  Reverse deduction within same TX pattern (compensating update)

Low-stock alerts route through Kafka → Notification Service → SMS/push to manager in < 30 s.

5.3 Kitchen Routing — Station Fan-Out​

Each menu item carries station_tags (e.g., ["grill"], ["cold", "bar"]). When an order is confirmed:

KitchenSvc groups order items by station:
  grill_items  = items where "grill" in station_tags
  cold_items   = items where "cold" in station_tags
  bar_items    = items where "bar" in station_tags

For each station with items:
  → Publish KDSOrderCard event on topic: kds.{restaurant_id}.{station}
  → KDS screens subscribe to their station topic via WebSocket
  → Card shows: table/order ref, item list, modifiers, special instructions, timer

Bump logic:
  Chef bumps an item → PATCH /kitchen/items/{id}?status=READY
  → KitchenSvc checks: are ALL items in order now READY?
     YES → OrderSvc transitions order to READY → notify waiter
     NO  → update item status, waiter app shows partial readiness

5.4 Reservation — Floor Plan Concurrency​

Double-booking prevention uses optimistic locking with a version counter on table rows:

-- Attempt to reserve (single statement CAS):
UPDATE tables
SET    status = 'RESERVED', version = version + 1
WHERE  id = $table_id
  AND  status = 'AVAILABLE'
  AND  version = $expected_version
RETURNING id;

-- 0 rows updated → conflict → return 409 to client
-- 1 row updated → reservation confirmed

The reservations table additionally enforces a partial index exclusion constraint:

CREATE UNIQUE INDEX idx_no_overlap
ON reservations (table_id, tstzrange(reserved_at, reserved_at + interval '2 hours'))
WHERE status NOT IN ('CANCELLED', 'NO_SHOW');

5.5 Offline POS — CRDT-Based Sync​

The POS app uses a Last-Write-Wins CRDT for inventory deductions and an append-only log for orders:

Conflict typeResolution strategy
Two POS devices sell the same last unit of an ingredientServer-side: whichever sync arrives first wins; second device's order flagged for manager review
Menu price changed during offline periodServer replaces offline price with canonical price at sync time; receipt reissued
Order placed offline then payment gateway responds with duplicateIdempotency key prevents double-posting

Step 6: Multi-Tenancy Architecture​

The platform is a SaaS product hosting 10k+ restaurant locations:

Tenant model: Shared database, row-level isolation
  - Every table includes tenant_id (restaurant_group_id)
  - PostgreSQL Row-Level Security (RLS) policies enforce isolation
  - API Gateway injects tenant_id from verified JWT claims
  - No cross-tenant data leakage possible at DB layer

Tenant hierarchy:
  RestaurantGroup (brand)
    └── Location (individual restaurant)
          ├── Menu (can inherit brand menu or override)
          ├── Inventory (always per-location)
          └── Staff (per-location, with chain-level admin role)

Customisation per location:
  - Local tax rates and fiscal printer config stored in TenantConfig (Redis)
  - Menu items can be 86'd locally without affecting other locations
  - Price overrides per location (e.g., airport surcharge)

Step 7: Scalability​

Horizontal Scaling​

  • Menu service is stateless and scales to 100+ replicas; menu is cached aggressively — DB reads are rare
  • Order service sharded by restaurant_id (consistent hash) to co-locate all orders for a location on the same pod and reduce cross-node coordination
  • Inventory service — one primary DB per region; writes are hot during service (concurrent covers). PgBouncer connection pooling prevents connection exhaustion during 300 TPS peaks

Peak Rush Handling​

During a Friday dinner rush on a 500-seat venue:

  • Orders burst to 50/min for 90 minutes
  • Redis absorbs 95% of menu reads
  • Kafka provides backpressure relief: kitchen routing and analytics consume async — no blocking the order confirm path
  • KDS updates via WebSocket over local LAN; even if cloud connectivity degrades, kitchen operates normally

Step 10: Observability​

Traces (OpenTelemetry):
  [API GW] → [OrderSvc] → [InventorySvc] → [PaymentSvc] → [KitchenSvc]
  Span tags: restaurant_id, order_id, channel, table_id

Metrics (Prometheus → Grafana / Datadog):
  rms.orders.placed_total           (counter, by channel, restaurant)
  rms.orders.confirmation_latency   (histogram p50/p95/p99)
  rms.kitchen.item_prep_time_s      (histogram, by station)
  rms.kitchen.kds_update_latency_ms (histogram — order placed → KDS display)
  rms.inventory.low_stock_alerts    (counter, by restaurant, item)
  rms.payment.capture_success_rate  (gauge)
  rms.pos.offline_queue_depth       (gauge, by device)
  rms.menu.cache_hit_ratio          (gauge)

Alerts:
  CRITICAL: order confirmation latency p99 > 2 s
  CRITICAL: payment failure rate > 1%
  CRITICAL: KDS update latency p99 > 5 s (kitchen blind to new orders)
  WARN: inventory item quantity_on_hand < low_stock_threshold
  WARN: POS device offline > 30 min
  WARN: Kafka consumer lag > 5k messages on kitchen.routing topic

Step 11: Trade-offs​

DecisionChosen ApproachAlternativeRationale
Inventory deductionSynchronous in order confirm pathAsync post-confirmationPrevents oversell; 50 ms overhead acceptable vs. double-selling the last steak
KDS transportWebSocket over LAN for in-restaurantHTTP pollingSub-second kitchen alerts require push; polling at 1 s intervals adds unacceptable latency drift
Offline POSOffline-first SQLite + CRDT syncAlways-online onlyRestaurants cannot have POS go dark during network outage; offline-first is a hard operational requirement
Tenant isolationShared DB + RLSSeparate DB per tenantSeparate DB per 10k tenants is operationally infeasible; RLS gives strong isolation with manageable ops overhead
Menu cachingFull menu blob in RedisPer-item cacheMenu is read 100:1 vs. write; full blob avoids N cache lookups per checkout; invalidation is single-key
AnalyticsClickHouse (OLAP)PostgreSQL analytical queriesPostgreSQL OLAP queries on 50 GB/day event volume would saturate the OLTP primary; ClickHouse is purpose-built
Aggregator integrationNormalisation adapter per aggregatorDirect SDK per platformNormalisation layer decouples order flow from vendor-specific payloads; new aggregators require only a new adapter
