🎓 System Design Basics

Essential concepts every software engineer should understand for building scalable, reliable distributed systems.

🔧 Core Components​

API Gateway vs Load Balancer​

API Gateway​

What is it?
A single entry point for all client requests that handles routing, authentication, rate limiting, and request transformation.

Key Functions:

  • Request routing
  • Authentication & authorization
  • Rate limiting & throttling
  • Request/response transformation
  • API versioning
  • Caching
  • Logging & monitoring

When to Use:

  • Microservices architecture
  • Need centralized authentication
  • API composition required
  • Client-specific responses (mobile vs web)

Example:

Client → API Gateway → [Auth Service, User Service, Order Service]
                    → Cache Layer
                    → Rate Limiter

Load Balancer​

What is it?
Distributes incoming network traffic across multiple servers to ensure no single server bears too much load.

Key Functions:

  • Traffic distribution
  • Health checks
  • SSL termination
  • Session persistence
  • Failover

When to Use:

  • Multiple identical servers
  • High traffic volumes
  • Need redundancy
  • Horizontal scaling

Example:

Client → Load Balancer → [Server1, Server2, Server3, Server4]

Key Difference:

  • API Gateway: Application-level routing, business logic
  • Load Balancer: Network-level distribution, no business logic

Forward Proxy vs Reverse Proxy​

Forward Proxy​

What is it?
Acts on behalf of clients to access resources from servers.

Use Cases:

  • Hide client identity
  • Bypass geo-restrictions
  • Content filtering (corporate networks)
  • Caching for clients

Example:

Client → Forward Proxy → Internet → Server
         (VPN, corporate proxy)

Reverse Proxy​

What is it?
Acts on behalf of servers, intercepting requests before they reach the backend.

Use Cases:

  • Load balancing
  • SSL termination
  • Caching
  • Compression
  • Security (DDoS protection)

Example:

Client → Internet → Reverse Proxy → [Backend Servers]
                    (NGINX, HAProxy)

Key Difference:

  • Forward Proxy: Protects clients, clients know about it
  • Reverse Proxy: Protects servers, clients don't know about it

📊 Scaling Strategies​

Horizontal vs Vertical Scaling​

Vertical Scaling (Scale Up)​

Definition: Add more resources (CPU, RAM, disk) to existing machine

Pros:

  • Simple to implement
  • No code changes needed
  • Maintains data consistency (single machine)
  • Lower maintenance

Cons:

  • Hardware limits (can only scale so far)
  • Single point of failure
  • Downtime during upgrades
  • More expensive at scale

Best For:

  • Legacy applications
  • Databases with complex joins
  • Applications not designed for distribution
  • Early-stage startups

Horizontal Scaling (Scale Out)​

Definition: Add more machines to distribute load

Pros:

  • Nearly unlimited scaling
  • Better fault tolerance
  • Cost-effective (commodity hardware)
  • No downtime during scaling

Cons:

  • Complex implementation
  • Data consistency challenges
  • More operational overhead
  • Network latency between machines

Best For:

  • Web applications
  • Stateless services
  • High-traffic systems
  • Cloud-native applications

Comparison:

Vertical Scaling:     Single Server [CPU ↑, RAM ↑, Disk ↑]
Horizontal Scaling:   [Server1] [Server2] [Server3] [Server4]

🗄️ Database Scaling​

Database Replication​

Master-Slave Replication​

How it works:

  • Master handles all writes
  • Slaves replicate data from master
  • Slaves handle read queries

Pros:

  • Improved read performance
  • Data redundancy
  • Backup capability

Cons:

  • Replication lag
  • Single point of failure (master)
  • Complex failover

Example:

Application
    ↓ (write)
  Master DB
    ↓ (replicate)
[Slave1, Slave2, Slave3] ← (read) Application

Master-Master Replication​

How it works:

  • Multiple masters that can accept writes
  • Bi-directional replication

Pros:

  • No single point of failure
  • Better write performance
  • Geographic distribution

Cons:

  • Conflict resolution needed
  • More complex
  • Consistency challenges

Database Sharding​

What is it?
Horizontally partitioning data across multiple databases.

Sharding Strategies:

  1. Range-Based

    Users A-M → Shard 1
    Users N-Z → Shard 2

  2. Hash-Based

    hash(user_id) % num_shards → Shard N

  3. Geographic

    US users → US Shard
    EU users → EU Shard

Pros:

  • Horizontal scaling
  • Better performance
  • Reduced index size

Cons:

  • Complex queries (joins across shards)
  • Rebalancing difficulty
  • Hotspot issues

Database Partitioning​

Vertical Partitioning​

Definition: Split table columns into separate tables

Example:

User Table:
Before: [id, name, email, bio, settings, preferences]

After:
User_Basic: [id, name, email]
User_Profile: [id, bio, settings, preferences]

When to Use:

  • Large columns (BLOBs, text)
  • Frequently vs rarely accessed data
  • Different security requirements

Horizontal Partitioning (Sharding)​

Definition: Split table rows across multiple tables/databases

Example:

Users Table:
Before: All 10M users in one table

After:
Users_1: Users with id 1-5M
Users_2: Users with id 5M-10M

🚀 Caching Strategies​

9 Caching Strategies​

1. Cache-Aside (Lazy Loading)​

How it works:

  1. Check cache first
  2. If miss, fetch from DB
  3. Update cache
  4. Return data

Pros:

  • Only cache what's needed
  • Resilient to cache failures

Cons:

  • Initial request penalty
  • Stale data possible

Code Example:

def get_user(user_id):
    user = cache.get(f"user:{user_id}")
    if not user:
        user = db.query(f"SELECT * FROM users WHERE id={user_id}")
        cache.set(f"user:{user_id}", user, ttl=3600)
    return user

2. Read-Through​

How it works:

  • Cache sits between app and database
  • Cache handles loading from DB

Pros:

  • Simplified application code
  • Transparent caching

Cons:

  • Initial request slow
  • Cache dependency

3. Write-Through​

How it works:

  • Write to cache and database simultaneously
  • Synchronous operation

Pros:

  • Cache always consistent
  • No stale data

Cons:

  • Higher write latency
  • Unnecessary caching of all writes

4. Write-Behind (Write-Back)​

How it works:

  • Write to cache immediately
  • Asynchronously write to DB

Pros:

  • Fast write operations
  • Batch writes possible

Cons:

  • Risk of data loss
  • Complex implementation

5. Write-Around​

How it works:

  • Write directly to database
  • Cache only on read

Pros:

  • Avoids cache pollution
  • Good for write-heavy

Cons:

  • Cache misses on recent writes
  • Read latency for new data

6. Refresh-Ahead​

How it works:

  • Automatically refresh hot cache entries before expiration

Pros:

  • Reduced latency
  • Predictable performance

Cons:

  • Complex prediction logic
  • Wasted refreshes

7. Cache Invalidation Strategies​

TTL (Time To Live):

cache.set(key, value, ttl=3600)  # Expires in 1 hour

Event-Based:

def update_user(user_id, data):
    db.update(user_id, data)
    cache.delete(f"user:{user_id}")  # Invalidate

Versioning:

cache.set(f"user:{user_id}:v{version}", user)

⚖️ Rate Limiting​

What is Rate Limiting?​

Controlling the rate of requests to prevent abuse and ensure fair usage.

Common Algorithms​

1. Token Bucket​

How it works:

  • Bucket holds tokens
  • Each request consumes a token
  • Tokens refill at fixed rate

Pros:

  • Allows bursts
  • Smooth traffic
  • Simple implementation

Example:

class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity
        self.tokens = capacity
        self.refill_rate = refill_rate  # tokens per second
        self.last_refill = time.time()
    
    def allow_request(self):
        self._refill()
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
    
    def _refill(self):
        now = time.time()
        tokens_to_add = (now - self.last_refill) * self.refill_rate
        self.tokens = min(self.capacity, self.tokens + tokens_to_add)
        self.last_refill = now

2. Leaky Bucket​

How it works:

  • Requests enter bucket
  • Process at constant rate
  • Overflow requests rejected

Pros:

  • Smooth output rate
  • Predictable behavior

Cons:

  • No burst allowance
  • Queue buildup

3. Fixed Window​

How it works:

  • Fixed time windows (e.g., per minute)
  • Count requests in window
  • Reset at window boundary

Pros:

  • Simple to implement
  • Low memory usage

Cons:

  • Burst at window boundaries
  • Unfair distribution

4. Sliding Window Log​

How it works:

  • Track timestamp of each request
  • Count requests in sliding window

Pros:

  • No boundary issues
  • Accurate rate limiting

Cons:

  • Memory intensive
  • Complex implementation

5. Sliding Window Counter​

How it works:

  • Hybrid of fixed window and sliding window
  • Weighted count based on overlap

Pros:

  • Memory efficient
  • Smooth rate limiting

Example:

def sliding_window_counter(user_id, limit, window):
    current_window = int(time.time() / window)
    previous_window = current_window - 1
    
    current_count = redis.get(f"rate:{user_id}:{current_window}") or 0
    previous_count = redis.get(f"rate:{user_id}:{previous_window}") or 0
    
    # Weight previous window by overlap
    overlap = (time.time() % window) / window
    weighted_count = previous_count * (1 - overlap) + current_count
    
    if weighted_count < limit:
        redis.incr(f"rate:{user_id}:{current_window}")
        return True
    return False

🔄 Message Queues​

What is a Message Queue?​

Asynchronous communication pattern where messages are stored in a queue between producers and consumers.

Popular Message Queues​

1. Apache Kafka​

Best For: High-throughput, event streaming

Key Features:

  • Distributed, partitioned
  • High throughput (millions/sec)
  • Data persistence
  • Pub/sub and streaming

Use Cases:

  • Event sourcing
  • Log aggregation
  • Real-time analytics
  • Stream processing

2. RabbitMQ​

Best For: Complex routing, task queues

Key Features:

  • AMQP protocol
  • Flexible routing
  • Multiple exchange types
  • Priority queues

Use Cases:

  • Task queues
  • RPC patterns
  • Microservices communication

3. Amazon SQS​

Best For: Simple queue, managed service

Key Features:

  • Fully managed
  • Scalable
  • Simple API
  • Dead letter queues

Use Cases:

  • Decoupling microservices
  • Batch job processing
  • AWS integration

Message Queue Patterns​

1. Point-to-Point (Queue)​

Producer → Queue → Consumer
  • One message, one consumer
  • Message removed after processing

2. Publish-Subscribe (Topic)​

Producer → Topic → [Consumer1, Consumer2, Consumer3]
  • One message, multiple consumers
  • All subscribers receive message

3. Request-Reply​

Client → Request Queue → Server → Reply Queue → Client
  • Synchronous-like pattern
  • Correlation IDs track requests

🏗️ Microservices vs Monolithic​

Monolithic Architecture​

Definition: Single, unified codebase and deployment unit

Pros:

  • Simple to develop initially
  • Easy to test and debug
  • Single deployment
  • Better performance (in-process calls)

Cons:

  • Difficult to scale
  • Tech stack locked in
  • Long deployment cycles
  • Single point of failure

When to Use:

  • Small teams
  • Simple applications
  • MVP/early stage
  • Tight deadlines

Microservices Architecture​

Definition: Application composed of small, independent services

Pros:

  • Independent scaling
  • Technology flexibility
  • Team autonomy
  • Fault isolation

Cons:

  • Operational complexity
  • Network latency
  • Data consistency challenges
  • Testing complexity

When to Use:

  • Large teams
  • Complex domains
  • Need for scalability
  • Different scaling requirements

Comparison Table​

AspectMonolithicMicroservices
DeploymentSingle unitIndependent services
ScalingScale entire appScale individual services
DevelopmentSimpler initiallyMore complex
Team SizeWorks for small teamsBetter for large teams
TechnologySingle tech stackPolyglot possible
TestingEasier integration testsComplex E2E testing
ReliabilitySingle point of failureFault isolation
PerformanceIn-process callsNetwork overhead

🌐 REST vs gRPC vs GraphQL​

REST (Representational State Transfer)​

Characteristics:

  • HTTP-based
  • JSON/XML payloads
  • Stateless
  • Resource-oriented

Pros:

  • Widely adopted
  • Easy to understand
  • Browser-friendly
  • Cacheable

Cons:

  • Over-fetching/under-fetching
  • Multiple round trips
  • Versioning challenges

Example:

GET /api/users/123
POST /api/users
PUT /api/users/123
DELETE /api/users/123

gRPC​

Characteristics:

  • HTTP/2 based
  • Protocol Buffers
  • Bi-directional streaming
  • Code generation

Pros:

  • High performance
  • Type safety
  • Streaming support
  • Efficient binary format

Cons:

  • Not browser-friendly
  • Steeper learning curve
  • Limited debugging tools

When to Use:

  • Microservices communication
  • High-performance requirements
  • Streaming data

Example:

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
  rpc StreamUsers (stream UserRequest) returns (stream UserResponse);
}

GraphQL​

Characteristics:

  • Query language
  • Single endpoint
  • Client defines response
  • Strongly typed

Pros:

  • No over-fetching
  • Single request
  • Strongly typed
  • Introspection

Cons:

  • Complex caching
  • N+1 query problem
  • Learning curve
  • Server complexity

When to Use:

  • Complex, nested data
  • Multiple clients (mobile, web)
  • Frequent schema changes

Example:

query {
  user(id: "123") {
    name
    email
    posts {
      title
      comments {
        text
      }
    }
  }
}

🔐 Authentication & Authorization​

JWT vs Session-Based Auth​

Session-Based Authentication​

How it works:

  1. User logs in
  2. Server creates session, stores in DB
  3. Client receives session ID cookie
  4. Client sends cookie with each request

Pros:

  • Server-side control
  • Easy revocation
  • Secure (session stored server-side)

Cons:

  • Stateful (scalability issues)
  • Session storage overhead
  • CSRF vulnerability

JWT (JSON Web Token)​

How it works:

  1. User logs in
  2. Server generates signed JWT
  3. Client stores JWT (localStorage/cookie)
  4. Client sends JWT in header

Structure:

header.payload.signature

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJ1c2VySWQiOiIxMjMiLCJleHAiOjE2MzA0NjEyMDB9.
signature_hash_here

Pros:

  • Stateless (scalable)
  • Cross-domain
  • Mobile-friendly

Cons:

  • Difficult to revoke
  • Larger payload
  • XSS vulnerability

OAuth 2.0 vs SAML​

OAuth 2.0​

Purpose: Authorization (delegated access)

Use Cases:

  • "Sign in with Google"
  • Third-party API access
  • Mobile apps

Flow:

User → App → OAuth Provider → Grant Token → App → API

SAML (Security Assertion Markup Language)​

Purpose: Single Sign-On (SSO)

Use Cases:

  • Enterprise SSO
  • Cross-domain authentication

Flow:

User → Service Provider → Identity Provider → SAML Assertion → Service Provider

Single Sign-On (SSO)​

How it works:

  1. User authenticates once with identity provider
  2. Receives security token
  3. Token used for multiple applications

Benefits:

  • One login for multiple apps
  • Centralized user management
  • Better security
  • Improved user experience

📊 CAP Theorem​

The Trade-Off Triangle​

        Consistency
           /\
          /  \
         /    \
        /  CA  \
       /        \
      /  CP  AP  \
     /______________\
Partition        Availability
Tolerance

You can only choose 2 out of 3:

  • Consistency: All nodes see the same data
  • Availability: Every request gets a response
  • Partition Tolerance: System continues despite network failures

Real-World Choices​

CP (Consistency + Partition Tolerance)​

Examples: MongoDB, HBase, Redis

Characteristics:

  • Prioritize data consistency
  • May reject requests during partitions
  • Strong consistency guarantees

Use When:

  • Financial transactions
  • Inventory systems
  • Atomic operations required

AP (Availability + Partition Tolerance)​

Examples: Cassandra, DynamoDB, CouchDB

Characteristics:

  • Always available for reads/writes
  • Eventual consistency
  • Conflict resolution needed

Use When:

  • Social media feeds
  • Shopping carts
  • Analytics/logging
  • High availability critical

CA (Consistency + Availability)​

Examples: Traditional RDBMS (single node)

Note: Not realistic in distributed systems as network partitions will occur

🔍 Consistency Models​

Strong Consistency​

Definition: Reads always return most recent write

Pros:

  • Simple to reason about
  • No stale data

Cons:

  • Higher latency
  • Lower availability
  • Coordination overhead

Example: Traditional databases with ACID transactions

Eventual Consistency​

Definition: Given no new updates, all replicas eventually converge

Pros:

  • High availability
  • Low latency
  • Better performance

Cons:

  • Stale reads possible
  • Conflict resolution needed
  • Complex application logic

Example: DNS, Cassandra, DynamoDB

Causal Consistency​

Definition: Operations that are causally related are seen by all nodes in the same order

Use Case: Social media (see your own posts before others see them)

Read-Your-Writes Consistency​

Definition: Users always see their own updates

Implementation: Route user's reads to same replica that handled writes

🎯 Common Design Patterns​

1. Event Sourcing​

Concept: Store changes (events) instead of current state

Benefits:

  • Complete audit trail
  • Time travel (replay events)
  • Event-driven architecture

Example:

Instead of: user.balance = 100
Store: [
  {event: "AccountCreated", balance: 0},
  {event: "MoneyDeposited", amount: 100}
]

2. CQRS (Command Query Responsibility Segregation)​

Concept: Separate models for reads and writes

Benefits:

  • Optimized read/write models
  • Independent scaling
  • Flexibility

Pattern:

Write Model (Commands) → Event Store → Read Model (Queries)

3. Saga Pattern​

Concept: Distributed transactions using compensating actions

Types:

  • Choreography: Events coordinate services
  • Orchestration: Central coordinator

Example:

Order Service → Payment Service → Inventory Service
    ↓               ↓                   ↓
If fails: Cancel Order ← Refund ← Rollback Inventory

4. Circuit Breaker​

Concept: Prevent cascading failures

States:

  • Closed: Normal operation
  • Open: Fail fast, don't call service
  • Half-Open: Test if service recovered

Benefits:

  • Fault isolation
  • Graceful degradation
  • Faster failure detection

5. Bulkhead Pattern​

Concept: Isolate resources to prevent total failure

Example:

Thread Pool 1: Critical operations
Thread Pool 2: Non-critical operations
Thread Pool 3: Background tasks

📚 Additional Concepts​

Idempotency​

Definition: Operation can be applied multiple times with same result

Importance:

  • Retry safety
  • Network reliability
  • Distributed systems

Example:

Idempotent: PUT /users/123 {name: "John"}
Not Idempotent: POST /users {name: "John"}

Distributed Tracing​

Purpose: Track requests across microservices

Tools: Jaeger, Zipkin, AWS X-Ray

Benefits:

  • Performance debugging
  • Dependency visualization
  • Error tracking

Service Mesh​

Purpose: Infrastructure layer for microservices communication

Features:

  • Traffic management
  • Security (mTLS)
  • Observability
  • Resilience

Examples: Istio, Linkerd, Consul
