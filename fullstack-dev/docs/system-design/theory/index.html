🧠 System Design Theory & Concepts

Advanced theoretical concepts for distributed systems, covering algorithms, consistency models, and architectural patterns frequently discussed in system design interviews.

🏛️ Architecture Patterns​

Microservices vs Monolithic Architecture​

Deep Dive Comparison​

Monolithic Architecture

Definition: Single, tightly-coupled application where all components are part of one codebase and deployment unit.

Characteristics:

  • Single codebase
  • Single deployment pipeline
  • Shared database
  • In-process communication
  • Unified technology stack

Advantages:

  1. Development Simplicity

    • Easier to develop initially
    • Single IDE/project setup
    • Straightforward debugging
    • Simple transaction management

  2. Deployment Simplicity

    • Single deployment artifact
    • No distributed system complexity
    • Easier rollback
    • Simpler versioning

  3. Performance

    • In-process function calls (faster than network)
    • No serialization overhead
    • Easier caching
    • Single database (no distributed queries)

  4. Testing

    • Easier end-to-end testing
    • No mocking of network calls
    • Simpler integration tests

Disadvantages:

  1. Scalability Limitations

    • Must scale entire application
    • Cannot scale components independently
    • Resource waste (over-provisioning)

  2. Technology Lock-In

    • Single technology stack for entire app
    • Difficult to adopt new technologies
    • Legacy tech debt accumulates

  3. Team Constraints

    • Coordination required across teams
    • Merge conflicts increase with team size
    • Difficult to work independently

  4. Deployment Risk

    • Small change requires full redeployment
    • Higher risk per deployment
    • Longer CI/CD pipelines
    • Downtime for entire application

  5. Fault Isolation

    • Single bug can crash entire system
    • Memory leak affects all features
    • No fault isolation

When to Choose Monolithic:

  • Small team (< 10 developers)
  • Simple domain
  • MVP/early stage product
  • Limited resources for DevOps
  • Tight coupling is acceptable

Microservices Architecture

Definition: Application composed of small, independently deployable services organized around business capabilities.

Characteristics:

  • Multiple codebases
  • Independent deployment
  • Decentralized data
  • Network communication
  • Polyglot technology

Advantages:

  1. Independent Scaling

    User Service: 10 instances (high load)
    Order Service: 50 instances (very high load)
    Payment Service: 5 instances (low load)
    • Scale only what needs scaling
    • Cost optimization
    • Resource efficiency

  2. Technology Flexibility

    Auth Service: Java + Spring
    Analytics Service: Python + Django
    Search Service: Node.js + Elasticsearch
    Recommendation Service: Python + ML libraries
    • Choose best tool for each job
    • Easier to adopt new tech
    • Team expertise alignment

  3. Team Autonomy

    • Teams own complete services
    • Independent development cycles
    • Parallel development
    • Reduced coordination overhead

  4. Fault Isolation

    • Service failure contained
    • Graceful degradation
    • Circuit breakers isolate failures
    • Overall system availability higher

  5. Easier Maintenance

    • Smaller codebases
    • Focused domain logic
    • Easier to understand
    • Refactoring less risky

Disadvantages:

  1. Operational Complexity

    • Multiple deployments
    • Service discovery needed
    • Distributed monitoring
    • Complex infrastructure

  2. Network Overhead

    • Inter-service latency
    • Serialization/deserialization
    • Network failures to handle
    • Bandwidth considerations

  3. Data Consistency

    • No distributed transactions
    • Eventual consistency
    • Data duplication
    • Complex queries across services

  4. Testing Complexity

    • Integration testing harder
    • Multiple services to mock
    • End-to-end testing complex
    • Contract testing needed

  5. Development Overhead

    • Service boilerplate
    • Inter-service contracts
    • Versioning complexity
    • More code overall

When to Choose Microservices:

  • Large team (> 20 developers)
  • Complex domain
  • Different scaling requirements
  • Need technology flexibility
  • High availability required

Migration Strategy: Monolith → Microservices​

Strangler Fig Pattern:

  1. Identify bounded contexts
  2. Extract one service at a time
  3. Route traffic through API gateway
  4. Gradually migrate functionality
  5. Retire monolith components

Example:

Phase 1: [Monolith] + [Auth Service]
Phase 2: [Monolith] + [Auth Service] + [Payment Service]
Phase 3: [Monolith] + [Auth, Payment, Order Services]
...
Phase N: [Auth, Payment, Order, User, Inventory Services]

Decision Matrix​

🔄 Distributed Algorithms​

Consistent Hashing​

Problem: Traditional hashing (key % n) fails when nodes are added/removed

Solution: Hash both keys and nodes onto a ring

How it works:

1. Hash nodes and keys to points on circle (0 to 2^32-1)
2. Key stored on first node clockwise from key's position
3. Adding/removing node only affects adjacent keys

Visual:

         Node A
           /\
          /  \
    Key1 /    \ Key2
        /      \
    Node C ---- Node B
       |          |
    Key4        Key3

Benefits:

  • Minimal key redistribution (K/n keys move, where K=total keys, n=nodes)
  • Scalability
  • Load balancing with virtual nodes

Virtual Nodes:

class ConsistentHash:
    def __init__(self, nodes=None, virtual_nodes=150):
        self.virtual_nodes = virtual_nodes
        self.ring = {}
        self.sorted_keys = []
        
        if nodes:
            for node in nodes:
                self.add_node(node)
    
    def add_node(self, node):
        for i in range(self.virtual_nodes):
            virtual_key = f"{node}:{i}"
            hash_key = self._hash(virtual_key)
            self.ring[hash_key] = node
            self.sorted_keys.append(hash_key)
        self.sorted_keys.sort()
    
    def get_node(self, key):
        if not self.ring:
            return None
        hash_key = self._hash(key)
        for node_hash in self.sorted_keys:
            if hash_key <= node_hash:
                return self.ring[node_hash]
        return self.ring[self.sorted_keys[0]]
    
    def _hash(self, key):
        return hash(key) % (2**32)

Real-World Usage:

  • Amazon DynamoDB
  • Apache Cassandra
  • Memcached
  • Content Delivery Networks (CDN)

Gossip Protocol​

Purpose: Disseminate information in distributed systems

How it works:

  1. Each node periodically selects random peer
  2. Exchanges state information
  3. Process repeats across network

Analogy: How rumors spread in social networks

Algorithm:

def gossip_protocol(node):
    while True:
        # Select random peers
        peers = random.sample(cluster.get_peers(), fanout)
        
        # Send state to peers
        for peer in peers:
            peer.send(node.state)
            
            # Receive and merge peer state
            peer_state = peer.receive()
            node.state.merge(peer_state)
        
        sleep(gossip_interval)

Properties:

  • Eventually consistent: All nodes converge to same state
  • Fault-tolerant: Works with node failures
  • Scalable: O(log n) rounds to reach all nodes

Use Cases:

  • Cluster membership (Cassandra)
  • Failure detection
  • Database replication
  • Configuration propagation

Example - Failure Detection:

Node A heartbeat: 100
Node B heartbeat: 98
Node C heartbeat: 50 (suspected failed)

Gossip spreads suspicion:
A → B: "C might be down"
B → D: "C might be down"
Eventually all nodes mark C as down

CRDT (Conflict-Free Replicated Data Types)​

Problem: Concurrent updates in distributed systems cause conflicts

Solution: Data structures that automatically resolve conflicts

Types:

1. G-Counter (Grow-only Counter)​

class GCounter:
    def __init__(self, node_id):
        self.node_id = node_id
        self.counts = {}  # {node_id: count}
    
    def increment(self):
        self.counts[self.node_id] = self.counts.get(self.node_id, 0) + 1
    
    def value(self):
        return sum(self.counts.values())
    
    def merge(self, other):
        for node_id, count in other.counts.items():
            self.counts[node_id] = max(
                self.counts.get(node_id, 0),
                count
            )

2. PN-Counter (Positive-Negative Counter)​

class PNCounter:
    def __init__(self, node_id):
        self.increments = GCounter(node_id)
        self.decrements = GCounter(node_id)
    
    def increment(self):
        self.increments.increment()
    
    def decrement(self):
        self.decrements.increment()
    
    def value(self):
        return self.increments.value() - self.decrements.value()

3. LWW-Element-Set (Last-Write-Wins)​

class LWWSet:
    def __init__(self):
        self.add_set = {}  # {element: timestamp}
        self.remove_set = {}  # {element: timestamp}
    
    def add(self, element):
        self.add_set[element] = time.time()
    
    def remove(self, element):
        self.remove_set[element] = time.time()
    
    def contains(self, element):
        add_time = self.add_set.get(element, 0)
        remove_time = self.remove_set.get(element, 0)
        return add_time > remove_time

Real-World Usage:

  • Riak database
  • Redis CRDTs
  • Collaborative editing (Google Docs)
  • Distributed caches

Vector Clocks​

Purpose: Track causality in distributed systems

Problem: Determine if events are concurrent or causally related

How it works:

  • Each node maintains vector of logical timestamps
  • Vector updated on each event
  • Vectors compared to determine causality

Example:

Node A: [1, 0, 0]  →  [2, 0, 0]  →  [3, 1, 0]
Node B: [0, 1, 0]  →  [1, 2, 0]  →  [1, 3, 0]
Node C: [0, 0, 1]  →  [0, 0, 2]  →  [1, 0, 3]

Comparison Rules:

def compare_vectors(v1, v2):
    if all(v1[i] <= v2[i] for i in range(len(v1))):
        if any(v1[i] < v2[i] for i in range(len(v1))):
            return "BEFORE"  # v1 happened before v2
        return "EQUAL"
    elif all(v2[i] <= v1[i] for i in range(len(v1))):
        return "AFTER"  # v1 happened after v2
    else:
        return "CONCURRENT"  # v1 and v2 are concurrent

Implementation:

class VectorClock:
    def __init__(self, node_id, num_nodes):
        self.node_id = node_id
        self.vector = [0] * num_nodes
    
    def increment(self):
        self.vector[self.node_id] += 1
    
    def update(self, other_vector):
        for i in range(len(self.vector)):
            self.vector[i] = max(self.vector[i], other_vector[i])
        self.increment()
    
    def is_concurrent(self, other):
        return (not self.happens_before(other) and 
                not other.happens_before(self))
    
    def happens_before(self, other):
        return (all(self.vector[i] <= other.vector[i] 
                   for i in range(len(self.vector))) and
                any(self.vector[i] < other.vector[i] 
                   for i in range(len(self.vector))))

Use Cases:

  • Conflict detection (Dynamo)
  • Causality tracking
  • Distributed debugging

Merkle Trees​

Purpose: Efficiently verify data integrity and identify differences

Structure: Hash tree where each leaf is hash of data block

Example:

         Root Hash
           /  \
          /    \
      Hash01  Hash23
       / \      / \
      /   \    /   \
   H(B0) H(B1) H(B2) H(B3)
     |     |     |     |
   Block0 Block1 Block2 Block3

Benefits:

  • Efficient verification: O(log n) comparisons
  • Partial sync: Only exchange different subtrees
  • Tamper detection: Any change affects root hash

Algorithm:

import hashlib

class MerkleTree:
    def __init__(self, data_blocks):
        self.leaves = [self._hash(block) for block in data_blocks]
        self.root = self._build_tree(self.leaves)
    
    def _hash(self, data):
        return hashlib.sha256(data.encode()).hexdigest()
    
    def _build_tree(self, nodes):
        if len(nodes) == 1:
            return nodes[0]
        
        next_level = []
        for i in range(0, len(nodes), 2):
            left = nodes[i]
            right = nodes[i+1] if i+1 < len(nodes) else left
            parent = self._hash(left + right)
            next_level.append(parent)
        
        return self._build_tree(next_level)
    
    def verify(self, index, data, proof):
        """Verify data at index using Merkle proof"""
        current_hash = self._hash(data)
        
        for sibling_hash, is_left in proof:
            if is_left:
                current_hash = self._hash(sibling_hash + current_hash)
            else:
                current_hash = self._hash(current_hash + sibling_hash)
        
        return current_hash == self.root

Real-World Usage:

  • Git (commit history)
  • Bitcoin/blockchain
  • Apache Cassandra (anti-entropy)
  • IPFS (content addressing)
  • Amazon DynamoDB (replica sync)

Bloom Filters​

Purpose: Space-efficient probabilistic data structure for membership testing

Properties:

  • False positives: Possible ("maybe in set")
  • False negatives: Not possible ("definitely not in set")
  • Space efficient: Much smaller than storing all elements

How it works:

  1. Initialize bit array of size m
  2. Use k hash functions
  3. Add: Set k bits to 1
  4. Query: Check if all k bits are 1

Example:

Bit array: [0, 0, 0, 0, 0, 0, 0, 0]

Add "apple":
  hash1("apple") = 2 → [0, 0, 1, 0, 0, 0, 0, 0]
  hash2("apple") = 5 → [0, 0, 1, 0, 0, 1, 0, 0]
  hash3("apple") = 7 → [0, 0, 1, 0, 0, 1, 0, 1]

Add "banana":
  hash1("banana") = 1 → [0, 1, 1, 0, 0, 1, 0, 1]
  hash2("banana") = 5 → [0, 1, 1, 0, 0, 1, 0, 1] (already 1)
  hash3("banana") = 6 → [0, 1, 1, 0, 0, 1, 1, 1]

Query "apple": Check bits 2, 5, 7 → All 1 → "Maybe in set"
Query "orange": Check bits 0, 3, 4 → Not all 1 → "Definitely not"

Implementation:

import hashlib

class BloomFilter:
    def __init__(self, size, num_hashes):
        self.size = size
        self.num_hashes = num_hashes
        self.bit_array = [0] * size
    
    def _hash(self, item, seed):
        h = hashlib.md5((str(item) + str(seed)).encode())
        return int(h.hexdigest(), 16) % self.size
    
    def add(self, item):
        for i in range(self.num_hashes):
            index = self._hash(item, i)
            self.bit_array[index] = 1
    
    def contains(self, item):
        for i in range(self.num_hashes):
            index = self._hash(item, i)
            if self.bit_array[index] == 0:
                return False  # Definitely not in set
        return True  # Probably in set

False Positive Rate:

P(false positive) ≈ (1 - e^(-kn/m))^k

Where:
k = number of hash functions
n = number of elements
m = bit array size

Use Cases:

  • Database query optimization (check if key exists before disk read)
  • Web crawlers (avoid re-crawling URLs)
  • Cache filtering (CDN, Akamai)
  • Spam filtering
  • Bitcoin wallets (check transaction relevance)

Example - Database Optimization:

Query: SELECT * FROM users WHERE email = 'user@example.com'

Without Bloom Filter:
1. Always read from disk (slow)

With Bloom Filter:
1. Check Bloom filter (fast, in memory)
2. If "definitely not" → return empty result
3. If "maybe" → read from disk

🔐 Consensus Algorithms​

Raft Consensus​

Purpose: Achieve consensus in distributed systems (leader election, log replication)

Key Concepts:

1. Roles:

  • Leader: Handles all client requests, replicates log
  • Follower: Passive, redirects to leader
  • Candidate: Tries to become leader during election

2. Terms:

  • Logical clock
  • Each term has at most one leader
  • Used to detect stale information

3. Leader Election:

1. Follower times out → becomes Candidate
2. Candidate increments term, votes for self
3. Sends RequestVote to all nodes
4. If receives majority votes → becomes Leader
5. If another leader found → becomes Follower
6. If election timeout → start new election

4. Log Replication:

1. Client sends command to Leader
2. Leader appends to local log
3. Leader sends AppendEntries to Followers
4. Followers append to their logs
5. Once majority replicate → Leader commits
6. Leader notifies Followers to commit
7. State machine applies committed entries

Safety Properties:

  • Election Safety: At most one leader per term
  • Leader Append-Only: Leader never overwrites log
  • Log Matching: If two logs contain same entry at same index, they're identical up to that point
  • Leader Completeness: If entry committed in term, it's in all future leaders' logs
  • State Machine Safety: If server applies log entry, no other server applies different entry at that index

Example:

Term 1: [Server1: Leader, Server2: Follower, Server3: Follower]
Client → Server1: SET x=5
Server1 log: [1: SET x=5]
Server2 log: [1: SET x=5] (replicated)
Server3 log: [1: SET x=5] (replicated)
Server1: Commits entry 1, applies SET x=5

If Server1 fails:
Term 2: Server2 or Server3 becomes Leader (has complete log)

Paxos Consensus​

Purpose: Achieve consensus even with failures

Roles:

  • Proposers: Propose values
  • Acceptors: Accept proposals
  • Learners: Learn chosen value

Phases:

Phase 1: Prepare

Proposer:
1. Select proposal number n
2. Send PREPARE(n) to majority of Acceptors

Acceptor:
1. If n > highest seen proposal number:
   - Promise not to accept proposals < n
   - Reply with highest accepted proposal (if any)
2. Else: reject

Phase 2: Accept

Proposer:
1. If receives majority promises:
   - Select value (highest accepted or own)
   - Send ACCEPT(n, value) to Acceptors

Acceptor:
1. If n >= promised proposal:
   - Accept proposal
   - Notify Learners

Example:

Proposer A: PREPARE(n=1)
Acceptors: All promise
Proposer A: ACCEPT(n=1, value=X)
Acceptors: All accept value X

Proposer B (concurrent): PREPARE(n=2)
Acceptors: Promise (reject A's accepts if n=1)
Proposer B: Must propose value X (already accepted)

Why Paxos is Hard:

  • Complex to understand
  • Difficult to implement correctly
  • Multiple edge cases

Raft vs Paxos:

  • Raft: Easier to understand, leader-based
  • Paxos: More flexible, no explicit leader
  • Both: Achieve same guarantees

🏗️ Advanced Design Patterns​

CQRS (Command Query Responsibility Segregation)​

Core Concept: Separate read and write operations into different models

Traditional Architecture:

Client → API → Business Logic → Database
                                    ↓
                                  (same model for read/write)

CQRS Architecture:

Commands (Write):
Client → API → Command Handler → Write Model → Write DB
                                      ↓
                                   Events
                                      ↓
Read Model (Read):
Projection ← Events → Read DB ← Query Handler ← API ← Client

Benefits:

  1. Independent Scaling

    Write Side: 5 instances (low write volume)
    Read Side: 50 instances (high read volume)

  2. Optimized Models

    • Write: Normalized, transactional
    • Read: Denormalized, fast queries

  3. Performance

    • Reads don't block writes
    • Read-specific optimizations
    • Multiple read models for different views

Example - E-commerce:

Write Model:

class CreateOrderCommand:
    user_id: str
    items: List[Item]
    total: Decimal

class OrderCommandHandler:
    def handle(self, command: CreateOrderCommand):
        # Validate
        if not self.inventory.check(command.items):
            raise InsufficientInventory()
        
        # Create order
        order = Order(
            id=uuid.uuid4(),
            user_id=command.user_id,
            items=command.items,
            status='PENDING'
        )
        
        # Save to write database
        self.order_repository.save(order)
        
        # Publish event
        self.event_bus.publish(OrderCreated(order))

Read Model:

class OrderQueryHandler:
    def get_user_orders(self, user_id: str):
        # Optimized read model (denormalized)
        return self.read_db.query("""
            SELECT 
                o.id, o.total, o.status,
                u.name, u.email,
                array_agg(i.name) as items
            FROM orders_view o
            JOIN users u ON o.user_id = u.id
            LEFT JOIN order_items i ON o.id = i.order_id
            WHERE o.user_id = ?
            GROUP BY o.id
        """, user_id)

Event Handler (Updates Read Model):

class OrderCreatedHandler:
    def handle(self, event: OrderCreated):
        # Update denormalized read model
        self.read_db.execute("""
            INSERT INTO orders_view 
            (id, user_id, total, status, items)
            VALUES (?, ?, ?, ?, ?)
        """, event.order_id, event.user_id, 
             event.total, event.status, event.items)

When to Use CQRS:

  • ✅ Complex domain logic
  • ✅ High read/write ratio imbalance
  • ✅ Different scaling needs
  • ✅ Multiple read representations
  • ❌ Simple CRUD applications
  • ❌ Small scale
  • ❌ Team lacks expertise

Event Sourcing​

Core Concept: Store changes (events) as source of truth, not current state

Traditional:

User: {id: 1, name: "John", balance: 100}

Event Sourcing:

Events:
1. UserCreated {id: 1, name: "John"}
2. AccountOpened {user_id: 1, balance: 0}
3. MoneyDeposited {user_id: 1, amount: 100}

Current state = replay all events

Architecture:

Command → Aggregate → Event → Event Store
                               ↓
                         Event Bus
                               ↓
                    [Projection1, Projection2, Projection3]

Benefits:

  1. Complete Audit Trail

    • Know exactly what happened
    • When it happened
    • Who did it

  2. Time Travel

    def get_balance_at(user_id, timestamp):
        events = event_store.get_events(user_id, until=timestamp)
        return replay_events(events).balance

  3. Event-Driven Architecture

    • Publish events to other services
    • Loose coupling
    • Reactive systems

  4. Debugging

    • Reproduce bugs by replaying events
    • Test with production data

Implementation:

class Event:
    event_id: str
    aggregate_id: str
    event_type: str
    data: dict
    timestamp: datetime
    version: int

class EventStore:
    def append(self, aggregate_id, events):
        # Optimistic concurrency control
        current_version = self.get_version(aggregate_id)
        
        for event in events:
            if event.version != current_version + 1:
                raise ConcurrencyException()
            
            self.db.insert(event)
            current_version += 1
    
    def get_events(self, aggregate_id, from_version=0):
        return self.db.query(
            "SELECT * FROM events WHERE aggregate_id = ? AND version > ?",
            aggregate_id, from_version
        )

class BankAccount:
    def __init__(self, account_id):
        self.id = account_id
        self.balance = 0
        self.version = 0
        self.changes = []
    
    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        
        event = MoneyDeposited(
            account_id=self.id,
            amount=amount,
            version=self.version + 1
        )
        self.apply(event)
        self.changes.append(event)
    
    def apply(self, event):
        if isinstance(event, AccountOpened):
            self.balance = 0
        elif isinstance(event, MoneyDeposited):
            self.balance += event.amount
        elif isinstance(event, MoneyWithdrawn):
            self.balance -= event.amount
        
        self.version = event.version

class BankAccountRepository:
    def get(self, account_id):
        events = self.event_store.get_events(account_id)
        account = BankAccount(account_id)
        
        for event in events:
            account.apply(event)
        
        return account
    
    def save(self, account):
        self.event_store.append(account.id, account.changes)
        account.changes = []

class SnapshotStore:
    def save_snapshot(self, aggregate_id, state, version):
        self.db.insert({
            'aggregate_id': aggregate_id,
            'state': serialize(state),
            'version': version,
            'timestamp': now()
        })
    
    def get_snapshot(self, aggregate_id):
        return self.db.query_latest(aggregate_id)

# Reconstruct with snapshot
snapshot = snapshot_store.get_snapshot(account_id)
account = deserialize(snapshot.state)
events = event_store.get_events(account_id, from_version=snapshot.version)
for event in events:
    account.apply(event)

Challenges:

  1. Event Schema Evolution

    # Version 1
    MoneyDeposited { amount: 100 }

    # Version 2 (need currency)
    MoneyDeposited { amount: 100, currency: "USD" }

    # Solution: Upcasting
    def upcast(event):
        if event.version == 1:
            event.data['currency'] = 'USD'  # default
            event.version = 2
        return event

  2. Query Complexity

    • Need projections/read models
    • Eventual consistency
    • Rebuilding projections time

  3. Storage Growth

    • Events accumulate forever
    • Solution: Snapshots, archiving

When to Use:

  • ✅ Audit requirements
  • ✅ Complex domain logic
  • ✅ Need temporal queries
  • ✅ Event-driven architecture
  • ❌ Simple CRUD
  • ❌ High write volume (millions/sec)
  • ❌ Storage constraints

Saga Pattern​

Purpose: Manage distributed transactions across microservices

Problem: No distributed ACID transactions in microservices

Solution: Sequence of local transactions with compensating actions

Types:

1. Choreography-Based Saga​

How it works: Services communicate through events

Example - E-commerce Order:

Order Service:
  CREATE ORDER → OrderCreated event

Payment Service (listens to OrderCreated):
  CHARGE PAYMENT → PaymentCompleted event

Inventory Service (listens to PaymentCompleted):
  RESERVE ITEMS → ItemsReserved event

Shipping Service (listens to ItemsReserved):
  CREATE SHIPMENT → ShipmentCreated event

If any step fails:
  Publish failure event
  Previous services compensate (refund, unreserve, etc.)

Implementation:

class OrderService:
    def create_order(self, order):
        # Local transaction
        order.status = 'PENDING'
        self.db.save(order)
        
        # Publish event
        self.event_bus.publish(OrderCreated(order))

class PaymentService:
    @event_handler(OrderCreated)
    def handle_order_created(self, event):
        try:
            payment = self.process_payment(event.order)
            self.event_bus.publish(PaymentCompleted(event.order, payment))
        except PaymentFailed as e:
            self.event_bus.publish(PaymentFailed(event.order, e))

class OrderService:
    @event_handler(PaymentFailed)
    def handle_payment_failed(self, event):
        # Compensating action
        order = self.db.get(event.order_id)
        order.status = 'CANCELLED'
        self.db.save(order)

Pros:

  • Decoupled services
  • Simple for simple flows
  • Good event-driven fit

Cons:

  • Hard to understand flow
  • Cyclic dependencies risk
  • Difficult to debug

2. Orchestration-Based Saga​

How it works: Central orchestrator coordinates

Example:

Order Saga Orchestrator:
  1. ORDER SERVICE: Create order
  2. PAYMENT SERVICE: Charge payment
  3. INVENTORY SERVICE: Reserve items
  4. SHIPPING SERVICE: Create shipment
  
If step N fails:
  Compensate steps N-1, N-2, ... 1

Implementation:

class OrderSagaOrchestrator:
    def execute(self, order):
        saga = Saga()
        
        try:
            # Step 1: Create order
            saga.add_step(
                action=lambda: self.order_service.create_order(order),
                compensate=lambda: self.order_service.cancel_order(order.id)
            )
            
            # Step 2: Process payment
            saga.add_step(
                action=lambda: self.payment_service.charge(order),
                compensate=lambda: self.payment_service.refund(order.id)
            )
            
            # Step 3: Reserve inventory
            saga.add_step(
                action=lambda: self.inventory_service.reserve(order.items),
                compensate=lambda: self.inventory_service.release(order.items)
            )
            
            # Step 4: Create shipment
            saga.add_step(
                action=lambda: self.shipping_service.create_shipment(order),
                compensate=lambda: self.shipping_service.cancel_shipment(order.id)
            )
            
            # Execute saga
            saga.execute()
            
        except Exception as e:
            # Compensate in reverse order
            saga.compensate()
            raise OrderFailed(e)

class Saga:
    def __init__(self):
        self.steps = []
        self.completed_steps = []
    
    def add_step(self, action, compensate):
        self.steps.append({'action': action, 'compensate': compensate})
    
    def execute(self):
        for step in self.steps:
            result = step['action']()
            self.completed_steps.append(step)
    
    def compensate(self):
        for step in reversed(self.completed_steps):
            step['compensate']()

Pros:

  • Clear business logic
  • Centralized control
  • Easier testing/debugging
  • Timeout handling

Cons:

  • Orchestrator complexity
  • Single point of coordination
  • Orchestrator must handle all scenarios

Saga Patterns Comparison:

AspectChoreographyOrchestration
CoordinationDistributed (events)Centralized (orchestrator)
ComplexityGrows with servicesIsolated in orchestrator
CouplingLooseModerate
Flow VisibilityScatteredClear
TestingHarderEasier
Best ForSimple flowsComplex flows

Challenges:

  1. Compensating Actions

    • Not always possible (email sent, external API called)
    • May need manual intervention
    • Semantic vs technical compensation

  2. Isolation

    • No ACID isolation
    • Dirty reads possible
    • Semantic locks needed

  3. Idempotency

    • Retry safety critical
    • Each step must be idempotent

Example - Idempotent Payment:

def charge_payment(order_id, amount, idempotency_key):
    # Check if already processed
    existing = db.query(
        "SELECT * FROM payments WHERE idempotency_key = ?",
        idempotency_key
    )
    
    if existing:
        return existing  # Return previous result
    
    # Process payment
    payment = stripe.charge(amount)
    
    # Store with idempotency key
    db.insert({
        'order_id': order_id,
        'amount': amount,
        'idempotency_key': idempotency_key,
        'payment_id': payment.id
    })
    
    return payment

🗂️ Distributed Data Patterns​

Database Per Service​

Concept: Each microservice has its own database

Benefits:

  • Service independence
  • Technology choice freedom
  • Fault isolation
  • Independent scaling

Challenges:

  • Data consistency
  • No joins across services
  • Distributed transactions

Solutions:

  1. API Composition

    GET /orders/123

    1. Order Service: Get order data
    2. User Service: Get user details (order.user_id)
    3. Product Service: Get product details (order.items)
    4. Combine results in API gateway

  2. CQRS with Event Sourcing

    • Services publish domain events
    • Other services build their read models

  3. Saga Pattern

    • Coordinate changes across services

Shared Database Anti-Pattern​

Why it's bad:

[Service A, Service B, Service C] → Shared Database

Problems:

  • Tight coupling
  • Schema changes affect all services
  • Difficult to scale independently
  • Deployment coordination needed
  • Technology lock-in

Migration Strategy:

  1. Identify bounded contexts
  2. Create separate schemas per service
  3. Add service APIs
  4. Migrate services one by one
  5. Remove cross-database queries

Data Replication Patterns​

1. Change Data Capture (CDC)​

How it works: Capture database changes and publish as events

Example:

MySQL → Debezium CDC → Kafka → [Service1, Service2, Service3]

Benefits:

  • Real-time sync
  • No application changes
  • Reliable event sourcing

Tools: Debezium, Maxwell, Oracle GoldenGate

2. Transactional Outbox​

Pattern: Store events in database, publish reliably

How it works:

BEGIN TRANSACTION;
  INSERT INTO orders (id, user_id, total) VALUES (1, 123, 100);
  INSERT INTO outbox_events (id, event_type, payload) 
    VALUES (uuid(), 'OrderCreated', '{"order_id": 1, ...}');
COMMIT;

-- Separate process
SELECT * FROM outbox_events WHERE published = false;
-- Publish to message queue
-- Mark as published

Benefits:

  • Guaranteed event publishing
  • No dual write problem
  • Transactional consistency

Implementation:

class OrderService:
    def create_order(self, order):
        with self.db.transaction():
            # Business logic
            self.db.insert_order(order)
            
            # Store event in same transaction
            event = OrderCreated(order)
            self.db.insert_outbox_event(event)

# Separate process
class OutboxPublisher:
    def run(self):
        while True:
            events = self.db.query(
                "SELECT * FROM outbox WHERE published = false LIMIT 100"
            )
            
            for event in events:
                self.message_queue.publish(event)
                self.db.mark_published(event.id)
            
            time.sleep(1)
