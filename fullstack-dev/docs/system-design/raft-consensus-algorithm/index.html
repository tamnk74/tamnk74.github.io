The Raft Consensus Algorithm

Overview​

Raft is a consensus algorithm designed to be easy to understand and implement. It's equivalent to Paxos in fault-tolerance and performance but is decomposed into relatively independent subproblems, making it more accessible for practical systems development.

What is Consensus?​

Consensus is a fundamental problem in fault-tolerant distributed systems where multiple servers need to agree on values. Key characteristics:

  • Fault Tolerance: The system continues to operate even when some servers fail
  • Majority Rule: A cluster can continue operating as long as a majority of servers are available
  • Consistency: Once a decision is made on a value, that decision is final
  • Safety: The system never returns incorrect results, even during failures

Consensus in Practice​

Consensus typically arises in the context of replicated state machines:

  1. State Machine: The component we want to make fault-tolerant (e.g., a hash table)
  2. Log: Contains commands that modify the state machine
  3. Consensus Algorithm: Ensures all servers agree on the commands in their logs

Raft Algorithm Components​

Raft decomposes the consensus problem into three relatively independent subproblems:

1. Leader Election​

  • Purpose: Select a single server to manage the replicated log
  • Process:
    • Servers start as followers
    • If no leader communication is received, a follower becomes a candidate
    • Candidates request votes from other servers
    • The candidate with majority votes becomes the leader

2. Log Replication​

  • Purpose: Leader accepts log entries from clients and replicates them across the cluster
  • Process:
    • Leader receives commands from clients
    • Leader appends entries to its log
    • Leader sends entries to followers
    • Leader commits entries once majority of servers have stored them

3. Safety​

  • Purpose: Ensure that if any state machine applies a command as the nth entry, no other state machine will apply a different nth command
  • Guarantees:
    • Election Safety: At most one leader per term
    • Leader Append-Only: Leaders never overwrite or delete entries
    • Log Matching: If two logs contain an entry with same index and term, they're identical up to that index
    • Leader Completeness: If an entry is committed in a given term, it will be present in leaders of higher terms
    • State Machine Safety: If a server applies an entry at a given index, no other server will apply a different entry at that index

Raft States​

Each server in a Raft cluster can be in one of three states:

Follower​

  • Default state for all servers
  • Passive: Only responds to requests from leaders and candidates
  • Timeout: If no communication from leader, transitions to candidate

Candidate​

  • Intermediate state during leader election
  • Active: Requests votes from other servers
  • Transitions: Becomes leader (majority votes) or reverts to follower

Leader​

  • Active state: Handles all client requests
  • Responsibilities:
    • Accept client commands
    • Replicate log entries
    • Decide when entries are committed
  • Heartbeats: Sends periodic heartbeats to maintain authority

Terms​

Raft divides time into terms of arbitrary length:

  • Sequential numbering: Terms are numbered with consecutive integers
  • Leader per term: Each term begins with an election; at most one leader per term
  • Term detection: Servers exchange current term numbers in communications
  • Term updates: If a server's term is stale, it updates to the newer term

Log Structure​

The Raft log consists of entries containing:

  • Index: Position in the log (sequential)
  • Term: Term number when the entry was created by the leader
  • Command: State machine command

Log Properties​

  1. Monotonic: Logs only grow (never shrink or change existing entries)
  2. Ordered: Entries are applied to state machine in log order
  3. Durable: Once committed, entries are never lost

Leader Election Process​

Election Timeout​

  • Followers wait for heartbeats from the leader
  • If timeout expires without communication, follower becomes candidate

Campaign Phase​

  1. Increment current term
  2. Vote for self
  3. Reset election timer
  4. Send RequestVote RPCs to all other servers

Voting Rules​

  • Each server votes for at most one candidate per term
  • Candidate must have log at least as up-to-date as voter's log
  • First-come, first-served within a term

Election Outcomes​

  • Win: Candidate receives majority votes, becomes leader
  • Lose: Another candidate wins and sends heartbeat
  • Tie: No candidate gets majority, new election begins

Log Replication Process​

Client Request Handling​

  1. Client sends command to leader
  2. Leader appends entry to local log
  3. Leader sends AppendEntries RPCs to followers
  4. Leader waits for majority to store entry
  5. Leader commits entry and applies to state machine
  6. Leader returns result to client
  7. Leader notifies followers of commitment in subsequent RPCs

AppendEntries RPC​

Contains:

  • Previous log index/term: For consistency checking
  • Entries to store: May be empty (heartbeat)
  • Leader commit index: Tells followers what entries are committed

Consistency Check​

  • Follower checks if its log matches leader's log at the previous index
  • If mismatch found, follower rejects the request
  • Leader decrements next index and retries
  • Eventually finds point where logs match

Safety Guarantees​

Election Restriction​

  • Candidate can only win election if its log contains all committed entries
  • Voting server denies vote if candidate's log is not at least as up-to-date

Commitment Rules​

  • Entry is committed when stored on majority of servers
  • All preceding entries are also committed (implicit commitment)
  • Leader never commits entries from previous terms directly

Log Matching Property​

  • If two entries in different logs have same index and term:
    • They store the same command
    • The logs are identical in all preceding entries

Cluster Membership Changes​

Raft supports dynamic configuration changes while maintaining safety:

Two-Phase Approach​

  1. Joint Consensus: Old and new configurations overlap
  2. New Configuration: Transition to new configuration only

Safety During Transitions​

  • No point where both old and new majorities can make independent decisions
  • Configuration changes are logged and replicated like normal entries

Practical Considerations​

Performance Optimizations​

  • Batching: Send multiple entries in single AppendEntries RPC
  • Pipelining: Send AppendEntries before previous ones are acknowledged
  • Async Application: Apply committed entries to state machine asynchronously

Timing Requirements​

  • Election Timeout: 150-300ms typical
  • Heartbeat Interval: 50ms typical (much less than election timeout)
  • RPC Timeout: Configurable based on network characteristics

Failure Scenarios​

  • Network Partitions: Minority partition cannot commit new entries
  • Server Crashes: Restarted servers catch up via log replication
  • Disk Failures: May require operator intervention for data recovery

Implementation Guidelines​

Core Components​

  1. Persistent State (stable storage):

    • Current term
    • Voted for candidate in current term
    • Log entries

  2. Volatile State (all servers):

    • Commit index
    • Last applied index

  3. Volatile State (leaders only):

    • Next index for each follower
    • Match index for each follower

RPC Definitions​

RequestVote RPC​

Arguments:
- term: candidate's term
- candidateId: candidate requesting vote
- lastLogIndex: index of candidate's last log entry
- lastLogTerm: term of candidate's last log entry

Results:
- term: current term for candidate to update itself
- voteGranted: true if candidate received vote

AppendEntries RPC​

Arguments:
- term: leader's term
- leaderId: for followers to redirect clients
- prevLogIndex: index of log entry immediately preceding new ones
- prevLogTerm: term of prevLogIndex entry
- entries[]: log entries to store (empty for heartbeat)
- leaderCommit: leader's commit index

Results:
- term: current term for leader to update itself
- success: true if follower contained entry matching prevLogIndex and prevLogTerm

Use Cases and Applications​

Distributed Databases​

  • Consensus on transaction commits
  • Leader election for primary replicas
  • Configuration management

Distributed Storage Systems​

  • Metadata consensus
  • Replication coordination
  • Cluster membership management

Microservices Architecture​

  • Service discovery consensus
  • Configuration distribution
  • Leader election for singleton services

Raft vs Other Consensus Algorithms​

Raft vs Paxos​

  • Understandability: Raft is designed to be easier to understand
  • Decomposition: Raft separates leader election, log replication, and safety
  • Strong Leadership: Raft uses a stronger form of leadership than Paxos

Raft vs PBFT​

  • Fault Model: Raft assumes crash failures, PBFT handles Byzantine failures
  • Performance: Raft generally performs better in crash-failure scenarios
  • Complexity: Raft is simpler to implement and understand

Tools and Visualizations​

Learning Resources​

  • The Secret Lives of Data: Guided visualization of Raft
  • Raft Paper: "In Search of an Understandable Consensus Algorithm"

Implementation Libraries​

Popular Raft implementations across different languages:

  • Go: HashiCorp Raft, etcd/raft
  • Rust: TiKV, async-raft
  • Java: Apache Ratis, SOFAJRaft
  • C++: LogCabin, braft
  • Python: PySyncObj, raftos

Best Practices​

Configuration​

  • Odd number of servers: Ensures clear majorities (3, 5, 7 nodes)
  • Geographic distribution: Spread across availability zones/regions
  • Resource allocation: Ensure adequate CPU, memory, and storage

Monitoring​

  • Term changes: Monitor for frequent leader elections
  • Commit latency: Track time from client request to commitment
  • Log growth: Monitor log size and compaction needs

Operations​

  • Rolling upgrades: Upgrade followers first, then leader
  • Backup strategies: Backup committed log entries and state machine snapshots
  • Capacity planning: Plan for peak load and failure scenarios

References​

  • Raft Paper - "In Search of an Understandable Consensus Algorithm"
  • Raft Website - Official Raft resources and implementations
  • Diego Ongaro's Dissertation - Extended Raft details
  • Raft Visualization - Interactive Raft cluster simulation

Conclusion​

The Raft consensus algorithm provides a practical, understandable solution for achieving consensus in distributed systems. Its clear separation of concerns and strong leadership model make it an excellent choice for building fault-tolerant distributed applications. The algorithm's emphasis on understandability has led to widespread adoption and numerous high-quality implementations across different programming languages and platforms.
