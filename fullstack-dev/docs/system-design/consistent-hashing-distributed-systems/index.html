Consistent Hashing in Distributed Systems

Consistent hashing is a fundamental technique for distributing data and load across multiple servers in a way that minimizes reorganization when servers are added or removed. This guide covers the architecture, implementation patterns, and production considerations.

Problem: Traditional Hashing Limitations​

The Basic Hash Problem​

Traditional modulo hashing assigns keys to N servers:

server_index = hash(key) % N

Problem: When the number of servers changes (N changes), almost all keys must be reassigned:

  • Adding 1 server: 99% of keys must move (with 100 servers → 101 servers)
  • Removing 1 server: 99% of keys must move
  • Impact: Massive cache invalidation, database storms, service disruption

Real-World Impact​

ScenarioTraditional HashingImpact
Rolling deployment (add/remove servers)~99% of cache keys invalidatedCache miss rate spikes to 100%
Auto-scaling eventMass key redistributionDatabase gets hammered with queries
Server failure + recoveryThundering herdCascading failures

Solution: Consistent Hashing​

Core Concept​

Instead of mapping keys to servers directly, consistent hashing maps both keys and servers to positions on a hash ring (a circular space).

hash(key) → position on ring (0 to 2^32 - 1)
hash(server_id) → position on ring

A key is assigned to the first server encountered moving clockwise around the ring.

Key Property: Minimal Redistribution​

When a server is added:

  • Only keys in the new server's "zone" are affected (~1/N of all keys)
  • Other servers' keys remain unchanged

When a server is removed:

  • Only keys from that server are remapped (~1/N of all keys)
  • Migration scoped, predictable

Architecture & Design​

Hash Ring Visualization​

Algorithm: Basic Consistent Hashing​

class ConsistentHashing:
    def __init__(self):
        self.ring = {}  # position -> server_id
        self.sorted_positions = []
    
    def add_server(self, server_id):
        """Add a server to the hash ring"""
        position = hash(server_id) % (2**32)
        self.ring[position] = server_id
        self.sorted_positions = sorted(self.ring.keys())
        return position
    
    def remove_server(self, server_id):
        """Remove a server from the hash ring"""
        position = hash(server_id) % (2**32)
        del self.ring[position]
        self.sorted_positions = sorted(self.ring.keys())
    
    def get_server(self, key):
        """Find the server responsible for a key"""
        if not self.ring:
            return None
        
        key_position = hash(key) % (2**32)
        
        # Binary search for the first server position >= key_position
        for position in self.sorted_positions:
            if position >= key_position:
                return self.ring[position]
        
        # Wrap around: first server on the ring
        return self.ring[self.sorted_positions[0]]

Virtual Nodes: Handling Unequal Load Distribution​

Problem: Single Position Per Server​

With only one position per server, load distribution can be highly skewed:

Server A hash=50    (zone: 50 to 150)    → 100 units
Server B hash=150   (zone: 150 to 300)   → 150 units  ❌ 50% more load
Server C hash=300   (zone: 300 to 50)    → 150 units  ❌ 50% more load

Solution: Virtual Nodes​

Instead of one hash position per physical server, create K virtual nodes per server:

Server A:
  - vnode A-1: hash=50
  - vnode A-2: hash=85
  - vnode A-3: hash=120
  (total: 3 positions on ring)

Server B:
  - vnode B-1: hash=150
  - vnode B-2: hash=200
  - vnode B-3: hash=250

Server C:
  - vnode C-1: hash=300
  - vnode C-2: hash=330
  - vnode C-3: hash=360

Benefits:

  • Load distributed evenly across all servers
  • Smooth degradation when a server fails (capacity spread across remaining servers, not concentrated)
  • Standard: 100-500 virtual nodes per physical server
class ConsistentHashingWithVNodes:
    def __init__(self, virtual_nodes=150):
        self.virtual_nodes = virtual_nodes
        self.ring = {}  # position -> server_id (physical)
        self.sorted_positions = []
    
    def add_server(self, server_id):
        """Add a server with multiple virtual nodes"""
        for i in range(self.virtual_nodes):
            vnode_key = f"{server_id}:{i}"
            position = hash(vnode_key) % (2**32)
            self.ring[position] = server_id
        self.sorted_positions = sorted(self.ring.keys())
    
    def remove_server(self, server_id):
        """Remove all virtual nodes for a server"""
        positions_to_remove = [
            pos for pos, srv in self.ring.items() 
            if srv == server_id
        ]
        for pos in positions_to_remove:
            del self.ring[pos]
        self.sorted_positions = sorted(self.ring.keys())
    
    def get_server(self, key):
        """Find responsible server for a key"""
        if not self.ring:
            return None
        
        key_position = hash(key) % (2**32)
        
        for position in self.sorted_positions:
            if position >= key_position:
                return self.ring[position]
        
        return self.ring[self.sorted_positions[0]]

Real-World Applications​

1. Distributed Cache (Redis Cluster, Memcached)​

Client Request for key="user:123"
         ↓
hash("user:123") → position=45000
         ↓
Find first server >= 45000 on ring
         ↓
Server C (position=60000)
         ↓
Return cached value or miss

Benefit: Consistent routing across requests; when servers added/removed, only a fraction of cache keys need to migrate.

2. Distributed Database Sharding​

Write to key="order:5678"
         ↓
hash("order:5678") → shard assignment
         ↓
Always routes to Shard 2 (even if Shard 1 added later)
         ↓
Data stays in same shard

Benefit: Eliminate expensive resharding migrations; support horizontal scaling.

3. Load Balancing & Service Discovery​

New request arrives
         ↓
hash(request_id) → position on ring
         ↓
First service instance clockwise
         ↓
Route to that instance

Benefit: Sticky session routing; requests from same client go to same server without explicit state.

4. CDN & Content Distribution​

Request for content ID="video:4k:abc"
         ↓
hash → edge server on ring
         ↓
Always serves from same cache location
         ↓
Maximize cache hits across geographic regions

Key Properties & Guarantees​

Load Balance Property​

With K virtual nodes per server and uniform hash function:

  • Each server receives ~1/N of all keys
  • Standard deviation: O(1/√(NK))
  • With 150 virtual nodes: <5% variance in practice

Replication Strategy​

Consistent hashing supports N-way replication by taking the next N servers clockwise:

Key k assigned to: [Server A, Server B, Server C]
             ↓
First replica:  Server A (primary)
Second replica: Server B (backup)
Third replica:  Server C (backup)

Fault tolerance: Survive up to N-1 server failures.

Data Migration on Topology Change​

Adding Server D between A and B:

  • Keys previously assigned to B → some now go to D
  • Migration amount: only keys in zone [D, B)
  • Formula: ~(1/N) × total_keys

Removing Server A:

  • Keys from A → assigned to next server (B)
  • All other key assignments unchanged

Implementation Patterns in Production​

Pattern 1: Memcached + Consistent Hashing​

from consistent_hashing import ConsistentHashRing

ring = ConsistentHashRing(
    servers=['mc1.prod', 'mc2.prod', 'mc3.prod'],
    virtual_nodes=150
)

# Get cache
server = ring.get_server('user:42:profile')
client = memcached.connect(server)
value = client.get('user:42:profile')

# Add new cache server
ring.add_server('mc4.prod')  # Automatic rebalancing

Pattern 2: Redis Cluster (Built-in)​

Redis Cluster uses consistent hashing (hash slots) internally:

redis-cli -h cluster-node1 SET mykey myvalue
  ↓
hash_slot = CRC16(mykey) % 16384
  ↓
Find node responsible for slot
  ↓
Write to node

Pattern 3: Database Sharding​

class ShardRouter:
    def __init__(self, shard_connections):
        self.ring = ConsistentHashRing(
            servers=list(shard_connections.keys()),
            virtual_nodes=200
        )
        self.connections = shard_connections
    
    def route_write(self, shard_key, data):
        server = self.ring.get_server(shard_key)
        db = self.connections[server]
        db.insert(data)
    
    def route_read(self, shard_key):
        server = self.ring.get_server(shard_key)
        db = self.connections[server]
        return db.query_by_key(shard_key)

Trade-Offs & Limitations​

Advantages​

AdvantageImpact
Minimal key redistribution on topology change~1/N keys move (vs ~N/(N+1) with modulo hashing)
Predictable load distributionEach server handles ~1/N of traffic
Supports replicationN-way redundancy without dual-hashing
Incremental scalingAdd servers without offline reshuffling

Disadvantages​

LimitationMitigation
Uneven distribution with few serversUse virtual nodes (150+)
Extra memory for ring data structureTypically <10KB (acceptable)
Cache miss spike during rebalancingCan reduce via gradual migration or read-through caching
Not optimal for heterogeneous serversUse weighted virtual nodes (more vnodes to faster servers)

When NOT to Use Consistent Hashing​

  • Very small dataset: Traditional sharding is simpler
  • Strongly consistent requirements: Need atomic distributed transactions (use consensus instead)
  • Single server: Unnecessary overhead

Advanced Topics​

Weighted Virtual Nodes​

For servers with different capacity, allocate virtual nodes proportionally:

class WeightedConsistentHashing:
    def __init__(self, server_weights):
        self.ring = {}
        self.servers = server_weights  # {'server_a': 1.0, 'server_b': 2.0}
        
        for server, weight in server_weights.items():
            vnodes = int(150 * weight)  # 150 vnodes per unit weight
            for i in range(vnodes):
                pos = hash(f"{server}:{i}")
                self.ring[pos] = server

Rendezvous Hashing (Alternative)​

An alternative approach that avoids the ring data structure:

def rendezvous_hash(key, servers):
    """Find best server for key using max hash"""
    max_hash = -1
    best_server = None
    
    for server in servers:
        h = hash(f"{key}:{server}")
        if h > max_hash:
            max_hash = h
            best_server = server
    
    return best_server

Pros: No ring maintenance, simpler lookup Cons: O(N) lookup time per key (where N = number of servers)

Failure Scenarios & Recovery​

Scenario 1: Server Failure​

Server B fails
    ↓
Keys that were on B → reassigned to next server (C)
    ↓
Backfill from replica or cold data source
    ↓
No impact on keys assigned to A or C

Recovery time: O(keys_on_failed_server), not O(total_keys)

Scenario 2: Adding Servers During High Load​

High traffic + add new servers
    ↓
Some keys start routing to new server (already loaded)
    ↓
New server receives spike of simultaneous misses
    ↓
Mitigate: Gradual warmup, prefetching, or shadow traffic

Scenario 3: Hash Function Collision​

If hash function has poor distribution:

hash("key1") = 100
hash("key2") = 100  ← collision
    ↓
Both assigned to same server → load skew

Mitigation: Use cryptographic hashes (SHA-256, MD5); pre-test on production data.

Performance Characteristics​

Time Complexity​

OperationComplexityNotes
Add/remove serverO(V log V)V = total virtual nodes (~150N)
Get server for keyO(log V)Binary search on ring positions
Rebalance after addO(1/N × keys)Only fraction of keys move

Space Complexity​

  • Ring storage: O(V) = O(150N) for N servers
  • Typical: ~1000-500K positions for production clusters
  • Memory: Usually <10-100 MB even for large deployments

Network Impact​

During rebalancing:

SizeKeys to MigrateData Transfer
100 servers, 1B keys~10M keys (1%)Depends on value size
10 GB cache~100 MB transferSub-second with 1Gbps NIC

Production Deployment Checklist​

  • Use 150+ virtual nodes per server
  • Test hash function distribution on actual key patterns
  • Implement monitoring for load skew (variance in keys per server)
  • Plan rebalancing during low-traffic windows
  • Implement gradual migration (don't move all keys at once)
  • Use N-way replication (typically N=3) for fault tolerance
  • Document shard key design (ensure even distribution)
  • Set up alerts for topology changes (add/remove servers)
  • Test single-server failure scenarios
  • Validate cache hit rate before/after rebalancing
