Google Calendar System Design: Planet-Scale Scheduling Platform

Overview​

Google Calendar is a large-scale scheduling and time-management platform that supports personal planning, shared calendars, invitations, recurring events, reminders, and multi-device synchronization.

From a system design perspective, the hard parts are:

  • Modeling complex temporal logic (time zones, DST, recurrence exceptions)
  • Maintaining reliable multi-user collaboration with ACLs and sharing rules
  • Delivering near-real-time updates across web, mobile, and integrations
  • Sending accurate notifications and reminders at massive scale

This document presents a practical architecture for a Google Calendar-like product.

Problem Statement​

Design a global calendar platform that allows users to:

  • Create, edit, delete, and search events
  • Manage one or more calendars per user (personal, team, resource)
  • Invite attendees, collect RSVP responses, and handle schedule updates
  • Define recurring events with exceptions and overrides
  • Share calendars with role-based access controls
  • Sync data across devices and third-party integrations (API, CalDAV)
  • Receive reminders and notifications with high reliability

Scale Assumptions​

  • 600M MAU
  • 120M DAU
  • 2B active events/day (including recurring expansions)
  • 300M event mutations/day
  • 10B reminder checks/day
  • 2M+ concurrent sync connections at peak

Core Data Model​

CREATE TABLE calendars (
  calendar_id      BIGINT PRIMARY KEY,
  owner_user_id    BIGINT NOT NULL,
  name             VARCHAR(255) NOT NULL,
  timezone         VARCHAR(64) NOT NULL,
  is_primary       BOOLEAN NOT NULL DEFAULT FALSE,
  created_at       TIMESTAMP NOT NULL,
  updated_at       TIMESTAMP NOT NULL
);

CREATE TABLE events (
  event_id             BIGINT PRIMARY KEY,
  calendar_id          BIGINT NOT NULL,
  organizer_user_id    BIGINT NOT NULL,
  title                VARCHAR(512) NOT NULL,
  description          TEXT,
  location             VARCHAR(512),
  start_ts_utc         TIMESTAMP NOT NULL,
  end_ts_utc           TIMESTAMP NOT NULL,
  timezone             VARCHAR(64) NOT NULL,
  recurrence_rule      TEXT,  -- RRULE if recurring master
  recurrence_parent_id BIGINT, -- null for master/single events
  status               VARCHAR(32) NOT NULL,
  etag                 VARCHAR(64) NOT NULL,
  created_at           TIMESTAMP NOT NULL,
  updated_at           TIMESTAMP NOT NULL
);

CREATE TABLE attendees (
  event_id         BIGINT NOT NULL,
  attendee_user_id BIGINT NOT NULL,
  response_status  VARCHAR(16) NOT NULL, -- needsAction, accepted, tentative, declined
  is_optional      BOOLEAN NOT NULL DEFAULT FALSE,
  updated_at       TIMESTAMP NOT NULL,
  PRIMARY KEY (event_id, attendee_user_id)
);

CREATE TABLE calendar_acl (
  calendar_id      BIGINT NOT NULL,
  principal_type   VARCHAR(16) NOT NULL, -- user, group, domain, public
  principal_id     VARCHAR(255) NOT NULL,
  role             VARCHAR(16) NOT NULL, -- owner, writer, reader, freeBusyReader
  created_at       TIMESTAMP NOT NULL,
  PRIMARY KEY (calendar_id, principal_type, principal_id)
);

Design notes:

  • Store canonical timestamps in UTC and keep original timezone metadata.
  • Model recurring masters separately from occurrence overrides/exceptions.
  • Use optimistic concurrency via etag or version number.

Recurrence and Timezone Complexity​

Common Temporal Pitfalls​

  • DST transitions can make local times ambiguous or invalid.
  • "Every weekday" depends on locale/business calendar.
  • Editing one occurrence vs whole series needs distinct semantics.
  • Cross-timezone invites require stable UTC storage and local rendering.

Mitigation Strategy​

  • Parse recurrence with RFC 5545-compatible engine.
  • Store timezone per event and compute local views at read time.
  • Represent occurrence edits as overrides linked to the recurring master.
  • Build deterministic test suites for DST boundaries in major time zones.

Notifications and Reminder Pipeline​

Design decisions:

  • Use idempotency keys to avoid duplicate reminders.
  • Recompute reminder jobs on event updates/cancellations.
  • Use dead-letter queues for failed deliveries and replay.
  • Persist delivery status for troubleshooting and user audit.

Scalability Strategy​

Partitioning​

  • Shard primary event storage by calendar_id to colocate calendar data.
  • Secondary index by (attendee_user_id, start_ts_utc) for invited events.
  • Maintain write-optimized mutation log for sync and search indexing.

Caching​

  • Cache day/week/month rendered views with short TTL.
  • Cache ACL decisions for hot calendars.
  • Cache free/busy blocks per user per horizon window.

Search​

  • Asynchronous indexing from mutation stream.
  • Eventual consistency acceptable for search (seconds-level lag).
  • Support typed filters: date range, attendee, organizer, location, status.

Reliability and Failure Modes​

Failure ModeUser ImpactMitigation
Reminder queue backlogLate notificationsPriority queues, autoscaling workers, backlog alarms
Search index lagNewly edited events missing in searchFallback to DB scan for narrow windows, index catch-up jobs
Sync token invalidationClient misses changesForce full resync with bounded snapshot endpoint
Region outagePartial/total unavailabilityActive-active multi-region, automated failover, async replication
Calendar ACL cache corruptionIncorrect visibilitySigned ACL versions + short TTL + DB fallback
Recurrence engine bugIncorrect event displayShadow validation jobs + canary rollout + safe fallback

Security and Compliance​

  • OAuth2/OIDC authentication; least-privilege API scopes
  • Fine-grained ACL checks at calendar and event level
  • Encryption in transit (TLS 1.2+) and at rest (KMS-managed keys)
  • Audit trails for sharing changes, event deletions, and admin actions
  • Data residency controls and retention policies for enterprise tenants

Trade-offs​

DecisionBenefitTrade-off
Expand recurrence on readLower storage and flexible windowsHigher read CPU for dense recurring calendars
Eventual search indexingFast writes and scalable indexingSlightly stale search results
Incremental sync tokensEfficient mobile syncToken lifecycle complexity
Cached rendered viewsLow-latency calendar UICache invalidation complexity
Multi-region active-activeHigh availabilityConflict handling and higher infra cost

When to Use This Architecture​

Use this design when you need:

  • Collaborative calendaring for consumers and enterprises
  • Complex recurrence and timezone correctness
  • API integrations and near-real-time sync
  • High-scale reminders and notifications

This is likely overkill for:

  • Single-user local calendar apps
  • Low-scale scheduling tools without sharing/invites
