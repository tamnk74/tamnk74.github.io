School Bus Tracker System Design

Problem Statement​

Design a real-time school bus tracking system that allows parents to monitor the live position of their children's buses, and automatically notifies them when a bus is approaching their home address. The system serves thousands of schools, each with multiple buses and hundreds of students.

Scale Envelope​

MetricValue
Schools2,000
Buses per school10
Total buses20,000
Students per school300
Total students / parents600,000
Location update cadenceEvery 2 seconds
Bus location writes20,000 ÷ 2 = 10,000 RPS
Parent app reads~30% of parents active at morning peak ≈ 1,500 RPS
Notification fanoutUp to 50 parents per GeoHash cell transition
Data retentionLocation history: 90 days
Availability target99.9% (≤8.7 h downtime/year)

Write throughput dominates — 10× more writes than reads — making this a write-heavy, latency-sensitive, geospatial system.

Functional Requirements​

  1. Frequent location updates — bus GPS position updated and visible to parents every 2 seconds.
  2. Live map visualization — parents and school admins see bus pins on a map in real time.
  3. Proximity notifications — push alert sent to parents ~2 minutes before the bus arrives at their home.
  4. Data isolation — each school sees only its own buses; parents see only buses carrying their children.
  5. Historical playback — school administrators can replay a bus route for the day.

Non-Functional Requirements​

NFRTarget
Location write latency (p99)< 200 ms end-to-end to Redis
Push notification delivery< 5 s after GeoHash boundary crossing
Read latency (parent map load)< 300 ms p99
Data consistencyEventual (last-write-wins for live location)
Availability99.9%
PrivacyParents see only buses associated with their children
SecurityJWT auth, TLS everywhere, PII in encrypted DynamoDB fields

High-Level Architecture​

API Design​

Bus → Server: WebSocket (location ingest)​

WS  /v1/buses/{bus_id}/location

Payload (sent every 2 seconds):

{
  "latitude": 40.712776,
  "longitude": -74.005974,
  "timestamp": "2026-05-23T07:45:12Z",
  "speed_kmh": 28,
  "heading": 315
}

Using WebSocket avoids TCP handshake overhead at 10,000 RPS. A RESTful POST would add ~3× the connection overhead.

Parent App → Server: REST (initial load)​

GET  /v1/buses/locations
Authorization: Bearer <JWT>
X-Authorization: <JWT>

The server resolves the parent's children → their bus IDs → returns current cached positions.

{
  "buses": [
    {
      "bus_id": "e3d54bd9-bbbc-4d8e-a653-a937c7c4a215",
      "driver": { "id": "a23e80d5", "name": "Rosella Huel" },
      "children": [{ "id": "0d95d921", "name": "Herminia Rippin" }],
      "location": { "latitude": 40.712776, "longitude": -74.005974 },
      "eta_minutes": 4
    }
  ]
}

Parent App → Server: WebSocket (live updates)​

WS  /v1/parents/{parent_id}/stream

After connecting, the ECS server:

  1. Reads the parent's bus_ids from Redis (or DynamoDB).
  2. Subscribes to bus#{uuid} Redis Pub/Sub channels.
  3. Forwards every published message to the WebSocket connection.

Geospatial Algorithm: GeoHash​

Three approaches were evaluated for matching bus positions to student home locations.

Evenly Divided Grid — rejected​

Static, equal-size grids fail in sparse rural areas (grids too large) and dense urban blocks (grids too coarse to distinguish adjacent houses).

Quadtree — rejected​

Excellent density-adaptive partitioning but it is an in-memory structure rebuilt on server boot. Dynamic house data makes invalidation costly, and grid boundaries are defined by data density rather than a configurable radius.

Google S2 — alternative​

Hilbert-curve based 1D cell IDs with arbitrary precision via min_level / max_level / max_cells. Ideal for geofence polygon coverage but operationally complex.

✅ GeoHash — chosen​

GeoHash encodes latitude/longitude into a base-32 string. Nearby coordinates share a common prefix, enabling range queries on a string index.

GeoHash LengthGrid SizeUse Case
54.9 km × 4.9 kmCity-level
61.2 km × 609 m✅ Notification proximity
7153 m × 152 m✅ Fine-grained block matching
838 m × 19 mToo small — over-triggers

Decision: Length 6–7 balances precision (notifies ~2 min before arrival) with false-positive rate.

const geohash = require('ngeohash');

// Encode student home location (precision 7 ≈ 150 m grid)
const homeGeohash = geohash.encode(40.6892, -74.0445, 7); // → "dr5ru7h"

// On bus location update, encode bus position at same precision
const busGeohash  = geohash.encode(latitude, longitude, 7);

// If busGeohash === homeGeohash → trigger proximity notification
// Also check 8 neighboring geohash cells to handle boundary edge cases
const neighbors = geohash.neighbors(busGeohash);          // 8 adjacent cells
const alertZone = new Set([busGeohash, ...neighbors]);
if (alertZone.has(homeGeohash)) {
  await enqueueNotification(parentId, busId, eta);
}

Checking 9 cells (cell + 8 neighbors) eliminates the boundary artifact where two nearby points hash to different cells across a grid edge.

Data Model (DynamoDB)​

Write-heavy workload (10,000 RPS) favors a NoSQL write-optimized store. DynamoDB with on-demand capacity mode provides linear horizontal scaling without pre-provisioned shards.

Parent Table​

PK: parent_id (String)
Attributes:
  - name, phone, email, school_id
  - student_ids: String Set
  - bus_ids: String Set       ← cached to avoid Student Table fan-out
  - device_tokens: String Set ← APNs/FCM tokens for push
  - notification_prefs: Map   ← channels: push | sms | email

Student Table​

PK: student_id (String)
Attributes:
  - name, school_id, parent_id
  - bus_id: String
  - home_lat, home_lng: Number
  - home_geohash: String       ← precision 7, indexed via GSI

GSI: geohash-bus-index
  PK: home_geohash
  SK: bus_id

The GSI enables the query: "Which students (and parents) live in geohash cell X and are associated with bus Y?" — the exact query needed when a bus crosses into a new cell.

Bus Location History Table​

PK: bus_id (String)
SK: timestamp (ISO-8601)
Attributes:
  - latitude, longitude, speed_kmh, heading
  - geohash_6: String          ← for boundary-change detection
  - geohash_7: String
TTL: 90 days (DynamoDB TTL attribute)

Location Update Flow (Bus Side)​

Key design decisions:

DecisionRationale
WebSocket ingest (not REST)Saves TCP handshake at 10,000 RPS
Kinesis/Kafka bufferDecouples ingest spike from DB writes; provides replay on consumer crash
Redis Cache (TTL 10s)O(1) last-known-location reads for parent app initial load
Redis Pub/SubPush-based fan-out to parent WebSocket servers without polling
SQS for DB writeAsync persistence; DB latency does not affect ingest pipeline
GeoHash boundary check at write timeLambda compares old/new geohash_6 per bus — only triggers notification on cell change, not every 2-second tick

Parent App Flow​

In-memory HashMap on ECS — each ECS instance maintains:

// connectionId → Set<busChannel>
const subscriptions = new Map<string, Set<string>>();

// wsConnectionId → connectionId (for reverse lookup)
const wsConnections = new Map<string, WebSocket>();

This avoids duplicate Redis subscriptions when multiple parents share a bus.

Notification Flow​

Notification payload (SNS → APNs/FCM):

{
  "title": "🚌 Bus approaching",
  "body": "Bus #7 is ~2 minutes from Maya's stop",
  "data": {
    "bus_id": "e3d54bd9",
    "eta_minutes": 2,
    "bus_lat": 40.712,
    "bus_lng": -74.005
  }
}

Deduplication: A Redis key notif:{bus_id}:{geohash}:{parent_id} with TTL 5 minutes prevents repeated alerts on the same boundary re-entry within the same morning run.

Scalability Deep Dive​

WebSocket Gateway (AWS API Gateway)​

Fully managed; scales horizontally with connection count. No provisioning required. ECS tasks behind it scale via CPU/connection-count metrics.

Kinesis / Kafka MSK​

Kinesis: add shards (UpdateShardCount) proportional to RPS. At 10,000 RPS with ~1 KB payload = ~10 MB/s — a single shard handles 1 MB/s, so 10 shards minimum.

Kafka MSK: partition count drives parallelism. Use bus_id as partition key to ensure ordered processing per bus.

Redis ElastiCache​

Cluster mode: shard bus:{id}:location keys across nodes. At 10,000 writes/s and 1,500 reads/s, a 3-shard r6g.large cluster provides headroom.

Pub/Sub: Redis handles millions of channels. Memory cost per channel is negligible. Horizontal scaling via ElastiCache Serverless.

DynamoDB​

On-demand capacity mode absorbs 10,000 WCU/s bursts automatically. Partition key = bus_id spreads load across physical partitions. Use TTL on history table to auto-expire records after 90 days without DELETE cost.

SQS Throughput vs FIFO Limits​

Queue TypeLimitSuitable for 10,000 RPS?
FIFO3,000 msg/s (with batching)❌ Not enough
StandardVirtually unlimited✅ Yes
Kinesis/Kafka directPartition-limited, configurable✅ Yes

Recommendation: Use Standard SQS for DB write queue (ordering not required, dedup at application layer). For notification queue, FIFO suffices (fanout volume is much lower than location ingestion RPS).

Alternative to Redis Pub/Sub: Erlang/Elixir + Phoenix​

For teams with Elixir expertise, Phoenix Channels (Elixir/OTP) is a viable alternative:

DimensionRedis Pub/SubElixir Phoenix Channels
Concurrency modelSingle-threaded event loop per nodeBEAM lightweight processes (millions concurrent)
Fan-outVia shared Redis clusterVia distributed Erlang message passing
Fault toleranceRequires Redis Sentinel/ClusterBuilt-in OTP supervision trees
Operational complexityLow (managed ElastiCache)Higher (requires Elixir expertise)
Best forAWS-native stacksGreenfield, high fan-out chat-like systems

For this architecture (AWS-native, Node.js workers), Redis Pub/Sub is recommended.
