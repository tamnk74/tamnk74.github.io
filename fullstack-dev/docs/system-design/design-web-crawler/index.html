Design a Web Crawler

Building a scalable web crawling and search indexing system

Overview​

This document outlines the design of a web crawler that indexes billions of web pages, generates reverse indexes for search queries, and provides fast search results with titles and snippets.

Step 1: Outline Use Cases and Constraints​

Use Cases​

In Scope​

  • Service crawls a list of URLs:
    • Generates reverse index of words to pages containing the search terms
    • Generates titles and snippets for pages
    • Title and snippets are static, they do not change based on search query
  • User inputs a search term and sees a list of relevant pages with titles and snippets
  • Service has high availability

Out of Scope​

  • Search analytics
  • Personalized search results
  • Page rank

Constraints and Assumptions​

State Assumptions​

  • Traffic is not evenly distributed (some searches are very popular)
  • Support only anonymous users
  • Generating search results should be fast
  • The web crawler should not get stuck in an infinite loop
  • 1 billion links to crawl
    • Pages need to be crawled regularly to ensure freshness
    • Average refresh rate of about once per week
    • 4 billion links crawled each month
  • Average stored size per web page: 500 KB
  • 100 billion searches per month

Calculate Usage​

  • 2 PB of stored page content per month
    • 500 KB per page × 4 billion links crawled per month
    • 72 PB of stored page content in 3 years
  • 1,600 write requests per second
  • 40,000 search requests per second

Step 2: Create a High Level Design​

Key components:

  • Crawler Service - Crawls and processes web pages
  • Pages Data Store (NoSQL) - Stores links to crawl and crawled links
  • Reverse Index Service - Generates search indexes
  • Document Service - Generates titles and snippets
  • Query API Server - Handles search queries
  • Memory Cache (Redis) - Caches popular search results
  • Web Server - Reverse proxy
  • Client - Search interface

Step 3: Design Core Components​

Use Case: Service Crawls a List of URLs​

We'll use a key-value NoSQL Database to store links. For ranked links in links_to_crawl, we could use Redis with sorted sets to maintain a ranking of page links.

Crawler Flow​

The Crawler Service processes each page link:

  1. Takes the top ranked page link to crawl
  2. Checks crawled_links for an entry with a similar page signature
    • If similar page exists, reduces the priority of the page link (prevents cycles)
    • Continue to next link
  3. Else, crawls the link:
    • Adds a job to the Reverse Index Service queue
    • Adds a job to the Document Service queue
    • Generates the page signature
    • Removes the link from links_to_crawl
    • Inserts the page link and signature to crawled_links

class Crawler(object):
    def __init__(self, data_store, reverse_index_queue, doc_index_queue):
        self.data_store = data_store
        self.reverse_index_queue = reverse_index_queue
        self.doc_index_queue = doc_index_queue

    def create_signature(self, page):
        """Create signature based on url and contents."""
        ...

    def crawl_page(self, page):
        for url in page.child_urls:
            self.data_store.add_link_to_crawl(url)
        page.signature = self.create_signature(page)
        self.data_store.remove_link_to_crawl(page.url)
        self.data_store.insert_crawled_link(page.url, page.signature)

    def crawl(self):
        while True:
            page = self.data_store.extract_max_priority_page()
            if page is None:
                break
            if self.data_store.crawled_similar(page.signature):
                self.data_store.reduce_priority_link_to_crawl(page.url)
            else:
                self.crawl_page(page)

Handling Duplicates​

Duplicate URLs​

For smaller lists: sort | unique

For 1 billion links, use MapReduce:

class RemoveDuplicateUrls(MRJob):
    def mapper(self, _, line):
        yield line, 1

    def reducer(self, key, values):
        total = sum(values)
        if total == 1:
            yield key, total

Duplicate Content​

Generate a signature based on page contents and compare signatures for similarity:

  • Jaccard index
  • Cosine similarity

Determining When to Update Crawl Results​

  • Pages need to be crawled regularly to ensure freshness
  • Add timestamp field indicating last crawl time
  • Default time period: one week
  • Frequently updated or popular sites: shorter intervals
  • Data mining to determine mean time before page updates
  • Support Robots.txt for webmaster control

Use Case: User Searches Keywords​

Flow:

  1. Client sends request to Web Server (reverse proxy)
  2. Web Server forwards to Query API server
  3. Query API server:
    • Parses the query:
      • Removes markup
      • Breaks up text into terms
      • Fixes typos
      • Normalizes capitalization
      • Converts to boolean operations
    • Uses Reverse Index Service to find matching documents
    • Reverse Index Service ranks results and returns top ones
    • Uses Document Service to return titles and snippets

REST API​

curl https://search.com/api/v1/search?query=hello+world

Response:

{
    "title": "foo's title",
    "snippet": "foo's snippet",
    "link": "https://foo.com"
},
{
    "title": "bar's title",
    "snippet": "bar's snippet",
    "link": "https://bar.com"

Step 4: Scale the Design​

Key Optimizations​

Memory Cache:

  • Popular queries served from Redis or Memcached
  • Reduces response times
  • Handles uneven traffic distribution and spikes
  • Reading 1 MB from memory: ~250 microseconds (vs 4x for SSD, 80x for disk)

Crawler Optimizations:

  • Sharding and federation for Reverse Index Service and Document Service
  • Keep own DNS lookup cache (refreshed periodically)
  • Connection pooling - many open connections at once
  • Consider UDP for performance boost
  • Ensure sufficient bandwidth for high throughput

Key Challenges​

  1. Avoiding Infinite Loops - Detect cycles using page signatures
  2. Duplicate Detection - URL and content deduplication
  3. Freshness - Regular re-crawling based on update frequency
  4. Scale - Billions of pages, petabytes of data
  5. Bandwidth - High throughput requirements
  6. DNS Lookup - Caching to avoid bottlenecks

Conclusion​

Building a web crawler at scale requires:

  • Efficient duplicate detection
  • Smart crawl prioritization
  • Robust cycle prevention
  • Distributed indexing and search
  • Aggressive caching for popular queries

The design balances crawling speed, storage efficiency, and search performance while handling billions of pages and searches.
