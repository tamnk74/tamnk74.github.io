Completing Item 140: Hold Test Automation Follow-up Meetings

Item: 140 | Architecture Management | Technical Backlog management | DEVELOPMENT (Sprint 1-N) | 3 | Recurrent follow-up meetings are conducted by the technical responsible in order to discuss the goals and issues that came from the test automation and coverage percentage. | Review the code coverage report (e.g., from lcov) in the same bi-weekly tech meeting. If coverage is dropping, create tasks to add tests. | |

This guide explains how to establish a regular cadence for discussing goals, progress, and issues related to test automation and code coverage in your Flutter project.

Why Hold Test Automation Follow-ups? 🧪​

  • Maintain Focus on Coverage Goal: Keeps the team accountable for the agreed-upon test coverage target (Item 24).
  • Identify Coverage Gaps: Highlights areas of the codebase with insufficient test coverage, indicating higher risk for regressions.
  • Track Automation Progress: Monitors progress on implementing higher-level automated tests (Integration, E2E) if that's a team goal (Item 157).
  • Discuss Test Quality & Flakiness: Provides a forum to discuss not just quantity (coverage) but also the quality and reliability (flakiness) of automated tests.
  • Share Best Practices: Allows team members to share effective testing patterns or troubleshoot common testing problems.
  • Generate Improvement Actions: Leads to specific tasks like adding tests to low-coverage areas, refactoring untestable code, or improving the CI testing environment.

Steps​

  1. Integrate into Existing Meetings (Recommended):

    • Similar to code quality follow-ups (Item 139), leverage existing technical team meetings.
    • Technical Backlog Refinement (Item 137): Dedicate 10-15 minutes (potentially right after the code quality review segment) of this bi-weekly meeting to test automation and coverage.
    • Team Technical Sync-up: If applicable.

  2. Prepare for the Review (Tech Lead/QA Lead):

    • Before the meeting:
      • Generate or locate the latest code coverage report (e.g., the HTML report generated from lcov.info, or the coverage view in SonarQube/SonarCloud).
      • Review the overall coverage percentage and the coverage on new code. Is it meeting the target (Item 24)? What are the trends?
      • Identify specific modules, features, or critical files with significantly low coverage.
      • Check the CI pipeline logs for any recent test failures or flaky tests.
      • Review progress on any ongoing UI/E2E test automation efforts.
    • Prepare 1-2 key talking points.

  3. Conduct the Test Automation Review Segment:

    • Share Screen: Display the coverage report (HTML or SonarQube).
    • Review Coverage Metrics:
      • State the current overall coverage and coverage on new code. Compare against the target. Celebrate meeting the goal!
      • Highlight trends (improving, stable, decreasing?).
    • Discuss Low-Coverage Areas: Point out 1-2 critical areas with low coverage. Discuss why coverage is low (difficult to test? recent feature without tests? oversight?).
    • Discuss Test Reliability: Ask the team: "Have there been any flaky tests in CI recently?", "Are tests running reliably locally?". Discuss potential causes and fixes for flaky tests (e.g., timing issues, improper setup/teardown, external dependencies).
    • Review Automation Progress (if applicable): Briefly discuss the status of any work being done on integration or E2E tests. Are there blockers? Is the chosen framework working well?
    • Identify Action Items: Capture specific actions needed.

  4. Create and Track Action Items:

    • Add Missing Tests: For critical areas with low coverage, create specific Jira tasks (e.g., "Increase test coverage for payment_bloc.dart") and add them to the Technical Backlog (Item 137).
    • Fix Flaky Tests: Create high-priority bug tickets or tasks to investigate and fix unreliable tests. Flaky tests erode trust in the test suite.
    • Refactor Untestable Code: If code is difficult to test, create tech debt tickets to refactor it for better testability.
    • Improve CI Environment: If tests fail in CI but pass locally, create tasks to investigate and stabilize the CI test environment.
    • Assign owners and prioritize these tasks in the technical backlog refinement.

  5. Keep it Focused and Actionable:

    • Stick to the timebox (10-15 min).
    • Focus on trends, critical gaps, and reliability issues. Avoid debugging specific failing tests during this meeting.
    • The goal is to maintain visibility, ensure accountability for the coverage target, improve test reliability, and generate prioritized actions for the backlog.

Regularly reviewing test automation and coverage ensures that testing remains a priority and that your test suite provides reliable protection against regressions. ✅
