Completing Item 73: Automate Build Artifact Generation

Item: 73 | Architecture Execution | Continuous Integration | PREPARATION (Sprint 0) | 2 | "The build to create artifact for environments are automated, and there is no manual steps, excluding configuring enviroment variables/settings." | Use CI/CD (e.g., GitHub Actions, Codemagic) for all artifact generation. Developers must not build release .aab/.ipa files locally. | |

This guide explains the importance of automating the generation of application build artifacts (.apk, .aab, .ipa) using a CI/CD server and why manual local builds for releases should be avoided.

Why Automate Artifact Generation?​

  • Consistency & Reproducibility: Ensures that every artifact is built using the exact same environment, tools, Flutter version, and build commands. Eliminates "works on my machine" problems.
  • Reduced Errors: Manual build steps are prone to human error (forgetting a flag, using the wrong signing key, incorrect environment configuration). Automation removes this risk.
  • Efficiency: Frees developers from the time-consuming and often tedious process of manually building, signing, and managing artifacts.
  • Security: Allows sensitive information like code signing keys and passwords to be managed securely within the CI/CD environment's secret management, rather than being stored on developer machines.
  • Traceability: CI/CD logs provide a clear record of how and when each artifact was built, linked to a specific code commit.

Implementation Steps​

  1. Mandate CI/CD for All Release Builds:

    • Establish a firm team policy: Developers MUST NOT create release builds (.aab/.ipa intended for distribution or production) on their local machines.
    • All artifacts intended for QA testing (Staging) or Production release must be generated by the automated CI/CD pipeline.

  2. Configure CI/CD Build Jobs:

    • As part of your CI/CD setup (Item 70, Item 45, etc.), create specific jobs or steps responsible for building the release artifacts.

    • Environment Configuration:

      • Use a clean, consistent build environment (Docker image, dedicated runner).
      • Install the exact required Flutter SDK version (use FVM - Item 2).
      • Install any other required dependencies (Java, CocoaPods, Fastlane).

    • Build Commands:

      • Use the correct flutter build commands for each platform:

        # Android App Bundle (Production)
        flutter build appbundle --release \
          --dart-define=VAR1=ProdValue1 \
          --dart-define=VAR2=ProdValue2

        # iOS IPA (Production)
        flutter build ipa --release \
          --export-options-plist=path/to/ExportOptionsProd.plist \
          --dart-define=VAR1=ProdValue1 \
          --dart-define=VAR2=ProdValue2

      • Ensure environment variables (--dart-define or .env files - Item 69) are correctly injected for the target environment (Staging, Prod). Retrieve sensitive values from CI secrets.

    • Code Signing:

      • Android: Securely provide the upload keystore file (.jks) and its passwords (key password, store password) to the build environment via CI secrets. Configure android/app/build.gradle to use these.
      • iOS: Securely provide the distribution certificate (.p12) and provisioning profile (.mobileprovision) and any associated passwords to the build environment via CI secrets. This is often complex and best managed using tools like fastlane match or specialized CI features (like Codemagic's key management). Configure Xcode settings or ExportOptions.plist accordingly.

  3. Artifact Storage:

    • Configure the CI/CD job to automatically archive and store the generated artifacts (.aab, .ipa, build logs, mapping files for Android crash symbolication) in a reliable location:
      • CI/CD platform's built-in artifact storage (often temporary).
      • GitHub Releases / GitLab Packages.
      • Dedicated artifact repository (Artifactory, Nexus).
      • Cloud storage (GCP Bucket, AWS S3).
    • Ensure artifacts are clearly named, versioned, and linked to the corresponding Git commit/tag.

  4. Exclude Local Build Files:

    • Ensure your project's .gitignore file includes the build/ directory and any locally generated artifact files to prevent accidental commits.

  5. Documentation and Communication:

    • Document in the team's wiki that all official builds come only from the CI/CD pipeline.
    • Explain why local release builds are prohibited (consistency, security, reproducibility).
    • Provide links to where team members can download the latest CI-generated builds for testing (e.g., Firebase App Distribution link).

By strictly enforcing automated artifact generation through CI/CD, you significantly improve the reliability, security, and traceability of your build process.
