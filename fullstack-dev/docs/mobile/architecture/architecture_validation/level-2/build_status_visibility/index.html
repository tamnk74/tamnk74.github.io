Completing Item 79: Ensure Build Status Visibility and Feedback

Item: 79 | Architecture Execution | Continuous Integration | PREPARATION (Sprint 0) | 2 | "The current status of the build is visible to everyone in the team and there is immediate feedback when the build run or fail (email, chat message, etc)" | Integrate the CI/CD tool with the team's chat (e.g., Slack/Google Chat) to post notifications for build successes and failures. | |

This guide explains how to make the status of your CI/CD builds easily visible to the entire team and ensure immediate feedback is provided upon completion or failure.

Why is Build Visibility and Feedback Important?​

  • Fast Feedback Loop: Immediately informs developers if their changes broke the build or failed tests, allowing for quicker fixes.
  • Team Awareness: Keeps the entire team (including QA, PO) aware of the integration status and the availability of new builds for testing.
  • Reduced Integration Time: Broken builds are identified and fixed faster, preventing them from blocking other developers.
  • Transparency: Makes the CI/CD process less of a "black box."
  • Accountability: Encourages collective ownership of maintaining a green build.

Implementation Steps​

  1. Choose Visibility Mechanisms:

    • CI/CD Dashboard: Most CI/CD platforms (GitHub Actions, GitLab CI, Codemagic, Jenkins) provide a web UI showing build history, current status (running, success, failure), and logs. Ensure all team members know how to access this.
    • Pull Request Status Checks: Configure the CI/CD platform to report the status of checks (lint, test, build, quality gate) directly within the Pull Request interface on GitHub/GitLab. This is crucial for blocking merges on failure. [Image of GitHub PR status checks]
    • Real-time Chat Notifications: Integrate the CI/CD platform with the team's primary chat tool (Slack, Google Chat, Teams). This provides immediate, push-based feedback.
    • Build Badges (Optional): Embed status badges (showing build success/failure for the main branch) in the project's README file.
    • Physical Monitors (Optional): In a co-located office, a dedicated monitor displaying the main branch build status can be effective (less common now with remote work).

  2. Configure Pull Request Status Checks:

    • In your CI workflow file (e.g., GitHub Actions YAML), ensure jobs corresponding to critical checks (analyze, test, format, build, SonarQube Quality Gate) are configured to run on pull_request triggers.
    • In your Git host (GitHub/GitLab), configure branch protection rules (Item 8) for the main branch to require these status checks to pass before merging.

  3. Configure Chat Notifications:

    • Select Target Channel: Choose a dedicated channel for automated notifications (e.g., #proj-mobile-alerts - Item 17) to avoid spamming general channels.
    • Configure Integration: Use built-in integrations or marketplace apps/plugins for your CI/CD platform and chat tool:
      • GitHub Actions: Use actions like rtCamp/action-slack-notify, slackapi/slack-github-action, or specific Google Chat actions.
      • GitLab CI: Built-in Slack/Teams integrations.
      • Codemagic: Built-in Slack/Email integrations.
      • Jenkins: Slack Plugin or others.
    • Configure Notification Triggers: Set up notifications for key events:
      • Build Failure (Most Important): Send an immediate notification on any build failure on the main branch or on a PR. Include a link to the failed build logs and @mention the commit author if possible.
      • Build Success (Main Branch): Notify when the main branch build succeeds after a merge (often coincides with deployment notifications - Item 70).
      • Build Success (PR - Optional): Optionally notify when a PR build passes (can be noisy). Status checks in the PR interface are often sufficient.
      • Deployment Success/Failure: Notify about the status of deployments to Dev/Staging/Prod environments.
    • Message Content: Make notifications clear and concise. Include:
      • Project Name
      • Branch Name / PR Number
      • Status (✅ Success / ❌ Failure)
      • Commit Author (if possible)
      • Link to Build Logs / PR / Deployment

  4. Document Access:

    • In your project onboarding guide or wiki, provide links to:
      • The CI/CD dashboard.
      • The chat channel used for notifications.
      • Instructions on interpreting status checks in Pull Requests.

  5. Establish Team Norms:

    • Broken Build is Priority #1: Emphasize the "Stop the Line" policy (Item 162). If the main branch build fails, fixing it becomes the team's top priority.
    • Monitor Notifications: Encourage team members (especially the author of the failing commit) to monitor the alerts channel and take action on failures promptly.

By ensuring build status is highly visible and feedback is immediate, you reinforce the core principles of Continuous Integration and enable the team to maintain a stable codebase.
