Completing Item 144: Track Defects Found During Code Reviews

Item: 144 | Architecture Validation | Architecture Evaluation | DEVELOPMENT (Sprint 1-N) | 2 | The defects identified during the code reviews become defects in the ticket control system (JIRA or similar) and are part of the quality metrics. | If a PR comment is not a simple fix (e.g., "This needs refactoring"), create a new Jira "Tech Debt" ticket for it and link it in the comment. | |

This guide explains how to handle significant issues identified during code reviews by tracking them formally in your ticket system (e.g., Jira), rather than letting them get lost in PR comments.

Why Track Code Review Defects Formally? 🧐​

  • Visibility: Ensures significant issues identified during review aren't forgotten after the PR is merged, especially if they aren't fixed within that PR.
  • Prioritization: Allows these issues (often technical debt or necessary refactoring) to be added to the Technical Backlog (Item 137) and prioritized against other technical work.
  • Tracking: Creates a record of identified issues and their resolution status.
  • Quality Metrics: Allows you to (optionally) track the number or types of significant issues found during reviews as an indicator of code quality trends or areas needing more attention.
  • Avoids PR Bloat: Prevents Pull Requests from becoming blocked indefinitely while developers attempt large refactorings suggested during review. Allows the main feature/fix to be merged while scheduling the larger improvement.

What Constitutes a "Defect" to Track?​

Not every PR comment needs a Jira ticket. Focus on issues that are:

  • Non-Trivial: Require more than a few minutes to fix (e.g., significant refactoring, addressing a complex logical flaw, adding substantial missing test coverage).
  • Architectural Concerns: Deviations from established patterns, performance bottlenecks, potential security risks that need more investigation or rework than a quick fix.
  • Technical Debt: Code that works but is overly complex, hard to understand, poorly tested, or likely to cause problems later.
  • Bugs: Actual logical errors found during review that might be complex to fix or whose fix is deferred.

Simple fixes (typos, naming convention violations, minor logic adjustments) should generally be addressed directly within the PR before merging and do not need separate tracking.

Steps​

  1. Identify Trackable Issues During Code Review:

    • When a reviewer identifies a non-trivial issue (as defined above), they should still add a comment to the Pull Request explaining the problem.
    • Crucially: The reviewer (or the PR author, upon discussion) decides if the fix is simple enough to handle within the current PR or if it should be deferred and tracked separately.

  2. Decision Point: Fix Now vs. Track and Defer:

    • Fix Now: If the issue is critical, blocks the core functionality of the PR, or is relatively quick to fix without significantly expanding the PR's scope. The author fixes it, pushes the update, and the review continues.
    • Track and Defer: If the issue represents significant technical debt, requires substantial refactoring, needs more investigation, or fixing it would excessively delay the merging of the primary feature/fix.

  3. Create a Ticket in Jira (If Tracking/Deferring):

    • Reviewer or Author: Creates a new task in Jira.
    • Ticket Details:
      • Type: "TechDebt," "Bug," or "Task" (use a consistent type or label like code-review-finding).
      • Title: Clearly describe the issue (e.g., "Refactor OrderService to separate concerns identified in PR #123").
      • Description:
        • Paste the context: Include the relevant code snippet(s).
        • Explain the problem: Detail why it's an issue (e.g., "Violates SRP," "Hard to test," "Potential performance issue under load").
        • Link back to the PR comment: Provide a direct link to the specific comment in the Pull Request where the issue was raised.
        • Suggest a potential solution if obvious.
      • Assignee: Assign initially to the original PR author or the Tech Lead for prioritization.
      • Labels: Add relevant labels (tech-debt, refactoring, performance, security, code-review-finding).

  4. Link and Update PR:

    • In the PR Comment: The person who created the Jira ticket should reply to the original review comment, stating that the issue is being tracked separately and providing the Jira ticket link. (e.g., "Good point. This requires a larger refactor. Created ticket MEC-789 to track this. Let's merge the current changes and address the refactor separately.").
    • PR Status: This allows the reviewer to potentially resolve their comment (knowing the issue is tracked) and approve the PR, unblocking the merge of the main feature/fix.

  5. Manage in Technical Backlog:

    • The newly created Jira ticket automatically enters the Technical Backlog (Item 137).
    • It gets prioritized during Technical Backlog Refinement along with other technical tasks.
    • It will eventually be scheduled into a sprint based on its priority.

  6. (Optional) Track Metrics:

    • Use Jira filters or dashboards based on the label/issue type (code-review-finding) to track:
      • Number of significant defects found per sprint/month.
      • Common types of defects being found.
      • Resolution rate of these defects.
    • Discuss these metrics during Architecture Maturity Reviews (Item 133) or Retrospectives to identify trends or areas for process improvement (e.g., if many similar defects are found, maybe coding standards need clarification or training is needed).

By formally tracking significant issues found during code reviews, you ensure they are not lost and can be addressed systematically, contributing to long-term code health without unnecessarily blocking feature delivery. Jira ↔️ PR
