Completing Item 107: Implement Automated Application Issue Response

Item: 107 | Architecture Execution | Continuous Monitoring | RELEASE | 5 | "When an issue has raised from application monitoring systems, there are actions that are automatically triggered that will not require manual intervention in order to fix it." | (Infra) Configure alerts (e.g., in Datadog) that can trigger automated rollbacks (e.g., via ArgoCD) if a new deployment shows a critical error spike. | |

(Note: Similar to Item 106, this is an advanced practice. For mobile apps, "automated fixes" usually mean automated backend rollbacks triggered by app monitoring, or potentially remote config changes.)

This guide discusses implementing automated responses triggered by application-level monitoring (like crash rates or performance metrics from the mobile app itself), typically involving backend rollbacks or configuration changes.

Why Automate Application Issue Responses?​

  • Fastest Reaction to User Impact: Issues detected directly from the app's behavior (e.g., sudden crash spike) can trigger remediation faster than waiting for backend metrics to degrade.
  • Reduced User Pain: Quickly rolling back a bad release or disabling a faulty feature via remote config minimizes the number of users affected.
  • Safety Net for Deployments: Provides an automated safety mechanism, especially for frequent releases.

Feasible Automated Actions (Triggered by App Monitoring)​

  • Automated Backend Rollback:
    • Trigger: Critical spike in mobile app crash rate (e.g., from Firebase Crashlytics Velocity Alert) or severe performance regression (e.g., Firebase Performance Alert for app start time) immediately following a backend deployment (assuming correlation is possible).
    • Action: Automatically trigger the CI/CD pipeline (e.g., ArgoCD, Jenkins) to redeploy the previous stable version of the backend service(s).
    • Implementation: Requires robust integration between app monitoring (Firebase, Sentry, Datadog RUM) and the backend deployment system. Monitoring tools might send webhooks on alerts, which trigger a rollback workflow. Needs careful correlation to ensure the app issue is likely due to the backend change.
  • Automated Feature Toggle Disable:
    • Trigger: Critical spike in crash rate or error logs specifically associated with a feature currently enabled via a feature toggle (e.g., Firebase Remote Config). Requires careful instrumentation (logging/crash reports tagged with active feature flags).
    • Action: Automatically call the feature toggle service's API (e.g., Firebase Remote Config REST API) to disable the problematic feature flag for all users.
    • Implementation: Requires monitoring tools capable of parsing logs/crash reports for feature context and triggering webhooks/functions that interact with the feature flagging service API.

Challenges for Mobile Apps​

  • Correlation: It can be difficult to automatically determine if a mobile app crash spike is definitively caused by a recent backend deployment versus an issue purely within the app code itself. False positive rollbacks can be disruptive.
  • Client-Side Issues: Many crashes or performance issues originate solely within the mobile app code. These cannot be fixed by backend rollbacks or remote config changes; they require a new app release. Automated rollbacks of app releases are generally not feasible (managed by app stores).

Steps to Implement (Focus on Backend Rollback Example)​

  1. Identify Reliable Triggers:

    • Focus on clear indicators from app monitoring that strongly correlate with backend health. Examples:
      • Firebase Crashlytics Velocity Alert for a crash happening deep within the network layer or directly after parsing a response.
      • Firebase Performance alert showing a sudden, massive increase in network request latency across many endpoints.
      • Custom alerts based on specific error logs sent from the app (e.g., "Received unexpected 500 error from /checkout API").
    • Avoid: Triggering on vague crashes or metrics that could have many causes.

  2. Integrate Monitoring with Deployment System:

    • Configure alerts in your app monitoring tool (Firebase, Datadog RUM, Sentry) for the chosen triggers.
    • Set up these alerts to send a webhook to an intermediary service or directly to your CI/CD platform when they fire.
    • Create a specific CI/CD job/workflow (e.g., rollback-backend-on-alert) that:
      • Receives the webhook payload.
      • Parses the payload to confirm it's the expected alert type.
      • Identifies the relevant backend service(s).
      • Triggers the deployment system (e.g., kubectl rollout undo deployment <service>, ArgoCD sync to previous commit) to revert the service(s) to the last known good version.

  3. Implement Safeguards:

    • Cooldown Period: Prevent the rollback from triggering repeatedly in a short period.
    • Manual Override: Provide an easy way for engineers to manually disable the automated rollback automation.
    • Clear Notifications: Send prominent notifications to the team chat (#alerts and #tech channels) whenever an automated rollback is triggered, including the triggering alert details.
    • Idempotency: Ensure the rollback action is safe to run multiple times if necessary (though cooldown should prevent this).

  4. Backend Deployment Strategy:

    • This automation works best with deployment strategies that allow easy rollbacks (e.g., Blue-Green, Canary with automated rollback support in tools like Argo Rollouts or Flagger).

  5. Document the Automation:

    • Clearly document which app monitoring alerts can trigger automated backend rollbacks.
    • Detail the workflow, involved tools (monitoring, webhooks, CI/CD), and safeguards.
    • Explain how to monitor the automation and how to disable it.

  6. Test and Iterate:

    • Test the end-to-end flow in a staging environment (requires simulating the alert trigger).
    • Start with non-critical services or configure the automation to require manual approval initially.
    • Refine the trigger conditions based on real-world experience to minimize false positives.

Automated responses triggered by application monitoring are powerful but complex to implement reliably. Start cautiously, focusing on clear trigger conditions and robust safeguards, often targeting backend rollbacks as the primary action.
