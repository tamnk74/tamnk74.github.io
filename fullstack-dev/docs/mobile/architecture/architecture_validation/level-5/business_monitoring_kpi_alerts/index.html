Completing Item 108: Configure Business Monitoring KPI Alerts

Item: 108 | Architecture Execution | Continuous Monitoring | RELEASE | 5 | "The business monitoring tools are measuring key indicators (conversion rate, number of sold items, average response time, etc). If there is an issue with <br>any of those key indicators the team will get notified." | (Business) Set up alerts on the business dashboard (e.g., "Signups dropped 50% in 1 hour") that notify the PO and tech leads. | |

This guide explains how to set up automated alerts based on significant changes or threshold breaches in your key business metrics (KPIs), ensuring relevant team members (especially Product Owners and Leads) are notified promptly.

Why Alert on Business KPIs?​

  • Early Problem Detection: Sudden drops in KPIs (e.g., signups, conversion rate, active users) can be the first sign of a critical technical issue (e.g., broken login, payment failure), a usability problem, or even external factors (marketing campaign ended, competitor launch).
  • Quantify Impact: Helps understand the business impact of technical incidents or feature releases.
  • Proactive Response: Allows the PO and team to investigate and react to significant business trend changes quickly, rather than waiting for manual report reviews.
  • Data-Driven Culture: Reinforces the importance of business metrics across the team.

Steps​

  1. Identify Alert-Worthy KPIs and Thresholds:

    • Collaborate with PO/Stakeholders: Review the primary KPIs defined in Item 104. Discuss: Which KPIs are critical enough that a sudden, significant change warrants an immediate alert?
    • Define "Significant Change": Determine what constitutes an anomaly worth alerting on. This requires understanding normal fluctuations. Examples:
      • Threshold Breach: "Conversion rate drops below 2% for > 1 hour."
      • Sudden Drop (Absolute): "Hourly signups drop by > 100 compared to the previous hour."
      • Sudden Drop (Percentage): "Daily Active Users (DAU) drops by > 20% compared to the same day last week."
      • Spike (Errors/Negative Metrics): "Payment failure rate exceeds 5% for > 30 minutes."
      • Absence of Data: "No new signups recorded in the last hour" (could indicate tracking failure).
    • Start Conservatively: Begin with alerts on only the most critical KPIs and set thresholds that avoid excessive noise from normal variations. You can tune them later.

  2. Choose the Alerting Tool:

    • Alerting capabilities depend on your business monitoring setup (Item 104):
      • BI Tools (Looker Studio, Tableau, Power BI, Looker): Many BI tools have built-in alerting features that allow you to set rules on dashboard metrics (e.g., "Alert if 'Sales' drops below X").
      • Product Analytics (Mixpanel, Amplitude): These platforms often have sophisticated anomaly detection and alerting features based on event data.
      • Backend Monitoring (Datadog, etc.): If KPIs are derived from metrics already in your backend monitoring system (e.g., number of orders processed), you can set up alerts there.
      • Custom Scripts: Querying underlying data (e.g., in BigQuery from Firebase Analytics export) with scheduled scripts that trigger alerts if thresholds are met.

  3. Configure the Alerts:

    • Using the chosen tool, create alert rules based on the defined KPIs and thresholds.
    • Target Audience: Configure the alert notifications to go to the Product Owner and Tech Lead(s) as the primary recipients. Consider a dedicated chat channel (e.g., #proj-mobile-biz-alerts) or email distribution list. Avoid sending these directly to the main developer or general alert channels initially, as they require business context for interpretation.
    • Notification Content: Ensure the alert message clearly states:
      • Which KPI is affected.
      • The threshold that was breached or the detected anomaly.
      • The current value vs. the expected value/threshold.
      • A direct link to the relevant dashboard or chart for investigation.

  4. Document the Alerts:

    • On your project wiki (e.g., on the "Monitoring & Alerting" or "Business KPIs" page), list the configured business alerts.
    • Include the KPI, the trigger condition/threshold, and who gets notified.

  5. Establish Triage Process:

    • Define who is responsible for acknowledging and initially investigating a business alert (usually the PO or Data Analyst).
    • The first step is typically to check the dashboard for context (is it a blip? a real trend? correlated with a release or external event?).
    • If a technical cause is suspected, the PO/Analyst should loop in the Tech Lead via the appropriate channel (e.g., #proj-mobile-biz-tech) with details and a link to the alert/dashboard.

  6. Tune and Iterate:

    • Monitor the alerts for frequency and relevance.
    • Adjust thresholds to reduce noise (false positives) or increase sensitivity (if real issues were missed).
    • Add alerts for new KPIs as they become important.
    • Review the alerting setup periodically (e.g., quarterly) with the PO.

Alerting on business KPIs provides a crucial layer of monitoring focused directly on the application's outcomes and value delivery.
