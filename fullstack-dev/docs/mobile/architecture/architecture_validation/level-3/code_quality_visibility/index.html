Completing Item 147: Ensure Code Quality Visibility and Feedback

Item: 147 | Architecture Validation | Architecture Evaluation | DEVELOPMENT (Sprint 1-N) | 3 | The code quality is visible to everyone in the team and there is immediate feedback whenever the quality has decreased. | Post SonarQube results to a chat channel. Configure the flutter analyze CI job to fail the build on any linter errors. | We set up a weekly SonarQube job to run and report the results to Google Chat. |

This guide explains how to make code quality metrics visible to the entire team and provide immediate feedback when quality standards are not met, fostering collective ownership.

Why Make Quality Visible and Feedback Immediate? 👀​

  • Transparency: Everyone can see the current state of code quality and how it's trending.
  • Collective Ownership: When quality metrics are shared, quality becomes a team responsibility, not just the Architect's or Lead's concern.
  • Fast Feedback Loop: Immediate feedback (e.g., a failing CI build on a PR) allows developers to fix issues while the context is still fresh in their minds, which is much more efficient. Delayed feedback (e.g., finding issues weeks later) is costly.
  • Reinforces Standards: Consistent, automated feedback reinforces adherence to coding standards and quality goals.
  • Motivation: Seeing quality metrics improve can be motivating; seeing them decline can be a call to action.

Steps​

  1. Immediate Feedback via CI on Pull Requests (Most Important):

    • Static Analysis (flutter analyze): Configure your CI pipeline to run flutter analyze --fatal-infos --fatal-warnings . on every Pull Request. This job must fail the build if any errors or warnings (based on your analysis_options.yaml - Item 145) are found.
    • Formatting Check (dart format): Configure CI to run dart format --output=none --set-exit-if-changed . on every PR. This must fail if code isn't formatted correctly (Item 6).
    • Unit/Widget Tests (flutter test): Configure CI to run flutter test on every PR. This must fail if any tests fail (Item 159).
    • SonarQube/SonarCloud Quality Gate: If using SonarQube/Cloud (Item 6, 25), configure it to analyze the PR and fail the build if the defined Quality Gate conditions (e.g., coverage on new code < 80%, new critical bugs > 0) are not met.
    • Required Status Checks: Configure your Git host (GitHub/GitLab) branch protection rules (Item 8) to require all these CI checks to pass before a PR can be merged. This provides immediate, blocking feedback.

  2. Visibility of CI Results:

    • Ensure CI results (pass/fail status, links to logs, SonarQube reports) are clearly visible directly within the Pull Request interface. Most CI/Git host integrations do this automatically. Developers should see a clear red 'X' or green '✓'.

  3. Shareable Dashboards:

    • SonarQube/SonarCloud: Make the project dashboard accessible to the entire team (read-only is usually sufficient). This dashboard shows overall trends for bugs, vulnerabilities, smells, coverage, duplication etc.
    • Test Coverage Reports: If not using SonarQube, configure CI to publish the HTML coverage report (lcov output) as an artifact, so team members can view detailed coverage if needed.
    • Monitoring Dashboards (for NFRs): Share links to Firebase Performance Monitoring, Crashlytics, and relevant backend monitoring dashboards (Datadog, etc.) that track NFRs related to quality (e.g., crash rate, performance targets).

  4. Automated Notifications (Use Sparingly but Effectively):

    • CI Failures: Configure CI to post a notification to the main technical chat channel (#proj-mobile-tech or #proj-mobile-alerts) only when a build/check fails on the main branch (e.g., main). PR failures are visible in the PR itself. Over-notifying for every PR failure creates too much noise.
    • SonarQube Summary (Optional): As noted in the item, setting up a periodic (e.g., weekly) summary post from SonarQube to a chat channel can be useful to remind the team of overall trends, but immediate PR feedback is more critical. Daily posts are usually too noisy.
    • Production Alerts: Critical production alerts (crashes, performance spikes) should definitely go to a dedicated alerts channel (Item 100).

  5. Discuss During Regular Meetings:

    • Briefly review key quality dashboards (SonarQube, Coverage, Firebase Crashlytics/Performance) during regular technical meetings (e.g., Technical Backlog Refinement, Architecture Maturity Review - Items 139, 140, 141) to discuss trends and identify areas needing attention.

  6. Documentation Links:

    • Include links to the key quality dashboards (SonarQube, Firebase, etc.) in your project's main README or development hub wiki page for easy access.

By making quality metrics highly visible and integrating immediate feedback directly into the PR workflow, you create a system where quality is constantly monitored and actively managed by the entire team. 📊✅❌
