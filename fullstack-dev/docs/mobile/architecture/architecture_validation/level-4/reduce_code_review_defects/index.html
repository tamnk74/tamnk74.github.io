Completing Item 149: Reduce Defects Found During Code Reviews Over Time

Item: 149 | Architecture Validation | Architecture Evaluation | DEVELOPMENT (Sprint 1-N) | 4 | The amount of defects identified during the code reviews are reducing over the time. | Track "Bugs found in production" vs. "Bugs found in QA." If production bugs are high, the code review process needs to be stricter. | | (Note: The suggested action in the item description seems slightly mismatched, focusing on bugs found later rather than during review. This guide focuses on reducing issues found during the review itself, implying improved quality before review).

This guide focuses on the goal and methods for reducing the number of significant defects or issues identified during the code review process over time. Achieving this indicates that code quality is improving before it even reaches the review stage.

Why Aim to Reduce Code Review Defects? 🤔​

  • Increased Efficiency: Fewer issues found during review means less back-and-forth between author and reviewer, faster PR approval times, and quicker merges (improved Lead Time - Item 10).
  • Improved Code Quality: Indicates that developers are internalizing coding standards, architectural patterns, and testing practices, producing higher-quality code initially.
  • Effective Automation: Suggests that automated checks (linting, testing, static analysis - Items 145, 148) are successfully catching many issues before human review.
  • Better Use of Reviewer Time: Allows reviewers to focus on more complex aspects like logic, design, and usability, rather than repeatedly pointing out basic standard violations or common errors.
  • Positive Trend Indicator: A downward trend in review defects is a strong sign of improving team practices and code health.

How to Measure (Prerequisite)​

  • You need a way to track significant issues found during reviews. This often involves:
    • Formal Tracking (Item 144): Using Jira tickets for non-trivial issues found in PRs provides a clear metric (number of code-review-finding tickets created per sprint/month).
    • Informal Tracking: Reviewers could use specific labels or comment conventions in the PR tool (e.g., [BLOCKER], [MAJOR]) and these could be manually tallied or potentially scraped via API. Formal tracking is generally better.

Strategies to Reduce Code Review Defects​

  1. Strengthen Automated Checks (Shift Left):

    • Aggressive Linting: Ensure your analysis_options.yaml is strict and covers common pitfalls and style issues (Item 145). Fail the build on any violation (Item 148). This eliminates entire classes of review comments.
    • Format Checking: Automatically check formatting (dart format) in CI and fail if incorrect (Item 6).
    • Test Coverage Gates: Enforce minimum code coverage on new code via SonarQube/CI (Item 148). This forces developers to add tests before review.
    • SonarQube Quality Gates: Fail builds on new bugs, vulnerabilities, or major code smells identified by SonarQube (Item 148).

  2. Improve Clarity of Standards and Architecture:

    • Ensure Coding Conventions (Item 3) and Architecture Foundation documents (Item 11) are clear, accessible, and well-understood by the team. Use examples.
    • If reviewers repeatedly point out violations of the same standard, it might indicate the documentation or communication needs improvement.

  3. Enhance Developer Practices:

    • Self-Reviews: Encourage developers to perform a thorough self-review of their code against the code review guidelines (Item 143) before submitting the PR.
    • IDE Integration: Ensure developers utilize IDE features that highlight lints and errors as they type.
    • Testing Habits: Foster a culture where writing unit/widget tests is an integral part of development, not an afterthought (Item 15).

  4. Knowledge Sharing and Training:

    • Pair Programming: Pairing can help developers learn standards and best practices from each other, catching issues even before a formal PR.
    • Targeted Training: If reviews consistently reveal misunderstandings in specific areas (e.g., state management, error handling, security), organize brief internal workshops or knowledge-sharing sessions.
    • Review Feedback: Use feedback from code reviews (especially recurring comments) as learning opportunities for the whole team (e.g., discuss a common mistake in a team sync).

  5. Analyze Trends and Adapt:

    • Track the Metric: Monitor the number of significant defects tracked from code reviews over time (e.g., monthly).
    • Identify Patterns: During retrospectives or technical meetings, discuss: "What types of issues are reviewers still finding frequently?", "Why are the automated checks not catching these?".
    • Adjust Automation & Guidelines: Use this analysis to:
      • Add new custom lint rules if appropriate.
      • Refine SonarQube rulesets.
      • Clarify sections in the coding guidelines or architecture documents.
      • Identify needs for further team training.

Reducing the number of defects found during code review is a sign of a maturing development process where quality is built-in early, supported by strong automation and clear guidelines, allowing human reviewers to focus on higher-level concerns. 📉➡️✅
