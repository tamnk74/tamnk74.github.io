Completing Item 46: Automate Pre-Production Environment Deployment

Item: 46 | Architecture Execution | Continuous Deployment | PREPARATION (Sprint 0) | 4 | "The deployment to the pre-production environment is automated and executed in a CI/CD server (Jenkins, Azure DevOps, etc)." | Create a separate workflow that deploys to a "Staging" track (e.g., separate Firebase project, or "Internal Testing" track on Play Store) from a release/* branch. | |

This guide explains how to set up an automated pipeline to deploy your Flutter app to a pre-production environment (often called Staging, UAT, or Release Candidate), which closely mirrors the production environment. This deployment typically happens less frequently than dev deployments, often triggered by creating a release branch or tag.

Why Automate Pre-Prod Deployments?​

  • Production-Like Testing: Provides an environment closely resembling production for final QA, UAT, performance testing, and regression testing before a production release.
  • Reduces Manual Effort: Automates the build and deployment process for release candidates.
  • Consistency: Ensures release candidate builds are created using a standardized, repeatable process.
  • Risk Reduction: Catches issues related to production-like configurations or infrastructure before hitting actual users.

Key Differences from Dev/Test Deployment​

  • Trigger: Often triggered manually, by pushing to a specific release/* branch, or creating a Git tag, rather than on every merge to main.
  • Configuration: Uses configuration (API endpoints, keys via dart-define or .env) specific to the Staging/Pre-Prod environment.
  • Build Mode: Typically builds are done in release mode (--release) to accurately reflect production performance and code optimization (unlike dev builds which might use debug mode).
  • Signing (Optional but Recommended): May use signing keys/profiles that are closer to production (e.g., Ad Hoc or Enterprise distribution for iOS, separate staging keys for Android) compared to debug builds. Still not the final production keys.
  • Distribution: Might use slightly different distribution tracks (e.g., TestFlight External Testing, Play Store Closed Testing/Beta Track, separate Firebase App Distribution project/group).

Steps​

  1. Choose Triggering Strategy:

    • Release Branch: Create a workflow that triggers when a branch matching release/v*.*.* is pushed. (Good for stabilizing a release).
    • Git Tag: Create a workflow that triggers when a tag matching v*.*.*+* (or similar release candidate pattern) is pushed. (Good for specific release candidate builds).
    • Manual Trigger: Create a workflow with workflow_dispatch allowing manual triggering, potentially requiring the branch/tag name as input. (Good for controlled RC builds).

  2. Create a Separate CI/CD Workflow:

    • Duplicate your dev deployment workflow (Item 45) or create a new one (e.g., .github/workflows/deploy_staging.yaml).
    • Update the on: trigger section based on your chosen strategy (release branch, tag, manual).

  3. Configure Build Steps for Pre-Prod:

    • Check out the correct code (based on the trigger event - branch or tag).
    • Set up Flutter, platform SDKs, dependencies as usual.
    • Crucially: Build the artifacts in release mode (--release) using the Staging/Pre-Prod configuration via --dart-define or .env.staging.
      • Android Example: fvm flutter build appbundle --release --build-name=... --build-number=... --dart-define=API_ENDPOINT=https://staging-api.example.com ... (AAB might be preferred here to test the format used for production).
      • iOS Example: fvm flutter build ipa --release --build-name=... --build-number=... --dart-define=API_ENDPOINT=https://staging-api.example.com --export-options-plist=path/to/ExportOptionsStaging.plist ... (Ensure appropriate staging/AdHoc signing).

  4. Configure Deployment Step for Pre-Prod:

    • Choose the appropriate distribution target for this environment:
      • Firebase App Distribution: Use a separate group (e.g., uat-testers) or even a separate Firebase project for staging builds.
      • TestFlight: Upload to App Store Connect for distribution to Internal or External Testers. Requires production-like signing. fastlane pilot can automate this.
      • Google Play Closed Testing: Upload to a Closed Testing track (Alpha/Beta) in the Play Console. Requires production-like signing. fastlane supply can automate this.
    • Update the deployment step in your CI/CD workflow to target the chosen platform/track using staging credentials/secrets.
    • Example (Firebase App Dist Staging Group): 
      - name: Upload to Firebase App Distribution (Staging)
        run: |
          firebase appdistribution:distribute build/app/outputs/flutter-apk/app-release.apk \
            --app ${{ secrets.FIREBASE_APP_ID_ANDROID }} \
            --token ${{ secrets.FIREBASE_CLI_TOKEN }} \
            --groups "uat-testers" \ # Target specific group
            --release-notes "Staging Build ${{ github.ref_name }} - ${{ github.sha }}"
    • Example (using Fastlane for TestFlight/Play Console): 
      # (Assuming fastlane is set up)
      - name: Deploy to TestFlight (iOS)
        run: bundle exec fastlane beta_ios
      - name: Deploy to Play Store Closed Testing (Android)
        run: bundle exec fastlane beta_android

  5. Add Notifications:

    • Notify relevant stakeholders (QA, UAT testers, PO) via chat/email when a new staging build is available, providing access instructions/links.

  6. Document the Process:

    • Update your CI/CD/Release documentation (Item 26) to include the staging deployment workflow, trigger mechanism, and how testers access these builds.

Automating pre-production deployments ensures a reliable process for getting release candidates into a production-like environment for final validation before impacting end-users.
