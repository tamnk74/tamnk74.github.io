Completing Item 30: Define Targets for NFR Metrics

Item: 30 | Architecture Definition | Non-functional requirements | SETUP | 4 | "There is a target for the NFR metrics.<br>The target is defined and documented." | Quantify NFRs (e.g., "99.9% crash-free users" via Firebase Crashlytics; "P95 API response time < 500ms" via backend monitoring). | |

This guide details the crucial step of assigning specific, measurable targets to the Non-Functional Requirements (NFRs) identified previously (Item 27) and documented (often using a template from Item 28). This step makes NFRs actionable and verifiable.

Why Define Specific Targets?​

  • Measurability: Turns vague goals ("fast app") into concrete, testable criteria ("startup < 2s").
  • Objectivity: Removes ambiguity and subjectivity in assessing whether a requirement has been met.
  • Focus: Guides development and testing efforts towards achieving specific outcomes.
  • Quality Gates: Enables automated checks in CI/CD or release processes based on hitting these targets.
  • Clear Communication: Provides unambiguous quality goals for the team and stakeholders.

Steps​

  1. Revisit Collected NFRs:

    • Use the NFR list (Item 27) or the populated NFR template (Item 28) as your input.

  2. For Each Key NFR, Define Metric, Target, and Tool:

    • Go through each NFR statement and determine:
      • How can we measure this? (Metric): Identify a specific, quantifiable indicator.
      • What is the acceptable value? (Target): Define the precise threshold, number, or state that signifies success.
      • How will we perform the measurement? (Tool/Method): Specify the tool or process used to measure the metric.

  3. Quantify Common Flutter NFRs (Examples - expand on Item 28):

    • Performance:

      • NFR: "App starts quickly."
        • Metric: Cold App Startup Time (P90 or P95 - percentile ensures most users have this experience).
        • Target: < 2.0 seconds.
        • Tool: Firebase Performance Monitoring.
      • NFR: "Screens load fast."
        • Metric: Screen Trace Duration (P90) for critical screens (e.g., Home, Product Detail).
        • Target: < 500ms.
        • Tool: Firebase Performance Monitoring (Custom Traces).
      • NFR: "Scrolling is smooth."
        • Metric: Frames Per Second (FPS) during scroll / Number of Jank Frames.
        • Target: Maintain ~60 FPS / 0 Jank frames on target devices.
        • Tool: Flutter DevTools (Performance Overlay, Track Widget Builds). Note: Hard to automate fully, often requires manual profiling.
      • NFR: "App uses reasonable memory."
        • Metric: Memory usage after specific flow.
        • Target: < 250 MB on mid-range device (example target).
        • Tool: Flutter DevTools (Memory tab), Android Studio Profiler, Xcode Instruments.

    • Reliability:

      • NFR: "App doesn't crash often."
        • Metric: Crash-Free User Rate.
        • Target: > 99.9%.
        • Tool: Firebase Crashlytics.
      • NFR: "Backend is available."
        • Metric: API Endpoint Uptime / Availability.
        • Target: > 99.9%.
        • Tool: Backend monitoring (Datadog, GCP Monitoring uptime checks).
      • NFR: "Network errors are handled gracefully."
        • Metric: Percentage of failed network requests showing user-friendly error messages.
        • Target: 100%.
        • Tool: Manual testing, Code review.

    • Maintainability:

      • NFR: "Code is easy to test."
        • Metric: Line Coverage on New Code (Unit/Widget Tests).
        • Target: > 80%.
        • Tool: flutter test --coverage, SonarQube/lcov report.
      • NFR: "Code follows standards."
        • Metric: Number of New Major/Critical Code Smells.
        • Target: 0.
        • Tool: SonarQube Quality Gate.
      • NFR: "Build process is fast."
        • Metric: CI Pipeline Duration (PR check).
        • Target: < 15 minutes.
        • Tool: CI/CD Platform (GitHub Actions logs, etc.).

    • Security:

      • NFR: "Dependencies are secure."
        • Metric: Number of New Critical/High Vulnerabilities detected in dependencies.
        • Target: 0.
        • Tool: Snyk / Dependabot / SonarQube vulnerability scan.
      • NFR: "Data is encrypted in transit."
        • Metric: Usage of HTTPS (TLS 1.2+).
        • Target: 100% of external API calls.
        • Tool: Code review, Network proxy inspection (during testing), Pen-Test report.

    • Compatibility:

      • NFR: "Supports target OS versions."
        • Metric: Minimum Supported OS Version.
        • Target: Android API 23+, iOS 13.0+ (example targets).
        • Tool: build.gradle (minSdkVersion), Podfile (platform :ios).

  4. Document the Targets:

    • Fill in the Metric, Target, and Measurement Method/Tool columns in your NFR spreadsheet (from Item 28).
    • Ensure the wiki page or document summarizing NFRs (Item 27) also includes these specific targets for key requirements.

  5. Review and Approve:

    • Review these quantified targets with the development team for feasibility.
    • Present and get approval from the Product Owner/stakeholders (as per Item 29), ensuring they understand what is being promised and measured.

Defining these targets is essential for turning quality requirements into actionable, verifiable goals.
