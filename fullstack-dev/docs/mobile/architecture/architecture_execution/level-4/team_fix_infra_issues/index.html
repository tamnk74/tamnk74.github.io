Completing Item 102: Enable Team to Fix Infrastructure Issues

Item: 102 | Architecture Execution | Continuous Monitoring | RELEASE | 4 | The team can fix the issue when infrastructure monitoring is showing any problems. | (Infra) Ensure developers have the necessary (but limited) access and runbooks to debug and redeploy backend services when an issue is found. | |

(Note: This item implies a higher level of DevOps maturity where the development team has some capability to address infrastructure/backend issues, not just the mobile app itself. The scope depends heavily on team structure and responsibilities.)

This guide outlines steps to empower the development team (potentially including Flutter developers if they have backend responsibilities or the team is full-stack) to diagnose and potentially fix issues related to the backend infrastructure supporting the mobile app.

Why Empower the Team?​

  • Faster Resolution (MTTR): Reduces hand-offs and waiting times for a separate Ops/Infra team, especially for common or well-understood issues.
  • Increased Ownership: Fosters end-to-end responsibility for the service, from code to production operation.
  • Better Root Cause Analysis: Developers who understand the code and can see the infrastructure behavior are often better positioned to find the root cause of problems.
  • Skill Development: Encourages developers to learn more about the operational aspects of their services.

Scope and Prerequisites​

  • Team Structure: This is most applicable to teams with a DevOps culture, full-stack developers, or embedded SREs/Ops personnel. It's less relevant if there's a strict separation between Dev and Ops.
  • Infrastructure: Assumes infrastructure is managed via code (IaC - Terraform, etc.) and deployments are automated via CI/CD pipelines.
  • Access Control: Requires carefully defined, least-privilege access controls (IAM roles).
  • Training & Documentation: Developers need appropriate training and clear documentation (runbooks).

Steps​

  1. Define Scope of "Fixable" Issues:

    • Identify common, well-understood infrastructure/backend issues the development team could potentially resolve themselves. Examples:
      • Service Restart: A specific backend service (pod/container) becomes unresponsive and needs restarting.
      • Rollback Deployment: Rolling back a recent backend deployment that introduced instability.
      • Scaling: Manually triggering a scale-up/down action if autoscaling is misconfigured or too slow (less ideal, but sometimes necessary).
      • Clearing Cache: Flushing a problematic cache.
      • Known Application Bug Remediation: Running a predefined script to correct data corrupted by a known bug.
    • Exclude: Clearly define issues that must be escalated to a dedicated Infra/Ops/DBA team (e.g., underlying hardware failures, network configuration, database schema changes, major security incidents).

  2. Provide Necessary (Limited) Access:

    • Work with the Infra/Security team to grant developers least-privilege access required to perform the defined actions. Examples:
      • Permission to trigger specific CI/CD pipeline jobs (e.g., "Redeploy Staging Backend," "Rollback Production Backend").
      • Read-only access to logs and monitoring dashboards (Item 101).
      • Permission to restart specific pods/containers in Kubernetes (e.g., via kubectl rollout restart deployment).
      • Permission to run specific, pre-approved scripts via an automation tool (e.g., Jenkins job, Rundeck).
    • AVOID: Granting broad access like SSH to servers, direct database write access, or admin privileges in the cloud console.

  3. Develop Clear Runbooks/Playbooks:

    • For each type of issue the team is expected to handle, create a detailed runbook (a step-by-step guide). Store these on the team wiki.
    • Runbook Content:
      • Symptom: How the issue manifests (e.g., specific alert message, monitoring graph pattern, user report).
      • Diagnosis: Steps to confirm the issue (e.g., "Check logs for error X," "Verify API endpoint Y returns 503").
      • Resolution Steps: Exact commands or UI clicks needed to fix the issue (e.g., kubectl rollout restart deployment <service-name> -n <namespace>, "Click 'Run Job' on Jenkins job 'Clear-Product-Cache'"). Include screenshots if helpful.
      • Verification: How to confirm the fix worked (e.g., "Check monitoring graph Z returns to normal," "Verify API endpoint Y now returns 200 OK").
      • Escalation: Crucially: Define when to stop and escalate to the Infra/Ops team if the runbook steps don't resolve the issue. Include contact information/procedures for escalation.

  4. Training:

    • Conduct training sessions to walk developers through the common issues, the monitoring tools, the available actions, and the runbooks.
    • Ensure developers understand the potential impact of the actions they can take and the importance of following the runbooks precisely.

  5. Logging and Auditing:

    • Ensure all actions taken by developers (pipeline triggers, commands) are logged and auditable.

  6. Review and Iterate:

    • After incidents, review the effectiveness of the runbooks and the team's ability to resolve the issue. Update runbooks based on lessons learned.
    • Use retrospectives to discuss challenges or successes in handling infrastructure issues.

Empowering the team requires trust, clear procedures (runbooks), appropriate tooling, and careful access control. When done correctly, it can significantly improve incident response times.
