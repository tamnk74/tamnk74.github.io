Completing Item 24: Align on Test Coverage Goal

Item: 24 | Architecture Definition | Communication & Alignment | SETUP | 3 | "There is a goal in terms of target automated <br>test coverage percentage and this target is aligned with the team and the key project sponsors." | Formally agree with the PO and team on a target (e.g., 80% line coverage for unit/widget tests). Configure CI to fail if coverage drops below this. | |

This guide explains how to define, agree upon, and document a target for automated test coverage (specifically line coverage for unit and widget tests) in your Flutter project.

Why Define a Coverage Goal?​

  • Measurable Quality Target: Provides a quantifiable goal for testing efforts, moving beyond vague statements like "well-tested."
  • Focuses Effort: Helps the team prioritize writing tests, especially for critical business logic.
  • Regression Prevention: Higher coverage generally correlates with a lower chance of regressions.
  • Stakeholder Communication: Gives stakeholders (like the PO) a tangible metric related to code quality and stability.
  • CI Enforcement: Allows you to automatically enforce a minimum quality bar in your CI pipeline.

Understanding Code Coverage​

  • Line Coverage: The percentage of executable lines of code that were run during the execution of your automated test suite (flutter test --coverage).
  • What it Measures: Whether a line of code was executed by a test.
  • What it Doesn't Measure:
    • If the test assertions were meaningful or correct.
    • If all logical branches (e.g., edge cases within an if statement) were tested. (Branch coverage is a separate metric, often harder to track with standard Flutter tooling).
    • The overall quality or maintainability of the code or tests.

Coverage is a useful indicator but not a guarantee of quality. Aiming for 100% is often impractical and leads to diminishing returns.

Steps​

  1. Understand Your Starting Point (Optional but Recommended):

    • If the project has existing code, run flutter test --coverage and generate an initial coverage report (e.g., using genhtml lcov.info --output-directory coverage_report).
    • Analyze the current coverage percentage and identify areas with low coverage. This provides context for setting a realistic target.

  2. Propose a Target:

    • Common Targets: For Flutter unit and widget tests (excluding integration/E2E tests), a common and reasonable target for line coverage is often between 70% and 85%.
    • Considerations:
      • Project Criticality: Higher criticality might warrant a higher target.
      • Team Experience: Teams new to testing might start lower (e.g., 60-70%) and increase gradually.
      • Code Complexity: Highly complex business logic requires more thorough testing. UI-heavy code might naturally have slightly lower unit/widget test coverage (relying more on integration/manual tests).
    • Scope: Be clear that this target applies primarily to Unit Tests (test/**) and Widget Tests (test/**), not necessarily Integration Tests (integration_test/**) or generated code.

  3. Discuss and Align with the Team:

    • Present the proposed target to the development team.
    • Explain what coverage means and its limitations.
    • Discuss the feasibility and the effort required to reach and maintain the target.
    • Adjust the target based on team consensus. Ensure the team buys into the goal.

  4. Align with Product Owner / Key Sponsors:

    • Schedule a brief meeting with the PO and potentially other key stakeholders.
    • Explain the concept of code coverage in simple terms ("It's a measure of how much of our code is checked by automated tests when we make changes").
    • Present the team-agreed target (e.g., "We're aiming for 80% line coverage for our core logic").
    • Explain the trade-offs: "Achieving and maintaining this coverage level means dedicating a portion of our development time to writing tests, which might slightly slow down new feature delivery initially but will improve stability and reduce bugs long-term."
    • Get formal agreement or acknowledgment from the PO/sponsors. This ensures they understand the investment in quality.

  5. Document the Goal:

    • Create an "Automated Test Coverage Goal" page on your wiki or add a section to your "Testing Guide" (Item 15).
    • Clearly state the agreed-upon target percentage (e.g., "The target line coverage for unit and widget tests is 80%.").
    • Specify what code is included/excluded (e.g., "This target applies to code in the lib/ directory, excluding generated files (*.g.dart, *.freezed.dart)").
    • Mention the tool used to measure coverage (flutter test --coverage producing lcov.info).

  6. Implement Measurement and Enforcement:

    • CI Pipeline:
      • Ensure your CI pipeline runs flutter test --coverage on every PR.
      • Use tools to parse the lcov.info report (e.g., lcov command-line tool, GitHub Actions like coverallsapp/github-action or codecov/codecov-action, or SonarQube integration).
    • Quality Gates (Recommended):
      • Configure your CI tool or SonarQube (Item 6) to fail the build if:
        • Overall project coverage drops below the target (use with caution, can be annoying).
        • Coverage on New Code within a Pull Request is below the target (this is often the most effective gate). Set this threshold in SonarQube or using CI coverage tools.

  7. Monitor and Review:

    • Regularly review coverage reports (e.g., bi-weekly during tech backlog refinement - Item 138).
    • Discuss trends and identify areas needing more tests.
    • Revisit the target annually or if project circumstances change significantly.
