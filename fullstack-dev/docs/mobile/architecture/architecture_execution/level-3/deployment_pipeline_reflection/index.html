Completing Item 53: Ensure Pipeline Reflects Development Flow

Item: 53 | Architecture Execution | Continuous Deployment | DEVELOPMENT (Sprint 1-N) | 3 | Deployment pipeline contains step/task reflecting actual development flow and release flow. | Structure the CI/CD YAML to mirror the process: Setup->Analyze & Lint->Run Tests->Build App->Deploy to Firebase/Store. | |

This guide emphasizes structuring your CI/CD deployment pipelines logically to mirror your team's actual development and release workflow steps.

Why Structure Pipelines Logically?​

  • Readability & Maintainability: A pipeline structured like the manual process it replaces is easier for developers to understand, troubleshoot, and modify.
  • Clarity: Makes the purpose and sequence of each stage explicit.
  • Troubleshooting: When a pipeline fails, a logical structure helps pinpoint which phase of the process encountered the error (e.g., failure during testing vs. failure during deployment).
  • Onboarding: Helps new team members understand the build and release process by looking at the pipeline definition.

Standard Workflow Stages (Flutter Example)​

A typical Flutter CI/CD pipeline, whether for PR checks, Dev deployment, or Production release, often follows these logical stages:

  1. Setup Environment:

    • Checkout code (specific branch, tag, or PR ref).
    • Set up the build runner environment (e.g., select macOS/Linux, install OS dependencies).
    • Set up Flutter SDK (e.g., using FVM).
    • Set up platform SDKs (Java/Android SDK, Xcode/Gems/CocoaPods).
    • Set up secrets/authentication (e.g., decoding signing keys, logging into cloud services).
    • Install project dependencies (flutter pub get).

  2. Validate Code Quality:

    • Run static analysis (flutter analyze).
    • Check code formatting (dart format --set-exit-if-changed).
    • (Optional) Run custom validation scripts.

  3. Test:

    • Run Unit & Widget Tests (flutter test --coverage).
    • (Optional/Conditional) Run Integration Tests (can be slow, might run conditionally or in a separate workflow).

  4. Static Analysis Platform (Optional but Recommended):

    • Upload coverage reports and analysis results to SonarQube/SonarCloud.
    • Check Quality Gate status.

  5. Build Artifact:

    • Run code generation if needed (flutter pub run build_runner build).
    • Build the actual app artifact (.apk, .aab, .ipa).
      • Use --release mode for Staging/Prod builds.
      • Inject environment configuration using --dart-define (Item 44).
      • Include versioning information (--build-name, --build-number) (Item 42).
      • Handle code signing correctly for the target environment/platform.

  6. Deploy / Distribute:

    • Upload the artifact to the target platform (Firebase App Distribution, TestFlight, Google Play Console, etc.). Use tools like firebase-tools, fastlane, or specific CI/CD actions.

  7. Post-Deployment (Optional):

    • Run smoke tests against the deployed environment.
    • Send notifications (Slack, Google Chat, Email).
    • Create Git tags or releases.

Implementation​

  1. Review Your Current Pipeline(s): Look at your existing CI/CD YAML files (e.g., .github/workflows/*.yaml, codemagic.yaml). Do they follow a logical sequence? Are the steps clearly named?

  2. Refactor for Clarity:

    • Use Stages/Jobs: Most CI/CD platforms allow grouping steps into logical stages or jobs (e.g., jobs: in GitHub Actions, stages: in GitLab CI). Use these to represent the major phases (Validate, Test, Build, Deploy).
    • Descriptive Step Names: Give each step a clear name: that explains exactly what it does (e.g., name: Run Unit & Widget Tests, name: Build Android Release App Bundle).
    • Comments: Add comments within the YAML file to explain complex steps or non-obvious configurations.
    • Separate Workflows: Consider separating fundamentally different processes into distinct workflow files (e.g., pr_check.yaml, deploy_dev.yaml, release_production.yaml) instead of having one massive file with complex conditional logic. Link them logically (e.g., deploy_dev triggers on merge after pr_check succeeded).

  3. Example Structure (GitHub Actions):

    name: Build and Deploy App

    on: # ... trigger ...

    jobs:
      # --- Validation Job ---
      validate:
        name: Validate Code Quality
        runs-on: ubuntu-latest
        steps:
          - name: Checkout Code
            uses: actions/checkout@v3
          - name: Setup Flutter (FVM)
            # ...
          - name: Install Dependencies
            run: fvm flutter pub get
          - name: Check Formatting
            run: dart format --output=none --set-exit-if-changed .
          - name: Analyze Code
            run: fvm flutter analyze --fatal-infos --fatal-warnings .

      # --- Test Job (Depends on Validation) ---
      test:
        name: Run Tests
        needs: validate # Run after validation passes
        runs-on: ubuntu-latest
        steps:
          - name: Checkout Code
          - name: Setup Flutter (FVM)
          - name: Install Dependencies
          - name: Run Unit & Widget Tests
            run: fvm flutter test --coverage
          - name: Upload Coverage Report (Example)
            uses: actions/upload-artifact@v3
            with:
              name: coverage-report
              path: coverage/lcov.info

      # --- Build Job (Depends on Test) ---
      build:
        name: Build App Artifacts
        needs: test
        runs-on: macos-latest # Often need macOS for iOS builds
        # environment: dev # Optional: Scope secrets
        steps:
          - name: Checkout Code
          - name: Setup Flutter (FVM)
          - name: Setup Java/Android
          - name: Setup iOS (Certs/Provisioning via Fastlane Match etc.)
          - name: Install Dependencies
          - name: Build Android APK (Dev Example)
            run: fvm flutter build apk --debug --dart-define=...
          - name: Build iOS IPA (Dev Example)
            run: fvm flutter build ipa --debug --export-options-plist=... --dart-define=...
          - name: Upload Build Artifacts (for deployment job)
            uses: actions/upload-artifact@v3
            # ... upload APK and IPA ...

      # --- Deploy Job (Depends on Build) ---
      deploy:
        name: Deploy to Firebase App Dist (Dev)
        needs: build
        runs-on: ubuntu-latest
        steps:
          - name: Download Artifacts
            uses: actions/download-artifact@v3
            # ... download APK and IPA ...
          - name: Install Firebase CLI
          - name: Deploy Android to Firebase
            run: firebase appdistribution:distribute ...
          - name: Deploy iOS to Firebase
            run: firebase appdistribution:distribute ...
          - name: Send Slack Notification
            # ...

  4. Documentation: Ensure your CI/CD documentation (Item 26) reflects this logical structure, perhaps even including a simplified flowchart corresponding to the pipeline stages/jobs.

By structuring your pipelines logically, you make them more understandable, maintainable, and reflective of your team's actual workflow.
