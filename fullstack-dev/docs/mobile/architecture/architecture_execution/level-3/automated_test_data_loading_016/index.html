Completing Item 16: Define Automated Test Data Loading

Item: 16 | Architecture Definition | Architecture & Coding Guidance | PREPARATION (Sprint 0) | 3 | There is a definition about how to load data for automated testing and this plan meets the project requirements. | Define a strategy to inject mock data for integration/UI tests (e.g., using a mock repository, or tools like Patrol). | |

This guide explains how to define and document a strategy for providing consistent and controllable data to your automated integration and end-to-end (E2E) tests in Flutter. Unit tests use mocks directly (Item 15), but higher-level tests often need a more structured approach.

Why Define a Data Strategy for Tests?​

  • Consistency: Ensures tests run reliably without being affected by real backend changes or flaky data.
  • Control: Allows you to test specific scenarios (e.g., empty lists, error states, specific user roles) by providing tailored data.
  • Isolation: Prevents tests from polluting real development or staging databases.
  • Speed: Using local mock data is much faster than relying on network calls.

Strategies​

Choose one or a combination of the following strategies based on your testing needs and architecture:

  1. Mocking at the Repository Layer (Recommended for Integration Tests):

    • Concept: For integration tests (testing features or flows within the app), replace the real Repository implementations (which talk to APIs/DBs) with mock implementations that return predefined data.

    • Implementation:

      • Use a Dependency Injection (DI) framework like get_it.
      • In your main app setup (main.dart), register the real repositories.
      • In your test setup (test/integration_test/app_test.dart or similar), create mock repository implementations (using mocktail).
      • Before running the app in the test, unregister the real repositories and register the mock ones using your DI container.
      // Example test setup with get_it and mocktail
      import 'package:get_it/get_it.dart';
      import 'package:mocktail/mocktail.dart';
      import 'package:flutter_test/flutter_test.dart';
      import 'package:integration_test/integration_test.dart';

      // Assuming you have these defined:
      // import 'package:your_app/main.dart' as app; // Your main entry point
      // import 'package:your_app/domain/repositories/user_repository.dart';
      // import 'package:your_app/domain/entities/user.dart';
      // import 'test/mocks.dart'; // Contains MockUserRepository

      void main() {
        IntegrationTestWidgetsFlutterBinding.ensureInitialized();
        late MockUserRepository mockUserRepository;

        setUpAll(() {
           // Ensure real dependencies are registered if main does it
          // app.setupDependencies(); // Or however your app does it

          // Override with mocks for tests
          GetIt.instance.allowReassignment = true; // Allow overriding
          mockUserRepository = MockUserRepository();
          GetIt.instance.registerSingleton<UserRepository>(mockUserRepository);
        });

        setUp(() {
          // Reset mocks before each test if needed
          reset(mockUserRepository);
        });

        testWidgets('Login screen shows error on failed login', (tester) async {
          // Arrange: Setup mock response for this specific test
          when(() => mockUserRepository.login(any(), any()))
              .thenThrow(Exception('Invalid credentials'));

          // Act: Start the app
          app.main(); // Or the relevant function that starts your app
          await tester.pumpAndSettle();

          // Interact with the UI... tap login button etc.
          await tester.enterText(find.byKey(Key('emailField')), 'wrong@example.com');
          await tester.enterText(find.byKey(Key('passwordField')), 'wrong');
          await tester.tap(find.byKey(Key('loginButton')));
          await tester.pumpAndSettle();

          // Assert: Verify mock was called and UI shows error
          verify(() => mockUserRepository.login('wrong@example.com', 'wrong')).called(1);
          expect(find.text('Invalid credentials'), findsOneWidget);
        });

        testWidgets('Login screen navigates on successful login', (tester) async {
           // Arrange: Setup mock success response
           final tUser = User(id: '1', name: 'Test', email: 'test@example.com');
           when(() => mockUserRepository.login(any(), any()))
               .thenAnswer((_) async => tUser);

           // Act...
           // Assert: Verify navigation, perhaps expect find.text('Welcome Test')
        });
      }

    • Pros: Relatively easy to set up with DI, fast execution, good control over data for different scenarios within the app.

    • Cons: Doesn't test the real API contract.

  2. Using a Mock Backend Server (Recommended for E2E Tests):

    • Concept: Run a local HTTP server during your E2E tests that intercepts API calls and returns predefined JSON responses. Tools like Maestro or Patrol often integrate well with this.
    • Implementation:
      • Choose a mock server library (e.g., mock_web_server in Dart, or external tools like WireMock, Mockoon).
      • Define expected API requests and their corresponding JSON responses (store these JSON files in your test assets).
      • In your test setup, start the mock server.
      • Configure your app (e.g., via dart-define or DI overrides at the HTTP client level) to point to the mock server's local address (http://localhost:8080) instead of the real API endpoint only during tests.
      • In each test, configure the mock server to expect certain requests and provide specific responses.
    • Pros: Tests the app's networking layer and JSON parsing. Closer to real-world interaction.
    • Cons: More setup required, need to maintain mock JSON responses, slightly slower than repository mocking.

  3. Dedicated Test Backend Environment:

    • Concept: Maintain a separate deployment of your actual backend specifically for automated testing. This backend has its own database that can be reset or seeded before test runs.
    • Implementation:
      • Requires significant infrastructure setup (a full, isolated backend environment).
      • Need robust mechanisms to reset the database state before each test run or suite (e.g., API endpoints to clear/seed data, database snapshots).
      • Configure the app (via dart-define) to point to this test environment endpoint during test execution.
    • Pros: Tests against the real backend code and API contract. Highest fidelity.
    • Cons: Slowest execution, complex infrastructure, requires careful state management, can be costly.

Documenting the Strategy​

  1. Choose your primary strategy (or strategies for different test types - e.g., Repository Mocking for integration, Mock Server for E2E).
  2. Create a "Test Data Strategy" section on your "Testing Guide" wiki page (from Item 15).
  3. Describe the chosen approach(es): Explain how data is provided (DI overrides, mock server, test backend).
  4. Provide Examples: Include code snippets showing how to set up mocks or configure the mock server for a typical test scenario.
  5. Location of Test Data: Specify where mock data (e.g., JSON files for the mock server) is stored within the project structure.
  6. Tooling: List any specific libraries (mocktail, mock_web_server) or tools used.

By defining and documenting this strategy, you ensure your automated tests are reliable and effective.
