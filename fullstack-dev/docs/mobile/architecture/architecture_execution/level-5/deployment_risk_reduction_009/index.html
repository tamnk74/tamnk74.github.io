Completing Item 9: Implement Deployment Risk Reduction Strategy

Item: 9 | Architecture Definition | Architecture & Coding Guidance | SETUP | 5 | "There is a strategy that helps to reduce the risk of production deployments (blue-green deployment, canary release, feature toggle, etc)." | Implement a feature toggle system (e.g., Firebase Remote Config). Use the phased rollout capabilities in the Google Play Console and App Store Connect. | |

This guide explains strategies to reduce the risk associated with deploying new versions of your Flutter mobile app to production users. Unlike web applications, true blue-green or canary deployments are difficult, so the focus shifts to phased rollouts and feature toggles.

Key Strategies for Mobile Apps​

  1. Phased Rollouts (Google Play & App Store Connect):

    • Concept: Gradually release the new app version to a small percentage of users first. Monitor for issues (crashes, performance regressions, negative feedback) before increasing the percentage.
    • Implementation (Google Play - Android):
      • When creating a Production release in the Google Play Console, choose Staged rollout.
      • Start with a small percentage (e.g., 1%, 5%, 10%).
      • Monitor: Closely watch Firebase Crashlytics, Firebase Performance Monitoring, and user feedback channels during the rollout.
      • Increase Percentage: If no critical issues arise after a period (e.g., 24-48 hours), increase the percentage (e.g., to 25%, 50%, 100%).
      • Halt Rollout: If critical issues are found, click Halt rollout in the Play Console. Fix the issues, upload a new version, and start a new staged rollout.
    • Implementation (App Store Connect - iOS):
      • After your app version is approved, go to the version details page.
      • Under "Phased Release for Automatic Updates," select Release over a 7-day period.
      • iOS will automatically manage the rollout percentage over 7 days (e.g., Day 1: 1%, Day 2: 2%, Day 3: 5%, etc.).
      • Monitor: Closely watch Firebase Crashlytics, Performance Monitoring, and user feedback.
      • Pause/Resume: You can Pause the phased release in App Store Connect if issues are found. After fixing and potentially submitting an expedited review for a patch, you can Resume or release the fixed version to all users.
    • Documentation: Document the standard phased rollout plan (percentages, monitoring period) in your release process documentation.

  2. Feature Toggles (Feature Flags):

    • Concept: Deploy new features hidden behind a remotely configurable flag. This allows you to deploy the code to production but only enable the feature for specific users (testers, internal team) or gradually roll it out, independent of app store releases. It also provides an immediate "kill switch" if the feature causes problems.

    • Implementation:

      • Choose a Service: Use a feature flagging service like:

        • Firebase Remote Config: Simple, free, integrates well with Firebase. Good for basic on/off toggles and gradual rollouts by user percentage or properties.
        • LaunchDarkly, ConfigCat, Statsig: More advanced features (targeting, A/B testing, SDKs).

      • Integrate the SDK: Add the chosen service's Flutter SDK to your pubspec.yaml.

      • Implement Toggles in Code:

        // Example using Firebase Remote Config
        final remoteConfig = FirebaseRemoteConfig.instance;
        await remoteConfig.setConfigSettings(...); // Set fetch intervals
        await remoteConfig.fetchAndActivate();

        // In your widget or bloc:
        bool isNewFeatureEnabled = remoteConfig.getBool('show_new_checkout_flow');

        if (isNewFeatureEnabled) {
          // Show new UI or execute new logic
          return NewCheckoutScreen();
        } else {
          // Show old UI or execute old logic
          return OldCheckoutScreen();
        }

      • Wrap Major Features: Enclose significant new features or risky changes within if (isFeatureEnabled) blocks.

      • Remote Configuration: Configure the flags (show_new_checkout_flow) in the service's dashboard (e.g., Firebase Console). Set the default value (usually false).

    • Rollout Strategy:

      1. Deploy the app with the new feature code, but the flag turned OFF.
      2. Enable the flag for internal testers/QA first via the service dashboard.
      3. Gradually increase the percentage of production users who have the flag enabled (e.g., 1%, 10%, 50%, 100%) via the service dashboard.
      4. Monitor for issues. If problems arise, turn the flag OFF immediately in the dashboard – no app store update needed!

    • Cleanup: Once a feature is fully rolled out and stable, schedule tech debt tickets to remove the old code path and the feature flag check to avoid clutter.

    • Documentation: Document which features are currently behind toggles and the process for rolling them out.

  3. Thorough Testing (Pre-Deployment):

    • While not a deployment strategy itself, robust automated testing (unit, widget, integration) and manual QA on staging environments significantly reduce the risk of deploying bugs.

Documentation​

Update your project's wiki or deployment documentation:

  • Detail the standard phased rollout percentages and monitoring periods for both Android and iOS.
  • Explain how to use the feature toggle system (Firebase Remote Config or other).
  • List any currently active feature toggles and their status.
  • Emphasize the importance of monitoring during rollouts.

By combining phased rollouts and feature toggles, you gain significant control over production releases, minimizing the blast radius of potential issues.
