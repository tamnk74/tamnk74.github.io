Completing Item 55: Automate Production Deployment (with Approval)

Item: 55 | Architecture Execution | Continuous Deployment | DEVELOPMENT (Sprint 1-N) | 5 | The deployment can be executed automatically for Production environment (Except for release approval) | Automate the build and *upload* to App Store Connect / Google Play Console (e.g., using fastlane). The final "release to users" step remains manual. | |

This guide explains how to automate the build and submission process for production releases of your Flutter app, while retaining a crucial manual approval step before the app actually goes live to all users.

Why Automate Production Submission?​

  • Reduces Manual Errors: Building, signing, and uploading production artifacts manually is complex and prone to errors (using wrong keys, profiles, configurations).
  • Consistency: Ensures every production submission follows the exact same verified process.
  • Speed: Significantly speeds up the process of getting an approved build ready for release in the app stores.
  • Traceability: The automated process is logged and version-controlled (Item 54).

Why Retain Manual Release Approval?​

  • Business Control: Allows the Product Owner or Release Manager to decide the exact timing of the release based on business factors (marketing alignment, support readiness, user impact).
  • Final Sanity Check: Provides a final checkpoint before impacting all users.
  • Phased Rollout Management: The manual step is where the phased rollout (Item 9) is typically initiated and managed. App stores require manual intervention to start/manage these rollouts.

Steps​

  1. Prerequisites:

    • A reliable CI/CD platform is set up.
    • Pipeline-as-code is used (Item 54).
    • Secure management of production signing keys, certificates, and API keys within the CI/CD platform's secrets management. This is critical and platform-specific (e.g., GitHub Secrets, Codemagic encrypted environment variables, secure files). Access to production secrets should be tightly controlled.
    • A dedicated Git tag naming convention for production releases (e.g., vMAJOR.MINOR.PATCH+BUILD) (Item 42).

  2. Create a Dedicated "Release Production" Workflow:

    • Create a new CI/CD workflow file (e.g., .github/workflows/release_production.yaml).
    • Trigger: Configure this workflow to run only when triggered manually (e.g., workflow_dispatch in GitHub Actions) or automatically when a specific production tag pattern (e.g., v*.*.*+*) is pushed. Do not trigger this automatically on merges.
    • Inputs (if manual trigger): Require the exact Git tag to build from as input.

  3. Automate Production Build:

    • The workflow must perform the following steps:
      • Checkout the exact Git tag specified for the release.
      • Set up Flutter, platform SDKs, dependencies.
      • Securely access and configure production signing credentials (e.g., decode Android Keystore from secrets, set up iOS certificates/profiles using fastlane match or manual certificate installation from secrets).
      • Build the artifacts (.aab for Android, .ipa for iOS) in release mode (--release).
      • Inject production configuration using --dart-define (Item 44).
      • Use the correct version name and build number derived from the Git tag or pubspec.yaml (Item 42).

  4. Automate Submission to Stores:

    • Use Automation Tools: Leverage tools specifically designed for app store interaction, most commonly fastlane.

      • fastlane supply: Automates uploading Android builds (.aab) and metadata/screenshots to the Google Play Console. Configure it to upload to the Production track (or potentially start a staged rollout directly if the API supports it).
      • fastlane pilot or fastlane deliver: Automates uploading iOS builds (.ipa) and metadata/screenshots to App Store Connect TestFlight (for final testing) or directly for review. Configure it to submit for review.

    • CI/CD Integration: Add steps to your "Release Production" workflow to execute the appropriate fastlane lanes after the build is complete.

      # Example steps after build (assuming Fastlane setup)
      - name: Upload Android to Play Store Production Track
        run: bundle exec fastlane deploy_android_production
        working-directory: ./android # Or wherever Fastfile is

      - name: Upload iOS to App Store Connect for Review
        run: bundle exec fastlane deploy_ios_production
        working-directory: ./ios # Or wherever Fastfile is

    • Secrets: Securely provide fastlane with the necessary API keys or authentication credentials (e.g., Google Play Service Account JSON, App Store Connect API Key) via CI/CD secrets.

  5. Define the Manual Approval/Release Step:

    • The automated workflow STOPS after successful upload/submission.
    • Document the manual steps required in the Google Play Console and App Store Connect to actually release the submitted build to users:
      • Google Play: Go to the Production track, review the release created by the pipeline, and click "Start rollout" (initiating the phased rollout - Item 9). Monitor and increase percentage manually.
      • App Store Connect: Wait for the build to pass review ("Waiting for Review" -> "Ready for Sale"). Go to the approved version, select the phased release option (Item 9), and click "Release". Monitor and manage the phased release manually if needed.
    • Clearly define who is responsible for performing this final manual release step (e.g., Release Manager, PO, Tech Lead).

  6. Notifications and Logging:

    • The automated workflow should notify the responsible person(s) upon successful submission to the stores.
    • Ensure the workflow logs clearly indicate the version submitted and the target track/status.

By automating the build and submission but keeping the final release step manual, you balance efficiency and consistency with necessary business control over production deployments.
