Completing Item 48: Ensure Deployment Rollback Capability

Item: 48 | Architecture Execution | Continuous Deployment | PREPARATION (Sprint 0) | 2 | It is possible to rollback the deployment (code and database). | For the app: Document how to promote a previous, "known good" build in App Store Connect / Play Console. For DB: Ensure DB migration scripts have "rollback" scripts. | |

This guide covers ensuring and documenting that you can roll back both the application deployment (Flutter app) and any associated database changes if a deployment goes wrong.

Why is Rollback Capability Important?​

  • Fast Recovery: Allows quick restoration of service if a critical bug is introduced by a new deployment (reduces MTTR - Mean Time to Recovery, Item 10).
  • Risk Mitigation: Provides a safety net, making deployments less stressful.
  • Confidence: Increases confidence in deploying more frequently.

Rollback Strategy Components​

You need separate but coordinated strategies for the application and the database.

1. Application Rollback (Flutter App)​

  • Challenge: As noted in Item 7, you cannot instantly "pull back" an installed app from user devices. Rollback means distributing a previous, stable version through the app stores.
  • Mechanism:
    • Identify Last Known Good (LKG) Version: Keep track of the version string (MAJOR.MINOR.PATCH+BUILD) and corresponding Git tag of the last stable production release.
    • Retrieve LKG Artifact: Ensure you have access to the signed production artifacts (.aab, .ipa) for the LKG version (stored in GitHub Releases, Artifactory, etc. - Item 12).
    • Google Play Store (Android):
      1. Go to Production release track in Play Console.
      2. Create a new release.
      3. Upload the LKG .aab file (or select from library). It will likely need a new, higher build number than the faulty version but can have the same semantic version (e.g., faulty was 1.2.1+60, rollback is 1.2.1+61 built from the code of 1.2.0+55). Alternatively, use a patch version increment (e.g., 1.2.2+61).
      4. Submit and roll out to 100%.
    • App Store Connect (iOS):
      1. You must increment the version number (e.g., if faulty was 1.2.1, the rollback needs to be 1.2.2).
      2. Check out the Git tag of the LKG version (e.g., v1.2.0+55).
      3. Update the pubspec.yaml version to the new incremented version (e.g., 1.2.2+61). Re-run pod install if needed.
      4. Build and archive using the LKG codebase but the new version number.
      5. Upload this new build (1.2.2 (61)) to App Store Connect.
      6. Submit for expedited review if the issue is critical.
      7. Release once approved.
  • Automation: While the store submission often requires manual steps, the process of finding the LKG tag and building the rollback artifact can be automated via CI/CD (e.g., a "Rollback Build" workflow triggered manually with a tag input). See Item 52/59 for single-click ideas.
  • Documentation: Document these platform-specific steps clearly in your release/rollback runbook (Item 7).

2. Database Rollback (Backend)​

  • Mechanism: Rely on the capabilities of the database migration tool (Liquibase, Flyway - Item 47) used by the backend team.
  • Prerequisites:
    • Rollback Logic: Developers must consistently write the rollback (undo) logic for every database migration script they create.
      • Liquibase Example (XML): Uses <rollback> tags.
      • Flyway Example (SQL): Requires separate U<version>__undo.sql files or specific procedures.
      • SQL Example (Manual Tagging): 
        --changeset author:yourname id:20251025_add_last_login
        ALTER TABLE users ADD COLUMN last_login TIMESTAMP;
        --rollback ALTER TABLE users DROP COLUMN last_login;
    • Tool Support: The chosen migration tool must support a rollback command.
  • Execution:
    • If a deployment fails due to a database migration error or introduces bad data related to schema changes, the backend team runs the migration tool's rollback command (e.g., liquibase rollbackCount 1, flyway undo).
    • This command executes the predefined rollback logic for the most recently applied migration(s).
  • Coordination: Database rollbacks must often be coordinated with application rollbacks if the application code depends on the faulty schema changes.
  • Testing: Crucially, test rollback scripts in a non-production environment periodically to ensure they work as expected. Untested rollback logic is unreliable.
  • Limitations: Rollbacks involving destructive changes (dropping tables/columns) can cause data loss if not carefully managed. Some complex migrations might be difficult or impossible to roll back automatically and may require manual intervention or restoring from a backup (Item 12).
  • Documentation: The backend team's documentation should cover how to execute a database rollback using their chosen tool.

Overall Process​

  1. Detection: Identify a critical issue post-deployment via monitoring or user reports.
  2. Decision: Quickly decide if a rollback is necessary (vs. rolling forward with a hotfix).
  3. Execution:
    • Initiate the application rollback process (build/upload LKG version via stores).
    • If necessary, coordinate with the backend team to execute the database rollback.
  4. Verification: Monitor the system closely after the rollback to ensure stability is restored.

Documenting this entire coordinated process (App + DB) in a rollback runbook is essential.
