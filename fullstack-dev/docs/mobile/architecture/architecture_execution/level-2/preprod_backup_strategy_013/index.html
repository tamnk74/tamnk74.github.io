Completing Item 13: Define Pre-Production Backup/Restore Strategy

Item: 13 | Architecture Definition | Architecture & Coding Guidance | PREPARATION (Sprint 0) | 2 | "The backup/restore strategy for pre-production environments (database, files, etc) is defined and documented." | Document the backup/restore process for the staging database. Ensure dev/staging environments can be easily rebuilt from SCM. | |

This guide focuses on defining and documenting the backup and restore strategy for your pre-production environments (e.g., Staging, QA, UAT). These environments are typically less critical than production but still require a recovery plan.

Why Document This?​

While less critical than production, losing a staging environment (especially its data) can disrupt testing, delay releases, and require significant effort to rebuild. A defined strategy mitigates this risk.

Key Differences from Production Strategy​

  • Lower Criticality: Data loss might be acceptable or recoverable from other sources.
  • Cost Sensitivity: Backup solutions might be less frequent or have shorter retention to save costs.
  • Rebuild vs. Restore: It might be faster/easier to rebuild the environment from scratch (using IaC and seeding data) than to restore a full backup.

Steps​

  1. Identify Pre-Production Environments and Assets:

    • List your environments (e.g., Staging, QA).
    • Identify key assets for each:
      • Backend Database: (e.g., Staging PostgreSQL DB).
      • Configuration: Environment variables, secrets (often managed similarly to production but with different values).
      • Test Data: Any specific datasets required for testing.
      • Infrastructure: Kubernetes cluster setup, serverless functions (managed via IaC).
      • Source Code / CI/CD Config: Already covered by Git (same as production).

  2. Define Backup Strategy for Each Asset:

    • Backend Database (Example: Staging GCP Cloud SQL):
      • Strategy: Use automated backups but potentially with lower frequency/retention than production.
      • Mechanism: Automated Backups (daily snapshots). PITR might be disabled to save cost unless specifically needed for staging testing scenarios.
      • Frequency: Daily (automated).
      • Retention: Shorter retention (e.g., 7 days).
      • Consider: Is restoring essential, or can the DB be wiped and re-seeded with test data easily? If re-seeding is easy, backups might be less critical.
    • Configuration & Secrets:
      • Strategy: Same as production - IaC and Secrets Management.
      • Mechanism: Use the same IaC scripts (Terraform, etc.) but with staging variable files. Use the same secrets manager but with staging/ prefixed secrets.
      • Backup: Implicit via Git (IaC) and secrets manager redundancy.
    • Test Data:
      • Strategy: Define how essential test data is managed.
      • Mechanism:
        • Option A: Generate test data via scripts (e.g., seeding scripts run after deployment). These scripts should be versioned in Git. Backup = Git.
        • Option B: Sanitize and import a subset of production data periodically. The backup is the script/process used for this.
        • Option C: Rely solely on database backups if the specific state needs preservation.
    • Infrastructure:
      • Strategy: Rebuild from Infrastructure as Code.
      • Mechanism: Use Terraform/CloudFormation/etc., versioned in Git.
      • Backup: Git history.

  3. Define Restore Procedures (Focus on Rebuilding):

    • Primary Strategy: Emphasize rebuilding the environment from scratch using IaC and data seeding scripts.
      1. Run IaC scripts (terraform apply -var-file=staging.tfvars).
      2. Deploy the latest application code via CI/CD pipeline to the new infrastructure.
      3. Run data seeding scripts or the prod data import process.
    • Secondary Strategy (if needed): Document how to restore the database from its automated backup via the cloud console/CLI, similar to production but targeting the staging instance.

  4. Document the Strategy:

    • Create a "Pre-Production Backup and Restore Strategy" page on your wiki, separate from or linked within the production strategy.
    • Detail the chosen approach for each environment (Staging, QA).
    • Clearly state if the primary recovery method is rebuilding via IaC and seeding.
    • If database backups are used, specify frequency and retention.
    • Include links to IaC repositories and data seeding scripts.

  5. Test the Rebuild/Restore Procedure:

    • Periodically (e.g., every 6 months), attempt to completely destroy and rebuild a pre-production environment using only IaC, CI/CD, and data seeding scripts. This validates your automation and ensures you can recover quickly even without traditional backups.
