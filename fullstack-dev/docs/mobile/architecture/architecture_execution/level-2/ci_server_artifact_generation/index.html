Completing Item 80: Generate Artifacts on CI Server

Item: 80 | Architecture Execution | Continuous Integration | PREPARATION (Sprint 0) | 2 | "The build artifact is generated from a CI/CD server (Jenkins, Azure DevOps, etc)" | Prohibit local builds for releases. All test and production artifacts *must* come from the CI/CD pipeline. | |

(Note: This item is conceptually identical to Item 73, "Automate Build Artifact Generation". Both emphasize that artifacts must be built on a CI/CD server, not locally.)

This guide reiterates the critical practice of generating all official build artifacts (.apk, .aab, .ipa) exclusively on a centralized CI/CD server.

Why Centralized Artifact Generation is Crucial​

  • Consistency & Reproducibility: CI/CD servers provide a controlled, standardized environment, ensuring every artifact is built identically, regardless of which developer committed the code. This eliminates variability from local machine configurations (OS versions, installed tools, Flutter SDK versions).
  • Reliability: Automated processes are less prone to human error than manual build steps performed locally.
  • Security: Centralizes the management of sensitive signing keys and credentials within the secure environment of the CI/CD platform, rather than distributing them across developer machines.
  • Traceability: Creates an auditable trail linking every official build artifact back to a specific code commit and the CI/CD job that produced it.
  • Efficiency: Automates the build process, saving developer time.

Implementation (Reinforces Item 73)​

  1. Strict Policy: Implement and enforce a strict team policy: Release artifacts (for QA, Staging, Production) are never built on developer laptops. All official builds must originate from the designated CI/CD pipeline.
  2. CI/CD Pipeline Setup: Configure your CI/CD pipeline (GitHub Actions, GitLab CI, Codemagic, Jenkins, etc.) with dedicated jobs/workflows to:
    • Checkout the correct source code version (commit/tag).
    • Set up the precise build environment (Flutter SDK version via FVM, dependencies).
    • Inject environment-specific configuration (--dart-define or .env files retrieved from secrets - Item 69).
    • Execute the flutter build appbundle --release or flutter build ipa --release commands.
    • Handle code signing securely using secrets managed by the CI/CD platform (Item 73).
  3. Artifact Archiving: Automatically archive the generated .aab/.ipa files, along with any necessary metadata (version info, commit hash, build logs, symbolication files), in a reliable location (CI artifacts, GitHub Releases, Artifactory, etc. - Item 73).
  4. Prohibit Local Release Builds:
    • Communication: Clearly communicate the policy and its rationale to the team.
    • Access Control (Signing Keys): Limit access to production signing keys/certificates strictly to the CI/CD environment. Developers should not have easy access to production secrets locally.
    • Process: Ensure the only way to get a build for QA or Production is through the automated pipeline (e.g., via Firebase App Distribution links generated by CI, or builds submitted to TestFlight/Play Console by CI).

Documentation​

  • Explicitly state the "CI/CD server builds only" policy in your project's README, onboarding guide, and release process documentation.
  • Document how developers or testers can access the official builds generated by the CI/CD server (e.g., links to Firebase App Distribution).

This practice is fundamental to reliable, secure, and reproducible builds in a team environment. It moves artifact generation from an error-prone manual task to a controlled automated process.
