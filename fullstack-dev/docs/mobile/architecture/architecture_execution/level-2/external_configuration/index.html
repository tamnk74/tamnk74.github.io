Completing Item 44: Externalize Environment Configuration

Item: 44 | Architecture Execution | Continuous Deployment | DEVELOPMENT (Sprint 1-N) | 2 | "The configuration that is specific for each environment, such as API endpoints and configuration for database connection are configured externally to the deployment package as environment variables." | Use dart-defineor.envfiles (e.g., viaflutter_config) to inject environment-specific variables (API endpoints, keys) at build time. Do not hardcode them. | |

This guide explains how to manage environment-specific configurations (like API endpoints, API keys, feature flags) externally, rather than hardcoding them directly into your Flutter application code. This is crucial for building artifacts that can target different environments (Dev, Staging, Prod).

Why Externalize Configuration?​

  • Avoid Hardcoding: Prevents sensitive information (API keys) or environment details (URLs) from being committed to version control.
  • Environment Flexibility: Allows the same codebase to be built to target different backend environments or use different keys without code changes.
  • Consistency: Ensures a standard way of managing configuration across the app.
  • Security: Keeps secrets out of the codebase.

Methods for Externalizing Configuration in Flutter​

  1. Using --dart-define (Recommended for CI/CD):

    • Concept: Pass key-value pairs during the flutter run or flutter build command. These values are accessible in Dart code via String.fromEnvironment, int.fromEnvironment, bool.fromEnvironment.

    • Implementation:

      • Build Command:

        # Development Run
        flutter run \
          --dart-define=API_ENDPOINT=[https://dev-api.example.com](https://dev-api.example.com) \
          --dart-define=API_KEY=DEV123 \
          --dart-define=FEATURE_X_ENABLED=true

        # Production Build
        flutter build appbundle --release \
          --dart-define=API_ENDPOINT=[https://api.example.com](https://api.example.com) \
          --dart-define=API_KEY=PROD789 \
          --dart-define=FEATURE_X_ENABLED=true

      • Accessing in Dart:

        const String apiEndpoint = String.fromEnvironment(
          'API_ENDPOINT',
          // Provide a sensible default for local runs if no define is passed
          defaultValue: '[https://default-api.example.com](https://default-api.example.com)',
        );

        const String apiKey = String.fromEnvironment('API_KEY'); // No default = compile error if not defined

        const bool isFeatureXEnabled = bool.fromEnvironment(
          'FEATURE_X_ENABLED',
          defaultValue: false,
        );

        // Use these constants in your code (e.g., in your Dio client setup)
        Dio dio = Dio(BaseOptions(baseUrl: apiEndpoint));
        dio.options.headers['Authorization'] = 'Bearer $apiKey';

    • Pros: Built into Flutter, simple for CI/CD environments where variables are easily passed on the command line, avoids extra files.

    • Cons: Can make local flutter run commands verbose if there are many variables. Defaults need careful management. Values are compiled into the app.

  2. Using .env Files (Good for Local Development & CI/CD):

    • Concept: Store configuration variables in .env files (e.g., .env.dev, .env.prod). Use a package like flutter_dotenv or flutter_config to load these values at runtime (or compile time, depending on the package).

    • Implementation (flutter_dotenv example - loads at runtime):

      • Add flutter_dotenv to pubspec.yaml.

      • Create .env files (e.g., .env.dev, .env.prod) and add them to .gitignore.

        # .env.dev
        API_ENDPOINT=[https://dev-api.example.com](https://dev-api.example.com)
        API_KEY=DEV123
        # .env.prod
        API_ENDPOINT=[https://api.example.com](https://api.example.com)
        API_KEY=PROD789

      • Load the appropriate file in your main.dart before runApp:

        import 'package:flutter_dotenv/flutter_dotenv.dart';

        Future<void> main() async {
          WidgetsFlutterBinding.ensureInitialized(); // Needed before async

          // Determine which .env file to load (e.g., based on --dart-define)
          const env = String.fromEnvironment('ENV', defaultValue: 'dev');
          await dotenv.load(fileName: ".env.$env");

          runApp(MyApp());
        }

      • Access variables:

        import 'package:flutter_dotenv/flutter_dotenv.dart';

        String apiEndpoint = dotenv.env['API_ENDPOINT'] ?? 'default_fallback';
        String apiKey = dotenv.env['API_KEY']!; // Use ! if you are sure it exists

    • Implementation (flutter_config example - loads at compile time):

      • Add flutter_config to pubspec.yaml.

      • Create .env files as above (add to .gitignore).

      • Setup native platform integration (follow package instructions).

      • Configure build command/CI to select the .env file (e.g., using flutter build --dart-define=ENV_FILE=.env.prod).

      • Access variables (values are compiled in):

        import 'package:flutter_config/flutter_config.dart';

        String apiEndpoint = FlutterConfig.get('API_ENDPOINT');

    • Pros: Keeps local run commands clean, separates config clearly, standard .env format. flutter_config compiles values in (like dart-define).

    • Cons: Requires an extra package. flutter_dotenv loads values at runtime (slightly less secure, minor startup cost). Requires careful .gitignore management. Need a mechanism (like dart-define) to choose which .env file to load/compile.

Steps to Implement​

  1. Choose a Method: Select either --dart-define or an .env package based on team preference and workflow. Using dart-define is often simpler for CI/CD, while .env files can be cleaner for local development. You can combine them (e.g., use dart-define to specify which .env file flutter_dotenv should load).
  2. Identify Configuration Variables: List all values that change between environments (API URLs, keys, analytics IDs, feature flags, logging levels).
  3. Refactor Code: Remove hardcoded values and replace them with access to the chosen configuration mechanism (e.g., String.fromEnvironment or dotenv.env[]).
  4. Create Configuration Files/Variables:
    • If using .env, create the .env.dev, .env.staging, .env.prod files and add them to .gitignore. Store secrets securely (e.g., CI/CD secrets, secrets manager) and inject them into the .env file during the CI/CD build process, not in Git.
    • If using dart-define, ensure your CI/CD pipeline passes the correct defines for each environment build. Store secrets in CI/CD secrets.
  5. Configure Build/Run Commands:
    • Update launch.json (for VS Code local runs) and CI/CD scripts (flutter build commands) to pass the correct --dart-define flags or select the correct .env file.
  6. Document the Process:
    • On your project wiki, document:
      • The chosen configuration method.
      • Where environment variables are defined (e.g., "See .env.dev (gitignored), values sourced from CI secrets").
      • How to access variables in Dart code.
      • How to run/build the app for different environments (provide example commands).

By externalizing configuration, you create a more flexible, secure, and maintainable application build process.
