Completing Item 27: Map and Collect Non-Functional Requirements (NFRs)

Item: 27 | Architecture Definition | Non-functional requirements | SETUP | 1 | All the Non-functional requirements related to the application are being mapped and collected. | Create an "NFR" page in Confluence, listing requirements for the mobile app (e.g., Performance: app start time < 2s; Security: data at rest encrypted; Usability: accessibility support). | |

This guide covers the initial step of identifying, discussing, and collecting the Non-Functional Requirements (NFRs) relevant to your Flutter mobile application. This forms the basis for defining measurable targets later (Item 30).

What are NFRs?​

NFRs define how the system should perform its functions, rather than what functions it should perform (Functional Requirements). They specify the quality attributes, constraints, and characteristics of the system.

Why Collect NFRs Early?​

  • Impact Architecture: NFRs heavily influence architectural decisions (e.g., performance requirements might dictate state management choices, security requirements affect authentication flows). Addressing them early prevents costly rework later.
  • Set Expectations: Clarifies quality expectations with stakeholders.
  • Guide Development: Provides guidelines for developers on aspects like performance optimization, error handling, and security considerations.
  • Inform Testing: Defines what aspects need to be tested beyond basic functionality (performance testing, security testing, usability testing).

Steps​

  1. Identify NFR Categories:

    • Start with common quality attribute categories relevant to mobile apps:
      • Performance: Speed, responsiveness, resource usage (CPU, memory, battery).
      • Reliability: Stability (crash rate), availability (backend uptime), error handling, data integrity.
      • Usability: Ease of use, accessibility (WCAG compliance), learnability, user satisfaction.
      • Security: Authentication, authorization, data protection (in transit, at rest), vulnerability prevention.
      • Maintainability: Code quality, testability, deployability, modularity, documentation.
      • Scalability (Backend): Ability of the backend to handle increasing user load (indirect impact on app performance/reliability).
      • Portability/Compatibility: Supported OS versions (iOS, Android), device types (phone, tablet), screen sizes/orientations.
      • Compliance: Adherence to legal or industry regulations (e.g., GDPR, HIPAA if applicable).

  2. Brainstorm Specific NFRs within Categories:

    • Conduct brainstorming sessions involving the Architect, Tech Lead, Developers, QA, and Product Owner.
    • For each category, ask probing questions:
      • Performance: "How fast should the app start?", "How quickly should lists load?", "Should scrolling be perfectly smooth?", "What devices should we target for performance?", "Will it consume excessive battery?"
      • Reliability: "How often is it acceptable for the app to crash?", "What happens if the network is unavailable?", "How should errors be handled and reported?"
      • Usability: "Does the app need to support accessibility features (screen readers, dynamic font sizes)?", "Is offline mode required?"
      • Security: "What sensitive data are we handling?", "How will users log in?", "Are there specific encryption requirements?"
      • Maintainability: "How quickly should we be able to fix critical bugs?", "How easy should it be to add new features?", "What level of test coverage do we need?"
      • Compatibility: "Which minimum iOS and Android versions must we support?", "Does it need to work on tablets?"

  3. Gather Input from Stakeholders:

    • Discuss NFRs with the Product Owner and key business stakeholders. They often have implicit expectations about performance, reliability, and security.
    • Ask about business drivers: "Are users likely to abandon the app if it's slow?", "Are there legal requirements for data security?"

  4. Collect and Document Initial NFRs:

    • Create an "NFRs" page on your project wiki (Confluence).
    • Organize the collected requirements by category.
    • Write down each requirement as a clear statement, even if it's not yet fully quantified.
      • Initial Example: "The app should start quickly."
      • Initial Example: "The app should not crash often."
      • Initial Example: "User login credentials must be stored securely."
      • Initial Example: "The app needs to support screen readers."
      • Initial Example: "Support Android API 23+ and iOS 13+."

  5. Review and Refine:

    • Review the initial list with the team and PO.
    • Prioritize the NFRs – which ones are most critical for success?
    • Identify NFRs that need further clarification or quantification (this leads into Item 28 & 30).

This initial collection phase creates a shared awareness of the quality attributes expected from the application, setting the stage for more detailed definition and measurement.
