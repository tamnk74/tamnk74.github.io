Completing Item 14: Document 3rd Party Dependencies

Item: 14 | Architecture Definition | Architecture & Coding Guidance | PREPARATION (Sprint 0) | 1 | "Internal and external important 3rd party APIs, libraries, framworks, tools which being used are documented.<br>" | Maintain a wiki page listing all critical pub.devpackages (frompubspec.yaml) and all backend API endpoints with their purpose. | |

This guide explains how to document the important internal and external dependencies your Flutter application relies upon.

Why Document Dependencies?​

  • Visibility: Makes it clear what external components the application relies on.
  • Risk Assessment: Helps identify critical dependencies that might pose risks (e.g., unmaintained libraries, unstable APIs).
  • Onboarding: Helps new developers understand the tech stack and integrations.
  • License Compliance: Provides a basis for tracking licenses of third-party libraries.

Steps​

  1. Identify Key Dependencies:

    • External Libraries/Packages (pubspec.yaml): Review your pubspec.yaml file. Focus on important packages, not every single transitive dependency. Key ones often include:
      • State Management (Bloc, Riverpod, Provider)
      • Navigation (go_router, auto_route)
      • Networking (Dio, http)
      • UI Components (major UI libraries if used)
      • Local Storage (Hive, sqflite, shared_preferences)
      • Authentication (firebase_auth, specific OAuth libraries)
      • Core Utilities (intl, logger, freezed, json_serializable)
      • Platform Integrations (camera, location, permission_handler)
    • External APIs: Services your app calls directly over the network:
      • Primary Backend API (the main API gateway for your application).
      • Authentication Services (Firebase Auth, Auth0, Cognito).
      • Payment Gateways (Stripe, Braintree).
      • Analytics (Firebase Analytics, Mixpanel).
      • Crash Reporting (Firebase Crashlytics, Sentry).
      • Mapping Services (Google Maps API, Mapbox).
      • Other SaaS products (Push notifications, CMS, etc.).
    • Internal APIs: Other microservices or systems within your organization that the app's primary backend relies on (useful context even if the Flutter app doesn't call them directly).
    • Development Tools: Critical tools used in the development or CI/CD process (e.g., FVM, Codemagic, Fastlane, SonarQube).

  2. Create the Documentation:

    • Create a "Dependencies & Integrations" page on your team's wiki.
    • Use separate sections for "Flutter Packages," "External APIs," and "Development Tools."

  3. Document Each Dependency:

    • Flutter Packages:
      • Create a table listing the key packages from pubspec.yaml.
      • Include columns for:
        • Package Name: (e.g., flutter_bloc) - Link to pub.dev page.
        • Purpose: (e.g., "State Management")
        • Current Version: (e.g., ^8.1.3) - Note: This requires manual updates or automation.
        • License: (e.g., MIT) - Important for compliance.
        • Notes/Risk: (e.g., "Core dependency", "Consider alternatives if maintenance stops").
      • Automation: Consider scripts that can parse pubspec.lock to help keep versions and licenses up-to-date.
    • External/Internal APIs:
      • Create a table listing the APIs.
      • Include columns for:
        • API Name: (e.g., "Main Backend API Gateway")
        • Purpose: (e.g., "Provides core application data and functionality")
        • Owner/Provider: (e.g., "Internal Backend Team", "Google Firebase", "Stripe")
        • Documentation Link: Link to Swagger/OpenAPI spec or developer docs.
        • Environment Endpoints: List the base URLs for Dev, Staging, Prod.
        • Auth Method: (e.g., "JWT Bearer Token", "API Key")
        • Notes/Risk: (e.g., "Critical path dependency", "Rate limits apply").
    • Development Tools:
      • List key tools.
      • Include:
        • Tool Name: (e.g., "FVM - Flutter Version Management")
        • Purpose: (e.g., "Manages Flutter SDK versions per project")
        • Version: (e.g., "Latest stable")
        • Link: To official website/docs.

  4. Maintain the Document:

    • Review Regularly: Revisit this document quarterly or before major releases.
    • Update Process: Make updating this document part of the process when adding or removing significant dependencies (e.g., add a checklist item to the Definition of Done for relevant stories).
    • Dependency Updates: Establish a process for regularly checking for and applying updates to Flutter packages (e.g., run fvm flutter pub outdated monthly).
