Completing Item 42: Track Artifact Version per Environment

Item: 42 | Architecture Execution | Continuous Deployment | DEVELOPMENT (Sprint 1-N) | 1 | There is a way to track the artifact version deployed in each environment. | Use the pubspec.yamlversion (e.g.,1.0.0+1). Ensure the CI build number (e.g., from GitHub Actions) automatically increments the build number (+1). Tag the Git commit with the version number. | |

This guide explains how to implement a system for clearly identifying which version of your Flutter application artifact (.aab/.apk for Android, .ipa for iOS) is deployed to each environment (Development, Staging/QA, Production).

Why Track Artifact Versions?​

  • Troubleshooting: When a bug is reported in a specific environment (e.g., Staging), knowing the exact version helps pinpoint the relevant code changes and logs.
  • Verification: Allows QA and POs to confirm they are testing the correct build corresponding to a set of features.
  • Rollback Identification: Helps identify the specific "last known good" version needed for a rollback (Item 7).
  • Release Management: Provides clarity on what has been deployed where.

Steps​

  1. Establish a Versioning Scheme:

    • pubspec.yaml Version: Use the version: field in your pubspec.yaml file as the source of truth for your application's version. Follow Semantic Versioning (SemVer): MAJOR.MINOR.PATCH+BUILD.
      • MAJOR: Increment for incompatible API changes.
      • MINOR: Increment for adding functionality in a backward-compatible manner.
      • PATCH: Increment for backward-compatible bug fixes.
      • BUILD: Crucial for tracking. This number must be unique for every build/artifact generated. Often corresponds to the CI pipeline run number. It distinguishes different builds of the same semantic version (e.g., 1.2.0+55 vs. 1.2.0+56).
      • Example: version: 1.2.0+55
    • Management: Increment MAJOR.MINOR.PATCH manually (or via scripts) based on the nature of changes included in a release. The BUILD number should typically be incremented automatically by the CI/CD system.

  2. Automate Build Number Incrementing (CI/CD):

    • Configure your CI/CD pipeline (GitHub Actions, Codemagic, Jenkins, etc.) to automatically set the build number.

    • GitHub Actions Example:

      name: Build and Deploy

      on:
        push:
          branches: [main]
        workflow_dispatch: # Allow manual trigger

      jobs:
        build:
          runs-on: ubuntu-latest # Or macos-latest for iOS
          steps:
            - uses: actions/checkout@v3

            # Get version from pubspec.yaml (e.g., 1.2.0)
            - name: Get Package Version
              id: package_version
              uses: CumulusDS/get-package-version-action@v1.3.0
              with:
                path: ./pubspec.yaml # Path relative to repo root

            # Construct full version: 1.2.0+<GitHub Run Number>
            - name: Set Full Version
              id: full_version
              run: echo "::set-output name=version::${{ steps.package_version.outputs.version }}+${{ github.run_number }}"

            - name: Setup Flutter (using FVM)
              # ... FVM setup steps ...

            - name: Build Android App Bundle
              run: |
                fvm flutter build appbundle \
                  --release \
                  --build-name=${{ steps.package_version.outputs.version }} \
                  --build-number=${{ github.run_number }}
                # Add --dart-define flags for environment here if needed

            - name: Build iOS IPA (Example - needs macOS runner)
              if: runner.os == 'macOS'
              run: |
                fvm flutter build ipa \
                  --release \
                  --build-name=${{ steps.package_version.outputs.version }} \
                  --build-number=${{ github.run_number }}
                  # Add export options, etc.

            # ... Rest of deployment steps ...

            - name: Print Version Deployed
              run: echo "Deployed Version ${{ steps.full_version.outputs.version }}"

    • Explanation:

      • The semantic version (MAJOR.MINOR.PATCH) is read from pubspec.yaml.
      • The unique CI run number (github.run_number in this example) is used as the BUILD number.
      • These are passed to flutter build using --build-name and --build-number. Flutter embeds this information into the final artifact.

  3. Tag Git Commits on Release:

    • When a specific commit is built and submitted for production release, create a Git tag matching the version including the build number (e.g., git tag v1.2.0+55 <commit-hash>, git push origin v1.2.0+55).
    • This directly links the production artifact version back to the exact code it was built from. GitHub Releases can be automatically created from tags.

  4. Make Version Visible in Deployed Environments:

    • Firebase App Distribution / TestFlight: These platforms automatically display the version (1.2.0) and build number (55) of the uploaded artifact.

    • In-App Display (Optional but Recommended):

      • Use the package_info_plus package to read the version information embedded in the app.
      • Display the full version string (e.g., 1.2.0+55) somewhere accessible within the app itself (e.g., in a settings or about screen). This allows users and testers to easily report which version they are using.
      import 'package:package_info_plus/package_info_plus.dart';

      // ... somewhere in your init logic or settings screen ...
      PackageInfo packageInfo = await PackageInfo.fromPlatform();
      String appVersion = packageInfo.version; // e.g., "1.2.0"
      String buildNumber = packageInfo.buildNumber; // e.g., "55"
      String fullVersion = '$appVersion+$buildNumber';

      // Display fullVersion in the UI

    • Deployment Logs: Ensure your CI/CD deployment logs clearly state the full version string (MAJOR.MINOR.PATCH+BUILD) that was successfully deployed to each environment (Dev, Staging, Prod Submission).

  5. Document the Process:

    • Add a section to your SCM/Release Process documentation explaining:
      • The versioning scheme (MAJOR.MINOR.PATCH+BUILD).
      • How the build number is automatically generated (e.g., "from CI run number").
      • When Git tags are created (e.g., "on production release builds").
      • How to find the deployed version for each environment (e.g., "Check Firebase App Distribution," "Look at the About screen in the app," "Refer to CI deployment logs").

By implementing these steps, you create a clear and traceable link between your code, your build artifacts, and your deployed environments.
