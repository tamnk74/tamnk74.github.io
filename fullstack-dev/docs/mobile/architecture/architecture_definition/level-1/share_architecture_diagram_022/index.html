Completing Item 22: Share Overall Architecture Diagram

Item: 22 | Architecture Definition | Communication & Alignment | SETUP | 1 | The overall Architecture diagram is shared and explained to all project stakeholders. | Pin the high-level architecture diagram (showing Flutter app, BFE, 3rd party services) in the main developer chat channel and review it during kickoff. | |

This guide details how to create, share, and explain a high-level architecture diagram to ensure all project stakeholders (technical and non-technical) have a common understanding of the system's main components and interactions.

Why Share a High-Level Diagram?​

  • Common Understanding: Provides a visual overview that's easier to grasp than detailed documentation.
  • Context: Helps everyone understand how the Flutter mobile app fits into the larger ecosystem.
  • Scope Definition: Clarifies the boundaries of the system and its key external dependencies.
  • Onboarding: Gives new team members (including non-technical ones) a quick overview of the system landscape.

Steps​

  1. Define the Scope and Audience:

    • Audience: All project stakeholders - Developers, QA, PO, Project Manager, key business sponsors, potentially external partners.
    • Level of Detail: Keep it high-level. Focus on major components and interactions, not internal implementation details. The C4 Model's System Context Diagram or Container Diagram level is appropriate. Avoid showing individual classes or functions.

  2. Identify Key Components:

    • The Flutter Mobile App itself.
    • The primary Backend For Frontend (BFF) or API Gateway the app communicates with.
    • Major backend microservices (if relevant and known to stakeholders).
    • Key third-party services (Authentication provider like Firebase Auth/Auth0, Payment Gateway like Stripe, Analytics like Firebase Analytics, Push Notifications like FCM/APNS, Mapping Service like Google Maps).
    • Databases (represent as a single box, e.g., "Application Database").
    • External systems the backend might integrate with (e.g., CRM, ERP).
    • Types of Users (e.g., "Mobile User," "Administrator").

  3. Choose a Diagramming Tool:

    • Use a tool that allows easy creation and sharing:
      • Miro / Mural
      • Lucidchart
      • draw.io (diagrams.net) - Free
      • Excalidraw - Simple, hand-drawn feel
      • PlantUML / Mermaid (Code-based, good for version control)

  4. Create the Diagram:

    • Layout: Place the mobile app centrally or prominently.
    • Notation: Use simple boxes for components and arrows for interactions. Label boxes clearly. Label arrows with the purpose of the interaction (e.g., "Logs In via," "Fetches data using," "Sends analytics events to").
    • Example (Conceptual): 
      +----------------+       +-------------------+       +---------------------+
      | Mobile User    |<----->| Flutter Mobile App|<----->| Backend API Gateway |
      +----------------+       +-------------------+       +---------------------+
                                     |       ^                     |       ^
                                     |       |                     |       | Uses
                                     v       |                     v       |
                        +--------------+     |   +-----------------+   +-------------+
                        | Firebase     |     |   | Product Service |---| App DB      |
                        | Auth         |-----    +-----------------+   +-------------+
                        +--------------+                     |
                                     |                       | Sends events to
                                     v                       v
                        +--------------+          +-------------------+
                        | Firebase     |          | Firebase Analytics|
                        | Analytics    |          +-------------------+
                        +--------------+
    • Keep it Simple: Resist the urge to add too much detail. Aim for clarity over completeness at this level.

  5. Share the Diagram:

    • Embed: Embed the diagram directly into the main project overview page on your wiki (Confluence).
    • Pin: Pin a link to the diagram (or the wiki page) in the main project chat channel(s) (#proj-mobile-general, #proj-mobile-tech).
    • Repository: If using a code-based tool like PlantUML, commit the source file (.puml) and the generated image (.png) to your Git repository (e.g., in a /docs/architecture folder).

  6. Explain the Diagram:

    • Kickoff Meeting: Present and walk through the diagram during the project kickoff meeting. Explain what each box represents and how they interact.
    • Onboarding: Use the diagram as a central piece during onboarding sessions for all new team members (technical and non-technical).
    • Reference: Refer back to the diagram during discussions about new features or integrations to provide context.

  7. Maintain the Diagram:

    • Update the diagram if major components are added, removed, or interactions change significantly. Assign an owner (e.g., Architect) to keep it reasonably current. It doesn't need to reflect every minor change.
