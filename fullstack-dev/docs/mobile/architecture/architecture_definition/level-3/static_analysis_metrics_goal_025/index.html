Completing Item 25: Align on Static Analysis Metrics Goal

Item: 25 | Architecture Definition | Communication & Alignment | SETUP | 3 | "There is a goal for the metrics (Complexity, Duplications, Issues, Maintainability, Reliability, Comments, etc) related to static code analysis.<br>The goal is communicated to the team members." | Configure SonarQube/SonarCloud quality gates (e.g., "A" rating for Maintainability) and link the dashboard in the developer channel. | |

This guide explains how to define, communicate, and enforce goals for static code analysis metrics, typically using a platform like SonarQube or SonarCloud, for your Flutter project.

Why Define Static Analysis Goals?​

  • Beyond Linting: Goes beyond basic style checks (flutter analyze) to measure deeper code quality aspects like complexity, duplication, and potential bugs.
  • Objective Quality Measurement: Provides quantifiable metrics for maintainability, reliability, and security hotspots.
  • Early Feedback: Integrates into the CI/CD pipeline to provide developers with immediate feedback on the quality of their code changes within Pull Requests.
  • Track Trends: Allows the team to monitor code quality over time and identify degrading areas.
  • Enforce Standards: Quality Gates can automatically prevent merging code that doesn't meet the defined quality standards.

Key Metrics (Commonly Tracked by SonarQube/SonarCloud)​

  • Reliability (Bugs): Number of code locations likely to be bugs (e.g., potential null pointer exceptions, incorrect exception handling). Goal: 0 New Bugs. Rating (A-E). Goal: A Rating.
  • Maintainability (Code Smells): Number of issues related to code clarity, complexity, duplication, and adherence to good practices. Measured often as "Technical Debt" (estimated time to fix smells). Goal: 0 New Code Smells, < 5% Tech Debt Ratio. Rating (A-E). Goal: A Rating.
  • Security (Vulnerabilities & Hotspots): Potential security flaws (e.g., hardcoded secrets, insecure web calls) and security-sensitive areas needing review. Goal: 0 New Vulnerabilities, Review all New Security Hotspots. Rating (A-E). Goal: A Rating.
  • Code Coverage: (Covered by Item 24). Percentage of code executed by tests. Goal: > 80% on New Code.
  • Duplication: Percentage of duplicated lines/blocks across the codebase. Goal: < 3% or < 5% on New Code.
  • (Complexity): While not a direct Quality Gate metric usually, SonarQube measures Cyclomatic Complexity per method/function. High complexity often correlates with smells and bugs. Aim to keep complexity low through refactoring.

Steps​

  1. Set Up SonarQube/SonarCloud:

    • Ensure SonarQube (self-hosted) or SonarCloud (cloud-based) is set up and integrated with your CI pipeline (as described in Item 6).
    • Make sure analysis runs automatically on every Pull Request and merge to the main branch.

  2. Define the Quality Gate:

    • Focus on New Code: The most effective approach is to apply strict rules only to the code modified or added in a Pull Request ("New Code"). This prevents blocking merges due to pre-existing issues in legacy code while ensuring new contributions meet the standard.
    • Navigate to Quality Gates in your SonarQube/SonarCloud project/organization settings.
    • Create or Edit a Quality Gate: Configure conditions based on the metrics above, applied "On New Code":
      • Reliability Rating is not worse than A (or New Bugs is not > 0)
      • Maintainability Rating is not worse than A (or New Code Smells is not > 0)
      • Security Rating is not worse than A (or New Vulnerabilities is not > 0)
      • Security Hotspots Reviewed is 100% (or set New Security Hotspots > 0 as a warning)
      • Coverage on New Code is not < 80% (adjust percentage based on Item 24)
      • Duplicated Lines on New Code (%) is not > 3% (or 5%)
    • Overall Code: You can set less strict conditions for the overall codebase (e.g., Overall Coverage > 70%) as a longer-term goal, but focus the blocking gates on New Code.
    • Assign: Assign this Quality Gate to your Flutter project in SonarQube/SonarCloud.

  3. Communicate the Goals and Process:

    • Team Meeting: Dedicate time to explain the chosen metrics, the Quality Gate conditions (especially the "On New Code" focus), and why they are important (maintainability, fewer bugs, security).
    • Show the Dashboard: Walk the team through the SonarQube/SonarCloud dashboard. Explain how to interpret the results, especially within a Pull Request.
    • Link the Dashboard: Pin a link to the project's SonarQube/SonarCloud dashboard in the main technical chat channel and include it in the project's README/wiki.
    • PR Integration: Ensure SonarQube/SonarCloud analysis results (especially the Quality Gate status - Pass/Fail) are clearly visible directly within the Pull Request interface in GitHub/GitLab.

  4. Integrate into Workflow:

    • CI Failure: The CI build must fail if the SonarQube/SonarCloud Quality Gate fails. This prevents merging substandard code.
    • Developer Responsibility: Developers are responsible for checking the SonarQube report in their PR, understanding the issues raised, and fixing them before requesting final reviews or merging.
    • Review Process: Code reviewers should also check the Quality Gate status and glance at reported issues as part of their review.

  5. Monitor and Refine:

    • Regular Review: Briefly review the overall SonarQube dashboard during tech backlog refinement meetings (Item 138) to track trends.
    • Adjust Gates: If the Quality Gate proves too strict initially (blocking too many PRs) or too lenient, adjust the conditions based on team feedback and experience. The goal is continuous improvement, not paralysis.

By setting clear goals via Quality Gates and making the results visible, you encourage developers to write cleaner, more reliable, and more secure code from the outset.
